## 1. Purpose and scope

### 1.1 What it does

After a pull request is merged, `/sc:closeout <PR>` does five things, in this order:

1. **Truth check.** A script reads the pull request state first. Only a merged pull request goes on. For a merged one it also compares what the pull request held with what the merge changed, using a three-dot diff. It never decides from commit ancestry.
2. **Issue.** A model decides whether the pull request's issue is done: it reads the issue's own done-criteria against what the pull request and its linked pull requests delivered, and writes a verdict (`done`, `not_done` or `unclear_escalate`) into a fixed-shape file (ruling 32, section 5.2). The model investigates first (the issue's criteria, remaining items and later stages, comments, and the other open or merged pull requests that reference it) and lists what it checked in every verdict. Only a `done` verdict closes the issue, with one note that says why it is done, what merged and who merged it. A `not_done` verdict leaves the issue open, posts one short marked note of what remains, and hands back to the caller: the result carries the unmet criteria, so the orchestrator continues the work (ruling 36; the skill never starts it). `unclear_escalate` is only the result after the investigation, and is escalated. An already-closed issue is left alone. The words `Fixes`, `Closes` and `Refs` in the pull request body are read and printed as data (`links=`); they decide nothing.
3. **Work report entry.** It settles the issue's entry in the work report.
4. **Worker's Orca task.** It settles the Orca task of the worker that built the pull request.
5. **Result.** It prints one short, fixed-shape result. The orchestrator records it; a person reads it printed.

Each of the three items (issue, entry, task) ends with one stated final status or with an escalation that says why not. An item with neither fails the skill's own check (section 3).

"Completed" means merged. "Deployed" means verified in the place it runs. This version never writes "deployed" (section 5.5).

From the issue: making the merge; the wave 8 text of the orchestrator design (issue #655 owns it); the draft additions A to E to that design; anything else in Jay's repository, such as its pull request sweep.

### 3.2 What the orchestrator passes, and what a hand run needs

| Input | From the orchestrator | A hand run |
|---|---|---|
| The pull request | the number it merged in wave 7, or found already merged by a person | typed |
| The issue | the issue it is working (`--issue`) | found from the pull request's closing references and body (section 4.4) |
| The worker's Dispatch | the Dispatch id in its state file (`--dispatch`) | none: the task is found by its title `<owner>/<repo>#<N>` (section 5.4) |
| The entry key | its `<key>` (`--entry-key`) | derived from the repo and the issue number |
| The done verdict (D19) | none: the skill's own model session writes it; wave 8 calls the skill and passes nothing | none: the skill's model session writes it |

The caller must run it inside a checkout of the `origin` repo (wave 1 of the orchestrator already runs from `<checkout>`), with `gh` logged in, `git` and `jq` on the path. `orca` and a bound Orca Run are needed only for the task item; without them that item is `escalated` and nothing else changes.

Where the orchestrator calls it: after the merge (wave 7) and after the orchestrator's own close of the issue, if its wave 8 still has one, and before the report refresh. The exact wave 8 text is the 655 side's. A result with `issue.handback: remaining` is the orchestrator's cue to continue the work that was not done (it records what remains, updates the plan with `/sc:issue --plan` and starts a new worker through the same waves; ruling 36); this skill returns the cue and does none of that. Both orders are harmless: a closed issue is left alone and an entry already moved is `already_final` (section 6). The orchestrator calls it as a skill (`Skill sc:closeout-protocol`), as the 655 draft's wave 8 does. The scripts it runs, in this order, are:

```text
branch-landed.sh <PR>                                          one line, exit 0 only for MERGED
settle.sh issue    <PR> [--issue N] [--match M]                the find pass: no --verdict, one line
settle.sh evidence <PR> --issue N                              one line; writes the evidence file (read only)
settle.sh issue    <PR> --issue N --verdict F [--what TEXT] [--match M]    one line
settle.sh entry    --key <key> [--issue-open] [--match M]      one line (--issue-open when the issue item did not end closed)
settle.sh task     [--dispatch ID | --title T] [--match M]     one line
settle.sh check                                                reads the three lines on stdin
```

Between `evidence` and the second `issue` call the skill's model session reads the evidence file and writes the verdict file (section 5.2, `refs/done-check.md`). A model is needed there (and for the note's one sentence) and nowhere else, so the scripts alone can no longer settle the issue item. A call of `settle.sh issue` without `--verdict` on an open issue with no marker note that counts (written by an author who can already close the issue, 5.2 step 3.2) gives `escalated why=no_verdict` and writes nothing (this is also the find pass: its line names the issue number). An orchestrator session that wants to avoid the skill call must itself do what the skill does there: run `evidence`, read it following `refs/done-check.md`, write the verdict file from the stub template in the temporary directory that `evidence` names, and pass `--verdict` and `--dir`. That is a permission and not a requirement; the 655 draft does not use it (it calls the skill and, on failure, repeats once, escalates and has a person run the skill), and a direct call with no verdict is `no_verdict`, never a close.

`--match` carries the `match=` value of the `MERGED` line. With `differs`, each step prints `escalated why=merge_differs` and writes nothing (section 4.4), so the rule lives in the script, not in a model's reading.

A skill inside a skill is itself UNVERIFIED (risk K17 of the orchestrator design, `docs/designs/orchestrator.md` line 891; U6 below), which is why the scripts carry every status and every write, and the skill adds only the two pieces of judgment (the done verdict and the note's sentence) and the printing (D6). The contract of ruling 19 therefore reads: the orchestrator may run the scripts itself, but then it supplies the verdict itself; without one the issue item is `escalated why=no_verdict`.

### 3.3 The result

The result is printed last, also after a stop, as one YAML block (the style of the return contract of `sc-issue-protocol`, `SKILL.md:105-150`). `templates/result.md` holds its fixed shape.

```yaml
closeout:
  pr: <number or null>
  status: complete | partial | stopped
  verdict: MERGED | OPEN | CLOSED | NONE | UNKNOWN
  merged_by: <name or null>
  merge_commit: <first 7 characters or null>
  match: same | differs | unchecked | null
  pr_links_issue: closing | refs | none | null
  issue: {number: <number or null>, status: <word>, detail: <token>, note: <posted | already_there | none | null>,
          handback: <remaining | none | null>, remaining_file: <path or null>, remaining: [<one line per unmet criterion>],
          handback_text: <the fixed sentence of section 5.6 or null>}
  entry: {key: <key or null>, status: <word>, detail: <token>}
  task:  {id: <id or null>, status: <word>, detail: <token>, dispatch: <state read or null>}
  escalations: ["<item>: <one sentence: why not, and the one next step>"]
  stop: <STOP code or null>
```

- `<word>` is one of the four final status words (section 5.1).
- `issue.note` says what became of the closing note. Its closed set of values is the `note=` field of the `ISSUE` line (section 5.2 step 3): `posted` (this run posted the note: the done note, or the not-done note of a `not_done` verdict), `already_there` (a note with the marker was already on the issue, so none was posted), `none` (no note was written or found: the issue was already closed, for example by the merge keyword, or the item escalated before the note was posted), and `null` (the run stopped before the issue item, so there is no line). The orchestrator records this value as the "comment" of the draft part D requirement (section 12.2, row 7).
- **The hand-back (ruling 36, D22).** `issue.handback` tells the caller whether it must continue the work. Its closed set: `remaining` (only when `issue.status` is `settled` and `issue.detail` is `left_open`: the done-check found the issue not done, left it open with its note, and the orchestrator takes the rest), `none` (every other issue line: a `done` and its close, an issue already closed, a rerun after a failed close, and an escalation of any kind, `unclear` included), and `null` (the run stopped before the issue item). `issue.remaining_file` is the path of the verdict file `done-verdict.md` in the private temporary directory of D20 when `handback` is `remaining`, else `null`. `issue.remaining` is the unmet criteria, one line for each criterion whose delivered word in the verdict file is `partly` or `not_delivered`, in the order of the file and in the two forms of the not-done note (`<criterion> (delivered in part by PR #<n>)` or `<criterion> (no pull request yet)`), with no cap (the comment lists at most 10, the result lists all); it is `[]` when `handback` is not `remaining`. `issue.handback_text` is the fixed sentence of section 5.6 when `handback` is `remaining`, else `null`, so a person reading the printed block is told what happens next. All four values are copied, with no judgment, from the `ISSUE` line (`how=left_open`, `remaining=<k>`) and from the verdict file that the script already checked. The skill does not delete the temporary directory (the operating system's temporary space does); its path is in the result, and a caller that needs the criteria later copies them into its own state at once. A `done` run and an `unclear_escalate` run carry no hand-back (`none`, `null`, `[]`, `null`).
- `status: complete` means no item is `escalated`. `partial` means at least one is, and each has its sentence in `escalations`. `stopped` means the verdict is not `MERGED` or a STOP code fired; no item was written, the three items print `null` and `stop` says why.
- A person sees the block printed. The orchestrator records it in the entry and in its state file. The same block is the only output; there is no second summary.
- The block never names the agent or the model (D8, section 10 row 6).
- The check: before printing, `settle.sh check` reads the three item lines. An item with no status word, or `escalated` with a `why` token that has no sentence in the table of section 5.6, makes it print `CHECK_FAIL <item>` and exit 2; the skill then sets that item to `escalated` with `why=not_reached` and prints `status: partial`. An item is never silent.

## 4. The truth check script

`scripts/branch-landed.sh <PR>` is Jay's script, adapted (section 2.2). It is the only place that decides whether a pull request merged and what merged. It changes nothing: its only write is `git fetch`, which touches objects and `FETCH_HEAD`, never a branch, the index or the working tree.

### 4.1 The order, and what it never does

1. **Arguments and origin.** Check the argument and parse `origin` into `owner/repo` (Jay's lines 34-45, kept). A URL for another repo is refused.
2. **State.** One read: `gh pr view <N> --repo <R> --json number,state,mergedAt,mergedBy,mergeCommit,baseRefName,headRefOid,commits,url`. The verdict comes from this and nothing else.
3. **Held versus merged, only for `MERGED`.** A three-dot comparison against the base (section 4.4). It sets `match=` and never the verdict. If any step of it fails, `match=unchecked`.

It never uses commit ancestry (`git merge-base --is-ancestor`, `git branch --merged`, `git rev-list`, `git log` ranges) and never a two-dot diff of a branch tip against the base. Reason, from Jay's header (`branch-landed.sh:4-9`): a squash merge rewrites the commits and the branch is deleted, so ancestry calls every landed branch abandoned.

### 4.2 Arguments

`<PR>` is a number, `#<number>` or `https://github.com/<owner>/<repo>/pull/<number>`. Only the number is used. For a URL, the owner and repo in it must equal `origin`'s, else `UNKNOWN reason=foreign_repo`. Every `gh` call carries `--repo <R>` (the fork-safety scan of `tests/skills/test_issue_worker_agents.py:45` is applied to the script and the skill). The script reads no stdin and asks nothing, as `finish-merge.sh` states (line 28).

### 4.3 Results: tokens, exit codes, one stdout line

Exactly one stdout line. The first word is the token; the rest are `key=value` fields separated by one space, and no value has a space. Details go to stderr only (the style of `finish-merge.sh:20-24`, whose failure is one token and exit 2).

| Case | Stdout line | Exit |
|---|---|---|
| State `MERGED` | `MERGED pr=661 by=<login or unknown> merge=<40 hex> base=<branch> head=<40 hex> match=<same, differs or unchecked> url=<url>` | 0 |
| State `OPEN` | `OPEN pr=<N> url=<url>` | 1 |
| Not readable, bad arguments, no origin, another repo, no `jq`, a bad JSON answer | `UNKNOWN reason=<usage, no_origin, foreign_repo, no_jq, gh_failed or bad_json>` | 2 |
| `gh` says there is no such pull request | `NONE pr=<N>` | 3 |
| State `CLOSED` | `CLOSED pr=<N> url=<url>` | 4 |

The five tokens and the exit codes 0, 1, 2, 3 and 4 are Jay's (`branch-landed.sh:14-16,30,42,63,72,75,77`). Exit 0 only for `MERGED`, as in line 16. Today `gh` answers a missing pull request with `GraphQL: Could not resolve to a PullRequest with the number of 999999` and exit 1 (command run 2026-11-19); the script maps that text to `NONE` and every other failure to `UNKNOWN reason=gh_failed`. A closed pull request that was not merged has state `CLOSED` and `mergedAt` null (PR 663 on this repo is one).

### 4.4 The held-versus-merged comparison

The question: is what the merge changed the same set of files that the pull request held? The check compares file names, not contents, because a squash merge on a moved base can legitimately differ in content from the head.

1. `git fetch --quiet origin <base> refs/pull/<N>/head`. GitHub keeps `refs/pull/<N>/head` after the branch is deleted: read 2026-11-19, the branch of PR 660 is gone from `origin` and `git ls-remote origin refs/pull/660/head` still answers; the same holds for the 11 other merged pull requests checked.
2. `held` is the three-dot diff against the base as it was just before the merge: `git diff --no-renames --name-only <merge>~K...<head>`, where `<head>` is `headRefOid`.
3. `merged` is the change the merge made, one commit at a time: for each of the K newest commits `c` on the base, `git diff-tree -r --no-renames --name-only <c>^1 <c>` (a commit against its own first parent, which is exact and is not the stale-branch comparison Jay warns of at `branch-landed.sh:18`). The union is `merged`.

Both commands carry `--no-renames` on purpose. `git diff` detects renames by default and `git diff-tree` does not, so without the flag a pull request that renames a file gives `held` with only the new name and `merged` with the old and the new name, the sets never match, and decision D17 would hold all three writes for ever. This was reproduced in a scratch repository (git 2.47.3): a squash merge of a branch that renames `old.txt` to `new.txt` and edits `keep.txt` gave `held` = {`keep.txt`, `new.txt`} and `merged` = {`keep.txt`, `new.txt`, `old.txt`}. With `--no-renames` on both, both sets are {`keep.txt`, `new.txt`, `old.txt`}: a rename is listed as a delete and an add, on both sides. The flag is chosen over `-M` on both sides because a `-M` list depends on a similarity threshold applied separately to each command, while `--no-renames` depends on nothing. A deleted-file squash also gave equal sets.
4. `K` is 1 for a squash merge or a merge commit. If the sets differ and the pull request has more than one commit (`commits` in the state read), the script tries `K` equal to that number, which is what a rebase merge leaves. Equal sets give `match=same`; otherwise `match=differs`. Any failed step gives `match=unchecked`.

Checked on this repository, read-only, 2026-11-19: the steps above (with `K` = 1, and without `--no-renames`, which this cycle added) were run by hand over the 12 newest merged pull requests (PR 649 to 667): 8 squash merges (one parent) and 4 merge commits (two parents), 1 to 9 commits each, 2 to 181 files. All 12 gave equal sets (`same`). That survey did not include a pull request that renames a file (a later review found none of the 14 newest has one), so it says nothing about renames; the rename case was added to 4.5 and to the tests and was reproduced in a scratch repository (above). No rebase merge was among the 12, so the second try is untested (U2).

What `match` changes: `same` and `unchecked` change nothing. `differs` stops the writes: each `settle.sh` step, given `--match differs`, prints `escalated why=merge_differs` and writes nothing (decision D17, section 1.3; the sentence is in section 5.6). Reason: the first line of the issue is that closeout "checks that what merged is what was asked for"; closing an issue over a merge that is not what was asked would be the wrong write.

## 5. Settling the three items

`scripts/settle.sh` has three settle steps, `issue`, `entry` and `task`, plus `evidence` (a read-only step that gathers what the done-check reads, section 5.2) and `check`. Each settle step reads the current state first and writes only if the state is not already final. Each settle step prints one stdout line (`ISSUE`, `ENTRY`, `TASK`), exit 0 when the status is `settled`, `already_final` or `none_found`, exit 1 when it is `escalated`, and for bad arguments `SETTLE_FAIL <reason>` with exit 2 (the failure style of `finish-merge.sh:43-48`). The line is `<ITEM> <status> <key>=<value> ... how=<token>` or `... why=<token>`; the result's `detail` is that `how` or `why` token, and the result's `issue.note` is the `note=` value of the `ISSUE` line. Statuses come from the tables below, not from a model: the model writes a verdict file and a sentence, and the script turns the verdict word and the read-backs into a status (D6).

### 5.1 The four final status words

| Word | Meaning | Written by this run? |
|---|---|---|
| `settled` | The item is now in its final state because of this run. | yes |
| `already_final` | The item was already in its final state; nothing was written. | no |
| `none_found` | The surface was reachable and holds no record for this pull request, so there is nothing to settle. | no |
| `escalated` | The item could not be settled. A reason token and one sentence say why and give the one next step. | no |

`none_found` is a stated result, not a skip: it says the place was looked at. A surface that could not be looked at is `escalated`, never `none_found`. This is the rule that keeps a hand run on an ordinary pull request honest: with no Orca Run or no report command, those items say so. An issue that the done-check finds not done is `settled`, not `escalated`: it stays open with its one marked note, which is its final state for this run (`how=left_open`, section 5.2 step 4), and the result hands back to the orchestrator, which continues the work (ruling 36); `escalated` is kept for a case where a person must decide something.

### 5.2 The issue (`settle.sh evidence`, and `settle.sh issue <PR> [--issue N] [--verdict F] [--what TEXT]`)

1. **Which issue.** On GitHub a pull request number is also an issue number, and a reference can name another repository, so a number counts only after two filters.
   - *Where candidates come from, in this order:* `--issue`; else the rows of the pull request's `closingIssuesReferences`; else the numbers in the pull request body written as `<keyword> #N`, `<keyword> <owner>/<repo>#N`, `<keyword> <issue URL>`, or as `#N`, `<owner>/<repo>#N` or an issue URL with no keyword (`<keyword>` is one of GitHub's closing words or `Refs`).
   - *Filter 1, the repository.* Only a reference whose repository equals the pull request's own repository `<R>` (which is the `origin` repo, D4) counts. A `closingIssuesReferences` row counts only when its `repository` (`owner.login` and `name`, both present in the rows read on 2026-11-19) equals `<R>`; a body reference written with another `<owner>/<repo>` or another repo's URL never counts. A cross-repository reference is never a candidate for a close. A bare `#N` means `<R>`.
   - *Filter 2, an issue and not a pull request.* Each remaining candidate, including a number given with `--issue`, is read with `gh api repos/<R>/issues/<N>`. An object that has a `pull_request` key is a pull request (the REST issues endpoint returns pull requests and marks them that way; read 2026-11-19: the object of PR 661 has the key and the object of issue 651 does not): it is dropped from the candidates, and a `--issue` number that is a pull request gives `escalated why=not_an_issue`. The number of the pull request itself is dropped without the call. A failed read gives `escalated why=issue_lookup_failed`.
   - *Result.* Exactly one candidate left: it is the issue. None left: nothing qualifies, the issue item is `escalated why=no_issue_named` (error code `E-NO-ISSUE`, section 3.4) and nothing is written to any issue. More than one: `escalated why=several_issues`. Because a state of `MERGED` can only be a pull request, step 3 only ever sees `OPEN` or `CLOSED`.
2. **The link is read as data and decides nothing.** `links=closing` when the issue is in `closingIssuesReferences` or the body has a closing keyword for it; `links=refs` when the body mentions it without one; `links=none` when it appears nowhere (possible only with `--issue`). The value is in the line and in the note. Matching `Fixes`, `Closes` or `Refs` no longer decides whether anything is closed (ruling 32): a closing keyword does not make an issue done, and `Refs` does not make it not done. The words only help to find which issue to judge (step 1) and are one fact the model reads (step 4).
3. **Read, then write: two guarded calls, in this order (D7).**
   1. *Read.* `gh issue view <N> --repo <R> --json state,stateReason,comments` (each comment object carries `body`, `createdAt`, `author.login` and `authorAssociation`; read on issue 569 of this repository, 2026-11-19: `MEMBER`). `CLOSED`: `already_final how=already_closed note=none`, with `reason=<stateReason>` read as data (`COMPLETED` for issue 651, read 2026-11-19); no write, no note, and the issue is never reopened. `OPEN`: go on.
   2. *The gate before any write (ruling 32).* Nothing below this point is written unless the issue is judged done, except the one marked note of a `not_done` verdict (step 4). The two markers are whole strings and never match each other: the done marker `<!-- sc:closeout pr=<PR> -->` and the not-done marker `<!-- sc:closeout pr=<PR> verdict=not_done -->`. **A marker counts only on a comment by an author who can already close the issue.** Two tests, in this order. First, the comment's `authorAssociation` is `OWNER`, `MEMBER` or `COLLABORATOR`: a cheap filter, so no call is made for a comment by any other author (`NONE`, `CONTRIBUTOR`, `FIRST_TIME_CONTRIBUTOR` and the rest). Second, the author's login (the comment's `author.login`) holds a role that can close an issue: `gh api repos/<R>/collaborators/<login>/permission --jq .role_name` prints `admin`, `maintain`, `write` or `triage`. Read on this repository on 2026-11-19: an account with `admin` printed `admin`, one with `maintain` printed `maintain` (its `permission` field says `write`, which is why the finer `role_name` is the field used), and two organisation members who write comments as `MEMBER` printed `read`; `triage` was not read on any account (UNVERIFIED, U5). `triage` is in the list on purpose: a triage account can close an issue itself, so its marker extends nobody's power, and the account that runs the closeout may be one. The permission is read once per distinct author in a run. **What a failure does: two answers make the marker ABSENT, and any other failure stops the item.** (a) The lookup answered, and the answer is that the author cannot close the issue: a `role_name` of `read`, `none` or any other value; an empty `role_name` (a bot login answered `none` with an empty role and exit 0, read); or an HTTP 404 (a login that is not a user, or no longer a collaborator: `gh` exits 1 and prints `(HTTP 404)`, read). A comment with no author login is absent too, since there is no one to look up. The marker is treated as absent and the run goes on as if it were not there. (b) The lookup failed in any other way: a non-zero exit that is not that 404 (a network error, a rate limit, an HTTP 5xx), or a reply that is not JSON with a `role_name` string. Then the item is `escalated why=issue_lookup_failed` and nothing is written (no verdict is read, no note, no close), exactly as for an unreadable timeline; a failure for the author of any comment that passes the first filter and holds the done marker stops the item. The reason: a failed lookup says nothing about the author, so reading it as absent would switch off the reopen guard below for a real closeout marker, and a rerun could close again an issue that a person reopened (review 6, A6-01). The test reads the role of the comment's author and not the login that runs the closeout, so it keeps working when a person's login and the orchestrator's login differ (section 6). A marker that fails either test, by an answer of case (a), is treated as absent everywhere in step 3 and step 4: for the done marker, for the not-done marker, for the guard of write 1 and for both read-backs. The stop of case (b) is made once, at this gate, for a done marker: write 1 is reached only after the author of every done-marker comment that passes the first filter has been looked up (the answers are kept for the run), so it needs no second stop. For a not-done marker, and for the read-back of a note the closeout has just posted, a lookup that fails is read as absent, which costs at most one more note and never a close. The marker format is public, so anyone could type it; the two tests mean a typed marker skips the done-check only if its author could close the issue directly anyway. Two cases pass the gate to the writes of a `done`. (i) A comment of the issue, written by such an author, already holds the marker `<!-- sc:closeout pr=<PR> -->`: an earlier run judged the issue done and posted its note, so no new done-check is made and no verdict is needed; but if the issue's timeline holds a `reopened` event later than that comment, a person reopened it after the closeout. The timeline is read in full, every page and not the first one: `gh api --paginate "repos/<R>/issues/<N>/timeline?per_page=100" --jq '.[] | select(.event=="closed" or .event=="reopened") | [.event, .created_at] | @tsv'` (the flags are in `gh api --help` of `gh` 2.103.0, and the call was run on issues 569 and 571 of this repository), which prints one tab-separated row of the event name and its UTC time for each `closed` and `reopened` event of the whole timeline. A single page holds the oldest 100 events and a reopen is among the newest, so the call is never made without `--paginate`. Each `reopened` time is compared with the comment's `createdAt` (both are UTC times written `YYYY-MM-DDTHH:MM:SSZ`, so text order is time order). A `reopened` time after the comment: the item is `escalated why=reopened`, nothing is written, and the issue is not closed again (D21). A read that fails (a `gh` exit other than 0, or a row that is not two fields): the item is `escalated why=issue_lookup_failed`, nothing is written. Otherwise go to write 2 with `note=already_there`. (ii) No done marker that counts (every lookup above answered): the issue must have a `done` verdict file passed with `--verdict` (step 4). With no file or a malformed one the item is `escalated why=no_verdict`; with `unclear_escalate` it is `escalated why=unclear`; in both nothing is written. With `not_done` the item is `settled how=left_open` and the only write is the one marked note of step 4 (no close, ever), and the result hands back to the caller (step 4, ruling 36). With `done` the run goes on to write 1.
   3. *Write 1, the note, guarded by the marker.* If the marker is already on the issue (on a comment that counts, step 3.2), the note is not posted again (`note=already_there`); a marker typed by another author does not stop the note. Otherwise `gh issue comment <N> --repo <R> --body <note>` (the note ends with the marker as its last line), then the comments are read back and must hold the marker on a comment that counts (`note=posted`; the account that runs the closeout must therefore itself pass both tests of step 3.2, U5). A failed post or a missing marker: `escalated why=note_failed`, and the issue is not closed.
   4. *Write 2, the close, guarded by the state.* The state is read again just before the call; if it is now `CLOSED` (a person closed it in the meantime), nothing is written: `already_final how=already_closed` with the `note=` value from write 1. Otherwise `gh issue close <N> --repo <R> --reason completed` (flag verified in `gh issue close --help`, 2026-11-19; no `--comment`, so `gh` makes one call), then a read back. Closed: `settled how=closed_now`. Not closed: `escalated why=close_failed`; one note is on the open issue, and the rerun finds the marker, posts nothing and closes.
   5. *The line.* `ISSUE <status> n=<N> links=<closing|refs|none> how=<closed_now|already_closed|left_open> note=<posted|already_there|none>`; a `why` replaces `how` when escalated. `how=left_open` is the `not_done` path: the issue stays open and its not-done note is on it (`note=posted`, or `note=already_there` on a rerun), and the line ends with `remaining=<k>`, the number of unmet criteria (at least 1), which is on no other `ISSUE` line (the hand-back, step 4). `note=` is on every `ISSUE` line: `none` when no note was written or found (an already closed issue, or an escalation before any note was posted: `no_issue_named`, `several_issues`, `not_an_issue`, `issue_lookup_failed` from step 1, `merge_differs`, `no_verdict`, `unclear`, `note_failed`), `posted` or `already_there` after `close_failed`, and `already_there` for `reopened` and for an `issue_lookup_failed` that came from the guard's timeline read or from the permission lookup of a done marker's author (the marker note is on the issue). The result block copies it into `issue.note` (section 3.3).
4. **The done-check (ruling 32, D19): a model decides whether the issue is done, before anything is written.** It runs for an open issue with no marker note (step 3.2), after step 1 found the issue.
   - *The evidence, read by a script.* `settle.sh evidence <PR> --issue <N>` makes a private temporary directory (D20: `mktemp -d` under `${TMPDIR:-/tmp}`, named `sc-closeout-<owner>__<repo>__<PR>.XXXXXX`, mode 700, outside the checkout) and writes `evidence.md` in it from this fixed list of read-only calls and nothing else: (1) `gh issue view <N> --repo <R> --json title,body,state,comments`: the issue's body (first 20000 characters) and its first 30 comments; (2) `gh pr view <PR> --repo <R> --json body,files,changedFiles,baseRefName,mergedAt,closingIssuesReferences`: the pull request's body and up to 100 file names, with the total `changedFiles`; (3) the linked pull requests, from two sources joined: `gh api "repos/<R>/issues/<N>/timeline?per_page=100"`, taking the `cross-referenced` events whose `source.issue` has a `pull_request` key and the same repository, and `gh pr list --repo <R> --state all --search "<N>" --limit 10 --json number,state,mergedAt,baseRefName` (the search matches the number as text, so it only proposes candidates); (4) the open pull requests that name the issue, `gh pr list --repo <R> --state open --search "<N>" --limit 10 --json number,baseRefName,headRefName`; (5) for at most 10 pull requests in all (the target first, then merged ones, then open ones) `gh pr view <n> --repo <R> --json state,mergedAt,baseRefName,body,files,changedFiles`, body cut at 2000 characters and at most 100 file names each; (6) the times of the `closed` and `reopened` events, from every page of the timeline: the same filtered `gh api --paginate ... --jq` read as the reopen guard of step 3.2, which keeps only those two kinds of event, so it is small and has no cap and is not counted in `events=`. A failure of that read (a `gh` exit other than 0) is `EVIDENCE fail why=gh_failed`: a reading error, never a truncation. The file starts with `issue: <owner>/<repo>#<N>` and `pr: <PR>`, then holds, for each pull request read in items (2) and (5), a header line `PR #<n> state=<OPEN|CLOSED|MERGED> files=<listed>/<total> files_truncated=<yes|no>` followed by one `file: <name>` line per listed file (`files_truncated=yes` when `changedFiles` is more than the names listed), so that the script can check a verdict against it (below). The line it prints is `EVIDENCE ok prs=<k> comments=<c> events=<e> truncated=<yes|no> dir=<path>`, `truncated=yes` when any cap cut something, or `EVIDENCE fail why=gh_failed` with exit 1; `dir` is the temporary directory. The skill does not delete the directory (the operating system's temporary space does); it holds issue and pull request text, so it is private (mode 700) and is never posted. It writes nothing to GitHub and nothing in the checkout.
   - *The verdict, written by the model.* The skill's model session reads `evidence.md` and `refs/done-check.md` and nothing else (it runs no `gh` of its own, so the bound is the script's). It copies `templates/done-verdict.md` to `done-verdict.md` in the temporary directory that the `EVIDENCE` line names (`dir=`; stub first) and fills it in place. The fixed shape, one key per line:
     ```text
     verdict: done | not_done | unclear_escalate
     issue: <owner>/<repo>#<N>
     pr: <PR>
     checked:
     - [<issue_body | issue_comments | target_pr | linked_pr | other_pr | later_stage | remaining_item | timeline>] <the number or name read> | <what was found there, one line>
     criteria:
     - [<fix_approach | test_plan | acceptance | done_when | other>] <the issue's own criterion, short> | <delivered | partly | not_delivered | unknown> | <PR #<n>: <file>, <file>; PR #<m>: <file>, or none>
     unsettled: <only with unclear_escalate: what could not be settled after the investigation>
     question: <only with unclear_escalate: the one question for a person>
     reason: <one plain sentence, at most 40 words, that the closing note quotes>
     ```
   - *What the model must do (the text is `refs/done-check.md`, the judgment file): investigate first, then decide.* It always reads, in the evidence file, the issue's own done-criteria (Fix approach, Test plan, acceptance criteria, "Done when" list; an issue with none of these gets one criterion, its title and first paragraph, with source `other`), the issue's remaining items and the later stages it names, the issue's comments, the target pull request, the pull requests that are linked to it, and the other open or merged pull requests that reference the issue. It lists what it read under `checked:` in every verdict, not only in the unclear one: each place, with the number or name and what was found there; every verdict must list at least the issue body, the issue comments, the target pull request and the other pull requests (the last as "none found" when there are none). Then it writes `done` only when every criterion is `delivered`, with a pull request number and file names, by the target pull request or by a linked pull request that is merged. For a multi-part issue (the `#571` pattern: Parts A, B and C, one pull request per part) a pull request that delivers one part gives `not_done` while another part is still open or has no pull request; the remaining items and the criteria that are `partly` or `not_delivered` say what is left. A `reopened` event after the merge counts against `done`. `unclear_escalate` is only the result after all of that, when the model still cannot tell (a criterion that cannot be checked from files, or `truncated=yes` with criteria not shown delivered by the pull requests that were read): it then fills `unsettled:` and `question:`. It is never the first answer to a `Refs` link or to a multi-part issue. Never quote a pull request title, never name the agent or the model, no em or en dashes, people by name.
   - *What the script does with it* (`settle.sh issue <PR> --issue <N> --verdict <file> --dir <dir>`; `--dir` is required with `--verdict` and is the `dir=` of the `EVIDENCE` line). First the shape check, which refuses the file as `no_verdict` if any of these fails: the first key is `verdict` with a word of the closed set; `issue:` and `pr:` equal the call's (so a stale file is refused); `checked:` has lines of a closed set of place kinds, each with what was found, and holds at least the kinds `issue_body`, `issue_comments`, `target_pr` and `other_pr` (the last may say "none found"), whatever the verdict; `criteria:` has at least one line with the four parts, a source and a delivered word from the closed sets, and one or more `PR #<n>: <file names>` parts separated by `;`, or `none` (a file name that holds a comma or a semicolon cannot be cited, so the model cites another file); `done` needs every criterion `delivered` with a `PR #<n>`, `not_done` needs at least one `partly` or `not_delivered`, `unclear_escalate` needs a non-empty `unsettled:` and a non-empty `question:`; `reason:` is one non-empty line of at most 40 words; no text of the file contains the target pull request's title (case-insensitive), a name from `scripts/deny-names.txt` (D20), or U+2014 or U+2013. **Then the cross-check against the evidence**, which needs no judgment and is also a refusal as `no_verdict` when any of it fails. It reads `<dir>/evidence.md`, which must exist, be readable and name the same issue and pull request as the call (a missing, unreadable or mismatched evidence file refuses the verdict, so a stale or foreign evidence file proves nothing). (a) Every `PR #<n>` cited in a criterion is the target pull request or has a header line in `evidence.md` (it was read); in a `done` verdict it must have `state=MERGED` there, so an open pull request, or one the evidence does not hold, cannot deliver a criterion. (b) Every file name cited with a pull request is one of the `file:` lines of that pull request in `evidence.md`, unless its header says `files_truncated=yes` (then the names of that pull request are not checked). (c) The number on a `target_pr` or `linked_pr` line of `checked:` has a header line in `evidence.md`. (d) A criterion marked `delivered` with `none` instead of a pull request is refused, in any verdict. The reason of a refusal (which check, which number or file) goes to stderr, with the other details of the script (section 4.3 gives the style). These checks prove that the pull requests and numbers a verdict cites exist in the evidence the script read, and that its file names do for a pull request whose evidence list is complete; for a pull request whose list is truncated (check (b)) the file names are not checked at all. They do not prove that the criteria it lists are the issue's real ones, or that a `delivered` claim is true (12.1). Then the table, which is the only place a status comes from: `done` goes to the two guarded writes of step 3 (`settled how=closed_now`, or `already_final` if a person closed it in the meantime); `not_done` is not an escalation: it posts the one marked not-done note (below) and gives `settled how=left_open`, and never closes; `unclear_escalate` gives `escalated why=unclear`; a missing or malformed file gives `escalated why=no_verdict`; for these last two nothing is written to the issue.
   - *The `not_done` path, in detail.* The issue stays open and its item has a stated final status: `settled how=left_open`. Why `settled` and not a new word: `settled` means the item is in its final state for this run, and an open issue with one note saying what remains is exactly that; `escalated` is kept for a case where a person must decide something, which a `not_done` issue is not. The four status words and the closed set of `how` and `why` tokens stay; the only additions are `how=left_open`, the not-done marker, and (the hand-back, below) the `remaining=<k>` value of the line and the result fields; no status word or token is added. The note (`templates/not-done-note.md`, stub first) reads: "A pull request merged: `<owner>/<repo>#<PR>` on `<date UTC>`, by `<name>`, commit `<7 characters>`. The closeout checked whether this issue is done, and it is not yet. What remains: one line per criterion that is `partly` or `not_delivered`, `<criterion> (delivered in part by PR #<n>)` or `<criterion> (no pull request yet)`, at most 10, then "and `<k>` more". Why: `<reason>` The issue stays open." Its last line is the marker `<!-- sc:closeout pr=<PR> verdict=not_done -->`. It is guarded like write 1 of step 3: if that marker is already on the issue, on a comment that counts (step 3.2), the note is not posted again (`note=already_there`); a not-done marker typed by another author is treated as absent, so it neither stops the note nor counts as the note; otherwise `gh issue comment <N> --repo <R> --body <note>`, then the comments are read back and must hold the marker on a comment that counts (`note=posted`), else `escalated why=note_failed`. The issue is never closed and never reopened on this path, and a rerun with the marker present writes nothing more. A later run may still reach `done` (another pull request has delivered the rest): the not-done marker does not stop it, because only the done marker does.
   - *The hand-back (ruling 36, D22).* The issue stays open, and the run also hands back to the orchestrator, which continues the work that was not done: it records what remains, updates the issue's plan with `/sc:issue --plan` and starts a new worker through the same waves (the 655 side's, section 12.2 rows 11 to 13). The skill only returns what the orchestrator needs. The `settled how=left_open` line ends with `remaining=<k>`, the number of criteria whose delivered word is `partly` or `not_delivered` (at least 1: the shape check of a `not_done` file requires one). The result carries `issue.handback: remaining`, `issue.remaining_file` (the verdict file `done-verdict.md` in the private temporary directory of D20, the `dir=` of the `EVIDENCE` line), `issue.remaining[]` (the unmet criteria, one line each, uncapped, as they are in the verdict file) and `issue.handback_text` (the fixed sentence of 5.6), exactly as section 3.3 says, so the orchestrator reads what remains without parsing a comment. The skill does not delete the temporary directory and puts its path in the result; a caller that needs the criteria later copies them into its own state at once. The skill never starts a worker, a plan or a Dispatch (D15, section 8.3), and it does not count rounds: a rerun that finds the issue still not done (the not-done marker is already there, so no second note) returns the same unmet criteria again, and bounding the rounds is the caller's (12.1). A `not_done` verdict whose note failed to post is `escalated why=note_failed` and carries no hand-back; an `unclear_escalate`, a missing verdict and a `done` carry none.
   - *The bound.* The model reads one file whose size is fixed by the caps above: at most 30 comments, 10 pull requests, 100 file names each, 100 timeline events (for the cross-reference read; the `closed` and `reopened` times are read from every page, filtered, and are not capped). Nothing past a cap is read; what the caps cut is shown by `truncated=yes`, and the model's way out of a case it cannot settle inside the caps is `unclear_escalate`. There is no open-ended search.
   - *Escalation, and how it is recorded.* Escalation happens only after this reading, when the model still cannot tell (`unclear_escalate`); a `not_done` verdict is not an escalation (the not-done path above). An escalation is recorded in three places: the `ISSUE` line (`escalated why=unclear`), the result's `escalations` entry (the fixed sentence of section 5.6, followed by the verdict's `unsettled` and `question` lines, so it names the one question for a person), and the verdict file, which stays in the temporary directory (the `dir=` of the `EVIDENCE` line) for a person to read until the operating system clears it. Nothing is posted to the issue: no comment and no label.
5. **The note** (`templates/closing-note.md`, stub first, slots filled by the script): "Closed after pull request `<owner>/<repo>#<PR>` merged on `<date UTC>` by `<name>`, commit `<7 characters>`. `<what>` Why the issue is done: `<reason>` Criteria checked: one line each, `<criterion> (PR #<n>)`, at most 10, then "and `<k>` more". The pull request `<closes this issue with a closing keyword | names this issue without closing it | does not name this issue, so this note is the link>`. Status: completed (merged)." Its last line is the marker `<!-- sc:closeout pr=<PR> -->`, which write 1 of step 3 reads back. The model writes two things that reach the note: `<what>` (one plain sentence from the pull request's files, 25 words at most; without `--what` the script writes "`<n>` files changed.") and the verdict's `reason` and criteria lines (step 4), which the script has already checked. The link sentence is the `links=` value read as data (step 2). The title of the pull request is not quoted (D8).
6. **Names.** `<name>` is the `name` of the merger's public profile (`gh api users/<login> --jq .name`, which returned `Ironbelly` for the account that merged PR 661 on 2026-11-19), else the login. A merger GitHub does not report is written "someone GitHub does not name". The agent and the model are never named; the scan of section 10 covers the note, the line and the result. The script applies the checks of step 4 (no title of the pull request, no name from `scripts/deny-names.txt`, no U+2014 or U+2013) to the `--what` sentence as well, and writes the default sentence in its place if it fails.

### 5.3 The work report entry (`settle.sh entry --key <key>`)

What exists today, read on 2026-11-19: no `superclaude orchestrator` command is in `src/superclaude/cli/` on this base and `report-entry` and `orchestrator_repo` appear nowhere under `src/`. The `agent-work-report` skill is in the IronFlow repo (`.claude/skills/agent-work-report/`), where `.dev/coordinator/` holds runs, priorities, settings and a report page but no `orchestrated/` folder. That skill says every open item of the previous report is listed again or closed "with a reason the source confirmed" (its `SKILL.md`, "Nothing silently dropped"). The per-issue entry files and the command that closes one are the orchestrator design's (`docs/designs/orchestrator.md` on the 655 branch, lines 484 and 520: `superclaude orchestrator report-entry --key <key> --closed` "moves the entry file to `orchestrated/closed/`"), built in the orchestrator's pull requests, and the skill's move into IronClaude is its piece C.

So the interface this skill uses is one command and nothing else, and it never edits a report file itself (D10):

| Step | Result line |
|---|---|
| `--issue-open` was passed (the issue item did not end closed: `not_done`, `unclear`, `no_verdict` or `reopened`): the entry of an open issue is not closed, and the command is not run: for `not_done` the entry stays open because the orchestrator continues the work and will update it (ruling 36), not because a person must act; for `unclear`, `no_verdict` and `reopened` it stays open because the issue is open and the item is escalated | `ENTRY already_final key=<key> how=issue_open` |
| `superclaude orchestrator report-entry --help` fails or the command is not found (today, and until the orchestrator's pull requests land) | `ENTRY escalated key=<key> why=surface_absent` |
| Present: run `superclaude orchestrator report-entry --key <key> --closed`; its first stdout word `moved` | `ENTRY settled key=<key> how=moved` |
| first word `already_closed` | `ENTRY already_final key=<key> how=already_closed` |
| first word `no_entry` (the surface is reachable and has no entry for this key, for example a pull request nobody orchestrated) | `ENTRY none_found key=<key>` |
| a non-zero exit or any other first word | `ENTRY escalated key=<key> why=entry_command_failed` |

The first-word contract (`moved`, `already_closed`, `no_entry`; exit 0) is what this skill needs from that command. It is not yet written anywhere: UNVERIFIED, section 11, U1, and a requirement the orchestrator's pull request B has to meet or the skill adapts to what it prints. Before the move lands, with no entry present, the entry item is therefore `escalated` and its sentence says what to do by hand. When the orchestrator calls this skill, its own wave 8 call of the same command becomes a repeat and answers `already_closed`; the 655 side may then drop it. The current draft part D has the orchestrator write the entry (wave 8 runs `report-entry --closed` after the closeout and the audit, and the report command writes their results into the entry; its 5.10 row 9: one writer per status). This spec differs because the issue asks this skill to settle the entry; whether the two orders give the same entry is not established, and the difference needs a ruling (section 12.2, row 2).

### 5.4 The worker's Orca task (`settle.sh task [--dispatch ID | --title T]`)

1. **Preflight.** `orca` must run, and `orca orchestration run-current --json` must show a bound Run (`result.run` is `null` when none is; shape read 2026-11-19). Else `TASK escalated why=no_orca` or `why=no_orca_run`.
2. **Find the task.** With `--dispatch`, the row of `orca orchestration worker-list --json` whose `dispatchId` matches gives its `taskId` (both fields read in the output of 2026-11-19). Otherwise `orca orchestration task-list --json` (it answers `run_required` when no Run is bound, read the same day) and the task titled `<owner>/<repo>#<N>`, the title the orchestrator gives it in wave 4 (`docs/designs/orchestrator.md` line 491). No match: `none_found`. A failed lookup: `escalated why=task_lookup_failed`.
3. **Read, then write.** A task already `completed` or `failed`: `already_final how=already_<status>`. Any other: `orca orchestration task-update --id <id> --status completed --result "merged <owner>/<repo>#<PR>"`; the statuses and `--result` are verified in `task-update --help` (valid: pending, ready, dispatched, completed, failed, blocked). Then a read back: `settled how=completed`. A failed write: `escalated why=write_failed`.
4. **Not touched, only read.** The worker's Dispatch and its terminal: no `worker-release`, `worker-stop`, `worker-abandon` or message to the worker (D15). With `--dispatch`, the `dispatchStatus` of its `worker-list` row (value `dispatched` seen on 2026-11-19) is printed as `dispatch=<state>` on the `TASK` line and nothing more. The task's `result` text holds no name.

The JSON field names of the task title and status are UNVERIFIED (U3); the fixture test of section 10 pins them once read from a real Run. Whether Orca already moves a task to `completed` itself when its worker finishes is UNVERIFIED (U4); the read-then-write step is correct either way.

### 5.5 "Completed" and "deployed"

- **Completed** means merged. It is the only status word this version writes for the issue and the task.
- **Deployed** means verified in the place it runs. This version never writes the word: no output of the skill or its scripts contains it (D9). The skill's instruction files define it so that nobody writes it by habit.
- **What will count as a recorded check**, for a later change the owner decides: a record that names what was checked (a health check or an installed version), where it runs, the result and the time in UTC, written by whoever ran it, in a file or comment the caller points to. The closeout would copy it and name its source. This version has no input for it, so the word is not written.

### 5.6 The escalation sentences

Each `why` token has one fixed sentence, so the same words come out whoever calls the scripts. The sentence goes in the result's `escalations` list as `"<item>: <sentence>"`.

| Item | `why` | Sentence |
|---|---|---|
| issue | `no_issue_named` | The pull request names no issue and none was passed. Run closeout again with `--issue <N>`. |
| issue | `several_issues` | The pull request names more than one issue. Run closeout again with `--issue <N>` for each. |
| issue | `not_an_issue` | The number given is a pull request. Run closeout again with the issue's number. |
| issue | `issue_lookup_failed` | The issue could not be read, so it was not checked and not changed. Run closeout again, or pass `--issue <N>` for a different issue. |
| issue | `no_verdict` | No usable done-check verdict was given, so the issue was not judged and not changed. Run closeout again (the skill writes the verdict). |
| issue | `unclear` | The done-check investigated and still could not tell whether the issue is done; the verdict lists what it checked and what could not be settled. The one question for a person follows. |
| issue | `reopened` | A person reopened the issue after the closeout's note. Closeout did not close it again. A person decides. |
| issue | `note_failed` | Posting the closing note failed, so the issue was not closed. Run closeout again. |
| issue | `close_failed` | The closing note is on the issue but closing the issue failed. Run closeout again (it closes the issue and posts no second note), or close it by hand: `gh issue close <N> --repo <owner>/<repo> --reason completed`. |
| entry | `surface_absent` | This install has no command that updates a work report entry. Check the entry for `<key>` by hand. |
| entry | `entry_command_failed` | The report entry command failed. Run it again by hand with `--key <key> --closed`. |
| task | `no_orca` | Orca is not available here, so the worker's task was not looked at. Settle it from a session that has the Run. |
| task | `no_orca_run` | No Orca Run is bound to this session, so the worker's task was not looked at. Settle it from the coordinator's session. |
| task | `task_lookup_failed` | The task could not be looked up. Run `orca orchestration task-list` in the coordinator's session and set it by hand. |
| task | `write_failed` | Setting the task failed. Set it by hand with `orca orchestration task-update --status completed`. |
| all three | `merge_differs` | The merge changed different files than the pull request held. Check it, then run closeout again. |
| any | `not_reached` | Closeout did not reach this item. Run closeout again. |

**The hand-back sentence (ruling 36).** A `not_done` run is not an escalation, so its sentence is not in the table above and has no `why` token. When `issue.handback` is `remaining`, `issue.handback_text` holds exactly this sentence, with the issue's number filled in by the printing step and nothing else changed: "The issue is not done and stays open with one note of what remains. The orchestrator takes the rest from here; by hand, run `/sc:issue --plan <N>` and start a worker on what remains." It names neither the agent nor the model. `settle.sh check` does not read it (it checks the three item lines); a test checks it (10.4 row 20).

## 6. Two actors, one pull request

A person and the orchestrator can both settle one pull request: the person merged first, the orchestrator found it merged, or both ran closeout. A second run is harmless because of these rules, each one testable:

| Rule | What it gives |
|---|---|
| The truth check only reads. | Both runs reach the same verdict. |
| The skill keeps no state of its own: no lock, and no file that a later run reads. Each run that makes a done-check makes its own private temporary directory outside the checkout, with an evidence file and a verdict file that no later closeout run reads (D20); the caller of a `not_done` run reads the verdict file once, from the path in the result (ruling 36). The one marker it uses is a comment on the issue itself (the note's last line), and it counts only when the comment was written by an author who can already close the issue (`authorAssociation` `OWNER`, `MEMBER` or `COLLABORATOR`, and a repository role of `admin`, `maintain`, `write` or `triage` read for that author, D21), whatever login that person or the orchestrator uses; a marker on any other comment is treated as absent, and so is one whose permission lookup answers that its author cannot close (a role that cannot close, an empty role, an HTTP 404), so a marker typed by a stranger neither skips the done-check nor suppresses a note. The state is still in the surfaces, which each run reads first. | There is nothing to get out of step, and a run that stopped half way is finished by the next one. |
| Every write is read-then-write (`settle.sh`, section 5). An issue already `CLOSED` is not closed and gets no note; an entry already closed answers `already_closed`; a task already `completed` or `failed` is left. | The second run's lines read `already_final` and write nothing. |
| The note and the close are two calls, the note first, each guarded by a read-back of the issue state and of the marker comment `<!-- sc:closeout pr=<N> -->` (a marker that counts, by an author who can already close the issue: D21, section 5.2 step 3). | A failed close leaves one note on an open issue; the rerun sees the marker, posts nothing and closes. The other bad state, an issue closed with no note, cannot come from this order. |
| The done-check is not repeated once the done marker note (from an author who can already close the issue, D21) is on the issue: the marker records that an earlier run judged the issue done, so a rerun after a failed close finishes the close without a new verdict. A `not_done` run posts its own not-done note once (its own marker); a rerun with that marker writes nothing more, and a later run can still reach `done` when another pull request has delivered the rest. A person's reopen is not undone: a `reopened` event after the note, read from every page of the timeline, gives `escalated why=reopened`, and a timeline that cannot be read, or a permission lookup of the marker's author that fails without an answer, gives `escalated why=issue_lookup_failed` with nothing written (D21). | A rerun cannot reach a different verdict and close an issue whose first run said done and failed half way, and it cannot fight a person who reopened the issue. |
| The orchestrator's own wave 8 steps (its issue close, its `report-entry --closed`) are read-then-write too. | Either order of the orchestrator's steps and this skill gives the same final state (section 3.2). |
| A person who closes the issue, or merges, while a run is going only changes what the next read shows. | The close is guarded by a state read just before it, so a close made in the meantime is not repeated. |

What a second run prints: the same block, with the items that the first run settled now `already_final`. The orchestrator may record it again without harm.

The one race left: both actors read the issue as open with no marker in the same second and both post the note. GitHub has no compare-and-set for a comment, so the marker read narrows this and cannot remove it. The worst case is two notes and one close; nothing is lost or wrongly closed. The check is in section 11 (U5). A failed close and its rerun are not this race: they are covered by the marker. Because the done-check is a model's judgment, two actors that both run it before either posts can also reach different verdicts: the one with `done` writes the note and closes, the one with `unclear_escalate` writes nothing, the one with `not_done` posts only its not-done note, and the second one's guard (a state read before the close) finds the issue closed. Nothing is closed unless one of them judged it done, and a `not_done` note on an issue that the other closed is the one stale note this race can leave.

### 8.2 The judgment, and everything else

Judgment is used in two places, both by the skill's own model session. (1) The done-check verdict: whether the issue is done, with the criteria it read, the evidence for each, what it looked at and one reason (section 5.2 step 4, ruling 32). (2) The note's one sentence (`--what`). Every status comes from a table in a script, from the verdict word and the read-backs, and every escalation sentence is fixed text in the table of section 5.6, and the hand-back sentence is fixed text under it; the model never writes any of them, and the hand-back values are copied from the checked verdict file and the `ISSUE` line with no judgment. Everything else is a script or a table, so a direct call of the scripts gives the same words as a call of the skill, except that the issue item needs a verdict: without one it is `escalated why=no_verdict` (D6, section 3.2). This matches the issue's own allowance, which lets judgment decide an item's final status, as far as ruling 32 needs it for the issue item and no further; the entry and the task are still decided by their tables alone.

### 8.3 Will Do and Will Not Do

Will Do: resolve the repo from `origin` only and pass it on every `gh` call; read the pull request state first and act only on `MERGED`; decide whether the issue is done by reading its own criteria against what the pull request and its linked pull requests delivered, writing the verdict into the fixed-shape file; close an open issue once, only after a `done` verdict, with a note that says why and names who merged, crediting people by name; leave an issue that is not done open with one short marked note of what remains, and return the unmet criteria in the result for the orchestrator to continue the work (ruling 36); escalate only a case it still cannot tell after investigating; settle the entry and the task by read-then-write, or escalate with the reason; print the result block last, also after a stop.

Will Not Do: merge, push, commit, stage or delete a branch or a worktree; use commit ancestry or a two-dot diff; decide whether an issue is done by matching the words `Fixes`, `Closes` or `Refs`; write a status or an escalation sentence, or run a `gh` command of its own while judging (it reads the evidence file only); close an issue that is already closed or that a person reopened after its note; write the word "deployed"; edit or delete any comment or text on GitHub, or reopen an issue; release, stop, abandon or message a worker or its Dispatch; start the work that a not-done issue still needs (a worker, a plan or a Dispatch) or count rounds of hand-backs; write a report file by hand; name the agent or the model, or quote the pull request title; ask the person a question; start a worker agent; pass an Orca link flag, or call `orca` anywhere but in `settle.sh task`; print or write a secret.

The command file's Boundaries repeat the same two lists; a test checks they match (the pattern of `tests/skills/test_issue_protocol.py:601`).
