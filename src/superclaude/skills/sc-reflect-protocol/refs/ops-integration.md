## -f rule (CLAUDE.md ABSOLUTE)

If `git add` requires `-f` on **any** `.claude/` path (except `.claude/settings.json`), STOP. The `-f` is the violation siren — it means you are about to commit `.claude/{skills,commands,agents,hooks,templates}/*` content, which is **gitignored sync-dev output** of `src/superclaude/`.

The correct response is **always** the same:

1. STOP the `git add -f` attempt. Do not retry with `-f` removed against the same path.
2. Move the change to `src/superclaude/` (the source-of-truth tree). For this skill that means `src/superclaude/skills/sc-reflect-protocol/`.
3. Run `make sync-dev` to mirror `src/superclaude/` into `.claude/`.
4. Stage **only** the `src/` side. The `.claude/` mirror is regenerated by `superclaude install` downstream and by `make sync-dev` for contributors — it is never the place to author changes.

The only exception is `.claude/settings.json` (project hook + permission registrations, not auto-generated). ANY other exception requires explicit user instruction in the same session and must be called out in the commit message or PR body (e.g., "user authorized staging `.claude/foo` because X"). Without that explicit authorization, treat every `.claude/<not-settings.json>` path as forbidden to stage.

**Why the `-f` is the signal:** A successful `git add` against a `.claude/` path means the file was either (a) already tracked from before the gitignore landed, or (b) staged with `-f`. Case (a) is grandfathered; case (b) is the violation. The `-f` flag is the only signal that distinguishes the two at staging time, which is why this rule lives at the CLAUDE.md level and not just in a pre-commit hook — the hook catches commits, not stages, and the human eye must catch the `-f` before it gets that far.

**Common failure modes this rule catches:**

- Hand-edited paste-ready commit commands that staged `.claude/skills/...` alongside `src/superclaude/skills/...`. Doubles every diff, invites drift, and breaks `make verify-sync` for the next contributor.
- Task-file instructions that name `.claude/` staging steps. If a task file says `git add .claude/skills/foo/`, the task file itself is wrong — escalate to fix the task file, do not follow it.
- Follow-up suggestions in agent responses that include `.claude/` staging steps. Apply the same escalation.
- Risk-note language like "stage the synced `.claude/` mirror so reviewers see both sides". Reviewers see the `src/` change; CI runs `make sync-dev` and reviews the same mirror locally. Never stage both sides.

See memory `feedback_claude_dir_gitignored.md` for the full rationale and the prior incident that motivated this rule.

## Hook redirect

The `.claude/settings.json` PreToolUse hook rejects writes to `.claude/skills/*-workspace/**` with a redirect to `.dev/eval-workspaces/<skill-name>/`. This skill's eval workspace MUST land at `.dev/eval-workspaces/sc-reflect/` to pass the hook. The `.gitignore` also matches `.claude/skills/*-workspace/`, so any misplaced workspace cannot be committed.

Both gates work together:

- **PreToolUse hook** — catches the write at tool-call time, before any file lands on disk under `.claude/skills/*-workspace/`. The rejection message names the correct destination (`.dev/eval-workspaces/<skill-name>/`) so the redirect is mechanical.
- **`.gitignore`** — catches any workspace that bypassed the hook (e.g., out-of-band file creation). Such a workspace cannot be staged without `git add -f`, which then triggers the `-f` rule above.

For this skill specifically, the eval workspace path is `.dev/eval-workspaces/sc-reflect/`. The skill-creator plugin's default sibling-workspace convention (`.claude/skills/sc-reflect-protocol-workspace/`) is **overridden** by the project-level rule in `CLAUDE.md` and enforced by the hook.

**Authoritative source for the redirect:** `.dev/README.md` carries the canonical "where things go" decision guide. The override applies regardless of any path the plugin itself suggests or attempts — the hook redirect message names `.dev/eval-workspaces/<skill-name>/` and that name is non-negotiable. The redirect is cited as a *behavior* (sibling-workspace under `.claude/skills/*-workspace/`), not a file path or line number, so the override survives upstream skill-creator updates.

**Why two-layer enforcement.** The PreToolUse hook is the active gate; the `.gitignore` is the passive backstop. A misconfigured environment (missing hook registration, hook script disabled) would let a workspace land at `.claude/skills/sc-reflect-protocol-workspace/`, but the `.gitignore` still prevents that workspace from being committed without `-f` — at which point the `-f` rule (above) kicks in. The two layers cover each other.

## sync workflow

The 5-step pre-commit procedure for any change to this skill:

1. **Edit `src/superclaude/skills/sc-reflect-protocol/SKILL.md`** (and/or `src/superclaude/commands/reflect.md` if the command surface also changes). Source of truth is **always** `src/superclaude/`. Never edit `.claude/skills/sc-reflect-protocol/SKILL.md` directly — that copy is regenerated.
2. **Run `make sync-dev`** to mirror the updated `src/superclaude/{skills,agents,commands}/` tree into `.claude/`. This is the canonical sync command (Makefile:109).
3. **Run `make verify-sync`** — must exit 0 (Makefile:166). The pre-commit hook also runs this, so a non-zero exit blocks the commit. A non-zero exit means `src/` and `.claude/` diverged; re-run step 2 or investigate the diff.
4. **Run `make lint-architecture`** (Makefile:362) to confirm bidirectional command↔skill link integrity and frontmatter completeness. This catches missing `Skill:` pointers in `commands/reflect.md` and missing `command:` back-references in the skill frontmatter.
5. **Stage ONLY `src/` and `.dev/` paths.** NEVER stage `.claude/` paths. If `git status` shows `.claude/skills/sc-reflect-protocol/` changes after step 2, that is expected sync output — leave it unstaged. If `git add` ever requires `-f` for a `.claude/` path, apply the `-f` rule above.

| `make sync-dev` | existing, Makefile:109 | Mirror `src/superclaude/{skills,agents,commands}/` → `.claude/`. Step 2 of the sync workflow. |
| `make verify-sync` | existing, Makefile:166 | Confirm `src/` and `.claude/` match. Step 3 of the sync workflow; also pre-commit hook. |
| `make lint` | existing, Makefile:48 | Run `ruff` linter against Python sources. Baseline for any code-touching PR. |
| `make test` | existing, Makefile:13 | Full pytest suite. Baseline for any code-touching PR. |

**CI policy summary.** Every PR that modifies `src/superclaude/skills/sc-reflect-protocol/**` or `src/superclaude/commands/reflect.md` MUST pass `make reflect-eval-quick` plus the standard baselines (`make lint`, `make test`, `make verify-sync`, `make lint-architecture`). Release-candidate branches add `make reflect-eval`. The cost-profile regenerator (`make sync-cost-profile`) is run by the contributor whenever spec §15 budgets change; the resulting `refs/cost-profile.yaml` diff is reviewed in the same PR.

**Failure-handling expectations:**

- `make verify-sync` non-zero exit → re-run `make sync-dev`. If still non-zero, inspect the diff (`git status` against `.claude/skills/sc-reflect-protocol/`) and reconcile with `src/superclaude/skills/sc-reflect-protocol/`. Never resolve by editing `.claude/` directly.
- `make lint-architecture` failure → fix the missing pointer (most commonly a stale `Skill:` line in `commands/reflect.md` or missing `command:` back-reference in skill frontmatter), re-run `make sync-dev`, re-verify.
- `make reflect-eval-quick` failure → inspect the failing pilot case under `.dev/eval-workspaces/sc-reflect/`. The pilot suite covers the 3 highest-leverage paths (T1 happy-path, T2 escalation, T3 promotion-gate). A failure here is rarely cosmetic.
- `make reflect-eval` failure on an RC branch → triage per case category; T1/T2 regressions block the RC, T3 promotion-gate regressions may or may not block depending on the gate-condition involved (see §9.4 contract-evolution rules).

## Vendor-heterogeneity WARN

**Source:** spec §4.0 step 0.6 (vendor heterogeneity check).

For each resolved alias, extract the vendor (Anthropic / Qwen / Kimi / DeepSeek / OpenAI-compat / etc.) by alias-name heuristic. Emit one of:

- `t2_vendor_diversity: multi` (≥2 vendors among resolved aliases)
- `t2_vendor_diversity: single` (all aliases share one vendor)

When `single`, emit a WARN with the suggested env-var override (the full message body is this section). This is **warn-only in v1**; behaviour does not block. See §11.0 (sufficiency-conditional preamble) and the v1.1 deferred-hardening notes in §19.

The vendor heuristic reads the `ANTHROPIC_DEFAULT_*_MODEL` family of environment variables and any auggie alias mappings present in the resolved-alias set. When all aliases share a single vendor prefix, reviewer diversity is **model-only** (multiple model classes from one vendor) rather than **full** (model classes spanning multiple vendors). This is a meaningful degradation for adversarial robustness — common-mode reasoning errors are more likely when reviewers share an upstream training lineage.

The WARN message points operators at the environment-variable override path (e.g., setting `ANTHROPIC_DEFAULT_SONNET_MODEL` to a Qwen or Kimi alias when available) so the next run can achieve `multi`. The warn-only posture is deliberate: blocking on single-vendor in v1 would lock out solo-developer setups that have no multi-vendor budget. Hardening to a configurable block-mode is tracked in §19 (v1.1 deferred items).

Telemetry: `ensemble.t2_vendor_diversity` is recorded in `metrics.json` (string label, see §15.1) and influences `ensemble.t2_effective_diversity` (`full | model-only | vendor-only | none`).

**Suggested WARN body (operator-facing):**

```text
[reflect][WARN] Vendor heterogeneity: single
  Resolved aliases: <list-of-alias-names>
  All aliases map to vendor: <vendor-prefix>
  Effective reviewer diversity: model-only (degraded from `full`)
  Suggested override (env-var path):
    export ANTHROPIC_DEFAULT_SONNET_MODEL=<qwen|kimi|deepseek-alias>
  Rationale: multi-vendor reviewers reduce common-mode reasoning errors.
  This is warn-only in v1; behaviour does not block. See §11.0 / §19.
```

The exact message body is implementation-defined but MUST include: the resolved-alias list, the shared vendor prefix, the effective-diversity downgrade, and at least one concrete env-var override hint. The "warn-only in v1" disclaimer is mandatory so operators do not interpret the message as a blocker.

## Metrics ingestion config

**Source:** spec §15.1 (Metrics Export).

Reflect emits a structured `<output>/metrics.json` per run and appends a one-line summary to `.dev/reflect/runs.jsonl` for cross-run aggregation. The schema deliberately uses flat numeric leaves at the inner level so that conventional flatteners produce metric names like `sc_reflect_wave_durations_ms_wave_0` and `sc_reflect_promotion_gate_conditions_passed`.

### Prometheus `json_exporter`

```yaml
modules:
  default:
    metrics:
      - name: sc_reflect
        path: '{ . }'
```

Point the exporter at the path to `metrics.json` (1-line config; consume all top-level groups; flatten with `_` separator).

### StatsD `dogstatsd-json`

```json
{"source": "metrics.json", "prefix": "sc_reflect", "separator": "_"}
```

Each top-level group becomes a metric namespace; nested numeric leaves become individual counter/gauge submissions.

### OpenTelemetry `json-receiver`

```yaml
receivers:
  json:
    path: <output>/metrics.json
    prefix: sc_reflect
```

The receiver flattens the same way (`_` separator, top-level groups become attribute namespaces).

### Counter / gauge / string classification

| Class | Fields |
|---|---|
| **Counters (monotonic)** | `wall_clock_ms`, `token_usage.*`, `evidence_validator.citations_*`, `deviation_counts.*`, `promotion.gate_conditions_passed` |
| **Gauges (snapshot)** | `tier_reached`, `calibration.calibrated_confidence_*`, `adversarial.convergence_score`, `evidence_validator.drop_rate` |
| **Strings (PromQL labels)** | `status`, `mode`, `*_diversity` enums, `promotion.action`, `adversarial.merge_method` |

### `runs.jsonl` append schema

A one-line JSON summary is appended to `.dev/reflect/runs.jsonl` at end-of-run. The schema is a **subset** of `metrics.json` containing only cross-run-comparable fields:

```json
{"run_id": "...", "timestamp": "...", "skill_version": "1.0", "mode": "post", "tier_reached": 2, "status": "success", "wall_clock_ms": 124000, "token_usage_total": 47832, "calibration_delta": -0.03, "convergence_score": 0.82, "evidence_validator_drop_rate": 0.0, "deviation_counts_regression": 0, "promotion_action": "moved"}
```

`.dev/reflect/runs.jsonl` is **append-only**, **gitignored** by convention (per-machine, not per-repo state), and consumed by meta-eval (§9.3 row 9), CI dashboards, and operator `jq` queries like `jq '.[] | select(.status=="failed")' .dev/reflect/runs.jsonl`. The append-write is best-effort: if the global file is unwritable, reflect logs a WARN and continues — the per-run `metrics.json` remains the authoritative copy.

### Stability guarantee

The `metrics_schema_version` field is governed by §9.4 contract-evolution rules:

- **Additive changes** (new fields, new enum values) bump the **minor** version. Consumers tolerant of unknown fields (per §9.4) continue to work without changes.
- **Renames or removals** bump the **major** version. Consumers must update their flattening / ingestion config.

The schema is forward-compatible at the consumer level via the same unknown-field-tolerance rule as §9.4. Operators pinning a specific `metrics_schema_version` in dashboards SHOULD treat the major-version digit as the breaking-change indicator and rebuild dashboards only on major bumps.

### Operator quick-reference

Common `jq` queries against `.dev/reflect/runs.jsonl`:

```bash
# All failed runs in the file
jq -c '. | select(.status=="failed")' .dev/reflect/runs.jsonl

# Calibration drift over the last 50 runs
jq -c '.calibration_delta' .dev/reflect/runs.jsonl | tail -n 50

# Promotion-action distribution
jq -r '.promotion_action' .dev/reflect/runs.jsonl | sort | uniq -c | sort -rn

# Runs where the evidence validator dropped >10% of citations
jq -c '. | select(.evidence_validator_drop_rate > 0.10)' .dev/reflect/runs.jsonl
```

For per-run `metrics.json` inspection (full schema), point at `<output>/metrics.json` directly — the per-run file carries all fields documented in §15.1, not just the cross-run subset.

**Dashboard recommendations:**

- Calibration-drift panel: `sc_reflect_calibration_calibration_delta` (gauge, time-series, alert on |delta| > 0.15 sustained).
- Adversarial-convergence panel: `sc_reflect_adversarial_convergence_score` (gauge, distribution).
- Evidence-validator drop-rate panel: `sc_reflect_evidence_validator_drop_rate` (gauge, alert on > 0.10).
- Promotion-gate panel: `sc_reflect_promotion_gate_conditions_passed` / `sc_reflect_promotion_gate_conditions_total` (ratio gauge; ratio < 1.0 means at least one gate condition failed).
- Token-budget panel: `sc_reflect_token_usage_total` (counter; rate over time correlates with cost).
- Degradation panel: count of runs where any `*_diversity` field reports `degraded` / `single` / `none` (string label aggregation).
