# IronClaude: How We Work

This guide tells you which IronClaude skills and commands to use for each kind of work, and in what order. Keep it open while you work. `superclaude install` copies this guide to `~/.claude/HOW-WE-WORK.md`; run `superclaude update` after upgrading IronClaude to refresh that copy. `superclaude update` overwrites every file it ships, including an edited `~/.claude/CLAUDE.md`, and keeps no backup. It also deletes and re-copies each shipped skill folder in `~/.claude/skills/`, so any file you added inside one is lost. Copy any file you changed or added before you run it. Plugin installs ship only some of these commands and skills; for the full set run `pipx install git+https://github.com/IronbellyOrg/IronClaude && superclaude install` (the `superclaude` package on PyPI is the upstream project, not IronClaude).

## 1. How much process does this job need?

Match the requested outcome and any explicit command or existing plan first. These levels choose implementation process, not how much research or how many output artifacts a report needs. Most planned implementation uses level 3; choose level 4 only for its stated explicit or exceptional machinery need.

<!-- level-table:v1 -->

| Level | Use this when | What you run | What you end up with |
|---|---|---|---|
| **1. Ask a question** | You want to understand code, a decision, or how something works, and you do not want anything changed. | Ask Claude in plain English. For an explanation of specific code, `/sc:explain src/jobs/runner.py`. | An answer. No files change. |
| **2. Make a small, direct change** | The change is in one source file (plus its test file), needs five edits or fewer, and you already know exactly what it should be. | Ask Claude to make the change and run the related test, or use `/sc:task "Rename recieved_at to received_at in src/jobs/runner.py and update its tests"`. Inspect the actual classification and verification evidence: STANDARD permits affected tests or documented manual verification; LIGHT includes scope/sanity checks; EXEMPT covers non-code operations. Do not assume every tier ran tests, describe LIGHT as unchecked, or report manual verification as a test pass. Run the related test if it has not run. | The bounded edit and its recorded verification, including an observed related-test result when available. |
| **3. Follow a checked implementation plan** | Ordinary implementation needs a written plan, including work across many files or several sessions, with or without an existing spec. | `/sc:workflow "<what to change, why, which files or spec>" --depth standard --handoff none` writes a plan with acceptance criteria (a written definition of "done" for each step) and runs an advisory check against your request. Standard is the default; use quick for smaller checked plans, not all ordinary work. It prints the actual plan path, `.dev/tasks/to-do/<id>/<id>.md`, and the check result. `<id>` is the generated plan folder's name. Read the plan and check result, then, only when execution is requested, run `/sc:implement <that path>`. It implements each step and checks compliance with its criteria. | A plan folder holding the plan and `progress.md` (one line per step), plus code changes if execution was requested. If interrupted, run the same `/sc:implement` command again; it continues from the first unfinished step. When every step passes, a final independent review runs and the folder moves to `.dev/tasks/done/`. On any system other than Linux (including macOS) the move is refused on purpose: the folder stays in `.dev/tasks/to-do/` and the run reports archive-blocked. That is expected; never move the folder by hand. |
| **4. Explicit or exceptional task-file work** | You explicitly select MDTM (the task-file/checklist format), supply an existing MDTM task for execution, or have an exceptionally complex, long-running phased program with a stated need for its research, checklist and phase-reviewer machinery. | For creation, `/task-builder "<what to build, why, which code, why MDTM>"` researches the code and writes a task file under `.dev/tasks/to-do/`. Add `--spec <path>` when a spec, PRD or TDD exists. Read the task file and check result; only when execution is requested, run `/task <path to task file>`. An existing MDTM task goes directly to `/task`, without rebuilding it. | The requested task file, or its execution through the checklist and reviewer panels after each phase except setup, followed by tests and a final audit. Resume with the same executor. |
| **5. Research first** | You do not yet know how the current system works, what needs to change, or whether the idea is feasible. | `/tech-research "<question, why you need it, which code to look at>"`. Stop at the report for a research-only request. If you decide to build, use `/sc:workflow "<what to build> as recommended in <report path>. Code: <folders>"`, then read its plan and use `/sc:implement <printed plan path>` when execution is requested (level 3). Level 4 needs its own explicit or exceptional justification. | A report at `.dev/tasks/to-do/TASK-RESEARCH-<topic>-<timestamp>/RESEARCH-REPORT-<topic>.md` with findings, options, and a recommended plan; implementation is a separate decision. |
| **6. Write a full specification** | You need a PRD and TDD for a new product, component or major feature that others will build against. | `/prd`, then `/tdd`, with the requested reviews. Stop after the requested documents for document-only work. Ordinary subsequent implementation planning uses `/sc:workflow`, then `/sc:implement` when execution is requested. Offer `/roadmap` only for explicit composer selection or the exceptional level-4 machinery need; it internally uses `/task-builder` and `/task` and can create phase task files. See workflow 3.1 of the routing guide (`HOW-WE-WORK.md`). | The requested reviewed documents. Planning and execution are separate; expressly selected document skills and the roadmap composer keep their own internal machinery. |

**Hard limit:** if the work needs more than 5 edits or touches more than one source file (its matching test file does not count), it must go through a written plan: normally level 3, not automatic level 4. An edit is one change in one place in a file (one block of consecutive changed lines); renaming a name used in 8 places is 8 edits and requires a written plan. The one exception is contained `/sc:cleanup` and `/sc:improve` work on a folder (section 3.7 of the routing guide): commit first and review `git diff` afterwards. This exception does not cover structural migrations. Direct command selection does not waive the written-plan requirement.

File count, multiple sessions, an existing spec/PRD/TDD, risk, auditability, drift concerns or resume alone never select level 4. A twelve-file feature across several sessions still uses level 3 without a concrete MDTM machinery need. Inspection breadth is not mutation breadth: reading thirty files for an explanation or report does not require an implementation plan.

When an adequate approved plan already exists, use its existing executor directly; do not rebuild it. Managed workflow packages use `/sc:implement`; existing MDTM execution uses `/task`. Explicit `/sc:implement` selection retains that executor's own semantics, not MDTM checklist/phase execution, even if the source resembles MDTM.

## 2. How to write a request

Every research, document, and task skill works from the same four things. If the first one is missing or vague, the skill stops and asks you for it. The other three are optional, but each one makes the result noticeably better and faster. Put all four in your first message:

1. **What** you want: the question, feature, or document.
2. **Why** you need it, and any constraints.
3. **Where to look:** the code folders and documents it should read, as paths.
4. **Where the result goes**, if it matters.

| Weak request | Strong request |
|---|---|
| `/tech-research "rate limiting"` | `/tech-research "What would it take to add per-tenant rate limits to the public API? One tenant is overloading it. Look at src/api/middleware/, src/tenants/, and config/limits.yaml. I need options with effort and risk, and a recommended plan."` |
| `/task-builder "add rate limits"` | `/task-builder "Add per-tenant rate limits as recommended in .dev/tasks/to-do/TASK-RESEARCH-rate-limits-<timestamp>/RESEARCH-REPORT-rate-limits.md. Code: src/api/middleware/, src/tenants/. Why: one tenant is overloading the API."` |
| `/tech-reference "rate limiting"` | `/tech-reference "Document the rate limiting feature we just built. Code: src/api/middleware/rate_limit/. Audience: engineers who maintain it. Output: docs/api/rate-limiting-technical-reference.md."` |

## 3. Workflows

### 3.1 Build a new product or major feature (full specification)

Use this when people need to agree on *what* is being built and *how* before anyone writes code. The example specifies usage-based billing. **For documents only, stop after the requested documents and reviews; do not append a roadmap, phase tasks, implementation or shipping.** PRD and TDD skills keep their own document-generation machinery, including any internal task-builder/task use. That does not choose the later product implementation process.

1. **Shape the idea (only if it is still vague).**
   `/sc:brainstorm "Usage-based billing for API customers: metering, monthly invoices, overage alerts" --depth standard`
   It asks you questions, has several agents propose approaches, and merges them into `.dev/brainstorms/<timestamp>-<name>/merged-requirements.md`. It stops there. If no PRD is needed and implementation is requested, take those requirements into `/sc:workflow`, then `/sc:implement` after reading the plan. Do not add a task-file handoff merely because no PRD is needed.

2. **Write the product requirements document (PRD).** The PRD defines *what* to build and *why*: users, problems, requirements, success measures, and scope.
   `/prd "Create a PRD for usage-based billing. Purpose: align product and engineering on the first release. Start from .dev/brainstorms/<timestamp>-usage-billing/merged-requirements.md. Relevant code: src/billing/, src/api/metering/. Output to docs/billing/PRD_BILLING.md."`
   The skill researches, writes, and reviews the PRD itself, including its own consistency checks.

3. **Get an expert critique of the PRD.**
   `/sc:spec-panel @docs/billing/PRD_BILLING.md --mode critique --focus requirements`
   A panel of named software-requirements experts judges whether the requirements are measurable, testable, and complete. It only reports. Decide which findings to accept, ask Claude to apply them to the PRD, then run the same command again until no critical findings remain.

4. **Write the technical design document (TDD) from the PRD.** The TDD defines *how* it will be built: architecture, data, interfaces, testing, and migration.
   `/tdd "Create a TDD for the billing service from docs/billing/PRD_BILLING.md. Relevant code: src/billing/, src/api/metering/. Output to docs/billing/TDD_BILLING.md."`

5. **Get an expert critique of the TDD.**
   `/sc:spec-panel @docs/billing/TDD_BILLING.md --mode critique --focus architecture,testing`
   Apply accepted findings the same way as step 3.

6. **Check whether it should be split (optional).** If the work looks too big for one release:
   `/sc:release-split docs/billing/TDD_BILLING.md`
   It writes its analysis to `docs/billing/release-split/`. "Do not split" is a normal answer. If it recommends a split, it writes a separate spec for each release: use the Release 1 spec in place of the TDD in step 7, and do not plan Release 2 until Release 1 is built and validated.

7. **Plan only if implementation planning is requested.** Ordinary post-document planning uses workflow, not an automatic roadmap/task-builder chain:
   `/sc:workflow "Plan usage-based billing from docs/billing/PRD_BILLING.md and docs/billing/TDD_BILLING.md. Keep the old invoice API working. Code: src/billing/, src/api/metering/." --depth standard --handoff none`
   Read the actual printed plan and advisory check result. Standard is the ordinary default; quick is appropriate for smaller checked plans. A new component or accepted PRD/TDD is not itself a reason to select MDTM.
   - **Conditional roadmap alternative:** only when you explicitly select `/roadmap`, or have an exceptionally complex, long-running phased program with a stated need for MDTM research, checklists and phase-reviewer panels, use `/roadmap "Create a full roadmap from docs/billing/PRD_BILLING.md and docs/billing/TDD_BILLING.md. Each phase must be independently deployable and keep the old invoice API working. Project name: billing-v2. Dry run first so I can review the phase plan."`
   - The expressly selected composer internally uses `/task-builder` and `/task` to generate the roadmap and can create downstream phase task files. This is its document machinery, not permission to implement product phases. Its dry run presents phases for approval; the full run prints the roadmap path under `.dev/tasks/to-do/TASK-ROADMAP-billing-v2-<timestamp>/`, phase task paths and checks under `qa/`. Read them before any product execution.
   - If the summary lists only build requests (`build-requests/BUILD_REQUEST-phase-NN-<name>.md`), its middle setting stopped before phase task creation. Within this selected MDTM route, `/task-builder <path to that build request> --spec docs/billing/TDD_BILLING.md` creates each phase task. Asking for a full roadmap selects the full composer pipeline. Do not use this branch solely because a spec exists or work spans files or sessions.

8. **Execute only when requested, using the selected plan's executor.** For the ordinary workflow plan, `/sc:implement <actual printed plan path>` implements and checks each step; read its ledger and final independent review. Do not rebuild an adequate approved plan.
   For the conditional MDTM branch only, `/task <path to the phase 1 task file>` runs its checklist, phase-reviewer panels (except setup), tests and final audit. Do not repeat its own checks. The internal audit compares a commit range and can miss uncommitted work, so use the re-confirm audit in step 9.

9. **Confirm the selected work passed.** For a workflow plan, consume its compliance results and final review before shipping. For MDTM phases, open the task file's `reflect_post` entry and report; resolve Open Questions with your lead (or yourself), then re-confirm with `/sc:reflect --mode post --tasklist <path to the task file> --spec docs/billing/TDD_BILLING.md --diff <commit before the work started> --no-promote` before the next phase. Give one commit, not a `..HEAD` range, so the working tree is included. Stage only intended new files before auditing; never stage generated `.claude/` mirrors. Commit a passing phase only when authorized; the next phase's baseline is the commit made when the previous phase passed (the first uses the commit before work started). Use `HEAD` only if no commit was made since this phase started; otherwise find the baseline with `git log --oneline`. The internal audit runs before the MDTM task is marked done, so leave its folder in `.dev/tasks/to-do/`.

10. **Review and open a pull request.** Workflow 3.11.

11. **Document what was built.** Workflow 3.9 (`/tech-reference`).

**If `/task` stops partway:** it shows the reviewers' findings and writes them to the Task Log at the bottom of the task file (the file's `status` may say Blocked, with a reason). Decide the fix with your lead (or yourself, if you work alone): change the code, correct the spec, or amend the task item. Then run the same `/task <path>` command again; it continues from the first unchecked item. Never tick items by hand to get past a stop.

### 3.2 Add a feature to an existing system (no PRD needed)

Use this when the requirements are already clear and the feature extends something that exists. The example adds CSV export to an invoices page.

1. **Understand the current code (if you need to).**
   `/tech-research "How does the invoices list load and format its data, and what would need to change to add a monthly CSV export? Finance needs it for month-end. Look at src/invoices/ and src/api/routes/invoices.py."`

2. **Write and agree the spec.** Save a short spec file, for example `docs/specs/invoice-csv-export.md`, saying what changes, which files, and how you will know it works. If it includes a new interface or API, `/sc:design invoice-export-api --type api --format spec` drafts that part; paste its output into the spec file. Have your lead approve the spec.

3. **Plan from the approved spec.**
   `/sc:workflow docs/specs/invoice-csv-export.md --depth standard --handoff none`
   Read the actual printed plan and its advisory check result before execution. Resolve gaps before the first step starts; do not repeat workflow's built-in pre-check. An existing spec, multiple files or several sessions do not by themselves select MDTM. If an adequate approved plan already exists, skip plan creation and use its executor directly.

4. **Run the approved plan only when execution is requested.** `/sc:implement <actual printed plan path>`. It checks compliance step by step and records the results. If it stops, follow 3.3; resume with the same command, not a replacement task file.

5. **Confirm and ship only when requested.** Read the compliance results and final review, then follow workflow 3.11. Explicit MDTM creation/execution or exceptional complex long-running phase machinery remains level 4; use `/task-builder ... --spec <spec path>` and `/task <task file>` only for that justified branch (3.1).

### 3.3 Make a small, well-defined change

1. **One source file (plus its test), five edits or fewer:** use level 2 (section 1).

2. **Beyond the direct-change limit:** normally use `/sc:workflow`, then `/sc:implement`. Standard is the ordinary planning default; for this smaller checked plan, quick is appropriate:
   `/sc:workflow "Make the retry limit in src/jobs/runner.py configurable from settings.yaml, default 3, and cover it with a unit test" --depth quick --handoff none`
   Read the plan at the path it prints (`.dev/tasks/to-do/<id>/<id>.md`; `<id>` is defined in section 1, level 3) and the check result printed with it, and check that each step's acceptance criteria clearly say what "done" means. Then:
   `/sc:implement .dev/tasks/to-do/<id>/<id>.md`
   It records available lint, typecheck and tests as extras; compliance with the acceptance criteria is the task verdict. Small first-pass checks can be inline, so not every task uses an independent agent; the managed package's final review is independent.
   - **If a step still fails its check after the automatic retries (one fix pass, then up to three new attempts written from stronger models' advice; the step's acceptance criteria never change),** `/sc:implement` stops with the code `E-HALT-QA` and prints the progress file path (`progress.md`, beside the plan). Either fix the code and resume, or have your lead explicitly accept the explained gap in the current conversation. A clear reply such as "yes, accept step 2 as explained" is sufficient after Claude explains the exact scope, reason and cost if wrong. Claude records that confirmation automatically as a `Ruling:` in the progress file and retains the non-compliant verdict; you do not need to hand-write task or archive records. Unclear or missing acceptance stays blocked. The same acceptance covers ordinary archiving of unchanged accepted work, but never waives a fresh independent final review or authorizes commit, PR, merge or release. Existing manually written records remain valid. If it stops with `E-RESUME-NEEDED`, something outside the step failed (for example the reviewer crashed): run the same command again, and do not add a ruling. (The installed rule: `~/.claude/skills/sc-implement-protocol/refs/ledger.md`.) Do not edit the plan after the first step starts; the tool stops with `E-PLAN-CHANGED`.

3. **Ship.** Run the tests yourself only if nothing ran them (a plain edit, or a trivial `/sc:task` change). Then follow workflow 3.11. Its `/code-review` step looks for bugs, which the step-by-step reviewer does not.

### 3.4 Fix a bug

1. **Diagnose it.** Describe what happens, what you expected, how to reproduce it, and paste the exact error.
   `/sc:troubleshoot "Nightly invoice job fails with KeyError: 'tenant_id' in src/billing/invoice_job.py since yesterday's deploy. Expected: invoices for all tenants. Reproduce: python -m billing.invoice_job --date 2026-09-30" --type bug`
   Use `--type test`, `build`, `performance`, `deployment`, or `security` when that fits better. Diagnosis writes tool-owned reports and evidence, not product fixes; diagnostic runs still require the relevant execution permission. It can return supported, inconclusive, failed or blocked results. Standard depth can escalate to competing hypotheses; quick stops after the first pass and deep requests the deeper investigation. No duration or success is guaranteed.
   For a remediation-planning offer, add `--fix` only if you want it: after a supported successful diagnosis and your acceptance, standard depth offers workflow planning. It does not authorize implementation. `--depth quick --fix` is invalid. Explicit `--depth deep --fix` currently selects MDTM remediation; depth is coupled to that route, not a file-count or risk rule. For deep diagnosis followed by ordinary planning, omit `--fix`, then plan separately from the supported report.

2. **Read the report** at `.dev/troubleshoot/<name>-<timestamp>/REPORT.md`. It says whether the fix belongs in the code, the test, or the documentation.

3. **Fix it.**
   - **Small fix (one source file plus its test, five edits or fewer):** first ask Claude to add a test that reproduces the bug (using the report's reproduction steps) and confirm the test fails. Then make the fix and run `/sc:test tests/billing/test_invoice_job.py --coverage` to confirm the new test and the existing ones pass.
   - **Ordinary planned fix:** `/sc:workflow "<the supported fix described in REPORT.md, with a test that reproduces the bug>" --depth standard --handoff none`, then read the printed plan and use `/sc:implement <printed plan path>` only when execution is requested. If a planning offer already produced an adequate approved plan, use it directly. Do not diagnose again merely to obtain planning.
   - **Explicit or exceptional MDTM fix:** use level 4 only for explicit MDTM selection or an exceptionally complex, long-running program needing its research/checklist/phase-panel machinery. If an explicitly requested deep-plus-fix offer is accepted, its current route creates an MDTM task for `/task`; read its checks and final audit. Ordinary deep diagnosis can instead feed the separate workflow plan above.
   - **Unconfirmed, failed or blocked report:** do not plan or apply a speculative fix or bypass its blocker. Preserve the report's evidence, hardening blockers and authorization limits; follow only its supported conditional checks or next steps. A deeper investigation is not an unconditional rerun instruction.

4. **Ship.** Workflow 3.11.

### 3.5 Investigate how something works, or whether an idea is feasible

| You want to know | Run and stop |
|---|---|
| How our system works or whether a change is feasible | `/tech-research "<question, purpose, code paths>"` produces a code-grounded report. Stop there unless implementation planning was requested. |
| Current external, academic, competitive, market, standards or technical evidence | `/sc:research "<question and constraints>"`. Preserve requested depth: quick, standard, deep or exhaustive. Do not force deep over an explicit preference. Stop at the evidence and synthesis. |
| Whole-project or module static health | `/sc:analyze <target>`. No focus is required for a broad assessment. Add the requested quality, security, performance or architecture focus, quick/deep depth or text/json/report format only when applicable. It reports findings, not source fixes. |
| An audience-tailored explanation | Ask directly for a simple answer, or `/sc:explain <target>` with the requested basic/intermediate/advanced level, text/examples/interactive format and domain context. Inspection breadth alone does not require implementation planning. |

### 3.6 Make a hard decision or compare options

| Situation | Run and stop |
|---|---|
| The idea or requirements are still unclear | `/sc:brainstorm "<the idea, who it is for, the main constraint>"`. Stop at merged requirements. Later requested planning uses workflow/implement, not an automatic task-file handoff. A brainstorm dry run can write preparatory artifacts; it is not a zero-write promise. |
| Compare existing designs, plans or drafts | `/sc:adversarial --compare <file-a>,<file-b>` requires 2-10 existing readable files. Keep requested depth, focus, interaction and output. Stop at comparison and merged artifacts, not product implementation. |
| Generate competing designs from a source | `/sc:adversarial --source <file> --generate <type> --agents <specs>`. Preserve all three required inputs. Do not turn a single source into an invalid one-file comparison. |
| Continue an adversarial pipeline | `/sc:adversarial --pipeline @<pipeline.yaml> --pipeline-resume --output <existing output>` preserves the pipeline and checkpoint location. Pipeline mode is mutually exclusive with compare and source/generate/agents modes. |
| Review a populated spec, PRD or TDD | `/sc:spec-panel @<file>`. Critique is the recommendation default for a critique request without another supported mode, not a forced command default. Preserve discussion or socratic requests, focus and format. A business-viability question belongs to business-panel, not spec critique merely because its input is a PRD. |
| Explicitly derive a scoped spec from a populated document | `/sc:spec-panel @<file>` with the derivation intent in the request. Obtain the required target release when missing for TDD input; preserve consent before changing the input. Raw PRD/TDD authoring belongs to the document skills. Do not invent a downstream flag from prose-only examples. |
| Use swarm, choose its settings or request multi-model review | `/sc:swarm-wizard --goal "<goal>" --target <path>` preserves the supplied goal, target and output. Missing goal/target is gathered by interview; a target needs at least 50 non-whitespace bytes. The installed swarm CLI must be reachable. A real run requires explicit go-ahead, a passing stub dry run and the T2ProxyUrl/T2ProxyKey/T2Model01 environment contract. Command and protocol disagree on missing-proxy STOP versus stub fallback: disclose this contract gap, not a guaranteed fallback. Settings help does not authorize a real launch. Run preparation and previews write artifacts. |
| Business viability, market position or strategic choices | `/sc:business-panel <document-or-inline-content>` uses simulated expert perspectives. Preserve discussion/debate/socratic/adaptive mode, requested experts, focus and synthesis-only output. Stop at analysis, not a measured commercial prediction or automatic specification rewrite. |

### 3.7 Refactor or clean up code

1. **Audit only when that is the requested outcome.**
   `/sc:cleanup-audit <folder>` writes reports and checkpoints under `.claude-audit/`; it does not edit audited inputs. Preserve the requested surface/structural/cross-cutting/all pass, domain focus and batch size. Structural and cross-cutting work need the earlier pass context. Hidden paths and BMAD-owned paths are excluded by an unremovable scope floor; a hidden-config-only target is not exhaustively audited. For such a target still route to `/sc:cleanup-audit`, state that its paths fall under that exclusion floor so coverage cannot be exhaustive, and never claim exhaustive coverage. Do not force all passes. **For report-only auditing, stop here: no cleanup, improve or commit.**

2. **Small, contained cleanups or improvements, only when requested.** Commit first so every change can be undone. Choose the operation requested, not both by default:
   `/sc:cleanup src/billing/ --type code --safe --interactive` for cleanup, or `/sc:improve src/billing/ --type maintainability --safe --interactive` for maintainability.
   Improve also supports quality, performance or style. Preserve the supplied type, safety and interaction controls. `--interactive` asks before complex changes, but some edits still apply automatically: cleanup can remove unused imports and unreferenced code; improve can change formatting, naming, imports and annotations. Review `git diff` before keeping anything. An improvement-only request does not authorize compulsory cleanup/deletion. Neither command's example-only preview or validation controls establish a supported flag.

3. **Structural refactors or work outside the contained-folder exception:** write down the intended change and acceptance criteria, then use `/sc:workflow <spec path>`, read its plan, and run `/sc:implement <printed plan path>` when execution is requested (3.2). Many files or risk alone do not select MDTM; level 4 needs explicit selection or a stated exceptional complex long-running machinery need. The cleanup exception does not cover an architectural migration.

### 3.8 Run tests and check coverage

- `/sc:test <target>` runs an existing suite. Preserve a requested unit/integration/e2e/all type, coverage or watch setting. Watch alone does not add fix. E2E needs its browser tooling and services ready; tests can write caches, reports, fixtures and external state, so execution is not read-only inspection.
- Only an explicit `/sc:test <target> --fix` request permits its simple-failure repair behavior; disclose source edits and retain applicable planning limits. A failing-test diagnosis and YAML tier validation are different outcomes (3.4 and 3.13). Do not invent a numerical ceiling for what it can repair.
- `/sc:test` does not write new tests. For ordinary planned test authoring, include tests in the spec and workflow plan (3.2); for a bounded direct change, ask Claude to write them (3.4 step 3). Existing approved plans keep their executor.

### 3.9 Document existing work

These skills document things that already exist. A PRD and a TDD are planning documents for something you are about to build; see 3.1.

| You need | Run |
|---|---|
| A technical reference for a built feature: architecture, how it works, how to extend it | `/tech-reference "Document the usage billing feature. Code: src/billing/, src/api/metering/. Audience: engineers who maintain it. Output: docs/billing/billing-technical-reference.md."` |
| Step-by-step instructions to install, deploy, or operate something | `/operational-guide "Write the operational guide for deploying the billing worker to staging and production, including rollback. Sources: deploy/worker.yaml, scripts/deploy_worker.sh. Audience: on-call engineers. Output: docs/billing/billing-worker-deploy-operational-guide.md."` |
| A README for a project, module, or package | `/readme "Write the README for the src/billing/ package: what it does, setup, configuration, and how to run its tests. Use docs/billing/billing-technical-reference.md if it exists. Audience: new engineers. Output: src/billing/README.md."` |
| Focused inline docstrings, external reference, API reference or a user guide | `/sc:document <target> --type <inline/external/api/guide> --style <brief/detailed>` uses the requested type and style. Inline output edits source: retain the direct-change limit or use a written workflow plan when exceeded. Do not silently replace a short docstring request with a full TDD. |
| Coordinated project-wide documentation and navigation | `/sc:index <target>` with requested docs/api/structure/readme type and md/json/yaml format; not the compact repository map from index-repo. |

All document routes retain supplied source paths, audience, output intent and existing project standards. Template-led README, operations and technical-reference skills own their research/review lifecycles. A requested Technical Design Document uses `/tdd` or `/sc:tdd`, not test-driven development, and stops at that document (3.13).

### 3.10 Check plans or finished work without changing them

- **Pre-execution coverage:** `/sc:reflect --mode pre --spec <spec>` requires the spec; tasklist is optional. Include `/sc:reflect --mode pre --spec <spec> --tasklist <plan>` when a plan exists. Do not manufacture a missing tasklist or rebuild an adequate approved plan just to audit it.
- **Consume existing checks:** a workflow plan's advisory pre-review is printed and recorded in `return-contract.yaml`; consume it rather than repeat it. For MDTM, read `reflect_pre` and resolve its Open Questions. A genuinely separate governing spec can warrant a separate comparison; a skipped/failed review is not a passing check.
- **Post-execution audit:** use either `/sc:reflect --mode post --diff <ref-or-diff-path> --no-promote` or `/sc:reflect --mode post --task-log <log-path> --no-promote`. Spec and tasklist are recommended context when available, not mandatory together. One baseline commit includes the current working tree; a commit range audits that range. Intended new files must be staged to appear in the working-tree diff. Preserve the actual baseline and never stage generated mirrors just for an audit.
- **Report-only:** post audits need `--no-promote` to suppress folder promotion; they still write audit artifacts and may run verification tools subject to their execution permissions. Do not substitute a headless auto-fix wrapper for interactive report-only work. Preserve failed, partial, inconclusive or blocked results, carried hardening blockers and human-decision requirements.
- **Optional remediation:** standard `/sc:reflect --remediate` offers workflow planning only after the audit and acceptance; execution is a separate user action. Requested `/sc:reflect --depth deep --remediate` currently couples remediation to MDTM. Deep alone does not remediate. For ensemble review plus ordinary planning, `/sc:reflect --tier 2 --depth standard --remediate` avoids selecting the deep-MDTM branch. Consume workflow's built-in pre-review rather than reflecting twice. Legacy task analyze/validate aliases remain supported; prefer mode syntax for new handoffs.

### 3.11 Review only, or deliberately ship and open a pull request

**Review-only stop:** `/sc:auggie-review <PR-number-or-URL> --no-post-pr --no-remediation-offer` keeps findings local and suppresses the planning offer. For a diff use `/sc:auggie-review --diff <base>...HEAD --no-post-pr --no-remediation-offer`; for a snapshot use `/sc:auggie-review --snapshot <path> --no-post-pr --no-remediation-offer`. Do not append commits, pushes or PR creation to findings-only work. Resolve a real target, the Auggie CLI and Git working tree, plus authenticated gh for a PR. Preserve requested depth, focus, output and internal reviewer selection. The Auggie model defaults to prism-b when not overridden; revagent chooses an internal reviewer, not Auggie's model.

Accepted ordinary remediation offers use design then workflow/implement; accepted deep-review offers currently select task-builder/task. Planning never authorizes execution. For deep findings followed by ordinary planning, suppress the automatic offer and separately hand accepted findings to workflow. The internal design referral has an undeclared destination option: that contract gap must not be copied into a runnable chain or silently repaired here.

**Shipping only when requested and authorized:**

1. Commit locally on the feature branch only when authorized.
2. Run `/code-review`; use `/security-review` when authentication, permissions, secrets, input or paths changed. Authorize and record any fixes before branch review.
3. Review the branch with `/sc:auggie-review --diff origin/<main branch>...HEAD --no-post-pr --no-remediation-offer`.
4. Push only with approval, preserving the intended origin repository and head branch.
5. For creation, `/sc:pr-submit --head <branch> --title "<title>" --body "<body>"` needs authenticated gh. For attachment use `/sc:pr-submit --pr <number>` instead of creating another PR. For continuation use `/sc:pr-submit --resume <run-log.jsonl>` and retain that monitor's PR, repository, head and recorded authority.
6. Select **exactly one** monitor ceiling for the chosen operation, before emitting the handoff:
   - Creation only, or absent/uncertain review App: monitor 0.
   - Proposals without source edits: monitor 1.
   - Local fixes without publication: monitor 2 (halts before push).
   - Requested and authorized full loop: monitor 3 (the current command default). This may commit and push fixes, retrigger review, and reply to and resolve fixed threads.

Pass the one selected monitor value explicitly. A stronger project rule can require monitor 3: if that conflicts with the requested lower ceiling, disclose the policy conflict and withhold execution, never silently increase authority. Monitored runs require the review App, matching PR head checkout/commit and CI-wait prerequisites. They are attended in-session loops, not daemons. Monitor 3 publishes only the cycle's permitted fix commit to origin, never an upstream or protected/default branch, and never an unrelated local commit range. Silence or timeout is not a clean review. Recommending any branch performs no Git/GitHub action.

### 3.12 Resume after a crash or a lost session

There are two ways to resume. Use the first if you set it up; the second always works.

**1. Reopen the conversation (ccsession).** Do this before you need it: start the session with `ccsession <name>`, or inside Claude Code run `/rename <name>` and send one more message (or quit) so ccsession records it. Later, from a terminal in any worktree or copy of the same repo (outside git, the same folder), run `ccsession <name>` to reopen that conversation. `ccsession --here` lists the names for this repo. `superclaude install` sets this up; `~/.local/bin` must be on your `PATH`.

**2. Restart from the work's own files.** This works in a brand-new conversation.

- **A supplied PR monitor log.** `/sc:pr-submit --resume <run-log.jsonl>` resumes that PR monitor, not general implementation. Preserve recorded repository, PR, head and ceiling; do not create a second PR. A plain existing-PR attachment uses `/sc:pr-submit --pr <number>` with one explicitly selected ceiling (3.11).
- **A task file (`/task`).** Run `/task <path to the task file>` again. It continues from the first unchecked item.
- **A simple plan (`/sc:implement`).** Run `/sc:implement .dev/tasks/to-do/<id>/<id>.md` again. The `progress.md` file beside the plan records every finished step, and the run continues from the first unfinished one. If the folder has already moved to `.dev/tasks/done/`, the work is finished. Folders named `TASK-WF-*` are `/sc:workflow` plans: run them with `/sc:implement`, never with `/task`.

`/sc:save` and `/sc:load` store and load project memory as plain markdown files under `.superclaude/memory/`. They are not a way to resume work or a guarantee of complete executor state. Other command-owned continuations keep their own supplied pipeline, output folder, validated proposal or document-task input; do not convert them into task-builder or a fresh generic plan. Clarify the artifact when it is not known.

### 3.14 Known contract limitations and lifecycle

- **Roadmap and fidelity activation:** keep generation's positional-input command separate from its legacy multi-spec/template protocol, and keep the directory validator separate from the investigative roadmap/spec auditor. Auggie's design destination referral is undeclared; offer separate ordinary planning from accepted findings, not a certified broken chain.
- **Other deferred differences:** spawn's final decomposition-only stop wins over earlier execution prose. Swarm's missing-proxy STOP/fallback disagreement is disclosed without promising a real run or fallback. Load's example-only checkpoint option is not executor recovery. Task's classification-before-tools prose does not waive the governing skill-first rule; do not duplicate its internals here. Active plugin copies can lack skills or safeguards even when command files exist: verify them or report unavailable/contract gap. Planning depth is not a guarantee of multi-session plan generation, while implement execution is resumable. Validate-tests needs a real YAML suite. Startup status messages do not prove agent/PM activation.
- **Retired framework identities:** estimate, the sc dispatcher, select-tool and task-mcp are not current runnable framework targets, even if readable installed remnants survive. Answer retirement questions with the underlying intent and a current independently verified alternative; do not trust task-mcp's stale replacement metadata or resurrect bypass flags. Independently authored installed-only/custom commands remain eligible; uncertain ownership of a same-name override needs clarification, not blanket rejection.

## 4. Rules everyone follows

- **Write it down.** Plans, research, and findings are saved to files (most under `.dev/`), not only into the chat. If the session dies, the files are what survives.
- **Let a skill finish.** Once a skill starts, let it run through all of its steps. Do not stop it halfway or skip steps.
- **Do not repeat a skill's own checks.** Task files already run reviewer panels, tests, and a final audit. Read their results instead of running the same checks again.
- **Never turn off a quality check.** Do not disable or skip a reviewer step to save time. If one seems wrong or too slow, raise it with your lead.
- **Read a plan or task file before you run it.** Make sure it matches what was agreed.
- **Never push without approval.** Commit locally, show your lead what changed, and push only when they say go. One exception: after that approved push, `/sc:pr-submit --monitor 3` (workflow 3.11) pushes the fixes it makes for review findings and failing CI checks without asking again. If your lead wants to see those fixes before they are pushed, use `--monitor 2` instead: it makes the fixes locally and stops before pushing.
- **Do only what was asked.** If you think something else should change, suggest it instead of doing it.
- **When unsure which tool to use,** run `/sc:recommend "<what you want to do, and why>"` or ask your lead before starting anything large.
- **A `/sc:` command whose file names a skill starts by loading that skill.** If Claude answers such a command without loading it, start a new chat and run the command again. Commands whose file names no skill (for example `/sc:help`, `/sc:explain`, `/sc:test`) run from their own file, so no skill load is expected.

Where this guide says "your lead", read "yourself" if you work alone.
