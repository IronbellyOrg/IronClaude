- proto/ and pkg/tuibbssdk carry no separate license: no LICENSE file in either directory, and no SPDX or copyright header (proto/v1/plugin.proto has no license line; pkg/tuibbssdk/doc.go:1-5 has none). They therefore sit under the root AGPL-3.0 LICENSE by default.
- Section 13 framing: TUIBBS states the clause applies "in full" because users interact with it over SSH (NOTICE:24-26), and the obligation "is triggered by operating the service; it is not limited to distributing the binary" (NOTICE:33-34). NOTICE says nothing about separate programs that talk to TUIBBS.
- Plugin architecture (from docs, not code-verified): four tiers; tier1 compiled-in Go (in-process), tier2 "gRPC subprocess via hashicorp/go-plugin v1.8.0", tier3 gopher-lua sandbox, tier4 wazero with no runtime activation at v1 (docs/decisions/adr-x5-module-dispatch.md:24-29). Tier 2 modules run "in an isolated child process" invoked over gRPC with per-launch AutoMTLS and a handshake cookie (internal/plugin/grpcsub/README.md:3-5, 25-29). The host launches the child (`Open(Config)`; internal/plugin/grpcsub/README.md:10-12). Modules are declared by a `modules/<name>/module.toml` manifest (internal/plugin/README.md:158-163). Payloads cross the boundary as opaque `[]byte` plus a ContentType (docs/decisions/adr-x5-module-dispatch.md:73-81). The wire contract is `proto/v1/plugin.proto`, `package tuibbs.plugin.v1`, `service ModuleService` (proto/README.md:3-4).
- The plugin-side helper `Serve(ModuleServer)` lives in `internal/plugin/grpcsub` (internal/plugin/grpcsub/README.md:13-14). Go's internal-package rule means code outside module `github.com/tuibbs/tuibbs` cannot import it; a Python plugin would have to implement the go-plugin handshake, AutoMTLS and `ModuleService` itself from the .proto. Feasibility of a Python tier-2 plugin under AutoMTLS: UNVERIFIED.
- `pkg/tuibbssdk` is "the only TUIBBS code path importable from outside the host module" (pkg/tuibbssdk/doc.go:1-3) and must not import internal/ (pkg/tuibbssdk/README.md:6-8). `pkg/tuibbs/` (theme, components, notify) does import internal/ packages (pkg/README.md:12-18). A Python program would import neither; it would only use the .proto schema, or files.
- A separate MCP host exists that speaks the Model Context Protocol through `modelcontextprotocol/go-sdk`, with no TUIBBS proto (proto/README.md:9-10; docs/mcp-tools.md exists, not read). It is another possible arm's-length interface; fit: UNVERIFIED.
- Facts that bear on "separate work" (inputs for the reviewer, not a conclusion): (a) a snapshot file is plain data exchange with no TUIBBS code in the Python process; (b) an independent gRPC service would use only the AGPL-licensed .proto schema, possibly generated into Python stubs; (c) a go-plugin tier-2 child is launched, configured and lifecycle-managed by the TUIBBS host, speaks a host-defined protocol and runs as part of the service SSH users interact with; (d) becoming a TUIBBS module in Go (tier 1) means compiling into the AGPL binary.

- Network path needed for each option (reasoning from the facts above; Coder network rules are UNVERIFIED):
  - (i) Snapshot file: the observer writes a file in the Coder workspace; something must copy it to the TUIBBS host (outbound scp/rsync from Coder to the host's admin SSH, which is a different daemon from TUIBBS's port 2222), or TUIBBS must pull it, which needs inbound access to Coder. Push from Coder is the simplest path. TUIBBS has no file-ingest feature today; a module or a TUIBBS change would have to read it.
  - (ii) gRPC: as a tier-2 go-plugin child, the observer must run on the TUIBBS host itself (the host launches it; go-plugin talks over a local socket, UNVERIFIED for this repo), so Orca data still has to reach that host by some other channel. As an independent service, either TUIBBS dials the observer in Coder (inbound to Coder: needs a tunnel or port forward) or the observer dials TUIBBS, which has no gRPC listener today and would need a new one.
  - (iii) SSH-served view: users already reach TUIBBS on 2222, so a TUIBBS module view needs only the Orca data on the TUIBBS host (same transfer problem as (i)). Alternatively the observer can serve its own terminal view from Coder over Coder's SSH, with no TUIBBS involvement.

- The AI-session line (v1.1 spawn, v1.2 read-only watch, v1.3 persistent lifecycle, "observe-only", control deferred to v1.4) is the closest existing feature to an agent observer (CHANGELOG.md:49-54, 65-67).

## Verdict

This is not legal advice. TUIBBS is AGPL-3.0-only with no plugin, linking or interface exception, and its proto/ and SDK carry no separate license, so any reuse of the TUIBBS proto or a host-launched tier-2 plugin is an open question for a license review; a snapshot file, or an independent observer that uses no TUIBBS code, keeps the clearest separation.
Copyright sits with an undefined "The TUIBBS Authors", in practice one human (Ryan wiancko / ironbelly) with heavy Claude co-authorship and no CLA, so adding an exception is feasible but needs that holder's decision.
TUIBBS is a young (five-month), private, dogfood-only hobby project with good CI and 338 test files but no successful release run; it exposes only SSH on port 2222, so any integration needs Orca data moved from Coder to the TUIBBS host first.
