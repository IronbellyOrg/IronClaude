**Karl Wiegers** (lead). "Lacks measurable acceptance criteria: how would you validate compliance in production?"

- [F9] Requirement-to-acceptance traceability is incomplete. Severity MAJOR (non-blocking). Of WC-1 to WC-12 (`SPEC:59-70`), WC-1, WC-3, WC-6 and WC-12 have no acceptance check anywhere in section 7; WC-10 is checked only for pr-submit (AC-4.3, `SPEC:210`); WC-11 is checked only for `/sc:save` (AC-3.4, `SPEC:207`); WC-7 is checked by AC-0.4 (`SPEC:194`), which says "verified in the step-5 transcript" although step 5 (`SPEC:184`) only searches for `AskUserQuestion`. Priority High. Quality impact: Testability 5/10 to 8/10.
- [F10] The status vocabulary is under-defined. Severity MAJOR (non-blocking). `partial` is listed (`SPEC:62`) and mapped to `succeeded` (`SPEC:63`, `SPEC:263`) but never defined per command, so two implementers will classify "cleanup applied the safe items and deferred the rest" differently. A `succeeded` outcome settles the Task (`CAPS:77`), which makes dependents ready in the ready view (`CAPS:86`); only the coordinator reading the report first (`SPEC:73`) prevents a dependent starting on partial work. `blocked` maps to `--outcome failed` (`SPEC:63`), so the Orca Task becomes `failed` and its dependents stay blocked until a `--retry-of` replacement completes (`CAPS:90`); the spec's own word `blocked` also collides with Orca's Task status `blocked` (`CAPS:89`). No retry cap or coordinator procedure for a blocked Task is given, and no schema version is carried, although the existing workflow contract is already versioned ("contract 1.1", `INV-B:272`) and its `status` vocabulary was never compared with the new four-value set (`SPEC:62`, `SPEC:261-262`). Recommendation: define `partial` as "deliverable usable, listed items not done" with a mandatory `incomplete_items` list; state that the coordinator treats `partial` as not-ready for dependents unless the brief says otherwise; add `contract_version`; add a coordinator procedure for `blocked` (answer, then `worker-start --retry-of` with the answer as a flag). Priority High. Quality impact: Consistency 6/10 to 8/10.

**Michael Nygard.** "What happens when this fails? Where are the monitoring and recovery mechanisms?"

- [F5] A stale contract can be read as the current result. Severity MAJOR (blocking). WC-4 has the command write `return-contract.yaml` "on every outcome" (`SPEC:62`) and WC-5 sets `--outcome failed` only "when ... no report exists" (`SPEC:63`). WC-6 lets a resume or retry run reuse the same directory (`SPEC:64`; resume flags in `SPEC:83-91`, `SPEC:109`, `SPEC:114`, `SPEC:118`), and WC-3 re-invokes the command "with the answer as a flag" after a block (`SPEC:61`). Nothing says the contract is removed or marked `running` at start. Attack state trace: attempt 1 ends with `status: blocked`; the coordinator answers; attempt 2 starts in the same directory, the model is killed or hits context exhaustion before the final write; the old file still exists, so WC-5 sees "a report", reads `blocked`, and the worker (if still alive) reports `failed` for the wrong reason, or the coordinator opens the stale file and acts on it. A contract written only at the end also cannot distinguish "crashed" from "never started". Recommendation: the command writes `status: running` (with the dispatch's start time) as its first action and replaces it on every exit path; WC-5 treats `running` as no report. Priority High. Quality impact: Reliability 5/10 to 8/10.
- [F8] The liveness requirement cannot be met by the mechanism it prescribes, and is untested. Severity MAJOR (non-blocking: the consequence of missed heartbeats is itself UNVERIFIED, `CAPS:130`, `CAPS:182`). WC-10 splits Bash waits to at most 4 minutes (`SPEC:68`). The long silent stretches in this spec are mostly Agent-tool calls (cleanup-audit waves of 7-8 agents, tdd tiers, troubleshoot Tier 2, `INV-A:42`, `INV-B:221`); one such call blocks the top-level session for as long as the longest subagent runs, and the session cannot heartbeat in between. The only live check of cadence is AC-4.3 for pr-submit (`SPEC:210`), and 7.2 never measures heartbeat gaps. pr-submit's own iteration length is UNVERIFIED (`SPEC:283`). Recommendation: first settle whether heartbeat age matters to Orca liveness (`CAPS:182`); if it does, state what a fan-out command must do (bounded waves) and test it; if it does not, downgrade WC-10 to advice. Priority Medium. Quality impact: Reliability 6/10 to 7/10.
- [F12] The spec weakens binding README evidence on an inference. Severity MAJOR (non-blocking). The README lists "a supervised Claude worker that waits on a question fails Orca's 60-second readiness limit" as evidence (`README:13`). Section 1.4(2) narrows it to a pre-input-box wrapper prompt and states that a command's own question "comes after readiness, so it does not fail `worker-start`" (`SPEC:44`). The same capabilities inventory records that for Claude the task is passed on the command line, not typed (`CAPS:47`), so a command whose first step is a gate (cli-eval missing `$1`, "STOP and ask", `INV-A:44`) runs while the TUI may still be starting. WC-11 forbids two workers writing the same file (`SPEC:69`) and the brief states "worktree placement" (`SPEC:73`), but Orca workers share the current worktree by default (`CAPS:115`) and the spec does not mark which commands change source or run builds (implement, cleanup, improve, document inline, test `--fix`, build, `INV-A:40`, `INV-A:47`, `INV-A:51`, `INV-B:234`). `/sc:test` running beside `/sc:implement` in one tree is a race even if no file is written twice. Recommendation: add an "edits the tree" column to section 3 and a rule that two edit-capable workers get separate worktrees. Priority Medium. Quality impact: Reliability 6/10 to 8/10.

=== ADVERSARIAL ANALYSIS ===

Template (FR-3). Each entry names the finding it supports; the full critique entry is in the buckets above.

1. I can break this specification by **Accumulation Attack** (F1, CRITICAL). The invariant at **section 1.3 / section 2.3 (`SPEC:39`, `SPEC:73`): "several workers, then one worker on their reports" delivers all N reports** fails when **one or more producer Tasks end failed or blocked**. Concrete attack: before: 4 troubleshoot Tasks started, 1 aggregator Task with `--deps` on all 4. Step 1: producer 3 stops on the `--depth deep` short-input STOP and writes `status: blocked`. Step 2: WC-5 sends `--outcome failed`, so Task 3 is `failed`. Step 3: Orca refuses to start the aggregator (`task_not_startable`, `CAPS:88`, `CAPS:90`). After: 3 usable reports are stranded and no rule says who starts the aggregator, with which inputs, or with what minimum. Variant: 3 of 4 fail, 1 report remains, and the aggregator is an adversarial run that needs at least 2.
2. I can break this specification by **Sequence Attack** (F2, CRITICAL). The invariant at **section 6, P1 (`SPEC:159`): "flag accepted by every command; gates converted later"** fails when **a coordinator uses the flag between P1 and P2**. Concrete attack: before: P1 merged, P2 not. Step 1: brief says `/sc:auggie-review 412 --unattended`. Step 2: the command accepts the flag as a no-op, runs, posts `gh pr review --comment` with no prompt (`INV-A:38`). Step 3: it ends the turn on the remediation offer. After: a GitHub post that WC-9 forbids and a worker that never sends `worker_done`.
3. I can break this specification by **Sequence Attack** (F5, MAJOR). The invariant at **WC-4/WC-5/WC-6 (`SPEC:62-64`): "a report exists iff the run wrote it"** fails when **a resume or retry reuses the output directory**. Concrete attack: before: `<dir>/return-contract.yaml` holds `blocked` from attempt 1. Step 1: coordinator answers and starts `--retry-of`.
