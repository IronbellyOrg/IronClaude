## 1. Decision: Orca coordinates, commands stay the units of work

### 1.1 The decision
An Orca coordinator plans the work, creates Tasks, starts one worker per Task and reads each worker's report. Each IronClaude `/sc:` command stays a self-contained unit of work: one worker (a top-level Claude session in its own Orca terminal) runs one command and reports it with `worker_done`. Commands themselves contain no Orca calls. What changes in the commands is limited to the worker contract in section 2: a way to run without a person, a fixed report file, and a resume or safe re-run.

### 1.3 Rejected alternative: commands call Orca internally
In the alternative, a command would itself start Orca workers for its fan-out (for example one worker per `/sc:tdd` research agent), send its own `worker_done`, and call `orca orchestration ask` for its questions. It is rejected for these reasons:

| # | Reason | Evidence |
|---|---|---|
| R1 | It cannot run as a worker at the current setting. Nesting depth is 1 on this machine and "1 means a coordinator dispatches workers and those workers may not dispatch further", so a command that calls `worker-start` from inside a worker would be refused with `nested_worker_depth_exceeded`. Which call sites enforce the check was not traced; `worker-start` and `dispatch` are presumed (UNVERIFIED, `CAPS:103`). A new Run does not reset depth, and Orca's own advice is "Do the work in this terminal". The two designs exclude each other unless the user raises the depth setting. | `CAPS:97-101,103`; `orca-data.json:1` quoted at `CAPS:98` |
| R2 | It breaks standalone use. Commands are installed to `~/.claude/` and run in other projects. Without a running Orca every orchestration call fails with `runtime_unavailable`; outside an Orca terminal the caller must pass `--from`; and a session with no live preamble must not send lifecycle messages at all. | `CLAUDE.md:74`; `CAPS:147` (`cli-error.js:49-53`); `CAPS:148-149` (`[G]` line 41; `terminal-identity.js:213-215`) |
| R3 | A command cannot own the completion message. `worker_done` is accepted only from the dispatched pane, and the Task and Dispatch IDs exist only in the preamble given to the worker session, not in the command's arguments. | `CAPS:76`, `CAPS:150` (`[H:send]` line 40); `CAPS:148` (`[G]` line 38) |
| R4 | The executable name differs by platform and setup (`orca-ide` on Linux outside Orca terminals, an `orca` shim inside them), so command text that calls Orca would carry platform logic. | `CAPS:145` (`/opt/Orca/resources/bin/orca-ide:16`; `linux-orca-cli-shim/orca:2`) |
| R5 | It would create a second orchestrator below the coordinator. The inventories already mark the commands that orchestrate (`/sc:agent`, `/sc:pm`, `/sc:spawn`) coordinator-only because two controllers compete. | `INV-A:90`; `INV-B:285-286` |

What the alternative would have given, and how this spec gets it instead: per-unit liveness, Task records and independent retry for heavy fan-out. Orca keeps those records only for workers the coordinator starts (`CAPS:158`). Under this decision the coordinator gets them by splitting the work into separate worker Tasks (for example several `/sc:troubleshoot` workers, then one `/sc:adversarial` worker on their reports), not by commands calling Orca. How the aggregator's inputs are chosen when some producers fail is the fan-in rule in section 2.4 (F1).

2. **The 60-second readiness evidence is binding; how far it reaches is not settled (F12).** The README records that a supervised Claude worker that waits on a question fails Orca's 60-second readiness limit (`.dev/orca-command-refactor/README.md:13`). The observed failure was a question shown *before* Claude reached its input box (`EVIDENCE.md:39`, a shell wrapper's session-name prompt). Once the worker is past readiness, Orca reports a worker waiting on a prompt as "healthy, not failed" (`CAPS:52`, `CAPS:129`), and the failure mode is then a silent stall with no `worker_done`, seen only through `worker-show`'s `agentWait` or a missing report. What is not shown is whether a command whose very first step is a gate can run before readiness: for Claude the task is passed on the command line, not typed after the input box appears (`CAPS:47`), and a command such as `/sc:cli-eval run` with no argument starts with "STOP and ask" (`INV-A:44`). WC-2 makes the design safe in both cases, because under `--unattended` no gate waits. Section 2 covers both cases.
3. **Agent-tool fan-out inside a worker has no proven limit, but no proof of none either.** No Orca limit on subagents was found, and whether a subagent's Bash `send` would be accepted as the worker's own is UNVERIFIED (`CAPS:155`, `CAPS:159-160`, `CAPS:186`). The contract forbids subagents from sending lifecycle messages, so the design does not depend on that answer.

## 2. The worker contract

### 2.1 Terms
- **Worker run**: a session that received an Orca preamble carrying a Task ID and a Dispatch ID. Only such a session may send lifecycle messages; a session the user started, inside or outside Orca, is an ordinary session (`CAPS:148`, `[G]` lines 38 and 41).
- **Unattended mode**: the behaviour a command switches to when its caller passes `--unattended`. It is the only command-side change the contract asks for besides report files and resume. It names no Orca command, so the same mode serves any caller that has no person at the keyboard. How the mode is selected (flag versus detecting the preamble) is open decision D1 in section 9; this spec is written for the recommended flag.
- **Token rule for the switch (F6)**: unattended mode is on only when `--unattended` is a standalone argument token on the command line, outside any quoted argument, topic, inline content or pasted text. The same characters inside a quoted topic or inline specification (for example `/sc:explain "what does --unattended do"`) leave the command in normal mode. The rule is written in full once in the contract file and tested by AC-1.5; because a command decides its mode before it reads that file, each command's `## Unattended mode` section also restates the switch in one line (the token rule) and names the `contract_version` it implements (N22).
- **Report directory (F4)**: `--report-dir <dir>`, a new directory-valued flag on every command that accepts `--unattended`. It is independent of any file-valued `--output` that a command already has. The coordinator passes it in the brief, so the report location is known before dispatch.
- **Contract file**: one shared document, named `src/superclaude/core/WORKER-CONTRACT.md`, installed to `~/.claude/WORKER-CONTRACT.md`. Core `.md` files install to `~/.claude/` (`src/superclaude/cli/install_core.py:4,33`; `CLAUDE.md:83,408`), and the new name must be added to `KNOWN_CORE_FILES` (`src/superclaude/cli/install_core.py:13-24`). Each changed command adds a short `## Unattended mode` section that lists only its own gate resolutions and report file and points to the installed contract path, so the shared rules are written once.
- **Contract file layout (F14)**: the file has two parts. Part A is command-facing: the rules of WC-2, WC-4, WC-5 (status values only), WC-6, WC-9, WC-11, the token rule, the report schema with a `contract_version` field (value `1`), and no Orca command names. Part B is for the worker session and the coordinator: WC-3, WC-5, WC-7, WC-10, WC-12 and the brief template. Part B links to Orca's own guide (`orca-ide skills get orchestration`) for Orca behaviour instead of copying it, and states the Orca build its examples were checked against (`1.4.237-aidev02`, `CAPS:8`). Fail-closed rule: a command in unattended mode that cannot read `~/.claude/WORKER-CONTRACT.md` resolves every gate as blocked and still writes its report (with `contract_version: 1`); it never falls back to a prompt. The same rule covers a file older than the command (a file whose `contract_version` is lower than the `contract_version` the command's own `## Unattended mode` section names, N22). The command decides it is in unattended mode from the one-line switch in its own section, so the fail-closed rule does not depend on reading the contract file.

### 2.4 Fan-in: several producers, one aggregator (F1)
When the coordinator splits work into N producer Tasks and one aggregator Task that reads their reports (for example four `/sc:troubleshoot` workers, then one `/sc:adversarial` worker, section 1.3), these rules apply.
1. The aggregator's brief lists its input report paths explicitly. It is not given dependencies as its input list: Orca refuses to start a Task whose dependency failed (`task_not_startable`, `CAPS:88`, `CAPS:90`), and it counts a `partial` report as a success (WC-5).
2. The brief names a minimum number of usable inputs M for the aggregator. For `/sc:adversarial` M is 2: its Mode B runs 2-10 generator agents and 2-10 advocates (`INV-A:35`), and a comparison of fewer than two artifacts has nothing to compare; that reading of the range is this spec's, UNVERIFIED (N24).
3. A producer's report is usable only when its `status` is `succeeded`, or `partial` with the brief stating that partial inputs are accepted; a producer from a command outside the contract work is usable when the success condition in its section 3.1 row is met (WC-5; N2). The coordinator opens each report (WC-5 procedure) before counting.
4. When some producers end `failed` or `blocked`, the coordinator first applies WC-5's retry procedure to each of them: the answered retry for a `blocked` one, a plain retry for a `failed` one, both within the cap of 2 retries per Task (N18). A `partial` producer the brief does not accept is unusable: it is left out of the input list and the aggregator Task carries no `--deps` on it, although Orca settled it as completed (N18). If the number of usable reports is still at least M after that, it creates the aggregator Task with no `--deps` on the failed producers, lists only the usable reports, and says in the brief how many inputs were dropped. If it is below M, the coordinator does not dispatch the aggregator and reports the shortfall (which producers, their `blocked_question` values) to the person.
5. Worked count: 4 producers, 1 `blocked`: 3 usable, aggregator runs on 3 after the retry procedure has failed to rescue the fourth. 3 `blocked`: 1 usable, below M = 2, so no aggregator and a shortfall report. 4 `succeeded` with one `partial`: 4 reports, 3 complete; the brief decides whether the fourth counts (rule 3).

## 8. Non-goals
1. **Commands calling Orca.** No command, skill or agent gains an Orca call, a `worker_done`, or Orca-specific branching (section 1.3, SA-2).
2. **Changing Orca or its settings.** Nesting depth stays 1 unless the user decides otherwise (D5); no change to Orca's readiness limit, guides or code (`CAPS:98`).
3. **Building a coordinator program.** The coordinator is an Orca coordinator session following Orca's own guide (`CAPS:12-13`); this spec adds a brief template, not a new CLI, daemon or scheduler.
4. **Turning coordinator-only commands into workers** (section 4).
5. **Removing or weakening any interactive behaviour for people** (section 5). `--unattended` is opt-in.
6. **Changing the `/sc:implement` Ruling rule** unless the user chooses D2 option (b) (`sk/sc-implement-protocol/refs/qa.md:238`).
7. **Making Agent-tool subagents into Orca workers**, or letting subagents send lifecycle messages (WC-7).
8. **Fixing every defect the inventories list.** Only defects that stop a command working as a worker are in scope. Others stay recorded in the inventories, for example `/sc:agent`'s missing opening frontmatter line (`INV-A:36`) and the cleanup/improve rollback claims (`INV-A:118`).
9. **Remote workers, model and effort choice, and cost tuning.** `--on <environment>`, `--model` and `--effort` are coordinator choices Orca already supports (`CAPS:128`, `CAPS:135-139`); this spec does not set them.
10. **Implementing anything in this run.** This is a planning spec (`.dev/orca-command-refactor/README.md:6,30`).

## 9. Open decisions for the user
Five decisions belong to the user. Each is self-contained, with a recommendation. Phases 0-3 can proceed on the recommendations (they only turn outward defaults off, N19); Phase 4 waits for D2-D4.

**D1. How does a command know it is running without a person?**
- (a) **Explicit `--unattended` flag in the brief (recommended).** The coordinator writes it into every worker's command line; a person never types it. Example: `/sc:troubleshoot "login fails" --unattended --output .dev/troubleshoot/login/`. It is testable by grep. A person does not type it, and the token rule of section 2.1 stops the characters `--unattended` inside a quoted topic or pasted content from switching the mode (F6; AC-1.5).
- (b) **Detect Orca.** The command checks `ORCA_TERMINAL_HANDLE` or looks for a worker preamble in the conversation. The variable is set in Orca terminals (`CAPS:149`, observed in a dispatched worker at `CAPS:151`); whether it is also set in a person's own Orca tab is UNVERIFIED, and if it is, prompts would vanish for a person working in Orca, breaking SA-1; preamble detection depends on the model reading prose and cannot be tested mechanically.
- Recommendation: (a).

**D2. When `/sc:implement` halts for a Ruling inside a worker, who may give it?**
- Today a Ruling is accepted from "clear user confirmation in the current conversation" or from a valid existing operator Ruling, and "another agent's message" does not count (`sk/sc-implement-protocol/refs/qa.md:232,238`). An Orca coordinator is another agent.
- (a) **Keep the rule (recommended).** The worker stops, writes the halt to its ledger and contract, and ends `failed`. The person reads the halt and gives the Ruling by running `/sc:implement <plan>` in their own session, which resumes from the ledger.
- (b) **Allow a relayed Ruling.** The coordinator asks the person, then answers the worker's `ask` with the person's exact words, which the worker records verbatim as the Ruling. Faster, but it weakens a deliberate safety rule and trusts the coordinator to relay faithfully.
- Recommendation: (a), because the rule exists to stop an agent approving its own work.

**D3. Should `/sc:pr-submit` run as an Orca worker at all?**
- It opens the PR, commits fixes, pushes, and replies to and resolves review threads, all outward actions (`sk/sc-pr-submit-protocol/SKILL.md:189,196`), and runs an attended poll loop whose waits have a 600-second default budget over several rounds (`cmd/pr-submit.md:49`; `sk/sc-pr-submit-protocol/SKILL.md:41-64`). The repo requires it for every PR (`CLAUDE.md:50`).
- (a) **Coordinator or person only (recommended).** The coordinator (a top-level session) runs it after the workers finish; no pr-submit changes in Phase 4.
- (b) **Worker, with pre-authorization.** Apply the section 3 row (wait splitting, summary file, HALTs as blocked) so several PRs can be monitored in parallel.
- Recommendation: (a), unless parallel PR monitoring is a real need.

**D4. May a coordinator's brief authorize a worker's outward actions?** (affects post-release, pr-submit under D3 (b), auggie-review `--post-pr`, task `commit`/`push`)
- (a) **Only when the user's own instruction to the coordinator names that action for that task (recommended).** The coordinator quotes the instruction in the brief and passes the command's explicit flag; without it every outward default is off (WC-9).
- (b) **Never.** Workers make no outward changes; the coordinator or person performs every push, PR, comment, install and VM step after reading the reports.
- Recommendation: (a). It matches the repo's own rule that post-release confirms outward steps "unless the user pre-authorized them this session" (`sk/sc-post-release-protocol/SKILL.md:340,351`).

**D5. Should Orca's nesting depth be raised so commands could start their own Orca workers?**
- Today depth is 1: workers cannot start workers (`CAPS:97-98`). Raising it is a setting in Orca's desktop app (`CAPS:99`).
- (a) **Keep depth 1 (recommended).** This spec does not need deeper nesting; fan-out stays inside commands or is split into Tasks by the coordinator.
- (b) **Raise it.** Would allow the rejected alternative (section 1.3) and break R1's protection against runaway fan-out.
- Recommendation: (a).
