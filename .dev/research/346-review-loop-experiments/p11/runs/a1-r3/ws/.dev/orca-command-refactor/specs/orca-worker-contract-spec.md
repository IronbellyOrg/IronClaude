## 1. Decision: Orca coordinates, commands stay the units of work

### 1.1 The decision
An Orca coordinator plans the work, creates Tasks, starts one worker per Task and reads each worker's report. Each IronClaude `/sc:` command stays a self-contained unit of work: one worker (a top-level Claude session in its own Orca terminal) runs one command and reports it with `worker_done`. Commands themselves contain no Orca calls. What changes in the commands is limited to the worker contract in section 2: a way to run without a person, a fixed report file, and a resume or safe re-run.

### 1.3 Rejected alternative: commands call Orca internally
In the alternative, a command would itself start Orca workers for its fan-out (for example one worker per `/sc:tdd` research agent), send its own `worker_done`, and call `orca orchestration ask` for its questions. It is rejected for these reasons:

| # | Reason | Evidence |
|---|---|---|
| R1 | It cannot run as a worker at the current setting. Nesting depth is 1 on this machine and "1 means a coordinator dispatches workers and those workers may not dispatch further", so a command that calls `worker-start` from inside a worker would be refused with `nested_worker_depth_exceeded`. Which call sites enforce the check was not traced; `worker-start` and `dispatch` are presumed (UNVERIFIED, `CAPS:103`). A new Run does not reset depth, and Orca's own advice is "Do the work in this terminal". The two designs exclude each other unless the user raises the depth setting. | `CAPS:97-101,103`; `orca-data.json:1` quoted at `CAPS:98` |
| R2 | It breaks standalone use. Commands are installed to `~/.claude/` and run in other projects. | R3 | A command cannot own the completion message. `worker_done` is accepted only from the dispatched pane, and the Task and Dispatch IDs exist only in the preamble given to the worker session, not in the command's arguments. | `CAPS:76`, `CAPS:150` (`[H:send]` line 40); `CAPS:148` (`[G]` line 38) |

| R5 | It would create a second orchestrator below the coordinator. The inventories already mark the commands that orchestrate (`/sc:agent`, `/sc:pm`, `/sc:spawn`) coordinator-only because two controllers compete. | `INV-A:90`; `INV-B:285-286` |

What the alternative would have given, and how this spec gets it instead: per-unit liveness, Task records and independent retry for heavy fan-out. Orca keeps those records only for workers the coordinator starts (`CAPS:158`). Under this decision the coordinator gets them by splitting the work into separate worker Tasks (for example several `/sc:troubleshoot` workers, then one `/sc:adversarial` worker on their reports), not by commands calling Orca.

### 1.4 How strong the evidence is
The evidence supports the decision. Three gaps are stated plainly:
1. **No command in scope has been run end to end as an Orca worker in this run.** Every verdict in both inventories comes from reading files (`INV-B:323`). The only end-to-end proof is the PR #329 run, and its brief told workers to run `/sc:adversarial` through an Agent-tool subagent (`.dev/codegraph-migration/orchestration/README.md:31`), so it proves the nested route, not the direct route this spec requires. Whether every such spawn succeeded is UNVERIFIED (`CAPS:156`, `CAPS:187`). Phase 0 (section 6) therefore starts with live smoke runs.
2. **The 60-second readiness evidence is narrower than it looks.** It concerns a question shown *before* Claude reached its input box (`EVIDENCE.md:39`, a shell wrapper's session-name prompt). A command's own `AskUserQuestion` or chat question comes *after* readiness, so it does not fail `worker-start`; Orca reports such a worker as waiting, "healthy, not failed" (`CAPS:52`, `CAPS:129`). The real failure mode for a command prompt is a silent stall with no `worker_done`, which the coordinator sees only through `worker-show`'s `agentWait` or a missing report. Section 2 covers both cases.
3. **Agent-tool fan-out inside a worker has no proven limit, but no proof of none either.** No Orca limit on subagents was found, and whether a subagent's Bash `send` would be accepted as the worker's own is UNVERIFIED (`CAPS:155`, `CAPS:159-160`, `CAPS:186`). The contract forbids subagents from sending lifecycle messages, so the design does not depend on that answer.

## 2. The worker contract

### 2.1 Terms
- **Worker run**: a session that received an Orca preamble carrying a Task ID and a Dispatch ID. Only such a session may send lifecycle messages; a session the user started, inside or outside Orca, is an ordinary session (`CAPS:148`, `[G]` lines 38 and 41).
- **Unattended mode**: the behaviour a command switches to when its caller passes `--unattended`. It is the only command-side change the contract asks for besides report files and resume. It names no Orca command, so the same mode serves any caller that has no person at the keyboard. How the mode is selected (flag versus detecting the preamble) is open decision D1 in section 9; this spec is written for the recommended flag. The switch counts only when `--unattended` is a standalone argument token outside any quoted argument; the same text inside a quoted topic or in file content does not switch the mode (finding 11).
- **Contract file**: one shared document, proposed as `src/superclaude/core/WORKER-CONTRACT.md`, installed to `~/.claude/WORKER-CONTRACT.md`. Core `.md` files install to `~/.claude/` (`src/superclaude/cli/install_core.py:4,33`; `CLAUDE.md:83,408`), and the new name must be added to `KNOWN_CORE_FILES` (`src/superclaude/cli/install_core.py:13-24`). Each changed command adds a short `## Unattended mode` section that lists only its own gate resolutions and report file and points to the installed contract path, so the shared rules are written once.

### 2.3 What the coordinator owes each worker
The contract only works if the brief carries what the command would otherwise ask a person. For each Task the coordinator's brief states: the exact command line including `--unattended` and every flag section 3 lists as required; the output location, so the contract path is known before dispatch by the WC-4.1 placement rule (a generated name is the exception: the worker reports its path), through the command's own output flag or the new `--report-dir` that its section 3 row names (N1); which outward actions, if any, are authorized (WC-9); and the worktree placement (`CAPS:115`). After `worker_done`, the coordinator opens the report file, applies WC-5, then releases or reuses the worker (`CAPS:107-113`). A contract older than the dispatch is stale and is never read as the outcome (finding 3).

Four further duties sit with the coordinator:
- **One output location per Task (N4).** Every Task gets its own output location (directory, or file for a file-valued flag), never shared with a concurrent or sibling Task; only the retry of the same Task reuses its location (WC-6). A command with a fixed output location (cleanup-audit, index-repo) has at most one Task running per worktree. Without this, a command's start-up removal of a stale contract (WC-4.4) could delete a sibling's contract, and a sibling's contract could pass the staleness test as this worker's outcome. Step 4 of 7.2 also checks that the contract's `command` equals this Task's command line.
- **Start instruction (finding 5).** The brief tells the worker to start the command as its first action through the Skill tool (`skill` = the command's name, for example `sc:troubleshoot`; `args` = the argument string), and never to paraphrase the command or run its protocol from memory. Orca places the Task text inside a preamble that carries the Task and Dispatch IDs (`CAPS:76`, `CAPS:78`, `CAPS:148`), and Claude gets that task on its command line (`CAPS:47`, C2), so a slash command written in that text may not be expanded as a command; this is UNVERIFIED. The PR #329 brief wrapped the call in an Agent-tool subagent while its contract says `skill-direct` (E3, section 1.4 (1)); the brief must not copy that wrapper (WC-7). AC-0.4 checks that the skill loaded.

## 9. Open decisions for the user
Five decisions belong to the user. Each is self-contained, with a recommendation. Phases 0-3 can proceed on the recommendations; Phase 4 waits for D2-D4.

**D1. How does a command know it is running without a person?**
- (a) **Explicit `--unattended` flag in the brief (recommended).** The coordinator writes it into every worker's command line; a person never types it. Example: `/sc:troubleshoot "login fails" --unattended --output .dev/troubleshoot/login/`. It is testable by grep, and because it counts only as a standalone unquoted argument (section 2.1) it cannot misfire on a person's quoted text such as `/sc:tdd "explain the --unattended flag"` (finding 11).
- (b) **Detect Orca.** The command checks `ORCA_TERMINAL_HANDLE` or looks for a worker preamble in the conversation. The variable is set in Orca terminals (`CAPS:149`, observed in a dispatched worker at `CAPS:151`); whether it is also set in a person's own Orca tab is UNVERIFIED, and if it is, prompts would vanish for a person working in Orca, breaking SA-1; preamble detection depends on the model reading prose and cannot be tested mechanically.
- Recommendation: (a).

**D2. When `/sc:implement` halts for a Ruling inside a worker, who may give it?**
- Today a Ruling is accepted from "clear user confirmation in the current conversation" or from a valid existing operator Ruling, and "another agent's message" does not count (`sk/sc-implement-protocol/refs/qa.md:232,238`). An Orca coordinator is another agent.
- (a) **Keep the rule (recommended).** The worker stops, writes the halt to its ledger and contract, and ends `failed`. The person reads the halt and gives the Ruling by running `/sc:implement <plan>` in their own session, which resumes from the ledger.
- (b) **Allow a relayed Ruling.** The coordinator asks the person, then answers the worker's `ask` with the person's exact words, which the worker records verbatim as the Ruling. Faster, but it weakens a deliberate safety rule and trusts the coordinator to relay faithfully.
- Recommendation: (a), because the rule exists to stop an agent approving its own work.

**D3. Should `/sc:pr-submit` run as an Orca worker at all?**
- It opens the PR, commits fixes, pushes, and replies to and resolves review threads, all outward actions (`sk/sc-pr-submit-protocol/SKILL.md:189,196`), and runs an attended poll loop whose waits have a 600-second default budget over several rounds (`cmd/pr-submit.md:49`; `sk/sc-pr-submit-protocol/SKILL.md:41-64`). The repo requires it for every PR (`CLAUDE.md:50`).
- (a) **Coordinator or person only (recommended).** The coordinator (a top-level session) runs it after the workers finish; no pr-submit changes in Phase 4.
- (b) **Worker, with pre-authorization.** Apply the section 3 row (wait splitting, summary file, HALTs as blocked) so several PRs can be monitored in parallel.
- Recommendation: (a), unless parallel PR monitoring is a real need.

**D4. May a coordinator's brief authorize a worker's outward actions?** (affects post-release, pr-submit under D3 (b), auggie-review `--post-pr`, task `commit`/`push`)
- (a) **Only when the user's own instruction to the coordinator names that action for that task (recommended).** The coordinator quotes the instruction in the brief and passes the command's flag for that one action (one flag per action class, WC-9); the quote is the coordinator's duty (section 2.3), the command checks only the flag (finding 13). Without the flag every outward default is off (WC-9).
- (b) **Never.** Workers make no outward changes; the coordinator or person performs every push, PR, comment, install and VM step after reading the reports.
- Recommendation: (a). It matches the repo's own rule that post-release confirms outward steps "unless the user pre-authorized them this session" (`sk/sc-post-release-protocol/SKILL.md:340,351`).

**D5. Should Orca's nesting depth be raised so commands could start their own Orca workers?**
- Today depth is 1: workers cannot start workers (`CAPS:97-98`). Raising it is a setting in Orca's desktop app (`CAPS:99`).
- (a) **Keep depth 1 (recommended).** This spec does not need deeper nesting; fan-out stays inside commands or is split into Tasks by the coordinator.
- (b) **Raise it.** Would allow the rejected alternative (section 1.3) and break R1's protection against runaway fan-out.
- Recommendation: (a).
