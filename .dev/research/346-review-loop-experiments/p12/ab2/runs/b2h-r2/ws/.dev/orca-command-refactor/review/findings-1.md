### B-1
### B-1. WC-3 lets the coordinator answer gates that the spec reserves for a person (CRITICAL-class safety boundary, blocking)
- Quotes: WC-3 (`spec:61`): "When a gate would resolve as blocked and the worker session holds a preamble, the session may instead ask the coordinator once ... then re-invoke or resume the command with the answer as a flag."
- Conflicting texts: the implement row (`spec:109`): on `E-HALT-QA` or `E-NO-RULING` the command stops "with the halt recorded ... the Ruling rule itself is unchanged". D2(a) (`spec:234-236`): the worker "ends `failed`" and "the person ... gives the Ruling". Non-goal 6 (`spec:218`) keeps the Ruling rule. The cli-portify row (`spec:105`) says "each of the three approval gates resolves as blocked". The source rule (`.dev/orca-command-refactor/inventory/commands-a.md:66`, citing `qa.md:238`) says "another agent's message ... [is] not acceptance".
- Grading sentence: An implementer who follows WC-3 as written, for implement's Ruling gate (blocked per `spec:109`), asks the coordinator and then re-invokes `/sc:implement` with the coordinator's reply as a flag. That builds a Ruling given by another agent, which the rule in `qa.md:238` and D2(a) forbid, and it is wrong because the coordinator then decides the worker's own halt. The same follows for the cli-portify approval gates (`spec:105`), where the coordinator would approve a step the spec says a person approves (`.dev/orca-command-refactor/inventory/commands-a.md:45`).
- Fix to consider: WC-3 names the gate classes it may not answer (Ruling, human approval, outward authorization), and limits `ask` to informational questions. The same change should make D2 and WC-3 agree.

### B-2
### B-2. The report path is not known before dispatch for three commands, and `--output` has two meanings (blocking)
- WC-4 (`spec:62`) says `<output-dir>` is "the directory the coordinator passed (`--output` / `--output-dir`)". Section 2.3 (`spec:73`) depends on this: "so the report path is known before dispatch (WC-4)".
- `/sc:workflow` (`spec:92`) writes `.dev/tasks/to-do/<id>/return-contract.yaml`, has "Fresh package each run", and takes no output flag (`spec:92`). The `<id>` is generated by the command (`.dev/orca-command-refactor/inventory/commands-b.md:272-273`). The path therefore cannot be given in the brief.
- `/sc:tdd` (`spec:90`) takes `--output <file>` (`.dev/orca-command-refactor/inventory/commands-b.md:47`), so `<output-dir>` is undefined for it.
- `/sc:spec-panel` (`spec:120`) says "add `--output`; contract". The spec-panel command definition that this review is run under (`command.md`, Unattended mode, line 460) says `--report-dir <dir>` is the only directory flag and "`--output` is file-valued". It also says a run without `--report-dir` is refused.
- Grading sentence: An implementer who follows WC-4 and `spec:73` cannot give `/sc:workflow` a contract path before dispatch, because the id is generated, and passing `--output <dir>` to `/sc:spec-panel` is refused (`command.md:460`) and to `/sc:tdd` leaves the directory undefined. That is wrong because the coordinator's brief must carry the report path before dispatch.
- Fix to consider: state one directory flag per command in section 3, or pass an explicit `--report-dir`/`--output-dir` that the brief sets; for workflow, add an output-directory input that the command must honor.

### B-3
### B-3. AC-1.1 cannot pass as written for `/sc:load` (blocking)
- AC-1.1 (`spec:195`): "every command in sections 3.1-3.2 has a `## Unattended mode` section naming `return-contract.yaml`".
- The load row (`spec:112`): report "none (see note)". P1 (`spec:159`) adds only "load (usage line only)". The Decision on `/sc:load` (`spec:265`) says "a report file would be an unrequested addition".
- Grading sentence: An implementer who follows the load row and P1 adds only a usage line, so the AC-1.1 test finds no section naming `return-contract.yaml` for load and fails. To make it pass, the implementer must add a contract that `spec:265` forbids. Two stated texts cannot both hold.
- Fix to consider: either exempt load in AC-1.1 and in P1 by name, or give load a contract. Choose one and record it in the Decisions table.

### B-4
### B-4. Cleanup-audit's fixed output path violates WC-11 (blocking, data loss)
- WC-11 (`spec:69`): "Two workers in one worktree must never write the same file. Default output paths carry a timestamp or the slug the coordinator passes."
- Cleanup-audit row (`spec:85`): "output dir is fixed, so one audit per worktree at a time (WC-11)". The fixed path is `.claude-audit/pass<N>-summary.md` (`.dev/orca-command-refactor/inventory/commands-a.md:42`, and `:107`). Workers share the worktree by default (`.dev/orca-command-refactor/inventory/orca-capabilities.md:115`).
- Section 2.3 (`spec:73`) lists no coordinator rule that serializes these workers.
- Grading sentence: An implementer who follows `spec:85` and `spec:73` dispatches two single-pass cleanup-audit workers for the same pass into the default shared worktree. Both write `.claude-audit/pass<N>-summary.md`, so the second overwrites the first, which is wrong because WC-11 forbids two workers writing one file and nothing in section 2.3 prevents it.
- Fix to consider: give cleanup-audit a per-dispatch output directory (a WC-11 slug), or add the serialization rule to section 2.3 and to the brief template.
