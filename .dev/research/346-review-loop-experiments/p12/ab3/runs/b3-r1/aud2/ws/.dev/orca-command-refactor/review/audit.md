## === REQUIREMENTS ANALYSIS ===

### F-1 [BLOCKING] [MAJOR] WC-3 lets any blocked gate be answered by the coordinator, which contradicts the Ruling rule D2 keeps and the outward-action rule WC-9/D4 sets

- Expert: Wiegers (traceability and consistency), Whittaker (Sentinel Collision / Sequence attack).
- Stated texts: WC-3 `spec:61`: "When a gate would resolve as blocked and the worker session holds a preamble, the session may instead ask the coordinator once ... then re-invoke or resume the command with the answer as a flag." It has no exception list. The implement row `spec:109` makes the Ruling gate resolve as blocked. D2 `spec:232-236` (recommended option a) and non-goal 6 `spec:218`: the Ruling rule is unchanged, and "another agent's message" is not a Ruling (`INV-A:66` quotes `refs/qa.md:238`: "Silence, a generic request to continue, another agent's message ... not acceptance"). WC-9 `spec:67` and D4 `spec:244-247`: an outward default turns on only through the command's explicit flag written in the brief, and only when the user's own instruction names that action. WC-3 is written into `WORKER-CONTRACT.md` in P0 (`spec:158`), before D2 and D4 are decided (`spec:154,225`: P0-P3 proceed on recommendations).
- An implementer who follows the stated text as written builds a worker contract in which a worker that hit `E-HALT-QA` asks the coordinator, receives the coordinator's answer, and re-invokes `/sc:implement` with that answer as the Ruling; the same path turns on `--post-pr`, a task `commit`/`push`, or a post-release install from a coordinator reply that no brief carried. That is wrong because it is exactly D2 option (b), which the spec itself recommends against ("it weakens a deliberate safety rule", `spec:235`), and because WC-9/D4 require the authorization in the brief and traceable to the user. The AC that should catch it, AC-4.1 `spec:208`, tests `/sc:implement` only after P4, and nothing tests WC-3 against WC-9 in P0-P3.
- Concrete attack (Whittaker): state before: implement ledger halted at `E-HALT-QA`, contract `blocked`, `blocked_question` = "Ruling?". Step 1: worker `ask`s. Step 2: coordinator answers "accept". Step 3: worker re-runs `/sc:implement <plan> --resume` with the answer. State after: the ledger records a Ruling that came from an agent, with D2 still "undecided" and no user words in the brief.
- Recommendation: add to WC-3 one exclusion: the `ask` route is for open parameters only; a gate that is a safety Ruling or an outward authorization (WC-9) stays `blocked` and ends `failed`, unless D2(b)/D4(a) is in force and the brief quotes the user's instruction. Priority: High. Quality impact: Consistency and safety-boundary correctness of the contract's central rule.

### F-2 [BLOCKING] [MAJOR] WC-4's fixed-name contract in "the directory that holds the file" collides for sibling outputs, which WC-11 forbids

- Expert: Wiegers, Adzic (concrete scenario), Whittaker (Accumulation attack).
- Stated texts: WC-4 `spec:62`: the report directory is "the directory that holds the file when `--output` is a file (tdd, init-lite)", and the file is always `return-contract.yaml`. Applied to tdd `spec:90`, init-lite `spec:87` and spec-panel `spec:120`, and to AC-2.2 `spec:200` ("for tdd, the directory of `<file>`"). WC-11 `spec:69`: "Two workers in one worktree must never write the same file." Workers share the current worktree by default (`CAPS:115`, quoting `[G:placement]` lines 8-11). The spec's own plan is parallel workers per Task (`spec:39`, section 1.3), and section 2.3 `spec:73` says only that the brief states "the output directory"; nothing makes it unique per Task. The spec does see this collision where the directory is fixed (cleanup-audit, `spec:85`: "one audit per worktree runs at a time (WC-11)") but not for file-valued outputs.
- An implementer who follows WC-4 as written writes the contract of `/sc:tdd ... --output docs/tdd/billing.md` to `docs/tdd/return-contract.yaml`. That is wrong because a second tdd worker with `--output docs/tdd/auth.md` writes the same path.
- Concrete attack: state before: no `docs/tdd/return-contract.yaml`. W1 (auth) and W2 (billing) run in one worktree. W2 finishes first: file = `succeeded`, W2 sends `worker_done --report-path docs/tdd/return-contract.yaml`. W1 later fails and overwrites it with `failed`. State after: the coordinator opening W2's reported path reads W1's `failed` contract; the 7.2 step-3 check `--outcome matches the contract's status` (`spec:182`) fails for W2 or passes by accident.
- Recommendation: for a file-valued `--output`, name the contract after the output file (for example `<output-stem>.return-contract.yaml`) or require a unique report directory per Task in the brief (`spec:73`). Priority: High. Quality impact: Correctness of the one artifact the whole design relies on (`spec:62`).
