### Whittaker findings (all below blocking)
- F3 (Zero/Empty attack on WC-5): I can break this specification by **Zero/Empty Attack**. The invariant at **WC-5 (`spec:63`)** fails when the command wrote a contract that is empty, unparsable, or has no `status` key. Concrete attack: a command crashes mid-write and leaves a 0-byte `return-contract.yaml`. WC-5 sends `--outcome failed` only "when the report says `failed` or `blocked`, or no report exists", and `--outcome succeeded` "otherwise". State trace: file exists, content `""`, so "no report exists" is false and the "report says failed" test is false, so the worker sends `succeeded`. The 7.2 step-4 check (`spec:183`) would catch it, but that check is a coordinator-side test, not part of the worker rule. Graded Medium: it is an unstated edge case, and the text needs the implementer to choose the worse reading.
- F6 (Sequence attack on WC-3 and WC-6): I can break this specification by **Sequence Attack**. The invariant at **WC-6 (`spec:64`)** ("a retry must not corrupt the first attempt's output") fails when WC-3 (`spec:61`) has the worker re-invoke the command after a `blocked` stop. Concrete attack: a `fresh dir` command (for example `/sc:troubleshoot`, `spec:91`) runs with `--output D`, stops `blocked`, writes `D/return-contract.yaml`. The worker asks the coordinator and re-invokes with the answer as a flag and the same brief. Whether it reuses `D` or "writes each run into a fresh output directory" (`spec:64`) is not stated, and the coordinator passed `D` before dispatch (`spec:73`). Graded Medium: it needs a guess about which reading an implementer picks.
