## 1. Worker-start readiness limit and what blocks it

- **Default limit is 60 seconds.** `/opt/Orca/resources/app.asar.unpacked/out/shared/orchestration-timing-budgets.js:13`: `exports.ORCHESTRATION_READINESS_TIMEOUT_MS = 60_000;`. Lines 16-19 use the caller's value only when it is a positive finite number: `return typeof timeoutMs === 'number' && Number.isFinite(timeoutMs) && timeoutMs > 0 ? timeoutMs : exports.ORCHESTRATION_READINESS_TIMEOUT_MS;`. The compiled worker-start path uses the same default: `/opt/Orca/resources/app.asar.unpacked/out/main/chunks/orcad-migration-source-retention-BKoqlqOo.js:590` (minified) contains `D=\`agent_readiness\`;let o=Date.now()+(l.timeoutMs??6e4)`.
- **The caller can raise it per start.** `[H:worker-start]` line 3 accepts `[--timeout-ms <n>]`; line 30: "--timeout-ms <ms>     Maximum wait time before timing out". The client waits longer than readiness by a fixed grace: `orchestration-timing-budgets.js:11` `AGENT_PROMPT_EFFECT_TIMEOUT_MS = 30_000` and line 15 `ORCHESTRATION_WORKER_START_CLIENT_GRACE_MS = exports.AGENT_PROMPT_EFFECT_TIMEOUT_MS + 20_000` (so 60 s readiness + 50 s client grace by default).
- **Exit code contract.** `[H:worker-start]` line 48: "The call exits 0 only for ready. Failed or outcome_unknown exits 1 and JSON includes stage/failedStage, setup, effects, residualResources, and recovery commands when needed." `[G]` lines 111-113: "If `worker-start` exits non-zero, do not relaunch. Read the receipt's `failedStage` and `residualResources`, then load `references/recovery-and-cleanup.md`."
- **What "ready" means.** Readiness waits for the agent's fresh input box ("composer") or an idle TUI before Orca types the task: `orcad-migration-source-retention-BKoqlqOo.js:590` contains `function bU(e,t,n){return n.agent&&!n.reusesTerminal?VJe(e,t,n.agent,n.timeoutMs):e.waitForTerminal(t,{condition:\`tui-idle\`,timeoutMs:n.timeoutMs})}` and `e.waitForFreshWorkerComposer(...)`. For Claude the task is passed on the command line, not typed: `/opt/Orca/resources/app.asar.unpacked/out/shared/tui-agent-config.js:16-22` (`claude: { detectCmd: 'claude', promptInjectionMode: 'argv', ... draftPromptFlag: '--prefill', preflightTrust: 'claude' }`).
- **What blocks it.** Anything that keeps the agent from reaching its ready input before the limit:
  - An interactive prompt at startup that nobody answers. Proven for Claude: `.dev/evals/ccsession-orca-e2e-20261026/EVIDENCE.md:39`: "`orca orchestration worker-start --agent claude` ... sat at the unanswered question, and Orca never typed into it; worker-start failed after the 45-second limit given (`state: failed, stage: agent_readiness, lastError: timeout`)." After the wrapper's question gained a 30-second auto-fallback, the same start passed: `EVIDENCE.md:45`: "worker-start returned after 34s, `state: ready, stage: input_accepted`". `EVIDENCE.md:56`: "Raising `CCSESSION_ASK_TIMEOUT` above about 45 seconds would make supervised workers fail again."
  - Trust, update, working-directory, hooks-review and other interactive dialogs. The compiled code names these blocked reasons: `orcad-migration-source-retention-BKoqlqOo.js:590` maps `codex-update-prompt`, `codex-trust-workspace`, `codex-cwd-prompt`, `codex-hooks-review-prompt`, `codex-interactive-prompt` and throws "Agent startup blocked: ..." or "Agent did not become ready (...)". `tui-agent-config.js:169-172` (Antigravity): "agy's first-launch trust menu consumes the bracketed paste ... a supervised worker would otherwise always fail at agent_readiness". Orca pre-accepts trust for Claude (`tui-agent-config.js:22` `preflightTrust: 'claude'`).
  - Setup that must finish first. `[H:worker-start]` line 40: "Repository start-immediately runs setup beside the agent; wait-for-setup gates agent readiness and task input." The compiled path fails with stage `setup_start` ("Setup terminal failed to start before the gated agent launch.") or `setup_wait` (`orcad-migration-source-retention-BKoqlqOo.js:590`).
- **Not a limit on the worker's later work.** The 60 s applies only to startup; once `input_accepted`, a worker waiting on its own `ask` is healthy. `[H:worker-show]` line 16: "observation.agentWait names a worker parked on a prompt only a human can answer ... A waiting worker is healthy, not failed." A person's own launch tab has no limit: `EVIDENCE.md:35`: "No time limit was observed for a person's launch tab."
- **Spec consequence.** An IronClaude command launched as a worker must not show any interactive question (for example `AskUserQuestion`, a session-name prompt) before its agent input is ready; questions after start must go through `orca orchestration ask` (section 2).

## 2. ask / reply for worker questions

- **Worker asks with a blocking call.** `[H:ask]` line 3: "Usage: orca orchestration ask (--question <text> | --resume <message_id>) [--to <run:id>] [--run <run_id>] [--options <csv>] [--timeout-ms <n>] [--from <handle>] [--retry-request <id>] [--json]"; line 5: "Ask the coordinator a question and block until answered".
- **Default recipient is the owning Run.** `[H:ask]` line 23: "From an active Dispatch, a new question defaults to its owning Run mailbox."
- **Timeout does not lose the question; resume by ID.** `[H:ask]` line 24: "Timeout leaves the question pending; resume with the original message ID." `[G:worker-contract]` lines 28 and 31-32: "ORCA orchestration ask --from <worker_handle> --resume <message_id> --timeout-ms 600000" and "A timeout or disconnect leaves the original question pending. Resume its message ID; do not create a duplicate question."
- **Never a local question prompt.** `[G]` lines 80-82: "use the preamble's `ask` command for a blocking coordinator question. Never open a local question TUI the coordinator cannot answer. Resume the same message ID after an ask timeout." (This is why an IronClaude command that calls `AskUserQuestion` stalls under Orca: the coordinator cannot see that prompt.)
- **Coordinator answers with reply.** `[H:reply]` line 3: "Usage: orca orchestration reply --id <msg_id> --body <text> [--run <run_id>] [--from <handle>] [--retry-request <id>] [--json]". `[H:send]` line 32: "To answer a worker question, use orchestration reply --id <msg_id> --body <text> with the same Orca CLI executable." `[G:messaging]` line 58: "The coordinator answers that message with `reply`."
- **Questions surface in the coordinator wait.** `[G]` line 108: "ORCA orchestration check --wait --types \"worker_done,escalation,question\" --timeout-ms 900000 --json"; line 127: "ORCA orchestration reply --id <message_id> --body \"<answer>\" --json".
- **No heartbeat needed while blocked in ask.** `[G:worker-contract]` lines 10-11: "Skip them while blocked inside `ask` or `check --wait`; those calls are liveness signals."
- **Gates are not for answering asks.** `[G:messaging]` line 60: "Use a gate only for a coordinator-owned Task-DAG decision"; line 71: "Do not create a gate merely to answer a worker's `ask`."
- **Coordinator follow-ups to a running worker are pull-only.** `[G:worker-contract]` lines 36-38: "The coordinator steers a running worker with `send --to dispatch:<id>`. That enqueue is durable but does not interrupt you, so nothing arrives unless you look". `[G]` lines 73-74: "A successful `orchestration send` proves durable enqueue; its wake or nudge is best-effort attention only and does not prove the recipient read or accepted it."
- **Ownership loss signal.** `[G:worker-contract]` lines 49-52: "If `check` returns `consumer_fenced`, this process no longer owns its Dispatch ... Stop, do not send `worker_done`, and do not retry the check. An empty `check` never means you were replaced; `consumer_fenced` is the only way you learn that."
- UNVERIFIED: the default `--timeout-ms` of `ask` when the flag is omitted. `[H:ask]` line 18 says only "Maximum wait time before timing out"; the guides always pass `600000`.

## 6. Release, retain and cleanup

- **One decision per settled worker.** `[G]` lines 166-170: "After an accepted success or failure report, immediately do exactly one: 1. Reuse the same proven agent terminal for an immediate follow-up Dispatch. 2. Record user-requested retention with `worker-retain`. 3. Run `worker-release`."
- **Release is cleanup after settlement, never cancellation.** `[G]` lines 172-174: "Release is post-settlement cleanup, not cancellation. Only an accepted settlement authorizes it; no other observation does. If release is uncertain, follow its exact recovery receipt and never substitute `terminal close`."
- **What release does.** `[H:worker-release]` lines 16-20: "Post-completion cleanup for a settled (succeeded or failed) worker; closes only the exact coordinator-owned agent terminal of that worker." / "An inspectable output archive is preserved before the terminal closes, so worker-read still returns output afterwards." / "Never closes setup terminals, configured tabs, reused or pre-existing terminals, user-taken-over terminals, or unproven identities." / "Idempotent: repeating the call reports already_released. Only release_unknown exits 1; retained, release_pending, and already_released exit 0."
- **What retain does.** `[H:worker-retain]` lines 16-18: "Records a durable user-requested exception; a later explicit worker-release clears it and releases the terminal." / "Performs no process or filesystem action." `[G:recovery]` line 157: "Retain only when the user explicitly wants the settled terminal kept live."
- **Never release on these signals.** `[G:recovery]` lines 169-172: "Never release because of timeout, TUI idle, heartbeat, status, question, escalation, or stale/rejected completion. If the receipt says `release_pending` or `release_unknown`, follow its exact recovery action. Never substitute `terminal close`."
- **A failed start still owns a terminal.** `[G:recovery]` lines 163-165: "A `worker-start` that failed before its agent was ready still owns the terminal it created. Its receipt names `worker-release`, and `worker-list` reports that row as `reclaimable`; release it there rather than closing the terminal by hand."
- **Coordinator turn cannot end with unreleased workers.** `[G]` lines 177-179: "Enumerate the terminals still owing a decision with `worker-list --run <run_id> --terminal-state reclaimable --json`, and do not end the coordinator turn until it returns none." Terminal states: `[H:worker-list]` line 3: "--terminal-state <active|reclaimable|retained|release_pending|release_unknown|released>". `[H:worker-list]` line 19: "Terminal state is process accounting and is reported separately from Task status; a completed Task can still own a live terminal."
- **Stop and abandon (before settlement).** `[H:worker-stop]` line 5: "Fence one Dispatch and stop its supervised agent terminal"; line 17: "Never deletes the worktree, setup terminal, configured tabs, or unrelated processes." `[H:worker-abandon]` line 16: "Retains all possibly-live resources and performs no process or filesystem action." Use only after positive proof: `[G:recovery]` lines 54-56.
- **Worktrees are never deleted by these verbs.** `[G:recovery]` lines 134-135: "`worker-stop` closes only the exact proven supervised agent terminal. - **Retry and circuit breaker.** `[G:recovery]` lines 117 and 120-125: "ORCA orchestration worker-start --task <task_id> --retry-of <dispatch_id> --worktree <explicit_placement> --agent <agent> --json" and "After three consecutive failures for one Task, its dispatch context circuit-breaks and the Task is failed. ... - **Lost mutation responses.** `[G:recovery]` lines 77-79: "Every orchestration mutation accepts `--retry-request <id>`, which reuses one operation identity so Orca can replay, join, or recover it instead of starting a duplicate." Check first with `request-show --request <request_id>` (line 82).

## 7. Liveness verdicts

- **Three verdicts only.** `[G]` lines 58-60: "The execution host owns process, filesystem, transcript, stop, and cleanup facts. Preserve the verdicts `live` / `unverifiable` / `exited`; contact loss is not process death." `[G:placement]` lines 76-78: "Render only `live`, `unverifiable`, or `exited`. Connection loss, relay absence, missing client inventory, or timeout yields `unverifiable`, never synthetic exit".
- **Two layers; the fleet verdict wins.** `[G]` lines 61-63: "`worker-list`'s `projection.liveness` is the fleet verdict for the agent; `worker-show`'s `observation.status` is PTY liveness only. A live terminal can still hold a dead or stuck agent." `[G:recovery]` lines 25-31 repeat this and add: "a `live` terminal whose agent died at a trust prompt still reads `live` there."

## 9. Orca not running, or session outside an Orca terminal

- **Executable name.** On Linux the CLI is `orca-ide` to avoid the GNOME Orca screen reader: `/opt/Orca/resources/bin/orca-ide:16`: "# Why: Linux executableName is `orca-ide` (avoids Ubuntu GNOME Orca conflict);". On this machine `~/.local/bin/orca` is also a dispatcher to `orca-ide` (`/home/coder/.local/bin/orca:2-3`), but that file is local setup, so a portable spec must call `orca-ide` outside Orca terminals. `[G]` lines 69-71: "Use the executable you used to run `skills get` for the entire run. ... - **Check readiness first.** `[G]` line 104: "ORCA status --json" is the first step of the supervised loop. `[H:status]` line 5: "Show app/runtime/graph readiness". Observed now: `"app": {"running": true, ...}`, `"runtime": {"state": "ready", "reachable": true, "connectionState": "connected", ...}`.

## 10. Workers that spawn Agent-tool subagents

- **Agent-tool subagents are not Orca workers, so the depth limit does not count them.** The depth fence is about "Sub-worker dispatch" through Orca (`/opt/Orca/resources/app.asar.unpacked/out/shared/nested-worker-depth.js:7-11, 18-19`), and its own advice is "Do the work in this terminal instead of dispatching a sub-worker." (line 22). No Orca guide or `--help` text read for this report mentions Claude Code's Agent tool or caps in-process subagents. UNVERIFIED that Orca never limits them; no evidence of a limit was found in `[G]`, the six of its seven references that were read, `[CLI]`, or `[H:orch]`.
- **Prior run shows it works in practice.** `.dev/codegraph-migration/orchestration/README.md:31` instructed Orca workers to "spawn an agent (Agent tool) to invoke `/sc:adversarial --compare <option files> --depth quick`"; README section "Evidence to read" (`.dev/orca-command-refactor/README.md:12`) records that this run "landed as PR #329". UNVERIFIED in this report whether every such spawn succeeded; the worker transcripts were not read.
- **Orca sees subagents only as UI child rows.** `/opt/Orca/resources/app.asar.unpacked/out/shared/agent-child-work-listing.js:2-3`: "Which child work the worktree sidebar and the chat's strip list: running children only, by one rule, from every source they read (a CLI pane's hook roster and a chat session's records alike)." These rows are display and stop targets (`agent-child-work-stop-targets.js:2-4`), not Tasks or Dispatches. UNVERIFIED whether a running child row changes the worker's `projection.liveness`.
- **Provenance rule.** `[G]` lines 46-47: "Never substitute a non-Orca subagent tool when Orca orchestration provenance was requested." So if the coordinator needs per-unit Task/Dispatch records, the fan-out must be Orca workers from the coordinator, not Agent-tool subagents inside one worker (and section 5 forbids a worker from starting them at default depth).
- **Lifecycle messages must stay with the worker's main session.** The worker sends `worker_done` "exactly once, from the dispatched terminal" (`[G]` lines 88-89) and "only from the dispatched pane" (`[H:send]` line 40). A subagent's Bash runs in the same pane environment, so Orca probably could not tell a subagent's `send` from the worker's; UNVERIFIED (not tested, because sending a test lifecycle message would affect this live Dispatch). The spec should forbid subagents from sending `worker_done`, `heartbeat` or `ask`, and keep these in the worker's top-level session.
- **Questions from subagents.** A subagent cannot answer through the coordinator by itself without the preamble values; the worker's top-level session should collect them and use one `ask` (`[G]` lines 80-82). UNVERIFIED whether `ask` from a subagent's Bash would be accepted.
- **Commands that must be top-level cannot be pushed into a subagent of a worker.** `/home/coder/.claude/skills/sc-pr-submit-protocol/SKILL.md:47-49`: "**Top-level activation required.** This skill MUST run in the main orchestrating session ... Do NOT run it inside an Agent-tool subagent that itself spawns skills." Lines 82-84: "Never hand a side effect to a background shell, detached loop, or subagent". Such a command can still be an Orca worker, because an Orca worker is a top-level Claude session in its own terminal (`[H:worker-start]` line 38, `--agent claude`).
- **Long-running work inside a worker is not limited by readiness.** The 60 s limit ends at `input_accepted` (section 1); after that the worker's only timing duties are the preamble's heartbeat cadence, which it skips while blocked in `ask` or `check --wait` (`[G:worker-contract]` lines 10-11). UNVERIFIED whether Orca has any upper bound on a Dispatch's total run time; none was found in the sources above.
