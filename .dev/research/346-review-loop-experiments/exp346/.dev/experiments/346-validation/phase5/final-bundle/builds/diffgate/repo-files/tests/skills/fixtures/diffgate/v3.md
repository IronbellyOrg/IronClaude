# Widget Service Specification

## 1. Scope

The widget service stores widgets for the billing team and serves them over HTTP.
It replaces the nightly export job that copies widgets into the reporting database.

## 2. Requirements

- FR-1: A client creates a widget with a POST request to the widgets endpoint.
- FR-2: A client reads a widget by its identifier and receives the stored fields.
- FR-3: The service rejects a widget whose price is negative, missing or not a number with status 400 (R1.1, R2.1).
- FR-4: Deleting a widget removes it from every listing within one minute.

## 3. Storage

Widgets are stored in one table keyed by identifier.
The table keeps the creation time and the last update time of each widget.
Backups run every night and are kept for thirty days so audits can read them (R1.2).

| Field | Type | Rule |
|---|---|---|
| id | text | unique, assigned by the service |
| price | number | zero or more |
| owner | text | required |

## 4. Errors

Every error response carries a machine-readable code and a human message.
A request with an unknown field is rejected with status 422 and names the first unknown field (R1.3, R2.2).

## 5. Acceptance

The service passes when every requirement above has an automated test.
