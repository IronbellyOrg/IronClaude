# 151
fix(prd): deliver specs/refs inline instead of cloud-only --file flag
2026-06-09T12:20:52Z
7601ad2548e232ce89219908f726d4e35fe41412
## Root cause

The PRD CLI pipeline passed **local filesystem paths** to `claude --file` — a **cloud-download mechanism** (`file_id:relative_path`) that requires `CLAUDE_CODE_SESSION_ACCESS_TOKEN`. In a headless `--spec` run with no session token, the `claude` subprocess exits 1 in ~0.3 s with `Error: Session token required for file downloads`, crashlooping the pipeline at `scope-discovery`. PRD was the **only** pipeline emitting `--file`; roadmap / tasklist / validate already forbid it (FR-003/FR-023) and deliver content inline.

## The fix (3 files)

- **`src/superclaude/cli/prd/process.py`** — remove both `--file` emissions, the `_build_file_args` method, its `extra_args=file_args` wiring, and the three now-dead constants (`_PHASE_ALLOWED_REFS` / `_FILE_SIZE_THRESHOLD` / `_SPEC_FILE_STEPS`); de-`--file` the module + class docstrings.
- **`src/superclaude/cli/prd/prompts.py`** — upgrade `_authoritative_specs_block` to inline each existing spec's content via the reused `_read_file` (50 KB cap + `_TRUNCATION_MARKER`) under a `--- SPEC: <path> ---` header, behind a **mandatory `Path(p).is_file()` guard**. Missing/stale paths fall back to a path-only line and never call `_read_file` — so a resumed run with stale `parsed-request.json` SPECS paths cannot re-introduce a crash via a bare `FileNotFoundError`. Signature + both call sites unchanged; empty-input `""` contract and the substrings `AUTHORITATIVE SPECIFICATIONS` / `MUST Read each one IN FULL` preserved.
- **`tests/cli/prd/test_spec_flag.py`** — `TestSpecFileAttach` → `TestSpecFileNotAttached` (asserts `--file` absence via `build_command()`) + new `TestAuthoritativeSpecsBlockInline` (content-inline / >50 KB truncation / missing-path no-raise); empty-input lock retained.

This matches the no-`--file` contract the roadmap/tasklist/validate pipelines already enforce. No pipeline redesign; executor crashloop hardening is out of scope (separate follow-up).

# 153
fix(task-builder): base POST-reflect --diff on merge-base working-tree, not start_commit
2026-06-10T02:46:33Z
10723863389b8fce9cf9474b3f628c963725daf8
## Problem
The task-builder's generated **POST-reflect gate item** emitted:
```
/sc:reflect --mode post --diff <start_commit>..HEAD ...
```
where `start_commit` is `git rev-parse HEAD` captured at task start (frontmatter `start_commit`). That base is **wrong in two common cases**:

1. **Uncommitted work (the usual `/task` outcome).** `/task` edits the working tree but does not commit, so a `<base>..HEAD` *commit range* audits **none** of the task's changes.
2. **Interleaved commits.** If an unrelated commit lands on the branch after task start, `start_commit..HEAD` spans **foreign work**.

Both were hit live while auditing the PRD `--file` fix (#151): `start_commit` (`ac80f176`) pointed before an unrelated sprint-recovery commit, and the PRD work was uncommitted on top — so `ac80f176..HEAD` covered only the foreign commit. The reflect run had to be hand-retargeted to the working-tree diff.

# 154
fix(prd): exempt sequential completion phase from parallel-instructions gate
2026-06-10T02:46:58Z
e97aa4fd2a9d317abdc19f6ce2b5ccd35497df0e
## Problem
`_check_parallel_instructions` (gates.py) enforced the parallel-keyword requirement on **every** phase ≥2 — despite its `"phases 2-5"` docstring. It false-positived on the final **sequential completion/presentation phase** and **HALTed a live heavyweight PRD run** at `build-task-file`:

```
Phase 7 missing parallel execution instructions (expected one of: parallel, concurrent, simultaneously, batch)
```

Ground truth from the run: the generated task's parallel work phases run **2→6** (investigation, gates, web-research, synthesis, assembly — all passed), and only **Phase 7 "Present to User & Complete Task"** (sequential by anti-orphaning convention) lacked parallel keywords.

## Fix
Exempt the final phase **only when its heading marks it a completion phase** (`present`/`complete`/`finaliz`/`sign-off`/`wrap-up`). A final phase that is **not** completion-titled (e.g. a 2-phase task whose Phase 2 is real work) is **still checked** — so short tasks keep enforcement and the existing `test_check_parallel_instructions_missing` stays green. Phase 1 (setup) remains exempt as before (the check starts at phase 2). Net rule: **exempt the bookends (setup + completion), enforce the middle work phases.**

# 155
fix(prd): make parallel-instructions gate advisory (warn, don't halt)
2026-06-10T05:13:30Z
eb9a2633bfc49b96f2a677fd907a68976f2a5fd9
## Problem
`_check_parallel_instructions` is a **STRICT** semantic check on the `build-task-file` gate. Its heuristic detection (loose `Phase \d` heading matching + literal-keyword matching) has **false-positived twice** on well-formed generated task files, each time **HALTing a ~25-minute heavyweight PRD run**:
1. flagged the sequential final **completion** phase (Phase 7) — patched by #154;
2. after #154, flagged "Phase 2" because the regex also matched Task-Log `### Phase N - … Findings` placeholder headings, and the loop tripped on the empty `Phase 2 - Codebase Research Findings`.

**Cost asymmetry:** a false positive halts a long, expensive run; the failure the gate guards against (a task that runs agents serially instead of in parallel) is merely *slower, not wrong*. A hard gate inverts that asymmetry.

## Fix
Add a **per-check advisory severity** to the gate framework rather than chasing detection bugs forever:
- `SemanticCheck.advisory: bool = False` (`pipeline/models.py`).
- The STRICT semantic-check loop (`pipeline/gates.py`) **logs a WARNING and proceeds** when an `advisory` check fails, instead of failing the gate.
- Mark **only** `parallel_instructions` advisory (`prd/gates.py`). `task_phases_present` and `b2_self_contained` stay STRICT/halting.
