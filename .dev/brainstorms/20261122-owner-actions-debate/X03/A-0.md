CODEOWNERS text (sole owner `@ironbelly`; the file lists who must approve a change to a path):

Ruleset `master-gate` (Settings, Rules, Rulesets, New branch ruleset): Enforcement Active. Target: branch, include `refs/heads/master` only. Bypass list: role Repository admin, mode "For pull requests only" (no direct pushes). Rules ON: Restrict deletions; Block force pushes; Require a pull request before merging with Required approvals 0, Dismiss stale approvals when new commits are pushed ON, Require review from Code Owners ON. Rules OFF: required approvals above 0, approval of the latest push, conversation resolution, required status checks, linear history, signed commits. Merge methods: leave all three allowed (Clay and the owner use merge commits and squash).
The owner creates it in the web page, not by API: the bypass line is the one setting that can fail silently (the API wants a numeric role id; the docs page I fetched gives no id mapping, so UNVERIFIED). An agent then reads it back with `gh api repos/IronbellyOrg/IronClaude/rulesets` and `.../rulesets/<id>` and compares every value to this list.
**Sentence the owner says:** "Go on X03: add the CODEOWNERS file, then I set the master-gate ruleset on master only, as in A-0; integration stays out for now; tell Clay first; no agent uses admin bypass unless I type 'merge PR N with bypass' in chat."
**Then an agent:** drafts the notice to Clay; opens the CODEOWNERS PR with `/sc:pr-submit --monitor 3` and merges it only on the owner's typed go; reads the ruleset back; runs the test in section 5; reports the three PR states in chat; records the owner's sentence word for word in the plan's decision record.
**Rollback:** Settings, Rules, `master-gate`, Enforcement: Disabled (one click; or Delete). The CODEOWNERS file is inert without the ruleset and can stay. Roll back if the test fails, or if a gated PR of Clay's waits more than 3 working days after the owner was asked and nobody can say why.

## 4 Implications, benefits, risks, costs
**Benefits.** A PR from Clay (or anyone but the owner) that touches the five paths cannot merge without the owner's approval. Force push to master and deletion of master are blocked. Every other PR flows as it does today. Bypass use leaves a trail on the pull request and in the audit log (GitHub's wording, found by search, not read in full).
**For Clay.** PRs touching the five paths show "review required" until ironbelly approves; other PRs are unchanged (0 approvals). Direct pushes to master stop (none seen). `integration` is unchanged, including direct sync pushes. Clay cannot approve or bypass: maintain role is not on the bypass list.
**For agents on the shared login.** Authoring and opening PRs are unchanged. A PR the owner's login authored on a gated path cannot be approved by anyone (the author cannot approve their own PR), so it merges only through the bypass: the owner clicks "Merge without waiting for requirements", or types "merge PR N with bypass" and an agent runs `gh pr merge N --repo IronbellyOrg/IronClaude --admin` for that one PR. That is 5 of the last 40 merged PRs. A direct `git push origin master` now fails, which the launch prompt already forbids.
**For `/sc:pr-submit`.** No change to opening or monitoring; it never merges. Its fix pushes after a review will dismiss an approval on a gated PR, so the owner approves after the monitor finishes; put that line in the PR body. UNVERIFIED: whether pr-submit's reading of PR state copes with "review required" (it does not merge, so low risk).
**Risks.** (1) The known limit INV-025 stays open: any session on the shared login can still use the bypass, so this narrows the risk, it does not close it. (2) UNVERIFIED until the test: code owner review may not block a non-owner author at 0 approvals. (3) A queue on the owner: D16 counted about 17 Clay PRs in about 10 days on both branches (its estimate, a floor); the owner's measured median response on Clay PRs was 4.4 hours (D16 VERDICT line 100). (4) Gated work can sit on integration unreviewed until the release PR; the owner then reviews only the owned files, but in bulk. (5) PR 684-type merges (no owned path) are not stopped. (6) Clay may dispute "sole owner is ironbelly": their merged design says Clay (D16 VERDICT line 97). Mitigation: notice first, one-click rollback. (7) If ironbelly is unreachable, gated PRs wait; the bypass is the same person.
**Costs (estimates; basis: D16's own figures, no measurement).** Owner: 5 min chat plus about 10 min in the settings page (D16 puts the ruleset at 15 to 30 min admin time) = about 15 to 20 min. Agent: CODEOWNERS PR about 15 min (D16 estimate) plus about 15 min for read-back, test and report = about 30 min, excluding `--monitor 3` waiting. Clay: about 5 to 10 min (notice reply, one throwaway PR). Review at day 14: about 20 min (D16). One-off total about 1 hour of attended time; ongoing cost is the owner's review of gated PRs. Money: none; a public repository on the free plan can use rulesets (UNVERIFIED for this organisation until creation succeeds).
