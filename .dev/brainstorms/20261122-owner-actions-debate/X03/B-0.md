## 3 Alternatives rejected
- One required approval on every PR (D16 fallback 1): 25 of the last 30 merged PRs were merged by the login that authored them, and the owner's own agent PRs have no second approver (the author cannot approve; Clay and `IB-JonathanB` have never reviewed one). Every owner PR would need the bypass, which trains everyone to click it. Kept only as the fallback if the test fails.
- No bypass at all: the owner's own gated PRs are authored under `ironbelly`, so nobody can approve them, and an emergency revert like PR 662 would need the ruleset switched off, a worse and more forgettable act than a PR-only bypass.
- Classic branch protection: no gain; a ruleset can be switched Disabled without deleting its settings, which is the rollback I want.
- Required CI checks now (`.github/workflows/test.yml` runs on PRs to both branches): a hung or flaky required check blocks every merge and also trains bypass. Revisit after the 14-day review with real pass rates.
- Wider CODEOWNERS (D16 measured the five-path list matching 27 of 60 PRs, and `*` would be all): turns the owner into a queue; the shared login does not reduce the load.
- Waiting for a separate agent login (OA-6) or org-level ruleset read first: leaves master open two days after PR 700. Ask OA-6 in parallel; it does not block this.

## 4 Implications, benefits, risks, costs
- **Clay:** PRs touching the five paths show "Review required" and need an `ironbelly` approval; every later push dismisses it; all other PRs behave as today. Clay can no longer push directly to master or integration, delete them or force-push. Clay should accept the roles text before the announcement (D16 A-003); otherwise the dispute moves to the merge button.
- **Agents on the shared login:** a PR an agent opens is authored by `ironbelly`, so on gated paths it passes only through the bypass. The rule text must say agents never pass `--admin` and never switch the ruleset off, and may merge a gated PR only on the owner's typed go. `/sc:pr-submit --monitor 3` needs no change: it pushes fixes and never merges; the owner must re-approve after its pushes.
- **Limit (INV-025, carried):** the gate does not stop a feature-branch push, and any script on the shared login can run `gh pr merge --admin` or edit the ruleset. It stops mistakes by non-owner logins, direct pushes, force pushes and deletions. It does not make "a worker cannot merge" true; only OA-6 plus the ruleset does. Do not claim more.
- **Benefits:** the exact PR 700 pattern is blocked; accidental history rewrite and branch deletion are blocked; integration stops being a side door; rollback is one call.
- **Risks:** (1) a gated path missed, so a deletion elsewhere passes (PR 682 hit a gated file only by 1 of 36); (2) the owner's queue (D16 estimate: about 17 Clay PRs in about 10 days on both branches, of which only the gated share needs the owner; the share is UNVERIFIED); (3) a stale-approval loop with `/sc:pr-submit`; (4) "require code-owner review at 0 approvals blocks a non-owner author" is untested here (UNVERIFIED), hence the tests; (5) a mistaken ruleset locks out merges, hence Disabled first, a read-back and the bypass.
- **Rollback (under 2 minutes):** `gh api -X PUT repos/IronbellyOrg/IronClaude/rulesets/<id>` with `enforcement` set to `disabled`, or the toggle in the UI; full removal is a DELETE of that id. The saved JSON recreates it. CODEOWNERS alone does nothing; remove it by PR. Trigger: any non-gated PR blocked, the owner blocked despite bypass, or a test that does not block (then keep the structural rules, drop the code-owner rule, and the owner picks fallback 1, 2 or 3).
- **Cost (ESTIMATES, basis D16 figures plus my sum):** owner chat decision 20 min; CODEOWNERS PRs 2 x 15 min = 30; ruleset JSON, read-back, plain list 20 min agent; owner switch-on 10; four tests 4 x 5 = 20 plus waiting for Clay; announcement 5; 14-day review 20. About 2 hours of people and agent time, of which the owner about 45 minutes. Ongoing: the owner's review queue; measure it at day 14.
