## 3 Alternatives rejected
- **Treat as a rule breach and record it** (B.3 "Yes"). Rejected: no rule existed; the repository is public so a breach note names a person; it hits the one person whose acceptance FR-76 needs; and the owner self-merges too. The only gain, "a first test case", is delivered by the neutral worked example.
- **Ask Clay to revert or re-open PR 700 for review.** Rejected: master is already where the owner wanted it and PR 701 is merged on top; a revert of the repair would re-delete the plan-approval code and cost hours. A cheap read-only diff (step 5) gives the same assurance.
- **Written warning or strike record.** Rejected: process that buys no protection; the ruleset is the protection.
- **Wait until X03 is done to decide.** Rejected: the answer costs nothing, and leaving it open leaves Clay unsure and the plan row open. X13 does not depend on X03; only the words "would have been blocked" do.
- **Public comment on PR 700 or on issue 450.** Rejected: nothing a public reader needs; every public line stays neutral and only in `docs/decisions.md`.

- Benefits: no friction with Clay; the review-rule roll-out starts from agreement; one worked example for the rule text and the announcement; the plan row closes.
