# X12 (OA-23) Claim route after the X-001 live check. Agent B, round 0 (risk-first lens)

Terms. X-001: the open question "does the claim agent, started by the poll at the claim step, stay alive after its claim in the shared `Coordinator` worktree where the standing coordinator lives?". D07: the earlier debate on topology that found the shared worktree. RK-7: the plan's risk row for it. K1: the plan's pick that the poll claims and the coordinator adopts. 516: Coder issue 516, which makes the `Coordinator` branch, worktree and `COORD-<RepoName>` session.
Route A: `claim_by poll` (the poll launches the claim, in the shared worktree). Route B: each claim in a worktree of its own. Route C: `claim_by coordinator` (the coordinator claims; reserved).

## 1 Proposal

Run X-001 by hand, off the poll, on a throwaway repo and a throwaway issue, before any poll is enabled. Never in IronClaude's main checkout (where ORCH-IronClaude works) and never in a real project's `Coordinator` worktree.
Setup (an agent, after the owner's go): in the throwaway repo make a test worktree named `Coordinator` through Orca with `--agent` (owner rule), and let its one agent stand in for the coordinator (idle, then asked to copy claim files and make one commit). 516 does not need to have landed for this.
Launch the exact command the poll builds: `orca agent launch --agent claude --worktree path:<test worktree> --surface terminal --prompt "<text from build_claim_prompt>" --json` (master `launch.py:136-157`).
Three runs: (1) a normal claim; (2) a claim the skill refuses (for example an issue it must stop on; the stop code is UNVERIFIED); (3) a normal claim left idle 30 minutes.
Measure at the four points RK-7 names (before launch, after both comments are posted, after the claim result, just before the stand-in coordinator writes) and again at +30 minutes. At each point read three things, all read-only: `orca terminal list --worktree path:<wt> --json`; the machine's process list (every `claude` process whose `/proc/<pid>/cwd` is that worktree); `git -C <wt> status --porcelain` and any `.git/index.lock`. The two live-agent sources must agree; if they disagree the answer is "cannot tell".
Decision rule (fixed before the run, so nobody bends it afterwards):
- GREEN: in all three runs the claim terminal and process are gone by the "just before coordinator writes" point and still gone at +30 minutes, both sources agree, and the claim left only untracked `.dev/issues/<N>/` files. Result: Route A, cap 1, throwaway issue only, no 516 change.
- RED: any run shows the claim agent alive at either late point, any disagreement between sources, any index lock, or any run not completed. "Cannot tell" counts as RED. Result: Route B. `claim_by coordinator` stays reserved and is not chosen.
Route B, exact shape: the poll creates one worktree per claim with `orca worktree create` carrying the claim agent as that worktree's one agent (this is what the owner's "every worktree gets an agent" rule already asks for), saves it as `launch_cwd` (plan row INV-018), and the coordinator copies the claim files from there. The coordinator's worktree gets no claim agent.
516 change: none to its scope in either result. Under RED only, post this note on Coder 516 (after the owner's go): "Correction to the owner decisions of 2026-11-18: the watcher's claim sessions no longer start in the `Coordinator` worktree. The watcher starts each claim in a worktree of its own. This issue's scope is unchanged: one `Coordinator` branch, worktree and `COORD-<RepoName>` session per project. Please do not add a claim worktree to the check."
Owner says in chat (one sentence; the owner supplies the repo name, because no throwaway repo is named in the plan files I read): "Yes, run the claim-lingering check by hand on <throwaway repo> issue <N>, three runs; if every run ends clean record Route A (poll, cap 1, throwaway issue only), otherwise record Route B (a worktree for each claim); nothing else changes and no real repo is switched on."
Agent then: runs the three runs, writes the record (observations at every point, both sources, raw outputs), states GREEN or RED by the rule, and asks the owner to confirm the route in chat. Only after that words-in-chat does it record OA-23 and, under RED, ask for the go to post the 516 note and add the Route B item to watcher issue 717.

## 2 Why this is best

- The plan already makes this check a gate: FR-70 "real rollout stays off until the X-001 live check ... is recorded and the owner picks the route" (`spec/SPEC.md:327`); RK-7 High with the four-point record (`SPEC.md:651`; `brainstorm/run/merged-requirements.md:817`); S17 order puts X-001 before OA-23 (`merged-requirements.md:547`); the default is poll, cap 1, throwaway, rollout off (`SPEC.md:585`).
- Nothing today shows the claim session ends. `refs/claim.md:94` on origin/master (2ea524514) ends the claim "here", which describes the procedure, not the terminal; the claim is a Claude CLI terminal started by `orca agent launch` (`launch.py:28`, `:136-157`), and an interactive CLI normally waits at its prompt. That is an inference, not an observation (UNVERIFIED), which is exactly why a live check is needed.
- Running by hand is safe: it uses the same launch command and the same claim skill as the poll, so the answer transfers; it needs no cron, no 516, no real repo. The poll itself cannot serve any repo until 516 creates the worktree (`debates/D07/VERDICT.md` item 9: `worktree_invalid`).
- Harm is real if lingering is missed: the coordinator commits claim records and needs "no other unpushed commit"; a sibling agent in that tree breaks it (`D07/adversarial/adversarial/invariant-probe.md`, INV-004, HIGH, UNADDRESSED).
- The listing and close commands exist in the design for the same Orca (`docs/designs/sc-issue-claim-pipeline-flag.md:190-191`, on origin/master). Whether the listing is complete for poll-launched agents is itself unproven (`merged-requirements.md:330, 890`), so I add the process table as an independent second source.
- Failing safe: unknown counts as lingering; the rule is written before the data.

## 3 Alternatives rejected

- First live check through the real poll on a throwaway issue (the plan's default order): makes cron, shared worktree and the unknown fail together, and is blocked until 516 lands.
- Skip the check and always isolate (Route B now): safest on paper, but costs the build below for a possible non-problem and Route B itself is untested (`orca worktree create` with `--agent --prompt`, and a taken name getting a numeric suffix per 516's own note). The check also tests that.
- Route C now (`claim_by coordinator`): S17 excludes it (`SPEC.md:503`); it is unproven that a coordinator can run the claim skill in its own session (`merged-requirements.md:889`); it holds the coordinator for the whole claim; it would need standing grants (OA-11 defaults to none); it contradicts K1 "the wake never means please claim". The merged spec's own advice (route C if lingering is seen, `merged-requirements.md:332`) is the one point where I disagree.
- A standing shared `Claim` worktree made by a 516 change: the owner rule forces an agent into it at creation, so a second agent arrives with the first claim; and 516 sits on hold at Clay's request (comment of 2026-11-20) in a repo the owner runs separately. Slower and no safer.
- A person closes each claim terminal: not zero setup, fails whenever a person forgets.
- The poll closes its own claim terminal (`orca terminal close`): needs a terminal handle in the launch reply (UNVERIFIED) and kills a session by script; keep as a later option, not the fix.

## 4 Implications, benefits, risks, costs

Benefits: one fact replaces a guess; the route follows a rule written beforehand; the real coordinator worktree is never the test bed; under GREEN the built poll is kept unchanged.
Costs (estimates; basis: three short runs, a 30-minute wait that runs beside the second record, and the size of `launch.py`, about 420 lines with one argv builder at `:136-157` and one launcher at `:399-416`): GREEN about 3 hours total (setup 1, runs and watching 1.5, record 0.5). RED adds about 8 to 12 hours (poll builds and saves the per-claim worktree 4 to 6, tests 2 to 3, cleanup of finished claim worktrees without `--force` or `rm` 2 to 3) plus 0.25 hour for the 516 note.
Risks: the claim writes to GitHub (comments, assignment) and may write to ClickUp; whether ClickUp is touched on a throwaway repo is UNVERIFIED, so the agent reads the claim skill's ClickUp step first and the owner is told before the go. Three runs prove only the paths tried, so GREEN keeps cap 1 and "throwaway only", and a hung claim later is still a risk (follow-up: refuse a launch when a non-coordinator agent is alive in the worktree, only once the process-table source is proved complete). The shared login `ironbelly` means these writes look like the owner's; mark the throwaway issue clearly. Route B adds worktrees and branches that need cleanup, and its Orca behaviour is unproven. A stand-in coordinator is not the real one, so a RED here may be milder than real life; that errs safe.
