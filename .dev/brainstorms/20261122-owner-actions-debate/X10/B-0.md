# X10 (OA-20) Proposal B-0: flipping WORKER_BINDING_PROVEN after a live binding probe

Agent B, lens: risk-first. Written 2026-11-22. All facts read from origin/master (2ea524514, fetched today) or the named files; anything not read is marked UNVERIFIED. Hour figures are estimates.

Short names. "The guard" is `launch-level-guard.sh` (a hook that blocks a governed session's commit, push, merge and similar calls); on master it is version 2 (`src/superclaude/hooks/scripts/launch-level-guard.sh:10`). Levels: W worktree, WA worktree after plan approval, F full, FS full with submit. "Binding" is the guard recognising a session as governed because its first prompt carries `[sc-launch:v1:<nonce>]` and a `pending/<nonce>` file exists. "The probe" is a live run of Orca `worker-start` workers that checks binding. "Issue 442" holds the guard's live observations (OB-H1 to OB-CTX).

## 1 Proposal
Keep the constant false until two clean runs of a worker-specific binding probe pass on the code that will ship, an independent agent re-reads the raw evidence, and the owner says one sentence naming the pull request head sha. Do it in two probes, not one.

**Probe 1, early feasibility (before the coordinator build, stage S14).** An agent starts one worker with the real `worker-start` on a disposable issue, after running `orca_worktree.py pending --level worktree` and putting the marker first in the prompt. It answers only the question the plan has never tested (RK-1): does the marker arrive at the guard intact. If not, stop building the worker route and fall back to "no worker on a real issue" (D05 confidence note b).

**Probe 2, the pass list (stage S17, against built code).** Run by an agent driving real terminals and saving screens and hook logs, on disposable issues only, with the probe worktree's `origin` (fetch and push) pointed at a local bare repository and checked by script before each prompt. Pass criteria, each needs a saved raw row, not an agent's summary:
- P1 Marker: the worker's first prompt event holds the marker at position 0, and the real `worker-start` reply shape is saved (the assumed key paths are UNVERIFIED, `launch.py` OPERATION_ID_PATHS).
- P2 Receipt: `pending/<nonce>` is gone within 60 s (the proposed value, record the real time), the session file holds the worker's own session id, and with two workers started in one cycle each file is matched to its worker by inode.
- P3 Enforcement in the worker's own session, at W then at WA after `release-worker`: `/sc:implement` refused at W and allowed at WA; `git commit`, bare `git push`, `git add && git commit` and `git merge` each show a hook row with no tool-result row plus the transcript "Blocked:" line; scripted `git push origin master` is refused. An agent that declines to type a command is NOT a pass (issue 442 left the protected push pending twice for that reason).
- P4 Fail-safe: a fake worker whose prompt has no marker leaves `pending/<nonce>`, and the coordinator stops it and escalates; a run with `jq` missing gives a refusal and no worker; a wrong nonce binds nothing and is caught the same way.
- P5 Session continuity: after `/clear`, kill and resume after `worker_done`, and a Claude Code restart, the worker is either still bound or the coordinator detects the change and stops it. Never silently unbound and working (runbook item 13, UNVERIFIED so far).
- P6 Environment: the worker's `HOME`, `PATH` and `jq` match what the guard needs; one `send` and one `ask` with no `--to` reach the coordinator.
- P7 Limits recorded, not passed: a script that pushes a feature branch, a push to `integration`, and a nested bare `claude "<prompt>"` (issue 678, item 8 FAIL) are written down as NOT stopped.
Two consecutive clean runs on unchanged code are required. A small coupling test (same idea as the existing R33 test) fails if the constant is true and the saved probe record is missing, has a failing row, or its recorded sha256 of the guard, `orca_worktree.py` and the hand-off template no longer match the files.

**The flip.** An agent makes a one-line commit (constant to true, plus the probe record), opened only with `/sc:pr-submit --monitor 3`. A different agent session that did not run the probe re-reads the raw files and writes a verdict that lists every row it could not confirm. Precondition read by `gh` just before the go: either the ruleset exists, or the owner accepts its absence in the sentence below.

**Owner sentences, in chat.** Probe go: "Go for the binding probe: an agent may start workers with worker-start on disposable issues <numbers> only, nothing else." Flip go: "Go to flip WORKER_BINDING_PROVEN for head sha <sha> of PR <n>. I read the probe record and the verifier's verdict. I accept that a script run, a push to integration, a nested claude run and a changed session id get past the guard, and that master has no ruleset <or: the ruleset is set>. Workers may run bound at worktree level, then worktree-approved after a recorded plan approval. Full submit stays closed." The agent records these words, date and sha in the task ledger under `.dev/tasks/` (staged, not committed) and posts nothing else.

**What stays off.** Full or FS for workers; `GOVERNED_LEVELS_ALLOWED` (the separate watcher gate, `launch.py:48`); `auto_enable`, cron, `coordinator_autostart`, cap above 1; `IR7_REFUSE`. A failed receipt check on any real issue after the flip sets a state file that refuses all later real starts until the owner says so (proposal; file path UNVERIFIED, the guard's TAMPER class covers `*.config/superclaude`).

## 3 Alternatives rejected
- Flip on the strength of issue 442's claim-route results: wrong route, stale guard version, three gate rows still FAIL or pending.
- One probe only at S17: finds a dead worker route after the whole coordinator is built. Probe 1 costs a few hours and can end the work early.
- Flip together with opening FS: FS lets a worker commit, push and open pull requests, the largest blast radius; D05 ties FS to OA-5 and issue 442 observations (`OA-TRIAGE.md:38`), and protected push is still pending.
- A config key or environment variable as the switch: the config directory is not tamper-protected (docstring at `launch.py:48-52`); only a reviewed commit counts.
- A person at the terminal as runner (the issue 442 pick-up note): agents already drove the 11-18 and 11-21 runs through saved screens; the owner's scarce attention is better spent as the go, with an independent verifier as the check on the runner.
- One clean run is enough: 442 needed several attempts (item 7 passed on its third run, `observation-results.md:248`); two consecutive passes cost little and catch flakiness.
- Never flip, keep probe issues only: safest, and the fallback if Probe 1 or P4 fails, but it leaves the unified plan with no worker.

## 4 Implications, benefits, risks and costs
Benefits: the plan's one High, never-observed risk (RK-1) gets a yes or no with raw evidence; a silent unbound worker on a real issue becomes detectable and stoppable; evidence cannot go stale unnoticed because it is bound to file hashes; the flip is a one-line, easy-to-review commit.
Costs (all estimates; basis: the 2026-11-21 claim rerun took 64 minutes of run time, and issue 442 needed four runs over four days for twelve items):
- Probe 1: 3 to 5 hours (scripting plus one worker run, reusing the 442 scripts). Probe 2: 8 to 14 hours over two clean runs, plus reruns after failures. Coupling test and hash record: 1 to 2 hours. Independent verifier: 1 to 2 hours. Flip PR with review monitor: 2 to 3 hours. Owner time: two chat sentences and about 20 to 40 minutes reading one table.
- Delay: no worker on a real issue until S14 to S16 are built and Probe 2 passes twice.
Risks that remain after a clean flip (state them, do not hide them):
- The guard reads command text only. A script run, a push to `integration`, a new session id, tools outside the hook matcher pass (D05 `VERDICT.md:22`, INV-034, INV-019, INV-003, INV-036). Binding mitigates honest drift on master and main; it does not stop a determined worker.
- The launch account is also an approver. Worker, owner and approver files all sit under the login `ironbelly`. The guard's own comment says names built from strings are not matched (`launch-level-guard.sh:454`), so a script can reach `*.config/superclaude`. Binding does not separate approval from work; only OA-6 (a separate agent login) plus the ruleset does. Until then merges stay typed by hand.
- No ruleset today (0 rulesets, master unprotected), so a worker's script push to master is stopped by nothing on GitHub.
- A probe false pass: an agent can be told to produce the evidence it is graded on. Counter: saved raw rows, a verifier that did not run the probe, hash-bound record, owner reads the list of unconfirmed rows.
- Owner under time pressure says yes to a summary. Counter: the sentence must name the head sha and the accepted limits, so a bare "go" is not a flip.
- A passing probe on a disposable issue does not predict a real repository (different hooks, `HOME`, MCP set; INV-012 UNVERIFIED). First real issue runs with cap 1 and the owner watching.
- Guard changes after the flip (a v3) silently invalidate the record; the coupling test turns that into a failing test.
