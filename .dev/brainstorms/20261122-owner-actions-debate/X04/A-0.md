# X04 round 0, agent A (pragmatic lens): Orca auth token printed in a debate subagent transcript

## 1 Proposal
Do one cheap check, add one prompt rule, and purge nothing.
1. The check (about 5 minutes of agent time). One agent runs a short script that pulls the leaked token out of the one transcript that holds it and counts how often it appears in the current Orca runtime file. It prints only two numbers, never a token. Exact commands (the agent must not cat either file):
   `umask 077; d=$(mktemp -d /tmp/x04.XXXXXXXX)`
   `grep -ohE 'authToken.{1,14}[0-9a-f]{48}' /home/coder/.claude/projects/-home-coder-workspaces-IronClaude/1779a921-dc86-44c8-867c-d5e117eb8e31/subagents/agent-a0164e160fb68a09c.jsonl | grep -oE '[0-9a-f]{48}$' | sort -u > $d/old`
   `echo old_tokens=$(wc -l < $d/old); echo still_in_runtime_file=$(grep -c -F -f $d/old /home/coder/.config/orca/orca-runtime.json); shred -u $d/old; rmdir $d`
   Read the result: `old_tokens=1 still_in_runtime_file=0` means the leaked token is dead (done). `still_in_runtime_file=1` means it is live: the owner quits and reopens Orca at a quiet moment (this closes every open terminal and agent session, so pick the time), then the agent runs the same check again and expects 0. `old_tokens=0` means the check proved nothing; stop and report.
2. The prompt rule (about 15 minutes). Put this in the shared brief that debate and subagent prompts start from: "Never open, print or search the contents of any file under ~/.config/orca, ~/.config/gh, ~/.ssh, or any file whose name contains runtime, token, secret, credential or env, unless the task names that exact file. To learn a value from such a file, ask for that one field (for example `jq -r .port`), never print the file and then hide parts of it. Use `stat` or `ls -l` to test that a file exists. If a command might print a secret, make it print a count (`grep -c`) or exit status (`grep -q`)."
3. No transcript purge. No hook now (see section 3).
Owner sentence in chat: "X04 approved: run the Orca token same-or-different check, tell me the result, do not purge the transcript, and add the no-secret-files rule to the debate brief."
What an agent then does: runs the check, records the result and my approval in the progress log, makes the brief edit, and tells the owner the one line to act on only if the result is live.

## 2 Why this is best (evidence)
- What leaked and where: the D02 debate (an earlier debate in the unify plan) printed the `authToken` field of `/home/coder/.config/orca/orca-runtime.json` into its own transcript. Sources: `.dev/brainstorms/20261120-pr686-unify/DECISIONS.md:1176-1178`, `debates/D02/VERDICT.md:63`, `STATE.md:27`, `debates/D02/adversarial/adversarial/rounds/round2-advocate-2.md:86` ("my redaction pattern did not match").
- Only one transcript holds it. I searched by file name only (`grep -l` for the shape `authToken` plus 48 hex characters) in every Claude transcript changed since 2026-11-20 03:30, and the answer was one file: `.../1779a921-dc86-44c8-867c-d5e117eb8e31/subagents/agent-a0164e160fb68a09c.jsonl`, 2,061,029 bytes, last written Nov 20 04:18, mode 600. The main session transcript for that session does not match. A wider scan of all of `~/.claude`, `.dev`, `.cache` and `/tmp` timed out, so those places stay UNVERIFIED beyond what the coordinator checked in `.dev`.
- The token is probably already dead. In `/opt/Orca/resources/app.asar` the runtime server class sets `authToken=(0,Y.randomBytes)(24).toString("hex")` as a per-instance field, so a new server object likely gets a new token (24 bytes = 48 hex characters, which matches the shape I found). Orca's main process, pid 481, started Sat Nov 21 02:08:40 2026 (`ps -o lstart`), and `orca-runtime.json` was rewritten 2026-11-21 02:08:41 (`stat`). The leak (Nov 20, about 04:00 to 04:18) is before that restart. That is strong but not proof; whether the token is stored and reused across restarts is UNVERIFIED, which is why step 1 compares values instead of assuming.
- Who could have read the transcript: only the Unix user `coder`. `/home/coder` is `drwx------`, `~/.claude` is `drwx------`, and 962 of 963 subagent transcript files are mode 600 (the one 644 file is a workflow journal, not the token file). 17 of 43 session folders are `drwxr-xr-x` but sit under the 700 parents. `id` shows only uid 1000 in this container. Because the owner and all agents share one login, any agent session on this host could read it. Root or the hosting platform could too (UNVERIFIED), and the text was sent to the model service as part of that subagent run, which nobody here can recall.
- What the token allows: it belongs to Orca's runtime server, which the `orca` command uses to create and remove worktrees, open terminals and send text into them (that is, run commands as `coder`), launch agents, and use Orca's browser (`~/.claude/skills/orca-cli/SKILL.md` description). Reach is local: Orca pid 481 listens on unix socket `/home/coder/.config/orca/o-481-5fa4.sock` (mode srw-------), and on loopback only at 127.0.0.1:6768 and 127.0.0.1:45953 (read from `/proc/net/tcp` and `/proc/*/fd`). The only non-loopback listener, 0.0.0.0:61333, is `tailscaled`, not Orca. Someone who already runs code as `coder` gains nothing from the token; a different local user could reach the loopback ports. Which RPC the two loopback ports serve is UNVERIFIED.
- The rule gap is real: `grep` of `~/.claude/CLAUDE.md`, `settings.json`, hooks, `RULES.md` and the orca skill finds no rule against printing runtime files. This round's brief already carries "never read or print `orca-runtime.json`", so the fix is to make that sentence standard, with an allowlist (ask for one field) instead of a denylist (hide parts after printing), because the denylist is exactly what failed in D02.

## 3 Alternatives I rejected
- Restart Orca now to force a new token: costs every open terminal and session, and the evidence says it already happened on Nov 21 02:08. Only needed if step 1 says live.
- Purge or redact the transcript: rewrites a 2 MB session log (risk of breaking resume), and the token is only useful while it is live. If it is dead, the leftover text is a random string with no use. If it is live, rotate it; purging would not undo exposure anyway.
- Do nothing because the socket is mode 600: skips a 5 minute check and leaves the loopback ports and the same-login agents unaccounted for.
- Edit the runtime file or the token by hand: it is Orca's own file; a wrong edit breaks the `orca` command for every session.
- A blocking hook now (a PreToolUse guard that refuses commands naming `orca-runtime`, like `.claude/hooks/reject-workspace-writes.sh` registered at `.claude/settings.json:5-10`): good second layer but new code and tests for a once-seen mistake. Defer until a second incident; the prompt rule is enough for now.
- Make the owner rotate "to be safe": it costs real session loss for a token that is probably already replaced.

## 4 Implications, benefits, risks and costs
- Benefit: closes the item with evidence in minutes, with no outage, and no new tool or code.
- Cost (estimates): owner chat 1 minute; check 0.1 hour (one command, basis: one pipeline and one result); brief edit 0.25 hour (one paragraph, basis: wording plus where to place it); if live, owner restart 0.1 hour plus lost sessions; optional hook later 1 to 2 hours (basis: one script like the existing hook, one settings entry, one test).
- Risk 1: the check reads the token into memory and a private temp file (mode 600, deleted by `shred -u`). Mitigation: only counts print; the agent must run it as written and may not add `cat`, `echo` of the variable, or `set -x`.
- Risk 2: the check uses a pattern match; if the transcript stores the token with a different layout, `old_tokens=0`. Mitigation: that result is reported as "not proven", not "safe".
- Risk 3: the prompt rule can be ignored by a careless agent; a hook is the only mechanical fix. Accepted for now.
- Risk 4: the app code finding comes from a minified bundle; treat "regenerated at start" as likely, not proven, until step 1 runs.
- Residual: the model service saw the token once; with a dead token that has no further use.

## 5 Preconditions and order
- No dependency on any code stage. Do it any time before the watcher goes live (spec panel finding F13 says rotating has no stage and is not yet a precondition of the live enable: `spec/panel/review-1/spec-panel-report.md:240`; I suggest it become one line in the live-enable checklist, since the check takes minutes).
- Order: owner gives the sentence in chat, agent runs the check, agent records the result, only then (if live) the owner restarts Orca, then the agent re-runs the check, then the brief edit. The brief edit does not need to wait for the check.
