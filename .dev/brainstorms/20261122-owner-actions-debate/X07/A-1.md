# X07 (OA-11) standing grants. Agent A, round 1 (Pragmatic lens)

Checked 2026-11-22 after `git fetch`; master tip `2ea524514`. SPEC = `.dev/brainstorms/20261120-pr686-unify/spec/SPEC.md`. "Grant" = a standing permission for one kind of GitHub write. "S14" = plan stage 14, which builds the merge path and the grant checks.

## 1 Agreed (what I now accept from B, and what I changed)
- **Store grants in their own file, not in the watcher config.** Verified: `cycle.py:59-71` on master lists the allowed top-level keys and has no `grants`; `cycle.py:223-226` turns any other key into `config_invalid`. A typo in a grants key could stop the poll. `generate.py:210` already puts the approvers list in its own file beside the config (`<name>-approvers.txt`). I had put grants in the config (SEC-10 wording). Changed: `<config_dir>/<name>-grants.json`.
- **Expiry.** I had "none by default". B's point that nobody revokes what they forgot holds, and a dated end is one date compare. Changed: every record has an end date, and the refusal says "expired on <date>".
- **Names only for a grant.** The tool refuses "all" or "everything" in a grant sentence. A revoke may say "all".
- **Revoke rules.** Newest line per repo and entry wins; a revoke wins a tie; it bites at the next write. An agent may suspend an entry after a wrong write if it says so in chat; only the owner turns it back on. Both only narrow.
- **Who records.** Only a session the owner opened and types in (SEC-08 already says typed by a person in their own session, never relayed). Never a worker, never a script-started coordinator.
- **Failed runs need only `issue.comment`.** SPEC FR-83 (line 243) already says "Failed, blocked or partial: comment only", but its last sentence demands both grants. I accept the wording fix: a succeeded run needs both, a failed run needs only the comment.
- **Assign stays ungranted.** D04 item 6 (`debates/D04/VERDICT.md:22`): `E-NO-GRANT` backs only the coordinator's own verbs; assignment comes from `/sc:issue`. Both of us withhold it.
- **Real repos: body entry only after the owner has read one posted plan section** (B's sample-first rule).

## 3 Revised proposal (the one I would sign)
**Entries.**
1. Give `issue.comment` and `issue.status.move` first. They are the two writes the `complete` verb makes (FR-83). Status moves only to In review; a person's move to Done is left alone.
2. `issue.body.append_plan_sections`: give it when a verb that checks it exists. First on the throwaway repo, then on a real repo only after one posted plan section has been read by the owner.
3. `issue.assign`: not given. Claim assigns `@me` and is idempotent.
4. Never standing: `pr.merge`, `issue.close`, `issue.hold` (SEC-06, Q03). One per-PR go on the head sha covers merge and that PR's issue close (OD-10).

**Scope.** One repository per record. A repo added later starts empty. Usable only on an issue that has an adoption record (FR-29). That check is my proposal; UNVERIFIED that S14 enforces it. Order: throwaway repo (OA-19; not yet named, UNVERIFIED) first, then `IronbellyOrg/IronClaude` after the throwaway run passes.
**Expiry.** Record carries an end date: 30 days (throwaway) or 90 days (real repo) unless the owner names a shorter date.
**The owner's one sentence:** `Grant issue.comment and issue.status.move on <owner/repo> for 30 days.`
**Recording.** The same session records it and replies once. Before S14: one line in the interim ledger (SEC-14, task package under `.dev/tasks/`, always staged), marked "procedure only, not enforced by code": id, date, repo, entries, end date, quoted words, recorder. From S14: `repos grant` writes the same fields into the grants file. The grants-file path joins the SEC-10 protected set (verb refusal plus Write/Edit hook). The owner writes no file.
**Reading.** Every write re-reads the file; missing, malformed, unknown entry, wrong repo, expired, or repo disabled means no grant. Each use is logged in `grants-use.jsonl` naming the grant (SPEC line 176, SEC-07).
**Revoke.** `Revoke issue.comment on <owner/repo>.` or `Revoke all on <owner/repo>.` An agent appends a revoke line the same turn. A revoke needs no accepted-record check (it only narrows). Neither SPEC nor DECISIONS names a revoke verb, so add `repos revoke` to S13.
**Refusal (printed before any `gh` call, no issue text echoed, SEC-16):** `Refused: no standing permission for <entry> on <owner/repo> (none recorded, expired on <date>, or revoked). Nothing was written to issue <N>. To allow it, the owner says in chat: "Grant <entry> on <owner/repo> for <30|90> days." The coordinator recorded an escalation locally.` For a failed run whose comment is refused, the local escalation must show the failure so it is not hidden.

**Benefits.** The coordinator can close the loop on a finished issue with no owner round trip. Authority is two small writes, one repo, adopted issues, short life. A typo cannot stop the poll. Merge, close and tag stay out.
**Risks (each narrows, none closes).**
- Shared login `ironbelly`: only our verbs check grants (D15 row D5; SEC-13, SEC-18). A shell with the login can run `gh` directly. Say "narrows", never "closes".
- Public repo: comments and Status moves are world-readable and appear as the owner. Comment text stays outcome word, validated paths, PR number. A comment can be deleted; a Status move moved back. Edit history of a body write stays after revoke.
- Before S14 nothing refuses a write (grep for `grant` in `src/superclaude/cli/issue_watch/` on master returns nothing; `issue_pipeline/complete.py:3` and `cli.py:252` say "under the issue's grant row" in text only). Also SPEC line 61 is stale: `complete.py` is already on master (UNVERIFIED which PR landed it).
- Contract lines `WORKER-CONTRACT.md:302-303` still say "that issue's grant row". Amend with FR-84 and the owner's chat approval (OA-7). Line 57 matched my search for the "still written by the owner" wording; B's reading of it is UNVERIFIED by me.
- Expiry chore: one sentence per repo per 30 or 90 days; if forgotten the coordinator refuses safely, and the text says "expired".

**Costs (estimates, basis stated).**
- Owner: about 1 minute per sentence (one message). Agent recording: about 15 minutes per grant (one ledger line and a read-back).
- Spec and contract edits: about 1.5 hours (SEC-07, SEC-10, X-1/OD-11/OA-11 three-versus-four wording, FR-83 sentence, contract 302-303; basis: about eight table rows).
- Build over what S14 already has: grants-file loader with expiry 1 hour; `repos revoke` 1 to 2 hours; expiry, wildcard, revoke-tie and malformed-file tests 2 to 3 hours; adopted-issue check 1 hour. About 5 to 7 hours total (basis: about eight small tests plus about 80 lines; I did not measure Clay's parser).

**Order.** (1) Owner confirms the chat-grant reading (OA-7). (2) Spec edits land before S14 so tests pin expiry and the file. (3) S13 and S14 built. (4) OA-19 names the throwaway repo; owner says sentence 1. (5) After the throwaway run passes, sentence 2 for `IronbellyOrg/IronClaude`. (6) Body entry per item 2 above.
