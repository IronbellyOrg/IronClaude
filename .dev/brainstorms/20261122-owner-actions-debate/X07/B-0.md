# X07 round 0, agent B (risk-first): which standing grants the coordinator may have (OA-11)

Checked 2026-11-22 against origin/master tip 2ea524514 (after fetch) and the plan files. Words used: a "grant" is a standing permission for one kind of GitHub write; "S14" is plan stage 14, the stage that builds the merge path and the grant checks; "ledger" is the interim record file of owner answers (SEC-14).

## 1 Proposal
**The action.** Give grants one repository at a time, never global, each with an expiry, and give fewer than the plan's four at first.
1. **Scope: per repository, on this host.** A grant names one `owner/repo` and is stored on the host where the owner said it. A grant here does not reach Clay's or Jonathan's hosts or any repository added later.
2. **First grant: the one throwaway repository of OA-19 only.** Entries given: `issue.comment` (result or hand-back comment), `issue.status.move` (Project Status to In review only, never Done), `issue.body.append_plan_sections` (plan sections added to the issue body).
3. **Withheld: `issue.assign`.** The claim assigns `@me` and is idempotent when the issue is already assigned to the login. So the coordinator only claims issues a person already assigned, and needs no standing assign. Not grantable at all: `pr.merge`, `issue.close`, `issue.hold` (SEC-06, Q03).
4. **A real repository gets its own sentence after its own switch-on (OA-19).** Its first plan-body write is a per-issue go; the standing body entry is granted only after the owner has read one posted plan section.
5. **Expiry: every grant ends on a stated date.** Default 30 days, at most 90 days, no "forever". After it ends the writes refuse until the owner says the sentence again.
6. **The owner's one chat sentence (names only, no wildcards):** `Grant issue.comment and issue.status.move on IronbellyOrg/<throwaway-repo> for 30 days.` (`<throwaway-repo>` is not yet named; UNVERIFIED which repo OA-19 will pick.) The tool refuses the words "all" or "everything" for a grant.
7. **What an agent then does.** Only a session the owner opened and types in records it (never a worker, never a script-started coordinator). Replies "Received" once. Before S14 it appends one line to the ledger (L-01): grant id, date, host, repo, entries, expiry date, the owner's quoted words, recorder; the line says "procedure only, not enforced by code". From S14 `repos grant` builds the same record from the parsed sentence and appends it to `<config dir>/issue-watch.d/<name>-grants.json`, a file beside the approvers file, not a key inside the watcher config.
8. **How a grant is read.** Every write re-reads the file, no cache. Missing, unreadable, malformed, unknown entry name, wrong repo, past expiry, or the repo's `enabled` false means no grant. Each use is logged with the grant id (SEC-07).
9. **Revoke.** Owner says `Revoke issue.comment on <repo>.` or `Revoke all on <repo>.` (revoke may use "all"; grant may not). The agent appends a revoke line; the newest line per repo and entry wins and a revoke wins a tie; it bites at the next write. An agent may also suspend an entry on its own after a wrong write and must say so in chat; only the owner re-enables it.
10. **Refusal text (plain English):** `Refused: the coordinator has no standing permission to <entry> on <repo> (none recorded, expired on <date>, or revoked). Nothing was written. To allow it the owner says in chat: "Grant <entry> on <repo> for 30 days." Any session the owner types in then records it.`

## 2 Why this is best (evidence)
- **Master has no grant code today.** `git grep -i grant` on origin/master under `src/superclaude/cli/issue_watch/` finds nothing. `issue_pipeline/complete.py:1-4` only says it runs "under the issue's grant row" and has no check. `WORKER-CONTRACT.md:303` ("post an issue write without that issue's grant row") and `hooks/scripts/launch-level-guard.sh:76` are text only. So until S14 a grant is a procedure, and the plan must say so (SEC-18 "narrows").
- **Master line 57 still says "still written by the owner"** (`WORKER-CONTRACT.md:57`), against the owner's chat rule (Q01 item 2). The grant cannot be recorded in chat until the owner confirms that one reading (OA-7).
- **Grants must not live in the watcher config.** `cycle.py:223-226` rejects any unknown top-level key (`_TOP_KEYS` at `cycle.py:59`), so a `grants` key makes `config_invalid` and the poll would stop. A separate file follows the approvers-file pattern (`generate.py:210`, `:257`); a bad grants edit then costs only coordinator writes, never the poll. SPEC row 2 (`SPEC.md:172`) puts grants in the per-repo config: this is a change I propose.
- **Per repo, not global.** New repos are generated off (`generate.py:252` `"enabled": False`) and OA-19 starts every repo off (`SPEC.md` section 10.6). A global grant would arm a repo the owner never saw. The repo is public, and `gh api repos/IronbellyOrg/IronClaude` shows visibility public.
- **Status move is already bounded in code:** only from Research, Spec, Plan, Debug to In review (`predicates.py:300`, `complete.py:55-59`, `:409`); a person's move to Done is left alone. The comment holds only an outcome word, validated paths and a PR number (`complete.py` docstring).
- **Assign is not controlled by a grant.** `E-NO-GRANT` does not see `/sc:issue` writes (D04 item 6); the claim runs `gh issue edit --add-assignee @me` (`sc-issue-protocol/SKILL.md:74`, `:87`) and is idempotent when already assigned (`refs/claim.md:43`), stops if assigned to someone else (`SKILL.md:164`). A grant with no control is only a permission.
- **Body edits are the riskiest of the three:** a body edit after approval voids the approval (D01 item 5, quoted in issue 716 S02-F9), the text is public, and the body is later read by agents (SEC-16). Hence the sample-first rule for real repos.
- **Shared login.** `gh api .../collaborators` shows `ironbelly` admin true; `clayphi` and `IB-JonathanB` push true, admin false. A grant cannot prove who typed (OA-6 unnamed, SEC-09), so it must be small, short and visible, not trusted.
- **Plan record.** OD-11 and SEC-07 (`SPEC.md:107`, `:296`); QG3 item 3 (empty default, quoted words, date, scope, recorder); OA-11 safe default (`SPEC.md:580`); interim ledger SEC-14 (`SPEC.md:303`).

## 3 Alternatives rejected
- **Plan default as written (four entries, no expiry, in the config).** Rejected: assign has no control, the body entry is unproven on public text, no expiry on a shared login, and the config key breaks the poll (`cycle.py:223`).
- **No standing grants, a per-use chat sentence every time.** Safest on paper, but each plan and result waits on the owner, and a person under time pressure then says "grant everything" once. Names-only sentences with a short expiry keep the sentence small and the pressure low.
- **Global grants.** Rejected, see per-repo evidence.
- **Grants with no expiry and revoke only.** Rejected: nobody revokes what they forgot; a dated end fails safe by itself.
- **Standing `issue.close` or `pr.merge`.** Barred by SEC-06 and OD-10; one per-PR go bound to the head sha covers merge and close.
- **A hook or file lock to keep agents out of the grants file.** All sessions run as one OS user, so it only narrows (OD-12, QG3 item 4); I keep the verb refusal and the Write/Edit hook of SEC-10 and add nothing more.

## 4 Implications, benefits, risks and costs
**Benefits.** The coordinator can post results and plan sections on the throwaway repo from day one with one owner sentence; a forgotten grant ends by itself; a typo in grants cannot stop the poll; no grant can merge, close or tag; the owner's rule (chat only, no file written by the owner) holds.
**Risks that remain (each narrows, none closes).**
- Any session on this host can type a ledger line claiming the owner said it; the quoted words and recorder make that visible after the fact, not impossible (OA-6, SEC-09).
- Before S14 nothing refuses a write; the grant is a procedure plus a log line.
- The coordinator's own shell can run `gh issue comment` as the shared admin login whatever any grant says (SEC-13 style limit).
- Public text is permanent: a comment or body edit stays in the edit history after revoke. Revoke stops new writes only.
- Expiry adds a chore: one sentence per repo per 30 days. If the owner forgets, the coordinator degrades to refusing, with the sentence in the refusal. That is the safe failure, but it can look like a bug; the refusal text must say "expired".
- A refusal on a failed run's comment would hide the failure from the issue: `complete` currently demands both comment and status entries (FR-83, `SPEC.md:243`). I suggest FR-83 need only `issue.comment` for failed, blocked or partial outcomes and `issue.status.move` only for succeeded (a spec change for the debate).
**Costs (estimates, basis stated).**
- Spec edits: SEC-07 gains expiry, per-repo scope, withheld assign, separate file; fix the three-versus-four mismatch (FOLLOW-UPS G1); issue 716 S05-F23 says the plan-body grant is "not one of" the four, against `SPEC.md:107`, to be reconciled. About 1 hour (estimate: five table rows and one issue edit).
- Build at S14: `repos grant` and `revoke` verbs, loader with expiry and fail-closed reads, refusal text, one `E-NO-GRANT` test per entry (four cases in SEC-07) plus expiry, wildcard, revoke-tie and malformed-file cases. About 8 to 12 hours (estimate: about 10 test cases plus about 150 lines of code; I did not measure Clay's parser, `repos.py:295-299`, which I could not open in master).
- Interim ledger entry per grant: about 15 minutes of agent time. Owner time: about 1 minute per sentence.
