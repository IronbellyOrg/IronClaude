# X07 (OA-11) Which standing grants the coordinator may have. Agent A, round 0 (Pragmatic lens)

Read-only investigation on 2026-11-22. Paths: SPEC = `.dev/brainstorms/20261120-pr686-unify/spec/SPEC.md`, DEC = `.dev/brainstorms/20261120-pr686-unify/DECISIONS.md`, QG3 = `.dev/brainstorms/20261120-pr686-unify/debates/QG3/VERDICT.md`. "master" = origin/master after `git fetch`.

## 1 Proposal

Give two standing grants, to one repository at a time, and only when the code that reads them exists. Give nothing today.

- **Grant now-ish (at S14, when FR-83 can run): `issue.comment` and `issue.status.move`.** They cover the one write the coordinator makes after a worker finishes: one result comment (outcome word, checked file paths, PR number only) and, for a succeeded run only, the Project Status move to "In review" (SPEC FR-83, line 243).
- **Do not grant yet: `issue.assign` and `issue.body.append_plan_sections`.** The first has no consumer in the first build (the claim session already assigns). The second is used only by the hand-back re-plan (FR-35, S15c), which voids the issue's approval anyway. Each is granted by its own sentence when its stage lands.
- **Never standing:** `pr.merge`, `issue.close`, and `issue.hold` (SEC-06, Q03). Merge and close stay one per-PR go on the head sha (OD-10).
- **Scope: per repository, never global.** The entry lives in that repo's own config next to `merge_safety_files` and `reviewers` (SEC-10 names that file as the protected one). A repo added later starts empty. Order: the S17 throwaway repo first, then `IronbellyOrg/IronClaude` after the throwaway run passes.
- **Issue scope inside a repo:** a grant is usable only for an issue that has an adoption record (FR-29). Proposal, UNVERIFIED that S14 code enforces it: without this, a grant is a license for any issue number.
- **Expiry: none by default.** It ends on revoke. The owner may add "until <date>" in the sentence; the record stores it and the verb refuses after it. A silent lapse would make results stop appearing, which is worse than a standing low-stakes write.

**The one chat sentence (owner):** `Grant issue.comment and issue.status.move on <owner/repo>.`
**What the agent does (the same session, from that message):** run the grant verb (SEC-07 names `repos grant`; its flags are not designed, so the command below is a sketch, UNVERIFIED):
`superclaude coordinator repos grant --repo <owner/repo> --entry issue.comment --entry issue.status.move --owner-words "<the sentence>" --recorded-by <agent id>`
The record holds the quoted words, the date, the repo, the entries, optional end date and the recorder (Q01 item 3; SEC-08). Before S13 the verb does not exist: the agent writes the same five fields into the interim ledger in the unification task package (SEC-14, always staged), and S13 imports it. The owner writes no file.

**Revoke:** owner says `Revoke issue.comment on <owner/repo>` (or `Revoke all grants on <owner/repo>`). The agent removes the entry the same turn and records the words. A revoke only narrows, so it must not need the SEC-10 accepted-record check. Neither SPEC nor DEC names a revoke verb (`grep -i revok SPEC.md` returns only merge-go lines 110, 290, 615, 683), so add `repos revoke` to the S13 skeleton. Each use is logged in `grants-use.jsonl` naming the grant (SPEC line 176, SEC-07).

**Refusal message** (printed before any `gh` call, JSON contract plus one plain line):
`E-NO-GRANT: <owner/repo> has no grant "issue.comment", so nothing was written to issue <N> on GitHub. To allow it, the owner says in chat: "Grant issue.comment on <owner/repo>." The coordinator has recorded this as an escalation.`
It names the missing entry and the sentence, never echoes issue text (SEC-16), and the escalation is a local report entry, not a GitHub write.

## 2 Why this is best (evidence)

- **No code reads grants today.** `git grep -i grant origin/master -- src/superclaude/cli/issue_watch/` prints nothing. The only GitHub write in that folder is the label `create` at `repo_init.py:76`; `cycle.py:205` says the cycle "writes nothing". SPEC line 62 lists `E-NO-GRANT`, `merge-gate`, `answer-check` as "NOT BUILT anywhere". So a grant recorded today protects nothing and can go stale; recording it when S14 lands keeps the record fresh (Q01 item 4: a go must be newer than the entry's last edit).
- **The two entries are exactly what FR-83 needs.** SPEC line 243: without `issue.comment` and `issue.status.move` the completion verb "refuses before any `gh` call". Master contract `WORKER-CONTRACT.md:302-303` still says the completion verb runs "only under that issue's grant row" and "post an issue write without that issue's grant row" is forbidden. The per-issue row has no reader on master (QG3/Q01 reading), so a standing per-repo entry is the replacement, and FR-84 must say so (see section 5).
- **The other two have no first-build consumer.** `grep -n 'issue\.assign\|append_plan' SPEC.md` finds them only in SEC-07, FR-07 and X-1. Claim assignment is done by the claim session `/sc:issue --claim` built at `launch.py:33-36` on master, not by a coordinator grant. The plan-body write belongs to `/sc:issue --plan` under hand-back (FR-35, D09 verdict line 21). QG3's own reason for dropping `issue.hold` applies: "a grant for a write the poll never makes is a trap" (variant-1 K6 row, `brainstorm/run/nested/adversarial-1/adversarial/variant-1-opus-architect.md:99`).
- **Per repo fits the design already.** SEC-10 protects per-repo keys including `grants`; DEC line 1357 and QG3 OD-11 default is empty and fail closed; the plan's own text is "default empty, owner grants once in chat, agent records" (QG3 item 3, line 16).
- **The repo is public and `master` is unprotected.** `gh api repos/IronbellyOrg/IronClaude --jq .visibility` printed `public`; `gh api .../branches/master/protection` returned HTTP 404 "Branch not protected" (2026-11-22). That is why merge and close are not standing; a comment and a Status move are bounded, and a person can undo both.
- **Matches the rule that the owner writes no file.** QG3/Q01 item 1: the grant is given in chat and recorded by the agent (SEC-14).

## 3 Alternatives rejected

1. **All four entries now (the plan's maximum, SEC-07).** Two have no consumer and one (`append_plan_sections`) edits the body of an approved issue, which voids approval and, in a public repo, edits text people read. Rejected: more standing power than the first build uses.
2. **No standing grants; a chat go for each comment and Status move.** This is the safest and the slowest: one owner sentence for every finished issue, and the loop stalls whenever the owner is away. Rejected because both writes are reversible, bounded and logged. It remains the fallback if the owner declines the grant.
3. **One global grant for every repo.** A repo added later would inherit a write power the owner never looked at; public repos differ in who can see the comment. Rejected.
4. **Expiry clock (for example 14 days).** Adds a silent failure: results quietly stop. The plan itself uses no clock for the merge go in the first build (OA-13a, SPEC line 110). Rejected; use revoke and the use log instead.
5. **Owner types the grant into the config file.** Breaks the owner rule (never writes a file); QG3 OD-12 also puts that file behind verb and hook guards.
6. **Grant today, before S13.** Nothing reads it (section 2); the owner would carry an unused permission for weeks. Rejected; the decision "which two, which repo" can still be said and ledgered now if the owner prefers.

## 4 Implications, benefits, risks, costs

**Benefits.** The coordinator closes the loop on a finished issue (comment plus "In review") with no owner round trip. Authority stays small: two writes, one repo, on adopted issues. A tested refusal tells the owner exactly what to say. Every use is logged naming the grant.

**Risks.**
- **Shared login (`ironbelly`).** The grant is checked only by our own verbs ("covers verb writes only", row D5 of `debates/D15/VERDICT.md`; SEC-13, SEC-18). An agent or script with the login can run `gh` directly. Treat it as a brake on honest drift, not a security wall; word it "narrows", never "closes".
- **Public repo.** Comments and Status moves are world-readable and appear as the owner. FR-83 limits comment text to the outcome word, validated paths and a PR number; keep that test (no issue text, no paths outside the repo). A wrong comment can be deleted by the owner; the Status move can be moved back by hand.
- **Prompt injection.** Issue text is untrusted (SEC-16). The blast radius of a hostile issue is capped at a comment and a Status move on an adopted issue.
- **Contract mismatch.** Master contract line 302-303 says "that issue's grant row". Until amended, a literal worker could read a standing per-repo grant as not enough.
- **Fresh-record risk.** If the owner says the sentence early and S14 changes the entry names, the record is wrong. Mitigated by saying it at S14.

**Costs (estimates; basis stated).**
- Owner: one chat sentence per repo per entry set, about 1 minute each (estimate: one message). Two repos, so 2 sentences now, 1 more per later entry.
- Agent recording: about 0.25 h per grant (estimate: one ledger entry or one verb call plus a read-back).
- Extra build over the plan: `repos revoke` verb with a test, 1 to 2 h (estimate: mirrors `repos grant`, same lock and record check, one test); the "adopted issue only" check, 1 h (estimate: one lookup of the FR-29 record plus one test). The per-entry `E-NO-GRANT` tests are already in S14 (SEC-07 acceptance), so they are not new.
- Contract wording change for lines 302-303 rides in the FR-84 amendment; extra review about 0.5 h (estimate).
