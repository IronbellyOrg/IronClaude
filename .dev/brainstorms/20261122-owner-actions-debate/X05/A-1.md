## 3 Revised proposal (the unified one I would sign)
Definition. "The owner" for typed answers means the GitHub account `ironbelly`, identified by its numeric id, and only that. Agents on the host run as a separate machine account ("AGENT", name the owner's choice; `IB-AIReviewer` is an existing read-role org member of unknown purpose, so the owner says whether it is meant to be this account).
Order and who does what:
1. Owner says in chat: "OA-6: the owner means ironbelly only. Create a separate agent account. Record it." An agent records the quoted words, date and recorder in the interim ledger (SEC-14) and runs `git add .dev/tasks` (no commit unless asked). Until cutover nothing else changes.
2. Owner (account creation and 2FA are owner-only) reads GitHub's machine-account terms, creates AGENT, turns on 2FA, invites it as an outside collaborator with Write on IronClaude only (and on `IronbellyOrg/Coder` only if the owner wants agents filing issues there).
3. OA-5 ruleset, set by the owner with the D16 settings (master and integration, pull request required, code owner review, dismiss stale approvals, bypass for Admin only). It needs the CODEOWNERS PR first (D16 VERDICT) and the roles accepted by Clay. AGENT has Write, so no bypass.
4. An agent reads `ironbelly`'s id and AGENT's id (`gh api users/<login> --jq .id`) and writes `owner_account_id`, `approval_excluded_ids` and the agent id to per-repo config, plus the migration list of open issues assigned to `ironbelly`. S14 builds the id parameter and the fail-closed refusal (SEC-09). It states the residual risk: chat-only answers (grants, `--apply`) still leave no GitHub trace (D06 item 9).
5. Owner switches ONE host: stores the AGENT token, revokes old `ironbelly` tokens. The owner says go, then tests run on throwaway PRs: `gh api user --jq .login` prints AGENT; the collaborator permission read prints `write`; an unapproved AGENT PR cannot merge; `gh pr merge --admin` and a push to master are refused; both review bots answer; claim assigns AGENT; issue type, Complexity and Approved writes work; watcher sees an AGENT-assigned issue.
6. Owner says "Cut over" in chat; agent records it with the ruleset id and AGENT token expiry date. Only now may `answer-check` pass a merge go, and only with the GitHub approval by `ironbelly` on that head sha. The chat go stays first (owner rule); the Approve click is the lock key, not a second go. Other hosts switch one by one with the same first two tests.
Effects. `/sc:pr-submit`: no change to `--repo IronbellyOrg/IronClaude`; it never merges (`git grep "pr merge"` over its skill and code on origin/master found nothing); PR author, replies and resolves become AGENT; its fix pushes dismiss stale approvals, so the owner approves after the last round. Workers: same login as the coordinator; can push feature branches, open PRs and comment, cannot merge, bypass or approve as the owner (SEC-13 stays "narrows"). Coordinator: merges only after the chat go plus the id-matched approval; never holds an owner credential; before cutover it asks the owner to merge by hand.
Cost (estimates; basis: D16's own figures of about 20 min owner chat and 15 to 30 min for the ruleset, plus ordinary account setup and my judgement). Owner: about 1 to 1.5 h one-time, about 1 min per merge, about 15 min per token renewal (token expiry assumed 90 days). Agent: about 3 to 4 h one-time (id parameter inside S14 1 to 2 h, tests about 1 h, ledger, config and migration about 1 h). Ruleset time is OA-5's, already counted.
Main risks and fixes: old `ironbelly` credential left on the host (revoke, `--admin` test, id check); owner logs back in under pressure (break-glass rule, id check announces it); bots silent on AGENT (test first, SEC-04 hold); token expiry stops all agents (date in ledger, owner keeps browser path, fails safe).
