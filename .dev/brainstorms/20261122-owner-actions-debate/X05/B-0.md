# X05 B-0: who counts as "the owner" for typed answers (OA-6). Agent B, risk-first lens

Read-only investigation on 2026-11-22. Anything I did not open is marked UNVERIFIED. Estimates are marked as estimates.

## 1 Proposal
**Definition.** "The owner" for typed answers is the GitHub account `ironbelly` and nothing else. That login is kept by the person and taken off this host. Every agent on this host works as a separate agent account (a GitHub "machine account", a normal free account used only by programs). A session kind is not used as the check.

**Settings and steps.**
1. Owner creates one free GitHub account for the agents (name is the owner's choice; "AGENT" below), turns on two-factor sign-in, and adds it to IronbellyOrg/IronClaude as an outside collaborator with the Write role (not Maintain, not Admin).
2. Owner signs AGENT in to the `gh` tool on this host, signs `ironbelly` out of it, and revokes every old `ironbelly` token in GitHub settings. Admin work (ruleset, approval label) is done by the owner in the browser, never by logging `ironbelly` back in here.
3. OA-5 ruleset as D16 recommends (master and integration, pull request required, review from code owner `@ironbelly`, dismiss stale approvals, bypass for the Admin role only). AGENT has Write, so it has no bypass.
4. `answer-check` takes the owner identity as a parameter: the numeric id of `ironbelly` (read with `gh api users/ironbelly --jq .id`). A typed go counts only if (a) it was recorded from live chat with the four SEC-08 checks, and (b) for a merge, GitHub shows an approving review by that id on that exact head sha, newer than the gate output. For the `Approved` label the watcher already needs the approver id in its approvers file; AGENT's id goes in `approval_excluded_ids`.
5. Fail closed: if the host login's id equals the owner id (the shared login is back), `answer-check` and the merge verb refuse and say why. Every merge is then typed by hand, as today.
6. Until the cutover entry in step "Preconditions" exists, keep today's default (OA-6 unnamed, SPEC.md:578).

**Sentences the owner says in chat.** Decision: "Create a separate agent GitHub account for the agents on this host. In the plan, 'the owner' for typed answers means the GitHub account ironbelly only. Record that." After the account exists: "The agent account is called <login>." After tests pass: "I have removed ironbelly from this host and revoked its old tokens. Cut over."

**What an agent then does.** Records each sentence with the owner's quoted words in the interim ledger (SEC-14); reads both account ids; writes `owner_account_id`, `approval_excluded_ids` and the agent id into per-repo config; builds the id parameter and the refusal in S14 (SEC-09); runs the throwaway tests after the owner's go. It never creates the account, never holds the `ironbelly` credential, never sets the ruleset.

## 2 Why this is best
- Nothing today tells a person from an agent: D06/VERDICT.md:22 (item 9), invariant-probe.md:11 (INV-003, HIGH), SPEC.md:647 (RK-3). A session kind is a label an agent can claim. Naming it would turn today's fail-safe default ("cannot pass", SPEC.md:578, DECISIONS.md:1263) into a pass on forgeable input. D04/VERDICT.md:41 already says the test must not be "a login".
- The shared login is the whole hole. Live reads: repo PUBLIC, viewer permission ADMIN, `rulesets []`, master `protected:false`, no CODEOWNERS on origin/master. With admin on the same login, a script can merge or bypass (SPEC.md:302 SEC-13, :577; D16/VERDICT.md:61). The ruleset alone leaves a choice between that hole and a deadlock (no non-author approver for the owner's own PRs, D16/VERDICT.md:61). A second login removes the choice.
- The credential can be separated cheaply. The `gh` login sits in `/home/coder/.config/gh/hosts.yml`, mode 600, owner `coder`, the unix user every agent runs as (stat only; contents not read). `GH_TOKEN`/`GITHUB_TOKEN` unset; no `.git-credentials`, no `.netrc`, no ssh keys (only `known_hosts`), no global credential helper. So removal looks like one logout. Keyring storage and Orca's own GitHub auth: UNVERIFIED.
- Watcher code already has the mechanism (origin/master): `approvers_file`, `owner_account_id`, `approval_excluded_ids` (cycle.py:109-112, :268); `cli.py:214-222` warns `approver_is_launch_account`; `predicates.py:253-260` rejects an approval unless the actor id is in approvers and not excluded. No new watcher code for the label.
- Reviewers act on other authors' PRs: PR 700 and PR 690 (author clayphi) got comments from `augmentcode[bot]` and `chatgpt-codex-connector[bot]` (gh api). For a brand-new account: UNVERIFIED.
- GitHub's terms allow one free machine account beside a personal one (search result quoting Terms of Service B.3; page not opened, wording UNVERIFIED).
- The merge log cannot separate person from agent: of the last 30 merged PRs, 19 show `ironbelly` and 11 `clayphi` (gh pr list).

## 3 Alternatives I rejected
- **Name the owner's interactive session as the check.** Forgeable: the same terminal accepts `orca terminal send` (D06/VERDICT.md:22), and whether the harness marks sent text differently from typed text is UNVERIFIED (D06 Unverified list). Kept only as the chat rule it already is (SEC-08: never relayed).
- **Leave it unnamed.** Safe for `answer-check`, but it protects nothing on GitHub: agents on the shared admin login can still merge. It is my fallback if the owner will not run a second account, not my answer.
- **Ruleset only (OA-5), shared login.** Either keep the admin bypass (agents can use it) or drop it (the owner's own PRs deadlock).
- **A GitHub App instead of a machine user.** Stronger tokens, but `@me` and `gh api user` (used by `/sc:issue --claim`, claim.md:26, :47) and "assignee set equals own login" (predicates.py:172-182) need a user account; apps cannot be assignees (from memory, UNVERIFIED). Revisit later.
- **A separate unix user or container for agents, one GitHub login.** Hides the file but agents still need GitHub write as `ironbelly`. Good extra hardening, not a substitute.
- **Reuse the existing `IB-AIReviewer` account** (org member, read role, created 2025-10-10). Its purpose and who holds it are unknown: UNVERIFIED; ask the owner before reusing.

## 4 Implications, benefits, risks, costs
**Benefits.** "A worker cannot merge" becomes true (SPEC.md:577, needs OA-5 too); INV-025 and INV-003 move from open to checked for merges and the label; a leaked agent token is worth Write, not Admin; the log shows who acted (owner or agent).
**/sc:pr-submit.** `gh pr create --repo IronbellyOrg/IronClaude` unchanged; PR author becomes AGENT; it never merges (SEC-22), so the ruleset does not touch it. Its fix pushes dismiss stale approvals (D16/VERDICT.md:68), so the owner approves after the last round. The silent-reviewer skip stays; test that both reviewer bots answer AGENT's PR first.
**Workers.** Same unix user, so same AGENT login: they can still push feature branches, open PRs and comment (SEC-13 residual) but cannot merge to protected branches, bypass, or approve as the owner.
**Coordinator and watcher.** `gh api user` returns AGENT; claims assign AGENT; the watcher launches only when the assignee set is exactly its own login (predicates.py:172-182), so issues now assigned to `ironbelly` read as `assigned_other` until reassigned (migration list needed). Clay and Jonathan are bound by the ruleset too (Maintain, no bypass); Clay merged 11 of the last 30, so the roles text in D16 must be accepted first.
**Risks (with fix).**
- R1 An `ironbelly` credential survives somewhere on the host, so the owner thinks it is separate. Fix: revoke old tokens in GitHub; a throwaway test that `gh pr merge --admin` and a push to master are refused for the host login; the step-5 id check.
- R2 Owner under time pressure logs `ironbelly` back in for an emergency (like revert PR 662). Fix: written break-glass rule (use browser or own laptop); step 5 makes the regression announce itself.
- R3 Reviewer bots go silent on AGENT, the skip rule reads that as clean (reviewers.py:390-391, :414-419). Fix: test before cutover; SEC-04 hold.
- R4 AGENT suspended or token expires: agents stop. This fails safe; keep the owner's browser path.
- R5 A merge needs one extra owner click. Fix: none wanted; that click is the machine-checkable go. The chat go stays first (owner rule).
- R6 Chat-only answers (grants, `--apply`) still leave no GitHub trace; they stay a recorded procedure with the residual risk stated (D06 item 9).
**Costs (all estimates).** Owner one-time about 1 h (account, two-factor, invite about 30 min; login swap and token revoke about 30 min; basis: ordinary account setup). Agent one-time about 3 to 4 h (id parameter and refusal 1 to 2 h inside S14; three throwaway PR tests about 1 h using D16's test protocol; ledger, config and assignment migration about 1 h). Ongoing: about 1 min per merge, at most 19 per 30 merged PRs (the window length is UNVERIFIED), and about 15 min per token renewal if tokens expire quarterly (assumed). Code outside S14: none for the watcher (keys exist).

## 5 Preconditions and order
1. Owner decides OA-5 and OA-6 together in chat (they are a pair); D16 roles accepted by Clay and CODEOWNERS merged before the ruleset (D16/VERDICT.md:84-85).
2. Owner creates AGENT, invites it with Write (owner-only: account creation and admin).
3. Agent records the sentences, reads the two ids, drafts the config and the migration list of issues assigned to `ironbelly`.
4. Owner swaps the host login, revokes old tokens, sets the ruleset (admin only).
5. Throwaway tests (they write to GitHub, so the owner says go first): AGENT-authored PR cannot merge unapproved; `--admin` and master push refused; both reviewer bots reply; claim assigns AGENT; watcher sees an AGENT-assigned issue.
6. Owner says "Cut over"; agent records it. Only then does S14 `answer-check` pass anything (SPEC.md:498). Before that, hand-typed merges.
7. Rollback: the owner says OA-6 is unnamed again; AGENT can stay; merges are typed by hand. Never roll back by logging `ironbelly` into the host.
