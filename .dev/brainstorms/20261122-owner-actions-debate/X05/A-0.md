# X05 (OA-6) Who counts as "the owner" for typed answers: agent A, round 0 (Pragmatic lens)

Status: stub, sections appended below. Facts checked on 2026-11-22 with gh reads; unchecked items are marked UNVERIFIED.

## 1 Proposal
Two steps. Step 1 is free and done now. Step 2 (a second GitHub login) is worth doing, but only at a named trigger, not as a condition of S14.

STEP 1, name the session kind (no new account). The words recorded for OA-6 and used as the `answer-check` parameter `owner_session_kinds: [person_opened]`:
"The owner's typed answer is text the owner types in the live chat of a Claude Code session that a person opened by hand in an Orca terminal (the main-checkout session, or the coordinator session the person opened). These never count: text from a `worker-start` worker, from a session a script or the watcher started, anything sent with `orca terminal send`, a mailbox message, an issue or PR comment or review text, and any text carrying a `[sc-launch:v1:...]` marker. An answer counts only in the session that received it, quoted word for word with its date, and recorded by that session's agent."
Limit, kept in the spec wording (SEC-18, "narrows"): this names a convention and does not prove who typed; until Step 2 a script on this host can still type as the owner.
The sentence the owner says in chat: "OA-6: my answer is only what I type in a session I opened myself. Workers, script-started sessions, relays and GitHub text never count. Record it. A separate agent login: yes, later, after the master ruleset and before any autostart or worker go-live."
What an agent then does: (a) writes the OA-6 row in the interim ledger (SEC-14: quoted words, date, scope, recorder) and runs `git add .dev/tasks`, no commit unless asked; (b) carries the parameter and the limit sentence into SEC-09 and RK-3 when the owner approves spec edits; (c) until `answer-check` is built, the coordinator does the four by-hand checks (DECISIONS.md:662) and refuses a go that came by any excluded route.

STEP 2, a machine login for agents. The owner creates it (only the owner can: email, 2FA). Settings: org member of IronbellyOrg, role Write on IronClaude (never Maintain or Admin); a fine-grained token limited to that repo, expiry 90 days (my choice; UNVERIFIED against what the claim pipeline needs, see section 4); the owner stores it from the owner's own terminal with `coder secret create github --env GH_TOKEN` so no agent sees it (Coder docs: `GH_TOKEN` is a user secret, RAD-9). `ironbelly` stays admin and stays off agent hosts. The login name is the owner's pick; UNVERIFIED which names are free. `IB-AIReviewer` is already an org member with read role (purpose UNVERIFIED); the owner says whether it is meant to be this account.
Recording: one ledger entry (login name, role, setup date, token expiry date, which hosts switched) plus two per-repo config keys `owner_login: ironbelly` and `agent_login: <name>`; `answer-check` and the merge verb read them.
Test that must pass before any host is called switched: from an agent session `gh api user --jq .login` prints the agent login; `gh api repos/IronbellyOrg/IronClaude/collaborators/<name>/permission --jq .permission` prints `write`; on a throwaway PR `gh pr merge --admin` is refused once the ruleset is on.
Merge go after Step 2: the owner says the go in chat (recorded, as SEC-01) and clicks Approve on that PR in GitHub. The ruleset (PR required, 1 approval, code-owner review, dismiss stale approvals, no bypass for the agent login) then makes the approval a platform fact that is tied to the head sha and that no agent token can produce. The merge verb reads "approved by ironbelly on this head" from GitHub as its check. The chat go stays the owner's rule; the click is the lock key, not a second go.

## 2 Why this is best
- The default is a dead end for S14: `answer-check` "cannot pass; S14 ships but every merge stays typed by hand" (SPEC.md:578; OA-TRIAGE.md:19). Step 1 removes that at no cost.
- Nothing in the plan can prove who typed: INV-003 "Nothing does; naming the full sha adds no protection against a script that knows the sha" (invariant-probe.md:11), RK-3 (SPEC.md:647), D06 item 9 (VERDICT.md:22). So a rule that only names a session kind is honest but weak; I say so in the wording.
- Only a second login gives real separation: "a separate agent login (OA-6) plus the ruleset is the only way to make 'a worker cannot merge' true" (SPEC.md:577, RK-2 at :646). D16 line 61: with the planned admin bypass "sessions on the shared `ironbelly` login can use the bypass".
- Today nothing blocks a merge. gh reads: `gh api repos/IronbellyOrg/IronClaude/rulesets` prints `[]`; `branches/master/protection` returns 404 "Branch not protected"; `gh api user --jq .login` in this session prints `ironbelly`; `collaborators` shows `ironbelly` admin true, `clayphi` and `IB-JonathanB` maintain; the org is on the Free plan and the repo is public (rulesets on public repos: UNVERIFIED for Free; D16 plans one).
- One login also blocks required review: D16 line 61 says "the sole non-author approver for the owner's own gated PRs does not exist", which is why D16 sets 0 approvals. With PRs authored by the agent login, `ironbelly` becomes a real non-author approver, so 1 required approval can work.
- Coder already holds the token as one per-user secret (`coder secret create github --env GH_TOKEN`, startup-sections.md lines 48-49, 74 in IronbellyOrg/Coder), so the switch is a secret change, not new plumbing.
- `/sc:pr-submit` never merges: `git grep -n "pr merge" origin/master -- src/superclaude/skills/sc-pr-submit-protocol src/superclaude/pr_submit` returned nothing. So the login change touches it only for push, PR create, comments and thread resolves.

## 3 Alternatives rejected
- Leave OA-6 unnamed (the default). Safe, costs no setup, but the coordinator's merge path (S14) is dead and every merge stays hand-typed. Kept only as the fallback if the owner declines.
- Make the second login a precondition of S14. Rejected: no merge verb or `answer-check` exists yet (SPEC.md:674), autostart is off (OA-18 default), so it would add account, token and per-host work before there is anything to protect.
- Prove "typed by a person" mechanically (spot `orca terminal send` text, a harness marker). No evidence the harness marks sent text differently (D06 VERDICT.md:86, UNVERIFIED); I would not build on it.
- Name Clay or IB-JonathanB as the required approver and keep the shared login. Puts the owner's merges behind another person's hours, and agents on the admin login still bypass.
- A challenge code shown to the owner. A script can read the same terminal (D06 merged-output.md:184), so it adds friction and no protection.
- Reuse `IB-AIReviewer` as the machine login without asking. Its role and purpose are unknown to me; the owner decides.

## 4 Implications, benefits, risks, costs
Benefits: Step 1 makes the check definable and makes the coordinator refuse relayed, worker and GitHub-text "gos" at once. Step 2 makes "a worker cannot merge into master" a GitHub fact and gives the 1-approval rule a real approver.
Effect on `/sc:pr-submit`: no change to the skill or to `--repo IronbellyOrg/IronClaude`; PR author, review replies and thread resolves become the agent login; it already uses feature branches and PRs only. A one-PR test must show Augment and Codex still review (UNVERIFIED that they do not care who authored it).
Effect on workers: they hold only the agent token, so they cannot merge past the ruleset or change repo settings; they can still push feature branches, comment and open PRs (SEC-13 stays true: the guard narrows, it does not close).
Effect on the coordinator: it merges only after the owner's chat go and a GitHub approval by `ironbelly` on the head sha; it never holds the owner credential. Without Step 2 it asks the owner to merge by hand.
Risks: (1) the agent token is readable by anything on the host, so Step 2 limits what it can do, not who can use it; (2) the claim pipeline writes issue types, the Complexity field and the `Approved` project field: a Write-role token may lack org project permission (UNVERIFIED; test before switching) and the watcher login in FR-01 (SPEC.md:191, "assigned only to the watcher login") may need to be the agent login; (3) token expiry stops every agent at once (Coder writes `gh-auth-missing`); put the expiry date in the ledger and a reminder; (4) the owner must merge or approve from a place that holds the `ironbelly` credential (browser or own laptop), not an agent host; (5) GitHub's machine-account terms: UNVERIFIED, check before creating.
Costs (estimates, basis: D16's own figures of about 20 minutes of owner chat and 15 to 30 minutes for the ruleset, VERDICT.md:19, :23, and my guess for the rest): Step 1 about 0.25 h owner chat plus about 1 h agent for the ledger row and two spec edits. Step 2 about 0.5 to 1 h owner (account, 2FA, invite, token, secret), about 0.25 h per host to switch and test (host count UNVERIFIED), about 1 to 2 h agent for config keys, the throwaway-PR test and doc text; the ruleset is OA-5 work already counted. Total about 3 to 5 h for Step 2.

## 5 Preconditions and order
1. Owner says the Step 1 sentence in chat; an agent records it. Nothing else is needed; S14 can then build `answer-check` with the parameter.
2. OA-5: the ruleset needs the CODEOWNERS PR first (D16 VERDICT.md:85); no CODEOWNERS file exists in this local checkout (not checked on origin/master). Set it with no bypass for the agent login; the admin bypass stays for `ironbelly`.
3. Owner checks GitHub's machine-account terms, picks the login name (or reuses `IB-AIReviewer`), creates it, invites it with Write.
4. Owner stores the token on ONE host; run the three tests of section 1 plus a pr-submit dry PR and a claim dry run; then the other hosts one by one.
5. Trigger rule: no `coordinator_autostart` (OA-18), no real-repo watcher switch-on (OA-19), no `WORKER_BINDING_PROVEN` flip (OA-20) and no merge automation before step 4 is recorded. If the owner declines Step 2, those four stay off and merges stay by hand.
