## 2 Still rejected (with evidence)
1. **Fine-grained token for an outside collaborator.** GitHub's page lists as unsupported a fine-grained token "to contribute to repositories where the user is an outside or repository collaborator" (re-fetched). It also says an organisation can block classic tokens (HTTP 403). So the agent credential is a classic token or a `gh` OAuth login, not a fine-grained one. The bound on damage is the invitation (Write on IronClaude only), not the token. The step 6 test must include "the credential still works under the org's token settings" (which setting is on: UNVERIFIED).
2. **"The ruleset alone stops an agent merge."** D16 sets 0 required approvals, code-owner review and admin bypass (D16 VERDICT.md lines 23, 61). D16's own caveats say the gate may not block a non-owner author at 0 approvals (lines 106, 113). So an agent PR on an ungated path can be merged by a Write-role login with no approval, and a worker can call `gh pr merge` itself, which `answer-check` never sees. A-2 says the owner "may raise it to 1 later". For a fail-safe lens "later" is wrong: the gap is open from cutover day. Section 3 puts the decision at cutover.
3. **D16 line 97 changes under the split.** D16 assumes an approval is posted "for the owner" by a session on the owner's login after the typed go. With two logins an agent cannot post that approval as `ironbelly`; the owner clicks Approve in the browser. That is the point of the design (no script can fake it), but it adds one click per gated merge, which neither side had counted. The D16 text must be amended in the same edit that records OA-6.

## 3 Revised proposal (the unified one I would sign)
**Definition.** "The owner" is the person behind GitHub account `ironbelly`, by numeric id.
- Tier 1 (chat-only answers: grant rows, `--apply`, cleanup approval, design go): text the owner types in the live chat of a session the owner opened by hand. Never a `worker-start` worker, a script or watcher session, `orca terminal send`, a mailbox message, or issue or PR text. The receiving session records the words, date, scope and recorder (SEC-08) and runs `git add .dev/tasks`, no commit. Spec text and coordinator procedure only; it narrows and cannot prove who typed (SEC-09, SEC-18, D06 item 9). Needs no account; do now.
- Tier 2 (a merge, the `Approved` label): the Tier 1 go plus an approving review by the `ironbelly` id on the exact head sha, newer than the gate output, clicked by the owner in the browser. `answer-check` and the merge verb refuse, with a reason and a failing test, when the live login id (`gh api user --jq .id`, not config) equals the owner id, or when no such review exists. Never a pass on session kind alone.

**Second login: worth it.** Order:
1. Owner in chat: "OA-6: the owner means ironbelly only; chat answers count only from a session I opened; create a separate agent account." Agent records it and amends D16 line 97 (section 2 point 3).
2. Owner (account creation, 2FA and admin are owner-only) reads GitHub's machine-account terms, creates the agent account with 2FA, invites it as outside collaborator with Write on IronClaude only. Whether `IB-AIReviewer` (existing read collaborator, purpose unknown) is reused, and whether Coder is added: the owner says.
3. Owner sets the OA-5 ruleset (D16 settings) after the CODEOWNERS PR merges and Clay accepts the roles, plus the approvals choice in section 4.
4. Agent reads both ids, writes `owner_login`, `agent_login` and the watcher keys, and lists open issues assigned to `ironbelly` (they read as `assigned_other` until reassigned). It also writes the list of owner-only actions that move to the owner's browser (repo settings, ruleset, labels, org issue fields, Approve clicks); the full list is UNVERIFIED.
5. Owner switches ONE host: signs `ironbelly` out of `gh`, replaces the Coder `github` secret with the agent credential, revokes every old `ironbelly` token (both routes: the `hosts.yml` login and an inherited `GH_TOKEN`).
6. Owner says go; agent runs throwaway-PR tests: login prints the agent in a fresh shell and in an Orca session; permission is `write`; an unapproved agent PR cannot merge on a gated AND an ungated path (per the section 4 choice); `gh pr merge --admin` and a push to master are refused; both review bots answer an agent PR (silent reads as clean, SEC-04 hold); claim writes work; the watcher sees an agent-assigned issue; a pr-submit dry PR.
7. Owner says "Cut over"; agent records it with the ruleset id and credential expiry. Other hosts follow one by one with tests 1 and 2. Rollback: owner says OA-6 is unnamed again; merges by hand. Break-glass: the owner's browser or own laptop, never `ironbelly` on the host.

**Effects.** `/sc:pr-submit`: same command and `--repo IronbellyOrg/IronClaude`; it never merges; PR author, replies and resolves become the agent; its fix pushes dismiss stale approvals, so the owner approves after the last round. Workers: same agent login as the coordinator; push, open PRs, comment; cannot approve as the owner or use admin bypass. Coordinator: merges only after the chat go plus the id-matched approval; before cutover it asks the owner to merge by hand.

**Cost (estimates).** Owner about 1 to 1.5 h once, about 1 to 2 min per gated merge (chat go plus browser Approve), about 15 min per credential renewal, about 0.25 h per extra host. Agent about 3 to 4 h (S14 id refusal 1 to 2 h, tests 1 h, ledger, config, migration 1 h). Ruleset time belongs to OA-5.

**Risks.** A surviving `ironbelly` credential (revoke, live-id refusal, `--admin` test). Owner logs back in under pressure (break-glass rule; the refusal makes it visible). Silent bots on a new account. Credential expiry stops all agents (fails safe). Chat-only answers leave no GitHub trace.
