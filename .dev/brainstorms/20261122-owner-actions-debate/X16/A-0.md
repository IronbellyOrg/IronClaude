## 1. Proposal

One small check, then update only the hosts that fail it. No blanket install, no process around hosts that pass.

**Who is affected.** Only a host where someone ran `superclaude install` or `superclaude update` from master while PR 682 was on master (00:02 to 15:07 UTC on 2026-11-20), outside the Coder template.
- Coder workspaces, the owner's and other users': not in the window. The Coder template installs a build pinned to one IronClaude commit. The pin was 64dfc0e from 2026-11-19 03:58 UTC (that commit is older than PR 682) and became 2ea5245 on 2026-11-21 00:55 UTC. No pin ever contained PR 682. Their only need is the normal template roll to 2ea5245, which the template script forces on boot when the pin changed.
- Not Coder (a laptop, another server, a CI box): at least Clay and IB-JonathanB, who maintain and may have installed from master. Ask them; nobody else is known.

**The check (read-only, 10 seconds, run on each non-Coder host).**
`sha256sum ~/.claude/hooks/launch-level-guard.sh ~/.claude/WORKER-CONTRACT.md | cut -c1-12`
Read the first column against this table (the launch guard is the script that limits what a claimed worker session may run):
- guard `a561b1a7e7e7`: affected (the post-682 guard, without the release-worker rule).
- guard `71e479dd1076`: older but not harmful (pre-682 or post-700); lacks version stamp 2, so it needs the update before the watcher goes live.
- guard `e6fc1470ae82` and contract `f0b85e7fec01`: done.
- anything else: someone edited it; diff first (below), do not overwrite blindly.

**The procedure on a host that needs it.**
1. Save the files first: copy `~/.claude/hooks/launch-level-guard.sh`, `~/.claude/WORKER-CONTRACT.md`, `~/.claude/CLAUDE.md` and `~/.claude/settings.json` to a dated folder. (`update` overwrites them with no backup of the first three.)
2. Diff each against the target. The repository is public, so no clone is needed: `curl -fsSL https://raw.githubusercontent.com/IronbellyOrg/IronClaude/2ea524514154bde03258a7d7d8a0265c371609af/src/superclaude/hooks/scripts/launch-level-guard.sh | diff - ~/.claude/hooks/launch-level-guard.sh`; the contract is `.../src/superclaude/core/WORKER-CONTRACT.md`, CLAUDE.md is `.../src/superclaude/core/CLAUDE.md`. A difference in the guard or contract is expected and is the point. A difference in CLAUDE.md is the host's own text: merge it by hand after the update.
3. Move the tool to the pin: `pipx install --force "git+https://github.com/IronbellyOrg/IronClaude.git@2ea524514154bde03258a7d7d8a0265c371609af"` (fork URL, never the upstream project).
4. Run `superclaude update` (it forces every file; `superclaude install --force` is the same for these files). Do not use plain `superclaude install`: it keeps existing files.
5. Verify: rerun the check (must print `e6fc1470ae82` and `f0b85e7fec01`); `superclaude issue-watch --help` must list commands (that group is registered at `src/superclaude/cli/main.py:577-579` on master); then restart any Claude session on that host.

Drafts one comment for issue 717 (the watcher backlog issue, open) asking each maintainer to run the check and reply with the first column only, and posts it with `gh issue comment 717 --repo IronbellyOrg/IronClaude` once the owner's chat go covers the post. ## 2. Why this is best (evidence)
- The window: PR 682 merged 2026-11-20T00:02:36Z, PR 700 (the rollback) 15:07:32Z (`gh pr view`). PR 707 (guard version 2) merged 22:09:24Z, so a host that did nothing wrong in the window is still on guard version 1 and needs `--force` once more (PR 707 body: "hosts run superclaude install --force").
- Plain install never fixes this: `install_core.py:71-73` and `install_hooks.py:282-284` skip any file that exists; update forces at `main.py:383` and `main.py:412` (all in `archive/pr-682/INSTALL-TEST.md` sections 2 and 6, which I re-checked against master's `main.py`).
- Coder pins: `gh api` on IronbellyOrg/Coder commits of `Dockerfile.coder`: bump to 64dfc0e at 2026-11-19T03:58Z, bump to 2ea5245 at 2026-11-21T00:55Z, nothing between. `git merge-base --is-ancestor 64dfc0e 01e7a9e23` is true (64dfc0e is older than PR 682). The template script `catalogue/ironclaude/install.sh` adds `--force` whenever the recorded SHA differs from the pin (lines near 92-95 of the file as read; the comment there says a plain install would keep old files).
- This workspace: installed guard sha `e6fc1470ae82` and contract `f0b85e7fec01` equal origin/master 2ea5245 exactly, file time 2026-11-21 01:00:42Z, five minutes after the pin bump. So the template path works and already updated it.
- Fingerprints (`git show <commit>:... | sha256sum`): guard at 64dfc0e, 471f10511 (PR 700) and 0a4664457 (PR 701) is `71e479dd1076`; at 01e7a9e23 (PR 682) it is `a561b1a7e7e7` (matches INSTALL-TEST.md); at 2ea5245 it is `e6fc1470ae82`. The post-682 tree has 0 files under `cli/issue_pipeline/`; the others have 10 or 11.
- A stale guard fails closed for governed launches: the claim check refuses a host whose guard lacks the stamp line `# launch-level-guard-version: 2` (`orca_worktree.py:876` and `:1023-1026` on master), and the guard governs only sessions the claim script launched (guard header, `launch-level-guard.sh:5-7`). With OA-20 not flipped and no worker on a real issue (DECISIONS.md line 1268), nothing is live, so the cost of a stale host today is a refused launch, not a breach.

## 3. Alternatives rejected
- Run `superclaude install --force` everywhere now: blind overwrite with no backup of guard, contract or CLAUDE.md, and it runs the retire step (`main.py:250-262`, `install_retired_files.py`), which FR-66 and OA-21 say not to do until the eight removal PRs are confirmed. Rejected.
- Bump the guard stamp to force a refresh: the installer never reads the stamp (INSTALL-TEST.md section 1). Rejected.
- A new inventory tool or registry of hosts: the set that can be affected is two or three people; a script would cost more than asking. Rejected.
- Wait for a stale host to be refused at claim time: works as a safety net but the first user finds out mid-claim. Kept only as the backstop, not as the plan.
- Treat every Coder workspace as needing a manual update: the template already does it with `--force` on the next boot after the pin changes. Rejected.

## 4. Implications, benefits, risks, costs
Benefits: the owner is safe without a per-host ceremony; Coder users get no new work; the check is read-only and exact (a file hash, not a guess); it also finds hosts that never reached guard 2.
Risks: (a) a non-Coder host we do not know about is missed; the backstop is the refused claim. (b) `update` also runs the retire step on a non-Coder host and can remove unmodified retired skills (task, task-builder, prd, tdd and similar, from PRs 650 and 656); the Coder template boot already does this on every pin change, so Coder hosts are not newly exposed. (c) CLAUDE.md on a host is overwritten; step 1 and the diff catch local text. (d) A Coder workspace not restarted since 2026-11-21 00:59Z (merge time of Coder PR 520) is still on the old pin; whether other users' workspaces were updated is UNVERIFIED (I did not query Coder).
Costs (estimates, my basis is the steps above, not a measurement): owner chat go 2 minutes; agent drafts and posts the comment 0.2 hour; each non-Coder host about 0.3 hour (the check 1 minute, saving and diffing 5 minutes, tool upgrade and update with its network step about 10 minutes, restart and verify 5 minutes); assume 2 hosts, so about 0.6 hour of other people's time plus 0.5 hour of agent time. Coder workspaces: 0 extra hours beyond the template roll already done.
