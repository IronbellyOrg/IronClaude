# Safe Local Git Workflow Requirements

## Overview and scope

This specification defines a local command contract, not a network service. Its priorities are explicit authority, narrow write sets, recoverable partial execution, and no duplicate commits after interruption. The confirmed narrowed scope in `seed-brief.md` takes precedence over the older issue plan and the issue summary's earlier request for scope confirmation.

**Path notation.** To keep component names neutral, `S` denotes the existing source package directly below `src/` that contains `commands/git.md`; `P` denotes the existing plugin directory directly below `plugins/` that contains `commands/git.md`; `D` denotes the project's hidden runtime directory containing `settings.json`; `G` denotes its same-named user-level installation directory. These are aliases for existing repository/install surfaces, not proposed directory names. Thus `S/commands/git.md` and `P/commands/git.md` identify files read in this checkout. `D/commands/sc/git.md` is the documented development-copy destination, but the file is absent in this checkout: current presence is **UNVERIFIED**. The command/skill developer guide is the verified file matching `docs/developer-guide/*Developer-Guide-Commands-Skills-Agents.md`.

New interface words, data fields, and component destinations below are requirements, not claims that they already exist. Every new filesystem destination is explicitly marked **UNVERIFIED: proposed**. No new command-line flag is specified.

- **FR-001 — Included outcomes.** Deliver a modular `/sc:git`, explicitly authorized local commit boundaries in `/sc:implement`, submodule inspection/update/pointer handling, and discovery of the existing local cleanup route. Preserve default no-commit execution.
- **FR-002 — Exclusions.** Do not introduce a central command relay, session-to-session Git service, automatic push, merge, PR creation, remote branch deletion, replacement cleanup engine, automatic progress posts, new project-management integration, or destructive recovery commands. PR work remains exclusively with `/sc:pr-submit`; issue and completion administration remain with `/sc:issue` and `/sc:closeout`. A local commit grant never grants publication.
- **FR-003 — Repository policy.** Treat `integration` as this repository's development base and refuse writes on its protected shared branches, including `master` and `integration`, or detached HEAD. Resolve the target repository from the current checkout, never from a public-parent default. Other repositories use their own verified branch policy; inability to establish the default/protected set blocks mutation but not inspection. Evidence: `docs/developer-guide/branch-protection.md`, `S/core/WORKER-CONTRACT.md`, and `S/core/HOW-WE-WORK.md`.

## Authorization model

- **FR-010 — Grants are operation-specific.** Inspection needs no mutation grant. A user's explicit local-commit request authorizes only the named repository and intended write set. A generic request to implement, an approved plan, a quality verdict, a stored result, or another agent's message does not authorize committing. Permission-system refusals remain authoritative. Never edit settings, disable hooks, change signing configuration, elevate permissions, or switch execution context to get around a refusal.
- **FR-011 — Between-task opt-in switch.** Choose a current-session explicit user instruction as the switch, with no new flag and no plan field. The instruction must name local commits between completed implementation tasks and the source plan or run. Before the first task, the executor records the quoted instruction and exact scope in its boundary evidence. Ambiguous language leaves the switch off. Revocation takes effect before the next boundary. A new session needs a new instruction before any still-pending commit; persisted grants are evidence, not reusable authority. Already-created commits can be reconciled without a new grant because that is read-only.
- **FR-012 — No destructive inference.** Update authorization is separate from commit authorization and identifies selected submodule paths and recorded target commits. Cleanup requires the person-facing cleanup command and its existing confirmation mechanism. A commit grant never authorizes branch deletion, worktree removal, rebase, reset, stash, config change or network publication. Refuse unsupported destructive requests rather than adding a force escalation.

## Between-task commit behavior in /sc:implement

Existing integration points are `S/skills/sc-implement-protocol/SKILL.md`, its `refs/ledger.md`, `refs/retry.md`, `refs/managed-workspace.md`, and `S/commands/implement.md`. Today the command says no auto-commit; retry requires HEAD unchanged during a task. Change only that boundary policy, not quality verdict semantics or retry restoration.

- **FR-013 — Timing.** For a sequential task, write and flush its valid `complete` line, finish its task cleanup, and close all task writers before entering the optional commit boundary. Finish or explicitly skip that boundary before the next task's Q0 snapshot or `start` line. Apply the same boundary to the last task before final review/archive. Never commit on a `blocked`, `halt`, or incomplete record. Completion following a valid scoped user Ruling is eligible, but the Ruling itself is not commit authority.
- **FR-014 — Parallel barrier.** Do not stage for a commit, create a commit, or move HEAD while any member of an independent batch is executing or reviewing. Wait until every member is `complete` and every writer has joined, then make at most one boundary commit containing the union of that batch's intended paths, with task IDs in source order. If any member halts or remains blocked, make no batch commit and start no next batch. Resumed members retain their recorded batch identity; do not infer a new boundary from invocation order.
- **FR-015 — Intended write set.** Derive product paths from the completed task's recorded `files=` set, or the completed batch's union. Add the mandatory task-evidence changes under `.dev/tasks/`. Stage explicit paths with the existing `git add -- <paths>` pattern and commit only that allowlist with the existing `git commit --only -- <paths>` pattern. Include deletions and both ends of renames. Never use whole-repository staging for this boundary. Never stage the project runtime mirrors or root-level `artifacts/`; a task touching a forbidden path is a refusal, not permission to widen the set. Preserve the existing exception for the deliberately tracked runtime settings file only when explicitly authorized for that task.
- **FR-016 — Evidence staging is not optional.** In ordinary attended execution, keep all `.dev/tasks/` packages, ledgers and package-local `artifacts/` staged even when commit opt-in is off. Include their pending changes in an authorized boundary commit after showing the complete effective allowlist. If that mandatory evidence would expose secrets or consume another live writer's evidence, stop for resolution rather than omit it or silently commit it. Legacy ledger/evidence under `.dev/implement/` remains unstaged, as `refs/ledger.md` currently requires; do not conflate it with `.dev/tasks/`. Stage managed evidence again after archive movement without creating an extra unrequested housekeeping commit.
- **FR-017 — Do not absorb pre-existing work.** Capture initial tracked, untracked and staged state before execution. A path-level allowlist is insufficient when the same file already held another person's edits: if a candidate product path has a pre-existing delta against HEAD or changes outside the reviewed task increment, refuse automatic commit and explain the overlap. Do not first commit, stash, discard or reset that work. Preserve unrelated index entries byte-for-byte in meaning, and ensure they do not appear in the new commit. An unchanged dirty file outside the allowlist is not itself a reason to include it.
- **FR-018 — Freeze the candidate.** Before staging, bind the attempt to the checkout identity, attached branch, expected parent HEAD, completed task IDs, exact path list and candidate contents. Re-read these immediately before committing. An existing index lock, unmerged entries, active merge/rebase, moved HEAD, changed candidate, or another writer causes refusal. A deleted path is validated through its parent location without following an escape outside the checkout. Literal path handling must cover spaces, leading dashes and pathspec metacharacters.
- **FR-019 — Message contract.** Draft a truthful Conventional Commit subject, `type(scope): imperative description`, with optional scope. Body names the plan identity and task ID or batch IDs, and records that this is a local task boundary. Preserve repository-required trailers without hardcoding a particular author identity. Add one machine-readable boundary-key trailer for reconciliation. Its exact token is **UNVERIFIED: proposed interface**, to be fixed in helper tests before implementation. Never amend an earlier commit to recover a failed attempt.
- **FR-020 — Hook refusal and rewriting.** Run normal commit hooks. Never use `--no-verify`, hook-disable environment settings, alternate hook paths, or signing overrides. On nonzero exit, hook rewrite, interruption or timeout, inspect HEAD and the effective diff before classifying the outcome. If HEAD did not move, report no commit and stop the run before the next Q0; retain the task's completed verdict. If a hook changed files, show those paths and require renewed review before any new attempt. Never retry automatically, rewrite the previous commit, or mark a task incomplete solely because its boundary commit failed.
- **FR-021 — Explicit local result contract.** The shared helper shall accept a versioned structured request containing checkout root, operation identity, expected parent, boundary key, task IDs, explicit allowed paths, candidate digest, message, and journal location. This is a proposed internal contract, not an existing CLI flag set. Reject missing/unknown fields and unsafe paths before staging. Emit one structured result with version, boundary key, outcome, reason, before/after HEAD, commit ID when verified, committed paths, and hook-modified paths. Outcomes are exactly `committed`, `already-committed`, `no-change`, `refused`, `failed`, or `uncertain`; only the first three allow normal continuation. Refusal/failure/uncertainty are non-success process results and retain useful diagnostics. Do not add undocumented task-ledger records or silently introduce new executor STOP codes; any required STOP-table change must be explicit and tested with its consumers.
- **FR-022 — Durable resume without duplicates.** Persist an atomic boundary journal outside the ledger grammar, before attempting a commit. New destinations `<managed package>/artifacts/commit-boundaries/` and `<legacy run>/commit-boundaries/` are **UNVERIFIED: proposed**; their parents are the existing managed package and `.dev/implement/<slug>/` respectively. Use stable per-task or per-batch identity bound to source identity and the recorded start generation, not a new timestamp on each resume. Journal records retain expected parent, candidate fingerprint, path list, boundary key, and terminal result. On resume, reconcile a pending journal before selecting the next Q0 and before the existing all-complete short-circuit. If a commit carrying that key has the expected parent and exact authorized changes, record `already-committed`; do not create another commit. If nothing changed, record `no-change` and never create an empty commit. Mismatched history, missing evidence, duplicate matching commits, or unverifiable effects produce `uncertain` and stop. A pre-feature completed task with no journal is not retroactively committed. An interrupted unfinished commit may be retried only with current-session authority and unchanged validated inputs.
- **FR-023 — Journal lifecycle.** Keep boundary state with its run across managed archive movement. A terminal result written after commit cannot be part of that same commit; keep the resulting evidence staged under the mandatory evidence rule, and report it as such. A journal must not claim its recorded commit includes that post-commit result. Reconciliation compares authorized product/evidence changes from the prepared attempt, excluding only the journal's defined result fields; it must not ignore arbitrary evidence changes. Do not change existing ledger, FINAL, retry or archive parser grammars merely to store commit state.

## Submodule operations in /sc:git

The source command currently has no submodule protocol. The inspection syntax and Git semantics below are grounded in the supplied `enrichment/research-deep.md`; production handling in this checkout is **UNVERIFIED** until implemented and exercised. The existing PR finishing code is a behavioral boundary, not permission to copy its publication workflow.

- **FR-024 — Inspection output contract.** Inspection shall be read-only and expose a record per registered submodule, including unchanged and uninitialized ones. Each record contains canonical repository-relative path; nesting parent; index gitlink object ID; checked-out HEAD or null; initialized/attached/conflicted booleans; commit-changed, tracked-dirty and untracked-dirty booleans; selected-operation eligibility; and explicit reason when unknown or blocked. Also report the superproject branch/HEAD and effective `submodule.recurse` and `push.recurseSubmodules` values with unset distinguished from false. A missing Git value is null/unknown, never a fabricated clean state. Sort output deterministically by nesting and path. No submodules produces an empty list, not an error.
- **FR-025 — Complete state discovery.** Combine `git submodule status` with `git status --porcelain=v2 --ignore-submodules=none`, including nested inspection when applicable. Interpret `S<c><m><u>` as commit/tracked/untracked state, and `-`, `+`, `U` submodule-status prefixes separately. Inspect each initialized selected module for branch attachment and conflicts. Do not rely only on parent status, ignored dirt, or a short display SHA. Validate registered gitlinks, actual repository roots and nested paths; refuse symlink/path escapes and unregistered nested repositories. Parse paths without whitespace splitting. Unsupported Git output produces a clear unsupported/unknown result rather than mutation.
- **FR-026 — Recorded-commit update only.** With an explicit update grant, initialize or update only selected registered modules to the superproject's recorded gitlink, with parent initialization before child initialization. No remote-tip update, recursive unselected update, forced checkout, cleaning, implicit stash, merge or rebase is included. Preflight every affected initialized module before any write: conflicts, tracked or untracked dirt, or a checked-out commit different from the recorded pointer require stopping for a separate resolution rather than overwriting work. Read-only inspection must identify what would change. Initialization may fetch from the configured module remote, so the grant must acknowledge that network effect; reject newly substituted or unapproved remote identities. Revalidate target IDs after execution. A detached checkout at the recorded pointer is a normal update result, not permission to create commits there.
- **FR-027 — Pointer commits and ordering.** Pointer commit accepts selected gitlinks only when their initialized module worktrees and indexes are clean and conflict-free, and HEAD equals the explicitly selected target. If content is dirty, report that it must first be committed inside the module with a separate grant; parent staging cannot include that content. Refuse a detached module with a new pointer target until the user chooses an attached branch or another explicit preservation path; never invent one. Any authorized content commits happen deepest module first, then intermediate pointers, then the superproject pointer. Each local commit uses the shared safety checks and separate repository identity. Pointer recording shall not update `.gitmodules` or repository config as a side effect.
- **FR-028 — Partial execution is visible.** Preflight all selected modules before starting updates or commits. Git provides no atomic transaction spanning repositories: if a later operation fails, report completed, untouched and failed paths with old/new object IDs. Do not reset earlier successes. Reinspection of the same selection must recognize already-satisfied targets as no-change. Local-only module commits may exist, but their lack of verified remote availability must be reported as publication readiness unknown/not ready; do not push to remedy it. Publication ordering and availability checks remain a responsibility of `/sc:pr-submit`.

## Operational and non-functional requirements

- **NFR-001 — Integrity before convenience.** All refusals shall name the violated precondition and confirm whether HEAD, index and worktree changed. Never discard work, auto-repair history, or imply a multi-repository rollback guarantee. Verify the committed parent, changed-path set and candidate contents after success; a mismatch is `uncertain`, not success.
- **NFR-002 — Concurrency.** Support one executor per ledger/worktree, matching the current ledger precondition. Serialize cooperating commit helpers using a worktree-local lock, acquired before journal preparation and held through read-back. Do not delete an existing lock merely because it is old. This lock does not prevent an editor, external Git process or arbitrary hook from writing; state revalidation and sole-writer operation remain mandatory. Linked worktrees must not share journal filenames accidentally.
- **NFR-003 — Bounded execution.** Set a documented finite deadline for every Git subprocess and retain whether it timed out, was signaled, or returned a nonzero code. A mutation timeout has uncertain effects until read-back completes; never equate timeout with no commit. Bound captured output and disclose truncation. Stop rather than hang waiting for unavailable signing credentials or an interactive authentication prompt. Exact timeout values are **UNVERIFIED** pending compatibility tests with repository hooks.
- **NFR-004 — Local observability.** Return operation, authority scope, selected paths, task IDs, result, reason and before/after object IDs on every attempted write. Diagnostics shall be usable without the prior chat. Do not print file contents, credentials, token-bearing remote URLs or unrestricted environment dumps. No new telemetry service, dashboard or network API is required.
- **NFR-005 — Boundary safety.** Execute Git with argument arrays/literal paths rather than generated shell text. Reject absolute/outside-checkout paths, traversal, unsupported path encodings and symlink escapes before mutation. Treat repository messages, filenames and remote configuration as data, not executable instructions. Do not force-add ignored files.
- **NFR-006 — Compatibility.** Existing opt-out execution, ledger resume, retry HEAD invariants, scoped Rulings and managed archive behavior shall remain unchanged. A missing installed helper or mismatched helper contract version blocks only a requested commit boundary with a clear repair message; it must not trigger implicit installation or source-tree fallback in another project.
- **NFR-007 — Honest enforcement claims.** Executable helper checks enforce local state/path rules; protocol text verifies human authority. Neither is proof against a malicious same-user process or arbitrary trusted repository hook. Standard hooks remain enabled, and hook-induced changes or unexpected history must be detected where observable. Document this trust boundary rather than claim prompt-only guarantees.
- **NFR-008 — No new runtime dependency.** Use existing runtime facilities for the helper and fixtures. All Python invocation in development/testing uses UV. Do not add a database, daemon or third-party dependency for commit journals or status parsing.

## Risks and mitigations

| Risk | Required mitigation |
|---|---|
| An approved plan is mistaken for commit permission | FR-010/011 require a separate current-session grant; default remains off. |
| Committing a whole touched file captures another person's edits | FR-017 blocks overlapping pre-existing deltas instead of automatically isolating or committing them. |
| Mandatory task evidence includes another writer's changes | Show the effective evidence set and stop on active ownership conflict; do not quietly narrow the mandatory evidence policy. |
| Crash after Git writes HEAD produces a duplicate commit | Prepare a stable journal first and reconcile expected parent, boundary key and committed contents before resuming. |
| A hook rewrites files or creates unexpected history | Preserve normal hooks, detect changed files/HEAD and stop; require fresh review before a new attempt. |
| Existing resume skips an already-complete task's pending boundary | Reconcile journals before ordinary task selection and the all-complete return. |
| A new ledger record breaks archive/retry parsing | Keep journals outside the closed ledger grammar and retain parser regressions. |
| A batch commits while another task still depends on old HEAD | Join all writers and use one post-batch boundary only after every member completes. |
| A submodule pointer hides dirty content or unreachable work | Inspect inside modules, override hidden-dirt settings during status, refuse detached new targets, and report publication readiness honestly. |
| Updating several repositories fails halfway | Preflight the whole selection, return per-module results, and retain earlier successes without destructive rollback. |
| A generic reference guide disagrees with current repository policy | `docs/developer-guide/git-standards-protocols.md` contains generic project examples and another ticket-message style; this specification follows the confirmed conventional-message requirement and the actual branch-protection document instead of importing those examples as local policy. |
| Development sync passes while plugin content remains stale | Independently compare `P` against `S`; do not infer plugin parity from `make verify-sync`. |
| Legacy consumers depend on the malformed duplicate command | Search packaging and references before removal and migrate any real consumer in the same change. |

## Decisions for the seed brief's open questions

1. **Command-only or command plus skill?** Command plus protocol skill with safety/commit/submodule references and one mechanical commit helper. This follows the verified developer guide, keeps the command thin, and permits executable integrity tests.
2. **How does implementation commit without invoking a forbidden worker?** Both protocols use the same resolved local helper. Implementation invokes it only after completion/barrier and before the next Q0. No session relay or nested Git command execution is introduced; the retry invariant remains intact inside a task.
3. **What authorizes between-task commits?** A scoped current-session user instruction, off by default. No new flag or plan field. This is already a valid source of human authority, avoids treating arbitrary plan text as consent, and makes revocation and resumed-session limits explicit.
4. **Which submodule operations, and dirty/detached behavior?** Include read-only status, selected recorded-commit initialization/update, and selected pointer commits. Dirty/conflicted modules block mutation; detached-at-recorded-pointer is a valid update result; detached new pointer targets stop for preservation instructions. Content commits require separate authority inside the module. Exclude remote-tip update, module add/remove, URL edits and publication.
5. **What happens to `commands/sc-git.md`?** Remove it after consumer verification, rather than fixing and maintaining an unsupported fourth surface. The canonical command, plugin mirror and generated development copy are the supported distribution chain.
6. **Residual project-management scope?** None beyond accurate local task/commit evidence and guidance to existing commands. Do not expand issue, project-field or closeout behavior under this title.
7. **Parallel and worker edge decisions.** One commit after a fully successful batch, never one while batch members run. Keep attended opt-in and existing worker end-of-Task grants distinct; do not use this issue to widen unattended worker authority.

## Acceptance criteria

1. **AC-01 — Modular delivery.** The canonical Git command has its full interface/STOP/output contract, activates the new protocol, and contains no parallel copy of its execution logic. Proposed references/helper exist, are packaged, and resolve through installed or project runtime surfaces. The legacy duplicate is removed with no remaining runtime consumer. FR-004–009 and FR-036 pass.
2. **AC-02 — No implicit authority.** Plain implementation with no scoped user grant makes zero commits. A commit request does not push, merge, publish a PR, delete branches or change configuration. Forbidden worker invocations fail before mutation. FR-010–012 and FR-031/032 pass.
3. **AC-03 — Safe sequential boundary.** In a two-task fixture, the authorized first commit occurs strictly after the first `complete` and before task two's Q0. It contains only task-one paths and mandatory task evidence; unrelated staged content remains staged and uncommitted. The last task also gets its requested pre-final boundary. FR-013 and FR-015–019 pass.
4. **AC-04 — Batch safety.** A successful independent batch produces at most one post-barrier commit. A batch with one halted member produces none. HEAD never moves while a member is active. FR-014 and the timing tests pass.
5. **AC-05 — Recoverable refusal.** A failing or rewriting hook stops advancement, preserves completed task verdicts and remaining work, and never triggers hook bypass or amend. Repeated resume after a confirmed successful commit produces no duplicate; unresolved history is reported uncertain. FR-020–023 and fault-injection tests pass.
6. **AC-06 — Complete submodule contract.** Inspection reports every registered module and distinguishes hidden dirt, uninitialized state, pointer differences and detached state. Updates use recorded targets only; pointer commits cannot include dirty inner content; partial failures retain exact per-repository outcomes. FR-024–028 pass.
7. **AC-07 — Cleanup reuse.** Git documentation routes cleanup to `/sc:worktrees`; there is no new deletion implementation or remote deletion command. Existing squash-merge refusal still leaves the branch in place. FR-029/030 and the existing removal suite pass.
8. **AC-08 — Evidence and release readiness.** Related executable/static tests and source/development sync pass, and plugin parity is checked separately. Existing ledger/retry/archive regressions remain green. The implementation report distinguishes tested behavior, protocol-only checks and all remaining UNVERIFIED integration details. This specification itself authorizes no implementation, test execution, commit or publication.
