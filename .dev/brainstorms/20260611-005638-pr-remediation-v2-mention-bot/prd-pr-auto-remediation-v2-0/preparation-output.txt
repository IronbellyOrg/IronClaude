The product's reason-for-existing is to \"run a write+push-capable LLM on untrusted comment text\" safely, so its security/trust-boundary posture (authorization gate, injection containment, sandbox isolation, three-way secret separation) is first-class, not boilerplate.\n\nThe pipeline runs in **7 sequential phases**: (1) Preparation, (2) Deep Investigation via 7 parallel codebase research agents, (3) Research Completeness Verification gate, (4) Web Research via 3 parallel agents, (5) Synthesis into 9 template-aligned files plus a Synthesis QA gate, (6) Assembly into the final PRD with structural and qualitative QA, and (7) Present to User & Complete. The output is a **Feature PRD** (PR Auto-Remediation V2.0 is a feature/subsystem of the IronClaude framework, registered as a new `remediate` CLI group) following the project PRD template; platform-level sections (market sizing, value-proposition canvas, competitive analysis, monetization) are marked N/A with a reference to the Platform PRD.\n\nThe product is **reuse-dominant only at the headless-execution seam** (`ClaudeProcess` at `src/superclaude/cli/pipeline/process.py:72`) and the severity rubric (`src/superclaude/skills/sc-auggie-review-protocol/refs/severity-rubric.md:63-101`); the GitHub ingress/authz/reply/resolve surfaces, the injection-containment envelope, the sandbox, the two-phase idempotency ledger, and the deploy hardening are all greenfield. The single highest-risk reuse delta is `build_env` at `process.py:145-160`, which hard-codes `os.environ.copy()` and can only add (not restrict) env vars — so the spec's allowlist-env requirement (no
