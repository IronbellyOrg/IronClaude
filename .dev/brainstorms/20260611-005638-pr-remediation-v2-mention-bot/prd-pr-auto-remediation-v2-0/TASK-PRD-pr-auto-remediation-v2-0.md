# Create PRD for PR Auto-Remediation V2.0

## Task Overview

This task executes the heavyweight PRD-creation pipeline for **PR Auto-Remediation V2.0** — a mention-triggered remediation bot. A human collaborator replies `@bot <directive>` to a PR review comment; the bot detects the mention, authorizes the sender (live collaborator-permission check), remediates the finding under a conservative autonomy lattice (`propose < patch < fix < push < resolve`), replies to the originating review thread, and optionally resolves it. The product's reason-for-existing is to "run a write+push-capable LLM on untrusted comment text" safely, so its security/trust-boundary posture (authorization gate, injection containment, sandbox isolation, three-way secret separation) is first-class, not boilerplate.

The pipeline runs in **7 sequential phases**: (1) Preparation, (2) Deep Investigation via 7 parallel codebase research agents, (3) Research Completeness Verification gate, (4) Web Research via 3 parallel agents, (5) Synthesis into 9 template-aligned files plus a Synthesis QA gate, (6) Assembly into the final PRD with structural and qualitative QA, and (7) Present to User & Complete. The output is a **Feature PRD** (PR Auto-Remediation V2.0 is a feature/subsystem of the IronClaude framework, registered as a new `remediate` CLI group) following the project PRD template; platform-level sections (market sizing, value-proposition canvas, competitive analysis, monetization) are marked N/A with a reference to the Platform PRD.

The product is **reuse-dominant only at the headless-execution seam** (`ClaudeProcess` at `src/superclaude/cli/pipeline/process.py:72`) and the severity rubric (`src/superclaude/skills/sc-auggie-review-protocol/refs/severity-rubric.md:63-101`); the GitHub ingress/authz/reply/resolve surfaces, the injection-containment envelope, the sandbox, the two-phase idempotency ledger, and the deploy hardening are all greenfield. The single highest-risk reuse delta is `build_env` at `process.py:145-160`, which hard-codes `os.environ.copy()` and can only add (not restrict) env vars — so the spec's allowlist-env requirement (no `GH_TOKEN` in the Runner) needs a new seam, not the existing `env_vars` param.

## Key Objectives

The following objectives MUST be achieved by this task:

1. **Comprehensive, evidence-based research:** Produce 7 codebase research files and 3 web research files, every claim traced to actual source code (with `[CODE-VERIFIED]`/`[CODE-CONTRADICTED]`/`[UNVERIFIED]` tags for doc-sourced claims) or a cited external source URL.
2. **Quality-gated synthesis:** Produce 9 template-aligned synthesis files that pass an independent analyst + QA gate, with Feature-PRD scoping applied (platform-level content marked N/A and referenced to the Platform PRD).
3. **Assembled, validated Feature PRD:** A single `PRD_PR-AUTO-REMEDIATION-V2.md` within the heavyweight line budget (1500–2500 lines), passing structural (rf-qa) and qualitative (rf-qa-qualitative) validation with all fixes applied in-place.
4. **Surfaced open decisions:** OD-1 (sandbox technology), OD-2 (push-token mechanism), OD-3 (push-budget default), OD-4 (`patch`-level semantics), and the `remediation/` vs `cli/remediate/` source-home question carried explicitly as PRD Open Questions — never papered over with a silent default.
5. **TDD-ready handoff:** A PRD whose split-host decomposition (Dispatcher D1–D6, Runner R1–R4, host-side H1–H5, severity/deploy S1–S2) maps cleanly onto a downstream `/tdd` or `superclaude roadmap` run.
