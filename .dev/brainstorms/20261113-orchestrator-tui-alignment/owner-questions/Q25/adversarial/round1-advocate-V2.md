# Round 1 advocate: Variant 2 (owner opens each PR session personally)

Advocate persona: security (authority, least privilege, who may publish). Sources were read in this round unless marked UNVERIFIED. Line numbers refer to the files as read on 2026-11-14.

## Position summary

Publishing code to GitHub is the program's highest-authority act, and Variant 2 is the only route where the person's instruction to publish sits in the live conversation of the session that publishes, which is the condition the worker contract sets for outward actions (`WORKER-CONTRACT.md:240`). It also keeps the coordinator, which reads untrusted text, out of the publish path entirely. It pays for this with owner time on all nine PR items. That cost is real, and I argue only that it buys the strongest authority chain, not the best throughput.

## Steelman

**Variant 1 (worker builds, coordinator launches a PR session with `orca agent launch`).** In its strongest form, V1 keeps every control the program already has: a supervised worker under the brief guard, heartbeats and an admitted `worker_done` builds the code (`WORKER-CONTRACT.md:16-20`, WC-5, WC-10), the coordinator reviews the result and shows the person any unseen diff before the push (`:244`), and only then does a fresh top-level session publish under a `GRANT(<item>,pr-submit)` row (merged-requirements.md line 975, 6.4 rule 2). It matches the spec's recommended answer and the 6.3 PR-session row word for word (line 964), so no spec row changes (C-005). The person spends one confirmation, not nine sessions, and lanes keep moving while the owner is away (X-003). Its one-time check of the Orca behaviour with a named fallback (U-001) is careful engineering. What it gets right: separating "build" from "publish" into two agents with a review gate between them is sound least-privilege design.

**Variant 3 (one top-level agent per PR item, created with `worktree create --agent`).** In its strongest form, V3 uses only Orca's documented route, once per item, so the "never both" rule (line 951) holds by construction and nothing rests on the unverified second launch (X-001). The author of the change also answers its review findings, which avoids the cold-reader problem shared by V1 and V2 (X-004). It is one agent per item, the simplest topology for the coordinator, and it is the route the Round 3 advocate called "the only route the worker contract and the pr-submit skill both allow while D3 keeps pr-submit off workers" (round3-invariants-V2.md:53, confidence 85). What it gets right: it reads `WORKER-CONTRACT.md:243` ("run in an ordinary top-level session") as satisfied by any top-level agent, which is a defensible literal reading, and it does not pretend a worker can publish.

## Strengths claimed

1. **The publish instruction is in the publishing session's own live conversation.** `WORKER-CONTRACT.md:240` lets an outward action happen "only when the user's instruction names that action, and confirms with the person at the moment of action unless that instruction is in its live conversation". Under V2 the owner types the command (or the request) in the PR session itself, so the session never needs to trust a relayed instruction. Under V1 and V3 the instruction reaches the publishing session as a prompt the coordinator wrote, which is another agent's text; the ledger grant row is evidence the owner approved, but the launched session cannot tell an owner-written row from one another session wrote into the same file.
2. **The coordinator is removed from the publish path (least privilege).** The coordinator reads worker-written fields, transcripts and sweep reports, which the spec classes as untrusted input (merged-requirements.md line 632, TB-UNTRUSTED; 6.4 rule 9, line 982). In V1 and V3 the coordinator writes the prompt of a session that will push and open a PR, so an injection or a confused coordinator can start a publishing session with altered content. In V2 the coordinator's power ends at writing a "ready for PR" ledger row (variant-2 step 1); it cannot start a session that publishes. That shrinks the blast radius of a compromised coordinator to "a wrong row a person then reads".
3. **A person, not an agent, is the last gate before code leaves the host.** Launched sessions on this host run with permission checks off (`--dangerously-skip-permissions`, merged-requirements.md line 292, TB-PERM line 631; INV-011). V3 states plainly that its agent's "prompt and grant row are the only bounds" (variant-3 costs). V2 does not turn permission checks on either (whether a person-opened session on this host also runs with checks off is UNVERIFIED; it probably does through ccsession), but the person is at the keyboard of that session, watching it publish.
4. **`WORKER-CONTRACT.md:244` is met by construction, not by an agent's promise.** The rule says the coordinator shows unseen worker commits to the person "and pushes only on the person's go; no earlier pre-authorization waives this". In V2 the person reviews the diff in the very session that will push. In V3 that check moves into the publishing agent itself ("which the agent itself must honour", variant-3 costs), so the agent that wants to publish also decides it has shown the diff.
5. **It follows the program's own precedent for sessions that publish.** The coordinator is "an Orca coordinator session the person opened" (`WORKER-CONTRACT.md:69`; merged-requirements.md line 931), and the #539 author, the one other session that pushes, is "a top-level session, not a worker, because it pushes", named by the owner (line 965, Q33). The owner already "merges PRs" and "grants each outward action separately" (line 961). V2 makes every publishing session person-designated in the same way.
6. **No dependence on the unverified Orca behaviour (X-001), with a plain fallback.** V1 rests on a second `agent launch` in a `worker-start` worktree, UNVERIFIED (line 964). V2 does not need Orca to start anything: the owner can open a plain terminal in the worktree path. (See Concessions for the case where the owner opens it through Orca's UI.)
7. **Supervised-worker controls stay on the code (X-002).** Like V1 and unlike V3, the change itself is still built under the brief guard, heartbeats, WC-9's no-outward-action rule (`WORKER-CONTRACT.md:41-44`) and an admitted `worker_done`; the publishing step is added after, not instead.
8. **The coordinator keeps its watch duty and owns fewer sessions.** The coordinator never runs pr-submit (line 962) and, in V2, also never owns a publishing session's lifecycle, which V1 admits it must "track and close" (variant-1 costs). Its only PR duty stays `gh pr view <N> --repo IronbellyOrg/IronClaude` (line 962).

## Weaknesses identified in other variants

1. **V1: the authority to publish is relayed agent-to-agent.** The PR session's mandate is a coordinator-written prompt (variant-1 step 3). Agent messages are not the person's consent, and `WORKER-CONTRACT.md:240` asks for the user's instruction in the acting session's conversation or a confirmation at the moment of action. V1 does not say which of the two the launched session relies on; a prompt naming a grant row is neither.
2. **V1: rests on an unverified Orca behaviour, so its security model may never exist.** The second launch is UNVERIFIED (merged-requirements.md line 964; variant-1 costs: "if Orca refuses, the whole route needs replacing"). Its named fallback is V3, so a V1 choice is partly a deferred V3 choice.
3. **V1: the coordinator gains a publish-starting capability.** `orca agent launch` with a free-form prompt is the most powerful verb the coordinator would hold, and the coordinator is the session most exposed to untrusted strings (line 632). That is the opposite of least privilege.
4. **V3: the agent that writes the code also decides to publish it, unsupervised.** It drops the brief guard, heartbeats and the admitted `worker_done` (variant-3 costs; diff X-002), and the "show the person the diff" check is self-enforced. Its own open question admits the coordinator cannot detect that the agent "has stalled or gone off-brief without `worker_done` and heartbeats" (variant-3 unresolved).
5. **V3: the coordinator still starts publishing sessions.** `worktree create --agent --prompt "<item brief>"` (variant-3 answer) is the same relayed-authority pattern as V1, with no review gate between building and publishing.
6. **V3: nine spec rows change and the role model loses its build/publish split** (C-005; variant-3 costs), a larger edit surface for a security-relevant rule.

## Concessions

1. **Owner time is the real cost.** Nine PR items, each needing the owner to open and attend a session; "Owner latency is the real schedule" (merged-requirements.md line 523). Every lane holds while the owner is away, which for that period equals the default ("no PR is opened"). V1 and V3 clearly win X-003.
2. **The skill's "MUST run in the main orchestrating session" is a technical rule, not a person rule.** `sc-pr-submit-protocol/SKILL.md:47-49` asks for top-level activation so the skill can drive its poll loop and nested skills: "Do NOT run it inside an Agent-tool subagent". A coordinator-launched top-level session satisfies it as well as V2 does. V2's original "strongest reading" claim overstates this; "attended" (`:19`, `:43`) means the session stays open, not that a person watches.
3. **The person's review covers only the first push.** At `--monitor 3` the tool fixes confirmed findings and pushes them without asking (project CLAUDE.md; `SKILL.md:23-25`). Later fix pushes are not shown to the person first in any variant, V2 included, unless the owner stays at the screen.
4. **Cold reader (X-004).** The owner's session did not write the change, so V2 shares V1's weakness; V3 wins this point.
5. **V2 may hit the same Orca question if the owner opens the session through Orca's UI.** Line 951 says a worktree gets its agent from `worker-start` or `worktree create --agent`, never both. If the owner opens a Claude (CLI) session in a `worker-start` worktree through Orca, whether Orca allows it is the same UNVERIFIED behaviour as V1. V2's escape is that the owner can open a plain terminal in the worktree path instead; whether that counts as "an agent" under line 951 is a wording question the spec should settle. I could not read Orca's launch documentation (the `orca-cli` skill is a stub that loads a guide from the Orca executable, `~/.claude/skills/orca-cli/SKILL.md:15,36`, and running Orca was out of bounds).
6. **Fatigue risk.** Nine owner reviews invite rubber-stamping, which would erase strength 4 in practice. This is UNVERIFIED and depends on the owner.

## Shared assumption responses (A-001)

**QUALIFY.** `WORKER-CONTRACT.md:240` gives the coordinator every git and GitHub outward action, but `:243` carves PRs out of that: "PRs go only through `/sc:pr-submit --monitor 3`, run in an ordinary top-level session as decision D3 states, never as a worker". So the PR, its pushes and the review-fix commits that pr-submit itself makes do belong to the PR session under the contract as written. The gap is the first commit of the worker's uncommitted changes: `:245` gives commits in a worktree to the coordinator, while 6.4 rule 14 (merged-requirements.md line 987) gives them to the PR session. The gap must be closed by one sentence in the spec or by the owner's instruction per PR. Variant 2 closes it most directly, because `:240`'s own exception ("unless that instruction is in its live conversation") is met when the owner gives the instruction in the PR session. V1 and V3 need the contract note, because their instruction arrives in a coordinator-written prompt.
