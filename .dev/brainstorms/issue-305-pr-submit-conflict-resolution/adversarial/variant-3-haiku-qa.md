## 1. Purpose and Problem

sc:pr-submit cannot get a PR out of a merge-conflict state. The monitor can drive reviews, fixes, pushes, replies and CI to green while GitHub still refuses the merge (`mergeable: CONFLICTING`, `mergeStateStatus: DIRTY`), and the only output today is a report: the `--pr` path reports commits-behind (SKILL.md:267) and the create path rebases before publishing (SKILL.md:267) or halts (SKILL.md:220-223, :315) - the two contradict each other (seed brief Open Question 7). Nothing in the skill, the core, the scripts or the tests reads GitHub's conflict state (enrichment section 3: zero grep hits for `mergeable|mergeStateStatus|DIRTY|CONFLICTING`).

Conflicts range from mechanical (lockfiles, generated output, adjacent edits, tree conflicts with an obvious answer) to semantic (both sides changed the same behavior, migrations, submodules, binaries). The failure this spec must prevent is paying the semantic-conflict cost (model judgment, per-file intent records, human halts) for a lockfile conflict, and, worse, publishing a wrong resolution for a semantic conflict.

QA framing. This spec treats the feature as a set of testable seams first: every tier boundary must be a pure function with parametrized fail-closed tests; every publication rule (merge parents, marker scan, exact-path staging, no-force-push) must be pinned by a static-grep or unit test; every pinned count (41 events, one python block, push-guard wording order) that this feature touches must be re-pinned in the same commit, not left to break CI later.

## 2. Definitions

- **Conflict state**: GitHub reports `mergeable: "CONFLICTING"` (after at most one re-read when the first read is `"UNKNOWN"`, because GitHub computes it asynchronously - enrichment section 3, external) or `mergeStateStatus: "DIRTY"`, OR a local `git merge origin/<base>` stops with unmerged paths.
- **Unmerged path**: a path with an index entry at stage 1/2/3, or a two-letter `git status --short` conflict code (`DD`, `AU`, `UD`, `UA`, `DU`, `AA`, `UU`) (S-38).
- **Tier**: the complexity class of the WHOLE merge attempt (the maximum tier of any single conflicted path), which selects the resolution procedure and the process cost.
- **Merge cycle**: one attempt to integrate `origin/<base>` into the PR branch: fetch base, attempt merge, classify, resolve per tier, validate, commit (one merge commit), publish. A merge cycle is NOT a remediation cycle; it consumes no `round_counter` tick (FR-7.3).
- **Resolution record**: the per-file structured record (path, category, sides read, intent-ours, intent-theirs, decision, dropped-behavior, regenerated) required for every Tier 2 path before staging.
- **Conflict marker line**: a line starting with `<<<<<<<`, `|||||||`, `=======` or `>>>>>>>` at column 0 in a TRACKED file inside the merge's conflicted-path set. The pre-commit marker scan (FR-4) applies to tracked source paths only, with the exact allowance of research item R-11 and the rejection of R-12's blanket markdown exception (see FR-4 for the .md rule in this repo).
- **HALT**: `terminal_halted` appended to the run-log with a `reason`; nothing pushed; the merge is left aborted (Tier 3 pre-merge) or in progress locally (mid-resolution stop) per FR-8.2.

## 3. Mechanism Mix Decision

Decision summary - adopted: core helpers + one new ref + two script additions + evidence-validator reuse; rejected: new agent, new templates, mergiraf, any global config, any FSM state/event change beyond run-log events.

### 3.1 Adopted, with justification

1. **New pure-Python core helpers in a NEW module `src/superclaude/pr_submit/conflict.py`** (not appended to `fsm.py`). The deterministic decisions - tier classification from (paths, modes, status codes, marker counts), merge-parent check, marker-scan verdict, tier routing under the ordinal ceiling, merge-cycle event construction - belong in the importable core per the existing split (SKILL.md:36-41: core owns decisions, skill owns I/O). A new module is required rather than `fsm.py` edits for two QA reasons: (a) T-N50 bans the tokens `git` and `gh` in `CORE_PURE_FILES`, and `fsm.py` is in that list (test_static_grep.py:37-51) - conflict logic that must quote `git status --short` codes and index stages would force awkward wording inside `fsm.py` docstrings, while a new module can be added to `CORE_PURE_FILES` with rules stated once, still without shell commands; (b) `is_cross_cutting` treats any change touching `fsm.py` as cross-cutting and forces VG-2 `make test` (fsm.py:613-642, marker `fsm.py` at :623) - a new module keeps ordinary conflict work on targeted VG-1 runs. The helper for the merge-parent rule sits NEXT TO `push_parent_ok` conceptually but physically in `conflict.py`, imported and re-tested; `push_parent_ok` itself is NOT loosened (FR-5).

This follows the existing per-wave lazy-load pattern (wave table SKILL.md:252-265) and keeps the single-python-block invariant safe: conflict logic is PROSE in a ref, never a second python block in SKILL.md (test_cosmos_protocol.py:36, test_codex_reviews.py:688 pin exactly one block; enrichment section 6 flags a second block as a break point).
3. **Two script changes**: (a) `scripts/poll-augment-review.sh` gains the fields `mergeable` and `mergeStateStatus` in its `gh pr view --json` list, APPENDED after the existing fields - enrichment section 8 warns test_static_grep.py:636 pins the substring `--json headRefName,headRefOid,isCrossRepository` for the Wave 0 head-binding read; the poll script's own list today is `number,url,headRefName,headRefOid,baseRefName` (poll-augment-review.sh:38), so the new fields extend that list and the pinned substring stays intact; (b) one new script `scripts/merge-status.sh` (`--repo` pinned like every other script, enrichment section 1) that emits ONE JSON line with the unmerged-path inventory needed for classification: per path the `git status --short` code, the index modes (stage detection incl. mode 160000 submodule detection, R-43), and binary detection (`git diff --numstat` reporting `- -`). Scripts stay dumb data collectors; classification is the core's.

It validates the resolution record's cited hunks (the stated intents must ground in the actual sides). It cannot run git, which is exactly right: the git reads happened before, in the record. A NEW conflict-resolver agent is rejected (see 3.2).
5. **Run-log events: 3 new EventType members** (`conflict_detected`, `conflict_resolved`, `conflict_halted`), moving the closed enum 41 → 44, plus a `push_kind` field on the push triad (`fix` | `merge`). Both pinned counts change EXACTLY ONCE, in the same PR, with both pinning tests edited (test_run_log.py:168, test_codex_reviews.py:441). This is the cheapest honest option: the write-ahead run-log is the crash-recovery substrate (SKILL.md:44-45, recovery.py), and a merge cycle that cannot be distinguished from a fix push on `--resume` is an untestable recovery (enrichment section 8: the triad and recovery need a push-kind marker so Branch B re-drives the right commit).

### 3.2 Rejected, with reason

- **New agent (conflict-resolver)**: no capability gap. Tier 0/1 need zero judgment (deterministic regeneration or obvious-answer tree conflicts); Tier 2 judgment is the MAIN session's job because it must edit files and stage paths - an agent would need write tools, contradicting the skill's own rule that the main session performs every verification and edit (SKILL.md:82-84); Tier 3 halts. `merge-executor` merges debate documents, not branches (enrichment section 7). Cost (a new installed agent definition, sync, dual-surface lookups) buys nothing evidence-validator reuse plus main-session work does not. J-39 (conflict resolution is the agent's own work, not a script) supports keeping it in-session.
- **New template files**: templates are for operator-facing documents; the resolution record is a run artifact whose shape must be pinned by tests inside the ref (seed brief Open Question 6). `src/superclaude/templates/` holds none today (enrichment section 7), HALT messages live inline where tests pin them verbatim (enrichment section 7), and a template would add an install-surface presence check (tests/unit/test_cli_install.py:248-262) for no test benefit.
- **mergiraf or any structural-merge dependency**: seed brief Constraints: no new external dependency. R-64/R-65/R-66 scored 2/3/3.
- **Global git config changes (zdiff3, rerere)**: R-68 scored 1; violates seed brief Constraints (no global git config changes). The core reads whatever conflict style produced the file; S-17's three-side reading is done from index stages, not from marker sections, so zdiff3 is not needed.
- **New FSM states or transition edges**: the Codex/CI precedent shows the pattern - merge reviewer outcomes BEFORE the FSM sees them and keep the machine untouched (state-machine.md:62-68, :140-157). A merge cycle is resolved (committed or aborted) before the monitor's FSM path resumes; its only FSM-visible effect is a normal push with `push_kind: merge`. Zero new `MonitorState` members, zero new `transition()` edges, `state-machine.md` gains a prose subsection (not a state) describing the merge cycle as SKILL-owned. This removes the largest regression surface (enrichment section 4: a new event silently stays put without an edge, fsm.py:801-802; the C6 row-by-row assertions over the state set, state-machine.md:135-138).
- **Historical-resolution mining, sbse-recombine, meta-router, stacked-PR detection**: R-125, R-96, R-70, R-106 all scored 1. R-128 (never auto-apply a historical result, ROI 7) is adopted as a PROHIBITION in the ref, which is all of that subsystem worth keeping.
- **A new CLI flag (`--conflict-tier` cap)**: rejected for V1. The ordinal ceiling already tiers the behavior (FR-7.1); a second axis doubles the test matrix against the parser (fsm.py:73-99 accepts exactly today's flags). Revisit only if operators demand a propose-only-conflicts mode (Open Question 5).

## 4. Conflict Tier Model

Classification rule: after a merge attempt stops, `merge-status.sh` produces the per-path inventory; the pure helper `classify_conflict(paths)` returns the tier of the attempt = the MAXIMUM tier over paths (one bad file escalates everything, because the merge commit is atomic: a wrong resolution of one file poisons the whole commit). Tier assignment per path is mechanical and ordered (first match wins, mirroring the fixed order idea of R-42 while keeping only this repo's categories):

1. **Tier 3 (halt, never edit)**: index mode 160000 (submodule, R-43/R-56); binary (numstat `- -`, R-57); migration paths (`migrations/`, `alembic/versions/`, `prisma/migrations/`, `db/migrate/` - trimmed to ecosystems this repo plausibly touches, R-54); any path whose ours/theirs intent cannot each be stated in one sentence after the evidence pass (R-18); any Tier 2 path where VAL fails after resolution (FR-7.6).
2. **Tier 2 (text conflict resolved by intent)**: everything else with human-authored content - `.py`, `.md`, `.toml`, `.yaml`, `.cfg`, `.txt` under tracked source/docs/tests paths with an actual content conflict (stage 1/2/3 or `UU`/`AA`).
3. **Tier 1 (mechanical)**: lockfiles regenerable by a known package manager (`uv.lock` via `uv lock`, R-189; a `pyproject.toml` dependency-table conflict is resolved by the intent of the manifests then the lock is regenerated, R-58); generated output regenerated from a resolvable source (`.claude/` sync targets from `src/superclaude/` in THIS repo, docs/generated, R-58); snapshot/test-expectation files taken from the resolved code state then regenerated (R-60); whitespace-only or line-ending conflicts; tree conflicts with an obvious answer: `AA` both-added (merge contents, S-40), `DU`/`UD` delete-vs-edit where the edit is provably obsolete (deletion wins only with shown evidence, S-39/R-154), rename-vs-edit (apply the edit at the moved location, R-153).
4. **Tier 0 (no conflict)**: `mergeable: MERGEABLE` and `mergeStateStatus` in {`CLEAN`, `BEHIND`, `BLOCKED`} with no local unmerged paths. BEHIND-only is NOT a conflict: today's behavior is preserved (create path rebases, `--pr` path reports - the contradiction is settled in FR-5.1, not here).

Exit criteria per tier (the done condition the tests pin):

- **Tier 0**: exit immediately, no merge attempted, no events beyond `conflict_detected{tier: 0}`; zero process cost.
- **Tier 1**: every conflicted path staged (`git add -- <path>` exact path, J-56) after its mechanical resolution; zero conflict markers in tracked files (R-11); regenerated files staged (S-46); the merge commit exists. VAL NOT required for lockfile-only sets (see FR-7.5 for the VAL trigger rule).
- **Tier 2**: per-file resolution record complete (both intents one sentence each, R-18; behavior-after-merge sentence, R-156; dropped behavior named aloud when a side loses, S-29); evidence pass done (R-112: `git log --oneline --left-right --merge -- <file>`, `git show` of both sides, both merge-base diffs); evidence-validator verdict grounded for every record; markers zero; VAL green (the merge changed source, so VG-1 at minimum); merge commit exists.
- **Tier 3**: NO merge attempted or merge aborted cleanly (`git merge --abort`) BEFORE any resolution edit when classification alone routes every path to Tier 3; HALT event `conflict_halted{reason}`; nothing staged, nothing committed, nothing pushed; the HALT message names file, operation, step, branch (R-210) and each side's best-read intent (R-212). Mid-resolution escalation (a Tier 2 path that fails VAL or intent): leave the merge IN PROGRESS locally (J-53), HALT with the same message shape; never `reset --hard` (R-15), never stash (J-20).

Cost layering (the point of tiers): Tier 0 costs one poll-field read; Tier 1 costs one script run plus regeneration commands, no model judgment, no agent; Tier 2 adds the evidence pass, the record, one evidence-validator batch and VAL; Tier 3 costs one halt message. Nothing in Tier 1 or Tier 0 reads all three index stages beyond mode detection or spawns anything.

## 5. Placement in the sc:pr-submit Flow

### 5.1 Create path contradiction settled (prerequisite fix)

Wave 0's rebase-if-behind (SKILL.md:267) vs the STOP block / Error-Handling row HALT (SKILL.md:220-223, :315) is settled as: **create path rebase stays** (unpublished branch, no force-push needed - the rebase is safe precisely because nothing is published yet); the HALT applies ONLY to a conflict state that the rebase itself hits or a behind-base state discovered on `--pr`. The three text sites are made to agree in the same PR; the static-grep pins that quote them (test_static_grep.py:656-661) are updated in the same commit. This is a documentation-consistency fix with zero behavior change beyond the new conflict read, and it must land BEFORE the tier machinery, otherwise Wave 0 has two authors of behind-base behavior.

### 5.2 The new Wave 0b (conflict check), and the two re-check points

- **Wave 0b, after Wave 0 head binding, before Wave 1** (create and `--pr` paths, L1+): read `mergeable`/`mergeStateStatus` from the poll snapshot fields (or one `gh pr view` read on the create path where no snapshot exists yet). `UNKNOWN` → re-read once after a short delay, then treat a second `UNKNOWN` as no-signal and continue to Wave 1 WITHOUT halting (GitHub's async computation must not delay reviews; the re-check points catch it). `CONFLICTING`/`DIRTY` → run the merge cycle (section 6). A conflict resolved here means reviewers review a conflict-free head - the cheapest place to fix it, before any review budget is spent.
- **Re-check point A, Wave 8 entry**: before arming the CI wait, re-read the conflict fields. GitHub does not run `pull_request` workflows on a conflicted PR (enrichment section 3, external), so a Wave 8 wait on a still-conflicted PR may report `polling` forever until `--timeout`. A conflict here runs the merge cycle, then re-arms Wave 8 on the new head. This is the base-moved-during-the-run case (enrichment section 8, hook point c).
- **Re-check point B, pre-push head guard**: the guard already re-reads the PR (SKILL.md:274); its read gains the conflict fields. A conflict discovered here (base moved between VAL and push) → do NOT push; run the merge cycle; after the merge commit, the guard RE-RUNS in full (head equality against `pre_push_sha` is unchanged - the local merge did not move the remote head) and then the fix push proceeds with `push_parent_ok` against the updated `pre_push_sha` (after a landed merge, `pre_push_sha := merge_sha`, so the one-commit rule composes - FR-6.2).

### 5.3 Interaction with the monitor machinery

- **Ordinals L0-L3**: L0 never arms and never reaches Wave 0b (Wave 0b is L1+; the AC-1 byte-identical L0 sentence is untouched - test_static_grep.py:650-653 pins it). L1: detect + classify + PROPOSE the full resolution plan (paths, tier, commands) as text; the merge is NOT attempted and the working tree stays clean. L2: resolve + commit locally (the merge commit exists; nothing pushed; the cycle ends with a local-commit report - it is SKILL-owned, so the S4' halt state is not used). L3: resolve + commit + push the merge commit. This resolves seed Open Question 5: merge commits are LOCAL at every ordinal; only the PUSH is ceiling-gated.
- **`round_counter` / `max_rounds`**: a merge cycle NEVER ticks `round_counter`. The counter ticks only on the attributed re-review edge S5 → S2 (fsm.py:776-777; state-machine.md:91-93); a merge cycle produces no finding, no fix, no re-review request, therefore no tick. But a merge push LANDS: `rebuild_state` counts every `push_completed` (run_log.py:238-241), so a merge push would increment `push_count`. INV-R2's `push_count <= max_rounds + 1` (SKILL.md:275) is kept TRUE by excluding merge pushes from `push_count` via the `push_kind: merge` filter in `rebuild_state`, with a NEW output field `merge_push_count`. This keeps the existing invariant's meaning (review-driven pushes bounded by rounds) intact, keeps the pinned Output-Contract row (SKILL.md:239, == max_rounds at most) true for fix pushes, and makes the merge budget independently pinnable: `merge_push_count <= 1` per run (FR-7.4). Seed Open Question 4 answered: a merge commit is its own cycle TYPE, not the cycle's single commit; the one-fix-commit-per-cycle rule is untouched.
- **Reviewer re-trigger**: a merge push does NOT re-trigger reviewers (no `rereview_requested`; the pending-retrigger machinery keys on `applied_edits > 0` cycles, SKILL.md:274 S5a). Rationale: reviewers review the merged result at the NEXT fix push or at the operator's request; re-triggering on a merge would burn re-review budget on content the reviewers already saw (both sides' commits are individually reviewed). The merge push replies to and resolves NO thread. Seed Open Question 3 answered: a conflict resolution consumes no review round and does not re-trigger reviewers; at Wave 8 the merge simply re-arms the CI wait on the new head.
- **Run-log events**: `conflict_detected{tier, paths_count, base_sha}` at classification; `conflict_resolved{tier, files_staged, merge_commit_sha?, push_kind}` at merge-commit creation (and push, at L3); `conflict_halted{reason, tier}` at Tier 3 / mid-resolution stops. The push triad carries `push_kind: "merge"` on a merge push (fsm.py:238-288 `build_push_triad` gains an optional field, default `"fix"` - the default keeps every existing call site and test payload unchanged).
- **`--resume` crash recovery**: `detect_crash_window` matches on the idempotency key (recovery.py:57-80); the key format is unchanged (`push:<run_id>:<cycle_id>:<pre_push_sha>:<target_branch>`, fsm.py:227-235) - a merge cycle uses its OWN `cycle_id` (`merge-<n>`, n = merge_push_count so far), so a dangling merge `push_initiated` is distinguishable. Branch A (landed): synthesize `push_completed{recovered, push_kind: merge}`, resume at Wave 8 re-arm or Wave 1 continuation, NOT at S5a (no re-trigger to post). Branch B (not landed): re-drive the merge push with the RECORD's `target_sha` - the merge commit is still local and intact (a merge commit is not recomputed); the existing Branch-B skip-the-fix-commit logic (SKILL.md:268) maps directly: skip re-resolution, re-run the pre-push head guard with the record's `pre_push_sha`, push. Branch C: unchanged HALT_HUMAN (recovery.py:161-171). The `push_kind` marker is what lets Branch B know it must NOT look for a fix commit to skip - there is none.
- **No-stash / current-worktree**: never stash (J-20; worktrees share one stash stack); `git merge` refuses to start over local changes, and that refusal is CORRECT: it means operator dirt exists, so the merge cycle halts with reason `dirty_worktree` telling the operator to commit or discard their own files first. Only the current worktree is touched (J-91, J-05); no `git checkout main` (J-06); foreign-operation guards: halt if a rebase/cherry-pick/revert/sequencer is in progress (J-17), detect an in-progress merge via `git rev-parse --git-path MERGE_HEAD` (J-16), halt on detached HEAD (J-15).

## 6. Publication Without Force-Push

The ONLY publication mechanism: `git merge origin/<base>` into the PR branch producing a merge commit with parents exactly `[pre_push_sha, base_sha]`, pushed as a fast-forward via the existing `git push origin <target_sha>:<target_branch>` (never a force form - the force-push ban and its test test_static_grep.py:758-776 cover the whole skill folder, so the new ref and scripts must contain no force form either).

### 6.1 The merge-commit parent rule (extends push_parent_ok, does not loosen it)

New pure helper in `conflict.py`: `merge_push_parent_ok(target_parents, pre_push_sha, base_sha) -> bool` - True iff `target_parents` is exactly a 2-element list `[p1, p2]` where `{p1.lower(), p2.lower()} == {pre_push_sha.lower(), base_sha.lower()}` (order-independent: git records `[HEAD, MERGE_HEAD]` = `[pr_head, base_tip]`, but the helper must not depend on git's ordering), both ids full 40-hex, and `pre_push_sha != base_sha` (a self-merge is nonsense and fails closed). Everything else fails closed: 1 parent, 3+ parents (an octopus merge or a fix commit), root, short/null ids, non-list. `push_parent_ok` (fsm.py:582-600) is UNCHANGED and still rejects all two-parent commits - its pinning test (test_pre_pr_checks.py:216-222, id `merge`) stays green verbatim. The push site selects the helper by `push_kind`. Fast-forward safety argument: the remote PR head is `pre_push_sha` (confirmed by the pre-push head guard immediately before); the merge commit's first parent IS `pre_push_sha`; therefore pushing `merge_sha` is a fast-forward that publishes exactly one commit (the merge), carrying no other local work - the same property `push_parent_ok` guarantees for fix commits, proven by a different parent shape.

### 6.2 How the one-commit-per-cycle, staging and hook rules apply

- **The merge commit is exempt from one fix commit per cycle by construction** (it is a different cycle type with its own cycle_id), but it inherits the SPIRIT exactly: the merge push publishes exactly one commit (the merge); a fix push after a merge publishes exactly one commit (the fix, whose single-parent chain now includes the merge - `push_parent_ok` checks the fix commit's parent equals `pre_push_sha`, and after a landed merge `pre_push_sha := merge_sha`, so the rule composes with no change to `push_parent_ok`).
- **Exact-path staging (J-56)**: each resolved file is staged `git add -- <path>` the moment it is finished; regenerated outputs staged explicitly (S-46); never `git add -A`, never `git add .`, never staging outside the conflicted-path set. The merge commit is created with plain `git commit` (after all paths are staged) with `GIT_EDITOR=true` (message auto-generated), NEVER `--no-verify` (J-60); a pre-commit hook failure is reported verbatim (J-61) and halts with reason `merge_commit_failed`, merge left in progress, and `--amend` is forbidden after a hook failure (J-63 - the merge commit does not exist yet; amending would rewrite the previous PR commit). This is why the fix commit's `git commit --only -- <paths>` recipe (SKILL.md:274) cannot be reused: git refuses partial commits during a merge (enrichment section 2, external) - the merge commit is its own commit step.
- **Pre-push head guard**: unchanged procedure (SKILL.md:274): re-read the PR, `pr_head_ok(<local branch>, pre_push_sha, ...)`, `headRefName == HEAD_BRANCH`, THEN the parent check (with `merge_push_parent_ok` for a merge push), THEN `push_decision`. The pinned ORDER (head check < parent check < "The deterministic core DECIDES", test_static_grep.py:664-676) is extended, not reordered: the new merge-commit sentence sits between the parent check and DECIDES, mirroring the existing shape.
- **After the push**: `pre_push_sha := merge_sha`; the PR is mergeable again; the flow continues (Wave 1 reviews the merged head, or Wave 8 re-polls on the new head).

## 11. Out of Scope

- Rebase-based integration of a published head (requires force-push; banned).
- Resolving conflicts on a PR whose head is NOT the checkout (`pr_head_mismatch` path unchanged).
- PR decomposition / split recommendations for oversized conflicts (R-09/R-10/R-38, scored 1).
- mergiraf, zdiff3 config, rerere, any tooling or config change (NFR-2).
- Historical-resolution mining, sbse candidate recombination, meta-router, stacked-PR detection (all scored 1).
- Taking over a paused rebase/cherry-pick/revert that the OPERATOR started (J-17: halt the merge cycle, tell them to finish or abort theirs).
- A new CLI flag for conflict behavior (section 3.2).
- Automatically fixing semantic conflicts: Tier 3 halts, always. The troubleshoot dispatch seam (refs/troubleshoot-dispatch.md:51-60, enrichment section 7) is the future hook for diagnosis-assisted human resolution, not V1.
- Binary merging, submodule repinning, migration synthesis (R-54/R-56/R-57 halts).

4. **The `conflict_resolved` event payload**: per-file resolution records inline (large, useful for audit) or counts plus a path to a records file under `--output-dir` (small, redaction-safe)? QA recommendation: counts plus file path; records carry operator prose that has no schema.
