## Steelman

### Variant A (opus:architect) — strongest form

A's central claim is the only fully coherent account of **what a merge push is**: authored code landing on a PR. AD-3 makes a conflict cycle an ordinary remediation cycle — "It enters the existing FSM at `S3_FIXING` through one new edge, reuses `S7_VALIDATING`, `S4_PUSHING` ... and ticks `round_counter` on the existing INV-001 edge. This keeps `push_count <= max_rounds` ... INV-R2 `push_count <= max_rounds + 1` ... true with no edits" (A:45). Every existing invariant survives unedited because the merge is not special-cased. J-66 (the merge is authored code and is reviewed) is honored by construction: the S5a re-trigger means a bot reviews the resolution (A:245-247), with the S5 watermark gate guaranteeing "a review of the pre-merge head is never attributed" (A:247).

Three things A genuinely gets right that neither peer matches:

1. **AD-6, the read-only probe.** `git merge-tree --write-tree -z` "reports conflicted paths with their index stages ... without changing the working tree or index (verified locally with git 2.47.3 on 2026-11-04)" (A:51). This single decision makes L1 classification possible (propose a plan without starting a merge), makes Tier 3 a nothing-touched halt, and makes the parser testable from a captured fixture (A:557, `fixtures/merge_tree_conflict.z`). C's classify-after-merge design cannot do any of these three things — I concede this below.
2. **Conflict-first placement (AD-2).** "Reviewing a head that must change wastes reviewer quota, produces findings on pre-merge code, and CI cannot run while the PR conflicts" (A:43). B's own risk table concedes the inverse twice: K9 "The review phase has already run before a Tier 3 halt ... Wasted review time" (B:539). A's placement is the only one that never pays review cost on a head the merge will replace.
3. **The base-ancestry check (X-008).** A step 2 of the guard: "`git merge-base --is-ancestor <base_sha> origin/<base>` must exit 0 ... every other new ancestor is reachable from `base_sha`, and step 2 proved `base_sha` is on the remote base branch, so those commits are already public and reviewed on the base" (A:335, A:343). This is the only complete answer to why publishing a two-parent commit is safe; C's "publishes exactly one commit (the merge)" (C:93) is factually wrong against `fsm.py:585-587` ("A fast-forward push publishes every commit between the two").

A also has the best routing-coverage test of the three: FR-C6's "exhaustive table test over ordinal 0..3 x tier 0..3 x cap 0..2 x budget {spent, open} x `fsm_terminal` {True, False}" (A:473).

## Weaknesses Identified (in A and B)

### In Variant A

1. **The INV-016 audit record is falsified by its own push gate (X-010).** A reuses `evaluate_push_decision` "with `applied_edits = <resolved path count>`" (A:337). Predicate 5 exists to mean "grounded finding edits"; a resolved-path count is not that. The run-log then asserts a push was justified by finding-fixes when it was justified by a merge — the audit trail QA depends on post-hoc misdescribes the push. B's critique (B:108) is correct, and A's own FR-C18 AC cements the lie into a test ("`round_counter == 1`, `push_count == 1`, `rereview_request_count == 1`", A:509).
2. **A conflict consumes a review round — an operator-visible regression A rates High-likelihood itself.** "R-4 | A conflict cycle spends a round, so `--max-rounds 2` leaves one review-fix round | **High** / Low" (A:613). Default budget is 2, so every conflicted PR — the exact population this feature serves — silently loses half its fix budget to the unblocking step. The mitigation is "documented in the command" (A:613), i.e. accepted, not fixed.
3. **AD-7 changes L0 create-path behavior while claiming L0 identity.** Wave 0 runs at all ordinals ("Wave 0 (all ordinals)", SKILL.md:267), and AD-7 says "Wave 0 never rebases on either path" (A:53). At L0 on a behind branch, today's run rebases then opens the PR; after A it opens the PR without rebasing. A's NFR-6 preserves only the AC-1 *sentence* ("L0 AC-1 sentence unchanged", A:538) — the pinned text I verified at `test_static_grep.py:650-653` — while the *behavior* the ordinal contract describes changes. A flags no such risk; C's R7 exists precisely for this class ("The create-path contradiction is fixed by deleting the rebase, changing L0/L1 create behavior", C:167).
4. **The one FSM edge re-opens the largest regression surface for the smallest structural gain.** The edge forces `state-machine.md` growth and C6 row-test churn (A:89 rejects new *states* on exactly this ground, then accepts a new *edge* that touches the same enumeration), and the known silent failure mode applies: "an unknown edge stays put" (`fsm.py:801-802`, cited at A:32, C:44) — a misspelled event name yields a dead feature with no error. B and C get identical ceiling semantics from the ordinal routing function with zero FSM edits (B R3, B:106; C NFR-5, C:124).
5. **A's L1 stops the run before a single review poll** ("the run stops (no review poll, no merge started)", A:216). At L1 with a Tier 3 conflict the operator gets a halt and zero review signal — strictly less information than B's Wave 0 report plus completed reviews (B:250). AD-2's stale-findings argument justifies not *fixing* on a conflicted head; it does not justify discarding the reviews.

## Concessions (Variant C's own defects, acknowledged)

The diff-analysis flags X-008, X-012, X-023, X-033, X-034, X-035, X-037 against C. All seven stand; I concede each with the repair I would accept in the merged spec.

1. **X-008 — no base-ancestry check; "publishes exactly one commit" is false.** C:93 claims pushing `merge_sha` "publishes exactly one commit (the merge)". `fsm.py:585-587` says the opposite: "A fast-forward push publishes every commit between the two" — the merge also publishes every base-side commit not yet on the PR branch. Without A/B's `git merge-base --is-ancestor <base_sha> origin/<base>` check (A:335, B:353), nothing proves those commits are public. **Conceded; adopt the ancestry check and strike the "exactly one commit" sentence.**
2. **X-012 — L2 commits the merge locally, violating the ordinal contract.** C:80 ("L2: resolve + commit locally") contradicts `SKILL.md:273` ("changes are left in the working tree with **NO commit**, NO push, NO reply") and `state-machine.md:102` (T-412 "commit never") — both verified. C's defense (the cycle is SKILL-owned so S4' is unused) confuses FSM ownership with the ordinal ceiling: L2 never commits, period. **Conceded; adopt A's AD-9 / B's 6.4 step 8 (resolve, stage, VAL, stop with MERGE_HEAD present, uncommitted).**
3. **X-023 — the staged-set assertion is unsatisfiable.** FR-6.4's "staged-set == conflicted-path-set assertion before `git commit`" (C:111) cannot hold: during a merge git auto-stages cleanly-merged paths, so any merge with at least one non-conflicted changed file stages more than the conflicted set. **Conceded; adopt B's implementable form — staged ⊆ (base-changed since merge-base) ∪ (resolved paths) (B:352).**
4. **X-033 — the "unpublished branch" premise is likely false.** C:70 ("unpublished branch, no force-push needed") repeats B:622's premise, which the spot-check flags against SKILL.md:268's own force-push admission. **Conceded; A's AD-7 (remove the create-path rebase; behind is a Tier 0 report) is the mechanically correct settlement**, with C's R7 discipline (pins updated, not deleted) applied to the pin rewrite.
5. **X-034 — Wave 0b cannot exist as placed.** C:74 places Wave 0b before Wave 1 while reading "the poll snapshot fields" and appending `conflict_detected` (C:83) — but the output-dir, run-log and poll loop are initialized **in Wave 1** ("Initialize the output-dir + run-log + baseline, then enter the attended poll loop", SKILL.md:269, verified). No snapshot and no run-log exist at Wave 0b's position. **Conceded; move the gate to Wave 1 entry after run-log init, before the first poll — which is exactly A's C-initial (A:186). A's placement is superior.**
6. **X-035 — L1 proposes a classification it cannot produce.** C:80 has L1 "detect + classify + PROPOSE" with "the merge ... NOT attempted", but classification runs "after a merge attempt stops" (C:50). With no merge there is nothing to classify. **Conceded; adopt the read-only `merge-tree` probe (A AD-6 / B's `probe-merge.sh`) as the classifier input — it fixes L1, Tier 3-with-nothing-touched, and C's X-034 sequencing in one decision.**
7. **X-037 — re-check point B's sequence cannot pass either parent check.** As written (C:76): the fix commit exists, then the merge cycle runs, then "the fix push proceeds with `push_parent_ok` against the updated `pre_push_sha`". But the merge's first parent is the fix commit, not `pre_push_sha`, so `merge_push_parent_ok` fails; and the fix commit's parent is the old head, not `merge_sha`, so `push_parent_ok` fails. **Conceded. The repair is a reorder, not a removal: at re-check point B the remote PR head has not moved (only the base did), so the guard's head check still passes — push the fix first, set `pre_push_sha := target_sha`, then run the merge cycle on top.** The coverage window (base moves between VAL and push) is real and uncovered by A or B at this hook point; U-019's Low rating reflects the broken sequence, not the window.
8. **Two further C-internal defects I add myself:** X-036 (the Tier 2 rule at C:53 claims `UU`/`AA` while the Tier 1 rule at C:54 also claims `AA`; first-match-wins makes the Tier 1 `AA` unreachable as ordered) and X-038 (C:70's "HALT applies to ... a behind-base state discovered on `--pr`" contradicts C:55's "BEHIND-only is NOT a conflict ... `--pr` path reports"). Both are drafting errors; the merged spec should drop the "obvious-answer tree conflict" Tier 1 category entirely (see X-015 below) and keep BEHIND as report-only on both paths.
9. **C-036 — no executable test of the git mechanics.** C's section 9.3 pins merge mechanics as prose only (C:155). B's real-repo script tests under `tmp_path` with a stubbed `gh` and capability skip (B:460) are strictly better coverage of the riskiest commands; the merged spec should take them. A's captured fixture (A:557) remains the right form for the *parser*.

## Shared Assumption Responses

- **A-001 (branch rules accept a merge commit in a PR) — ACCEPT, and promote to a runtime check.** Unstated by my variant too. For this fork (squash-merge PRs) the assumption holds — the merge commit never lands on `master` — but the skill ships to arbitrary projects, where "require linear history" would make every correct resolution unmergeable. The merged spec should read the repo's allowed merge methods (or document the check as an operator note) before the first merge push; on failure it is a Tier 3 halt with nothing pushed, not a wasted resolution.
- **A-002 (evidence-validator's contract fits a resolution record) — QUALIFY.** The agent re-reads file:line citations (verified: `src/superclaude/agents/evidence-validator.md` is read-only Read/Grep/Glob). It can verify the record's cited hunks exist and that the stated intents *ground* in the actual sides — which is how C scopes it ("the stated intents must ground in the actual sides", C:35) — but it cannot judge an intent *true*, and A concedes the same ("It does not judge truth", A:441). All three variants slightly over-claim; the merged spec should state the validator's verdict as evidence-grounding, with B's one-revision-pass rule (B:349), not as semantic approval.
- **A-003 (target project has working VAL targets and a real suite) — ACCEPT.** VAL is the Tier 2 safety net and the skill runs in arbitrary projects. A's VG-1-escalates-to-VG-2 when no test area maps (A:313) is a partial mitigation; the merged spec should also report "no tests found for changed area" as an explicit line rather than a silent green.
- **A-004 (allowed-tools permits the new commands) — QUALIFY, against my own variant first.** C's `GIT_EDITOR=true git commit` (C:98) is env-prefixed and likely does not match the `Bash(git *)` prefix patterns (verified: `SKILL.md:4` lists only `Bash(gh *)`, `Bash(git *)`, `Bash(uv *)`, `Bash(make *)`, `Bash(jq *)`; X-039). B's three scripts face the same question the existing poll scripts already pose. A's U-002 (a test that every mechanical-rule program is in `allowed-tools`, A:407) is the right mechanism and should be generalized to every new command in the merged spec. `git commit -F <file>` (A, B) avoids C's problem entirely.
- **A-005 (new cycle ids cannot collide with existing ones) — ACCEPT, with one pin.** C's `merge-<n>` keyed on `merge_push_count` and B's `sync-<n>` are both prefix-disjoint from fix cycle ids by inspection, but none of us cites the existing generator. The merged spec needs one test asserting the generator's format cannot emit the new prefixes.
- **A-006 (re-run with `--pr <N>` after the operator finishes the merge passes head binding) — REJECT as stated.** Head binding requires local HEAD == `headRefOid` (SKILL.md:268), so an unpushed local merge commit fails `pr_head_mismatch` — the diff-analysis's only CONTRADICTED assumption, and it burns A's own recovery message ("Finish it by hand and commit ... Then re-run", A:174-175; X-041). B's instruction is the only correct one: "run `git commit` yourself **and push**" (B:351). The merged spec must adopt B's push-inclusive recovery text (or teach binding to recognize our recorded merge commit); C's HALT templates must be fixed the same way.
