## 1. Position summary
Variant 4 is the right skeleton and the wrong first draft. The skeleton (a `release/<rel>` branch kept in a different folder from the `<rel>/<kind>/NN-slug` work branches; stories squashed into the release line; the release landing on `master` by one merge-commit pull request; hotfixes from `master`; an explicit clean-up and revert rule) survives every failure scenario I could build from this repository's real history. The draft text itself has two defects that I concede below (pull request per story, and merging `integration` into the release), and `gfxai-fit.md` already corrects the first one (its named change 1: local coordinator squash merges). I defend V4 as "original plus the seven named changes in `gfxai-fit.md`, minus the `integration` merge", and I say plainly that this converges on V1 with four differences: the folder layout, squash instead of `--no-ff`, a beta freeze, and a release-PR acceptance gate.

Honest status of the source: the GFxAI document is "version 1.0", `status: "To Do"`, "Pending team review", its Release and Tagging section reads "To Do (No prework)", and the 2026-05-19 decision that amends it was never applied (`gfxai-approach.md` section 2). The fit note says about 30 of the last 40 merged GFxAI pull requests go straight to `master`. So V4's pedigree is evidence of the owner's intent and of what Clay may already know, not of a tested method. It should be judged on its mechanics, which is how this statement judges it.

## 2. Steelman of each opposing variant
### V1 (release line, local merges, one PR at the end)
Strongest version: it is the owner's own model made exact, and it needs no change to CI, repository settings or the worker contract. It keeps the ledger on the release branch (CONTEXT line 14), keeps BMAD planning on `master` (X-009), and never spends a bot review on half-done work. It alone sees the Clay hazard: "Merging `integration` in would make the release pull request carry Clay's unreleased work into `master`" (V1 Q3). I confirmed that mechanic today (E3), so V1 is right and V4 is wrong on X-003 and A-017. Its extras are real QA tools: the read-only trial merge with `git merge-tree` before every story merge (U-001), the path-claim comparison against open `integration` pull requests (U-003) and the per-story digest in the release PR body (U-002). V1 is also the most honest about its weak point: "nothing outside the coordinator's own local test run looks at the code until the end".

### V2 (trunk on `integration`, dark landing, short pull requests)
Strongest version: it has the best evidence base (DORA one-week batch limit, trunk-based two-day branches, Fowler on integration frequency) and the best failure story: "partial rollback is easy, which is the best rollback story of the three proposals" (V2 Q9; C-022). CI and both bots see every slice against the real `integration` ("the strongest guard", C-011), so semantic collisions show up at once. It needs no workflow edit and it is Clay's habit scaled up. This repository gives it real support: the observer work (#409) shipped as a sequence of pull requests titled "release 1" (#503) and "release 2" (#514) instead of one long branch (VERIFIED-TODAY, `git log origin/master --grep=409`), and the owner's sessions already land about 6 commits a day on `master` (E5), so "the owner clicks every slice" is not an impossible cost. V2 is also honest that its ledger problem is "the biggest process cost".

### V3 (release train, per-story PRs into a train branch cut from `integration`)
Strongest version: it keeps the batch isolation of V1 and the per-change CI and review of V2, with a time box where "the scope floats, the time does not" (U-010). It raises the three decisions that really are the owner's (merge authority, time box, whether to edit `test.yml`; U-012) instead of hiding them, and it proposes a throwaway test PR to check the CI filter and the Orca prefix before relying on either (U-013). It lands where Clay already lands (`integration`), so the existing promotion path is used. This repository's two releases so far (6.0.0 as #640, 6.1.0 as #664) both travelled `integration` to `master`, so V3 and V2 match the path the maintainers already walk (E4).

## 3. Strengths claimed
1. **The folder layout gives a ref-name rule that is checked, not hoped for (Q1, C-001).** V4 Q1: "`release/dash1.3` and `dash1.3/story/01-...` are in different folders, so git accepts both", and "(`release/proto-demo` and `proto-demo/feature/wizard-integration` both exist in GFxAI)". I re-tested it in a scratch repo (E1): `release/dash1.3`, `dash1.3/story/01-x`, `dash1.3/bugfix/02-y` and `hotfix/5-z` coexist, they also coexist under an `ironbelly/` prefix, and the two ways to break the rule fail loudly with git's own error (a bare `dash1.3` or a bare `release`). `git branch --list 'dash1.3/*'` lists a release's stories and fixes, and one pattern `release/**` names every release line for a CI filter, a ruleset or a clean-up script. Scope of the claim: flat names (V2, V3) are even safer against collisions; V4 wins on grouping and convention, not on robustness (see Concessions).
2. **Squash into the release line, merge commit into `master`: the one method pair that has already been shown to matter here (Q2, Q4, C-005, X-004).** The only branching incident in this repository's recent history is a merge-method mistake, not a size problem: release 6.1.0 was squash-merged as #658 and reverted ("squash-merged by mistake. The release is redone as a merge commit afterwards") by #662, then redone as #664 (E4). V4 states the method for both levels, with the reason ("so the release lands as one revertable unit and each story stays one commit"). Squashing the stories into a temporary line is safe because that line is deleted after landing and shares no history with `integration`. It also removes a revert trap that `--no-ff` has (E2): after `git revert -m 1` of a story merge, fixing the story branch and merging it again gives `CONFLICT (modify/delete)`, which under the worker contract stops the coordinator; with a squash commit the redo is a clean merge. V1 lists this exact trap as its risk 5 and marks it UNVERIFIED; I verified it.
3. **A cheap bisect and a plain revert unit (Q9, C-022).** One squash commit per story means a failing release can be bisected over N story commits (about 4 steps for 16 stories) and each is reverted with a plain `git revert <sha>`, no `-m 1` to remember. The story's own history stays in the ledger and the `.dev/` records, which V4 commits on the release branch.
4. **A freeze and an acceptance gate that the other three lack (C-016, U-018).** V4 Q6: "Beta freeze: when the release is in final testing, only critical fixes are allowed into the release branch", and Q4: full test tiers, two approvals and sign-off before the tag. At AI speed new stories keep arriving; a freeze is the only rule that makes "the release is being verified" mean something, and it is the compensating control for A-005 (green tests do not prove two stories do not collide semantically). It costs nothing: the coordinator owns the merge lane, so it can enforce the freeze by declining merges.
5. **Hotfix and landing rules that match what the maintainers already do (Q4, Q6, Q8).** V4 lands straight into `master` by a merge commit and then merges `master` back into `integration`. Clay's real practice is the same shape: five "merge master into integration" commits by clayphi between 2026-11-17 and 2026-11-19 (E4). V4 never branches a hotfix from a release ("Do NOT branch from release/*", source) and it does not touch Clay's `integration` habit while a release runs. This answers V1's own open point ("who syncs `master` into `integration` today is not stated"): a maintainer does, by hand.
6. **An explicit clean-up rule, which this repository needs more than the others admit (Q7, C-023).** The fork has "delete branch on merge" off (`delete_branch_on_merge: false`, E6) and 170 remote branches today. V2 and V3 rely on "Automatically delete head branches" (V2 section 3 step 4, V3 Q7) and both mark that setting UNVERIFIED; it is verified off, so a burst of 15 to 60 story pull requests leaves 15 to 60 stale branches unless someone deletes them. V4 is the only variant that took its clean-up rule from a real failure ("GFxAI left 6 `backup/...` branches and `release/v0.1` (0 ahead, 62 behind `master`)").
7. **Auditable provenance (S-002, U-014).** Every rule is tagged FROM SOURCE, FROM PRACTICE, MY ADAPTATION or UNSPECIFIED, so a reviewer can see in one pass which rules rest on evidence and which on invention. For a decision the owner has to sign, that is a QA property: it shows what is untested. V4 also lists what the source does not give ("What this proposal needs that the source does not give").
8. **Real long-lived-branch evidence, weighed both ways (C-021, U-015).** For the lesson: GFxAI `feat/OntRAG` merged `master` in twice (#129, #131) and still landed as #147 with 34 commits, 1,384 files, +242,976 lines and "file-level rejections", which is what a review does when it cannot read the whole diff. Against over-reading it: (a) that branch ran for months at human speed with no size cap; V4 asks for days-long stories and I accept V1's cap on top (Concessions); (b) this repository landed #640 (6.0.0, 1,146 files, +13,671/-189,325) and #664 (6.1.0, 181 files) as single pull requests and both stayed (E4), the failure was the merge click; (c) it is a sample of one repository that "mostly ignores" its own document. My reading: the lesson supports a size cap and a digest, not a ban on a release line.

## 4. Weaknesses identified in the others
Items marked (shared) also hit V4-with-named-changes; I list them so the comparison stays fair.

1. **V1: `--no-ff` story merges plant the revert-then-redo trap (C-005, C-022, U-005).** V1 Q9: "`git revert -m 1 <story merge commit>`" and its own risk 5 "A reverted merge cannot simply be merged again (unverified general git behaviour)". Verified today (E2): after the revert, fix the story branch and merge it again and git stops with `CONFLICT (modify/delete)`. Under the worker contract (CONTEXT line 9) a conflict stops the coordinator, so the commonest rollback path in V1 ends in a stop-and-report. V1 mitigates with "revert later stories in reverse order or fix forward"; it does not say how a reverted story is redone.
2. **V1: nothing is pushed until the release is complete (C-004; V1 section 1 "Nothing is pushed for review until the release is complete").** A release line that exists only in the coordinator's worktree for days is a single point of failure and invisible to the owner. A recently added tool removes finished worktrees (`feat(worktrees): remove finished git worktrees with /sc:worktrees ... (#711)`, commit 6b17a7449 on `master`); whether it can touch a worktree that holds unpushed release commits is UNVERIFIED, but the risk exists only because V1 keeps the line local. A forward-only push of the release branch after each story merge removes it and does not break "never rewrites a published branch". (This fix applies to V4 as well and I adopt it.)
3. **V1: no freeze or acceptance gate (C-016).** It has fix branches inside the release but no rule that stops new stories entering while the release is being verified; with serial local merges and no CI that window is where an unseen collision is merged last.
4. **V2: the ledger has no home and the release is not what the owner described (C-020, X-009; CONTEXT lines 7 and 14).** V2 Q7 itself: "This is a real mismatch and the biggest process cost of this proposal." The owner's model is one integration branch per release with story sub-branches; V2 removes the branch. A proposal that deletes the owner's stated structure needs the owner's explicit override, and V2 does not ask for it.
5. **V2 and V3: cut from `integration`, which is behind `master` today (C-002, X-001; VERIFIED-TODAY E4).** `git rev-list --left-right --count origin/master...origin/integration` prints `24 2`: `master` has 24 commits that `integration` lacks and `integration` has 2 that `master` lacks. A release line cut from `integration` starts with that gap and must merge it in before landing; maintainers already do this by hand ("chore: merge master into integration before wave 1", "... before wave 6"). V1 and V4 cut from `master`, the branch they land on, so the release line has no gap at birth (V4 must say so; it is silent, see Concessions).
6. **V2 and V3: the landing carries everything in `integration` (C-003, C-018, X-002, X-003).** V2 Q4: "the promotion carries Clay's merged work too. The dashboard release cannot be shipped without it, and Clay's unreleased work cannot be held back." V3 Q4 says the same. That makes the dashboard release hostage to any red change in `integration` (V2 risk 4, V3 risk 3) and puts a second full review over work that was already reviewed (V2 Q4: "mostly duplicated effort"). The owner's model says the release "merges to the default branch".
7. **V2: dark landing is unproven here and the cherry-pick rule has its own noise (C-012, C-015).** V2 Q5: "How practical flags are in this repository's dashboard code is UNVERIFIED". After the cut, "fix-only from then on, by cherry-pick": a cherry-pick plus a later merge of the same change is the classic duplicate-patch conflict. V2 does not say how it avoids it.
8. **V3: the CI story needs an edit that must land before the first story PR, and merge authority is unresolved (C-007, A-008, A-014, X-005).** `test.yml` (VERIFIED-TODAY, E7) triggers `pull_request` only for `branches: [master, integration]`. V3 needs `train/*` added and an owner decision on who clicks merge (its Open decision A); if the owner keeps clicking, "the train stalls behind the owner just as in Proposal 2" (V3 risk 1). V3 also moves BMAD planning to `integration` (X-009) and decouples "release done" from "on `master`" (V3 Q4: "the release is on `master` only when `integration` is promoted").
9. **V3: every story gets two bot reviews and then the roll-up gets two more (C-021, V3 risk 2).** At 15 to 60 pull requests per burst that is the highest bot and CI load of the four, for a roll-up V3 itself calls "mostly an integration check".
10. **(shared) V1 and V4: one large release PR (C-021).** I do not claim V4 solves it. V4 and V1 both rely on a story-count cap and a digest (V1 U-002) and on the release PR being the only review point; I take V1's mitigations (Concessions).
11. **(shared) V1 and V4: no CI before the release PR (C-007).** `test.yml` also has `workflow_dispatch:` (E7), so the coordinator could run the suite on a pushed release branch at any point without editing triggers (UNVERIFIED by me: not run, because it is a write to GitHub). That is a candidate mitigation for both, not a V4 advantage.

## 5. Concessions
1. **Pull request per story is indefensible here (C-004, C-007, X-008).** `test.yml` runs `pull_request` only for `master` and `integration` (E7), so a story PR into `release/dash1.3` gets no CI; each one needs its own top-level `/sc:pr-submit` session and two bot reviews; and V4's text contradicts itself (Q4 "CI and the two reviewers run once, at that point" against Q2 and the closing section). `gfxai-fit.md` named change 1 already replaces it with local squash merges by the coordinator. With that change V4 inherits V1's biggest weakness: no CI and no bot review until the release PR.
2. **Merging `integration` into the release is wrong (X-003, C-018, A-017).** Q3 says "merge, never rebase, `master` and `integration` into `release/dash1.3`" while Q8 says "a dashboard release does not pass through it". Both cannot hold; I tested the git mechanic (E3) and V1 is right. Drop it: merge `master` only, compare path claims with open `integration` pull requests at release start (V1 U-003), and merge `master` into `integration` after landing.
3. **Base branch not stated (X-001, C-002).** Cut `release/dash1.3` from `master`. This is what V4's own landing rule implies; it should have said so.
4. **Ledger and planning base not addressed (C-020, X-009).** Adopt V1: `sprint-status.yaml` and `.dev/` records on the release branch; BMAD planning of release n+1 starts from `master` after release n lands.
5. **Names: flat names are more robust, and V4 adds surface (C-001, A-007).** V2 and V3 use flat story names and have no folder rule to break. V4 has three levels (`ironbelly/dash1.3/story/01-slug` with the Orca prefix), and whether Orca and the new worktree clean-up tool cope with that depth is UNVERIFIED. Also, `hotfix/` and the word `bugfix` are new prefixes: this repository already uses `fix/`, `feature/`, `docs/` (VERIFIED-TODAY, `git branch -a`), so for shipped-code fixes use `fix/<issue>-<slug>` as V1, V2 and V3 do.
6. **"Cherry-pick or merge" for hotfixes is worse than V1's rule (C-015).** A cherry-pick into the release followed by merging `master` later duplicates the patch. V1's "the open release picks it up at the next merge-`master`-in" is simpler and correct for a line that merges back into `master`. Drop the cherry-pick option.
7. **No cap on how long the release line lives (C-013, X-006).** V4 says "keep stories short-lived" and keeps the source's "Weeks-months". That is a human-team number. Adopt V1's rule: days, not weeks; split the release if the line stays open longer than about a week; fall back to V3 if it keeps overrunning. I keep the release line because it is the owner's stated model (CONTEXT line 7) and holds the ledger.
8. **Squash loses story tips (C-005).** With `--no-ff` (V1) the story's own commits stay reachable as the second parent. With squash they live only in the story branch, which V4 deletes after the squash is recorded. The cost is real for fine-grained blame and bisect inside a story. I judge it smaller than the revert-then-redo trap (E2) because stories are small and the ledger and `.dev/` records stay, but it is the owner's call.
9. **Source rules that do not transfer (S-005).** Two approvers, Tier 1/2/3, five environments, "owner may force-push", "feature branch equals whole feature" (`gfxai-fit.md` "Parts of the source that do NOT fit"). The source says nothing about worktrees, a coordinator, serial merges or disjoint paths, so every parallel-AI rule in V4 is my adaptation (F5, A-001, A-002 are mine).
10. **Pedigree.** The document was never reviewed or applied by its own repository (status "To Do", "Pending team review"). I do not ask the debate to weigh it as precedent.
