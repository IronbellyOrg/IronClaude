# Round 1 advocate statement: Variant 2 (trunk on `integration`, flat story branches, dark landing, release is a cut and a promotion)

Persona: analyzer (evidence quality, logical consistency, flow metrics). Written 2026-11-23. Sources: `CONTEXT.md`, `adversarial/variant-1-original.md` to `variant-4-original.md`, `adversarial/diff-analysis.md`. Evidence IDs (S1 and so on) are the ones the variants cite from `research-notes.md`; I did not re-read that file, so I only reuse an S-ID where a variant states what it says. Anything I could not confirm is marked UNVERIFIED.

## Position summary
Variant 2 is the only proposal in which every unit of AI work is checked by CI and both automatic reviewers against the real shared line, on a small diff, with no workflow edit, no new merge authority and no long-lived branch to keep current. Its price is real and I state it: the owner clicks merge on every slice, and the ledger convention in CONTEXT line 14 has no branch to live on. I claim it wins on CI and review fit, collision detection latency, rollback granularity, ref-name robustness and flow, and I concede it loses on owner effort, the ledger, and isolation from Clay's unreleased work.

## Steelman of each opposing variant
### Variant 1 (release line, local merges, one PR at the end), strongest version
V1 is the owner's own model made precise (CONTEXT line 7), and it is the only variant that changes nothing: no workflow edit, no repository setting, no new merge authority, ledger and worker contract intact (V1 section 6). The owner makes one merge decision per release, which is the lowest owner load of all four. A release reaches `master` whole or not at all, so `master` never carries half a release. Its merge-commit-per-story (`--no-ff`) keeps a story boundary, so `git revert -m 1` removes a whole story (V1 Q2, Q9). Its read-only `git merge-tree` trial merge (U-001) is a cheap pre-merge guard nobody else has, and its path-claim comparison against open `integration` PRs (U-003) is a good early warning for Clay collisions. It keeps Clay's unreleased work out of the release PR (C-018, X-003), and V1 is honest about its own weak point (V1 section 1: "nothing outside the coordinator's own local test run looks at the code until the end"). If the owner's merge capacity is the real constraint (A-003), V1 is the one that respects it.

### Variant 3 (release train, PR-gated batch), strongest version
V3 is the best of the three alternatives because it keeps the owner's batch idea and still gives each story CI and both reviewers on a small diff (V3 section 1). It keeps the ledger and `.dev/` records on a branch (C-020), so CONTEXT line 14 is unchanged. Its time-boxed train with floating scope (U-010: "the scope floats, the time does not") is a cleaner answer to unfinished work than flags: a story that is not ready is not in the train, instead of being in and hidden. The `dash1.3-sync<N>` branch (U-011) lets a worker resolve a train-versus-`integration` conflict through the normal PR gate, the explicit "Open decisions" A, B and C (U-012) push the real choices to the owner, and the throwaway test PR to check the CI filter and the Orca prefix (U-013) is the right validation habit. It also lands on `integration`, which is Clay's lane and the repository's documented testing step.

### Variant 4 (GFxAI approach adapted), strongest version
V4 is the only variant with evidence from the owner's own organisation, and it labels every rule FROM SOURCE, FROM PRACTICE, MY ADAPTATION or UNSPECIFIED (U-014), so a reader can audit it line by line. Its real-history evidence (U-015) is valuable: PR #147 with 34 commits, 1,384 files and +242,976 lines merged "with file-level rejections", six stale `backup/...` branches, a stale `release/v0.1`. It carries an explicit source rule that AI agents have no merge right ("AI Agent: Merge to Main no", U-017), a full release gate (Tier 1+2+3 tests, two approvals, sign-off; U-018), a beta freeze, and a separate `hotfix/` prefix. It is the only variant that ships a decided approach already in use at the organisation, which lowers adoption friction if the team already knows it.

## Strengths claimed
1. **Every unit of work gets CI and both reviewers, against the real shared line, with zero configuration change (C-007).** CONTEXT line 11: CI runs only for PRs and pushes into `master` and `integration`. V2 opens each slice with `--base integration`, so the existing trigger already fires (V2 Q2: "CI on every slice runs against the real `integration`"; C-007 row: "no workflow edit"). V1 gets no CI before the end. V3 and V4 need `train/*` or `release/**` added to `test.yml` (C-007, A-008, A-013, V3 Open decision C). So V2 is the only variant that has per-change feedback with nothing to approve, schedule or get wrong first.
2. **The CI trigger cannot be silently disabled by the Orca prefix.** V3 risk 5 names the failure: a wrong pattern in the filter "leaves story pull requests with no CI while everyone assumes they have it", and A-011 notes that all four variants leave the Orca `--branch` prefix UNVERIFIED. The `pull_request` `branches` filter matches the base branch (S11 as V3 cites it), and V2's base is always `integration`, so whatever name Orca gives the head branch, the filter still matches. This is a logical-consistency argument: V2 removes a precondition the others carry.
3. **Shortest collision-detection latency (C-011).** V1: a semantic collision that merges cleanly is caught only by the coordinator's local suite after each merge (V1 Q2 prevention (c): "the only thing that catches"). V3: "one story later at worst", and Clay collisions only at merge-in or train PR time (V3 Q8). V4: coordinator merges one at a time, no stated automated guard. V2: the slice's own PR is tested against the real `integration` tip including Clay's merged work, so the collision shows as a red check on the PR that causes it. The test suite behind this is the same one V1 runs locally (see A-005), so V2 is no weaker on signal and strictly earlier and independent of the coordinator's machine.
4. **Finest rollback unit and cheapest rollback (C-005, C-022, Q9).** One slice is one squash commit, so a revert PR undoes exactly that slice, or the flag turns it off. V1 and V3 can only revert a whole story (`-m 1`) or the whole release; V4 reverts a story squash or the whole release. V2 also has the fastest path to a clean `master`: the release cut is a short fix-only branch, so a failing release is fixed by cherry-pick and re-promoted, or the dark feature is switched off, without reverting the roll-up. The cost (a story spans several commits) is conceded below.
5. **Ref-name robustness by construction (C-001).** A flat name `dash1.3-s04-x` is a leaf with no folder part, so it cannot collide with `dash1.3-s05-y`, with `release/dash1.3`, or with a hand-created `dash1.3`, because `-` is not a path separator (V2 section 2). V1 states its own residual risk: "a prefix surprise could break the leaf rule if someone creates `dash1.3` by hand" (V1 risk 4). V4 depends on the release folder `release/` differing from the release-name folder `dash1.3/`, and a stray `dash1.3` branch breaks all three-level story names. V2 and V3 share the flat story shape, but V2 has no long-lived parent ref at all, so there is nothing for a tool or a human to name wrongly.
6. **Smallest batch, shortest lead time, no accumulating work-in-progress (flow metrics, C-013, C-021).** In V1 every finished story waits for the whole release before anything outside the coordinator sees it; lead time per story equals release length, and V1 itself admits "Review-size risk is the highest" (V1 section 5) and that its own strongest evidence (S6, S19) "points against it" (V1 risk 1). V4 repeats the pattern and its own evidence is the 1,384-file PR #147. V2's slices are "hours to a couple of days" (V2 section 3 step 1), consistent with the two-day trunk-based norm (S1), DORA's one-week batch ceiling and its AI small-batch countermeasure (S6), Fowler's integration-frequency argument (S8). Caveat on evidence quality: S19 (Faros) is vendor data, and V2 itself says so (V2 section 8); S6 and S1 carry the weight.
7. **No serial coordinator lane in the merge path (A-002, A-004, C-010).** V1, V3 (if decision A is yes) and V4 all route story merges through the coordinator, serially, and stop on every conflict. V2: "The coordinator never merges in this model, so it never has to stop on a conflict; it assigns the fix to the worker" (V2 Q2). CI runs in parallel across open slice PRs, whereas V1's full local suite after each merge is a serial step in one lane (A-010). Parallelism is then limited by disjoint paths and owner capacity, not by one session.
8. **Respects the standing rules without negotiating any of them.** "Nothing is merged by an agent" (CONTEXT line 11) is kept as written; `/sc:pr-submit` is used for every PR as the repository requires; no rebase of a published branch (V2 section 3 step 3); no change to CI config. V3 asks the owner to relax the merge rule (A-014, Open decision A); V4 does the same by adaptation (C-006, X-005).
9. **Release is a decision, not a branch (C-002, C-008, C-013).** There is no long-lived line to merge `master` into at three points (V1 Q3) or `integration` into repeatedly ("the main weekly cost of this proposal", V3 Q3). Drift exposure is per slice, measured in hours, and the release cut lives "days at most" (V2 Q3). This removes the housekeeping class of work that the other three each carry.
10. **Uses the documented flow.** CLAUDE.md "Git Workflow": `master` (production) <- `integration` (testing) <- `feature/*`. V2 puts work through `integration` and promotes out of it. V1 and V4 bypass the testing branch for the dashboard (C-003, V1 Q8, V4 Q8), then must sync `master` back, which V1 flags as late collision discovery ("the collision shows up in that sync pull request, late").
11. **Honest unknowns with a first test attached (U-009).** V2 marks dark-landing practicality UNVERIFIED and says to pilot it on one story first (V2 Q5). V3's throwaway PR (U-013) is a compatible add-on and I would take it.

## Weaknesses identified in the others
### Against Variant 1
1. **Isolation is deferred, not removed (C-018, X-003, C-003).** V1 keeps Clay's unreleased work out of the release PR, but then must open the `master` into `integration` sync PR, and "the collision shows up in that sync pull request, late" (V1 Q8). The collision with Clay's work still happens; it happens after the release has landed on `master`, where it is most expensive. V2 pays the same coupling at the slice PR, where one small diff is the whole problem.
2. **Quality gate is one machine and one person until the end (C-007, C-011).** V1 Q2: no CI and no automatic reviewers per story; "the full local test run after each merge is the only thing that catches a semantic collision". That is the coordinator's own run, serial, and unreviewed. V1 section 5 lists the cost itself: "Semantic breakage between stories can sit for the length of the release."
3. **One large PR at the end (C-021, A-003).** V1 Q4 names the risk and proposes a story-count cap, a generated digest (U-002) and a split after about a week; the one-week figure is "extrapolated ... not a DORA figure for release branches". The digest helps the owner read, but it does not reduce what Augment and Codex must analyse at once, and V4's PR #147 with "file-level rejections" is the real-history failure of exactly this shape (U-015). A single owner click on a very large diff is also a weaker control than many small clicks, because review depth falls with size (S19, vendor data; treat as a signal, not proof).
4. **Self-conditional justification (C-013, X-006).** V1 Q5: "This proposal only holds if release branches stay days, not weeks. If they do not, switch to Proposal 3." A proposal that names its own fallback trigger concedes the central risk: AI authoring is fast and the human final review is not (A-016, V1 risk 3).
5. **Local merges leave no reviewable record outside the ledger (V1 section 5, risk 6).** "If the owner later wants an early look at a story, there is no pull request to review it in." The two automatic reviewers, which CONTEXT line 11 treats as part of the process, never see a story on its own.
6. **Merge-in housekeeping and a rebase-forbidden long line (C-008, C-009).** Three `master` merge-ins and a "never rebase after the first story branch was cut" rule are the overhead of keeping a line alive; V2 has no such line.

### Against Variant 3
7. **It needs a workflow edit and a prefix check that V2 does not (C-007, A-008, A-011, A-013).** V3 section 5: "This is outside the current 'CI only for master and integration' state and needs the owner's approval". V3 risk 5 is the silent-failure case. V2 has neither the approval request nor the silent failure.
8. **It needs a merge-authority decision to be useful (X-005, A-014, C-006).** V3 Q2: "this proposal works best if the owner allows the coordinator to merge story pull requests into a `train/*` branch only". V3 risk 1: "if the owner insists on clicking every story merge, the train stalls behind the owner just as in Proposal 2." So under the standing rule V3 has V2's owner load plus a train PR plus a roll-up review, and only under a relaxed rule does it beat V2 on owner effort. V3 states this itself, so it is not a rhetorical point.
9. **The train inherits `integration`'s state at the cut and drifts afterwards (C-002, C-008).** V3 risk 3: "A train branch cut from `integration` inherits whatever red or half-done work `integration` has at the cut." V3 Q3: the merge-in is "the main weekly cost". It also has to move BMAD planning to `integration` (X-009, V3 Q8). V2 runs the same cut but only for days and only at the end, after the switch-on slice has merged.
10. **Clay collisions surface later than in V2 (C-011).** V3 Q8: found "at merge-in time or at train-pull-request time". V2: at the slice PR.
11. **Stacking is weak and unusable under current CI (C-025, X-010).** V3 step 3 concedes "CI does not run on a pull request whose base is a story branch ... so stack only where the lower story merges within hours; otherwise wait." V2 simply does not stack, which is the same constraint stated as a rule instead of an optional feature that CI cannot check.
12. **A train is a long-lived branch with a time box the owner has not chosen (C-013, Open decision B).** V3 Q5: "the research gives no AI-specific number". The unresolved time box is a free parameter that decides whether V3 behaves like V1 or like V2, so its position on the spectrum is not testable until it is chosen.

### Against Variant 4
13. **Internal contradictions (X-003, X-008, A-017).** V4 Q8 says "a dashboard release does not pass through [`integration`]" yet Q3 merges `integration` into `release/dash1.3`. The merge makes the release PR carry Clay's unreleased work into `master`, which V1 states explicitly as the reason not to merge it in. And V4 Q4 says "CI and the two reviewers run once, at that point" while Q2 and the closing section add per-story-PR tests and a `release/**` CI trigger. A proposal that disagrees with itself on when its gates run cannot be evaluated on its stated flow.
14. **The "decided approach" is mostly adaptation.** By V4's own marks, the source gives no rule for Q3 (UNSPECIFIED), the justification in Q5 (UNSPECIFIED), Q7 (rest is MY ADAPTATION), Q8 (adaptation, source silent) or Q9 (UNSPECIFIED, "The source has no rollback rule"), and V4 replaces the source's rebase-only rule and merge-right rule in Q2. What is FROM SOURCE is the naming and the squash-into-release shape. Validation of the source against this repository is therefore thin.
15. **The source is a draft and its practice evidence is cautionary (U-015).** V4's header: the Git standards file is "a draft marked 'Pending team review'" (2025-12-11, version 1.0). The practice evidence V4 cites is a 1,384-file release PR merged "with file-level rejections", a long-lived branch needing two "merge main in" PRs, and stale branches. That evidence argues against the long-lived release branch, which is V2's side of C-013.
16. **Needs the same `test.yml` edit as V3 (C-007, A-008) and has no rollback rule (C-022).** V4 Q9 is entirely MY ADAPTATION or UNSPECIFIED.
17. **Whole release in one PR again (C-021).** V4 Q4 and the PR #147 warning describe V1's review-size problem, so critique 3 applies.

### Shared point
18. **Revert-then-re-merge is an unverified trap in V1 and V3 (C-022).** Both flag "Re-merging a branch whose merge was reverted needs the revert to be reverted first" as UNVERIFIED (V1 risk 5, V3 Q9). V2's rollback does not depend on re-merging a reverted branch: it fixes forward, flips the flag, or re-cuts. I do not claim a win on squash versus merge commit itself (X-004, A-006): no variant checked the repository's merge-method settings.

## Concessions
I do not defend these.

1. **Owner merge load (A-003, C-006).** V2 section 5: "the heaviest merge load of the three". Every slice needs an owner click, and CONTEXT line 11 rules out agent merges. The only mitigating fact is CONTEXT line 16: bursts of 15 to 60 AI-made PRs "are normal here", so this is the current load class, not a new one. But no variant, mine included, has a per-day capacity figure, so I cannot claim the owner can sustain it. Most likely failure (V2 risk 1): a queue of ready slices waiting for the owner. Cheapest test: measure owner time-to-merge on the first release's slices.
2. **The ledger has no home (C-020, X-009).** V1 and V3 keep `sprint-status.yaml` and `.dev/` records on the release or train branch (CONTEXT line 14); V2 does not, and says so ("the biggest process cost"). V2 is not allowed to claim a win on C-020. One candidate fix, labelled my proposal and UNVERIFIED against the BMAD tooling: keep one small record file per slice inside that slice's own PR, so the coordinator's ledger is a view derived at the release cut instead of a file written on a branch.
3. **Isolation from Clay (C-018, X-003).** V1 keeps Clay's unreleased work out of the dashboard release; V2 cannot ship the dashboard without it ("a bad Clay change blocks the release", V2 risk 4), and an `integration` that goes red from someone else's merge stalls every slice (V2 risk 3). If the owner prizes a release independent of Clay's cadence, V1 wins this point.
4. **Dark landing is unproven in this codebase (U-009, C-012).** Flags or branch-by-abstraction may not fit dashboard stories that change existing behaviour, and flags create debt (V2 risk 6, U-008). V3's "not in the train" answer (U-010) avoids both problems for a story that cannot land dark, at the price of a long-lived branch. If the first pilot shows most stories cannot land dark, V3 beats V2 for those stories.
5. **Duplicated second review at promotion (C-021).** V2 Q4: "the second review is mostly duplicated effort (cost)". V3 pays the same. Only V1 and V4 avoid it, by deferring all review to the end.
6. **Story-level revert is more work (C-005).** One story is k slice commits in V2, so reverting a whole story is k reverts, where V1 and V3 do one `git revert -m 1`. I counter only by labelling slice commits with the story id so they are findable; that is reasoning, not a tested workflow.
7. **Planning base for release n+1 is not stated in V2 (X-009).** V1 keeps it; V3 flags it as needing a change; V2 is silent. A gap in V2, to be closed in the merge.
8. **Merge-method and branch-deletion settings are unchecked (A-006).** Squash enabled and GitHub auto-delete of head branches (S12) are both UNVERIFIED in V2 (and V3).
9. **Per-slice cost.** More CI minutes and more review events per release than V1 (V2 section 5). V2's case is that this buys earlier detection and smaller reviews; the cost itself is real.

## Which diff points I say I win and why
### Wins I claim
- **C-007 (pre-merge CI and reviewer coverage per change):** per-slice CI and both reviewers with no workflow edit; V1 has none, V3 and V4 need the edit. Strength 1.
- **C-011 (collision control and detection latency):** the collision shows on the causing PR against the real `integration`. Strength 3.
- **C-008 (keeping the batch line current):** no long-lived line; drift per slice is hours; the `master` into `integration` sync is the only housekeeping. Strength 9.
- **C-010 (conflict procedure):** the coordinator is out of the merge path, so there is nothing to stop and report. Strength 7.
- **C-005 and C-022 (merge method and rollback state):** one squash commit per slice is the finest undo, with flag-off for dark features. I concede the whole-story `-m 1` convenience to V1 and V3 (concession 6), so I claim the win on granularity and on avoiding the revert-then-re-merge trap (shared point 18), not on whole-story revert.
- **C-001 (ref-namespace invariant):** a narrow win on robustness: no parent ref exists to be created wrongly. All four are valid names today, so this is a tie on correctness and a win on resilience (Strength 5).
- **C-013 and X-006 (justification of a long-lived release line):** V1 and V3 each state a time-box condition under which they fail, V4 gives none, and V4's own practice evidence (PR #147, two "merge main in" PRs) argues against long-lived lines.
- **C-003 (landing path):** V2 and V3 use the documented `integration` to `master` flow of CLAUDE.md; V1 and V4 bypass it and need a late sync. A win over V1 and V4, a tie with V3.
- **X-001 (base branch of the release line):** V2's cut from `integration` agrees with the documented flow; V1's `master` base is the cause of its late Clay sync.
- **X-003 and A-017:** V1 and V2 are consistent with each other and with git mechanics, V4 is not. I win against V4 and tie with V1, with V1 holding the isolation advantage (concession 3).
- **X-007 (rebase before first push):** tie with V4; V1 and V3 are stricter, and V2's narrow allowance is safe because nobody has branched from an unpushed slice.
- **X-008 (V4's internal CI timing contradiction):** a win by default; V2 has no internal contradiction of this type.
- **X-010 (stacked PRs):** V2's "do not stack" is the consistent consequence of CONTEXT line 11; V3's optional stack cannot be checked by CI.
- **U-006 (slice classification in the spec) and U-007 (just-in-time cut, fix-only after):** unique to V2 and the basis for dark landing and cheap rollback; I claim both as contributions a merge should keep. **U-008 (flag retirement)** and **U-009 (pilot first)** likewise, with U-009 extended by V3's U-013 throwaway PR check.

### Points I concede or share
- **C-006 / X-005 (merge guard):** V1 wins on owner effort; V3 and V4 propose a relaxation; V2 wins only on rule consistency.
- **C-012 (incomplete-work isolation):** V1 and V3 beat V2 on certainty of isolation (the branch itself, or "not in the train"); V2 wins only on speed. Open until the dark-landing pilot.
- **C-018 / X-003 (Clay coupling):** V1 wins.
- **C-020 / X-009 (ledger and planning base):** V1 wins; V3 second; V2 loses.
