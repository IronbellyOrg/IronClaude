# Round 1 advocate statement: Variant 3 (release train, PR-gated batch)

Persona: backend (data integrity, scalability, fault tolerance, CI). Written 2026-11-23. Variants are cited as V1 (release line), V2 (trunk, dark landing), V3 (train), V4 (GFxAI adapted). Diff ids come from `diff-analysis.md`. Anything I could not confirm is marked UNVERIFIED.

## Position summary
V3 is the only variant that keeps the owner's batch (nothing half-built reaches shared branches) while giving every story an outside check (CI plus Augment plus Codex) against the real batch tip, and it contains the cost of a failure to a private branch (`train/*`) instead of the shared trunk (V2) or an unchecked local branch (V1). Its price is real and I state it: one `test.yml` edit, a merge-authority decision (Open decision A), and a double review at the roll-up. V4 is closest to V3 but is V3 without the parts that make it internally consistent (C-007, X-003, X-008, A-017).

## Steelman of each opposing variant
### V1 (release line, local merges), strongest version
V1 is the owner's own model, made exact, and it asks the least of the repository. It needs no workflow edit, no new merge-authority rule, no change to the BMAD planning base (C-020: ledger and `.dev/` land on `master` with the release), and no `master` into `integration` back-port inside the release (C-015: the release merges into `master`, so a `fix/` from `master` just arrives at the next merge-in). It keeps Clay's unreleased `integration` work out of the release PR on purpose (X-003: "Merging `integration` in would make the release pull request carry Clay's unreleased work into `master`"). It also brings two guards V3 lacks: the read-only trial merge with `git merge-tree` before every story merge (U-001) and a generated per-story digest in the release PR body (U-002). It is honest about its limit: "Review-size risk is the highest of the three proposals" and "only if release branches stay days, not weeks". On a quiet, two-story release with a fast local suite it is the least machinery that works.

### V2 (trunk on `integration`, dark landing), strongest version
V2 has the best evidence base: trunk-based sources (S1, S2), DORA small batches (S6), and Fowler on integration frequency (S8) all point at it. Collisions show at once in CI against the real `integration` ("the strongest guard of the three", C-011). It needs no long-lived branch and no workflow edit (C-007). It has the finest rollback: one squash commit or one flag flip (C-022: "the best rollback story"). It matches Clay's habit exactly (Q8) and removes the sync-lag problem V1 has. Slicing stories into PR-sized pieces with a switch-on slice (U-006) is the real trunk-based discipline and the only variant that takes it seriously. It names its own costs honestly, including that the ledger convention does not fit (C-020).

### V4 (GFxAI adapted), strongest version
V4 is the only variant grounded in a decided approach from the owner's own organisation, with provenance marks per rule (U-014) so every line is auditable as FROM SOURCE, FROM PRACTICE or MY ADAPTATION. Its names are collision-proof by folder separation (`release/dash1.3` versus `dash1.3/story/01-...`), and GFxAI really has both shapes alive (C-001). Its real-history evidence (U-015: PR #147, 1,384 files, +242,976 lines, "file-level rejections"; six stale `backup/...` branches) is the best empirical warning against big-batch landing. It carries an AI-agent no-merge-right guard (U-017) and a full-tier release gate (U-018). Squash into the release gives a plain one-commit revert per story and avoids the revert-the-revert trap that merge commits have.

## Strengths claimed
1. **Every story is checked against the real batch tip by something outside the coordinator (C-004, C-007, C-011).** V3 Q2: "CI on every story pull request runs against the real train tip, so a semantic collision shows as a red check on the next story's pull request, one story later at worst." V1's only guard is the coordinator's own local run, which V1 itself calls "the only thing that catches a semantic collision that merges cleanly" (Q2c). Detection latency for two colliding AI stories is one merge in V3, the whole release in V1.
2. **Bulkhead for merge authority and for breakage (C-006, X-005).** V3 asks the owner to relax "owner merges every PR" only for pull requests into `train/*`, a private branch no other maintainer builds on, and only after CI is green and both reviewers have settled (Q2). The owner keeps the single click that puts code on a shared branch (train PR into `integration`). V2 would need the same relaxation on the shared trunk that Clay branches from, a much larger blast radius; without it V2 leaves the owner clicking every slice (CONTEXT line 16: 15 to 60 PRs in a few days). The same bulkhead isolates the batch from a red `integration`: V2 risk 3 ("`integration` can go red because of someone else's merge, stalling all slices") does not stall a train, because V3 chooses when to merge `integration` in.
3. **A collision with Clay is found before anything reaches `master` (C-003, C-018, Q8).** V3: "A collision with Clay's work is found at merge-in time or at train-pull-request time, in CI, and resolved by a worker; it is never deferred to a later `master` sync." V1's own Q8 admits the collision "shows up in that sync pull request, late", after the release is already on `master`, which CLAUDE.md calls production. V3 fails in a place where rollback is cheap (a private branch or `integration`), V1 fails after the release landed.
4. **Self-consistent with every fact in CONTEXT.md.** Merge not rebase (X-007), no folder/leaf clash (two shapes only), `/sc:pr-submit --base` for both story and train PRs, conflicts resolved by a worker never by the coordinator (CONTEXT line 9), and a named route for the one conflict nobody else routes: train versus `integration` goes to a `dash1.3-sync<N>` branch through the normal PR gate (U-011, C-010). V4 breaks itself in three places (X-003, X-008, C-002), see Weaknesses.
5. **Batch size is bounded by time, so no flags and no flag debt (C-012, C-013, U-010).** "The scope floats, the time does not." An unready story is "not in the train", which is a state the branch graph records, not a runtime flag that must be designed, tested in both positions and retired. V2 concedes flag practicality in the dashboard code is UNVERIFIED (U-009). V3 also gives the only explicit exit ladder: V1 says fall back to V3 if the branch lives more than days, V3 says fall back to V2 if trains routinely overrun. V3 is the middle rung both neighbours already point to, which makes it the reversible choice.
6. **Layered rollback with preserved story boundaries (C-005, C-022).** Merge commits mean three revert levels: one story out of the train (`git revert -m 1`), one train out of `integration` (single merge commit), the promotion out of `master`. Story tips stay reachable as second parents, so a landed train can still shed one story. "Prefer a fix train" over re-merge avoids the reverted-merge trap (UNVERIFIED general git behaviour, flagged in V3 Q9).
7. **Small-diff review load with a stated cost (C-021).** Each story is reviewed small, which is what S6 (DORA) and S19 (Faros) support; the roll-up is "mostly an integration check". V1 and V4 both put the whole release in one review. V4 even cites its own 1,384-file PR as the failure mode and then adopts the same landing shape.
8. **Fail-safe validation of its own riskiest assumption (U-013, risk 5, A-008, A-011).** V3 is the only variant that says: open one throwaway test PR first, because a wrong branch filter (Orca `ironbelly/` prefix) leaves story PRs with no CI "while everyone assumes they have it". Silent absence of a gate is the worst CI failure mode; V4 prescribes `release/**` with no equivalent check.
9. **Ledger and `.dev/` records stay on the batch branch (C-020).** CONTEXT line 14 holds for V3 (only the BMAD planning base moves, X-009, which I price below). V2 has no branch to hold the ledger and calls it "the biggest process cost".
10. **Explicit decision interface (U-012).** Open decisions A, B, C name exactly what the owner must rule on (merge authority, time box, `test.yml` edit). The other variants bury the same decisions inside prose (V4 lists "a rule for who may merge" as a gap).

## Weaknesses identified in the others
**V1**
1. **No external gate and no durable state until the end (C-004, C-007, A-005).** V1 Summary: "Nothing is pushed for review until the release is complete." As written, every merged story lives only in the coordinator's local worktree and the ledger; V1 Cost list says "Local-only merges are invisible on GitHub; the ledger is the only record of who merged what and when." Worktrees do get archived and removed (an untracked `.dev/worktree-archives/` shows in the current git status). V1 gives no backup-push step, so a lost or reset coordinator worktree loses the release, and the first outside check is the one large PR. V3 puts every merged story on GitHub, behind a check, with a PR record.
2. **Big-batch landing is V1's own named top risk (C-021).** V1 risks 1: "the strongest evidence in the research (S6, S19) points against it", and V1 Q5 says it only holds "if release branches stay days, not weeks", else "switch to Proposal 3". V1 is a weaker V3 by its own admission.
3. **It does not remove the Clay coupling, it moves it after the release is on `master` (C-018, X-003).** Avoiding `integration` is defensible, but V1 Q8 concedes collisions arrive "late" at the `master` into `integration` sync PR, and A-015 says who runs that sync is UNVERIFIED. The collision lands first on production and then on Clay's open branches.
4. **Reverts of dependent stories are manual (U-005).** "revert them in reverse order or fix forward" has no CI backing: each revert is again a local-only merge.

**V2**
5. **The owner is the throughput limit (C-006, A-003).** V2 Q2: "The merge is the owner's button, not the coordinator's." V2 cost 1 itself calls this "the heaviest merge load of the three" against bursts of 15 to 60 PRs (CONTEXT line 16). A single human serial lane at the head of the pipeline caps flow no matter how fast agents write. V3 turns that into one owner click per train once Decision A is yes.
6. **Half-built work sits on a shared branch that anyone can promote (C-012, C-018).** The existing `integration` to `master` promotion is a decision Clay can also make. In V2 any dashboard slice that is "flagged" or "dark" is in `integration` the moment it merges, so one wrong default or one dark-by-construction slice that is not really dark ships at a time the dashboard release did not choose. In V3 nothing from the release is in `integration` until the train lands, so there is no half-state to ship by accident.
7. **Dark landing is unproven here and costs state (C-012, U-009).** V2 Q5: "How practical flags are in this repository's dashboard code is UNVERIFIED." Every flag doubles the state space that tests must cover and adds debt to retire (U-008, S20). V3 gets the same isolation from the branch graph.
8. **No home for the ledger (C-020).** V2 Q7: "This is a real mismatch and the biggest process cost of this proposal": each ledger write becomes a PR into `integration`, which at 15 to 60 PRs per burst adds noise to the shared trunk.
9. **Squash plus per-slice PRs make the dashboard's history inseparable from Clay's (C-005).** A release revert in V2 cannot take out "the dashboard release" as one object, since there is no object; it can only revert a list of squash commits interleaved with Clay's.

**V4**
10. **It contradicts itself on integration (X-003, A-017, C-018).** Q8: "a dashboard release does not pass through it" and Q4 "Not through `integration`", yet Q3 merges `integration` into `release/dash1.3`. Git mechanics: once `integration` is merged into the release branch, the PR to `master` includes every commit of Clay's that is on `integration` and not on `master`. V4 therefore ships Clay's unreleased work to `master` without passing the `integration` to `master` promotion gate it claims to avoid. V3 admits the same coupling ("that promotion carries Clay's merged work too") and designs for it; V4 does not see it.
11. **It contradicts itself on when CI runs (X-008, C-007).** Q4: "CI and the two reviewers run once, at that point" versus Q2: story PRs get "the tests for that level and at least one review", and the closing section adds `release/**` to the PR trigger. Which is it? A backend reader cannot tell whether story PRs have CI.
12. **The base of the release line is undefined (C-002, X-001).** Q1 and Q3 never say what `release/dash1.3` is cut from. That decides whether the first merge-in is a no-op or a large conflict.
13. **No rollback, no conflict-prevention design, no cleanup rule from the source (C-022, C-023, C-011).** Q9: "The source has no rollback rule." Q2 prevention is "MY ADAPTATION" (disjoint paths), Q3 is "UNSPECIFIED", Q5 is "UNSPECIFIED", Q7 invents its rule. For the questions that matter most for AI parallelism (Q2, Q3, Q5, Q9), the GFxAI source gives nothing, so the "validated by a real approach" strength applies mostly to naming and merge method. The source is also a draft ("Pending team review") for whole-feature branches ("NOT = One task or one user story", C-014) and a rebase-only policy that clashes with `/sc:pr-submit` (C-009).
14. **It adopts the landing shape its own evidence condemns (C-021).** The 242,976-line PR #147 was a release-sized landing "with file-level rejections", and V4 still lands one whole-release PR into `master` with full tiers and two approvals (U-018). The gate is strong, the unit is too big to review.

## Concessions
1. **Decision A is a hard dependency.** If the owner will not let the coordinator merge into `train/*`, V3 stalls behind the owner exactly like V2 (V3 risk 1). V3 is not better than V2 on throughput without it.
2. **Double review.** Each change is reviewed by both bots at the story PR and again, as a roll-up, at the train PR (V3 cost 2, risk 2). Whether the roll-up pass is mostly noise is UNVERIFIED. V1 pays once; V2 pays twice as well (promotion).
3. **Clay coupling is accepted, not avoided (C-018).** V1 is right that avoiding `integration` keeps Clay's unreleased work out of the dashboard release. V3 ships the dashboard only when `integration` is promoted, with Clay's merged work in it, and inherits any red or half-done state at the cut (V3 risk 3, 4).
4. **Merge-in load against a fast-moving `integration` is V3's main weekly cost** (Q3). With one serial lane and no merge queue (S4), each waiting story must take the new train tip and re-run CI before its merge, so CI runs grow with the number of waiting stories. This is fine at two stories and degrades beyond about four (see A-004).
5. **`master` first fixes need a back-port (C-015).** V1 needs none because the release merges into `master`. V3 must carry the `master` into `integration` sync in the fix's definition of done (C-019).
6. **BMAD planning base moves from `master` to `integration` (X-009, C-020).** V1 keeps CONTEXT line 14 intact; V3 changes it.
7. **Squash is simpler to re-merge (C-005).** After a revert, re-merging a squash-landed story is a normal new squash; a reverted merge commit needs the revert reverted first. V2 and V4 win this narrow point. V3's fix-train rule is a workaround, not parity.
8. **V2 has the stronger published evidence base and the finest rollback (C-022).** Flag off is faster than any revert.
9. **Flat story names group worse than V1's sibling layout (U-004, C-001).** `git branch --list 'dash1.3-*'` works, but a folder view in tools does not.
10. **Per-story `/sc:pr-submit` sessions are costly.** It must run in its own top-level session in the story's worktree, so V3 needs one top-level session per story where V1 needs one per release. That is a coordinator cost I did not price in the original.
11. **Things to adopt from others.** V1's read-only `git merge-tree` trial merge before each story merge (U-001) and per-story digest in the roll-up PR body (U-002); V4's provenance habit (U-014), explicit stale-branch cleanup rule (C-023, U-015: V3 depends on the UNVERIFIED auto-delete setting S12), and V4's no-merge-right framing (U-017) as the explicit wording of what Decision A relaxes and for which branch only.
12. **Open items I cannot confirm.** Reviewer behaviour on `train/*` bases (A-012); the workflow-file version GitHub reads for `pull_request` (the GitHub docs page I fetched on 2026-11-23 did not say whether it is the PR head, base or merge commit: UNVERIFIED); whether the repository setting for merge commits is on (V1 flags the same).

## Diff points I say I win
**Win (clear):**
- C-004 (where stories merge): per-story PR into a private batch line gives an outside gate (strengths 1, 2) that V1 lacks and a blast radius smaller than V2.
- C-006 / X-005 (merge guard): authority relaxed for `train/*` only, behind CI and two reviewers (strength 2, A-014).
- C-010 (conflict procedure): only V3 routes the train-versus-`integration` conflict to a worker through the PR gate (U-011).
- C-012 / C-013 / X-006 (incomplete work, duration cap): time-boxed scope with an explicit exit ladder (strength 5, U-010).
- C-019 (sync obligation): smallest obligation of the four.
- C-025 / X-010 (stacks): the only variant with a stated stack policy, with the CI gap acknowledged.
- X-008 (V4 internal CI contradiction) and X-003 / A-017: V3 is consistent; V4 is not.
- U-010, U-011, U-012, U-013: unique and, I argue, load-bearing (U-013 most of all).

**Win against some variants, not all:**
- C-001 (ref-namespace): tie with V2 (flat, collision-proof by construction); better than V1 (relies on a remembered rule, V1 risk 4) and V4 (three levels, relies on two folders differing). Loses to V1 on browsability (U-004).
- C-002 / X-001 (base of the line): cut from `integration`, where Clay branches and where the landing happens, beats V4's silence. V1's cut from `master` is a valid alternative; I do not claim a win over it.
- C-003 / X-002 (landing path): landing in `integration` puts the one big merge where CI already runs and where Clay's work is visible. Concede the coupling (C-018).
- C-007 (pre-merge CI): beats V1; ties V4; loses to V2 on needing no edit.
- C-008 (staying current): beats V4 (consistent); V1's "master only" rule is internally coherent and avoids merge-in churn.
- C-009 / X-007 (rebase): tie with V1 and V2; beats V4's adapted rebase-before-push.
- C-011 (collision control): equal to V2, ahead of V1 and V4.
- C-021 (release size): ahead of V1 and V4; equal to V2.
- C-022 (rollback): ahead of V1 and V4 on layers; behind V2 on flag-off granularity.
