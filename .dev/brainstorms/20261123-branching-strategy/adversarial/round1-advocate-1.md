# Round 1 advocate statement: Variant 1 (release line with story branches), architect persona

Written 2026-11-23. Inputs read: CONTEXT.md, variant-1 to variant-4 originals, diff-analysis.md. Other advocates' files not read.

## 1. Position summary

Variant 1 is the only proposal whose base line has a single writer (the coordinator), whose rollback unit is one merge commit on `master`, and which needs no new repository configuration, no new owner decision and no unverified bot behaviour before the first story can start. Its real weakness is that nothing but the coordinator's local suite looks at the code until one release-sized pull request, and I say so below. I argue that this weakness is bounded (a story-count cap and a one-week limit) and is a cheaper price than the owner-click load of V2, the three owner decisions plus CI edit of V3, or the contradiction inside V4.

## 2. Steelman of each opposing variant

### V2 (trunk on `integration`, dark landing)
Strongest version: the research evidence points one way. Short branches of about two days (S1), DORA's one-week batch limit and its warning that AI raises instability unless batches shrink (S6), and Fowler's "raise the integration frequency" (S8) all favour V2. Every slice gets CI plus both bots on a small diff (C-007). CI runs against the real `integration`, so a semantic clash between two AI stories shows at once, which V2 calls "the strongest guard of the three proposals" (C-011). It needs no `test.yml` edit, because `integration` already triggers CI. It is exactly Clay's habit scaled up (Q8), so the owner and Clay share one lane and collisions with Clay surface early, not at a late sync pull request (C-019). Squash per slice gives the finest rollback grain, down to flag-off (C-022). It has no long-lived branch to drift (C-013). What it gets right that V1 does not: early, per-change feedback and the finest rollback grain.

### V3 (release train, PR-gated batch)
Strongest version: it keeps the batch isolation of V1 (the train is not shared) and still gives every story CI and both reviewers on a small diff, so the final roll-up is "mostly an integration check". It admits its costs openly (Open decisions A, B, C; U-012). It adds the time-boxed train with floating scope (U-010: "the scope floats, the time does not"), which is a cleaner answer to "is a long-lived branch justified" than anything V1 says, and a throwaway test pull request before anyone relies on the CI filter (U-013). It follows the repository's documented flow `master <- integration <- feature` (CLAUDE.md), so it fits Clay's lane (Q8) and collisions with Clay are found in CI at merge-in time. The `dash1.3-sync<N>` branch (U-011) keeps even train-versus-`integration` conflicts inside the normal pull request gate. What it gets right that V1 does not: per-story gating without giving up batch isolation.

### V4 (GFxAI approach adapted)
Strongest version: it is the only proposal with evidence from a real team using this shape. GFxAI has `release/proto-demo` and `proto-demo/feature/wizard-integration` side by side, which shows the folder layout works (C-001). It records that PR #147 reached 1,384 files and +242,976 lines (U-015), the best real-world warning about release-sized pull requests. Its provenance marks (U-014) make every rule auditable. It carries a rule the others treat only as habit: "AI Agent: Merge to Main no" (U-017). Squash per story gives one commit per story, so a revert needs no `-m 1` (C-005). It asks for the full Tier 1+2+3 tests, two approvals and sign-off at the release pull request (U-018). What it gets right that V1 does not: a real-practice size warning and a per-story review step.


## 3. Strengths claimed

1. **Single writer on the base line.** In V1 the only thing that moves `dash1.3/release` is the coordinator (V1 section 3: "merges ... one at a time, with a merge commit"). In V2 the base `integration` is written by the owner's clicks, Clay, and every slice; each AI worker's base moves under it whenever any of them merges, so each worker pays repeated merge-in cycles. In V3 and V4 the batch line is mostly single-writer but is also fed from `integration` (C-008). A single-writer line makes merge order serial by construction, which is the property AI-agent parallelism needs (S21: serial merges, ownership boundaries). Evidence: V1 Q2 "merges are serial"; V2 Q2 "The coordinator never merges in this model" (so nothing orders the slices except the owner's click order).

2. **It maps one to one onto the existing worker contract.** CONTEXT line 9: a child is made from the feature branch, "the coordinator merges the child branch into the feature branch after the result is admitted; a merge conflict is stopped and reported, never resolved automatically". V1 is that rule with the release branch as the feature branch. V2 discards it (coordinator never merges). V3 and V4 keep it but then add a pull request layer on top, which needs Open decision A (V3) or "a rule for who may merge into the release branch" (V4 closing section) before the first story can merge. V1 needs the same authority and nothing else (C-006). An architect counts dependencies: V1 has the fewest.

3. **Zero changes outside the branch layout.** V1 needs no `test.yml` edit (C-007, A-008, A-013), no ruleset entry, no assumption about how Augment and Codex behave on a non-default base (A-012), no auto-delete setting (V2 Q2 and V3 Q7 both rest on S12, UNVERIFIED). Its only repository-setting dependency is "merge commit allowed" on the one release pull request. V1's own UNVERIFIED items are five facts that need a lookup or a one-off test, not a change: the Orca `--branch` prefix, merge commit allowed on the release pull request, the `dash/1.3` tag clash (separate ref namespace, untested), who runs the `master` into `integration` sync today, and re-landing after a revert. None asks the owner to change a setting or depends on third-party bot behaviour. By contrast V3 and V4 each add a workflow edit (`train/*`, `release/**`) plus unverified Augment and Codex behaviour on a non-default base; V2 adds auto-delete, the merge queue plan and the practicality of dark landing in this code (its own "first thing to test").

4. **Smallest owner and CI load per release.** One pull request into `master`, one CI run, one Augment and Codex pass, one owner click. CONTEXT line 16 says 15 to 60 AI-made pull requests in a few days is normal. V2 multiplies the owner's merge button by the slice count (V2 section 5: "the heaviest merge load of the three"); V3 and V4 multiply CI runs and bot events by the story count plus one. A-003 is the assumption that breaks first for V2. V1 does not depend on it for anything but the final review (see concession 1 for the cost of that).

5. **Blast radius is contained until the very end.** A bad story never touches a branch Clay or any other session forks from. In V2 every slice lands in `integration`, so a bad slice is already in Clay's base before anyone knows; V2 itself lists "`integration` can go red because of someone else's merge" as risk 3. In V1 the worst case before landing is a local `git revert -m 1` on a branch only the coordinator and the story workers use (V1 Q9).

6. **The release is one revertable unit on `master`, and Clay's work is not inside it.** V1 keeps `integration` out of the release (V1 Q3), so the release merge commit contains only dashboard work. Reverting it removes exactly the release. V2 has no single commit for the dashboard release: its only whole-release revert is "revert the promotion merge commit" (V2 Q9), and the promotion carries all of `integration`, so that revert also removes Clay's merged work (V2 Q4: "the promotion carries Clay's merged work too"). V3 does have the train merge commit, but it lands the dashboard inside the same promotion, so shipping depends on Clay's state (C-018, V3 risk 3 and 4). This is the answer to question 9 that fits two maintainers on one repository best.

7. **It honours the owner's stated model and the ledger convention.** CONTEXT line 7: the release is a branch, stories are sub-branches, release merges to the default branch. CONTEXT line 14: the ledger is on the release branch and planning of n+1 starts from `master`. V1 keeps both exactly (C-002, C-003, C-020, X-009). V2 has no place for the ledger ("the biggest process cost of this proposal"). V3 must move BMAD planning to `integration`. These are structural dependencies in the owner's own tooling that V1 does not disturb.

8. **No back-port step for hotfixes.** Because the release branch merges back into `master`, a `fix/` from `master` reaches the open release by the routine merge-`master`-in step (V1 Q6). V2 needs cherry-picks plus an immediate sync pull request in the emergency case; V3 makes the back-port part of the definition of done ("forgetting it is the classic regression"); V4 needs a copy into every open release (C-015). One mechanism fewer to forget.

9. **The right guards for AI parallelism, cheaply.** A read-only trial merge with `git merge-tree` before each story merge (U-001) stops on a predicted conflict before the release tip is touched; path claims checked against open `integration` pull request file lists (U-003) give an early warning for Clay collisions; the per-story digest in the release pull request body (U-002) answers the review-size problem. None of the other three has a pre-merge guard of this kind.

10. **Story-level merge commits keep the AI audit trail.** Each story's commits (spec-compliance per task, ledger-linked) stay in history and stay reachable as the second parent of the merge commit (V1 Q7). Squash (V2, V4) collapses them into one commit and loses the per-task trail that the ledger refers to.

11. **Naming.** `git branch --list 'dash1.3/*'` shows one release and all its stories (U-004), and the leaf rule holds with or without the Orca prefix because a uniform prefix keeps siblings siblings (V1 section 2). I do not claim this beats flat names on robustness (see concessions).


## 4. Weaknesses identified in the others

### V2
1. **The owner is the single merge lane and the proposal says so.** V2 section 5: "The owner clicks merge on every slice", "heaviest merge load of the three", risk 1: "a queue of ready slices waiting for the owner". CONTEXT line 16 puts normal bursts at 15 to 60 pull requests in a few days, and V2 multiplies the pull request count by splitting each story into slices (C-004, A-003). The AI-agent parallelism that V2 is designed for is throttled at the one human step. Reviewer saturation is the bottleneck V2 itself cites (S19).
2. **It has no home for the progress ledger.** V2 Q7: the ledger problem is "a real mismatch and the biggest process cost of this proposal" (C-020). The ledger on the release branch is a standing fact (CONTEXT line 14), so V2 must either open ledger pull requests into `integration` (more owner clicks) or keep it on "the coordinator's own branch until promotion", which is a hidden long-lived branch inside a proposal that says it has none.
3. **Dark landing is unproven in this code.** V2 Q5: practicality "is UNVERIFIED and is the first thing to test on one story" (U-009). Stories that change existing dashboard behaviour need a flag or branch by abstraction, which AI-written code multiplies and V2 admits becomes dead code if not retired (S20, risk 6). Until the pilot succeeds, V2 is a bet, and V1 is not.
4. **Shipping is coupled to Clay's state.** The promotion "carries Clay's merged work too" (V2 Q4, C-018, X-003 position). A bad merge by Clay blocks the dashboard release (V2 risk 4), and a red `integration` stalls every slice (risk 3). The owner's model was a release that goes to `master` on its own.
5. **Whole-release rollback is worse than it looks.** Slices are squashed on a shared line, so there is no single commit for "the dashboard release"; the available whole-release rollback in V2 Q9 is flag off or "revert the promotion merge commit", and that merge commit holds Clay's work too (C-022).
6. **Duplicated review.** V2 Q4: "the second review is mostly duplicated effort", so the CI plus two bots cost is paid twice per slice, once per slice and once at promotion.

### V3
7. **It asks for everything V1 asks for, then adds three more owner decisions.** The coordinator merge authority (Open decision A) is the same authority V1 needs; on top V3 needs B (time box) and C (edit `test.yml` now) before story one can run (C-006, C-007, A-013, A-014). V1's marginal ask over today's worker contract is zero.
8. **Per-story CI and review rest on unverified third parties.** V3 risk 6: "Reviewer behaviour on pull requests whose base is a `train/*` branch ... is UNVERIFIED for Augment and Codex"; risk 5: a wrong filter pattern (the Orca prefix) leaves story pull requests "with no CI while everyone assumes they have it" (A-008, A-011, A-012). The advantage V3 sells is exactly the thing it has not verified, and its own advice is to run a throwaway pull request first. Until that passes, V3's real feedback loop is no better than V1's.
9. **Stacks are weak, so the dependency case falls back to waiting.** CI does not run on a pull request whose base is a story branch (V3 section 3 step 3, X-010), so dependent stories wait for the lower one to merge. V1's story worktrees cut from the release tip after a merge have the same wait, but V1 pays no CI and bot cost for it.
10. **It couples the release to the promotion cadence it does not control.** V3 risk 4. The train is cut from `integration`, so it "inherits whatever red or half-done work `integration` has at the cut" (risk 3), and "merge-in is the main weekly cost" (Q3) because Clay merges at AI speed (CONTEXT line 16). V1 avoids that merge-in against `integration` entirely (C-008).
11. **It moves the owner's planning base.** V3 Q8: BMAD planning must start from `integration`, contradicting CONTEXT line 14 (X-009). That is a change to the owner's tooling to fix a branching choice.
12. **Landing in `integration` departs from the owner's model.** CONTEXT line 7 says the release merges to the default branch. V3 lands in `integration` (C-003, X-002); the release is "on `master` only when `integration` is promoted" (V3 Q4).

### V4
13. **It contradicts itself on `integration` (X-003, X-008, A-017).** Q8 says "a dashboard release does not pass through" `integration`; Q3 merges `integration` into `release/dash1.3`. A pull request's diff against `master` is everything reachable from the head and not from `master`, so merging `integration` in puts every unpromoted commit of Clay's into the release pull request, which is exactly what V1 Q3 rules out. V4 cannot claim both.
14. **It contradicts itself on when CI runs (X-008).** Q4: CI and bots "run once, at that point"; Q2 puts a pull request with tests and at least one review on every story; the closing section adds `release/**` to `test.yml`. Which one is the proposal?
15. **Most of what V4 adds to V1 is the part with the weakest fit.** Strip V4 to its differences from V1 and three remain: a pull request per story (needs the CI edit, bot behaviour and merge-right decisions, as for V3), squash per story (loses the audit trail, strength 10) and merging `integration` in (weakness 13). Its other additions (provenance marks, size warning) are documentation, which V1 can absorb.
16. **The evidence base is thinner than it looks.** The source is a draft marked "Pending team review" with "no rollback rule" and "no flag policy" (V4 Q5, Q9); its own recommendation of "rebase-only" has to be reversed to fit `/sc:pr-submit` (C-009, X-007). The strongest real-world data point, PR #147, argues against what V4 keeps (a "Weeks-months" release branch, V4 Q5), not for any rule V4 adds.
17. **Three-level names add ref-conflict surface.** `dash1.3/story/01-slug` depends on nobody ever creating a branch named `dash1.3` or `dash1.3/story`, the same invariant V1 has, but with one more level to guard (C-001).


## 5. Concessions

1. **Review size is V1's worst risk and the evidence is against it.** V1's own section 7 risk 1 says so; DORA (S6) and the Faros data (S19, vendor) point the same way, and V4's PR #147 (1,384 files, +242,976 lines, merged "with file-level rejections") shows what a release-sized review turns into. V1's defence (story-count cap, per-story digest U-002, split after about a week) is a mitigation, not a cure. If the first dashboard release is more than a handful of stories, V1's single review will be weak. C-021 goes against V1.
2. **Nothing outside the coordinator's local suite sees the code until the end.** V2 and V3 detect a semantic collision at the next story; V1 detects it only through the local suite after each merge (V1 section 5, A-005). If the suite has gaps, a clash can sit for the whole release. C-007 and C-011 detection latency go against V1.
3. **Finest rollback grain belongs to V2.** A flag-off or a one-slice revert (C-022) beats `git revert -m 1` of a whole story. V1's grain is the story, which is the unit the owner plans in, but it is coarser.
4. **Flat names (V2, V3) are more robust than V1's folder names against hand-made mistakes.** A flat leaf can never be the folder part of another branch; V1's rule depends on nobody creating `dash1.3` by hand (V1 risk 4). V4 has the same exposure with an extra level, so I do not score it against V4 beyond a note. C-001 is a tie at best.
5. **V1 bypasses `integration`, which is the documented flow.** CLAUDE.md's "Git Workflow" says `master (production) <- integration (testing) <- feature/*`. V1 lands straight in `master`, so the dashboard release is not tested in `integration` first, and collisions with Clay show late at the sync pull request (V1 Q8 and section 5). V3 and V2 respect that flow. I say the owner's stated model (CONTEXT line 7) overrides it, but the cost is real.
6. **V1 is the most coordinator-dependent proposal.** Every merge, conflict stop and ledger write runs through one session (A-002). If it stalls, the line stalls.
7. **V3's time-boxed train with floating scope (U-010) is better than V1's justification.** "The scope floats, the time does not" turns the one-week cap into a rule that cuts scope instead of a warning. V1 should adopt it. Likewise U-013 (a throwaway test pull request before relying on any CI filter or Orca prefix), U-012 (open decisions escalated explicitly) and U-014 (provenance marks) are better practice than V1 shows.
8. **Squash gives simpler single-parent reverts (V4, C-005).** `-m 1` is a place to make a mistake, and I do not claim the audit trail is free of cost: it is more history to read. I hold only that for this repository the per-task trail is worth keeping.
9. **A `dash/1.3` tag could be ambiguous with a branch of that name.** Different ref namespaces, so no clash in git; V4's `dash-1.3` avoids even the ambiguity. Minor (C-024); I would accept a hyphen.
10. **The long-lived branch is not justified by DORA or trunk-based evidence.** It is justified only by the owner's model, explicit versioned releases (S3, S8) and a hard time cap. If the cap cannot be kept, V1 should fall back to V3, as its own Q5 says.

## 7. Diff points I say Variant 1 wins

### Wins (V1 should be the base for the merge)
- **C-002, X-001 (base of the release line):** cut from `master`, matching the owner's model (CONTEXT line 7) and the planning convention (line 14); V2 and V3 cut from `integration` and inherit Clay's state, V4 is silent.
- **C-003, X-002 (landing path):** one pull request into `master`, owner's model; V2 and V3 land through `integration` and ship Clay's work with it. V4 agrees with V1 here.
- **C-008, X-003, A-017 (currency and the `integration` boundary):** merge `master`, never `integration`; V1 is right by git mechanics and V4 contradicts itself.
- **C-018 (coupling to Clay's unreleased work):** only V1 keeps it out.
- **C-020, X-009 (ledger home and planning base):** V1 keeps the convention untouched; V2 has no place for it and V3 moves the planning base.
- **C-015 (hotfix and back-port state):** no cherry-pick or explicit back-port step, because the release branch merges back.
- **C-009, X-007 (rebase policy):** merge only, one invariant with no "before first push" carve-out that a worker can get wrong. Low severity.
- **C-005, X-004 (merge method), for this repository:** `--no-ff` keeps the per-task audit trail and gives one revert per story; V2 and V4 squash. Contested on simplicity (concession 8).
- **C-004, C-006, X-005 (where story work merges and who merges):** local coordinator merge is the existing worker-contract mechanism and needs no new setting; V3 and V4 need the same authority plus a pull request layer. V2 is the outlier by putting every merge on the owner. Contested: V3 and V4 argue the same authority buys per-story gating.
- **C-022 (rollback), release level:** one merge commit on `master` removes exactly the dashboard release, with stories still revertable inside it; V2 has no such unit. Story level is a draw with V3. Slice level goes to V2.
- **U-001, U-002, U-003 (V1 unique):** the trial merge, the per-story digest and the open-pull-request path comparison have no counterpart in the others.

### Draws or contested
- **C-001 (ref namespace):** all four avoid the conflict; flat names (V2, V3) are more robust, V1 and V4 depend on the same "never create the bare token" invariant. U-004 (grouped listing) is a low-value V1 plus.
- **C-010 (conflict procedure):** V1, V3 and V4 route conflicts to the story worker through the coordinator or pull request; V2 skips the coordinator. Close.
- **C-011 (collision control):** V1's guards (U-001, path claims) are better before the merge; V2's and V3's CI is better after it (detection latency). Split.
- **C-012, C-013, X-006 (incomplete-work isolation, justification of a long-lived line):** V1 wins against V2 on practicality (no flags, no pilot needed) and loses to V3's time-boxed train on rule design (concession 7). V1 should adopt U-010.
- **C-014, C-016, C-017, C-019, C-023, C-025:** no meaningful difference worth a point.

### Losses I accept
- **C-007 (pre-merge CI and reviewer coverage), C-021 (release size at final review), X-008 (V4 internal, no point either way):** V1 has the least feedback before the end and the biggest final review. V2 and V3 win these two on the evidence.
- **C-024 (tag naming):** V4's `dash-1.3` is slightly safer. Adoptable at no cost.
- **U-006 to U-009 (V2), U-010 to U-013 (V3), U-014, U-015, U-018 (V4):** worth importing into the merged proposal where they do not break the single-writer property (time box, throwaway test pull request, open decisions list, PR #147 as the size warning, release-PR tier gate). U-006 (slicing, dark landing) and U-011 (sync branch) are not needed in V1.
