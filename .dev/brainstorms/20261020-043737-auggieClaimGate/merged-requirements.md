# Auggie Claim Gate: Requirements and Design Spec (Variant 1, architect)

## 1. Summary

<!-- Source: Base (original) -->
auggie-review currently has one gate between a reviewer candidate and a published defect: does the cited `file:line` exist and does the snippet match (feature-baseline `SKILL.md` Wave 3 step 3, lines 165-169). That gate proves *location*, not *defect*. Every candidate that survives it becomes a graded defect: the rubric's category floors can raise it (`severity-rubric.md` lines 70-87), and low confidence only lowers it by one tier (lines 89-92). There is no outcome that says "not a defect" or "not proven".

This spec adds one **Claim Admission step** (Wave 3, step 3b) and a **candidate ledger** (`candidates.json`). Every grounded candidate gets exactly one *disposition*: `defect`, `unproven`, `rejected`, `intentional_limitation` or `documented_prerequisite`. The disposition is decided from structured causal evidence the reviewer must supply and the orchestrator must re-check: producer and entrypoint reachability, guards, intent and prerequisites, counterevidence, evidence kind, and base/head/current attribution. Severity is assigned only to admitted `defect` records. The report, the summary counts, PR posting and the remediation offer all read from that one ledger. A `jq` invariant check already permitted by the skill's `allowed-tools` makes the ledger-to-report consistency mechanical. Semantic judgment stays with the orchestrator, which must attempt to refute each candidate. No new agent, no new Python module and no change to `severity_router.py`.

Architectural stance: the failure is a **missing state in the data model** (no non-defect dispositions), not a missing reviewer. Adding reviewers without adding the state would only add more defects. Adding the state with a checkable evidence schema is the smallest change that closes the promotion path.


## 5. Design Decisions (Open Questions)

<!-- Source: Base (original); requirement-level tags inside mark every modified or added item -->

### D1. Structured candidate evidence vs. prompt-only checklist -> **structured evidence (chosen)**

<!-- Source: Base (original), D1 → Target D1, Disposition: preserved-exact -->

| Option | For | Against |
|---|---|---|
| Prompt-only checklist (tell the reviewer to check callers, intent, prerequisites) | Smallest diff (one prompt block) | Nothing downstream can check that it happened; publication stays ungated (seed brief Probe batch); the reviewer that produced the claim judges its own claim |
| **Structured claim fields in the existing findings JSON + orchestrator re-check** | Every admission criterion becomes a field that is present or absent and cited or not; the orchestrator can mechanically refuse admission when a field is empty; the same record feeds report, posting and remediation | Larger prompt contract; reviewer may fill fields with plausible prose (mitigated by D2 re-check and by requiring citations, not prose, in causal fields) |

The structured fields are an **additive extension** of the existing JSON contract (`auggie-prompts.md` lines 40-69), not a new schema family. Old fields keep their meaning. <!-- Source: Base (original), D1 additive-extension rule → Target D1 additive-extension rule, Disposition: preserved-exact -->

### D2. Independent semantic validator vs. strengthened orchestrator gate -> **strengthened orchestrator gate with a mandatory refutation step (chosen)**; no new agent

- `evidence-validator` cannot do this job: it verifies citations only and explicitly will not propose evidence or re-grade (`evidence-validator.md` lines 33, 137-144). Reusing it beyond that would claim a capability it does not have. It stays an optional citation re-check only. <!-- Source: Base (original), D2 bullet 1 → Target D2 bullet 1, Disposition: preserved-exact -->
- A second reviewer agent shares the reviewer's assumptions and model family (seed brief: "Independent reviewers can share assumptions"). Agreement between two passes is not semantic proof (constraint in the seed brief). <!-- Source: Base (original), D2 bullet 2 → Target D2 bullet 2, Disposition: preserved-exact -->
- The orchestrator already owns grounding and has the tools needed for refutation (Read, Grep, `git show` for base/head). The failure in the audit logs is that it was only asked to confirm location. The fix is to change its question from "does this line exist?" to "can I refute this claim from the cited entrypoint, intent and counterevidence?", with a recorded outcome per admission row (the refutation record, 6.4). <!-- Source: Base (original, modified) — D2 reference to the fixed procedure aligned with the Change #5 refutation record (consequential edit; logged in merge-log deviations) -->
- Escalation hook, not built now: the admission record is already the input contract an independent validator would need. Escalation trigger: consider a second reader only after `over_rejected` or `false_promotion` on complete records is non-zero in a measured run (11.3). <!-- Source: Base (original), D2 + Variant 3 (haiku:qa), §9 "If over_rejected or false_promotion is non-zero on complete records" → Target D2 escalation trigger, Change #15, Disposition: modified, Decision basis: C-023 V1+V3 unanimous (Scoring Matrix 90%) measured trigger -->

### D3. How much deterministic validation -> **structural invariants only, via `jq` (already in `allowed-tools`) plus contract tests; no runtime semantic automation**

Deterministic code can decide *shape* and *consistency*. It cannot decide whether a guard really blocks a path or whether a spec sentence really expresses intent. So determinism is limited to:

1. Ledger schema: every record has exactly one disposition from the enum, plus required fields per disposition. <!-- Source: Base (original), D3 item 1 → Target D3 item 1, Disposition: preserved-exact -->
2. Severity is non-null **iff** disposition is `defect`. <!-- Source: Base (original), D3 item 2 → Target D3 item 2, Disposition: preserved-exact -->
3. A `defect` record has `evidence_kind != "speculative"`, a non-empty `harm` and a non-empty `refutation` record; a `behavioral` defect also has a non-empty cited `reachability.entrypoint` (class-conditional, matching I-3 and AC-04). <!-- Source: Base (original), D3 item 3 → Target D3 item 3, Change #15, Disposition: modified, Decision basis: base-selection.md CORR-4 (class-conditional consistency with I-3/AC-04) -->
4. Report and summary counts equal ledger counts. Inline comments and remediation input are a subset of `defect` records. <!-- Source: Base (original), D3 item 4 → Target D3 item 4, Disposition: preserved-exact -->

<!-- Source: Variant 2 (opus:refactorer), §5/§6.5/OQ-3 "refs/claim-gate.md, exactly one jq block" + NFR-006 "one jq run per review" → Target D3 (jq location and invocation), Change #1, Disposition: modified, Decision basis: C-001 and C-029 Round 3 unanimous (Scoring Matrix 90%); timing changed to pre-post per INV-002 -->
These checks are exactly one fenced `jq -e` block in the one new ref, `src/superclaude/skills/sc-auggie-review-protocol/refs/claim-gate.md`. Refs are already loaded per wave (baseline SKILL lines 65, 143, 163), so the ref follows an existing pattern. The orchestrator runs that one program **once per review**, after `REVIEW.md` is written and before any Wave 4 action, as `jq -e -n --slurpfile ledger candidates.json --rawfile review REVIEW.md -f <extracted block>` (allowed: `Bash(jq *)` in `SKILL.md` line 4). No new agent, no new Python production module, no new tool permission and no edit to `severity_router.py`.

### 6.2 Candidate `claim` block (reviewer-supplied, additive to the existing contract)

<!-- Source: Base (original); requirement-level tags inside mark every modified or added item -->

Added to each object in `findings[]` (`auggie-prompts.md` Output contract). Causal fields hold **citations plus one sentence**, not essays. <!-- Source: Base (original), §6.2 claim-block placement rule → Target §6.2 claim-block placement rule, Disposition: preserved-exact -->

```json
"claim": {
  "observed": "<what the code does, one sentence>",
  "observed_at": ["<path:line>"],
  "expected": "<what should happen instead>",
  "violated_requirement": "<the rule or requirement the behavior breaks; must be non-empty for a defect>",
  "intent_sources": ["<path:line of spec/test/doc/comment/PR text stating intended behavior or a prerequisite>"],
  "intent_finding": "<none_found | supports_claim | contradicts_claim | deliberate_policy | documented_prerequisite>",
  "reachability": {
    "entrypoint": "<path:line of the production caller/command/hook that reaches observed_at, or null>",
    "producer": "<path:line or official external contract showing the triggering input is produced/accepted, or null>",
    "guards_checked": ["<path:line of each guard on the path, with 'blocks' or 'does_not_block'>"],
    "caller_search": "<Grep pattern and roots used; required when entrypoint is null>"
  },
  "harm": "<concrete supported consequence for a user/operator/data, or null>",
  "counterevidence": ["<path:line + one sentence for each fact that weakens the claim>"],
  "evidence_kind": "<runtime_reproduced | static_traced | protocol_literal | speculative>",
  "qualification": "<null, or { \"scope\": \"<the documented supported configuration the harm depends on>\", \"scope_citation\": \"<path:line of a documented supported configuration>\" }>",
  "disposition_hint": "<defect | unproven | rejected | intentional_limitation | documented_prerequisite>"
```
