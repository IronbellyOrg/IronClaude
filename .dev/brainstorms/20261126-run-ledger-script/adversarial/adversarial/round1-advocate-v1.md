# Round 1 advocate: Variant 1 (sonnet:architect)

Checks I ran read-only this round: `orca worktree list --json` rows carry `isMainWorktree` (true for `/home/coder/workspaces/IronClaude`) and `isArchived`; `orca orchestration run-create --help` shows a `--json` flag; `src/superclaude/cli/main.py` registers `sweep_group` at line 585-587 with the deferred import; `XDG_STATE_HOME` is already used by `issue_watch/cycle.py:196` and `observe/export.py:239`; `src/superclaude/hooks/scripts/` already holds hook scripts such as `require-orca-worktree-agent.sh`.

## 1. Position summary
V1 is the right base for the final spec because it is the only variant that delivers all four Success Criteria (the hook branch is tested or dropped with a rule), it names exit codes, a lock and a fixture-based test plan, and it states what to do when facts are UNVERIFIED. It is bigger than needed in places (package split, `show`/`path`, `--no-ledger`), and the final spec should trim those and adopt V2's path and sweep wiring.

## 2. Steelman of V2
V2's strongest version: the brief asks for a deterministic rebuild plus a sweep that reads it. The only thing that forces a second writer, a lock, a merge-under-lock rule and a hook parser is the hook, and the hook only closes a gap of at most one build interval (30 to 45 min) that `created_since_build` already closes at the next build. V2 deletes the hook, which turns every concurrency question (Q4) into "one writer, atomic rename" and removes the only component whose input (`run-create` output as seen by PostToolUse) nobody can verify without creating a Run, which the brief forbids. It meets the Success Criterion by the explicit "dropped with the reason written down" branch and offers a no-file fallback (coordinator runs the build after `run-create`). Its other choices are also right: one module, one command, no new sweep flag, XDG state path matching two existing modules, `generated_at` captured before the first Orca call (a real race V1 misses), a repeated-cursor FAIL guard, and a simpler exit code set. It also estimates about 150 lines against a package of five modules. Under "smallest correct change" this is a serious, honest design, and for the core build it is mostly what I would ship.

## 3. Strengths of V1
1. It honours the issue's chosen approach. Brief "Known Context" lists the PostToolUse hook as part of the approach; the owner already decided it. V1 ships it and only drops it on a stated, testable condition (V1 Q7: "If the id is not in the output, drop the hook and rely on the 45-minute build"). V2 overrides an owner-chosen element on a prediction.
2. Hook failure is cheap and well contained. V1's script always exits 0, validates the id shape with `run_[0-9a-f]{12}`, logs once when no id is found, and `add` is idempotent and validated. Blast radius is one missing Run for at most 45 min, the same outcome V2 accepts by default.
3. Lock plus merge closes a real lost-update race. V1 Q3/Q4: Orca reads take 10-50 s (probe: 26.1 s) before the write, so any append in that window is overwritten by a plain atomic rename. `source=="hook" and added_at > build_started_at` survives the merge, and `test_concurrent_add_and_build_no_lost_append` pins it. V2 avoids the race only by deleting the writer.
4. Stronger anti-wipe guards. V1's shrink guard (under 20% of old when old >= 5) and the "0 included while a Run was active in 24 h" guard catch a partial Orca read that returns a plausible non-empty list. V2's rule 4 only fires at exactly zero. Given the A-002 probe (ledger of 10 of 62), a bad read that drops to 1 or 2 Runs would pass V2's guards silently.
5. Distinct exit codes (V1 Q5: 1 Orca, 3 lock, 4 implausible) let cron logs and the sweep staleness message tell "Orca down" from "result looked wrong". V2 merges them into exit 1.
6. U-001 evidence is unique and correct: `worker-list --run <unknown>` is `ok:true` with no workers while `task-list` returns `run_not_found`. V1 states "use run-list as the universe". V2 never says this and its "fetch workers only for undecided Runs" short-circuit relies on a worker-list that cannot prove a Run exists.
7. Isolation of the shell-out layer in `orca.py` with an injected runner keeps `tests/sweep/test_probes_allowlist.py` valid and gives the fake-Orca tests one seam. `rules.py` as a pure `decide()` is the one seam worth keeping, because A-002 shows the rules will change soon (see 6).
8. Hook-entry expiry (24 h) and `last_seen_active` stop hook entries living forever; the `build` output counts blocked-only Runs so the owner sees the cost (U-001).
9. The test plan covers failure modes V2's list omits: lock timeout, corrupt ledger on sweep vs build, bad id in `add`, hook fails open with `superclaude` missing, byte-identical file and unchanged mtime on failure.

## 4. Weaknesses of V2
1. It drops an owner-chosen component on a prediction, not a measurement. V2 says the hook "only shortens that gap" but also says what `run-create` prints is UNVERIFIED. It did not attempt a fixture-based test, which is what the criterion says ("Hook tested for what `run-create` gives it"). The drop is allowed, but it is the weaker reading of the criterion.
2. Its `new` rule has a hole at the first build: "If there is no previous ledger or it is unreadable, this rule is skipped". A corrupt or deleted ledger (the exact failure mode these guards exist for) means every Run created since the last good build is excluded unless it has a live worktree or open task. V1 uses 24 h as the fallback.
3. `new` uses `created_at >= previous_ledger.generated_at`. With the `generated_at` taken before the Orca calls this is fine, but a Run created mid-build is only seen by the next build, and with a stale or failing build the lag is unbounded while sweep still reports "ledger is N h old" only as a header line.
4. Guard 4 triggers only on exactly zero included Runs. A partial read shrinking 10 to 1 writes silently. The coordinator then sweeps one Run and no one is told. (The diff probe shows the real inclusion count is only 10 of 62, so a drop to 1-2 is plausible-looking.)
5. The single exit code 1 conflates Orca failure with implausible result, so a cron log reader cannot tell which. `--accept-empty` is a narrower override than V1's `--force` guard split and leaves no way to accept a legitimate large shrink after a mass cleanup.
6. "No lock, add one only if the hook is ever adopted" is true for V2 as designed, but a cron overlap plus a manual run from the coordinator (V2's own fallback: "coordinator runs `superclaude run-ledger` itself right after `run-create`") creates exactly the second writer V2 claims to have removed. Its own fallback needs the lock it deleted. Atomic rename makes the loss benign for a pure rebuild, so this is Low severity, but the claim "no second writer" is not strictly true.
7. Its test list has no case for the sweep reading a stale ledger, a repeated cursor beyond the paging test, concurrent runs, or a corrupt ledger on read.

## 5. Concessions (V1 weaknesses)
1. Over-built for the brief. A five-module package, four subcommands (`show`, `path` have no Success Criterion), `--timeout`, `--no-ledger`, and about 40 tests. Under "smallest correct change" `show`/`path`, the `--no-ledger` flag and a separate `orca.py`/`store.py` split should go; one module with a pure `decide()` function is enough.
2. `~/.superclaude/run-ledger/` is a new top-level dotdir. The repo already uses `$XDG_STATE_HOME/superclaude/...` (`issue_watch/cycle.py:196`, `observe/export.py:239`). V2's path is the convention and V1's rejection of `.dev/coordinator/` does not justify a new home directory. V2 wins C-003.
3. V1 captures `built_at` implicitly; V2's explicit "capture `generated_at` before the first Orca call" is a correct detail V1 lacks (U-003).
4. The hook's value is small in steady state: the build runs every 45 min and the sweep reads the ledger every 30-60 min. V2's argument that the gap is minor is fair. V1's own fallback admits it.
5. The 24-h fallback for "no previous ledger" can admit many Runs on a fresh host with a busy day; it is bounded but it is a magic number.
6. The cron interval `*/45` aligns badly with a 30-60 min sweep; V2's `17,47` (30 min) lowers lag.
7. V1's guard thresholds (20%, 24 h, cap 20 pages) are unsupported by data; they are judgement calls and the spec should say so.

## 6. Shared assumptions

**A-001: QUALIFY.** Evidence: both variants mark only `PATH` as UNVERIFIED; neither checked that `orca` from a cron environment reaches the Orca server (socket, desktop session, auth). I did not test this and the brief forbids installing a crontab. Final spec should add: a pre-install step "from a minimal env, run `env -i HOME=$HOME PATH=<cron PATH> superclaude run-ledger build --dry-run` and confirm exit 0 before the owner pastes the crontab line"; the build must print "orca unreachable" distinctly (exit 1) and the sweep must treat a ledger older than 3 h as a warning that names `build.log`; keep the session-cron fallback written in the schedule file.

**A-002: REJECT.** Evidence: the diff-analysis probe shows the live-worktree rule never expires for the main checkout: `run_93bfa00cae2b` is IN permanently because Orca always lists `/home/coder/workspaces/IronClaude`, and `worktree list --json` marks that row `isMainWorktree: true` (verified this round). Also 6 Runs are IN on one old `ready` task, and `run_93bfa00cae2b` holds 15 `blocked` tasks. Final spec should add: (a) LIVE excludes rows with `isMainWorktree: true` and `isArchived: true`, so a Run counts only through a linked worktree (field names verified in `worktree list --json`; semantics of `isArchived` UNVERIFIED, so test with a fixture); (b) for `unfinished_task`, count only tasks in `ready`/`running`-like states whose Run also had activity within N days, or expire by `updated_at` age (owner picks N; the brief rejected a date window for Run inclusion, so this must be the owner's decision and default to "include and report the count", as V1 does); (c) `blocked` tasks are reported separately in the build output; (d) a regression test `test_main_checkout_worker_does_not_make_run_live`.

**A-003: ACCEPT.** Evidence: a 26.1 s sequential read cannot be a snapshot, but both builds are rebuilt from scratch every 30-60 min, a Run that flips mid-read is repaired by the next build, and including a Run wrongly costs only sweep time. Add one line to the spec: capture `build_started_at` before the first Orca call, and list worktrees last or first consistently (V1: first), noting that a Run created during the build is handled by `created_since_build` at the next build.
