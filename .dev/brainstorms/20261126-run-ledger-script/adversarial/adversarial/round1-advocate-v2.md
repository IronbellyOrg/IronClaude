# Round 1 advocate: Variant 2 (sonnet:refactorer)

## 1. Position summary
V2 meets every success criterion except the hook one with one module, one command and one writer, and it chooses the brief's allowed "dropped with the reason written down" outcome for the hook. The project rule is the smallest correct change; V1 adds a lock, a merge, a package and a hook to close a race that only exists because of the hook. V2 should win on structure, and a few V1 safety details should be borrowed (hybrid points below).

## 2. Steelman of V1
V1's strongest version: the issue itself asks for a PostToolUse hook, and V1 is the only variant that delivers what the issue chose. It keeps the "decide" logic as a pure function (`rules.py`, V1 Q1) so the inclusion rules are testable without Orca, and it quarantines all shell-outs in `orca.py`. Its concurrency story is complete: it reads Orca before taking the lock and merges hook entries added during the build (V1 Q3/Q4), so no append is lost. Its plausibility guards are richer (shrink guard, exit 4 "implausible" separate from exit 1 "Orca failed"), which matters because a cron job that silently shrinks the ledger to nothing would make sweep miss live work. It verified the `worker-list --run <unknown>` returns ok-with-zero-workers trap (V1 header, diff U-001) and prints the count of blocked-only Runs so the owner sees the cost. Its hook fails open and has a fallback to "drop the hook if the id is not in the output". If the owner wants instant pickup, V1 delivers it; V2 only offers a workaround.

## 3. Strengths of V2
1. Smallest surface that meets the criteria. One file (`src/superclaude/cli/run_ledger.py`, ~150 lines), one `main.add_command` line next to `main.py:587` (verified: `main.add_command(sweep_group, name="sweep")`). `src/superclaude/cli/` already holds both single-file modules (`doctor.py`, `ic.py`, `init_lite.py`) and packages, so a single file is within local convention (verified by `ls`).
2. No second writer, so no lock, no merge, no lost-append race. V2 Q4: "One writer only (the schedule)". Atomic `os.replace` is enough for one writer, and V1's own lock exists only to protect against the hook it adds (V1 Q3/Q4: "Orca reads ... BEFORE taking the lock ... merges ... hook entries").
3. The hook gain is small and its evidence is missing. V2 Q7: with a 30-minute rebuild, the `new` rule admits a missing Run at the next build, and sweep itself only runs every 30-60 min. V1 itself says what `run-create` prints to the hook is UNVERIFIED and the real test needs a throwaway Run that the brief forbids (seed-brief Constraints: do not create anything; V1 Q7). Building a hook on an unverified payload shape is the riskier path.
4. XDG state path matches existing code. `XDG_STATE_HOME` with `~/.local/state` is already used by `sweep/commands.py:253`, `sweep/probes.py:1370`, `observe/export.py:237`, `issue_watch/cycle.py:196` (verified by grep). V1's `~/.superclaude/run-ledger/` invents a new top-level dot directory (C-003).
5. `generated_at` captured before the first Orca call (V2 Q3, diff U-003) closes the real mid-build gap for the `new` rule with no machinery.
6. Rule 5 for no previous ledger (skip the `new` rule, C-005) avoids V1's 24-hour fallback, which on a first build admits every Run created in the last day; V2's choice cannot over-include, and the other two rules still seed the ledger.
7. Short-circuit order (tasks first, workers only for undecided Runs, V2 Q5) cuts calls; the probe in diff-analysis shows the unshortcut rebuild is 26.1 s, so either is acceptable, but V2 is lower.
8. Test list covers every named success criterion in ten tests (V2 Named tests), so the regression test the brief demands exists without 40 tests across five files (C-009).

## 4. Weaknesses of V1
1. Over-built for a script that runs every 30-60 minutes. Package of four modules plus a hook script plus a cron template plus a four-subcommand group (`build`, `add`, `show`, `path`). `add` exists only for the hook; `show` and `path` are conveniences nobody asked for (U-002 rates them Low). That violates the project's scope discipline rule.
2. The lock/merge design adds a new bug class. V1 merges "any entry with `source==\"hook\"` and `added_at > build_started_at`" and expires hook entries after 24 h. That is a second source of truth whose interaction with `created_since_build` is exactly what V2 flagged as a disagreement risk (V2 Q7 reason 2). 20-process concurrency tests are needed to prove it (V1 test list `test_concurrent_add_and_build_no_lost_append`), so the cost is paid in tests too.
3. The hook needs an owner edit of `~/.claude/settings.json` plus `jq` on the hook host, and V1 admits the payload is UNVERIFIED (V1 Q7). Its own "drop if no id" fallback shows it expects the hook may not work.
4. `--force` and the 20% shrink guard (C-006) add tuning knobs that are not in the brief. The brief asks for "implausibly empty" only. A 20%-of-old guard would wrongly block a legitimate cleanup after the owner settles several Runs (old included >= 5 to under 20%); then every build exits 4 until someone runs `--force`.
5. `--ledger/--no-ledger` on sweep (C-004) adds a flag for behaviour that is already the default; `--no-ledger` has no use because the old behaviour was an error.
6. Exit-code table of five values (C-007) for a cron job whose only consumer is a log file and sweep's staleness warning.
7. `blocked`-forever rule: V1 defaults to include and merely reports the count, so stale Runs stay in with no expiry (see A-002 below); V1 does not address the probe fact that `run_93bfa00cae2b` is permanently in.

## 5. Concessions (V2 weaknesses)
1. V2 does not deliver the hook, which the issue chose. The criterion is met only through the "dropped with the reason" branch, and I never tested the payload, so "the hook adds little" rests on arithmetic (up to 30 min lag) plus an UNVERIFIED payload claim, not on an experiment.
2. The pure-function split in V1 (`decide()` without I/O) is a real testability advantage; V2's single file could hide logic in the click command. V2 should still write the rules as a module-level pure function in the same file.
3. V2's guard 4 (0 included while old >= 1) has no 24-hour activity clause, so after the owner truly settles everything the job needs `--accept-empty`; V1's clause is slightly smarter.
4. Single-file layout stops scaling if more rules arrive. Acceptable now; split later.
5. V2's no-lock claim relies on a single schedule; two cron entries or a manual run overlapping the cron run is possible. Harm is small (two equally fresh whole files), but a `flock -n` in the cron line (V1 C-008) is cheap and V2 should take it.
6. V2's 50-page cap vs V1's 20 is arbitrary; at 100 rows per page both far exceed observed need (8 pages in total).

## 6. Shared assumptions
**A-001: QUALIFY.** Evidence: on this host `orca` resolves through a shim directory (`/home/coder/.config/orca/linux-orca-cli-shim/orca`, which `exec`s `/opt/Orca/resources/bin/orca-ide`) and that directory is on my interactive PATH only via Orca's environment; a cron PATH would not contain it. I ran the read-only `env -i HOME=/home/coder PATH=<shim>:/usr/bin:/bin orca orchestration run-list --json`: exit 0, `ok: true`. So a stripped environment works when the PATH is set and the Orca app is running; it does not prove the app is running at 03:00 or after a restart. Spec rule to add: the builder resolves the orca binary from `ORCA_CLI_BIN_DIR`, else `shutil.which("orca")`, else that shim path, and fails exit 1 with "orca not found / Orca app not running" (old ledger kept); the cron example sets `PATH=` explicitly and the delivery steps include one `env -i` real run of the exact cron line before the owner installs it.

**A-002: REJECT** (as an assumption that the two rules always mean "active work"). Evidence: diff-analysis probe: `run_93bfa00cae2b` is permanently IN because it used the main checkout (which Orca always lists) and holds 15 blocked plus 2 ready tasks; 6 more Runs are IN on one old `ready` task; 9 + 3 = 10 of 62 after union, against the issue's expected "3 live". Spec rule to add: (a) a worker whose `worktreeId` path is the repository's main checkout does not count for `live_worktree` (match only worktrees whose path differs from the repo root, or whose `isMainWorktree`-style flag is false: check the real field in `worktree list --json` during implementation); (b) report in build output and ledger the count of Runs admitted only by `unfinished_task` with `updated_at` older than 7 days, as "stale open Tasks"; (c) the owner decides whether to add an age cutoff on `blocked`/`ready` tasks; default now: keep them in (fail toward inclusion) and print the number. No settle-a-task action is built.

**A-003: ACCEPT.** Evidence: a rebuild reads for about 26 s (diff-analysis probe); a Run that flips between reads is repaired by the next 30-minute build, and `generated_at` captured before the first call (V2 Q3) already covers the one flip that matters (a Run created mid-build). Worktree list is read once, first, so a worktree removed mid-build leaves its Run IN for one more cycle, which is harmless. No extra rule needed beyond keeping `generated_at` before the first Orca call.
