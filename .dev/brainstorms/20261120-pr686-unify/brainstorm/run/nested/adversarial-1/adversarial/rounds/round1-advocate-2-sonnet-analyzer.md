# Round 1 advocate: variant 2 (sonnet, analyzer)

## 1. Position summary

V2 is the best base for the plan because it keeps the built, tested code paths (the poll claims, as `launch.py:33` and `cycle.py:1082-1112` already do), starts from what is on master with file:line evidence, and breaks the migration into small stages that each carry a named mechanical check, a rollback and preconditions. I do not claim V2 wins everywhere: V1 is better on where machine state lives and on the named state for waiting hand-backs, and V3 is better on crash and idempotency design and on keeping merge go entries out of git, so the right answer is V2 as the spine with those pieces grafted in.

Evidence base: I read the diff analysis, all three variants in full, the settled verdicts D05, D07, D08 and D10 where they bear on a point, and checked three code claims in the master snapshot (`cycle.py:216-226`, `cycle.py:1082-1112`, `launch.py` worktree use). Nothing was run.

## 2. Steelman of V1

The strongest version of V1: start from the end state and every other choice follows. If the coordinator claims inside its own session (`start_mode: wake`), one agent owns the issue from wake to merge and the D07 defect "one worktree, one live agent" disappears by design, because there is no second agent writing in the `Coordinator` worktree (V1 section 3, K1). The poll still records `claimed` on seeing the marker, so MR-2 holds in both modes, and a single config value (`start_mode`) rolls the whole thing back to the built claim path (U-001). Machine state (wakes, acks, per-issue state, go entries, use log) lives in one per-repo folder outside any git checkout, next to `dispatch.json` and `audit.jsonl`, which removes the risk of someone committing a mutable lock file and the need for a `.gitignore` edit in every project (K5, U-002). V1 also names a state the other two leave implicit, `waiting_reapproval`, outside the cap and with an expiry, which is exactly what D15 C-INV-1 and C-INV-2 ask for (K15, U-004), adds `coordinator_autostart` and a `coordinator_absent` reason so a script never starts a session without a recorded owner go (K11, U-003), and lays each owner answer out on its own line saying what it does (S-002), which is what a busy owner needs. Five extra conflicts (K11 to K15) show the end-state lens finds real seams.

What V1 genuinely gets right and V2 should take: the location of machine state (C-002), the `waiting_reapproval` state (U-004), `coordinator_autostart` and `coordinator_absent` (U-003), and the per-answer layout of the owner actions (S-002).

## 3. Steelman of V3

The strongest version of V3: the system is local and at-least-once, so the plan must say what happens at every crash boundary, and V3 is the only variant that does. It saves the claim attempt before launch (already built; `cycle.py:1092` says "durable before the launch call"), treats an unknown launch receipt as uncertain and never relaunches it (`test_unknown_launch_no_second_claim`), replays an outbox so "claim marker seen, wake not yet written" produces one adoption wake and never a second claim (U-012, `test_claimed_outbox_replay`), retargets an abandoned wake with a linked new id, persists the restart budget across a crash, and reconciles the exact head after an uncertain merge before any go is reused (U-013). Its integrity rules (stable action id per write, exclusive create, temp plus rename, fsync file and parent directory, reject symlinks and oversize files, lock order, producer releases before delivery; V3 section 4) are the concrete form of M1 and M2. V3 section 8 gives one failing-test name per failure row (U-014). Its 11-row stage table is also the most realistic size for a small team, and its go entry kept in ignored runtime state with the owner's quoted words copied to `records/` (C-009) avoids a mutable one-shot file on a shared tracked branch. Its rule "a failed read is unknown, not empty" matches the owner's silent-loss concern.

What V3 genuinely gets right and V2 should take: crash and idempotency design (C-010, U-011 to U-014), go entries not tracked in git (C-009, X-005), the sentence that the standing Coordinator stays read-only while a claim session runs (X-001), and the cleaner wording of the binding switch (C-003).

## 4. Strengths claimed

1. **Smallest diff on the claim path (C-001, K1).** V2 keeps the built poll claim (`launch.py:33`, the integer-only prompt) and adds a wake only after the marker shows. I checked master: the claim launch already saves `pending` durably before the launch call and records `unknown` and `abandoned` outcomes (`cycle.py:1090-1112`), and `marker_in_window` is the MR-2 guard D01 requires. V1's end state (coordinator claims) replaces that tested path with a never-tried one; V1 itself rates it RK-7 "M, never tried: context size, Skill tool access and the claim's worktree check are untested". A plan for a small team should move the tested code last, not first.
2. **Every stage is one PR with a named mechanical check, a rollback and preconditions (S-001, U-006).** V2 section 5 defines MC-1..MC-10 once, with proposed test names (for example `test_start_refuses_when_approval_removed_between_wake_and_start`, `test_ack_without_state_file_leaves_wake_entry`, `test_enabled_key_absent_means_off`) and the NG-2 argv test by its real name and line (`test_security_invariants.py:652`, `:683`). V1 names MC-1..MC-7 only; V3 lists the same conditions as a prose "merge gate M" with no ids. D14 asked for mechanical merge checks; V2 is the only variant a reviewer can tick off line by line.
3. **The revert is treated as the risk it is (U-007, S6).** D03 recorded that the full suite and `tests/hooks/test_launch_level_guard.py` did not finish on the revert tree, and that revert plus PR 686 breaks `superclaude --help` (29 test modules fail at collection). V2 S6 is a no-PR dry run bound to a recorded master sha that also runs `git apply --check` on the owner's 1,767-line planb patch and finds which verb exposes `brief.build`; V2 S8 adds a per-host diff rule before any `superclaude install` (NB-1). V1 has a dry run clause but no `git apply --check`; V3 has "exact-master clean revert trial" only.
4. **Rollback warning that matches the code (C-015).** V2 S12 says a rollback must also remove the new keys because the loader may reject unknown keys. Master confirms it: `cycle.py:216-220` raises `_invalid("unknown configuration key: ...")` and `cycle.py:222-226` requires `schema_version` to equal 1. V1 says the opposite ("readers ignore unknown keys", S10) and also proposes `schema_version` 2, which that loader refuses.
5. **Honest built-versus-not table with evidence (section 6).** Each row carries a file:line or a PR, the ledger word, and the stage that changes it, and it adds a consistency note that the guard is BUILT-ON only for sessions a claim launch bound ("no worker-start worker has ever been bound"). The diagram tags every box [B], [P], [C], [N] or [D]. This makes it hard for a later reader to mistake planb or an open PR for shipped code.
6. **`wake_enabled` default false (U-009, S13).** D10 gives three deliveries ten minutes apart, then an unread mark and exit 7. Without this key the poll would send wakes to a coordinator that does not exist yet, three times, for nothing. Neither V1 nor V3 has an equivalent switch for the transport alone (V1 has `start_mode`, which only helps once the coordinator exists).
7. **Lane 3 early (C-006, U-008).** D14 says the sweep contract and the text fixes are independent of lanes 1 and 2. V2 S4 and S5 ship them right after the hold; V1 puts them at S10 behind the revert and planb, which delays the observer by about nine stages for no dependency reason.
8. **NG-2 handled explicitly (C-013, K15).** V2 says the `hold:backlog` label creation is a GitHub write made by a person-run `repo-init` on the owner's go, never by the poll or cron, and that the poll skips quietly if the label is absent. V1 and V3 say only "init creates labels".
9. **The first live run is narrow (S15 then S16).** V2 ships the coordinator skill without the merge path ("PR ready, person merges by hand"), then the merge path as one unit, and states the deviation from D15 O4 and O5. This is a smaller blast radius for the first real issue than V3's order, which builds the merge unit (S7) before wake, cap and F binding (S8).
10. **A single, internally listed set of unproven items (V2 sections 7 and 8, last paragraph of 8).** Which verb exposes `brief.build`, the shape of PR 693's result file, whether per-repo loaders reject unknown keys and the proposed `.dev/coordinators/` sub-paths are all named UNVERIFIED rather than assumed.

## 5. Weaknesses identified in V1 and V3

V1:

1. **C-003 and X-002: "unbound and flagged" collides with the owner's own G2 sentence.** D05's verdict quotes it: "Before any other issue runs through the flow, the worker must be bound to the guard (G2)" (`debates/D05/VERDICT.md` line 47) and lists "may one more real issue run unbound while the gate is open" as an owner DECISION (line 56). V1's `BOUND_WORKERS_PROVEN = False` (V1 S11) answers that decision in the plan by letting real issues run unbound on a person's go. The owner's rule wins; V2 S15/S20 and V3 S9 keep real issues off until the live probe.
2. **C-014 and C-015: `schema_version` 2 and "readers ignore unknown keys" are contradicted by the loader.** Master `cycle.py:216-220` rejects unknown keys and `cycle.py:222-226` requires schema 1. V1's claim that "absent values let a version-1 file run" (V1 K4) and that readers ignore unknown keys (V1 S10) therefore needs a loader change that V1 never lists. This is a real rollback trap, not a style point. (The per-repo planb loader is not in my snapshots, so this is verified for master only.)
3. **X-006 and C-005: the sweep reads the watcher.** D11's verdict keeps the sweep stateless with a fixed read list and no GitHub call. V1 adds a subprocess (`issue-watch status --all --json`, which does not exist yet) to every sweep and notes its own cost risk (RK-17, "may slow it", not measured). V2 leaves the sweep untouched and gives the observer one extra read source.
4. **K1 end state depends on RK-7.** The coordinator running `/sc:issue --claim` inside its own long-lived session is untested for context size, Skill tool access and the worktree check (V1 RK-7). In the interim V1 ships `start_mode: claim`, so the shared-worktree defect it set out to remove is present until S14 anyway.
5. **Bundled PRs.** V1 S9 (adapted PR 686) also carries the store-state union, `start_mode`, config v2, the parity test and the reasons table; V1 S11 carries the skill, eight verbs, F binding and a config-dir hook in one PR. A reviewer cannot judge that in one pass, and the mechanical check list is shorter than V2's (MC-1..MC-7).
6. **S10 delays lane 3** (C-006) behind the revert for no dependency.

V3:

1. **S-001: the stage table hides PR boundaries.** Eleven rows, each bundling several PRs ("S1: 693 then adapted 690 then C1, keep 661"; "S3: Contract/guard amendment then draft planb landed before 686; new ledger after rebase"). The repo rule that every PR goes through `/sc:pr-submit --monitor 3` cannot be applied to a row that holds several PRs. There are no per-PR sizes, no per-PR rollback and no named mechanical check ids.
2. **S-002: the owner-action list is telegraphic.** "Hold 686/690: drafts stay." "No hold: no protected rollout assumption." "Cap 0: uncapped." (V3 section 7, item 8) The last line reads zero as "uncapped", while V1 OA-16 reads "Keep 0" as "no notices", and V2 reads default 0 as D17 deferred. An owner who answers by chat needs to know what each answer does; V3 leaves that to the reader.
3. **S-004: host-specific paths in the interface table.** Rows carry `/home/coder/...` absolute paths while the sentence above the table says to derive home and Orca roots at install time. A table meant as the contract should not hard-code one host.
4. **X-004 and C-004: V3 reverses the settled direction.** D12 and D15 R-2 make `plan_body.py check` the single definition; V3 makes a not-yet-built package module canonical. Parity makes the runtime outcome similar, but this reopens a settled verdict, and it asks the PR 690 owner to change the skill script to follow code that does not exist.
5. **No revert-day details.** V3 S2 says "exact-master clean revert trial" but has no `git apply --check` of planb on the revert tree and no per-host install diff beyond a precondition word; the 29-module collection failure (D03) is not named.
6. **Thin built-today table.** 17 rows with no file:line evidence in the cells; it relies on two ledger citations. That makes the V3 table harder to check than V2 section 6 (31 rows with cites).
7. **Config keys added under `schema_version` 1** (V3 section 4 "Config keys" row) have the same loader problem as V2 (`cycle.py:216-220`), and V3 does not say the loader must change; V2 does (S12).

## 6. Concessions about V2

1. **X-003 is a real internal contradiction.** V2 K14 says an unenforced switch lets the coordinator start a real-issue worker after a throwaway run and flag unbound starts; V2 S15 and R1 say real issues stay off until the probe. The S15 reading is the one that meets the owner's G2 sentence. K14 should be rewritten to V3's wording: `enabled` stays false until a live F probe proves binding; throwaway issues only before that.
2. **C-002 and X-005: V2 puts machine state in the Coordinator worktree and a one-shot go entry on a tracked shared branch.** A go entry with a `used` flag is mutable, and a tracked file on `coordinators` can be pushed or can conflict. V2's own K5 fallback names `<state_dir>/wakes/` and flags the unverified `_precheck` interaction with ignored files. V1's split (machine state outside git, human records on the branch) is cleaner and V3 is right about go entries. I concede both.
3. **S-001: 21 stages is heavy for a small team.** Each stage means a PR plus a `/sc:pr-submit --monitor 3` cycle. V2 should say S11 and S12 may merge into one PR if the reviewer size allows, and that S15 and S16 stay separate.
4. **C-010: crash design is thin.** V2 adds `woken` and `acked` states and M1/M2, but has no per-boundary crash tests, no outbox replay for "marker seen, wake not written", and no rule for an unknown launch receipt beyond the built `unknown` state. V3 U-011 to U-014 should be imported into S11, S13 and S17 tests.
5. **U-004 and U-003: V2 has no named `waiting_reapproval` state and no `coordinator_absent` reason.** It handles C-INV-1 and C-INV-2 only as S19 tests. V1's named state is better design.
6. **C-011: V2 over-reaches on D16.** D16 has no VERDICT.md. V2 builds D16 into owner items 2 and 4 and the S0 test; the ruleset recommendation itself is supported by D05 and D14, but the D16 throwaway test and "layer 3" language should be marked as a proposal, as V3 does.
7. **S-004: row numbers 4 and 22 are missing** from the interface table. Cosmetic, but it looks like a lost row.
8. **C-012: the 24-hour go expiry and in-flight expiry are my numbers**, labelled UNVERIFIED but with no source. They should be shown as a default the owner can overrule.
9. **K5 and K9 lean on UNVERIFIED behaviour** (the precheck on ignored files; PR 693's result file shape for `test_wake_written_only_after_claim_ended`). Both are named in R9 and the closing paragraph, but they are real dependencies.

## 7. Responses to A-001..A-005

- **A-001 (a coordinator session survives context exhaustion; a restart resumes from files alone): QUALIFY.** Accept it only as a design requirement, not as a fact. WORKER-CONTRACT rule S6 treats exhaustion as a real state, and nothing in the three variants proves a restarted session reads its way back. V2 has the per-issue state file (interface row 13) and a restart cap of 3 (S17), but no test that a kill at each wave resumes from the state file alone. Required addition: V3's per-boundary crash tests (U-014) plus one test "kill the coordinator after `worker_done`, restart, the next action is derived from the state file and the ledger, not from chat history".
- **A-002 (`worker-start` always gives each worker its own worktree): QUALIFY.** It is unobserved (V1 RK-11 says so; D05's verdict says binding a `worker-start` worker "has never been observed"). Cap 1 limits the damage but does not prove isolation. Required addition: the S20 staging probe records the worker's worktree path and fails if it equals the `Coordinator` worktree. Until then no stage may claim "workers have separate worktrees" as fact.
- **A-003 (before any coordinator exists there is a place and format for recorded owner answers): REJECT.** No variant names it. V2 S0 says "the agent records each answer" while its `records/` folder is created only at S15; V1 and V3 are the same. Required fix: name one interim ledger now (a single dated file in the migration's own task package under `.dev/tasks/`, which the repo rule says is always staged; exact name UNVERIFIED and the owner can overrule), with the Q01 fields (quoted words, date, exact scope, who recorded), and move or reference it from `.dev/coordinators/records/` at S15. The owner never writes the file.
- **A-004 (one project is one repository checked out once on one host; no monorepo, fork or second host): ACCEPT.** It is realistic for a small team and V1, V2 and V3 all use host-local locks and files. State it as a limit in the spec (V3 already does: "no cross-host claim guarantee until a shared lease design is approved"). V1's own reverse case for K5 (a second host) is out of scope under this limit.
- **A-005 (a script-started depth-0 coordinator is a top-level session where `/sc:pr-submit --monitor 3` may run): QUALIFY.** D06 allows `/sc:pr-submit` only in an ordinary top-level session and never as a worker, and the script-started coordinator is exactly the contested amendment (contract lines 70 and 245, R9/R17/R25) that V2 S8 holds until the owner approves in chat. Until then only a person-opened coordinator may run `/sc:pr-submit`. V2's S20 plan (a person's go at every push and merge, person-opened session) already fits; the end-state text should say so and not imply a script-started coordinator may submit PRs.
