## 3. New evidence not given before

All reads were Read/Grep only; nothing was run. "planb" is `/home/coder/workspaces/worktrees/IronClaude/claim-handoff-planb`.

**(a) Do the planb loaders reject unknown keys? Yes, and they also refuse any schema version but 1.** planb `cycle.py:54` sets `SCHEMA_VERSION = 1`; `cycle.py:59` defines `_TOP_KEYS`; `cycle.py:223-226` raises "unknown configuration key: ..." for any other key; `cycle.py:231-233` raises "schema_version must be the integer 1". `generate.py:247` writes the per-repo file's `schema_version` from `cycle.SCHEMA_VERSION`, so per-repo files go through the same rules. This closes the UNVERIFIED in my C-015 and R-list. Consequence: every variant that adds a key (all three do) must widen `_TOP_KEYS`, and an older binary refuses the new file whether or not the version number changes. A version bump only changes which error text appears. So: stay at schema 1 (smaller diff), widen `_TOP_KEYS` in the same PR that first reads a new key, and add V3 Round 1's version-pair rollback test (old binary against new file must fail closed with `config_invalid`, and the rollback step restores the old files). The store is different: planb `record.py:254-268` has a migration chain, so a new store state can be added with a version step.

**(b) Can a poll-launched claim session and the standing coordinator coexist in one worktree? Not safely today; the code gives no protection and no signal.**

When the claim ends (`refs/claim.md:94`: "the claim ends here ... no agent is launched"), nothing in the argv or the skill closes that terminal. It very likely stays as an idle second agent in the Coordinator worktree. UNVERIFIED: only a live check settles it.
