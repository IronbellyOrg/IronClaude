# Round 1, Advocate for Variant 1 (opus, architect persona)

## 1. Position summary

V1 should be the spine of the merged plan because it is the only variant that draws a clean line between machine state (outside git, beside the store the poll already keeps) and human records (in the project), and the only one that ships rollback and authority switches (`start_mode`, `coordinator_autostart`) as config keys from the first schema change. V1 loses on three points and should take them from the others: the owner's G2 sentence (no real issue runs unbound, so V3's "off until the probe" wins), crash and idempotency depth (V3), and smaller watcher PRs plus an early sweep change (V2).

Evidence base used below: the three variants, the diff analysis, the verdicts D05, D06, D07, D11, and code in `/home/coder/.cache/ic-snap-20261120/{master,pr-a}`, each line re-read for this round.

## 2. Steelman of V2

Strongest version of V2's case: "Keep what is built, change the least, and make every step a small PR with a named mechanical check." It is right on several points.

- Poll claims as built (V2 K1). The poll already launches `/sc:issue --claim <N> --pipeline none`, saves `pending` before the launch (master `cycle.py:1091-1092`, "FR-010: durable before the launch call") and keeps `marker_in_window` (MR-2). Changing who claims means new, untested code; V2 keeps the tested path and gives a clear reversal condition (a live collision in the `Coordinator` worktree).
- Small PRs. V2 splits PR 686's useful parts into three PRs (S11 plan check and reasons, S12 keys and `owner/name`, S13 wake transport behind `wake_enabled` false). Each one can be reviewed in one sitting and reverted alone. For a small team that is a real advantage over one large adapted draft.
- Lane 3 early. V2 ships the sweep's `session_id`, `worktree_path` and saved JSON at S5, independent of lanes 1 and 2, exactly as D14 lane 3 allows. D11 asks for these fields with no dependency on the watcher (D11 VERDICT lines 18 and 20).
- Honest rollback caution (C-015). V2 warns that the config loader rejects unknown keys. That is correct: master `cycle.py:216-220` raises `config_invalid` on any unknown key, and `cycle.py:222-226` refuses any `schema_version` other than 1.
- The ten mechanical checks MC-1 to MC-10 (U-006), including MC-8 (NG-2 argv test) and MC-10 (reasons table pin), are the most complete merge checklist of the three.
- The S6 revert dry run as its own step with a recorded master sha and a `git apply --check` of planb's patch (U-007) is the cheapest way to find the RK-4 rebase conflict before anyone is committed to it.
- `coordinator_session` as a key (U-010) makes the name change after Coder 516 a config edit, which matches D07 item 4 (`ORCH-IronClaude` until 516).

Where V2 is weaker is in section 5.

## 3. Steelman of V3

Strongest version of V3's case: "This is an at-least-once system on one host; design every write so a crash or a repeat at any boundary has no second effect, and turn nothing on until proof exists." It is right where the others are thin.

- Crash design per boundary (C-010, U-011, U-012, U-014). V3 is the only variant that handles a crash between "claim marker seen" and "wake written" (outbox replay, `test_claimed_outbox_replay`) and a lost launch receipt (`test_unknown_launch_no_second_claim`). Both are real: master marks a launch `unknown` (`cycle.py:1106-1109`) and nothing today replays a missed wake. V3's integrity rules (one action id per write, exclusive create, temp plus rename, fsync of file and parent directory, symlink and size refusal, lock order) are concrete and testable, and pr-a's wake writer already does part of it (V3 cites `pr-a wake.py:269-299`).
- The owner's G2 sentence (X-002). V3 says plainly: no real issue before a live F probe proves binding. That matches D05's "strengths that must be kept": "Before any other issue runs through the flow, the worker must be bound" (D05 VERDICT line 47, quoting `issue-pipeline-guard-g2.md:9`). Owner rules win ties.
- Merge result uncertain (U-013): reconcile the exact head before any reuse of a go; a restart never restores a consumed go. This closes a gap V1 and V2 leave open.
- Go entries split into a consumable runtime record and a quoted, unchanging record (`runtime/asks/` plus `records/`). That gives both a one-shot flag and a human audit trail.
- Scope honesty: single host, no cross-host claim guarantee, a lease only as a later design (A-004), and every number with no source labelled a proposal.

Where V3 is weaker is in section 5.

## 4. Strengths claimed

1. **Machine state outside git, human records inside the project (C-002, U-002).** V1 puts wakes, acks, per-issue state, go entries and the grant use log in the per-repo state folder and keeps `.dev/coordinators/` for human-readable records only (V1 section 2 K5, section 4 rows "Wake file" to "Grants, use log").
   - The poll already owns a per-user state folder outside any checkout: master `cycle.py:187-192` defaults `state_dir` to `$XDG_STATE_HOME` or `~/.local/state` plus `superclaude/issue-watch`, and `cycle.py:271-272` refuses a network filesystem for it. V1 extends a built, checked location; V2 and V3 create a second runtime location inside a git worktree.
   - D07 item 1 gives each child cycle "its own lock, state directory, kill switch and day cap" (D07 VERDICT line 15). D07 item 10 says the owner accepted the direction of a `.dev/coordinators/` directory but "the naming convention is NOT decided" (line 24). V1 honours both: state in the state directory, records in `.dev/coordinators/`.
   - Runtime files in a worktree need a git-ignore rule in every project before the first wake, and any `git add -A` by the coordinator (which commits under K2) can pick them up if the rule is missing. V2 already has to name a fallback to `<state_dir>/wakes/` (V2 K5 "what would reverse it"). V1's choice is that fallback as the default.
   - It removes contradiction X-005 at the root: a one-shot go entry with a `used` flag never lives on a tracked branch.
2. **Rollback and future modes as config keys, not code branches (U-001, C-014).** `start_mode` (absent means `claim`, the built path) reserves the coordinator-claims mode in the schema now, so adding it later is a reader change, not a schema change, and switching back is one config value (V1 K1, S9 tests "absent `start_mode` means `claim`"). This matters because the built claim path launches the claim agent into the configured worktree (master `cycle.py:1086`, `launch_cwd=str(cfg.worktree)`), which after Coder 516 is the `Coordinator` worktree; D07 item 8 calls that a defect ("one worktree holds one live agent at a time", D07 VERDICT line 22). V1 is the only variant with a designed exit from that defect that does not depend on giving claim agents their own worktrees.
3. **Authority as a recorded switch (U-003).** `coordinator_autostart` (absent means false) plus the reason `coordinator_absent` turns D06 item 6 into something a test can check: a script may start a coordinator at depth 0 only "when its launch prompt cites an authorization the owner gave in chat and an agent recorded" (D06 VERDICT line 19). V2 and V3 state the rule in prose only; V1 makes the default the safe, person-opened case, which also keeps `/sc:pr-submit` inside an ordinary top-level session (D06 item 5, line 18; see A-005).
4. **A named state for hand-back round 2 (U-004).** V1's `waiting_reapproval` sits outside the cap, is re-checked by the poll, gets a new wake id, and expires to `stopped`. The gap is real: pr-a `cycle.py:992-994` returns `None` for any non-failed entry ("already woken, acknowledged or abandoned: never woken again"). V3 reaches the same rule (its K11, K12); V2 only tests it late (S19). V1 puts it in the store-state union from the first watcher PR, so the cap code never has to be rewritten to exclude it.
5. **Follows the settled direction of the plan check (C-004, X-004).** `plan_body.py check` is the reference and the package holds a parity-tested copy, as D12 and D15 R-2 say. V3 reverses it.
6. **Owner actions written for the owner (S-002).** Each of V1's 22 items gives the choice and then, on its own line, what that answer does to the plan (V1 section 7, for example OA-1 "Yes: S5 reverts PR 682 ... No, only the start gate: PR 682 stands ... S5 is dropped"). That fits the owner's rules (answers in chat, recorded by an agent, plain English) better than V3's telegraphic bullets.
7. **Five conflicts the others miss (U-005).** K11 (who starts a coordinator), K12 (close after merge rides on the merge go), K13 (no cron line before S14, so no third contract), K14 (never restart an `ORCH-*` name before Coder 516, consistent with D07 item 4), K15 (hand-back round 2). Each has a pick and a reversal condition.
8. **One PR per stage, 15 stages.** A middle size for a small team: fewer hand-offs than V2's 21, and no V3 rows that bundle five or six PRs (V3 S8 bundles wake, cap, restart, F binding, audit, hand-back and report-entry).

## 5. Weaknesses identified in V2 and V3

**V2**

1. **Contradicts itself on the binding switch (X-003).** K14 says `WORKER_BINDING_ENFORCED` false lets the coordinator start a real-issue worker "only after a throwaway-issue bound run passed, and it flags unbound starts"; S15 says the same constant false "keeps real issues off until the probe". A builder cannot implement both. Only the S15 reading matches the owner's G2 sentence (D05 VERDICT line 47).
2. **One-shot go entries on a tracked branch (X-005, C-009).** V2 section 4 row 14 puts `records/` "tracked on the shared branch `coordinators`", and row 17 puts the merge go entry there with a one-shot "used" state. A consumed flag in git must be committed, and pushed to survive a lost worktree; until then the tracked copy says "unused". Two worktrees on that branch can conflict on the same file. A mutable token does not belong in version control.
3. **Runtime state inside the `Coordinator` worktree (C-002).** `wakes/` and `state/` must be git-ignored in every project before the first wake, and V2 itself lists the fallback to `<state_dir>/wakes/`. One of its own risk lines rests on this choice (V2 K5 "`_precheck` rejecting a worktree with ignored files"); on master the worktree check only tests that the directory exists (`cycle.py:375`), so that particular fear is unfounded, but the git-ignore dependency is not.
4. **The K1 fallback contradicts a standing coordinator (X-001).** V2's live plan is "coordinator started only after the claim result file exists" (V2 R9). D07 item 4 says "every project has a running session" (D07 VERDICT line 18, "REQ R9"). A standing session cannot wait to be started; at cap 1 the claim agent and the coordinator still share one worktree (master `cycle.py:1086`). V2 narrows the defect; it does not remove it.
5. **21 stages and three PRs on Clay's area.** S11, S12 and S13 each touch `issue_watch/` and each needs its own review round and Clay coordination (owner item 6). The split is good for review size, but the plan should say who owns each and that S11 and S12 are new PRs, not edits to Clay's.

**V3**

1. **Reverses a settled verdict on the plan check (X-004, C-004).** V3 makes the package module canonical and the installed script the parity-tested copy (V3 "Issue claim to work pipeline", REWRITTEN). D12 and D15 R-2 name `plan_body.py check` as the single definition. Verdicts are settled; V3 does not say why it reopens one.
2. **Owner actions not in plain English (S-002).** Items such as "Hold 686/690: drafts stay.", "Protect only: prove coverage.", "Validate only: record raw-edit bypass risk." (V3 section 7) do not say what the answer does to the plan. The owner's rules ask for plain English and every answer is recorded from chat, so each line must be understandable alone.
3. **The notice cap read the unsafe way.** V3 says "Cap remains 0, not proposed 5" (dashboard ADOPTED) but then lists "Cap 0: uncapped." as an owner choice (section 7 item 8). V1 (OA-16 "Keep 0: no notices") and V2 (S12 "a bad `reach_daily_max` is a config error, never 'no cap'") read 0 as the restrictive value. Reading 0 as "no cap" breaks the fail-closed rule.
4. **Bundled stages are too big to review or revert (S-001).** V3 S1 bundles PR 693, adapted PR 690 and rule C1; S8 bundles wake, cap, restart, F binding, audit, hand-back and report-entry. V3's own text says "Each stage is a separate reviewable PR", which these rows are not.
5. **Schema version 1 with new keys (C-014).** V3 keeps `schema_version` 1 while adding the merge block, grants, caps and tiers. Master's loader rejects unknown keys (`cycle.py:216-220`), so an older binary meets a new file with a generic `config_invalid`; a version bump at least names the cause and makes rollback explicit.
6. **Host paths in the interface contract (S-004).** V3's table spells `/home/coder/...` throughout. V3 says they "illustrate this host only", but an interface table is a contract; it should use the variables the code uses (`$XDG_STATE_HOME`, `orca worktree list`), as D07 item 9 asks ("a worktree path read from `orca worktree list` rather than the literal `/home/coder/workspaces/worktrees`").
7. **Runtime state, including consumable go entries, in the `Coordinator` worktree** (`runtime/asks/<key>.json`), with the same git-ignore dependency as V2 weakness 3.

## 6. Concessions about V1

1. **"Unbound and flagged" breaks the owner's G2 sentence (X-002, C-003).** V1 S11 copies D05 item 3 wording ("keeps real issues unbound-and-flagged until a reviewed commit flips it", D05 VERDICT line 21). But D05 also lists the owner's G2 condition among "strengths that must be kept" (line 47), and its first action is an owner DECISION on whether "one more real issue [may] run unbound" (line 56). Until the owner answers that in chat, the owner's sentence governs: no real issue before the probe. V1 should adopt V3's position, with V1's "flagged" path kept only for a throwaway issue or an explicit recorded owner answer.
2. **Crash and idempotency depth is thin (C-010).** V1 has M1 and M2 tests but no design for a crash between the claim marker and the wake write, no lost-receipt test, and no rule for an uncertain merge result. V3's U-011 to U-014 should be adopted whole.
3. **S9 rollback claim is incomplete (C-015).** V1 S9 says "Rollback: revert; absent `start_mode` keeps the built claim path anyway". Once any per-repo file is rewritten to schema 2 with new keys, a reverted loader refuses it (master `cycle.py:216-226`). That fails closed, which is safe, but the rollback step must also restore version 1 files. V1 S10's "readers ignore unknown keys" is about the sweep JSON, not the config, and does not cover this.
4. **S9 is too large and the sweep change is too late (C-007, C-006).** One adapted draft carrying plan check copy, store union, `start_mode`, config v2, reasons pin and wake moves is hard to review. V2's three-way split is better. The sweep's two fields and saved JSON depend on nothing in lanes 1 or 2 and should ship early (V2 S5); only the watcher feed waits.
5. **The sweep `watcher` block couples two pieces (C-005, X-006).** It does not add a GitHub call (`issue-watch status` reads only the local store and audit log, master `cli.py:164-182`), so it does not break D11, but it ties watcher freshness to the sweep's five-minute cadence and grows the sweep's read list. V2's "observer reads `issue-watch status --json`" is the smaller diff on a verb that already exists with no reader. I keep the watcher block only as a later option.
6. **The coordinator-claims end state is unproven (RK-7) and costs a second code path.** For a small team, wake mode should be built only if the S14 live run shows the shared-worktree collision, or the owner asks for it. The schema key can exist from day one; the code need not.
7. **D16 left out entirely (C-011).** Even without a VERDICT.md, its owner decisions (ruleset symmetry, `integration` in or out) affect S0. V1 has the ruleset as OA-5 but should list D16's two choices as V2 does, labelled "not settled".
8. **No suggested values for unsourced numbers (C-012).** Asking the owner with no suggestion slows S12. V2's "24 hours, UNVERIFIED" is the better way to ask.

## 7. Responses to A-001 to A-005

- **A-001 (a coordinator survives context exhaustion and a restart resumes from files alone): QUALIFY.** All three plans assume it and none tests it. It holds only if every fact the coordinator needs between wakes is on disk: wake, ack, `issues/<N>.json` (phase, worker id, nonce, PR, head sha, round), go entries. V1's per-issue state file has those fields (V1 section 4 "Per-issue state"); V3 adds the startup reconcile ("Startup reconciles outbox, wakes, states and consumed goes before new work"). The merged plan needs one test: kill the coordinator after `worker_done` and before the commit, start a fresh session, and show it continues from the files with no second worker and no second claim. Until that passes, compaction is a stated risk, not an assumption.
- **A-002 (`worker-start` always gives each worker its own worktree): QUALIFY.** V1 is the only variant that names it as unobserved (RK-11, K9). D07 item 8 already allows "keeps the cap at 1 until it does" (D07 VERDICT line 22). The plan must keep `max_in_flight` at 1 and add an S14 live check that records the worker's worktree path and confirms it is not the `Coordinator` worktree before any cap above 1.
- **A-003 (a place to record owner answers exists before any coordinator): QUALIFY.** The gap is real: all three plans have an agent record each answer from S0, but `.dev/coordinators/records/` does not exist until the coordinator is built. Proposal: until S11, the agent appends each answer (quoted words, date, exact scope, who recorded) to one file in the main checkout, for example `.dev/owner-rulings.md` (name UNVERIFIED, owner may pick), and the first coordinator PR copies those entries into `records/`. This keeps the owner rule "every approval is given in chat and recorded by the agent; the owner never writes a file".
- **A-004 (one project is one repo checked out once on one host): ACCEPT.** It is true of every plan and of the built code: the poll's state folder is per user on one host and refuses a network filesystem (master `cycle.py:271-272`), and the dispatcher loops over one host's `orca repo list` (D07 item 1). V3 states the limit best ("a second host remains unsupported until a shared lease design is approved and tested"); the merged plan should copy that sentence. Monorepos and forks need no special case today because the fork rule already makes `origin` the only remote.
- **A-005 (a script-started coordinator is a top-level session where `/sc:pr-submit --monitor 3` may run): QUALIFY.** D06 item 5 allows `/sc:pr-submit` only in "the ordinary top-level launch" and never as a `worker-start` worker (D06 VERDICT line 18); item 6 allows a script start "at depth 0 (a terminal plus `ccsession`, never `worker-start`)" (line 19), and its own Unverified list says depth 0 for that start was "not run" (line 88, design U3). So it holds for a person-opened coordinator now, and for a script-started one only after the U3 live test. V1's `coordinator_autostart` defaulting to false makes the person-opened case the default, which is why V1 handles this best.
