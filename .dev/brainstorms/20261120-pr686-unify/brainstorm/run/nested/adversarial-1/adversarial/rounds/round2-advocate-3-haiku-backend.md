### 3b The existing dispatch store can carry the outbox, but not unchanged

**Already built.** The store permits pending only from no entry or failed; it refuses starting pending from unknown: `/home/coder/.cache/ic-snap-20261120/master/src/superclaude/cli/issue_watch/record.py:538-546`. Its sweep abandons orphaned pending and expired launched entries, and a later marker can turn launched, unknown or abandoned into claimed: the same file `:627-685`. The cycle skips an already claimed entry and checks a marker rather than relaunching unknown or a previously launched abandoned entry: `/home/coder/.cache/ic-snap-20261120/master/src/superclaude/cli/issue_watch/cycle.py:915-931`. So V3 should describe no second uncertain launch as a safeguard to preserve and regression-test, not wholly new functionality. A reporting lease expiry is not proof an external process died and is not permission to repeat a launch.

**Available building blocks.** Planb already atomically saves the whole dispatch document, flushes its containing directory, and has an exclusive nonblocking lock with file-owner and inode checks: `/home/coder/workspaces/worktrees/IronClaude/claim-handoff-planb/src/superclaude/cli/issue_watch/record.py:370-419`. Its existing 60-minute lease is explicitly a launched-entry reporting lease, not a merge-go expiry: the same file `:440-441`.

**Required schema work.** Both inspected stores have the same six lifecycle state names and no delivery fields in Entry. Planb's reader rejects extra entry fields and extra top-level fields, and the migration registry is currently empty: `/home/coder/workspaces/worktrees/IronClaude/claim-handoff-planb/src/superclaude/cli/issue_watch/record.py:168-175`, `:213-248`. A migration mechanism exists, but it refuses an older document without a registered step and refuses a newer version: the same file `:251-278`. This is not a free-form JSON file where an outbox field can simply be added. Extend the typed document, validator, serializer and transition logic together; provide a tested store-version migration. Keeping config version 1 says nothing about keeping this changed store at version 1.

**Minimum proposed transaction and replay sequence.** This is design, not built code:

1. Under the existing watcher lock, save one document containing both the claim evidence and a delivery intent with a stable wake id, repository, issue, round and target generation. Preserve the claim state; delivery progress must not erase its duplicate-claim protection. A retry of delivery never calls the claim launcher.
2. Finish the locked cycle and release its lock before delivery can enter coordinator work. Today's cycle encloses its steps and final commit in the lock: `/home/coder/.cache/ic-snap-20261120/master/src/superclaude/cli/issue_watch/cycle.py:682-709`. Thus release-before-delivery needs an explicit post-commit phase; the existing lock does not automatically give V3 that ordering.
3. Publish the wake from the saved intent. On a crash before publication, replay the same id. On a crash after publication, verify or republish equivalent content with that id; do not create a new claim or silently replace a different payload. A retarget deliberately creates a linked generation, not an unrelated duplicate.
4. The consumer saves matching issue/round state before ack. The producer later reacquires its own lock, reloads the current document, and records the ack only if wake, round, target and state revision match. Never save a stale in-memory document after unlocking. This avoids making two renamed files pretend to be one transaction.
5. Replay outstanding intents even when the ordinary candidate path skips claimed entries. That path presently returns already_dispatched before any new launch: `/home/coder/.cache/ic-snap-20261120/master/src/superclaude/cli/issue_watch/cycle.py:920-921`. Recovery cannot depend on entering the normal claim path again.

One extra boundary matters: mark_claimed also accepts a marker with no prior entry, with zero launches, for a manually claimed issue: `/home/coder/.cache/ic-snap-20261120/master/src/superclaude/cli/issue_watch/record.py:660-665`. Do not create adoption permission for every such row during migration. Distinguish poll-owned work from manual claims and recheck the owner's start gates. Ambiguous old claimed rows need explicit reconciliation, not an automatic new worker.

These changes use one existing store and one existing lock, not a new service. They still need kill-and-restart tests before and after the joint save, wake publication, consumer state save, ack, and producer ack save. Existing launched-entry protection does not prove the new cross-file recovery behavior.
