**R-4 M1: code in 686 or a requirement on the unbuilt skill? (L3, in depth) Resolution: BOTH, as two separate rules.**
State mechanics. The wake path has three writes: (W1) the coordinator writes the per-issue state file; (W2) it writes the ack file listing the item as taken; (W3) the poll sees the ack, sets the entry `acked` and moves the wake file to done (`cycle.py:777-810`, `wake.move_to_done`). If W2 lands and the crash comes before W1: the poll marks `acked`, no state file exists, `route.in_flight` counts only `pending|woken|unknown` entries, and `_examine` returns `None` for any entry that is not `failed` (`cycle.py:994`, "never woken again"). The issue is in no count and is never re-woken: silently lost. If the order is right (W1, crash before W2): the state file exists, the poll re-wakes, and the coordinator must take the item again without a second start, so "take" has to be idempotent on an existing state file.
Rule A, on the writer (a requirement on the unbuilt coordinator skill, PR B): write the state file first, then the ack, never the reverse; take is idempotent. Where it goes: `docs/designs/orchestrator.md` for assigned items, next to the existing plan-request rule at D:539 (D10 names D:229 and D:536 as the lines that miss it), and the take step of the coordinator skill, in the same step list as "read the wake directory at every return" (D10 action row 63). Test for the skill: its step list has W1 before W2.
Rule B, on the reader (code in the adapted 686, testable today): `_ack_step` accepts a `taken` item only when its state file exists; otherwise the entry stays `woken`, the ack file stays, and a decision line records `ack_without_state`. Test: ack lists item X, no state file, run the cycle, X stays `woken`. This protects against any writer, including a hand-run or an older skill. D07 moves the state files project-local, so the lookup function changes but the rule does not. CLAY is right that Rule A cannot be tested until PR B exists; Rule B can, which is why M1 must not be left as spec only.
