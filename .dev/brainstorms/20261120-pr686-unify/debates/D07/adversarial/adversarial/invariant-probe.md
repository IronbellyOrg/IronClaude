| INV-001 | interaction_effects | The in-flight cap can be a dispatcher pre-check that skips the repo with `coordinator_full`, and the cap "limits new work, not resends or resume" (OURS Round 2 text for C-004). | UNADDRESSED | HIGH | The skip happens in `_precheck` before `_run_child` (DISP 269-304, 432-435), so the whole child cycle does not run. The orphan sweep (`record.sweep`, REC 627-651: every `pending` becomes `abandoned`, a `launched` entry past its 60 minute lease becomes `abandoned`) and the claim observation (`mark_claimed`, CYC 959) run only inside the child (`_sweep`, CYC 807-822). A repo that is full because of an orphaned `pending` entry (child killed between `mark_pending` and `mark_launched`) is therefore skipped every sweep, and the one process that could clear the entry never runs. Wrong outcome: a repo stays at `coordinator_full` forever with no person involved. The consensus says the cap spares resends, but a repo-level skip also blocks the sweep and the resend. The cap check must sit inside the child after the sweep, or the child must run in a no-launch mode. |
| INV-002 | state_variables | "In flight" ends when an issue is "closed, dropped or escalated", so the count falls by itself. | UNADDRESSED | HIGH | In OURS nothing writes a closing state where the dispatcher reads. The store has `pending, launched, unknown, failed, abandoned, claimed` (REC 34-36); `claimed` is terminal and `unknown` leaves only through `reset N` by hand (`_RESETTABLE`, REC 448, 706-720; `sweep` never touches `unknown`). R26 makes `launch_unknown` a designed outcome. Three `unknown` entries fill the default cap of 3 until a person runs `reset`, which breaks R17 "nothing manual". The claim-file half of the count ("claim files whose issue is not closed") needs a writer that marks the file closed: the coordinator, through a push that needs the push grant (OA decision 2), and a dead or never-started coordinator never writes it. CLAY has this writer (the orchestrator's own `in_progress` to `done` state file, DESIGN 702, `route.py` `in_flight`); the hybrid text does not carry it. No lease or expiry exists for a claim file. |
| INV-003 | count_divergence | The adopted count text ("store entries in pending, woken or unknown, plus claim files whose issue is not closed") counts each issue once and matches OURS states. | UNADDRESSED | MEDIUM | `woken` is a CLAY state and is not in OURS `ENTRY_STATES` (REC 34-36). `launched` (up to 60 minutes, REC 440-441) is not in the list, so a session that was launched but has not yet pushed its claim file is counted nowhere; the dispatcher can launch once per sweep during that window, so up to `DAY_CAP` 6 (CYC 36) sessions can be live against a cap of 3. The store entry (host-local `state_dir`) and the claim file (shared branch) describe the same issue, and the adopted text has no "count once" rule; CLAY Round 2 item 1 (`route.py` line 411, `key not in state_files`) says a double count fills the cap early. | INV-004 | interaction_effects | Claim sessions started by the dispatcher and the standing `COORD-<RepoName>` session can share the one `Coordinator` worktree. | UNADDRESSED | HIGH | `launch_argv` starts every claim agent with `--worktree path:<worktree>` (LAUNCH 136-157) and R10 says that worktree "is the same Coordinator worktree, where the coordinator session works". With the cap at 3 there can be up to 4 live agents in one working tree. Q26's claim procedure needs "fetch origin/coordinators with no other unpushed commit, commit the claim alone, push at once" (Q26 final.md claim procedure); that precondition cannot hold when sibling agents commit and rebase in the same tree (index lock, a sibling's dirty file swept into a commit). Wrong outcome: a refused or polluted claim push; under "no pushed claim, no dispatch" the issue stalls. Nobody in the debate addressed this: both papers treat the Coordinator worktree as the place the session "starts". |
| INV-005 | guard_conditions | A dead coordinator "with work in flight" can be restarted safely from the dispatcher. | UNADDRESSED | HIGH | CLAY Round 2 items 3 and 4 (`route.py` `end_finished`, lines 562-603: `has_session` None decides nothing; resume only when an `in_progress` state file exists; unacknowledged work alone is left to the resend) are not in the consensus text, which lists only "resume wake" and "bounded restart". Wrong outcomes: (a) an unreadable terminal list is read as "not running" and a second `COORD-<RepoName>` starts beside a live one; (b) today `ORCH-IronClaude` on the main checkout carries the duties (R9), so a "restart" of `COORD-IronClaude` creates a second duty holder; (c) the fail-closed count is reused as a start trigger: DESIGN 702 says a damaged file "can only stop new routing, never cause an extra issue", but with restart keyed to "work in flight" a damaged claim file now starts a session a person may have closed on purpose. |
| INV-006 | state_variables | A restart is "bounded" and the resume wake reaches the session. | UNADDRESSED | MEDIUM | CLAY's bound is the 3-attempt rule of DQ2, counted on unacknowledged wakes (DESIGN 710: "the start counts as delivery attempt 1"). OURS has no wake file, no acknowledgment and no attempt counter in the store (`ENTRY_STATES`; `launch.py` can only `orca agent launch` a new claim agent). So the bound has no state variable, and the "wake marked resume" has no channel. A coordinator that dies on boot (login, rate limit, bad worktree) is restarted every sweep. A restart is also outside every existing brake: not a `launched:` line so it does not stop the sweep (DISP 447-450), not in `consumed_at` so not in `DAY_CAP` (REC 699-703), and not under the 270 s cap, which is checked only at the top of each repo (DISP 398). After a workspace restart every project's coordinator is dead at once: six restarts is about 150 s of the 270 s budget before any child. |
| INV-007 | state_variables | The count of claim files on the shared branch is current when the dispatcher reads it. | UNADDRESSED | MEDIUM | The state lives in `.dev/coordinators/` on a branch a host may not have fetched (Q26: "fetch origin/coordinators" is a step of the claim procedure, so the working tree is stale by default). | INV-010 | guard_conditions | The org-wide search pre-check "fails open", so it cannot hide an issue. | UNADDRESSED | MEDIUM | The adopted text skips nothing on a failed search, 100 or more results, or a missing field. Gain is small: `_precheck` makes about 6 calls per repo and the search saves them only for idle repos, with 6 repos (OURS R21; DESIGN line 137). |
