# Invariant Probe Results

## Round 2.5 — Fault-Finder Analysis

**Basis:** Round-2 V2 rebuttal (round-2-rebuttal-v2.md) plus cross-referenced V1 arguments embedded therein. Input files variant-1, variant-2, diff-analysis, round-1 transcripts, and round-2-rebuttal-v1 were not present on disk; the probe derives the emerging consensus entirely from the V2 rebuttal's citations of V1 positions, its numbered concessions (UC-1..UC-4), and its closing-posture synthesis.

**Emerging consensus (points where V2 explicitly conceded or both sides aligned):**

- UC-1: Transactional audit writes (auth INSERT + audit INSERT in same DB transaction)
- UC-2: `volatile-lru` Redis policy with db-0/db-1 segregation
- UC-3: Pen-test engagement starts during M5 beta (10% traffic), not after GA
- UC-4: GDPR erasure endpoint ships in M4, not M6
- 12-month audit-log retention from day one (not 90-day extensible)
- Shared TypeScript interface file in monorepo (not published `@auth/contracts` package)
- Threat model extracted to standalone document, reviewed at M1 exit

**Shared assumptions probed (inferred from both variants):**

- A-001: Redis is the correct token store for v1.0 refresh/reset tokens
- A-002: PostgreSQL is the sole durable state store
- A-003: bcrypt cost 12 is the target hash parameter
- A-004: 5-failure lockout in 15-minute window
- A-005: JWT access tokens + opaque refresh tokens
- A-006: SOC2 is the binding compliance constraint (Q3 audit deadline)
- A-007: 3-5 person team for v1.0

| ID | Category | Assumption | Status | Severity | Evidence |
|----|----------|------------|--------|----------|----------|
| INV-001 | state_variables | **Concurrent password-reset requests invalidate prior tokens without user notification.** Both variants store one active reset token per user. If a user clicks "Forgot Password" twice, the second token overwrites the first. The first email's link is silently dead. V2 acknowledges this as an intentional trade-off ("the user sees 'This link has expired'"). But the UX does not distinguish "your link was superseded by a newer request" from "your link expired naturally," which is the correct security behavior (prevents enumeration). However, neither variant specifies that the second request should invalidate or revoke the first token *atomically* — if the Redis SET for the second token succeeds but the email send fails, the user has no valid reset path. | ADDRESSED | LOW | V2 explicitly acknowledges the trade-off (Criticism 3). The "dead link" UX is standard (Gmail, GitHub). The atomicity gap is bounded: user can retry the request. |
| INV-002 | state_variables | **Redis restart atomically invalidates all in-flight reset tokens.** V2 stores reset tokens in Redis with TTL. A Redis restart (planned or crash) wipes every active reset token. V1 stores reset tokens in PostgreSQL, surviving Redis loss. The consensus has NOT resolved this: V2 maintains "acceptable UX under failure" while V1 offers durability. The merged variant must choose one. | UNADDRESSED | MEDIUM | V2 Criticism 3 response: "Redis approach is the correct trade-off for v1.0." V2 does not concede. V1 position is strictly stronger for token durability. Neither variant's position was adopted as consensus. Merge must decide: Redis (V2, simpler) or Postgres (V1, durable). |
| INV-003 | state_variables | **Account-lockout window tracking uses PostgreSQL timestamps.** V2 confirmed lockout state lives in `users.failed_login_attempts` and `users.locked_until` in Postgres (NE-2 response). The "15-minute window" requires comparing `locked_until` to `CURRENT_TIMESTAMP`. This is clock-dependent on the Postgres server. If the app server and Postgres server clocks diverge, the lockout window could be shorter or longer than intended. Neither variant specifies `clock_timestamp()` vs `now()` semantics or requires NTP synchronization as an operational prerequisite. | UNADDRESSED | LOW | Standard operational assumption; NTP is ubiquitous in cloud deployments. The window deviation from clock skew would be milliseconds, not minutes. LOW because the security impact of a slightly longer/shorter lockout window is negligible. |
| INV-004 | guard_conditions | **Refresh-token rotation lacks replay protection under concurrent requests.** V1 uses atomic Lua scripts for rotation (variant-1 M2 D2.6, cited in V2 NE-1 context). V2's rotation mechanism is not explicitly specified in the rebuttal for concurrency safety. If two refresh requests arrive simultaneously with the same refresh token, the Lua script atomically detects reuse (one succeeds, one triggers replay detection). Without atomic Lua (or equivalent `WATCH/MULTI`), both could succeed, issuing two valid refresh tokens and silently invalidating the first — a token leak. The consensus adopts V1's transactional posture (UC-1) for audit writes but does NOT explicitly adopt atomic Lua for token rotation. | UNADDRESSED | HIGH | This is a correct-safety issue. If the merged variant uses V2's auth-first build order (V2 closing posture recommends this), the refresh-rotation logic ships in M2 before any formal concurrency testing. Without atomic Lua scripts or equivalent CAS, concurrent refresh from the same client (e.g., multiple browser tabs, mobile app background sync) can create orphaned valid tokens. V1's Lua-script approach is referenced in the debate but never explicitly adopted by V2 or the consensus. |
| INV-005 | guard_conditions | **JWT expiry validation assumes clock synchronization between auth server and resource server.** Both variants issue JWTs with `exp` claims. If the auth server clock and the resource server clock diverge by more than the token's remaining lifetime, the resource server will accept expired tokens or reject valid ones. Neither variant specifies: (a) a `leeway` parameter for JWT verification, (b) NTP as an infrastructure prerequisite, or (c) a maximum tolerable clock skew. | UNADDRESSED | MEDIUM | Standard issue for JWT-based auth. The fix is trivial (add 30s leeway to JWT verification). The concern is that neither variant makes this explicit in their deliverable specs, so the implementer might not include it. |
| INV-006 | guard_conditions | **Rate-limit counter eviction under `volatile-lru` still allows burst amplification.** UC-2 adopts `volatile-lru` with db-1 segregation for rate-limit counters. But `volatile-lru` still evicts keys with TTLs under memory pressure. Rate-limit counters have short TTLs (e.g., 60s), making them *more* likely to be evicted than long-lived tokens. Under sustained memory pressure, rate-limit counters are evicted preferentially (they're cheap, short-lived), allowing attackers to bypass rate limiting until counters rebuild. | ADDRESSED | MEDIUM | V2's own capacity planning (Appendix B: 1GB Redis, ~50-60MB expected usage) makes eviction at 15-20x growth a distant scenario. The 70% monitoring alert (700MB) provides weeks of lead time. The counter rebuild cost is 1 request. Risk is bounded. |
| INV-007 | count_divergence | **5-attempt lockout boundary: "5th failure returns 423" implies the 5th attempt is the one that triggers lockout, but the user gets one fewer attempt than expected.** V2 D2.3: "5th failure returns 423." If the user makes 4 failed attempts, they can still try a 5th time (which triggers lockout). But from the user's perspective, they get 4 "real" attempts before lockout. The UX expectation for "5 attempts" is typically 5 *failed* attempts before lockout, meaning the lockout triggers on attempt 6. V2's wording is ambiguous: does the 5th failure *return* 423 (locking on the 5th), or does the 5th failure *cause* the next request to return 423? | UNADDRESSED | LOW | The boundary condition is standard in auth implementations. V2's Postgres `failed_login_attempts` counter starts at 0; lockout triggers when it reaches 5. This gives the user exactly 5 failed attempts before lockout, which is the standard interpretation. The wording in V2 D2.3 could be clearer but is not incorrect. |
| INV-008 | count_divergence | **No maximum refresh-token rotation chain length is specified.** Neither variant caps the number of times a refresh token can be rotated. If an attacker compromises a refresh token but the legitimate user continues rotating (creating a new token each time), the attacker's stale token triggers replay detection and revokes the entire chain. But if the attacker rotates *before* the legitimate user, the legitimate user's token becomes the "replayed" one. Without a chain-length cap, an attacker who rotates first can continue indefinitely. Both variants' "rotation invalidates previous" semantics protect against silent persistence, but neither specifies a maximum chain depth or a "suspicious rotation rate" detection. | UNADDRESSED | MEDIUM | The "rotate-or-revoke" model means an attacker who rotates first gains a valid session, but the legitimate user is immediately alerted (their token is rejected). The user then re-authenticates, and the attacker's token becomes the stale one. This is self-correcting but requires the user to notice and re-login. A chain-length cap (e.g., 100 rotations per 24 hours) would detect automated rotation attacks. Not a correctness bug, but a defense-in-depth gap. |
| INV-009 | collection_boundaries | **No maximum concurrent session count per user.** Neither variant limits the number of active refresh tokens a user can hold. A single user can accumulate unlimited sessions (mobile, desktop, tablet, multiple browsers). Each session is one Redis key. Under extreme cases (malicious user, compromised account, integration test creating thousands of sessions), Redis memory grows without bound for a single user. | ADDRESSED | LOW | V2's capacity planning allocates for 100K tokens across all users. A per-user cap (e.g., 10 concurrent sessions, oldest evicted) is a reasonable post-GA addition. For v1.0, the memory footprint of unlimited sessions per user is bounded by the overall Redis capacity and monitoring. |
| INV-010 | collection_boundaries | **Empty session set on logout-all returns ambiguous response.** The `POST /auth/logout-all` endpoint revokes all sessions. If the user has no active sessions (e.g., all expired naturally), the endpoint should return 200 (idempotent success) or 404 (no sessions found). Neither variant specifies this edge case. For an auth service, idempotent 200 is the correct behavior, but the implementer needs explicit guidance. | ADDRESSED | LOW | Standard RESTful convention: destructive idempotent operations return 200/204 regardless of prior state. LOW because any reasonable implementation will handle this correctly. |
| INV-011 | collection_boundaries | **Empty/oversized input validation for email and password not specified at the invariant level.** V2's TDD specifies field names (Section 7.1) but the rebuttal does not confirm whether email format validation, password length bounds (min 8, max 128 to prevent bcrypt DoS), or Unicode handling are specified as invariants or left to implementation. bcrypt has a 72-byte input limit; passwords longer than 72 bytes are silently truncated, which is a security concern if users expect their full password to be hashed. | UNADDRESSED | MEDIUM | bcrypt's 72-byte limit is well-known but frequently overlooked. If the service accepts a 200-character password but only hashes the first 72 bytes, two different passwords sharing the same 72-byte prefix collide. The fix is: pre-hash with SHA-256 before bcrypt. Neither variant is documented as specifying this in the consensus. |
| INV-012 | interaction_effects | **Rate-limited request may or may not count toward lockout counter.** V2 stores lockout in Postgres and rate-limit counters in Redis. These are independent systems. A failed login attempt that is rate-limited (429 response) may or may not increment the Postgres lockout counter, depending on implementation order: if rate-limit check occurs *before* credential validation, the lockout counter is not incremented. If after, the counter increments but the response is 429 (not 401). Neither variant specifies the ordering or whether rate-limited requests count toward lockout. | UNADDRESSED | HIGH | This interaction determines whether an attacker can bypass lockout by saturating the rate limiter. If rate-limited requests do NOT count toward lockout, an attacker can: (1) make 4 failed attempts (incrementing lockout to 4), (2) wait for rate-limit window to expire, (3) make 1 more attempt (lockout to 5), (4) the 5th attempt is the actual password guess. But if the attacker saturates the rate limiter with invalid requests that DO count toward lockout, they lock themselves out faster. The security-optimal behavior is: *all* credential-validation attempts count toward lockout, regardless of rate-limit status. The response should be 429 if rate-limited, but the lockout counter should still increment. This must be explicit in the merged spec. |
| INV-013 | interaction_effects | **GDPR erasure in M4 (UC-4) conflicts with SOC2 audit-log retention (12-month default).** UC-4 moves GDPR erasure to M4. UC-1 makes audit writes transactional. The GDPR erasure endpoint must nullify PII (email, display_name) but SOC2 requires retaining audit logs for 12 months. If the `DELETE /auth/me` endpoint nullifies the user's PII *in the users table* but audit logs still contain the email address in event payloads, GDPR compliance requires those audit entries to be scrubbed too. The consensus does not specify whether GDPR erasure cascades to audit-log PII. | UNADDRESSED | HIGH | This is a compliance conflict with real legal consequences. If a GDPR subject-access request reveals that the user's email persists in audit_log rows after account deletion, the service is non-compliant. The fix is either: (a) audit logs reference user_id only (never PII directly), with PII resolved at query time from the users table (which has been nullified), or (b) a cascading UPDATE on audit_log rows to nullify PII fields. Option (a) requires the audit writer to never include email/display_name in event payloads. The consensus's UC-1 (transactional audit writes) does not specify what fields are written to audit_log. |
| INV-014 | interaction_effects | **Refresh-token rotation + concurrent request from same client creates race window.** Related to INV-004 but from the UX perspective: a mobile app making two simultaneous API calls discovers its access token expired. Both requests attempt to refresh simultaneously. Without atomic rotation, one refresh succeeds and the other fails (stale token). The client must handle this gracefully (retry with new token). Neither variant specifies the client-side retry logic or the server-side behavior for the second request (should it return 401 with a specific error code indicating "token was rotated, re-authenticate"?). | ADDRESSED | MEDIUM | V1's atomic Lua script handles the server side correctly (one succeeds, one triggers replay detection which revokes the chain). V2's approach is less clear but the consensus leans toward V1's atomic rotation. The client-side retry is a frontend concern, handled by V1's AuthProvider or V2's M5 frontend. |
| INV-015 | interaction_effects | **Password reset does not invalidate in-flight login sessions.** If a user requests a password reset and completes it, the old password is invalidated. But existing sessions (refresh tokens in Redis) created with the old password remain valid until they expire or are explicitly revoked. Neither variant specifies that password-reset confirmation should call `TokenManager.revokeAllForUser()`. UC-4's erasure endpoint uses this primitive, but the reset-confirm endpoint is not specified to invoke it. | UNADDRESSED | MEDIUM | Standard security practice: password change should invalidate all existing sessions. The `revokeAllForUser()` primitive exists (V2 M4 reset-confirm endpoint references it per UC-4). The question is whether the consensus *explicitly* requires reset-confirm to call it. If not, an attacker who compromised the password and created a session retains access even after the legitimate user resets their password. |
| INV-016 | sufficiency_challenge | **"M3 delivers GA-ready auth" (V2 position) is insufficient if observability is a hard prerequisite for production traffic.** V2's M5 (beta 10%) is the first milestone with monitoring dashboards and alerting. M3 ships login/register/refresh endpoints with no production monitoring. If the consensus adopts V2's build order (M2 auth endpoints in Sprint 4), the team can demo endpoints but cannot safely operate them in any environment without M5's observability. V1 defers endpoints to M3 but includes observability in the same milestone. The merged variant's M3 (if following V2's order) ships endpoints without monitoring, creating a gap between "demo-able" and "operable." | ADDRESSED | MEDIUM | V2's M5 beta includes rollback triggers and monitoring. The gap is between M3 (demo) and M5 (production). The consensus does not claim M3 is production-ready; it claims M3 is demo-ready. The sufficiency challenge is whether "demo-ready" is confused with "deployable" by stakeholders. LOW because V2's M5 explicitly gates production on monitoring. |
| INV-017 | sufficiency_challenge | **Pen-test during M5 beta (UC-3) is insufficient if the pen-test engagement timeline exceeds the beta window.** UC-3 adopts "start pen test during M5 beta at 10%." But pen-test engagements typically take 2-4 weeks (scoping, testing, reporting, remediation). V2's M5 beta is 2 weeks. If the pen test starts at the beginning of beta, findings land after GA. The consensus does not specify pen-test duration or whether findings *must* be resolved before GA flip. | UNADDRESSED | HIGH | This is the highest-impact unresolved sufficiency challenge. UC-3 narrows the blast radius from 100% to 10% *during the pen test*, but if findings land after the 100% GA flip (which is the typical timeline for a 2-week pen test starting during a 2-week beta), the blast radius is still 100% at remediation time. | INV-018 | sufficiency_challenge | **12-month retention default (consensus) is sufficient for SOC2 only if automatic partition pruning is enforced.** The consensus adopts 12-month retention from day one. But retention requires both: (a) data is retained for 12 months, and (b) data is purged after 12 months (to prevent indefinite retention, which is a separate compliance concern). Neither variant specifies automatic partition pruning, and the GDPR erasure interaction (INV-013) may conflict with the purge policy for users who exercised their right to deletion. | ADDRESSED | LOW | Standard PostgreSQL partitioning with `DROP PARTITION` handles this. The implementation detail is straightforward. The GDPR interaction is the real concern and is captured in INV-013. |

## Summary

- Total findings: 18
- ADDRESSED: 7
- UNADDRESSED: 11
  - HIGH: 3 (INV-004, INV-012, INV-017)
  - MEDIUM: 5 (INV-002, INV-005, INV-008, INV-011, INV-013, INV-015)
  - LOW: 3 (INV-003, INV-007)

### HIGH-severity UNADDRESSED items (convergence blockers)

1. **INV-004** — Refresh-token rotation lacks atomic replay protection under concurrent requests. The merged variant MUST specify atomic Lua scripts (or equivalent CAS) for rotation, regardless of build order. Without this, concurrent refresh from the same client can create orphaned valid tokens.

2. **INV-012** — Rate-limited requests' interaction with lockout counter is unspecified. The merged variant MUST specify: credential-validation attempts always increment the lockout counter, even when the response is 429 (rate-limited). If rate-limited requests bypass the lockout counter, an attacker can bypass lockout by saturating the rate limiter.

3. **INV-017** — Pen-test engagement starting during M5 beta is insufficient if the pen-test report lands after GA flip. The merged variant MUST gate the 100% GA flip on pen-test report delivery (not just pen-test start). Without this, the blast-radius reduction UC-3 intends is illusory.

### MEDIUM-severity UNADDRESSED items (should be addressed before merge)

4. **INV-002** — Redis restart invalidates all in-flight reset tokens (V2 position). Merge must choose Redis or Postgres for reset tokens and document the trade-off explicitly.

5. **INV-005** — JWT expiry validation clock-skew leeway not specified. Trivial fix (30s leeway), but must be explicit.

6. **INV-008** — No maximum refresh-token rotation chain length. Defense-in-depth gap for automated rotation attacks.

7. **INV-011** — bcrypt 72-byte truncation not addressed. Pre-hash with SHA-256 or cap password length at 72 bytes.

8. **INV-013** — GDPR erasure conflicts with SOC2 audit-log retention. Audit logs must reference user_id only, never PII directly, or cascading PII nullification is required.

9. **INV-015** — Password reset confirmation does not explicitly revoke all existing sessions. Must call `revokeAllForUser()` on reset-confirm.
