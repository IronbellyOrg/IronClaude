# Round 1 — Advocate for Variant 1 (Opus Default)

## Position Summary

V1 is the roadmap of an engineering team that has shipped an authentication service before and knows where the scars are. It front-loads cryptographic isolation (M2 as a library milestone), commits to a zero-loss data posture on tokens and reset state (Postgres + `noeviction`), and books KMS/HSM, OpenAPI spec-first, an outbox audit pattern, and a 30+ scenario edge-case catalog as first-class deliverables — exactly the controls a Q3 SOC2 audit will look for. V2 reads faster and lighter, but its lightness is achieved by deferring or downgrading the very controls that authentication services fail on in production: signing-key custody, audit-log durability, reset-token survival, and explicit anti-enumeration mechanics. For a service whose remit explicitly includes SOC2 Type II and is the identity blast-radius for the whole platform, V1's posture is the correct one.

## Steelman of V2 (REQUIRED before any critique)

Before critiquing V2, I owe an honest reading of its strongest arguments. V2 is not naive — it is making a coherent set of trade-offs.

**Auth-first build order (S-001, C-001, X-001).** V2's strongest argument is YAGNI applied to crypto. Building `JwtService` + `TokenManager` in isolation in M2 (V1's order) before any endpoint exists risks designing a library API that doesn't fit the call sites the endpoints actually need. V2 says: "tokens have no meaning without a use case. Building tokens first creates unvalidated code that may need rework." That is a real engineering hazard — premature abstraction is a documented failure mode, and many auth libraries that look elegant in isolation end up with awkward seams when wired to HTTP. V2 also gets a real benefit: M2 ships running endpoints (even with a session placeholder) that can be smoke-tested by humans and stakeholders end-to-end, which is more demoable and de-risks PRD interpretation earlier.

**Separated frontend (S-003, X-002).** V2's strongest argument is coordination economics. A serial backend→frontend sequence eliminates mock-drift (the bug where frontend code is written against a spec that backend then changes), eliminates the cost of holding 2 FE engineers idle for the first ~8 sprints if backend slips, and lets the entire team focus on one concern at a time. V2 explicitly: "Serial approach reduces coordination overhead and eliminates mock-drift risk entirely." For a 3–5 engineer team without dedicated frontend capacity, this is the operationally cheaper plan.

**Graceful-degrade Redis policy (C-008, X-003, X-004, C-005).** V2's strongest argument is operational realism. `noeviction` on a Redis instance that runs out of memory means *writes fail* — i.e., new logins cannot issue refresh tokens, and the service degrades to "nothing works" rather than "old sessions get bumped." V2's `allkeys-lru` says: under memory pressure, oldest unused tokens are evicted, affected users re-authenticate (a 1–2 second annoyance), and the service stays *up*. For reset tokens, Redis is faster and simpler than a Postgres table; the trade is that on a Redis full restart, in-flight resets are lost — but users can simply request a new reset email, which is the well-trodden recovery path on every consumer auth product. V2 is choosing availability over a particular notion of durability, and for non-critical state with a cheap retry path, that's defensible.

**Filesystem / K8s-secrets key management (C-011).** V2's strongest argument is cost-fit. KMS/HSM introduces a hard external dependency (R-DEP-1 in V1's own register: "KMS unavailable at signing time — Critical impact"), adds 5–50 ms of latency per signing operation, costs money, and requires IAM/role plumbing. For a v1.0 GA, Kubernetes secrets backed by encryption-at-rest with quarterly manual rotation is a defensible baseline that thousands of production auth services run on. Adopting KMS later is a deliberate upgrade path, not a structural blocker.

**Code-first / no OpenAPI ceremony (C-003, C-004).** V2's strongest argument is that for a 6-endpoint internal service with one frontend consumer and one SDK consumer, the OpenAPI + Spectral + `@auth/contracts` package + contract-test generator scaffold is heavy ceremony relative to what TDD §8 already specifies. Code is the source of truth; the OpenAPI spec becomes another artifact to keep in sync. V2 keeps the contract implicit and verifies it via integration tests against real endpoints — which is what catches the bugs that matter anyway.

**Unique strengths.** V2 also genuinely contributes things V1 lacks: the GDPR right-to-erasure endpoint (U-010 — a real GDPR Article 17 obligation V1 missed), the state-mechanics invariants INV-01..10 (U-009 — testable system properties more rigorous than V1's prose), an infrastructure cost estimate (U-008), and the open-questions resolution log (U-011). These are not stylistic preferences — they are substantive engineering value.

V2 is making a coherent "lean, ship, harden later" bet. That bet is defensible. I now argue it is the wrong bet *for this specific roadmap* — but it is not stupid.

## Strengths Claimed

1. **Token-first sequencing isolates the highest-risk surface for early security review (S-001, C-001, X-001).** V1 §11 "Sequencing Rationale" states: "Splitting them out lets us security-review and benchmark the crypto-sensitive code in isolation, with property tests on rotation invariants, before HTTP concerns muddy the waters." This is operationalized in M2 D2.6 (property-based tests on rotation invariants using fast-check) and M2 D2.4 (key-rotation drill in staging *before any user touches the system*). The CVE history of auth libraries is dominated by JWT pitfalls (alg confusion, none-alg, kid injection, refresh-rotation races) — these are exactly the bugs that get buried under HTTP plumbing if you build endpoints first.

2. **Zero-loss data posture is required by the threat model, not aesthetic preference (C-008, X-003, C-005, X-004).** V1 M1 Scope-In: "eviction policy set to `noeviction` on the auth keyspace." This is paired with V1's reset-token storage in Postgres (D4.4: `password_reset_tokens` table with `used_at`, `expires_at`, `SELECT FOR UPDATE`), making both refresh tokens and reset tokens survive Redis loss. The Operational Readiness section (§10) explicitly accepts "refresh-token loss is acceptable — users re-authenticate" *as a DR scenario*, not as steady-state Redis behavior. The distinction matters: V2 makes daily-operations behavior tolerate eviction; V1 reserves eviction tolerance for declared disasters, which is a strictly stronger invariant.

3. **KMS/HSM is the right baseline for a SOC2-bound service (C-011).** V1 M2 D2.3 records the KMS decision in ADR-002 and §9.1 SOC2 Control Mapping ties this to CC6.6 (transmission) and CC6.1 (logical access). SOC2 auditors specifically inspect signing-key custody; an answer of "Kubernetes secret mounted to a pod" gets follow-up questions about who has `kubectl get secret` access. V1's R-DEP-1 mitigation (local key cache with 5-min lifetime, circuit breaker, readiness probe) directly addresses the KMS-unavailability concern V2 uses to argue against KMS.

4. **OpenAPI spec-first prevents the most common integration failures (U-002, C-003, C-004).** V1 D1.4 creates the OpenAPI 3.1 spec stub for all 6 endpoints *in M1, before any implementation*, with Spectral lint in CI, contract tests generated from spec in M3 (per M3 Exit Criteria: "verified by contract tests generated from OpenAPI"), and a versioned `@auth/contracts` npm package (D1.3, U-001) consumed by both backend and frontend. This is the structural fix for the integration bugs V2 will absorb via "mock drift" arguments later.

5. **Frontend coupled in M3 eliminates an entire class of late-discovery bugs (S-003, X-002).** V1's M3 ships LoginPage, RegisterPage, AuthProvider (D3.8) alongside the endpoints. Because both sides consume `@auth/contracts` (D1.3), there is no separate "frontend integration" milestone where shapes must be reconciled — the shapes are reconciled at type-check time from M3 forward. This also lets V1 run real Playwright E2E suites (D3.9: 12 negative-path tests) during the milestone that introduces the endpoints, instead of pushing that discovery to M5.

6. **Hardening before GA, not after (S-005).** V1 M6 is "Production Hardening & GA Rollout" — pen test (D6.2), load test (D6.1), DR drill (D6.7), and *then* staged rollout. V2 inverts this: M5 = "Frontend Integration and GA Rollout" with M6 = "Production Hardening and Compliance Validation" *after* GA. Going to GA before pen testing is a posture I cannot defend for an authentication service — V2 D6.1 itself admits "Critical findings remediated before M6 exit," which means the service ships to 100% of users with known pen-test-uncovered Critical/High vulnerabilities possible until M6 closes.

7. **Outbox pattern for audit logs (C-006, R-COMP-1).** V1 D5.2 wires audit-event emission via outbox semantics: "write audit event row in same DB transaction as state change, then async publisher drains to long-term store. At-least-once semantics guaranteed." V2 D2.4 writes audit events synchronously in the request flow. Under SOC2 (V1 §9.1 CC7.2, CC7.3), missing events are findings; the outbox makes "request committed but audit lost" structurally impossible. V2's synchronous write can drop audit events if the audit insert fails after the auth row commits — exactly the scenario auditors probe for.

8. **Edge-case catalog provides traceable mitigations (U-005).** V1 §13 enumerates 30+ scenarios across 7 subsections (token rotation, session races, reset tokens, rate limits, malformed input, partial failures, concurrent state). Each is mapped to owner milestone *and* proof artifact (e.g., 13.1 "Concurrent refresh from two browser tabs → M2 D2.6 integration test with N=8 parallel requests"). V2 Appendix B's 10 invariants are valuable (U-009 — I conceded this), but invariants describe what must hold; the V1 catalog describes the specific failure paths and how they are tested.

9. **Hard external-dependency tracking (S-009).** V1 §4 lists external dependencies as explicit Hard edges in the dependency table: "External: PRD approval → M1 Hard," "External: KMS access → M2 Hard," "External: SendGrid → M4 Hard," "External: Pen-test vendor → M6 Hard." V2's dependency section lists only intra-roadmap edges. The Hard/Soft classification (S-009) lets the team escalate provisioning risk *before* the depending milestone starts — V1 §8 Assumption 3 explicitly: "KMS access… failure to confirm by end of M1 escalates to a P1 dependency block."

10. **STRIDE threat model produced in M1, before code exists (U-003).** V1 D1.6 ships the threat model in the foundation milestone, signed off by sec-reviewer. V2 has no equivalent — security analysis is folded into M6 pen testing, which is post-hoc by construction. Threat modeling pre-code is cheap; threat modeling post-code requires either rebuilding or accepting findings.

## Weaknesses in V2

1. **V2's M2 ships endpoints that M3 retroactively modifies (C-002, X-005).** V2 M2 D2.3 explicitly: login returns "session identifier placeholder"; M3 D3.5 and D3.6 are described as "Update POST /auth/login (D2.3) to return AuthToken pair." This means M2 exit criteria ("p95 login latency < 200ms," "audit log rows written for every registration") validate a response shape and behavior that M3 changes. The integration tests written in M2 must be re-written in M3 — that is rework V2 imposes on itself in exchange for the "ship something demoable in M2" benefit.

2. **`allkeys-lru` on the auth keyspace is a security posture downgrade, not just an operational one (C-008, X-003).** V2 M3 Risks: "Set maxmemory-policy to allkeys-lru… Token loss is acceptable; users re-authenticate." But the auth keyspace also holds the lockout counter (`auth:lockout:<userId>` in V1 M3, equivalent state in V2), the rate-limit sliding window, and the revocation list (jti blacklist in V1 M2). Under `allkeys-lru` and memory pressure, an evicted lockout counter resets a locked-out attacker to zero failed attempts. V2 does not address this contamination — its mitigation only covers refresh tokens, not all auth-namespaced keys.

3. **Reset tokens in Redis lose all in-flight resets on Redis restart (C-005, X-004).** V2 D4.4: "Reset token storage: tokens stored as SHA-256 hashes in Redis… 1-hour TTL." A Redis restart (failover, memory exhaustion, planned upgrade, AZ failure) atomically invalidates every reset email in flight. For users who clicked "Forgot Password" 30 minutes ago and have not yet completed the flow, the link they receive is dead with no diagnostic visible to them ("Invalid or expired token"). V1 D4.4 puts these in Postgres with `expires_at` enforced transactionally, surviving Redis loss.

4. **GA before pen test (S-005, V2 §M5 vs §M6).** V2 M5 D5.7: "Phase 3 GA 100%" *precedes* M6 D6.1 "Penetration test." V2 M6 Risks even concedes this: "Penetration test finds Critical vulnerability requiring architectural change… extend sprint by 1 week rather than shipping with known Critical." But the architecture is already shipped at 100% by that point — the "extend sprint" mitigation does not retract production exposure. For an authentication service this is the wrong order.

5. **V2 audit log retention is internally contradictory (X-006).** V2 §M6 D6.2 exit criteria says "Confirm 12-month retention policy" while the SOC2 mapping discussion treats default as 90-day "extensible to 12 months." If the M6 step is missed or the partitioning is misconfigured, V2 ships with 90-day retention that fails SOC2 Type II evidence collection. V1 commits to 12-month from M5 D5.1 as a hard schema property, not a configuration toggle.

6. **No spec-first artifact means no contract tests (C-003, C-004).** V2 has no OpenAPI spec deliverable, no `@auth/contracts` package, no contract-test generation. V2 M3 D3.4 (`GET /auth/me`) and M5 D5.4 (ProfilePage) both depend on the UserProfile shape. Without a single source of truth that both consume, the validation is "integration tests against real endpoints" — which catches contract drift *after* both sides are written, not *before*.

7. **Outbox pattern absent — audit completeness depends on best-effort sync writes (C-006).** V2 D2.4: "writes to audit_log table for every registration, login success, login failure, and account lockout event." No mention of transactionality with the state-change row. If the auth-row INSERT commits but the audit INSERT fails (constraint, connection drop), the system has performed a state change without an audit record — the exact scenario SOC2 CC7.2 cares about.

8. **No threat model deliverable; security analysis is implicit (V2 has no D-N for STRIDE / threat model).** V2 mentions sec-reviewer sign-offs at milestone exits (M3 "sec-reviewer approves RS256 key management procedure," etc.) but never produces a standalone threat-model artifact. V1 D1.6 produces this as a signed M1 deliverable, which is what an auditor asks for during evidence collection.

9. **No anti-enumeration acceptance test until late (V2 M2 Exit Criteria vs V1 M3 D3.9).** V2 M2 exit criteria includes "same response time within 50ms" — a 50ms variance window is generous given bcrypt latency dominates. V1 M3 D3.9 commits to "± 25 ms variance over 100 trials" with explicit dummy-bcrypt-on-unknown-user mitigation. V2's M2 D2.3 doesn't actually specify the dummy-hash mitigation in the deliverable text (it appears in V2's risk row, not the deliverable spec), making the implementation contract weaker.

10. **No explicit edge-case catalog means scenario coverage depends on developer recall (U-005 absent).** V2 distributes edge cases across milestone "Risks" tables (≈3 per milestone). Compare to V1's 30+ scenarios mapped to owner+proof. When the implementer is writing M3 endpoints under sprint pressure, "things I might have missed" is the single biggest source of post-GA findings; a catalog is a checklist artifact, V2 has prose.

## Concessions

I owe at least two honest weaknesses in V1.

1. **V1 missed GDPR right-to-erasure (U-010).** V2 D6.3 ships `DELETE /auth/me`; V1 has no deletion endpoint anywhere in M1–M6. GDPR Article 17 is not optional, and a SOC2-bound auth service that cannot delete a user's PII on request will fail privacy review. V1 §9.1 references GDPR Art. 5(1)(c) (data minimization) and Art. 7 (consent) but is silent on Art. 17. This is a real gap V1 must absorb in any merged variant.

2. **V1 lacks an infrastructure cost estimate (U-008).** V2 cites ~$450/month production (3 K8s pods $150, PostgreSQL $200, Redis $100). V1 produces no equivalent. For sprint/engineering management, this matters less; for product-team budgeting and ops-team capacity planning, it matters. V1 should add this — the cost is one paragraph.

3. **V1's M2-as-library milestone is genuinely vulnerable to V2's "premature abstraction" critique (C-001).** I argued above that token isolation is correct for crypto-sensitive code, but I must concede V2 has a point: if M2 designs `TokenManager.issuePair()` purely from spec, and M3 then discovers the endpoint flow wants `issueAndAudit()` as a single call, M2 needs revision. V1's mitigation is that `@auth/contracts` and the OpenAPI spec land in M1 — so M2's library design is informed by the real endpoint contracts, not invented in a vacuum. But this mitigation is partial; V1 does still pay some "library before caller" cost in coordination overhead.

4. **V1's state-mechanics rigor is prose-based, not invariant-table-based (U-009).** V2's INV-01..INV-10 is a stronger format for testable system properties than V1's §13 catalog. The catalog and the invariants are complementary — V1 should adopt V2's invariant table format on top of its catalog.

5. **V1's open-questions are surfaced in §8 Assumptions but not closed in a resolution log (U-011).** V2 Appendix A tracks PRD/TDD open questions with owner, target date, status. V1 mentions PRD-OQ-1 and PRD-OQ-4 in passing (§13.3, §7) but has no consolidated open-question register. V2's format is better for tracking-board purposes.

## Shared Assumption Responses

- **A-001:** ACCEPT — Both variants commit to 2-week sprints / 12 sprints / fixed team. V1 §2 and Assumption 1 are explicit; V2 Roadmap Overview is explicit. V1's 15% vacation/onboarding buffer (§8 Assumption 1) is a strictly stronger commitment than V2's silence on attrition, but the underlying sprint math is the same.

- **A-002:** ACCEPT — Both variants require external provisioning of Postgres 15+ and Redis 7+. V1 §8 Assumption 2 (with TLS, encryption-at-rest, automated backups specified) is more explicit than V2's Assumption 2-3, but both treat infrastructure as a hard external dependency, and both define a local-fallback escape valve (V1 docker-compose D1.7, V2 Docker Compose mentioned in M1 risks).

- **A-003:** ACCEPT — Greenfield deployment, no user migration. V1 leaves this implicit (no migration deliverables anywhere in M1–M6); V2 makes it explicit (Assumption 7). I accept the assumption but concede V2's explicit statement is the better practice. If this is invalidated (acquisition, user import), both roadmaps require significant re-planning — V1 §8 has no surfaced response for that contingency, which is a documentation gap V1 should close.

- **A-004:** ACCEPT — Single-region deployment for v1.0. V1 §7 Out of Scope ("Multi-region active-active") and §10 ("DR: Postgres point-in-time recovery, Redis replicas in two AZs") establish this; V2 Assumption 10 mirrors it. Both correctly defer cross-region complexity — multi-region token validation would require cache-coherence work that is genuinely out of scope for v1.0.

- **A-005:** ACCEPT — SOC2 Type II audit in Q3 2026 is the hard external deadline. V1 §1 Executive Summary and §8 Assumption 12 are explicit; V2's M6 scope and SOC2 mapping table imply it. I accept but note V1's explicit treatment is correct here — when compliance is the binding constraint, naming it shapes every sequencing decision (M5 compliance milestone in V1 exists for exactly this reason; V2 distributes compliance across multiple milestones and concedes the explicitness gap).

- **A-006:** ACCEPT — NTP clock sync with <1s drift. Both variants require this for the JWT 5s clock-skew tolerance. V1 §8 Assumption ("clock skew, M2 risk mitigation via NTP monitoring") and V2 Assumption 13 are aligned. I qualify slightly: V1 M5 D5.6 commits to clock-drift monitoring as an alert rule; V2 has no equivalent monitoring deliverable. So the assumption is shared, but only V1 enforces it operationally.

- **A-007:** QUALIFY — Pen-test vendor ≤ 4 weeks lead time. V1 Assumption 8 is explicit, V2 implies it in M6 entry criteria. I qualify rather than accept because *neither* variant has a fallback (internal security team scan, alternate vendor pool, delayed-rollout option) if the assumption fails. Both ship the same risk; V1 surfaces it as an assumption to challenge, V2 buries it in entry criteria. The qualification: A-007 holds only if pen-test booking happens at M6 *kickoff*, not M6 entry — V1 §M6 Risks explicitly: "book engagement at start of M6, not end," which is the right operational discipline.
