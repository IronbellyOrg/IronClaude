| ID | Category | Assumption | Status | Severity | Evidence |
|----|----------|-----------|--------|----------|----------|
| INV-001 | state_variables | V2's default-role hook (D-M5.5) prevents authorization vacuum. **Violated**: M4 (OAuth, D-M4.3 auto-creates users) runs *parallel* to M5 (RBAC, D-M5.5 defines the hook). Any user auto-provisioned via OAuth before M5 merges has zero roles. The claim "no user exists without at least one role" holds only at full-system ship, not during integration testing or partial deployment. | UNADDRESSED | HIGH | V2 parallelization table week 5: M4 OAuth + M5 RBAC run concurrently. D-M4.3 callback creates user; D-M5.5 default-role hook is in M5. No sequencing guard prevents M4 from completing before M5. |
| INV-002 | state_variables | OAuth callback always returns an email, so auto-provisioned users satisfy the users.email NOT NULL constraint. **Violated**: GitHub API returns null email if the user has not set a public email address. Apple "Hide My Email" returns a relay address (safe), but GitHub null-email triggers a DB constraint violation on `email TEXT NOT NULL` (V2 schema line 123) or crashes the encryption module (which expects a non-null value to encrypt). | UNADDRESSED | HIGH | V2 schema: `email TEXT NOT NULL` (line 123 of variant-2). V2 D-M4.3 says "fetches user profile from provider" but neither D-M4.1 nor D-M4.3 specify handling of null/missing email. V1 has the same NOT NULL constraint (D-M1.1 `email CITEXT UNIQUE`). |
| INV-003 | state_variables | Deactivation revokes all sessions atomically. **Violated**: JWTs are self-validating — no DB lookup on every request. After deactivation, existing JWTs remain valid for up to 15 minutes (access token TTL). In-flight requests with valid JWTs that already passed middleware continue to succeed. The "revokes all tokens immediately" claim (V2 D-M7.6) applies only to *refresh tokens*, not to already-issued access JWTs. | UNADDRESSED | MEDIUM | V2 D-M3.4: "access JWT (15min TTL)." V2 D-M7.6: "revokes all tokens immediately." These are inconsistent — only refresh tokens can be revoked server-side. Access JWTs validate via signature alone (D-M3.5 RS256). Same issue exists in V1 (D-M2.4: 15min JWT, D-M3.1 jti denylist, but denylist is Redis-based and checked on refresh, not every request). |
| INV-004 | state_variables | RBAC cache invalidation propagates within "one request cycle" (V2 exit criteria). **Violated during parallel M4/M5**: If M4 (OAuth) creates a user and M5 (RBAC) has not yet seeded roles, the authorization middleware (D-M5.2) loads an empty permission set. The 5-min TTL cache then serves empty permissions for up to 5 minutes even after roles are seeded. | UNADDRESSED | HIGH | V2 D-M5.2: "loads roles + permissions from DB (cached in Redis for 5min)." V2 D-M5.3 exit: "cache invalidation works within one request cycle." But this only tests the *invalidation* path, not the *initial empty* path. Parallel M4/M5 schedule (week 5-6) creates the race. |
| INV-005 | guard_conditions | Refresh token reuse detection (V2 D-M3.7, V1 D-M3.1) correctly distinguishes token theft from legitimate concurrent device usage. **Violated**: Two legitimate devices (phone + laptop) both hold valid refresh tokens. Phone A refreshes: old token revoked, new token issued. Phone B then tries to refresh with the (now-revoked) old token. D-M3.7 triggers full revocation of ALL tokens. Both devices are logged out. The system cannot distinguish "legitimate racing" from "theft" because the protocol has no device-isolation mechanism. | UNADDRESSED | HIGH | V2 D-M3.7: "detects reuse of revoked token (token theft detection) and revokes all tokens for that user." RFC 6819 section 5.2.2.3 pattern. V1 D-M3.1: identical pattern. Neither variant implements per-device token families or device fingerprints in the revocation decision. |
| INV-006 | count_divergence | Argon2id hash time fits within the NFR-001 budget of p95 < 200ms total API response. **Violated**: V2 D-M3.2 specifies "hash verification in <500ms." V1 D-M1.3 specifies "~250ms per hash." The login response path includes: password hash verify (200-500ms) + DB user lookup (~5-10ms) + JWT signing (~1-2ms) + Redis session write (~1-2ms) + network overhead (~5-10ms). Even at V1's 250ms, the hash alone exceeds the 200ms p95 target. V2's 500ms upper bound is 2.5x the NFR. | UNADDRESSED | HIGH | V2 D-M3.2: "<500ms on target hardware." V2 NFR-001: "API response < 200ms" (traceability table). V1 D-M1.3: "~250ms per hash" + V1 D-M2.4 exit: "Login p95 latency <150ms" — the 150ms target is lower than the 250ms hash time alone. Neither variant reconciles hash cost with NFR budget. |
| INV-007 | count_divergence | Account lockout threshold semantics are unambiguous. **Violated**: V2 D-M3.9 says "locks after 5 failures in 15min." Does failure #5 trigger the lockout (user sees rejection on 5th attempt), or does failure #5 increment the counter and the 6th attempt is the first rejected? V1 D-M6.3: "10 failed login attempts per email in 15min" — same ambiguity. The difference matters: if 5 is the trigger, an attacker gets exactly 5 guesses; if 5 is the counter threshold and lockout starts at attempt 6, the attacker gets 5 free guesses plus an ambiguous 6th. | UNADDRESSED | MEDIUM | V2 D-M3.9: "locks after 5 failures in 15min" (ambiguous "after"). V1 D-M6.3: "10 failed login attempts per email in 15min" (same ambiguity). Neither specifies whether the lockout-generating attempt itself is rejected or succeeds before triggering. |
| INV-008 | sufficiency_challenge | V1's DEK rotation (D-M4.4) satisfies GDPR Article 17 right to erasure for individual users. **Violated**: Rotating a column-encryption DEK renders *all* users' PII ciphertext undecryptable, not just the requesting user's. This is a bulk erasure mechanism, not a per-user one. If User A requests erasure, User B through User Z also lose their decryptable PII. Per-user DEKs would solve this, but V1 does not describe per-user key management. The approach is effectively "destroy all data to erase one user's data," which is not erasure — it is system-wide data destruction. | UNADDRESSED | HIGH | V1 D-M4.4: "rotate the column-encryption DEK so historical ciphertext is undecryptable." V1 D-M1.2: "application-layer envelope encryption with KMS-wrapped DEKs" — describes a single DEK for the column, not per-user DEKs. Consensus notes: "Agreement: V1 has X-001 documentation defect." The DEK rotation approach is acknowledged but its all-users impact is not analyzed. |
| INV-009 | collection_boundaries | V2's "2 years configurable" retention (D-M8.5) can be extended to 7 years for regulated customers after launch. **Violated**: The retention cron runs daily and drops partitions older than the configured threshold. If the system ran for 2 years at 2-year retention, partitions from years 3-5 were already dropped and cannot be recovered. "Configurable" applies only to future data, not retroactively. A regulated customer onboarding at year 3 would find years 1-2 missing. | UNADDRESSED | HIGH | V2 D-M8.5: "Deletes audit events older than 2 years (configurable); runs as daily cron." V2 audit_events schema: "PARTITION BY RANGE (created_at)" — partition drops are non-reversible. The consensus disagreement on "7-year retention (V1) vs 2-year configurable (V2)" does not address the retroactive gap. |
| INV-010 | collection_boundaries | V2's RBAC permission check (D-M5.2) handles the case where a user has no roles (empty permission set). **Violated during M4/M5 parallel phase**: If OAuth auto-provisions a user before RBAC roles are seeded, the middleware loads an empty permission set and returns 403 on all protected endpoints — including `/auth/profile` (the user's own profile, which should be accessible to any authenticated user). The `self:read` permission only exists after D-M5.1 seeds it. | UNADDRESSED | HIGH | V2 D-M5.1: seeds `self:read`, `self:write` permissions. V2 D-M5.2: "checks required permission against user permissions; returns 403 if insufficient." V2 D-M4.3: "auto-creates user if new." M4 and M5 are parallel (V2 dependency graph: both depend on M3, no edge between them). |
| INV-011 | interaction_effects | SendGrid downtime during password reset is handled gracefully. **Partially addressed**: V1 has a circuit breaker with Redis-backed retry queue (D-M2.3: "fallback to queued retry via Redis-backed BullMQ/Celery"). V2 has no equivalent mechanism — D-M3.6 only mentions "SendGrid dynamic template IDs configured." In both variants, the user-facing experience is "check your email" with no indication that delivery is delayed. No variant provides a fallback channel (e.g., in-app notification) or user-visible delivery status. | PARTIALLY ADDRESSED | MEDIUM | V1 D-M2.3: "circuit breaker... fallback to queued retry." V2 D-M3.6: no circuit breaker or retry mechanism specified. Neither variant provides user-facing degradation. Consensus does not address SendGrid single-point-of-failure beyond acknowledging A-002. |
| INV-012 | interaction_effects | JWT signing key rotation (planned) is distinct from JWT signing key compromise (emergency). **Violated**: V1 D-M9.2 describes "dual-key serving" for planned rotation. V2 D-M3.5 describes "gracefully handles tokens signed with previous key during overlap period." Both assume a clean rotation. In a key-compromise scenario, the correct response is immediate revocation of ALL existing tokens (no overlap period). Neither variant defines an emergency procedure for "private key exfiltrated" that differs from planned rotation. | UNADDRESSED | MEDIUM | V1 D-M9.2: "dual-key serving (old kid still validates)." V2 D-M3.5: "gracefully handles tokens signed with previous key during overlap period." V1 D-M7.5 runbook for "token signing key compromise" is listed but the runbook content is not specified — only the title exists. |
| INV-013 | interaction_effects | Rate limiter and account lockout reinforce each other without interference. **Confirmed**: V2's login rate limit of 5 req/min (D-M6.5) combined with lockout at 5 failures in 15 min (D-M3.9) means an attacker can submit at most 5 attempts per minute, reaching the lockout threshold in approximately 1 minute. The lockout then blocks for 30 minutes. V1's 10/min/IP rate limit plus 10-failure lockout in 15 min has the same reinforcing interaction. Both mechanisms operate on different counters (rate limit = all requests; lockout = failed logins only) and do not interfere. | ADDRESSED | LOW | V2 D-M6.5: "5 req/min for login." V2 D-M3.9: "locks after 5 failures in 15min." V1 D-M6.2: "10/min/IP for login." V1 D-M6.3: "10 failed login attempts per email in 15min." The counters are independent and reinforce each other correctly. |
| INV-014 | sufficiency_challenge | V2's "no UPDATE/DELETE permissions for app user" on audit_events (Blast Radius Analysis item 4) is sufficient for tamper *detection*. **Violated**: Lack of write access is necessary for preventing app-layer tampering but is NOT sufficient for detecting tampering. It does not detect: (a) superuser/DBA direct SQL modifications, (b) backup restoration with tampered data, (c) replication bypass, (d) PostgreSQL operating-system-level file tampering. V1's hash chain + daily Merkle root (D-M6.4) addresses all four scenarios by providing cryptographic proof of integrity independent of database access controls. | UNADDRESSED | HIGH | V2 Blast Radius Analysis item 4: "audit logs cannot be tampered with (separate table, no UPDATE/DELETE permissions for the app user)." This is an access control, not an integrity proof. The consensus notes: "Disagreement: Tamper-evidence approach (Merkle root V1 vs role perms V2)" but does not resolve the sufficiency gap. |
| INV-015 | sufficiency_challenge | V1's cryptographic erasure via DEK rotation plus PII pseudonymization satisfies GDPR Article 17 "right to erasure." **Violated on strict interpretation**: (a) Article 17 requires erasure of personal data "without undue delay." Pseudonymization (replacing email with `deleted-{uuid}@deleted.invalid`) is recognized under Article 4(5) as a *privacy-enhancing measure* but not as erasure. (b) The audit_events table retains actor_user_id references to the deleted user. (c) Metadata JSONB fields may contain user-identifiable fragments. (d) The user_id itself, if linked to any external identifier (OAuth provider_user_id), remains personal data. A strict regulator could argue that DEK rotation + pseudonymization is "effective erasure" under Recital 26 (data no longer identifiable), but this is a legal judgment, not a technical certainty. | UNADDRESSED | HIGH | V1 D-M4.4: "PII pseudonymized (email -> deleted-{uuid}@deleted.invalid)... cryptographic erasure." V1 D-M6.4: audit_events retain actor_user_id. GDPR Article 17(1): "right to obtain... erasure of personal data." Recital 26: "to determine whether a natural person is identifiable, account should be taken of all the means reasonably likely to be used." The consensus acknowledges the erasure approach disagreement but does not address legal sufficiency. |

### HIGH-UNADDRESSED findings (9)

1. **INV-001**: Default-role hook fails during M4/M5 parallel execution — OAuth creates users without roles
2. **INV-002**: OAuth null-email (GitHub) violates users.email NOT NULL constraint, crashes provisioning
3. **INV-004**: RBAC cache serves empty permissions for 5 min after M5 seeds roles during parallel phase
4. **INV-005**: Concurrent legitimate device refresh triggers false-positive theft detection, logs out all devices
5. **INV-006**: Argon2id hash time (250-500ms) exceeds NFR-001 budget of 200ms p95 total response
6. **INV-008**: V1 DEK rotation erases ALL users' PII, not just the requesting user — not per-user erasure
7. **INV-009**: V2 "configurable" retention cannot retroactively recover already-dropped partitions
8. **INV-010**: OAuth-provisioned user with no roles gets 403 on all endpoints including own profile
9. **INV-014**: V2 role-permission-based tamper prevention is not tamper DETECTION — misses DBA/backup/OS-level attacks
10. **INV-015**: V1 crypto erasure + pseudonymization may not satisfy strict GDPR Article 17 interpretation

### MEDIUM-UNADDRESSED findings (3)

1. **INV-003**: JWT self-validation allows 15-min post-deactivation access window
2. **INV-007**: Lockout counter semantics ambiguous — "after 5 failures" may mean attempt 5 or attempt 6
3. **INV-012**: No emergency key-compromise procedure distinct from planned rotation

### PARTIALLY ADDRESSED (2)

1. **INV-011** (MEDIUM): SendGrid downtime — V1 has retry queue but no user-facing degradation; V2 has no fallback
2. **INV-017** was folded into INV-009/INV-010 analysis (PostgreSQL scaling acknowledged in load-test milestones)

### ADDRESSED (1)

1. **INV-013** (LOW): Rate limiter + lockout interaction reinforces correctly — no interference detected
