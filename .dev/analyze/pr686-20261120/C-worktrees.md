## Orchestrator, coordinator, sweep: same thing or not?

- **Owner's coordinator**: a session a person opens (ORCH-IronClaude on the main checkout, planned `COORD-<RepoName>`, `Coordinator` branch and worktree, `.dev/coordinators/`). It supervises workers under `WORKER-CONTRACT.md`, acts outward only on a grant row or a person's go, and pushes worker commits only on that go (zero-setup R10, R17, R24; Q26 final.md).
- **#686's orchestrator**: started or woken by a script, one session per repo, at most 3 issues in flight, tag `orchestrator-<short>-<n>`, runs `/sc:orchestrator`, holds a standing grant list (`issue.assign`, `issue.comment`, `pr.merge`, `issue.close`) and merges (design DQ2, DQ6, DQ8). It also keeps the living work report.
- **A third "coordinator" in the design**: the single report session with tag `coordinator` that runs `/agent-work-report` (design DQ12 and 5.7 point 7). That is Clay's work-report coordinator (IronFlow spec), not the owner's.
- **Sweep**: read-only report that "recommends nothing and changes nothing". #686 does not touch it. The design says the orchestrator does its own check-ins, so it re-does part of what the owner's coordinator loop does with the sweep. UNVERIFIED whether the orchestrator skill calls `/sc:sweep`.
- **#339 "orchestrator mode"** (owner epic) and #444 (`/sc:orchestrator --sub`): the design takes the command name `/sc:orchestrator` and leaves `--sub` to #444 (section 1.3, OQ5). The name also clashes with the owner's epic title.

Plain answer: a different thing with a clashing name, in the same role family. It does the coordinator's supervising job, but no person opens it and it holds a standing grant, which the owner's coordinator model does not allow. The design admits the contract conflict (ADD1) and fixes it with a new "Orchestrated issue flow" section in `WORKER-CONTRACT.md`. That section is PR B, not #686.
