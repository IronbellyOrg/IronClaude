## What this does

**Tiers by Coder role** (IronClaude #311: ironbelly's comment there asks for roles instead of groups, since the license has no groups)
- New workspace setting `CCSESSION_TIER_RULES`. Entries are space-separated, `<who>=<start tier>[:<tier>,...][+models]`:
  - `<who>` is a Coder username, `role:<coder role>`, or `*` for everyone else, including a terminal that doesn't know its owner.
  - A username entry wins, then the first matching role entry, then `*`.
  - Roles come from `CODER_WORKSPACE_OWNER_ROLES`, which the Coder template sets (companion Coder PR).
- `+models` also lists each model of the owner's tiers in `/model`, ordered by the new `CCSESSION_MODEL_ORDER` setting.
- The line follows the same one-line safety rule as `CCSESSION_ACCESS`. A broken entry that applies to the owner stops the launch rather than opening every tier.
- `CCSESSION_ACCESS` becomes the older form, read only when the rules line is absent.

**Tier names can end in a letter:** `tier1a`, `tier1b` (`T1a_WINDOW`, `T1aModel01`, picker id `claude-gw-tier1a`). `--tier 1A` also works.

**New tier layout** (owner's spec, `ccsession-models.json` 2026-10-28.1). The models and windows themselves stay in the workspace settings file.

**Safe for workspaces still on older images**
- Older ccsession rejects the new model data, because it can't read letter tier names, and keeps its own copy.
- Older ccsession reads only `CCSESSION_ACCESS`.
- The companion Coder change keeps the old Tier 1 slots, so those workspaces keep working until they update. This was checked with master's code against the new settings file: no errors.
