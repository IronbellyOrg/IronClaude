## Feature Summary

Add the skill `sc-closeout-protocol` and its thin command `/sc:closeout <PR>`. After a pull request is merged, it checks that what merged is what was asked for, then settles the pull request's issue, its entry in the work report and its worker, each with a stated final status or an escalation that says why not. The orchestrator of issue #655 calls it in wave 8, and a person can run it by hand on any pull request.

## Problem Statement

A pull request can be merged and still leave loose ends: the issue is open or has no closing note, the worker that built it is still held, the issue is still marked in progress in the work report, and nobody checked that what merged is what was asked for.

This happened on 2026-11-19. IronClaude PR #661 (issue #651) was merged by a person (Ryan), and nothing settled its worker or its report entry until a human noticed an hour later. (In that case the merge itself closed issue #651, because the pull request body says `Closes #651`; the loose ends were the worker and the report entry.)

The orchestrator of issue #655 closes out the pull requests it merges itself, but a person merging by hand, or any other session, has no such step. The same steps are needed in both cases, so they belong in one skill that both use.

## User Story

As a maintainer who merges a pull request by hand, or as the issue-polling orchestrator that merges one itself, I want one command that settles the merged pull request, its issue and its worker, so that nothing is left silently in progress and what merged is checked against what was asked for.

## Proposed Solution

A new protocol skill `sc-closeout-protocol` with a thin command `/sc:closeout <PR>`, built in the same pattern as `sc-issue-protocol` and `commands/issue.md` (a thin command whose Activation names the protocol skill; a `SKILL.md` with the frontmatter, Will Do, Will Not Do and an error table; `refs/`, `templates/` and `scripts/`).

What it does, on a pull request given as a number or URL (the repo is always the `origin` repo):

1. Truth check after the merge. A script reads the pull request state first (merged or not, by whom, at what commit). Then it compares what merged with what the pull request held, using a three-dot diff against the base. It never decides from commit ancestry, because a squash merge leaves the original commits out of the base history. The script returns fixed results.
2. Update and close the issue. The closing note says what merged and who merged it. People are credited by name; the note never names the agent or the model (the gateway hides which agent did the work). The pull request body is checked for a link to the issue. An issue the merge did not close is closed.
3. Two words with fixed meanings: "completed" means merged, "deployed" means verified in the place it runs. The skill never writes "deployed" without a check.
4. Never leave an item silently in progress. The issue, the work report entry and the worker's Orca task each end with a stated final status, or with an escalation that says why not.
5. Work for a merge it did not make (a person merged first), and work with no orchestrator running.
6. Return a short result. When the orchestrator calls it (wave 8 of the orchestrator design, after the merge and the close and before the work report refresh), the orchestrator records the result; when a person runs it, the same result is printed. The orchestrator design titles wave 8 "Close and drop the entry", so the spec fixes the exact point inside that wave.

Judgment is used only for the closing note and for deciding what an item's final status is; everything else is a script.

Source: this is an adoption, not a rewrite. The closeout skill and `branch-landed.sh` in https://github.com/Simple-With-Us/AI-Fleet-Coordinator (`skills/closeout/SKILL.md`, `scripts/branch-landed.sh`) are Jay Wedgeworth's work, published under Apache-2.0, and the owner has approved using them. The spec and the build start from those two files and change only what our setup needs (our command and skill layout, our `gh` and Orca calls, the work report entry, the rules on naming people and never the agent); they do not redo the design. The Apache-2.0 notice and a statement of what was changed stay with the adopted files.

This is its own small pull request, separate from the orchestrator pull request of issue #655.

## Alternatives Considered

- Putting these steps only inside the orchestrator's wave 8: not chosen. A person merging by hand, or any other session, would still have no closeout step. One skill that both use avoids two copies.
- Writing the closeout skill from nothing: not chosen. Jay Wedgeworth's closeout skill and `branch-landed.sh` already do the truth check and the closeout, and the owner approved using them (Apache-2.0), so the work is to adapt them, not to redesign them.
- Deciding the merge verdict from commit ancestry: not chosen. A squash merge leaves the original commits out of the base history, so ancestry gives the wrong answer; the pull request state plus a three-dot diff is used instead.

## Impact Analysis (Blast Radius, Integration Impact)

- Blast Radius: the new files only, plus the registration edits above. Writes go to the issue (a closing note and a close), the work report entry and the worker's Orca task, so a wrong run could close an issue or release a worker too early. The skill reads the pull request state first and acts only on a merged pull request, and it never closes an issue twice.
- Integration Impact: issue #655 changes its wave 8 text to call `/sc:closeout` (belongs to #655). In this repo: the routing guide and its plugin copy, `tests/core/test_how_we_work_routing_table.py`, `tests/recommend/test_routing_refresh.py` and `docs/user-guide/commands.md`. `make sync-dev` copies the new skill and command into `.claude/`, and `make verify-sync` must pass.

## Risks & Mitigation

- A squash merge hides the original commits. Mitigation: pull request state first, then a three-dot diff against the base; tests with a fake `gh` and `git` for each merge type, none using commit ancestry.
- Writing "deployed" when nothing was checked. Mitigation: a fixed meaning for each word and a test that fails when "deployed" appears without a recorded check.
- Two actors settle the same pull request (a person and the orchestrator). Mitigation: read the current state first; an issue already closed is not closed again.
- An item left silently in progress. Mitigation: each item ends with a final status or an escalation, and a test fails otherwise.
- The work report entry surface is not in IronClaude yet. Mitigation: the spec defines the interface this skill uses; where the surface is absent, the result reports an escalation for that item instead of skipping it.
- The agent or the model named in a note a person reads. Mitigation: a test on every output for the agent and model names, with people credited by name.
- The repository is public. Mitigation: repo-relative paths only, and a test that no secret is printed or written.

## Fix approach

Repo: IronbellyOrg/IronClaude. Base branch: master. Own small pull request, separate from the orchestrator pull request of issue #655. Work on a feature branch from `origin/master`; open the pull request only through `/sc:pr-submit --monitor 3 --head <branch>`.

Commands, in order: `/sc:design` on this issue (a spec, `--type architecture --format spec`), then independent `/sc:spec-panel --mode critique` reviews by readers who did not write the spec, then the owner approves the spec before anything is built; after approval `/sc:workflow` on the spec, `/sc:implement` on the tasklist, and `/sc:pr-submit --monitor 3 --head <branch> --title "..." --body "..."`.

Steps, in order:

- Step 1: Write the spec (`docs/designs/`) as an adaptation of Jay Wedgeworth's closeout skill and `branch-landed.sh` (read both first; say what is kept as is and what changes for our setup): the flags, the steps of the truth check, the result it returns, how the orchestrator calls it and how a person runs it, which parts are scripts and which need judgment, what it writes where, where the Apache-2.0 notice goes, and the tests. Get it reviewed and approved before any build.
- Step 2: Add the skill `src/superclaude/skills/sc-closeout-protocol/` (`SKILL.md`, `refs/`, `templates/`, `scripts/`), starting from the adopted skill, and the thin command `src/superclaude/commands/closeout.md` that activates it, following `src/superclaude/skills/sc-issue-protocol/` and `src/superclaude/commands/issue.md`.
- Step 3: Start the truth check from the adopted `branch-landed.sh`: pull request state first, then a three-dot diff against the base, and no commit-ancestry test, with fixed results. The skill uses judgment only for the closing note and for deciding what an item's final status is. The script's output style can follow `src/superclaude/skills/sc-pr-submit-protocol/scripts/finish-merge.sh` (one stdout line, a fixed failure token).
- Step 4: Register the command: add a row to the `other-commands` block of `src/superclaude/core/HOW-WE-WORK.md` and copy the file to `plugins/superclaude/skills/sc-recommend/refs/HOW-WE-WORK.md` (the parity test needs identical files); add `closeout` to `_OTHER_COMMANDS` in `tests/core/test_how_we_work_routing_table.py` and to `_POST_REFRESH_ADDITIONS` in `tests/recommend/test_routing_refresh.py`; add the row and section to `docs/user-guide/commands.md`.
- Step 5: Add the tests listed in the Test plan.
- Step 6: In the orchestrator design (issue #655), wave 8 calls `/sc:closeout`; that text change belongs to issue #655, not to this pull request.

Assumptions: the two new test file names; the registration list in Step 4 (taken from the tests that pin the command lists); that the plugin mirror needs only the routing guide copy; that the spec lives under `docs/designs/`; and that the script language (Python as in `sc-issue-protocol`, or shell as in `sc-pr-submit-protocol`) is for the spec to choose.
