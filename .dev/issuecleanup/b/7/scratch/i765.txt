## Feature Summary
Protect the coordinator's Orca message watch from Claude Code's low-memory background-command cleanup. Separately, measure what should be stopped or limited instead, recommend a policy, and raise follow-up issues for anything to build.

## Problem Statement
A developer's coordinator lost its background message watch under critical memory pressure. Claude told the model not to restart it automatically, so the coordinator stopped receiving messages. This stops a background command, not a Claude session.
Claude Code 2.1.331 applies this rule only when all conditions hold: runtime pressure is `critical`; no session input for 30 minutes; no turn or helper agents running; `/proc/meminfo` has `MemAvailable` below both 10% of `MemTotal` and 4 GiB; and no earlier pressure stop in 30 minutes unless terminal input occurred since. The log is `LocalShellTask <id>: reaped under critical memory pressure after <n>m idle`. Its notice says to start Claude with `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1`; setting it inside an already running Claude does not work. The switch protects every background command in that session, not just the watch.
The watch is `orca orchestration check --wait --types status,dispatch,worker_done,merge_ready,escalation,handoff,decision_gate,question,heartbeat --timeout-ms 300000 --json`. It ends and is started again every five minutes. Measured real memory (PSS, which apportions shared memory) was about 33 MB per watch versus 110 MB in RSS; it stayed flat over 90 seconds. Four plain Orca calls each peaked at 109 MB for 0.2 seconds because each loads the Orca runtime. Stopping the watch recovers little memory but breaks coordination.
The same workspace's 12 Claude sessions, including helper processes, held 0.44-0.62 GB each (about 0.53 GB average), whether Orca marked them working or done. Claude itself held 250-400 MB, the Playwright plugin server about 107 MB per session, and codegraph servers 50-190 MB; idle CPU was 0.2-0.8% of a core each. Issue #648 measured codegraph first-index peaks of 3.6-4.0 GiB per new checkout: ten concurrent builds reduced available memory by about 34 GiB and doubled build time. The workspace had no memory cap (`memory.max=max`, no limit in the Coder template); its roughly 9 GB was part of roughly 49 GB host use, with 77-80 GB host memory shared across workspaces and 4.5 of 5.3 GB swap used. These are starting measurements, not a universal stopping policy. Source for runtime behavior and measurements: orchestrator's verified investigation, 2026-11-24, including the installed Claude program at `/opt/nvm/versions/node/v24.22.2/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe`.

## User Story
As a coordinator operator, I want its message watch to survive Claude's low-memory cleanup so that messages keep reaching the coordinator, and I want measured evidence before deciding which other processes to stop.

## Proposed Solution
**Part 1, change:** pass `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1` in the environment before starting the coordinator's Claude process. Decide and document whether this applies only to coordinator launches or all ccsession launches. Prefer a launch-time environment assignment over relying on settings whose timing is unverified. Do not solve this by telling the model to restart a command against Claude's notice.
**Part 2, research:** compare idle or finished sessions, open Playwright browsers, concurrent codegraph first-index builds, and a per-workspace memory cap under representative load. Measure memory actually recovered or peak memory avoided against work interrupted, recovery cost, and host impact. Recommend what to stop, limit or leave alone, with thresholds and follow-up issues; do not implement that broader policy in this issue.

## Out of Scope
Changing Claude Code itself; automatic watch restarts that disregard its notice; implementing a session reaper, browser cleanup, index scheduler or workspace memory cap before the research and follow-up decisions. Existing sessions are not retroactively changed by a launch fix.
