## Feature Summary

The plan for #655 turns each of the 21 Medium review findings into a task of the piece that owns it or records a reason it is not needed. Notes are fixed where the text is touched anyway.

## Problem Statement

Independent readers found 21 Medium findings while reviewing the issue-polling orchestrator design spec. None is fixed in the spec; the plan and pull request workers must handle them. About 40 notes remain in the source reports.

## User Story

Not known yet

## Proposed Solution

Run `/sc:workflow` on the approved spec for #655. Turn each Medium finding into a task of the piece that owns it or record a reason it is not needed. Fix notes where the text is touched anyway. The notes stay in the source reports: spec-review-part1.md, spec-review-part2.md, spec-review-part1-r2.md, and spec-review-part2-r3.md, kept in the orchestrator session records, not in this repo.

## From review 1, part 1 (spec-review-part1.md): Medium

Real defects that no named decision rests on; follow-up candidates.

- **M1. What happens to an assigned issue that is filtered out (unlisted or disabled repo, other assignee, day cap) is undefined, so R7 or the "Needs you proposal once" rule fails.** The store has no state for a skipped issue (4.10 `ENTRY_STATES`: `pending, woken, acked, unknown, failed, abandoned`), and step 8 filters before candidates exist. Either the issue stays "new" every cycle (a wake every 5 minutes, against R7 and the zero-token metric) or it is dropped silently (4.4's "Needs you proposal the orchestrator makes once when an issue shows up in an unlisted repo" has no producer, and the wake example shows `repo_not_listed` inside `skipped[]`). Evidence: spec lines 243 to 248, 290, 277, 174, 193, 390. The 17 open assigned issues found today include repos (IronOrca 5, Coder 3, Ironeye 1) that may not be listed.
- **M2. `--take` contradicts the wake rules.** Section 4.3 rule 2 (line 244) says `--take` "writes a synthetic wake"; wave 0 (line 440) says `--take` has no wake file and no acknowledgment "because the poll alone writes wake files"; 3.7 item 3 says the orchestrator never writes a wake file.
- **M3. Acknowledgment reasons are not in the poll's closed reason table.** 3.6 has the poll record skip reasons such as `claimed_elsewhere`; the acknowledgment also carries `malformed_item`, `co_assigned`, claim stops. None is among the 53 reasons of 4.7. `audit.py:280` and `:393` reject any reason not in `REASONS`, and 4.7 says a test asserts the table's exact contents, so the quoted 53 and that test are wrong if these are logged as reasons. Decide: store them as free `ack_reason` text outside the audit reasons, or add them to the table.
- **M4. `origin_mismatch` has three meanings.** Today it is a cycle reason with exit 2 (`audit.py:32`) used for the one worktree (`cycle.py:670-678`); `Config.worktree` is removed. 4.4 says a per-repo mismatch "is `origin_mismatch` and the issue is skipped"; the wake schema (3.4) lists `origin_mismatch` as a `checkout_state` of an `assigned` item (not skipped); DQ4 makes it escalation rule 8. 4.7 says every other reason keeps its kind and exit code, so a per-repo mismatch would stop the whole cycle with exit 2 unless the spec says otherwise.
- **M5. `gate-create` needs a Task and waves 0 to 3 have none.** `orca orchestration gate-create --help`: `--task <task_id>` is required. Escalations that happen before wave 4 creates a Task (malformed wake, `E-REPO-UNLISTED`, `E-CHECKOUT`, `E-CLAIM-STOP`, rule 8 on a failed worktree) still say "creates a decision gate" (5.6 item 2; template status line `Orca gate: <gate id>`). The spec does not say which Task such a gate attaches to.
- **M6. The DQ3 lease has no lifecycle for the winner.** Only the loser edits its lease to `released`. A winner that stops (`E-CLAIM-STOP`, skipped, escalated, merged and closed) keeps the lowest comment id forever, so any later orchestrator, or the same one after a reopen and `--take`, loses with `claimed_elsewhere`. "Its own lease" is also ambiguous when a host holds an old lease of a finished run. Evidence: spec line 105 (DQ3 layer 4) and wave 1 (line 448 to 451).
- **M7. ADD1 does not state how the worker brief guard passes for the `/sc:pr-submit` `Command:` line.** `WORKER-CONTRACT.md:16` and `:20` make the guard refuse the whole brief before anything runs when a `Command:` line names a never-as-worker command, and `:23` says "If D3 adds a worker route for pr-submit, D3 also states how that route passes the brief guard." The handoff (5.4 section 6) puts `/sc:pr-submit --monitor 3 --head {{branch}}` on a `Command:` line. ADD1 adds a `Flow: orchestrated-issue` line but says nothing about the guard or WC-9 override wording; the first live worker would send `guard refused:`. (`/sc:implement` also has no `## Unattended mode`, `grep -c unattended src/superclaude/commands/implement.md` is 0, so how its worker contract and report directory work in this flow is not stated either.)
- **M8. Cross-repo `worker-start` is presented as settled, but the coordinator spec records it as unproven.** `SPEC-AGENT-WORK-COORDINATOR-20261027.md` line 408 ("Cross-repo `worker-start` is unproven") and line 380. The orchestrator session runs in the orchestrator repo's workspace and wave 4 starts a worker in another repo's worktree. It is not in section 12 (U1 to U24) and not marked UNVERIFIED in wave 4.
- **M9. The plan-agent brief (wave 2) takes `<issue scope>` from issue text with no data rule.** The handoff template quotes issue text as fenced data (5.4 item 3), but the wave 2 `Command: /sc:analyze <issue scope> ...` has no such rule, and that agent runs in the user's real claim checkout (`path:<checkout>`), unbound, with no L1 or L2 guard (DQ7). Issue text is attacker-influenced (anyone with triage can assign). Say how `<issue scope>` is derived (a validated path or a fixed string) and where `<dir>` is.
- **M10. Idle hourly wakes and a never-cleared session spend tokens.** The hourly wake line (DQ10) is not gated on "a worker is in progress", so an idle hour starts a model turn that ends in `E-NO-WAKE`; neither it nor the poll's typed line clears the permanent session, while the report waker clears before every morning wake because a resumed conversation costs about 546k tokens a call (`waker.py:230-235`). 5.5 says the session "may be cleared" but names no step that does it. This works against "when nothing is new, no tokens are spent".
- **M11. The merge gate's closed `reasons` list does not map every `merge_wait` outcome.** `reviewers.py:395-424` returns `polling`, `clean`, `findings`, `declined`, `no_response`, `timeout`. The spec's closed set (line 485) has `review_pending` and `review_none_present` only; `declined` (Augment declined) and `timeout` (an active reviewer incomplete) and `findings` have no stated reason or mapping to hold, so `merge-gate` can return `merge_ok` or a reason the test list does not know.
- **M12. A restart with `worker_start_intent` and no worker found is not settled.** Wave 4 (line 472) says a found worker is adopted; it does not say what happens when `worker-list` shows none (start again, which can double-start if Orca lists late, or escalate). The existing text it builds on says the opposite of R5 here: `sc-issue-protocol/SKILL.md:140` ("with no worker the row stays for a person to settle"). R5 says retry once, so the spec must say how that retry is told apart from a start that is still in flight (for example `request-show` with a stored `--retry-request` id, which the spec only lists as UNVERIFIED U21).

## From re-review, part 1 (spec-review-part1-r2.md): Medium

- **N-M1. Nothing restarts a dead orchestrator session while workers are in flight.** The fix deletes the `coordinator-hourly` waker (DQ10, C17, O3 and O4). That hourly wake was the only trigger that started a missing session without a new assignment (`waker.py:214-217`, `start_session`). Now the poll starts a session only when it has a wake to send (4.5 step 11), and DQ10 says "with no worker in flight there is nothing to check". If the orchestrator session ends or Claude Code dies with workers running, their `ask`, `worker_done` and the pull request watch go unread until the next new assignment. Wave 0's `--resume` defines what a start does, not what causes one. Suggest: the poll also wakes (mailbox plus typed line, or starts the session) when any `.orchestrator/issues/*.json` is `in_progress` and no live orchestrator session exists, or `orchestrator-poll` marks the workspace unread in that case.
- **N-M2. 4.3 rule 2 and 4.5 step 8 omit `failed` entries.** Step 8 filters S1 by "no store entry (4.3)" and rule 2 (changed line 244) now lists what happens to `acked`, `pending`, `woken`, `unknown` and `abandoned` entries, but not `failed`. A pre-pending failure (for example a transient re-read error) leaves a `failed` entry; as written that issue is never a candidate again, so the retry that leads to `attempts_exhausted` (exit 7, the PR A test row, 3.7 item 1 "or 3 failed preparations") is unreachable and the old silent drop remains for this path. 4.10 keeps `fail`, `backoff_elapsed`, `BACKOFF` and the `in_backoff` reason, so the intent is clear; the two text lines need to say `failed` entries are re-examined once their backoff has elapsed. Evidence: old behaviour `cycle.py:934-935` (`backoff_elapsed` then `in_backoff`).
