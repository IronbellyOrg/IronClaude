## Findings so far: one inbox vs many Runs (coordinator observations, 2026-11-24; not the research this issue asks for)

**What was observed**
- A session can read one Run's inbox at a time. Even a read-only peek at another Run is refused: "This caller is bound to Run run_3c5063203944, not Run run_c6c0e8864967. Nothing changed."
- A session can still list another Run's workers and read their files on disk.
- Cost seen: the issue 751 agent asked "open the pull request?" at about 02:48 and the question sat unseen for about 10 hours, because that agent reports into its own Run, `run_71871571be85`, and the coordinator was bound to another. Issue 597's blocked question reached the coordinator only through a file.

**One Run per project**
- Rewards: one inbox and one wait cover every worker; a restart needs one command; the sweep and observer code, built around one Run, work as they are.
- Risks: unrelated work mixes in one inbox; one stuck or fenced session blocks everything; messages are one shared queue, so a slow handler delays all; the Run is harder to close or archive; launched agents appear to create their own Run (751's did; not verified), so a single-Run rule may not be enforceable for them.

**Many Runs**
- Rewards: isolation and a clean per-task record.
- Cost: every Run the session is not bound to is invisible for questions and decisions (confirmed above).

**What would have to change to sweep every inbox**
- `src/superclaude/cli/sweep/probes.py:49-60`: the allowlist is 10 read-only Orca commands. It reads workers and tasks of one Run and does not read messages. It needs a list-all-Runs command added and its tests updated.
- The real blocker is not our code: reading another Run's messages is refused for an unbound session. Options: an Orca change (a read-only cross-Run peek), a rule of one Run per project, or sweeps that take turns binding.
- `src/superclaude/cli/observe/commands.py:75,491`: the observer's question list reads one named Run only; it would have to loop over Runs.
- `WORKER-CONTRACT.md` needs a rule for when a Run is created, reused or switched.
- Interim workaround in the coordinator's own sweep: read every project Run's workers plus each launched agent's `result.md` and terminal tail. It misses messages that were sent but never acted on.

**Not known:** whether switching the bound Run (`run-use`) loses queued messages (not tested). The coordinator's lean, unproven: one Run per project plus an Orca request for a read-only cross-Run peek.
