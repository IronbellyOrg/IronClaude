## Problem Statement
Nothing tells the standing coordinator that the watcher claimed an issue, or that a claim finished. The code facts below were re-checked on master afb3ccf29 on 2026-11-24.
- When the watcher claims an issue, it starts the claim as a new Claude tab with `orca agent launch ... --surface terminal` (`src/superclaude/cli/issue_watch/launch.py:136-157`). It sends the coordinator no message.

## Findings so far: one inbox vs many Runs (coordinator observations, 2026-11-24; not the research this issue asks for)
**What was observed**
- A session can read one Run's inbox at a time. Even a read-only peek at another Run is refused: "This caller is bound to Run run_3c5063203944, not Run run_c6c0e8864967. Nothing changed."
- A session can still list another Run's workers and read their files on disk.
- Cost seen: the issue 751 agent asked "open the pull request?" at about 02:48 and the question sat unseen for about 10 hours, because that agent reports into its own Run, `run_71871571be85`, and the coordinator was bound to another. Issue 597's blocked question reached the coordinator only through a file.
**One Run per project**
- Rewards: one inbox and one wait cover every worker; a restart needs one command; the sweep and observer code, built around one Run, work as they are.
- Risks: unrelated work mixes in one inbox; one stuck or fenced session blocks everything; messages are one shared queue, so a slow handler delays all; the Run is harder to close or archive; launched agents appear to create their own Run (751's did; not verified), so a single-Run rule may not be enforceable for them.
**Many Runs**
- Rewards: isolation and a clean per-task record.
- Cost: every Run the session is not bound to is invisible for questions and decisions (confirmed above).
**What would have to change to sweep every inbox**
- `src/superclaude/cli/sweep/probes.py:49-60`: the allowlist is 10 read-only Orca commands. It reads workers and tasks of one Run and does not read messages. It needs a list-all-Runs command added and its tests updated.
- The real blocker is not our code: reading another Run's messages is refused for an unbound session. Options: an Orca change (a read-only cross-Run peek), a rule of one Run per project, or sweeps that take turns binding.
- `src/superclaude/cli/observe/commands.py:75,491`: the observer's question list reads one named Run only; it would have to loop over Runs.
- `WORKER-CONTRACT.md` needs a rule for when a Run is created, reused or switched.
- Interim workaround in the coordinator's own sweep: read every project Run's workers plus each launched agent's `result.md` and terminal tail. It misses messages that were sent but never acted on.
**Not known:** whether switching the bound Run (`run-use`) loses queued messages (not tested). The coordinator's lean, unproven: one Run per project plus an Orca request for a read-only cross-Run peek.

## Executive Summary
**An agent may read outside its assigned worktree, but may not create, change, delete, rename, or cause another process to modify files outside it.** This includes reaching a second checkout through an absolute path while the session itself remains in its original directory. A worktree is a checkout, not a filesystem permission boundary.
Propose a synchronous, all-tool PreToolUse guard tied to a fixed session scope. It rejects out-of-scope paths, unknown write-capable tools, and unconfined execution. It never treats a prompt, `cd`, an environment variable, or an agent-written approval file as permission to change the boundary. Denials explain the scope and direct the agent to request a human-controlled scope change rather than retry through another tool.
**A hook alone cannot make arbitrary shell code safe.** Therefore the enforceable design combines the hook with filesystem confinement: an outer boundary for the application and helpers, plus an inner executor boundary that keeps arbitrary agent code away from framework-only state. Without proven confinement, arbitrary shell/interpreter/browser execution and opaque mutators are denied, not guessed safe. A hook-only deployment can block direct editing mistakes, but must be labelled a limited guar
## System Context
### Existing System
The inspected guards address output placement and stale reads. Neither binds the destination to the session's assigned checkout. An absolute Edit to another checkout can pass freshness checks once that file has been read. A shell command can also run a script in another checkout without changing the session's working directory. Both routes must be stopped before a write occurs.
### Scope and trust assumptions
- Protect against mistaken or instruction-driven agents, including attempts to work around a denial through another tool. Include subagents and child processes.
- The human/administrator and the outer launcher are trusted. The model, repository contents, scripts it edits, tool descriptions, and new MCP tools are not policy authorities.
- Reads outside the checkout remain permitted by this design, subject to existing read permissions. Confidentiality and network publication permissions are separate policies.
- The agent cannot be given an unrestricted host shell, a privileged daemon socket, or writable enforcement code and simultaneously be promised confinement. Same-user host processes are not isolated merely by a mode-0700 directory.
- Agent scratch/cache and framework-only state are different permission classes. Agent execution may write only the owned checkout and private agent scratch/cache. Transcripts, policy records and telemetry belong to the trusted framework service and are inaccessible for writes from agent-controlled executors. A session-private mount alone does not create this distinction. Sibling sessions' state is never included.
- The original duplicate-decision problem also needs ownership coordination. This issue prevents out-of-worktree writes; it does not stop two sessions assigned the same worktree from duplicating reasoning, and does not implement a session-ownership registry.
- No changes to existing application code, settings, or other checkouts are authorized by this design request. All examples use invented fixture paths.

## What was tried
**The problem.** Today the owner and every AI helper that works for the owner (the Orca coordinator and worker sessions, scripts, the pull-request helper) sign in to GitHub as the same user, `ironbelly`, which is also the repository admin. GitHub cannot tell who did something: the person clicking "Approve" or a script running on the same machine. Our own checks cannot tell either.
**Why it matters.** The plan says things like "a worker cannot merge", "an approval means the owner approved", "a typed go means the owner typed it". On a shared login these rules can be written down but not proven. The plan already records this as open risks (requirement SEC-09, risk RK-3, invariant INV-025 in the unification plan). The plan's current default is: the typed-answer check cannot pass, so every merge is typed by hand.
**What was tried.** On 2026-11-22 two agents proposed and debated (three rounds) and a reconciler unified one proposal. The owner shelved it for further human debate and asked that the problem be filed with that proposal as one of the proposed solutions. Nothing below is decided or built.
**Proposed solutions (not decided).**
1. **Two tiers plus a separate agent GitHub account (the debated proposal).** "The owner" means the person behind `ironbelly`, by numeric id.
   - Tier 1, chat-only answers (a grant, a cleanup approval, a design go): counts only when the owner types it in a session the owner opened by hand; never from workers, script-started sessions, relays, or issue or PR text. Free, and can be done now. It narrows the risk but cannot prove who typed.
   - Tier 2, a merge or the `Approved` label: the chat go plus an approving GitHub review by the `ironbelly` account on that exact commit, clicked by the owner in the browser. The checks refuse if the login in use is the owner's own, or if no such review exists.
   - A second GitHub account for the agents (Write role, outside collaborator, 2FA), with `ironbelly` signed out of agent hosts. It must exist before merge automation, coordinator autostart, switching the watcher on for real repos, and flipping the worker-binding switch.
   - Needs the master protection rules (the ruleset of the plan's item OA-5) to make "a worker cannot merge" true.
2. **Chat-only rule, no new account.** Do only Tier 1. Cheap, but a script on the host can still type as the owner.
3. **Status quo.** Every merge is typed by hand by the owner; merge automation, coordinator autostart, real-repo watcher switch-on and the worker-binding flip stay off.
4. **Not evaluated yet:** a GitHub App (a bot identity) instead of a second user account.
**Costs (estimates, not measured).** Tier 1: about 15 minutes of the owner's time and about 1 agent hour. Second account: about 1 to 1.5 owner hours once, about 15 minutes per extra host, about 1 to 2 minutes per gated merge, plus about 3 to 4 agent hours of code and tests. Ruleset time belongs to OA-5.
**Risks of solution 1.** An `ironbelly` credential left on a host; the owner logging back in under pressure; review bots (Augment, Codex) staying silent on a new account, which reads as clean; credential expiry stopping all agents (fails safe); at 0 required approvals a worker could merge a path the rules do not gate.
**Unknowns.** Whether a Write-role account can do the claim's writes (assignee, issue type, Complexity field, `Approved` field); whether Augment and Codex review pull requests from a new account; how many hosts exist.
**Open choices from the debate.** (1) Required approvals on master: 1 (recommended by the debate, no agent self-merge on any path) or 0. (2) Should the agent account join the Coder organisation: no to start. (3) Reuse the existing `IB-AIReviewer` account: no, create a new one.
