# #771 [FEATURE] Wire `/sc:closeout` and `/sc:worktrees` into the coordinator's finish, and give a "not done" result somewhere to go [OPEN]
## Feature Summary

Thank you, Ryan, for the issue watcher and the standing coordinator ([PR #707](https://github.com/IronbellyOrg/IronClaude/pull/707)). Could we connect `/sc:closeout` and `/sc:worktrees` to the coordinator's finish after a person merges, and give a "not done" result somewhere to go?

## Problem Statement

This comes out of the gap check in issue #761. The description was checked against master at commit `afb3ccf29`.

Two finishing tools are built and merged, but the watcher and coordinator flow does not call them:

- `/sc:closeout` ([PR #683](https://github.com/IronbellyOrg/IronClaude/pull/683), merged 2026-11-20; issue #668, closed as completed). The command is in `src/superclaude/commands/closeout.md`, and the design is in `docs/designs/sc-closeout.md`. After a pull request is merged, it settles the issue, the work report entry and the worker's Orca task. It is "for a person or the orchestrator, never a worker" (`src/superclaude/commands/closeout.md:19`).
- `/sc:worktrees` ([PR #711](https://github.com/IronbellyOrg/IronClaude/pull/711), merged 2026-11-22; issue #687, closed as completed). The command is in `src/superclaude/commands/worktrees.md`. It removes worktrees whose work is finished and merged, subject to its safety checks. Its schedule is an opt-in Orca automation that is not switched on, so it does not remove worktrees on its own today.

A text search for `closeout` and `sc:worktrees` finds nothing in the watcher (`src/superclaude/cli/issue_watch`), the pipeline (`src/superclaude/cli/issue_pipeline`), the claim skill (`src/superclaude/skills/sc-issue-protocol`) or the watcher designs (`docs/designs/issue-watcher*.md`).

In the coordinator's rules, closeout appears only in the never-as-worker list (`src/superclaude/core/WORKER-CONTRACT.md:23`). The "Issue pipeline duties" list (`src/superclaude/core/WORKER-CONTRACT.md:292` to `303`) ends at `issue-pipeline complete`: the result comment and the move to In review. Nothing there says what to do once the person merges.

When closeout decides an issue is not finished, it leaves the issue open, posts one short note of what remains, and returns `settled how=left_open`. Decision D22 in `docs/designs/sc-closeout.md:78` also gives the result `issue.handback: remaining` and the list of unmet criteria, so the orchestrator can start the missing work. No coordinator rule reads that hand-back. A person has to notice the note on the issue.

A merged pull request can therefore stay unsettled, its worktree stays on disk, and a "not done" answer goes nowhere, unless a person remembers to run both commands by hand.

## User Story

As a person using the issue watcher and coordinator, I want a clear post-merge finish and a recipient for unfinished work, so that I do not have to remember both finishing commands by hand.

## Proposed Solution

These are questions and options, not decisions about how Ryan's work should change.

1. **Post-merge duty.** Could the coordinator's rules get one more duty: after the person merges, run `/sc:closeout` for that pull request, then the worktree cleanup (`/sc:worktrees`)? Would you prefer a duty on the coordinator's next wake, or a line in the result comment telling the person which command to type? The current worktrees command is person-only and requires the person to type `--apply` for removal (`src/superclaude/commands/worktrees.md:17`, `21`, `40`). Could we agree how the chosen route respects those rules before changing the contract?
2. **A place for "not done".** When closeout returns `settled how=left_open`, could the hand-back go to the coordinator? Could it then start the missing work as a new Task under the same rules, or tell the person? If you prefer that the person always decides, which note should they see, and where?
3. **Waiting for the merge.** At Full Submit, the launched agent opens the pull request, which then waits for the person. Could something watch it until it is merged or closed, so that question 1 has a trigger? If the coordinator already sees merged pull requests somewhere, where is that?

Open questions:

- [ ] Who runs `/sc:closeout` after a merge: the coordinator, the person, or a scheduled run?
- [ ] Who receives a `not_done` result, and what do they do with it?
- [ ] Should the `/sc:worktrees` schedule stay opt-in and off, with the coordinator calling it only for worktrees it created?
- [ ] UNVERIFIED: whether the coordinator can learn that a pull request was merged without polling GitHub. The check that would settle it: read what `/sc:sweep` and the watcher store report for a merged pull request.

## Acceptance Criteria

- [ ] The agreed post-merge route is written in "Issue pipeline duties", with who runs closeout and who handles cleanup.
- [ ] The agreed trigger distinguishes a merged pull request from one closed without merging. It does not merge anything itself.
- [ ] A `not_done` result has a named recipient and a stated next step: missing work under the existing Task rules, or a note to the person in an agreed place.
- [ ] The cleanup route keeps the command's safety checks and does not assume permission to add `--apply`.
- [ ] Rule tests cover the agreed route and keep the existing merge and worker boundaries intact.

## Out of Scope

**Kept as designed:** nothing merges a pull request except a person's own typed go. This is owner ruling R38 part D. A Full Submit go "never covers a merge" (`src/superclaude/core/WORKER-CONTRACT.md:246`). `/sc:pr-submit --monitor 3` drives the reviews and CI fixes up to the merge, not the merge itself.

Also out of scope:

- The 70 open review findings on the closeout design, tracked in issue #674.
- Changing or replacing the merged watcher. This issue only asks where the finishing tools plug into it.
