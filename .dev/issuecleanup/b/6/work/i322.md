## Executive Summary

**An agent may read outside its assigned worktree, but may not create, change, delete, rename, or cause another process to modify files outside it.** This includes reaching a second checkout through an absolute path while the session itself remains in its original directory. A worktree is a checkout, not a filesystem permission boundary.

Propose a synchronous, all-tool PreToolUse guard tied to a fixed session scope. It rejects out-of-scope paths, unknown write-capable tools, and unconfined execution. It never treats a prompt, `cd`, an environment variable, or an agent-written approval file as permission to change the boundary. Denials explain the scope and direct the agent to request a human-controlled scope change rather than retry through another tool.

**A hook alone cannot make arbitrary shell code safe.** Therefore the enforceable design combines the hook with filesystem confinement: an outer boundary for the application and helpers, plus an inner executor boundary that keeps arbitrary agent code away from framework-only state. Without proven confinement, arbitrary shell/interpreter/browser execution and opaque mutators are denied, not guessed safe. A hook-only deployment can block direct editing mistakes, but must be labelled a limited guard and must not claim complete worktree confinement. No implementation is included here.

## System Context

### Existing System

The inspected guards address output placement and stale reads. Neither binds the destination to the session's assigned checkout. An absolute Edit to another checkout can pass freshness checks once that file has been read. A shell command can also run a script in another checkout without changing the session's working directory. Both routes must be stopped before a write occurs.

### Scope and trust assumptions

- Protect against mistaken or instruction-driven agents, including attempts to work around a denial through another tool. Include subagents and child processes.
- The human/administrator and the outer launcher are trusted. The model, repository contents, scripts it edits, tool descriptions, and new MCP tools are not policy authorities.
- Reads outside the checkout remain permitted by this design, subject to existing read permissions. Confidentiality and network publication permissions are separate policies.
- The agent cannot be given an unrestricted host shell, a privileged daemon socket, or writable enforcement code and simultaneously be promised confinement. Same-user host processes are not isolated merely by a mode-0700 directory.
- Agent scratch/cache and framework-only state are different permission classes. Agent execution may write only the owned checkout and private agent scratch/cache. Transcripts, policy records and telemetry belong to the trusted framework service and are inaccessible for writes from agent-controlled executors. A session-private mount alone does not create this distinction. Sibling sessions' state is never included.
- The original duplicate-decision problem also needs ownership coordination. This issue prevents out-of-worktree writes; it does not stop two sessions assigned the same worktree from duplicating reasoning, and does not implement a session-ownership registry.
- No changes to existing application code, settings, or other checkouts are authorized by this design request. All examples use invented fixture paths.

## Component Architecture

### 1. Fixed session scope

**Responsibility:** bind a running session to one checkout before its first mutation. A trusted launcher resolves the initial Git top-level, worktree-specific Git directory and common Git directory, and records the canonical root and directory identity. Do not walk upward to the main checkout or interpret every Git worktree as writable. Non-Git sessions require an explicit directory selected by the human launcher.

**Proposed record:** schema version, session identity, parent identity if any, canonical root, root device/inode where supported, worktree Git-directory identity, policy digest, explicitly excluded nested checkouts, private scratch/cache paths, approved service interfaces, and verified confinement status. Store it outside agent-writable mounts. The exact path is deployment-owned, not a repository config value.

- The root is immutable for a session. Branch changes, a prompt containing a path, `cwd`, `CLAUDE_PROJECT_DIR`, `--add-dir`, environment changes and a Skill argument cannot enlarge it.
- On resume or compaction, verify the existing record. Do not silently rebind to the new current directory. Missing record, root replacement, moved checkout or identity mismatch denies mutation until the human restarts/rebinds through the trusted launcher.
- A child without a matching parent/scope record cannot mutate. SubagentStart supplies context only; PreToolUse and the execution boundary provide enforcement. A named remote worker is not assumed to inherit the scope.
- Root selection and any exceptional write permission require human control outside the agent's tool channel. For initial delivery prefer a new correctly scoped session over dynamic exceptions. Natural-language permission is not parsed into a grant.

### 2. All-tool admission hook

**Responsibility:** synchronous PreToolUse dispatch for every tool. Register with `matcher: "*"`; configure the command hook with `onFailure: "block"`, no async, and a finite timeout. Use documented deny JSON or exit 2. On a safe in-scope action return no objection, not an unconditional allow that skips other permission checks. Unknown tool names default to deny until classified.

**Proposed decision stages:** validate payload and scope; classify tool capability; resolve every affected resource; check protected paths and ownership; verify execution confinement where required; return no objection or deny. Malformed JSON, missing fields, unknown actions and adapter errors deny. Never expand `${...}` or execute shell text to discover its meaning.

**Decision and argument integrity are launch gates, not assumptions:**

- The official hooks guide documents a mod-approval exception when there are no managed settings and the active session is not using Team/Enterprise `/login` credentials. An API key or long-lived token is not that login. Do not describe every user/global hook denial as unoverrideable.
- Strict mode initially runs with mods disabled and a frozen, verified inventory of other hooks. Managed placement can strengthen precedence, but is not a substitute for checking the effective runtime. If mods cannot be excluded or denial precedence cannot be proved, do not advertise the hook as an enforced admission gate. The outer filesystem boundary must still stand independently.
- Matching PreToolUse hooks run in parallel. Documentation says multiple `updatedInput` rewrites are not merged and the chosen rewrite is not guaranteed. This guard emits no rewrites. Initially reject any other hook/mod/tool middleware permitted to rewrite tool arguments; vetted non-rewriting hooks such as freshness checks may coexist. Changing that inventory requires a trusted restart, not an agent edit.
- Future support for rewriting requires a proven final-execution boundary that validates the exact tool name and complete arguments after every rewrite, immediately before dispatch. A second ordinary parallel PreToolUse hook is not that boundary. Check a digest only if the executor actually consumes the checked arguments; a digest recorded in a log is not enforcement.
- Add canary tests for an original in-scope destination rewritten outside, original safe shell text rewritten into a mutation, mod approval of a denied call, and hot-loaded configuration. If any canary executes the forbidden effect, strict readiness fails.

**Minimum adapter inventory (actual loaded names and schemas must be enumerated in implementation):**

| Tool family | Inputs/effects that must be checked | Admission rule |
|---|---|---|
| Write / Edit / MultiEdit where present | `file_path`, all batch members | Every destination passes the path policy. Unknown batch shape denies. |
| NotebookEdit | `notebook_path` | Same policy as text files, regardless of cell operation. |
| Serena single-file edits | `relative_path` for replace_content, replace_symbol_body, insert_before_symbol, insert_after_symbol, safe_delete_symbol | Resolve against the server's actual project, not the hook's guessed cwd. Deny unless server binding and confinement are verified. |
| Serena bulk/refactoring | replace_in_files and rename_symbol; implicit reference updates | No single-path shortcut. Require confined server with scope limited to this checkout; a precomputed file list alone cannot prevent a race. |
| Serena memory and project services | write_memory, edit_memory, delete_memory, rename_memory; project/index updates | Deny by default. Route legitimate framework state through exact service exceptions; do not grant arbitrary global-memory writes. |
| Bash / PowerShell / Monitor or equivalent | Entire command, subprocesses, background flags, unsandboxed flags | General execution only inside the proven whole-process boundary. Deny explicit escape flags. Tool-name aliases do not change the rule. |
| Browser/code execution | Playwright evaluate/run-code, screenshots, downloads, uploads, browser profile writes; GUI/terminal controllers | Confined execution and scoped output/profile directories required. Deny access to an unconfined host browser or terminal. |

| SendMessage / remote workers | Execution requests to other sessions or host-side services | Deny mutating delegation through unrestricted peer messaging in strict mode. Permit only a scope-aware broker that cannot widen the originator's write scope. Free-text parsing is not enforcement. |

This inventory is a policy requirement, not a claim that every tool above is installed everywhere. Runtime tool-discovery must detect newly added tools and keep them denied until classified.

### 3. Filesystem path policy

**Responsibility:** a single reusable policy used by file adapters and brokers. Do not use a raw string-prefix test.

1. Parse the actual tool schema. Reject missing, ambiguous, NUL-containing or unsupported path forms. On Windows, drive-relative paths, UNC/device paths, junctions and alternate data streams need tested equivalents; strict mode stays unavailable there until proven.
2. Resolve relative paths against the tool executor's verified working directory. Independently confirm that executor still belongs to the fixed scope. A changed cwd cannot become a new scope.
3. For existing paths, inspect the resolved object and every relevant ancestor. For new files, resolve the deepest existing parent and check the remaining components; reject unresolved links and ambiguous normalization. Use component-aware ancestry.
4. Deny anything outside the owned root or inside a different nested Git checkout/worktree, including when the parent repository contains a `.dev/worktrees/` subtree. A read-allowed directory is not write-allowed.
5. Deny direct writes to policy/hook installation, loaded configuration, executable search-path overrides, `.git` pointer and administrative data. Ordinary source changes to a future hook implementation are permitted only when those files are not the live enforcement code. Live updates require a human-controlled restart/deployment.
6. Both ends of moves and renames must be owned. Reading a source outside and copying it into the checkout is subject to read policy; moving it would delete outside and is denied. Recursive operations must exclude all nested scopes and protected descendants.
7. Do not treat `realpath` as a race-proof guarantee. Reject in-place modification of multiply linked regular files unless ownership of all aliases is established; handle symlink/junction/mount aliases explicitly. A hook cannot force another tool's open/rename to use the object it checked. Strong mode therefore requires a confined filesystem view or a broker that opens paths safely relative to trusted directory handles and cannot follow escape links.

### 4. Execution boundary, not shell parsing

**Responsibility:** make a path hidden inside a script no more powerful than a literal path in Edit.

The mandatory strong-mode architecture has two permission layers:

1. An outer OS/container boundary contains the Claude Code process, hooks, local tool servers and helpers. Other checkouts are read-only or not mounted, and protected control files and nested worktrees remain denied.
2. Every agent-controlled executor, including shell descendants, arbitrary-code MCP servers and browser evaluation helpers, runs in an inner boundary with write access only to the owned checkout and private agent scratch/cache. Framework transcripts, telemetry, policy records and other service state are not writable or exposed through inherited writable descriptors. Use a separate execution identity and filesystem/process isolation, or an equivalently proven broker boundary. Prevent process-control interfaces, inherited handles and same-identity tracing from recovering the trusted parent's authority.

Built-in file adapters must deny framework-only destinations even though the trusted parent can write them. Trusted framework writes occur through fixed-purpose interfaces that do not accept agent-selected destinations or executable payloads. Hooks and helper programs with service authority must be immutable and vetted; arbitrary repository-defined hooks cannot be put in that trusted class.

If the deployed Claude Code/tool integration cannot establish the inner separation for an execution tool, block that tool. A single container shared by the CLI and its same-identity shell children is not proof of service-only access. Do not reuse a shared writable `/tmp`, shared home, package cache or host Git metadata as a broad exception. Seed read-only cache data or use private agent caches. Existing hard-link aliases must be separated or rejected at provisioning; mount pathname restrictions alone do not establish exclusive ownership of an inode.

The built-in shell sandbox is useful defense in depth but is NOT sufficient: official docs say file tools, MCP servers and hooks run outside it; it can grant additional directories and shared Git metadata. If used, require it available, prohibit unsandboxed fallback and excluded-command escapes, and verify the effective merged configuration. Do not silently turn off enforcement to make a build run.

In a hook-only deployment, arbitrary Bash, interpreters, build tools, generic browser execution and opaque MCP mutators are blocked. Initially expose reads through known non-executing tools and edits through tested path adapters. Any supposedly read-only shell broker must offer fixed structured operations implemented by trusted code, not execute agent-supplied commands. General coding workflows are unavailable until containment exists; this is an explicit tradeoff, not a security claim hidden behind command regexes.

No host Docker/Podman socket, unrestricted SSH, host IPC service, writable helper executable, privilege escalation, scheduler service or `/proc` process-control interface may bypass this boundary. Network/local services capable of writing the host must be denied or scope-aware. A tool inside a container can still ask an outside daemon to write files; process containment alone does not confine that daemon.

### 5. Narrow Git and framework service exceptions

Linked Git worktrees share objects, refs, configuration and administrative data. Granting write access to the common Git directory would permit changing another checkout or installing a hook that writes later.

- Strict default: direct common-directory writes and Git mutations requiring them are denied. This must not become a hidden allow rule just because Git fails.
- For practical use, a trusted Git broker accepts a structured operation tied to the bound worktree, branch and allowed remote. It validates effective Git configuration and disables untrusted hooks, filters, helper programs and repository-driven execution. It may stage owned files and commit only the assigned branch, but never switch another checkout, alter global/shared config, remove worktrees, update arbitrary refs, or reuse the shared stash. Pushes remain separately authorized outward actions.
- The broker must reject unsafe object paths/alternates and untrusted process environment. Shared-storage updates are narrow privileged operations, not permission for the agent to edit administrative files.
- Until this broker is implemented and proven, require human-run Git mutations or an isolated repository rather than linked-worktree shared metadata. Feature completeness must not be claimed without this explicit limit.
- Trusted framework hooks may write only their declared state/log destinations with session isolation. They must not interpret repository content as shell commands or accept arbitrary output paths. Native transcript/runtime writes use service-only destinations protected from agent executors by the inner boundary, not merely a separate mount shared with those executors. A telemetry service may accept a fixed record schema but not arbitrary file writes, code or destination paths.
- Existing unsafe hook/MCP/config behavior blocks strong-mode readiness. Test and enumerate which components need controlled service writes before enabling, rather than assuming the outer wrapper makes trusted hooks harmless.

## Data Flow

1. Human launcher selects checkout A and provisions an immutable scope plus the chosen enforcement level. Child execution, tool servers and private runtime directories are attached to that scope.
2. SessionStart verifies context. It cannot block launch, so a failure never marks the session safe. The first mutating PreToolUse still requires valid state.
3. A tool request arrives. The wildcard hook validates identity, classifies the tool, resolves its complete effect set, and checks its execution context.
4. An Edit to A passes the ownership checks and continues to normal permissions/freshness checks. An Edit to checkout B returns a denial before the tool opens B.
5. A script with no visible destination is either confined by the whole-process boundary or denied. Unknown MCP execution is not admitted just because its name sounds read-only.
6. Subagents use the same checks. Moving to another checkout requires a new human-authorized scope, not a message asking a peer to perform the denied edit.
7. Denials record session identity, tool name, reason code and sanitized destination metadata through the trusted logger. Do not log command bodies, file contents, credentials or full user-home paths. Logs are operational evidence, not a claimed tamper-proof audit.

Example denial, with invented paths: `WORKTREE_WRITE_DENIED: session owns /workspace/repo/checkouts/a; destination belongs to another checkout. No mutation ran. Do not retry through Bash, an MCP tool, or another agent. Ask the human to start a session in the intended checkout.`

A successful admission is not a transaction: a multi-file tool still needs its own atomicity/error semantics. A post-write diff or watcher can detect problems but cannot replace this pre-write boundary.

## Technology Decisions

| Decision | Choice | Reason / rejected alternative |
|---|---|---|
| Session root | Fixed launcher record, verified on resume | Per-call cwd and repository discovery can silently follow the agent into another checkout. |
| Tool coverage | Wildcard admission with explicit adapters | Edit-only and tool-name-pattern guards leave shell, MCP, batch and future tools open. |
| Arbitrary execution | Whole-process confinement or deny | No finite shell regex proves that a script, build or interpreter has no external writes. |
| Failure behavior | Deny, including timeout/startup errors | A fail-open parser or missing hook executable would silently remove the control. |
| Hook result | No objection for approved paths; explicit deny otherwise | Avoid skipping unrelated permission rules with broad allow responses. |
| Override and rewrite integrity | Strict mode disables mods and rejects rewriting hooks initially | Ordinary user-hook denials and parallel input validation are not guaranteed final authority. |
| Framework state | Separate service authority from agent executor authority | A private writable runtime mount shared by both identities is not service-only isolation. |
| Scope expansion | Human-controlled new session initially | No auto-approved exception, prompt-parsed override or agent-writable allowlist. |
| Shared Git directory | Deny direct access; optional narrow broker | Blanket common-directory allowance breaks checkout isolation. |
| Reads | Existing read permissions continue | The requested boundary is writes; do not invent a confidentiality system. |
| Policy implementation | Deterministic local code, no model call | A probabilistic judge is not a filesystem ownership check. |
| Strict support | Ship only on proven platform/client combinations | Unsupported systems must not silently degrade to the advertised strong mode. |

## Implementation Considerations

### Patterns to Follow

### Ways an agent could get around a naive guard, and required handling

These are defensive test classes, not claims that any one matcher prevents all of them.

| Route | Why a naive hook misses it | Required handling |
|---|---|---|
| Absolute path, `..`, prefix sibling such as `a-backup` | Session cwd is still A; string prefix looks similar | Canonical component ancestry against fixed root; reject B before write. |
| Symlink, junction, bind mount, hard link | Apparent path is inside A, target/storage is not | Inspect aliases; safe filesystem boundary/broker; reject shared inodes; race tests. |
| Swap symlink after check | PreToolUse and actual open are separate | OS boundary or safe broker; hook-only guarantee explicitly excludes race-proof confinement. |
| Shell redirect, append, tee, sed-in-place, move/copy/remove | No file_path argument exists | Confine command and all descendants or deny generic execution. |
| UV/Python/Node script, imports, shell startup, Make target | Destination/code can be computed or hidden in repository files | Do not evaluate scripts in hook; same execution boundary, trusted launch environment. |
| Download/extract/export, archive traversal | Tool appears to fetch or unpack, not edit | Validate output options and containment; malicious archive fixtures must not escape. |
| Git `-C`, work-tree/git-dir overrides, hooks/filters | Git can target B or run external helpers | Deny generic unconfined Git; structured broker with fixed repo identity. |
| Editor bulk rename and reference updates | One input symbol can change many files | Whole server scope and all effects bounded, not just the definition path. |
| Background command or scheduled job | Write occurs after hook returns or parent exits | Lifetime-bound process tree; stop descendants at teardown; no host scheduling service. |
| New MCP/browser/terminal execution tool | Name absent from known edit matcher | Default-deny unknown tools; adapters and scoped servers required. |
| Screenshot/network log/resource saved outside A | Read-like tool still writes an output | Validate filename/out_dir and service profile paths. |
| Local daemon/Docker socket/SSH/remote filesystem | Write is done by an external process with host access | No unscoped bridge; scoped broker or deny. |
| Agent/Workflow/Skill or peer message | Work delegated to a less restricted executor | Inherit scope; deny unverified workers and mutating peer bridges. |
| Edit settings, delete hook, replace interpreter or PATH helper | Next tool call runs without the guard or under altered code | Protect live controls outside writable mounts; verify effective config; human-only deployment. |
| Corrupt scope, parser failure, missing executable, timeout | Conventional hook error can be nonblocking | Explicit deny plus verified `onFailure: block`; launch canary tests; no strong mode if unsupported. |
| Resume from B / change project env / add-dir | Root accidentally recalculated or permission widened | Preserve fixed scope; no implicit widening; effective-config checks. |
| Read-triggered plugin/LSP helper side effect | Nominally read-only call starts code with host access | Include helpers in whole-process containment or deny that adapter; permission hints alone insufficient. |

### Review questions for this issue

Review the proposed contract, not an implementation: is blocking arbitrary execution without proven confinement the correct default; which OS/runtime backend can cover all local tool servers; and should the first release use human-run Git mutations until the narrow broker is ready? The recommendation is to keep those strict defaults rather than silently weaken the boundary.

### Error Handling

- Synchronous command hook; explicit deny on malformed/oversized payload, unknown schema/action, missing identity, corrupt policy, unresolved path, ownership mismatch or missing execution proof.
- Do not convert a failure to an advisory warning. Plain exit 1 is not sufficient: official docs describe it as nonblocking unless failure-blocking is configured.
- Require client proof that missing executable, signal, invalid output and timeout block PreToolUse through `onFailure: "block"`. If unsupported or not proven, refuse strong-mode startup. Merely printing an error in SessionStart does not block tools.
- No async admission and no post-write rollback as the primary defense. A rollback can overwrite somebody else's concurrent change.
- Reject startup or invalidate readiness when an effective plugin/hook change introduces mod approval or argument rewriting. No permission-mode assertion may stand in for verifying these separate override paths.
- Log errors via a trusted session-local service. Logging failure must not turn a denial into permission. Do not expose secrets while explaining a blocked destination.
- A human may disable the guard outside the agent environment, but that session then loses the enforced designation. Never claim this protects against an administrator who controls the host or against an independently running unconfined peer.

### Testing Strategy

**These are required acceptance checks for a future implementation; none has been executed by this design task.** Use temporary fixture repositories A and B with no personal files. Snapshot B's content and metadata before every test and assert no forbidden mutation occurred, including no creation/deletion/rename. Instrument external test processes where needed; a final content hash alone misses transient writes.

1. Direct tools: allow an ordinary in-A create/edit/notebook change; deny absolute/relative B destinations; test every installed mutation adapter and all members of a batch. One bad member denies the whole tool call before it begins.
2. Root identity: deny prefix siblings, traversal, symlinked parent/root, root replacement, mismatched cwd, environment override, add-dir broadening, resumed-session rebind, corrupt/missing record and unknown child identity. Verify inside relative paths resolve correctly, not to the launcher cwd by accident.
3. Alias/race coverage: symlink and junction fixtures, mount aliases, existing hard links, new link creation, symlink-swap concurrency, path parent replaced during create, recursive operation containing nested worktrees. Demonstrate the claimed guarantee at the actual filesystem boundary, not only with fake hook JSON.
4. Shell equivalence: test shell append, in-place editing, scripts/interpreters, inherited environment/startup files, build tasks, downloads/archives and chained commands whose effects target B. Confined execution must fail at the write; without confinement, admission must deny before execution. Do not run real exploit payloads against host data.
5. Execution bridges: test generic MCP execution, Playwright output/evaluation, resource exports, helper/LSP processes, daemon/socket/remote bridges, background processes, schedulers and work continuing after parent termination. Verify no allowed bridge can ask an unconfined host service to write B.
6. Delegation: child and nested child use the same scope; verified isolated child owns only its newly assigned root; deny a peer-session mutation request that would widen the initiating session. Verify new/renamed tools remain denied until classified.
7. Git: allow approved staging/commit through the broker only for A's assigned branch; deny B via `-C`/environment overrides, direct common-directory writes, config/hooks/filter changes, arbitrary refs, shared stash and worktree removal. Confirm no unrestricted Git exception exists in effective sandbox settings. If broker absent, test that mutations are denied and documented as human-run.
8. Policy integrity: attempts to edit live registration, policy state, enforcement code, helpers or broaden exception roots fail. Repository configuration and a newly written Skill cannot grant permission. Test every permission mode, including bypass-permissions.
9. Hook failure injection: malformed payload, invalid hook JSON, missing interpreter/executable, non-2 error, internal exception, timeout and termination. A canary side effect must never execute. Test competing allow/deny hooks and installer upgrades preserving failure-blocking registration.
10. Allowed service state: transcript, runtime, private temp/cache and trusted hook logger operate only in their specific destinations. Execute admitted agent code attempting to modify its own transcript, telemetry and policy/control state, including through inherited descriptors and parent-process interfaces; these attempts must fail while trusted service writes still succeed. Another session's scratch/state and broad home directories remain denied. Ordinary tests/builds run without writing a sibling checkout.
11. Override/rewrite integrity: attempt mod approval of a denial in an unmanaged API-key session, multiple `updatedInput` rewrites, an in-root path rewritten outside, shell arguments rewritten after admission and hot-loaded middleware. Strict launch must reject the configuration or the final execution boundary must deny the exact rewritten call. Test protected managed placement separately; do not infer it from user-hook tests.
12. Compatibility: installation/reinstallation preserves unrelated hooks; source/dev/plugin sync checks pass; launch refuses unsupported platforms/client versions and missing containment dependencies. No implementation release without observed real-tool tests, not just simulated input.
13. Regression reproducer: from A, read B's document, then attempt Edit B and attempt an absolute-path script invocation that writes B without changing cwd. Both must fail, while equivalent owned-file operations work under the advertised mode.

**Completion condition:** all tests for a claimed enforcement level pass independently, every discovered tool is classified, and the release documentation states which mechanisms are enforced versus blocked/unavailable. A limited direct-edit guard must never be reported as complete arbitrary-execution confinement.

## Suggested Phases

These are design delivery slices, not an approved implementation plan or an instruction to invoke task builders.

1. **Prove the platform contract.** Establish exact client support for all-tool PreToolUse, denial in every mode, failure-blocking hooks and subagent scope propagation. Inventory loaded tools and containment backends. Output: supported-platform matrix and canary results. Stop rather than invent support.
2. **Implement fixed scope and direct-tool guard.** Add the shared path policy, adapters, protected controls and fail-closed registration through the existing installer. Output: tested limited guard with unconfined execution denied. No complete-confinement claim.
3. **Prove outer confinement, inner executor isolation and service compatibility.** Include local MCP/browser/helper/child processes and private caches; keep framework-only runtime state out of executor write authority; deny host-writing bridges, process-control escapes and unsafe aliases. Output: full real-tool escape test results on each supported platform. Dependency: slices 1 and 2.
4. **Enable narrow Git mutations if approved.** Add and test the broker or retain human-run Git as an explicit limitation. Never widen the common-directory mount to bypass failures.
5. **Independent review and operator documentation.** Validate actual deployed enforcement, source/dev/plugin distribution, explicit limitations and safe human scope changes. Only after acceptance should implementation be considered ready. No automatic activation in this design issue.

## Risks & Technical Debt

| Risk | Impact | Required treatment |
|---|---|---|
| Arbitrary code cannot be understood from shell text | A regex gate silently misses writes | Confine execution or deny it. |
| Hook timeout/missing binary normally may be nonblocking | Guard disappears at exactly the failure | Prove failure-blocking behavior in target client; no silent downgrade. |
| Canonical-path race or inode alias | Checked path differs from written object | Filesystem/broker enforcement and alias/race tests; no hook-only race-proof claim. |
| Existing helpers, global state and caches expect host writes | Strict launch breaks normal tools | Inventory service interfaces; private caches; refuse unsafe components rather than broad home access. |
| Shared Git metadata | Worktree-local command changes another branch/config | Broker or human-run mutations. |
| Unknown MCP tool or plugin introduced later | New unguarded write route | Wildcard dispatcher and default-deny classification. |
| Mod approves a denied tool or middleware rewrites its arguments | Validated call is not the final executed call | Disable mods/rewrite hooks initially; require proved final-input enforcement before adding support. |
| Agent execution inherits framework runtime authority | Transcript/control integrity claim is false | Separate service and executor permissions with inner isolation; block execution if unavailable. |
| Malicious or unrestricted host service | Writes happen outside the confined process | Do not expose socket/network bridges with host write authority. |
| Administrator/human disables control | Cannot guarantee against host owner | Explicit trust assumption and loss of enforced status. |
| Two owners in the same worktree | Duplicate reasoning and colliding edits remain possible | Outside scope; this design is not an ownership lock. |
| Strong mode unavailable on a platform | User expects enforcement that is not present | Refuse that mode; clearly name the limited mode and its blocked capabilities. |

**Not built:** every proposed component. **Not verified:** exact deployed client support for failure-blocking hooks, a chosen whole-process backend, MCP/browser/helper compatibility, hard-link handling, and the Git broker. These are implementation release gates, not reasons to label the current proposal as a working security boundary.

## Alternatives Considered

### Prompt rule only

Useful explanation, not enforcement. The incident class already occurs despite working-directory instructions. Rejected as the boundary.

### Edit/Write path hook only

Small and valuable for direct mistakes. Rejected as the complete design because notebooks, bulk refactors, shell, helpers and alternate execution tools remain. Can ship only as a labelled limited guard with unsafe capabilities blocked.

### Shell denylist or a sophisticated shell parser

A parser can identify some literal destinations, but cannot prove what a script, build target, interpreter, environment hook or remote daemon will do. Reject as authorization; use targeted parsing only for better denial explanations, not to permit arbitrary execution.

### Built-in shell sandbox alone

Reuse it as defense in depth where supported. Reject as the entire boundary because official documentation excludes built-in file tools, MCP servers and hooks, and documents extra writable directories and shared Git metadata.

### Snapshot, detect and revert after execution

Reject as prevention: outside writes have already happened, and restoration can destroy another session's legitimate concurrent changes. Detection may supplement but never substitute for admission and filesystem enforcement.

### Entire-process filesystem boundary without a tool hook

Stronger against arbitrary code than a path matcher, but still needs per-tool handling for external services, peer delegation, protected controls and useful denials. Use both rather than claim one hook can inspect every program.

### Immediate implementation

Not requested. This issue asks reviewers to approve or amend the design before implementation. No settings were changed and no enforcement is active as a result of this document.
