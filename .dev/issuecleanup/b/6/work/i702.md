## Feature Summary

Protect the default branch `master` of IronbellyOrg/IronClaude (and, with their own rulesets, `integration` and the `v*` release tags) so nobody can push to it directly, nobody can force push to it and nobody can delete it. Changes reach it only through a pull request that a person or an automation may merge. The ruleset is written in this issue and committed as three JSON files; an org admin applies it on GitHub.

## Problem Statement

Today nothing protects `master`. `gh api repos/IronbellyOrg/IronClaude/branches/master/protection` returns 404, `gh api repos/IronbellyOrg/IronClaude/rulesets` returns `[]` and `gh api repos/IronbellyOrg/IronClaude/rules/branches/master` returns `[]` (checked 2026-11-20). Anyone with write access can push straight to `master`, force push over it or delete it. In the last 90 days 11 of 243 first-parent commits on `master` came in with no pull request (9 of them from the web editor and ad hoc pushes by two people; the last was 2026-10-27). Everything in `master` reaches every user who installs or upgrades, so an unreviewed or rewritten history there is the most expensive mistake the repo can make. The maintainers (`clayphi`, `ironbelly`, one other maintainer and Ryan wiancko) and the agents that work in the repo have this exposure.

## User Story

As a maintainer of IronClaude, I want the server to refuse any direct push, force push or deletion on `master`, so that every change to the branch users install from arrives through a pull request, whoever or whatever makes it.

## Proposed Solution

Three repository rulesets, all with no bypass actors and written as JSON in the repo (full JSON and reasons in `## Design`):

1. `protect-master` on `~DEFAULT_BRANCH`: rules `deletion`, `non_fast_forward` and `pull_request` with zero required approvals (so a person or an automation can merge, as Clay ruled).
2. `protect-integration` on `refs/heads/integration`: the same three rules, its own ruleset so it can be switched off alone.
3. `protect-release-tags` on `refs/tags/v*`: rules `deletion` and `non_fast_forward` only; creating a tag stays open so `git push origin vX.Y.Z` in the release flow still works.

The repo work is the three JSON files, one developer doc with the apply, check and break-glass commands, updates to the release procedure and CONTRIBUTING.md, and a test that pins the JSON. Applying the rulesets on GitHub is a human step for the admin `ironbelly`; no agent applies it. No new client side `pre-push` hook is built (reasons in `## Design`).

## Alternatives Considered

- Classic branch protection instead of rulesets: also works on a public repo on the Free plan. Rulesets were chosen because the same mechanism covers `integration` and tags, there is no hidden "include administrators" switch (an empty bypass list means everyone is blocked), and each is one JSON file.
- A bypass actor for the admin (`{ "actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "pull_request" }`): not recommended; a release pushes only a tag and a zero-approval pull request needs no bypass.
- A new general client side `pre-push` hook installed by `superclaude install`: not recommended (it can be skipped with `--no-verify`, needs a global `core.hooksPath` or a per-repo copy, and the server rule already covers every clone).
- Required reviews or checks: not now (Clay did not ask).
- Dry-run (`evaluate`) enforcement first: needs GitHub Enterprise, so the rulesets are created `active`.

## Impact Analysis (Blast Radius, Integration Impact)

- Blast Radius: everyone with write access to the repo. Direct pushes, force pushes and branch deletion on `master` and `integration` stop working for people, the admin included. Web-editor commits to `master` stop (the 2026-10-27 pattern). No workflow, release step or local tool found in the audit pushes to `master`.
- Integration Impact: the release flow is unchanged (a pull request merge, then `git tag -a`, `git push origin vX.Y.Z`, `gh release create`). `/sc:pr-submit` and the claim pipeline only push feature branches and open pull requests. The CI workflows run on `push` and `pull_request` to `master` and `integration` and do not write. The master-into-integration sync must become a pull request.

## Risks & Mitigation

- Lock-out or wrong rule: the rule blocks an emergency fix. Mitigation: the break-glass steps (the admin sets the ruleset to `disabled`, pushes, sets it back to `active`, and comments who, when and why).
- Parameter names wrong: the JSON was not run against the API. Mitigation: the implementer tries it on a scratch repo first and runs the check commands after applying.
- Unknown pusher: webhooks, apps and deploy keys were not readable. Mitigation: the admin confirms them before applying (step 1 of the human apply step).
- Habit change: the sync of `master` into `integration` and web-editor edits now need a pull request. Mitigation: docs and a note to contributors.
- No audit log guarantee: whether the Free plan keeps a log of ruleset changes is UNVERIFIED. Mitigation: record every break-glass use as an issue comment.
- Other repos stay open: 45 live private repos in IronbellyOrg cannot be covered on the Free plan. Mitigation: reported in the follow-up list; Clay decides on the plan separately.

### Ruleset (written, not run)

**Plan check.** GitHub docs ("Available rules for rulesets", "About protected branches") say rulesets and protected branches are available in public repositories with GitHub Free for organizations, and in private repositories only with Pro, Team or Enterprise. IronClaude is public, so a repository ruleset works. Classic branch protection also works; a ruleset is chosen because it can target `integration` and tags with the same mechanism, has no hidden "include administrators" switch (no bypass list means everyone is blocked), and is one JSON file. `evaluate` (dry run) enforcement needs GitHub Enterprise, so the ruleset is created `active`.

**Rules:** `pull_request` (a PR is required, zero approvals, so an automation or one person can merge), `non_fast_forward` (blocks force push), `deletion` (blocks deleting the branch). No required reviews, no required checks, no linear history, no `update` rule (it would block merges too).

File `ruleset-protect-master.json` (committed as `.github/rulesets/protect-master.json`):

```json
{
  "name": "protect-master",
  "target": "branch",
  "enforcement": "active",
  "conditions": {
    "ref_name": { "include": ["~DEFAULT_BRANCH"], "exclude": [] }
  },
  "bypass_actors": [],
  "rules": [
    { "type": "deletion" },
    { "type": "non_fast_forward" },
    {
      "type": "pull_request",
      "parameters": {
        "required_approving_review_count": 0,
        "dismiss_stale_reviews_on_push": false,
        "require_code_owner_review": false,
        "require_last_push_approval": false,
        "required_review_thread_resolution": false
      }
    }
  ]
}
```

Command an admin runs (NOT run by the author of this issue):

```bash
gh api --method POST repos/IronbellyOrg/IronClaude/rulesets --input ruleset-protect-master.json
```

Check after: `gh api repos/IronbellyOrg/IronClaude/rules/branches/master --jq '.[].type'` prints `deletion`, `non_fast_forward`, `pull_request`. Then `git push origin HEAD:master` from a scratch clone must be refused with a message that changes must be made through a pull request. (The scratch clone needs one new local commit first, for example `git commit --allow-empty -m scratch`; a push of an unchanged `HEAD` is "Everything up-to-date" and proves nothing.)

UNVERIFIED: the exact parameter names above come from the GitHub REST rules page ("pull_request" requires the five parameters shown; `deletion` and `non_fast_forward` take none). They were not exercised against the API because the author has no admin right and must not change settings. The implementer runs the check above on a scratch repo first.

### Bypass

Recommendation: **no bypass actors** (`"bypass_actors": []`). Reason: the release flow pushes only a tag, and a PR with zero required approvals needs no bypass to merge, so a bypass would add risk and remove nothing. With an empty list the admin is blocked too, which stops the web editor commits seen on 2026-10-27.

Break glass if an emergency needs a direct push: the admin (`ironbelly`) sets the ruleset to `disabled` (`gh api --method PUT repos/IronbellyOrg/IronClaude/rulesets/<id> -f enforcement=disabled`), pushes, and sets it back to `active`. The record is a comment on the issue (or the incident issue) naming who, when and why, plus the ruleset change shown in the repository's rule history. UNVERIFIED: whether the Free plan keeps an audit log of ruleset changes; do not rely on it, rely on the comment.

If Clay prefers a built-in bypass: add `{ "actor_id": 5, "actor_type": "RepositoryRole", "bypass_mode": "pull_request" }` (repository Admin role, may bypass only through a pull request). Not recommended.

### Client side pre-push hook

What already exists: `src/superclaude/hooks/scripts/launch-level-pre-push.sh` (issue #441, merged in #469). It is installed per clone by the `/sc:issue --claim` pipeline into `.git/hooks/pre-push`, not by `superclaude install` (install only copies the template to `~/.claude/hooks/`). It refuses pushes to `refs/heads/main` and `refs/heads/master` only for a governed agent session or an unclassified actor, and lets a human push through unchanged. Its refusal for a missing install is a warning only (`IR7_REFUSE = False`).

Recommendation: **do not build a new general hook in this issue.** Reasons: (a) the server ruleset already refuses the push for every person and tool, including a clone where no hook is installed; (b) a hook is skipped by `git push --no-verify`, by `-c core.hooksPath=...`, and it exists only in clones where it was installed; Jay Wedgeworth's own review says the same, it stops a confused agent, not a determined one; (c) a general hook installed by `superclaude install` would need a global `core.hooksPath`, which replaces each repo's own hooks, or a per-repo copy, which the existing #441 design deliberately avoids (it refuses to shadow foreign hooks). Revisit only if, after the ruleset is on, agents keep wasting a push round trip on the server refusal; then extend the existing hook's "ordinary" branch to also refuse `master` when the repo has the ruleset, in its own issue.
