## What this adds, in plain English

When a person claims an issue with `/sc:issue --claim --pipeline <level>`, the agent that is started is now watched by one bash script, `launch-level-guard.sh`. Before the agent runs a tool, the guard checks what that call would do and blocks it if the agent's level does not allow it. Levels: `worktree` (plan only until a person types `approved` or `/sc:implement`), `full` (may implement and commit, never push, merge or open a PR) and `full --submit` (may also push a feature branch and open a PR on this fork, never merge, never touch `main` or `master`). The guard blocks, for example: implementing before approval, commits, pushes (any push outside the exact allowed form, and every push to `main`/`master`), PR creation without an explicit repo, merges (git, gh and MCP), writes through the GitHub API, edits of the hook state or settings, starting other Claude, Orca or terminal sessions, and scheduling new turns. It exists because a claimed agent otherwise relies only on instructions in its prompt, which it can ignore.

It is a text-layer guard: it checks the routes the design lists. It is not universal prevention and not a defence against a hostile agent.

## Claim side (the launcher)

- A governed launch is refused before any record is written or agent started unless the guard is installed, registered so it can fire (both events, right matcher, no `disableAllHooks`), `jq` and `uv` exist, and the Linux process interfaces of the job-identity hook are available. `W-ENFORCEMENT-ABSENT` now means a refusal. The check only sees the claim process, not the environment the agent will run in.
- The launch result carries the release instruction and the status of the L1 and L2 layers.
- A missing L2 pre-push layer is the warning `W-L2-ABSENT`; the launch continues.
