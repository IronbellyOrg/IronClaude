# PR #584 feat(issue-pipeline): approval core for the issue-watcher claim handoff (Plan A) and the first live-test record [MERGED] merged 2026-11-17T04:00:59Z b6d038a30c15ebeab5797c7b039500ee5dc6bb63
Plan A of the issue-watcher claim handoff (Decision 6 = B): the code that lets a person-opened coordinator approve a plan through Orca's own ask and reply, accept an approval from an issue label or an `approved` comment, and never start the stage twice. Task 16 (remove the plain `approved` route) already merged separately as #583.

## What is in it
- **New package `src/superclaude/cli/issue_pipeline/`** and a new `superclaude issue-pipeline` command group, registered next to `issue-watch` in `main.py`:
  - `plan-hash`: a SHA-256 over a named list of plan files (name, length and bytes each; refuses absolute names, `..`, symlinks, missing files).
  - `check-approval`: only `approved` and `approved <record-id> plan-sha256=<64 hex>` are accepted, whole text, no trimming.
  - `init`, `adopt-create`, `adopt-mark`, `record-create`, `record-show`, `record-mark`: a locked, write-ahead approval record (adoption row per issue and stage, approval row per plan hash) built on the watcher's `FileStore.lock()`; `issue_watch/record.py` is not edited.
  - Stage predicates for the approval label and the `approved` comment, GitHub reads that turn comment text into booleans inside jq (comment text never reaches Python), and the read-only `stage-status` verb.
  - The worker brief builder (`brief.py` and a fixed template; Feature rows only, type `bug` refused) that matches section 5 of `WORKER-CONTRACT.md` word for word.
- **Recorded real GitHub responses** for the owner's throwaway issue 452 under `tests/issue_pipeline/fixtures/recorded/`.
- **`docs/designs/issue-pipeline-fu1.md`**: the first-live-test runbook with its record filled in (preconditions a to k, run on issue 452 on 2026-11-17).
- **Approvals go through chat**: decision D2 in `WORKER-CONTRACT.md` and the technical reference is amended so a person gives a Ruling in chat and the agent in that session records it; nobody has to write an approval into a file. An agent's own or another agent's message is still not an approval.
- **Two stale mentions of the removed `approved` route** found by the independent security review of #583 (LL-TURN text in the guard and its plugin copy, and the technical reference's Approval paragraph).

## What the live test found (also in the runbook)
- `worker-start` runs `claude --dangerously-skip-permissions --allowedTools=Grep`; the reply to an `ask` is stored as type `status`; `ask` resumes by message id; the claim script's worktree step reuses an existing worktree.
- A label or Project Status move shows in the issue events with its actor and type; a comment typed in the web editor arrives as exactly `approved`, and an edit sets `lastEditedAt`.
