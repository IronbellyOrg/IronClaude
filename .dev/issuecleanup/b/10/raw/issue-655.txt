## History and carried-over detail for #655 (moved out of the issue body)

The issue body holds the current design and the orchestrator's runtime workflow. This comment holds the history and the detail of what was carried over from #331 and #450 and what was dropped. Nothing here changes the design; the body links to this comment.

### Why this issue exists

The work to pick up assigned issues automatically was spread over three places, and none of it has run live:

- #331 (closed 2026-11-08) asked for a watcher. It was built as `superclaude issue-watch`, a poller inside each workspace (PR #447, review fixes PR #448). It has never run live, ships with `enabled: false` and has no schedule.
- #450 (open, status BLOCKED in the 2026-11-17 review) tracks the rollout: the live test, the 24-hour shadow run and cron.
- The coordinator handoff (PRs #584 and #591, recorded in `docs/designs/issue-watcher.md` section 2.1) added a plan-approval step after the claim, with its own code in `src/superclaude/cli/issue_pipeline/`.

All of it is built around layers that Clay's 2026-11-18 comment on #450 and later rulings remove: a trigger label, a second approval label from an approver list, a GitHub Project in the Backlog column, a plan-approval gate after the claim, a separate watcher session that must talk to the orchestrator, and cron. Each layer is one more thing a person or an agent has to set or handle. Today the watcher also works on one repository only (`REPO = "IronbellyOrg/IronClaude"` at `src/superclaude/cli/issue_watch/github.py:37`, `ORIGIN_REPO` at `launch.py:50`), and `/sc:issue --claim` resolves its repository from `origin` only.

### Carried over from #450 and the design (each one lands in the spec with a disposition)

- Reuse of the built `issue-watch` code as the orchestrator's poll step: `runner.py`, `record.py` (the dispatch record and its lock), `audit.py` (the audit log and its closed reason table), `launch.py` (Orca lookup, origin check, launch argv and outcome mapping), and the call-budget, error classification and rate-limit code in `github.py`. `cycle.py` is reshaped, not reused as is.
- Its safety features, all kept: at most one launch per issue (a durable dispatch record is written before the launch), a lock against two runs at once, a GitHub call budget, an audit log, a dry-run mode, only a validated integer reaches the poll script's launch prompt (the prompt the automation's script uses to start a session; the rule does not cover the orchestrator's handoff prompt to its workers), and an origin check.
- The live test against real `gh` and Orca, on throwaway assigned issues, replacing every guessed fixture under `tests/issue_watch/fixtures/_assumed_shape/` with captured real output (design `docs/designs/issue-watcher.md` section 15 lists what is UNVERIFIED), and a written live-test record.
- The 24-hour shadow run (a dry run that decides but launches nothing), the two-process lock test and the restart test (`docs/designs/issue-watcher-setup.md` sections 7, 8.2 and 8.3), before switching on.
- Follow-ups: FU-3 (narrower GitHub token), FU-4 (alert after three bad cycles), FU-5 (cheaper GitHub reads, for example conditional requests), FU-6 (permissions of launched sessions), FU-8 (automatic launch retry; now the orchestrator's own single retry), FU-10 (service-level review after 7 days live), FU-11 (size bound for the dispatch store), FU-12 (check that the state folder is on a local disk).
- Issue #442's launch checks (OB-H1, OB-H2, OB-H3, OB-CTX of the launch-level guard) before any agent launch. No governed worker is launched for a real issue until OB-H1 item 1, OB-H2 and OB-H3 pass.
- Owner questions Q1 to Q4 of the design: Q1 (one launch per run) is replaced by the new-since-last-poll rule; Q2 is answered by the orchestrator's own check and single retry (confirmed by Clay); Q3 is answered by exponential backoff; Q4 is accepted as written.

### Dropped on purpose

- The trigger label (`issue-watch:trigger`): assignment is the only trigger, and a label is one more thing a person must set.
- The approval label and the approver list, with FU-9 (approver role check): there is no approval step, so no approver to check; the plan is reviewed when the issue is created.
- The Project and Backlog requirement (`project_id`, the project-items read): nothing may depend on the board.
- The plan-approval gate after the claim (WORKER-CONTRACT WC-17, the `issue-pipeline` approval rows and `stage-status`, and the approval part of guard G2): the plan is reviewed at creation, so the worker does not wait for a label or an `approved` comment.
- Cron (FU-2 and its six-field entry): an Orca automation replaces it.
- FU-7 (revisit D1 and D2): it becomes this redesign.

### Alternatives considered

- Keep a separate watcher session plus the orchestrator: rejected by Clay (two agents to manage, they must talk to each other, and the orchestrator must also talk to the workers).
- Cron or a hosted listener instead of an Orca automation: rejected (Clay's ruling; the listener is the design's rejected options B and C).
- Keep the approval label and Backlog column as optional extras: rejected, because nothing may depend on them and each is one more thing to set.
- Two issues (one for templates, one for the orchestrator): this is the second; #651 is the first.

## Body updated: additions A to E and Clay's rulings of 2026-11-19, applied by the orchestrator session

The body now says what the approved design spec says. The spec is `docs/designs/orchestrator.md` on branch `clayphi/issue-655-spec` (approved by Clay on 2026-11-19 with his approval of additions A to E; not merged yet). The body went from 63,144 to 64,486 characters (limit 65,536), so detail is compressed and points to the spec; no decision, ruling, acceptance criterion or test of the old body was dropped except where the spec removed it.

What changed in the body:

1. **Plan before the claim.** An assigned issue without the three plan sections is held: the poll puts the label `hold:plan` (label only, no comment). After one hour with no plan and no sign of plan work, the poll sends ONE plan request to the repo's orchestrator, which creates the plan through `/sc:issue --plan <N>` (a new pull request, PR P, built before PR B). `hold:backlog` makes the system do nothing at all with an issue. A hold removed by hand stays removed.
2. **What reaches Clay.** One table of nine rows (the old eight rules keep their numbers in a column), rules on from the start, no warn phase, an unanswered question waits, publishing or tagging a release always needs a human OK, notices and escalations are lines of the issue's own entry in the living report, at most 5 notices per repo per 24 hours.
3. **What the orchestrator may and may never do.** A closed list, checked by a function in the code. It may interrupt a worker once, after writing the escalation, when a major issue must reach Clay, and it may delete ordinary files its work needs. It never tags or publishes a release without a human OK or directive, and it never names the agent in anything user facing.
4. **Closeout.** After a merge, wave 8 calls `/sc:closeout <PR>` (issue 668, a dependency). The closeout decides whether the issue is DONE by reading the issue's own criteria against what the pull request and its linked pull requests delivered; it does not decide by the words Fixes, Closes or Refs. A worker pull request says `Fixes <repo>#<number>` only when it fully addresses the issue, otherwise `Refs <repo>#<number>` (ruling 38, a clarification by GeneralIronFlow of ruling 26).
5. **Hand-back (ruling 36).** If the closeout finds the issue not done, the result goes back to the orchestrator: it records what remains, updates the plan with `/sc:issue --plan <N> --remaining <file>`, and starts a new worker through the same waves on a new branch, after the old worker is final. At most 3 hand-backs, and a round that makes no progress stops at once; every stop is an escalation under row 9.
6. **Audit and merge safety.** After a pull request lands, an audit (AU1 to AU8) checks the merge; only three audit findings reach Clay. A pull request with an open "changes requested" review is never merged. A pull request that changes CI or another merge-safety file (the per-repo list `merge_safety_files` in `repos.yaml`) waits for Clay's explicit OK for that pull request and that head, even when green and reviewed; an unreadable file list is a hold.
7. **Pull request split.** D (retire the old approval gate), A (the poll), P (`/sc:issue --plan`), B (the orchestrator skill and verbs), C (move `agent-work-report`), E (fixtures, live test, runbook), in that order where section 8.2 allows; issue 668 is its own issue. Twelve `superclaude orchestrator` verbs, 62 poll reasons, 13 gate reasons, tests T1 to T13, risks K1 to K28, UNVERIFIED items U1 to U60.
8. **Dropped from the body because the spec replaced it:** the plan agent started by wave 2, the orchestrator's own `gh issue close`, the eight numbered escalation rules (now the nine rows), the "Needs you" entry as a way to reach Clay, and the spec-review build step.

For this build, no pull request is merged by the orchestrator session or any worker; each stops at CI green, Augment and Codex finished on the final head and no open thread, and Clay does the QA and the merge.

@ironbelly this is so you can read our version before we compare it with yours. Nothing here is merged and nothing is switched on.

**How it works in our design.** The polling watcher (your issue watcher, reshaped) does not hand the issue to the session. When it finds a new assigned issue, it starts the orchestrator/coordinator session for that repo if none is running, or wakes the one that is. It then types one fixed line into it: `/sc:orchestrator --wake <wake id>`. The wake id is only a timestamp plus random characters, so no text from GitHub ever reaches a typed line. The issue details are written to a separate wake file (JSON), with a matching Orca mailbox message, and the skill reads that file to learn which issue to work on. With nothing new, nothing starts and no model runs.
