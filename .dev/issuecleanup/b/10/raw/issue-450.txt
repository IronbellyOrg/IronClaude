@ironbelly my thoughts on the watcher and orchestrator design (this issue and #331), all in one place:

1. **Front-load the planning into the issue when it is created.** Every `/sc:issue --create` template should carry Priority, Fix approach and Test plan, whatever the type and complexity. Then the polling orchestrator or the worker that picks the issue up does not have to do this work: beyond that point it is just execution. That lets us use cheaper models for execution and better models for the planning up front. I filed that as its own issue: #651.
2. **The only required trigger should be an assigned person or bot.** Whoever picks it up first marks it as picked up (the claim's "Claimed by" comment already works as that mark). The extra trigger label, the second approval label from an approver list and the Backlog column add another layer that a person then has to go and set, or another agent has to handle. That becomes the new burden we are trying to remove. Planning and review happen in the issue as it is created; once created and assigned, it should trigger and run through the pipeline.
3. **The claim assigning the issue does not fit this.** `/sc:issue --claim` assigns the issue to whoever runs it as its first step, but under these rules an issue only triggers once it is already assigned, so that step does nothing here. Its only useful part for this flow is the picked-up mark.
4. **The orchestrator should do the polling and the claiming itself.** Otherwise we have another agent to manage (an issue watcher plus the orchestrator), the watcher and the orchestrator have to talk to each other, and then the orchestrator also has to talk to the workers.
5. **Use an Orca automation, not cron,** for the schedule (every 5 minutes, or whatever we choose).
6. **When the orchestrator picks up an issue that has no plan, it runs an issue agent to write the plan into the issue first.**
7. **When it launches the agent in the right repo and worktree, the orchestrator writes a handoff prompt from a template** about that issue, so the agent starts with everything it needs.
8. **Consolidate this work into one issue, maybe two:** the templates issue above, and one issue for the polling orchestrator that replaces the open pieces spread across #331, #450 and the coordinator handoff.

What do you think?
