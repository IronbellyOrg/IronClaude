## V/C/L/R challenge

Corrected scoring: Value 27, Complexity 34, Likelihood 20, Risk 34. Value drops because much of the 62K LOC already works today and the net-new benefit is conditional multi-tool/multi-tenant service operation, not reuse of dormant IP. Complexity rises because the study undercounts sprint/executor.py, monitor.py, auth/RBAC, Backlog mapping, and permanent Python+Node operations. Likelihood drops because roadmap/executor.py is only partly factory-wrapped, sprint is not Protocol-clean, ACP parity is unproven, and EE licensing is a gating commercial unknown. Risk rises because the highest-risk items are not peripheral: telemetry, permission semantics, tenant isolation, and source-of-truth integrity are load-bearing.

## Pre-mortems

| Target | Failure | Root cause |
|---|---|---|
| monitor.py stream-json to ACP reconstruction | The ACP adapter shipped but never reproduced Claude Code's exact assistant/user/tool_result event richness. Turn counts, token totals, tool error attribution, and stall detection became approximate, causing false recoverable reruns and silent over-budget runs. | The study treated AcpAgent as a structural replacement for ClaudeProcess, but /config/workspace/IronClaude/src/superclaude/cli/sprint/monitor.py lines 253-258, 398-407, and 434-442 show the current telemetry depends on Claude stream-json event shapes, not generic text deltas. |
| Mastra API churn | After 18 months, the team spent recurring maintenance cycles chasing Mastra workflow/auth/ACP API changes instead of improving SuperClaude's domain logic. | The recommendation assumes version-pinning and abstraction seams are cheap; in reality the platform front became a permanent dependency surface with migrations, security patch tension, and adapter drift. |
| Mastra EE licensing trap | Phases 0-4 succeeded technically, then the project stalled because multi-tenant RBAC/SSO required an unacceptable EE contract or a DIY auth build larger than the seam swap. | The strategic driver was commercially gated but postponed to Phase 5, letting engineering build momentum before validating the business constraint. |
| Python-behind-MCP permanent two-runtime tax | The hybrid became a durable Python+Node+MCP+HTTP system with duplicated deployment, tracing, schema, error handling, and incident-response surfaces; nobody funded the later TS migration. | The plan framed the Python boundary as reuse-maximizing but underpriced operational ownership, schema versioning, latency, and failure translation across runtimes. |
| Multi-tenant pilot loses to current CLI plus worktrees | The pilot demonstrated worse throughput and reliability than the current local CLI/worktree/subagent workflow, because tenant isolation, queueing, authz, Backlog sync, and observability overhead outweighed multi-user benefits. | The study assumes service-ification is inherently valuable; it does not prove that the target users are constrained by the current CLI rather than by review quality, task decomposition, or model behavior. |

## Gate challenges

- Mastra-early vs Mastra-late is partly decidable now: default KILL Mastra-early until @mastra/acp licensing, ACP parity, and EE economics are verified. Introducing Mastra before the seam spike only adds churn surface.
- ACP parity is correctly framed as unresolved, but too broad. Split it into hard blockers: permission semantics, turn/token reconstruction, process lifecycle/cancellation, and workspace isolation. A single vague parity gate invites a false pass.
- @mastra/acp license is decidable now from package/source inspection, so it should be Phase 0 day-zero procurement/legal evidence, not an open architectural gate. If it is EE-gated, the Mastra-late/vendor-free premise is dead immediately.
- Per-tool ACP parity for Cursor/Gemini/Copilot is mis-prioritized. The real Phase 0 need is Claude parity plus one second tool to prove abstraction value; Cursor/Copilot breadth can wait. Treating all tools as a gate front-loads uncertainty that is not needed for a go/defer decision.
- Permanent polyglot vs transitional hybrid is not a later philosophical question; it is an architecture decision that must be made before Phase 1. If the org cannot commit to permanent Python-behind-MCP operations, the hybrid recommendation collapses into a full rewrite/no-go choice.

Start with a smaller pipeline/roadmap semantic-layer path, then sprint only after telemetry evidence. |
| Phase 3 — Backlog.md as task-of-record | **REVISE** | Make it a mirror trial, not task-of-record. Backlog.md lacks native MDTM gate/convergence/checkpoint semantics; promote only after lossless round-trip evidence and one-authoritative-write-path rules. |
| Phase 4 — Mastra Server multi-user + second flagship | **REVISE** | Only proceed if Phase 0 proves Mastra-specific value over a thin Python ACP client. Otherwise an HTTP front can be built around the existing CLI without adopting Mastra workflows yet. |

## Top risks

- The study overstates the central abstraction: pipeline is Protocol-injected, but roadmap is only partly wrapped and sprint is not substitution-clean.
- The 1.2K Claude-coupled figure is only valid for process+subclass+monitor, not for all load-bearing Claude assumptions embedded in sprint executor, commands, TurnLedger, prompts, and hooks.
- monitor.py telemetry reconstruction is not a peripheral parser swap; it is the budget/stall/error signal source for sprint reliability.
- The strategic value depends on Mastra EE or a large DIY RBAC build, and this is deferred too late in the roadmap.
- Backlog.md cannot be promoted to task-of-record until MDTM semantics have a lossless mapping or a strict derived-mirror rule.
- Permanent Python-behind-MCP creates a two-runtime operations tax that the study treats as a mitigation rather than a product architecture burden.
- Multi-tool ACP parity may force lowest-common-denominator behavior, weakening Claude-specific permission, turn, and workspace guarantees currently relied on by the CLI.
