# Proposal D: Reuse-maximizing: swap only the runtime seam. Keep the Python orchestration/domain logic and the Markdown harness (skills/agents/commands/gates); replace ONLY ClaudeProcess/stream-json with Mastra+ACP as the worker driver and multi-tenant front; wrap Backlog.md/Beads behind the existing task/checkpoint models. Minimize rewrite.

**Recommendation:** `hybrid`

**Thesis:** The codebase was already built for runtime substitution: pipeline/executor.py runs against an injected StepRunner Protocol, roadmap/executor.py already wraps the runtime behind a `claude_process_factory` + `_ClaudeRunner` adapter, and sprint/executor.py has an explicit `delegate_runner` branch (line 1007). ClaudeProcess exposes a clean build_command()/start()/wait()/terminate() lifecycle with on_spawn/on_signal/on_exit hooks. That means ~62K of the ~73K LOC — all gate/convergence/FMEA/audit/spec-parse logic plus the entire Markdown harness — is runtime-agnostic and reusable AS-IS, while the Claude-Code coupling is concentrated in ~1.2-1.6K LOC (ClaudeProcess + the stream-json monitor + tmux + installers). The reuse-maximizing move is therefore NOT a TypeScript rewrite of 65K LOC (that destroys the reuse premise). It is: (1) freeze the Python domain layer as-is behind an MCP/HTTP boundary, (2) replace the ClaudeProcess seam with an ACP driver — either via Mastra's AcpAgent or, cheaper still, a thin in-process Python ACP/stdio client that preserves the existing StepRunner interface — and (3) adopt Backlog.md/Beads behind the existing TaskEntry/CheckpointEntry models. Mastra earns its place ONLY as the multi-tenant HTTP/RBAC front and multi-tool generalization; it does not, and must not, absorb the domain logic. The hard truth: the strategic driver (multi-tenant RBAC) is Mastra-EE-paid and lives entirely OUTSIDE the reuse story, so the runtime-seam swap is high-confidence and high-leverage, but it does not by itself deliver the company-wide goal — that requires a separate, paid, build-or-buy RBAC decision.

**V/C/L/R:** Value 32 | Complexity 27 | Likelihood 29 | Risk 24

> Value 32/40: unlocks ~62K LOC of differentiated gate/convergence/FMEA/audit IP for multi-tool reuse and turns a single-user CLI into a service — but the FULL strategic prize (multi-tenant RBAC) sits behind a paid gate outside the swap, capping value short of 40. Complexity 27/40: the seam itself is genuinely well-isolated (StepRunner Protocol + claude_process_factory already exist, verified), which lowers it; the Python<->TS boundary, stream-json->ACP event reconstruction, and dual-store sync push it up. Likelihood 29/40: the structural ACP/AcpAgent match is near-exact and the codebase was built for substitution, so the SEAM swap is highly likely to succeed; the multi-tenant goal is much less certain (EE cost, per-tool ACP parity unverified, Mastra 1.x API churn). Risk 24/40: concentrated, not diffuse — monitor.py/turn-ledger rewrite, unverified max_turns/permission parity, Mastra EE vendor lock for the actual driver, and Beads/Dolt churn (mitigated by dropping Beads). Hybrid scoping (keep Python, swap only the seam, defer RBAC) is what keeps all four numbers moderate rather than the XL-rewrite alternative which would push Complexity/Risk past 35.

## Top Risks

- stream-json -> ACP event impedance: monitor.py's turn accounting, stall-watchdog, token budgeting, and error detection are bound to Claude Code's verbose stream-json shape. ACP emits normalized text-delta/agent_message_chunk events — if they can't reconstruct max_turns/turn-boundary/stall signals, the TurnLedger economic model and recoverable-rerun logic degrade. Phase 0 must verify this; it is the single highest-uncertainty technical risk.
- Strategic-driver/scope mismatch: multi-tenant RBAC — the stated reason for the whole project — is Mastra-EE-PAID and lives entirely outside the reuse swap. The runtime swap can fully succeed and still NOT deliver the company-wide goal without a separate paid (or large DIY) RBAC build. Risk of declaring victory on Phases 0-4 while the actual objective is unfunded.
- Python->TypeScript boundary tax: reuse-maximizing keeps 62K LOC in Python behind MCP/HTTP. That boundary adds latency, serialization, and operational surface (two runtimes to deploy/observe). If teams later demand a single-language stack, pressure mounts to rewrite the domain logic in TS — which destroys the reuse premise. The MCP boundary must be treated as a permanent architecture, not a stopgap.
- Per-tool ACP parity unverified: Mastra docs validate only Claude Code/Amp/Codex via AcpAgent. Cursor/Gemini/Copilot 'should' work (they speak ACP) but are unverified, and the multi-tool driver is half the business case. Each non-Claude tool needs its own integration spike; permission/max-turns knobs may not be 1:1.
- Vendor + version churn: Mastra shipped breaking changes 1.0->1.16 (codemods, getAgents->listAgents, telemetry overhaul, Node 22.13 floor); EE is a bespoke commercial license. Beads moved to Dolt-only with live stability issues and a maintainer fork freezing the old arch. Betting the work-of-record on fast-moving targets requires version-pinning + abstraction seams (mitigated by dropping Beads now and keeping Backlog.md, which is MIT/stable, as the only new store).

## Key Tradeoffs

["Swap the seam, not the stack: keeping Python domain logic behind MCP preserves ~62K LOC of moat at the cost of a permanent two-runtime (Python + Node) operational boundary. The alternative — full TS rewrite — gives a single stack but throws away the very reuse this angle exists to protect. We choose the boundary tax over the rewrite.","Cheap seam vs. Mastra-native front: a thin Python ACP/stdio driver preserving the StepRunner interface is the lowest-rewrite way to get multi-tool support (Phases 0-2 need no Mastra at all). Mastra AcpAgent + Server is only required when the HTTP/multi-tenant front arrives (Phase 4+). Sequencing Mastra LATE keeps early phases vendor-free and lets the EE decision be deferred.","Backlog.md yes, Beads no (for now): adopt Backlog.md (MIT, git-native, built-in MCP) as durable task-of-record because it matches the existing markdown-harness value with low friction; defer Beads because its DAG-scheduling duplicates the MDTM phase model, its Dolt backend is churning, and shipping both invites dual-source-of-truth drift. Reversible — Beads can be added later if bd-ready proves its worth.","Drop terminal UX to gain a service: tmux/TUI/summarizer (~1.6K LOC) are single-user-local concepts incompatible with the multi-tenant goal; retiring them (replaced by Mastra Server + OTel) is net-positive for the strategic direction even though it loses the polished local dashboard.","Hybrid keeps 'do not port' honest: by delivering value incrementally (multi-tool driver at Phase 2, multi-user at Phase 4) BEFORE the expensive RBAC gate at Phase 5, each phase is independently justifiable. If Mastra EE pricing or per-tool ACP parity disappoints, the org can stop after Phase 4 with real gains and the Python harness intact — which is why this is hybrid, not an unconditional go."]
