# Base Selection

**Convergence score:** 0.82 (PASS)

## Selected base

Proposal D (reuse-maximizing — swap only the seam) as the ARCHITECTURAL base, fused with Proposal C (strangler-fig) as the EXECUTION base. D supplies the verified core thesis (the codebase was built for runtime substitution via StepRunner Protocol + claude_process_factory, confirmed in code), the correct disposition philosophy (keep ~62K LOC Python domain logic, swap only the ~1.2K-LOC seam, defer Mastra/EE to the latest justifiable phase), and the most precise risk localization (monitor.py stream-json→ACP reconstruction is the true risk, not AcpAgent itself). C supplies the operational backbone D lacks: the parallel-run-with-5%-tolerance acceptance gate, the correctly S-sized Phase 0 spike, per-phase go/no-go gates, and the file-level port_matrix for task generation. Proposal A is the source for the risk taxonomy and the canonical naming of the EE-strategic-mismatch; Proposal B is the source for the hard commercial Phase-0 stop/go gate and the 'keep current CLI as benchmark' discipline and the 'what would have to be true' criteria.

## Per-proposal verdicts

### Reference architecture — maximize multi-tenant capability (Mastra runtime + ACP multi-tool + Backlog.md task-of-record + Beads deferred; HYBRID).

- **Steelman:** This is the most intellectually honest of the four because it refuses to let the seductive AcpAgent-as-ClaudeProcess analogy inflate the recommendation. Its decisive move is the LOC stratification — verified here: only ~1.2K LOC (process.py 244 + sprint/process.py 385 + monitor.py 571) is genuinely Claude-coupled, while gates.py, convergence.py, and audit/wiring_gate.py have literally zero subprocess/ClaudeProcess imports (confirmed: grep returned 0). That number is the load-bearing fact of the entire decision, and this proposal gets it right and uses it correctly to conclude HYBRID rather than rewrite. The port_matrix is the most disciplined: it assigns 'reuse-as-is' to the ~12.7K LOC FMEA/audit heuristic mass with the explicit rationale that rewriting subtle regex/AST heuristics to TS is high-risk/low-reward — exactly the right instinct. It alone names the strategic contradiction out loud: the WHOLE reason for the port (multi-tenant RBAC) is Mastra-EE-paid and sits OUTSIDE the reuse story, so a technically successful port can still fail the business objective. Phase 0 as a hard go/no-go gate on max_turns/permission/CLAUDE_WORK_DIR parity is the correct risk-sequencing.
- **Strongest objection:** It is structurally identical to Proposals C and D on the actual engineering plan (Phase-0 ACP spike → port sprint first → domain logic behind MCP → EE decision gate last) yet scores itself materially MORE optimistic (likelihood 24 vs C's 28, vs D's 29) while carrying the SAME unverified risks. Its self-assessment is internally inconsistent: it rates likelihood at 24/40 (below C and D) but presents the most confident 'reference architecture' framing — the rhetoric and the number disagree. More substantively, it over-centers Mastra. It treats AcpAgent + Mastra Server as the spine from Phase 1, when Proposal D demonstrates (and the verified StepRunner Protocol + claude_process_factory injection confirms) that a thin in-process Python ACP client could deliver multi-tool support in Phases 0-2 with ZERO Mastra dependency, deferring all Mastra/EE vendor risk. By committing to Mastra early it imports API churn (1.0→1.16+ breaking changes) and the EE licensing question earlier than necessary. The 'reference architecture' label also subtly biases toward the maximal end-state when its own VCLR says much of the value already exists today.
- **Verdict:** STRONG on diagnosis, OVER-COMMITTED on sequencing. Accept its LOC stratification and its naming of the EE-strategic-mismatch as the canonical framing; reject its early-Mastra centering in favor of D's vendor-deferred sequencing. Best source for the port_matrix dispositions and risk taxonomy, not for the phase ordering.

### Feasibility skeptic — risk-first no-go/defer.

- **Steelman:** This is the indispensable adversary and the only proposal that keeps 'do not port' genuinely alive rather than as a rhetorical hedge. Its central insight is unassailable and verified: Mastra replaces ONLY the ~1.2K-LOC runtime seam; the other ~60K+ LOC is domain intelligence Mastra does not touch — so a like-for-like replatform spends most of its budget recreating what already works while risking the loss of Claude-native control surfaces (stream-json telemetry, max-turn accounting, permission flags, hooks, freshness enforcement). It correctly identifies that the strategic driver is commercially gated and frames the decision as conditional: the port is justified ONLY if (a) EE cost is acceptable, (b) ACP parity is proven for Claude + ≥1 non-Claude tool, AND (c) a hybrid preserves Python/Markdown IP. Its 'what would have to be true' closing is the strongest decision-theoretic framing in the set. The VCLR (value 22, likelihood 16, risk 36) is the honest worst-case anchor that prevents the other three from drifting into optimism. Keeping the existing CLI as the live benchmark and fallback during every spike is operationally correct and underweighted by the others.
- **Strongest objection:** It scores a strawman. Its VCLR is explicitly 'for a full Stack D replatform, not a narrow ACP spike' — but NONE of the other three proposals actually recommend a full big-bang replatform; all three recommend the same hybrid/strangler path this proposal would itself endorse. So its low scores (likelihood 16) measure a plan nobody is proposing, which makes the headline 'defer' recommendation misleading: once you read its own Phase 0-6, it is a strangler-fig migration with gates — functionally the SAME plan as C and D, just labeled 'defer' instead of 'hybrid.' The disagreement is largely semantic/temperamental, not architectural. Second, it slightly overstates irreplaceable Claude-native value: freshness hooks, verify-sync, and /sc:* loading are genuinely Claude-coupled but are dev-ergonomics, not the competitive moat — the moat is the runtime-agnostic gate/convergence/FMEA/audit IP, which the port PRESERVES. Treating hook loss as a first-tier strategic risk inflates the no-go case.
- **Verdict:** ESSENTIAL as the gate-setter, WEAK as a standalone recommendation. Its 'defer' is really 'hybrid with hard commercial+parity gates before any TS rewrite' — which is the consensus. Adopt its Phase-0 stop/go commercial gate, its 'keep current CLI as benchmark' discipline, and its 'what would have to be true' criteria verbatim. Do not adopt 'defer' as the headline; it mis-scores a plan no one is advocating.

### Strangler-fig incremental migration — seam first, parallel-run, EE decision at business gate.

- **Steelman:** This is the best-engineered execution plan of the four. The strangler-fig framing is exactly right for a system where the coupling is a single well-isolated seam: prove AcpAgent in a <2-week spike (effort band S — the only proposal to correctly size Phase 0 as small), then run the new Mastra sprint workflow in PARALLEL with the existing Python CLI for 2-3 sprints with an explicit 'identical outcomes within 5% tolerance' gate. That parallel-run-with-tolerance-gate is the single most valuable operational idea in the entire debate — it converts a high-blast-radius cutover into an evidence-gated, reversible transition, and no other proposal specifies a concrete acceptance threshold. Its port_matrix is the most granular (file-by-file with LOC and difficulty), making it the most actionable for task generation. It correctly flags the Python→TS serialization-impedance risk at the MCP boundary (gate predicates returning Python dataclasses parsed from stdout JSON) — a concrete operational risk the others gloss. Each phase has a clean gate, preventing sunk-cost lock-in.
- **Strongest objection:** It is the most optimistic scorer (likelihood 28, risk 28) yet inherits every unverified parity risk, and its Beads disposition is internally inconsistent with its own risk list. It assigns Beads 'adapt' (wire behind createTool, 'start with embedded mode') in the port_matrix while simultaneously listing Beads Dolt instability as a top risk and acknowledging dual-source-of-truth drift — Proposals A, B, and the Beads research itself all conclude DROP/DEFER for v1. D is the outlier that keeps Beads in the plan, and its own evidence contradicts that choice. Second, its VCLR omits the 'value' field entirely in the provided structure (lists likelihood/complexity/risk/notes but the value anchor is buried in notes), making its scoring less auditable than A/B. Third, Phase 3 (RBAC) is sized XL and gated on EE procurement, but the plan still front-loads Mastra Server in Phase 2 — partially importing the vendor risk that Proposal D-the-reuse-maximizer (Proposal 4) defers more cleanly.
- **Verdict:** STRONG and the best EXECUTION skeleton. Adopt its parallel-run + 5%-tolerance gate, its S-sized Phase 0, and its file-level port_matrix as the task-generation substrate. Override its Beads 'adapt' to DROP/DEFER (align with A/B/research). Use it as the procedural backbone of the merge.

### Reuse-maximizing — swap ONLY the seam, keep Python domain + Markdown harness, defer Mastra/EE to latest possible phase.

- **Steelman:** This proposal contributes the single most important architectural insight in the debate, and it is VERIFIED: the codebase was already built for runtime substitution. The pipeline StepRunner Protocol's own docstring names 'Launching the claude -p subprocess' as the runner's sole responsibility (confirmed), roadmap/executor.py uses claude_process_factory + a _ClaudeRunner adapter (confirmed at line 1364/1253), and sprint/executor.py has an injectable subprocess factory (confirmed at line 1007). This means the seam swap is genuinely low-risk-adapt, not rewrite — the callers are unchanged. Its sharpest strategic move is decoupling Mastra from the seam swap: Phases 0-2 need NO Mastra at all (a thin Python ACP/stdio client preserving the StepRunner contract delivers multi-tool support), so Mastra Server + the EE licensing decision are deferred to Phases 4-5 where they are independently justifiable. This is the lowest-VCLR-risk plan (risk 24, complexity 27) precisely because it minimizes new vendor surface. It correctly identifies monitor.py's stream-json→ACP event reconstruction as the TRUE risk concentration (not the seam itself), which is more precise than the others' generic 'parity' framing.
- **Strongest objection:** Its headline claim over-generalizes from the pipeline seam to the whole system, and the codebase partially refutes it. It asserts the sprint flagship has an 'explicit delegate_runner branch (line 1007)' proving built-for-substitution — but verification shows line 1007 is a private `_subprocess_factory` test-injection hook with a hardcoded default to `_run_task_subprocess`, NOT a first-class clean StepRunner Protocol. The name `delegate_runner` does not exist in sprint/executor.py. So the 'already built for substitution' thesis is solid for pipeline/roadmap but OVERSTATED for the 2150-LOC sprint flagship, where the seam is a narrower test hook entangled with the monitor/TUI/tmux/TurnLedger machinery. Second, the permanent two-runtime (Python + Node) boundary it endorses is a real long-term operational tax it acknowledges but underweights — 'treat the MCP boundary as permanent architecture' is a significant org commitment to polyglot ops that the VCLR risk of 24 may not fully price. Third, by deferring Mastra so late, it risks delivering 'multi-user' (SimpleAuth) but never the 'multi-tenant' company goal if momentum stalls at Phase 4.
- **Verdict:** STRONG and the best ARCHITECTURE. Adopt its 'swap the seam not the stack,' its verified StepRunner/factory reuse argument, its 'monitor.py is the real risk' precision, and its Mastra-late sequencing. Correct its sprint 'delegate_runner' overstatement: sprint's seam is a private _subprocess_factory, not a clean Protocol, so sprint Phase 2 carries more rewrite than this proposal implies. Best source for disposition philosophy; pair with C's execution gates.
