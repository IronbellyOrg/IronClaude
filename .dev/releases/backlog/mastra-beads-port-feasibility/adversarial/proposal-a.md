# Proposal A: Reference architecture — maximize multi-tenant capability: Mastra as the agent/workflow runtime + ACP multi-tool driver + HTTP/RBAC front, with SuperClaude's domain IP preserved behind an MCP/HTTP seam and ported incrementally.

**Recommendation:** `hybrid`

**Thesis:** The most capable end-state is a Mastra-centered orchestration service where (1) `@mastra/acp` AcpAgent replaces the ClaudeProcess/stream-json seam and generalizes it to multi-tool (Claude Code/Codex/Gemini/Cursor/Copilot via ACP); (2) Mastra durable workflows (branch/loop/suspend/resume snapshots to Postgres) replace the MDTM checkpoint+rerun control flow; (3) Backlog.md (MIT) is the git-native markdown task-of-record driven over its built-in MCP server, with Beads (MIT) as an optional derived dependency-graph/ready-work scheduler; (4) Mastra Server + EE Auth/RBAC/SSO supplies multi-tenancy. The decisive structural finding is that only ~1.2K of ~73K LOC is genuinely Claude-Code-coupled (verified: ClaudeProcess 245 + sprint subclass 385 + monitor 570 stream-json parser + install/hook plumbing); the other ~60K+ LOC (gates, convergence engine, FMEA suite, audit suite, structural/semantic checkers, cosmetic remediator, models, skills/agents markdown) is runtime-agnostic Python/Markdown — verified that roadmap/gates.py, roadmap/convergence.py and audit/wiring_gate.py have ZERO subprocess/claude runtime coupling (only TYPE_CHECKING imports and docstrings). This is therefore a STRONG fit for the runtime seam but a PARTIAL fit as a full replatform: the bulk of the value is a Python→TypeScript migration of domain logic Mastra does not replace, and the strategic driver (multi-tenant RBAC) is commercially gated behind Mastra EE. Recommendation is HYBRID, not a like-for-like rewrite.

**V/C/L/R:** Value 34 | Complexity 33 | Likelihood 24 | Risk 30

> Value 34/40: the prize is real — multi-tenant, multi-tool, multi-user company platform unlocking ~60K LOC of runtime-agnostic IP (gates/convergence/FMEA/audit) for reuse beyond Claude Code, plus a tool-agnostic future. Capped below 40 because much of that IP already works today; the NET new value is multi-tenancy + multi-tool, which is significant but not existential. Complexity 33/40 (high=worse): Python→TS migration of a ~73K-LOC layer, dual data stores (Backlog.md+optional Beads), a hybrid Python-service-behind-MCP boundary, Mastra EE integration, and per-tool ACP spikes. The hybrid (keep domain logic in Python) materially lowers this from a full-rewrite ~40. Likelihood 24/40 (success probability, high=better): the seam analog is near-exact (AcpAgent) which is encouraging, but multiple UNVERIFIED parities (max_turns/permission-flag, @mastra/acp license, Cursor/Gemini/Copilot via Mastra) and fast API churn (1.0→1.16+ breaking changes) make first-attempt success uncertain; Phase 0 is the make-or-break gate. Risk 30/40 (high=worse): EE licensing cost/vendor lock for the actual strategic goal, Mastra API churn, Beads Dolt instability, and impedance mismatch encoding rich MDTM semantics into Backlog.md. Conclusion: a defensible HYBRID with a hard Phase-0 gate, NOT an unconditional go.

## Top Risks

- Strategic-driver is commercially gated: multi-tenant RBAC/SSO (the WHOLE reason for the port) is Mastra Enterprise Edition (paid written commercial agreement; production use forbidden license-free). The business case hinges on EE cost vs. the build-cost of DIY RBAC on the Apache server. If neither pencils out, the port's core justification collapses — keeping 'no-go/defer' live.
- ACP parity is UNVERIFIED for the load-bearing knobs: max_turns, permission_flag (--dangerously-skip-permissions/--allow-hierarchical-permissions), and CLAUDE_WORK_DIR isolation. ACP is a thinner contract than stream-json; if it doesn't expose these 1:1, the sprint budget model (TurnLedger = max_turns × phases) and permission semantics break. Phase 0 must prove this before any commitment.
- Scope reality: ~60K of ~73K LOC is domain logic Mastra does NOT replace. The 'replatform' is mostly a Python→TypeScript rewrite (or a permanent Python-service-behind-MCP hybrid). Underestimating this as a 'seam swap' is the #1 way the project blows its effort band — roadmap alone is 16.7K LOC.
- Mastra API churn: verified breaking changes across 1.0→1.16+ (getAgents→listAgents, telemetry overhaul, Node 22.13 floor, pagination). @mastra/acp is brand-new (~May 2026). Betting the company orchestration layer on a fast-moving target requires strict version-pinning + codemod discipline + an abstraction seam over Mastra itself.
- Data-layer instability/overlap: Beads is Dolt-only with verified open ops issues (orphaned sql-server daemons, embedded-mode panics, migration pull failures) and architectural churn (contributor forked to freeze classic arch). Backlog.md + Beads overlap creates dual-source-of-truth drift. Mitigation: drop/defer Beads in v1, make Backlog.md the single work-of-record.
- Tenancy is absent in BOTH data stores: Backlog.md (single-repo, stdio-only, no remote transport) and Beads (one un-permissioned graph per DB) supply zero RBAC. All multi-tenant isolation lands on Mastra EE + a custom authz gateway provisioning per-tenant repos/DBs — a non-trivial build that is easy to under-scope.
- Impedance mismatch: rich MDTM semantics (convergence scoring, fidelity/structural/semantic gates, obligation scanning, certification) have no native Backlog.md schema. Encoding them as labels/notes/docs conventions risks lossy round-trips; keeping them in the Mastra/Python layer means Backlog.md is only a partial task-of-record.
