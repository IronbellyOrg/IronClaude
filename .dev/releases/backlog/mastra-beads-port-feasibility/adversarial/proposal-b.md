# Proposal B: Feasibility skeptic: risk-first no-go/defer case for porting /config/workspace/IronClaude/src/superclaude/cli/ from its Claude Code subprocess model to Stack D (Mastra + Backlog.md + Beads).

**Recommendation:** `defer`

**Thesis:** Defer the full replatform. The strategic goal is multi-tenant, multi-user, multi-tool orchestration, but Stack D only cleanly solves the narrow runtime seam: replacing /config/workspace/IronClaude/src/superclaude/cli/pipeline/process.py::ClaudeProcess with Mastra ACP. It does not replace the bulk of SuperClaude value: roadmap gates/convergence/certification, sprint recovery semantics, FMEA/dataflow/guard/conflict analysis, audit logic, Claude Code hooks, slash-command loading, or tasklist semantics. The port risks spending most of the budget recreating what already works while losing Claude-Code-native features that currently provide real control: stream-json telemetry, max-turn accounting, permission flags, hooks, freshness enforcement, tmux/TUI operational UX, and /sc:* command semantics. The business case is only credible if Mastra EE licensing is acceptable, ACP parity is proven for Claude Code plus at least one non-Claude tool, and a hybrid architecture can preserve Python/Markdown IP instead of rewriting ~65K LOC into TypeScript.

**V/C/L/R:** Value 22 | Complexity 35 | Likelihood 16 | Risk 36

> Score is for a full Stack D replatform, not a narrow ACP spike. Potential value is real but conditional: multi-tool, multi-user, observable workflows could matter company-wide. Complexity and risk dominate because Mastra replaces only the runtime seam while most value remains Python/Markdown domain logic. Likelihood is low unless the plan stays hybrid and Mastra EE licensing is approved. Quantified loss: a full rewrite exposes roughly 65K LOC of orchestration, including about 50K LOC of portable Python/Markdown IP, to migration defects; drops Claude-Code-native hooks and stream-json observability; adds Node/Mastra/ACP/Backlog/Beads/Dolt operational surfaces; and may still fail the core goal if RBAC/SSO is not licensed.

## Top Risks

- Strategic blocker: the stated driver is multi-tenancy/RBAC, but Mastra production RBAC/SSO/permissioned Studio is EE-licensed. Without a paid agreement or custom authz build, the port under-delivers the main goal.
- Runtime parity risk: ACP is structurally promising but may not expose Claude Code's exact max-turn, permission, stream-json telemetry, process lifecycle, and hook semantics. Losing these weakens sprint recovery, budget accounting, monitoring, and safety.
- Rewrite trap: Mastra workflow primitives can sequence steps, but they do not replace SuperClaude's domain intelligence. A TS reimplementation of roadmap/sprint/pipeline logic risks spending large effort to recreate current behavior with lower reliability.
- Claude-Code-native feature loss: hooks, /sc:* command loading, UserPromptSubmit context, freshness-pre-edit, verify-sync enforcement, tmux UX, and stream-json monitor behavior have no direct Stack D equivalent.
- Dual-source-of-truth risk: Backlog.md plus Beads plus existing MDTM tasklists can create three competing task graphs unless one is explicitly authoritative and the others are derived.
- Operational expansion: Stack D adds Mastra server, Node 22+, storage adapters, ACP subprocess adapters, Backlog stdio wrappers, possible Dolt server mode, possible Inngest, and EE auth. This is much heavier than the current local CLI model.
- Beads maturity risk: Dolt-only storage, open breakage reports, version-track ambiguity, and unverified MCP maturity make it unsuitable as first-wave company work-of-record infrastructure.
- Multi-tool overpromise: Claude Code, Codex, Gemini, Cursor, and Copilot may all speak ACP in some form, but equivalent behavior through Mastra is unverified. Tool parity must be measured, not assumed.
- Tenant isolation remains external: Backlog.md and Beads have no native RBAC/tenancy. Tenant boundaries must be enforced above them, usually by Mastra EE or a custom gateway.
- Opportunity cost: the same engineering time could harden the existing ClaudeProcess seam, add a small ACP adapter, or expose current Python logic as services without a platform rewrite.

## Key Tradeoffs

The real choice is not 'port or do nothing'; it is 'preserve current Claude Code leverage while proving a narrow multi-tool/multi-tenant seam' versus 'rewrite a working orchestration product into a newer runtime whose main strategic feature is commercially gated.' Full port destroys value if it converts proven Python/Markdown IP into TypeScript before validating RBAC licensing, ACP parity, and task-store semantics. A defensible path is hybrid and evidence-gated: keep SuperClaude as source of truth, test Mastra ACP as the worker seam, trial Backlog.md as a markdown task layer, defer Beads, and only expand if the pilot demonstrates material gains in tenant governance, concurrency, observability, and non-Claude tool support. What would have to be true to justify continuing: Mastra EE cost is acceptable; ACP matches ClaudeProcess behavior within defined tolerances; at least two non-Claude tools execute real sprint/roadmap work successfully; Python analysis/gate IP can be reused without TS rewrite; Backlog.md can represent MDTM tasks without lossy drift; and the multi-tenant pilot shows better company-wide throughput than the current CLI plus worktrees/subagents model.
