# Group 1 — Skeptic Triage & Coupling (structured)

**Strongest combined direction:** Agent 1 MODERATE serial StepRunner/dependency-aware per-task execution combined with a revised Agent 2 Lean handoff: dependency-scoped markdown context injected into each per-task prompt, generated from actual completed upstream TaskResult objects, persisted on disk with simple atomic writes. Do not add mailbox or parallelism until this serial model has correct resume, budget, and observability semantics.

## Coupling conflicts

- Swarm execution plus Agent 2's prompt-only/downward-leg handoff conflicts: sibling agents cannot see each other's in-flight or completed results through a single initial prompt, so fan-in and downstream dependency context are missing.
- Swarm execution plus unstructured markdown-on-disk conflicts unless atomic write/rename, unique task-addressed paths, and reader consistency rules are specified; otherwise parallel writers race on the same filesystem surface.
- Worktree-isolated swarm plus raw shared path references conflicts: a path injected from one agent's worktree or shared release directory may be stale, absent, or semantically different in another agent's worktree unless paths are normalized and copied through a join artifact layer.
- Serial per-task execution plus a full mailbox/ack mechanism is over-coupled: there is no concurrent sibling visibility problem, so the extra broker state can create new failure modes without providing speed or correctness benefits over dependency-scoped disk context.
- Single per-phase execution plus per-task bus/mailbox conflicts at the lifecycle level: there are no separate task subprocesses to address or ack, and the current per-phase prompt asks one agent to execute all tasks internally.
- Agent 2 Lean's "wire build_task_context into build_prompt" conflicts with Agent 1's per-phase default framing: `build_task_context()` needs prior `TaskResult` objects, while per-phase `build_prompt()` is constructed before tasks execute.

## Top open risks

1. Partial-failure recovery contract: current per-task branch ignores `remaining` and does not emit actionable `build_resume_output()`, so recovery semantics must be defined before claiming per-task isolation benefits.
2. Cost accounting and prompt growth: per-task cold starts plus repeated context injection can increase tokens; require measured before/after budgets and hard prompt-size caps rather than assuming savings.
3. State authority and observability: decide which artifact is authoritative among result files, NDJSON output, context markdown, and any future bus; otherwise debugging regresses as state fragments across surfaces.
