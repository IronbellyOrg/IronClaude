## 0. TL;DR

OPS-005 is the operational runbook that turns the **regression-halt emission rate exceeding 20% of fix-cycle batches** into an explicit on-call response procedure under Engineering-Lead ownership. It covers a single, observable rate-level signal:

> **Across a release window's fix-cycle batches (per-gate retry loops governed by the FR-CONV.5 4-step ordering `regression → monotonicity → hard-cap → proceed`), the byte-exact halt-string `Regression detected on Item X.Y — previously PASS at cycle N, now FAIL. Halt overrides monotonicity check.` emission rate exceeds the `>20%` threshold documented at `roadmap.md:435` + `roadmap.md:441` + `roadmap.md:461` + `roadmap.md:468`.**

This is a **rate-level fix-cycle-quality signal**, not a per-event correctness signal: each individual regression halt is *correct behaviour* (the regression guard fired as designed when a previously-PASS item flipped to FAIL on the next cycle — see `SKILL.md:1039` and `rf-task-builder.md:370`). What OPS-005 audits is the **aggregate frequency** of those correct emissions: when more than one-in-five fix-cycle batches in a window hit a regression halt, the spawn-templates for the per-gate fix-cycle subagents are systematically allowing the subagent to undo a prior PASS while resolving a FAIL — and the resolution lever is **upstream-prompt-tightening**, not contract or precedence modification.

OPS-005 sits on **Step 1** of the 4-step ordering (regression precedes monotonicity per `SKILL.md:1041` + `SKILL.md:1072-1079` + `rf-task-builder.md:370`); OPS-004 sits on **Step 2**. Because Step 1 always exits before Step 2 is consulted ("Do NOT consult subsequent steps" — `SKILL.md:1074`), every regression halt in a window *suppresses* a would-be monotonicity halt for the same cycle transition. The two runbooks compose explicitly at §2.4.4. The runbook is owned by the **Engineering Lead** (per `roadmap.md:468`) — distinct from OPS-004's rf-task-builder maintainer ownership — because the resolution lever (spawn-prompt revision across the per-gate fix-cycle subagent templates) cuts across the orchestration layer and requires Engineering-Lead authority over the prompt surface. The resolution path is single-track per `roadmap.md:435` R-156 acceptance criteria ("resolution = tighten fix-cycle prompts (X-003 slow-convergence threshold REJECTED)") — there is no dual lever, because regression rate is a function of fix-cycle subagent fidelity rather than of input distribution. The runbook contains the five mandatory sections (symptoms / diagnosis / resolution / escalation / prevention) called out in roadmap.md:435 + phase-7-tasklist.md L759-763.

**Scope boundary.** OPS-005 covers **rate-level regression-halt response** — specifically, the byte-exact regression halt-message emission rate exceeding `>20%` of fix-cycle batches in a release window. It does **not** cover:

- A single regression-halt emission per se — every individual emission is correct behaviour, by design (per `SKILL.md:1039` + `:1074`), and the operator response to a single halt is the per-gate cap fallback at `rf-team-lead.md:417` after the regression block (the fourth-precedence step), not a runbook event.
- Monotonicity-halt rate (`>50%` threshold) → OPS-004 (D-0095). The 4-step ordering rule guarantees regression precedence over monotonicity; OPS-005 reads the Step 1 rate, OPS-004 reads the Step 2 rate, with explicit composition rules at §2.4.4 below.
- Self-Audit / semantic-check audit-target events → OPS-001.
- Synthetic-dnsp emission-count → OPS-002. (Note: cross-cycle synthetic-dnsp re-emission with identical `dedup_key` is INV-012 / DEDUP and cannot trigger regression — the prior verdict was FAIL, not PASS. So synthetic-dnsp persistence inflates `|F_n|` for OPS-004 but does not feed OPS-005's numerator.)
- All-partitions-exhaust HALT (zero-success cohort) → OPS-003. The all-agents-fail guard at `SKILL.md:682` is upstream of the regression check; an all-agents-fail cohort produces zero regression halts because there are no successful partition outputs to compute a PASS set over.
- `make verify-sync` PASS-rate failures → OPS-006.
- INV-018 layout-change blast radius → OPS-007.
- **The byte-exact regression halt-message wire string itself**, the 4-step ordering rule itself, the per-gate independent-counter invariant, or the regression-as-binary-PASS-to-FAIL contract — all are **frozen contracts** (API-004 byte-exact emission per `roadmap.md:115`; COMP-001-M5 / COMP-002-M5 precedence-rule per `roadmap.md:319` + `rf-task-builder.md:358`; X-003 rejection per `roadmap.md:305`). OPS-005 does NOT modify these; it acts at the *spawn-prompt level* (per-gate fix-cycle subagent templates) to reduce the rate at source.
- **X-003 slow-convergence threshold** — explicitly REJECTED per `roadmap.md:305`; OPS-005 MUST NOT relitigate. Regression detection is binary (PASS@N → FAIL@N+1); it has no "slowness" dimension. The X-003 variant (which would have applied a tunable shrink-rate floor) was rejected because it would have halted legitimate slow convergence in addition to regressions, contaminating the signal.

## 2. Runbook — 5 sections

### 2.1 Symptoms

The on-call Engineering Lead is alerted (by the MET-004 offline-grep aggregation per `roadmap.md:441` — "offline-grep-aggregate-per-release", run at every release boundary against fix-loop logs; surfaced by the rf-task-builder maintainer per `roadmap.md:461`) when **all** of the following are jointly observed across a release window's fix-cycle batches post-MIG-005 (anchor commit `db6166e`, 2026-05-18 — FR-CONV.5 landed):

1. **Aggregate emission count.** Across the release window, `grep -c '^Regression detected on Item .* — previously PASS at cycle .*, now FAIL\. Halt overrides monotonicity check\.$' <fix-loop-logs-merged>` returns a non-zero count. The grep target is the byte-exact halt-string emitted by the FR-CONV.5 regression guard (`SKILL.md:1058` + `rf-task-builder.md:370` — byte-exact per API-004 wire-string contract at `roadmap.md:115`, including the em-dash `—` U+2014 per `SKILL.md:1060`).
2. **Per-batch normalisation.** Let `batches_total` = the total number of fix-cycle batches in the window (counting each independent per-gate retry-loop instance — research-gate, synthesis-gate, report-validation, task-integrity, qualitative — separately per the `SKILL.md:1043` independent-counter invariant and the `rf-task-builder.md:372` "per-gate retry counters ... are independent and NEVER collapsed" rule). Let `batches_regression_halted` = the count of fix-cycle batches where at least one regression-halt was emitted during the batch's lifetime. Compute `regression_halt_rate = batches_regression_halted / batches_total`.
3. **Threshold breach (the OPS-005 trigger condition).** `regression_halt_rate > 0.20` (i.e., **more than one-in-five fix-cycle batches halted on regression**) — per `roadmap.md:435` R-156 ("threshold-greater-than-20%-documented") + `roadmap.md:441` MET-004 trigger row ("regression-alert:>20%-triggers-OPS-005") + `roadmap.md:461` MET-004 governance row ("regression>20% → OPS-005") + `roadmap.md:468` OPS-005 row ("Threshold >20% of batches"). Anything `≤20%` is below the alert (a small residual rate is expected because the regression guard exists to catch real fix-cycle defects; zero would be ideal but not realistic).
4. **Window scope.** The default window is **one release window** (offline-grep aggregate per release per `roadmap.md:441` + `roadmap.md:574`). Per-release rather than per-day to dampen short-term jitter; a release boundary is the canonical OPS-005 inspection cadence.
5. **(Optional)** Co-occurrence with OPS-004 trigger (monotonicity-halt rate `>50%`). When OPS-005 trips alongside OPS-004 in the same window, the regression precedence (Step 1 → Step 2 per the 4-step ordering at `SKILL.md:1074` + `rf-task-builder.md:370`) means OPS-005's rate is a *causal upstream* of OPS-004's measurement — resolving OPS-005 (tightening fix-cycle prompts so previously-PASS items stop regressing) may by itself drop OPS-004 below its `>50%` threshold without any OPS-004-specific action. See §2.4.4.

Detection sources: (a) MET-004 offline-grep aggregation surfaced by rf-task-builder maintainer to Engineering Lead (canonical — per `roadmap.md:441` + `roadmap.md:461` + `roadmap.md:574`); (b) per-release post-mortem audit (release-spec §8.3 row) inspecting halt-rate metrics; (c) ad-hoc Engineering-Lead audit when a release-spec §8.3 audit row surfaces an anomaly; (d) the GA-tagging committee at MIG-007b (T07.20) reading the M7-audit summary.

**Symptom not in scope.** A single regression-halt emission is NOT a symptom of this runbook — it is *correct behaviour* (the fix-cycle subagent regressed a previously-PASS item and the guard fired as designed). The rate dimension is what OPS-005 audits. Likewise, the presence of `[HALT-MONOTONICITY] |F|=<n>` emissions within the window is a Step-2 signal that routes to OPS-004, NOT OPS-005; monotonicity halts are *suppressed by* regression halts in the 4-step ordering, so OPS-005 counts only the Step-1 emissions that exited before Step 2 could be consulted (per `SKILL.md:1074` — "Do NOT consult subsequent steps"). Slow-convergence patterns like `|F|=5,4,3,2,1` are NOT symptoms — X-003 was REJECTED per `roadmap.md:305`; slow convergence is *desired behaviour* and OPS-005 must NEVER attempt to detect or halt it.

### 2.2 Diagnosis

Within **24 hours** of the MET-004 alert (the canonical event), and within **4 business hours of acknowledgement** by Engineering Lead, the Engineering Lead performs the following ordered diagnostic steps (with rf-task-builder maintainer support per `roadmap.md:461`):

1. **Confirm the rate and identify the sample of regression events.** Capture:
   - (a) Release-window identifier (release tag or branch range).
   - (b) Total fix-cycle batches in window (`batches_total`) and the per-gate decomposition (research-gate count, synthesis-gate count, report-validation count, task-integrity count, qualitative count — each tracked independently per `SKILL.md:1043` + `rf-task-builder.md:372`).
   - (c) Total regression-halted batches (`batches_regression_halted`) and the per-gate decomposition.
   - (d) `regression_halt_rate = batches_regression_halted / batches_total`; record the per-gate sub-rates too.
   - (e) The full list of regression halt-string emissions in the window (one line per emission with batch identifier, gate name, regressed item `X.Y`, prior-PASS cycle `N`, cycle of FAIL re-emission `N+1`, the originating BUILD_REQUEST identifier, and the spawn-prompt template identifier in use at that batch).
2. **Sample 3 regression events for deep inspection.** Per `roadmap.md:435` R-156 ("sample 3 regression events"), select 3 regression events drawn from the per-gate decomposition such that the sample covers (a) the gate with the highest per-gate regression rate, (b) the gate with the highest absolute regression count, and (c) a third event from any *different* gate to surface cross-gate patterns in the spawn-prompt templates. (If only one or two gates produced regressions in the window, sample 3 from within the available gates, preferring batches with distinct BUILD_REQUEST identifiers and distinct spawn-prompt template versions.)
3. **Inspect what changed between cycles for each sampled event.** Per `roadmap.md:435` R-156 ("inspect what changed between cycles"), for each sampled regression event:
   - (i) Pull the cycle-`N` execution log and the cycle-`N+1` execution log for the regressed item `X.Y`.
   - (ii) Diff the per-cycle subagent input prompts. Identify whether the spawn template carried forward the prior-cycle PASS verdict ledger; whether the assigned_files / scope changed across cycles; whether the cycle-`N+1` prompt included an explicit "do not modify already-PASS items" clause or implicit equivalent.
   - (iii) Diff the per-cycle subagent output artefacts for item `X.Y`. Identify the concrete change between cycle `N` (verdict PASS) and cycle `N+1` (verdict FAIL): which line(s) / fact(s) / structural field(s) flipped state.
   - (iv) Classify the change against the spawn-prompt template structure: was the regression caused by (1) the subagent re-doing the work for item `X.Y` from scratch (no PASS-ledger carry-forward), (2) the subagent collaterally damaging item `X.Y` while resolving a different FAIL item (scope leakage), (3) the subagent applying an inconsistent rubric across cycles (rubric drift in the prompt), (4) a genuine specification change between cycles (BUILD_REQUEST mutation mid-pipeline), or (5) a contract regression (the regression guard misfired on an item that was NOT previously PASS).
   - (v) Note the spawn-prompt template version and the concrete clause that allowed the regression.
4. **Verify the regression check fired correctly (precedence sanity).** For each sampled regression event, the orchestrator's execution log MUST show: (a) the regressed item `X.Y` carried verdict PASS at end-of-cycle-`N` AND verdict FAIL at end-of-cycle-`N+1` (both confirmed by dedup-key identity per `SKILL.md:1068`); (b) the byte-exact halt-string `Regression detected on Item X.Y — previously PASS at cycle N, now FAIL. Halt overrides monotonicity check.` was emitted (em-dash U+2014, exact spacing, exact terminal period); (c) the halt-string was emitted BEFORE the monotonicity check was consulted on that cycle transition (Step 1 before Step 2 per `SKILL.md:1041` + `SKILL.md:1074`); (d) the monotonicity check was NOT consulted on the regressed item (`SKILL.md:1074` "Do NOT consult subsequent steps"); (e) item `X.Y` was NOT a synthetic-dnsp finding with cross-cycle same-`dedup_key` re-emission (INV-012 / TEST-022 — those are DEDUP, never regression). Any breach of (a) through (e) is a contract regression and routes to class C5 in step 5 (immediate Engineering-Lead escalation under contract regression; the rate measurement is invalidated by the contract breach).
5. **Classify the rate root cause.** Per `roadmap.md:435` R-156 resolution wiring, OPS-005 rate breaches resolve into one of the following classes:
   - **C1 — No PASS-ledger carry-forward in the spawn template.** Sampled regression events share a "subagent re-did item `X.Y` from scratch with no awareness of the prior-cycle PASS verdict" signature in step 3.iv class 1. The spawn template is missing or under-emphasising the "PASS items are frozen; only modify FAIL items" clause. **Resolution = §2.3 C1** (tighten the spawn template — add an explicit PASS ledger and a "do not modify already-PASS items" clause).
   - **C2 — Scope leakage from FAIL items into already-PASS items.** Sampled regression events share a "subagent was resolving a different FAIL item and collaterally damaged item `X.Y`" signature in step 3.iv class 2. The spawn template allows the subagent's modification surface to extend beyond the FAIL set. **Resolution = §2.3 C2** (tighten the spawn template — constrain modification scope to the FAIL items by name; require diff-against-prior-cycle-PASS-set to be empty for non-FAIL items).
   - **C3 — Rubric drift in the spawn template across cycles.** Sampled regression events share an "acceptance rubric for item `X.Y` shifted between cycle N and cycle N+1" signature in step 3.iv class 3. The spawn template re-states the acceptance criteria in different language each cycle, allowing the subagent to interpret the criteria differently and re-classify a previously-PASS item as FAIL. **Resolution = §2.3 C3** (tighten the spawn template — pin the rubric verbatim across all cycles within a batch; use a single source-of-truth criteria block carried forward by identity).
   - **C4 — BUILD_REQUEST mutation mid-pipeline.** Sampled regression events share a "BUILD_REQUEST changed between cycle N and cycle N+1" signature in step 3.iv class 4. The fix-cycle loop should treat BUILD_REQUEST as immutable within a batch; if it does not, the regression is a *correct* response to a legitimate spec change but the loop's framing is wrong. **Resolution = §2.3 C4** (tighten the spawn template — pin the BUILD_REQUEST hash at batch-start and reject mid-batch mutation).
   - **C5 — Contract regression (NOT an OPS-005 root cause).** Step 4 found one of: (i) the regression halt-string was emitted on an item that did NOT carry PASS at cycle `N`; (ii) the regression check was bypassed and the monotonicity check fired on a regressed item; (iii) the byte-exact halt-string deviates from `Regression detected on Item X.Y — previously PASS at cycle N, now FAIL. Halt overrides monotonicity check.` (API-004 wire-format violation per `SKILL.md:1058` + `:1060`); (iv) a synthetic-dnsp cross-cycle re-emission triggered a regression halt (INV-012 violation per TEST-022 / `SKILL.md:1068` + `:1083`). **Resolution = §2.3 C5** (immediate Engineering-Lead escalation under contract regression — OUT OF SCOPE for OPS-005's rate-level remit, IN SCOPE for release-spec §19.4 rollback path scoped to FR-CONV.5).
6. **Confirm X-003 is NOT being relitigated.** Verify the diagnosis does not contain any of the following X-003-leaning recommendations: (a) "raise the >20% threshold to reduce alert volume"; (b) "ignore regression events where `|F|` shrank slowly across cycles"; (c) "apply a per-batch slowness threshold to filter out 'soft' regressions"; (d) "treat near-identical PASS↔FAIL flips on the same item as DEDUP-equivalent to synthetic-dnsp." All four are forbidden — X-003 was REJECTED per `roadmap.md:305` because regression detection is binary, and any "softening" introduces false negatives (real fix-cycle defects being filtered out under cover of "slow convergence"). The X-003-REJECTED preservation is part of OPS-005's resolution contract.
7. **Compose with peer runbooks.** Inspect whether the window also tripped OPS-004 (monotonicity-halt rate `>50%`). When both trip: regression halts at Step 1 *suppress* would-be monotonicity halts at Step 2, so OPS-005 is the *causal upstream* of OPS-004's measurement — see §2.4.4. Inspect whether the window also tripped OPS-002 (synthetic-dnsp emission count `>0` in production): synthetic-dnsp cross-cycle persistence CANNOT trigger regression (INV-012 / TEST-022) but a synthetic-dnsp finding with the *same dedup-key* on cycle `N+1` after a *real* PASS at cycle `N` on a *non-synthetic* item with that same dedup-key would be a contract regression (route to C5). Cross-runbook composition is documented at §2.4.4.

### 2.3 Resolution

The resolution path is **single-track** per `roadmap.md:435` R-156 acceptance criteria ("resolution = tighten fix-cycle prompts (X-003 slow-convergence threshold REJECTED)"). Every C1..C4 root-cause class resolves into a spawn-prompt revision; C5 is excluded from OPS-005's rate-level remit and routes to a separate Engineering-Lead contract-regression response. X-003 remains REJECTED and MUST NOT be revisited as a resolution lever.

### 2.5 Prevention

Prevention is enforced by four layered controls, all of which exist at landing time and persist through GA:

1. **API-004 byte-exact regression halt-string contract.** The wire string `Regression detected on Item X.Y — previously PASS at cycle N, now FAIL. Halt overrides monotonicity check.` is frozen at M1 per `roadmap.md:115` ("contract-freeze"); any drift (typo, capitalisation, spacing, em-dash variant, terminal-period omission, `X.Y`/`N` substitution-form drift) is detectable by exact-match grep and rejected at the FR-CONV.5 fixture gate (TEST-016 at `roadmap.md:324` — "grep-verbatim-message; ordering-assertion:confirms-regression-check-runs-first"). The byte-exact contract makes the rate measurement deterministic at the offline-grep aggregation layer.
2. **COMP-001-M5 / COMP-002-M5 precedence-rule freeze.** The 4-step ordering rule (`regression → monotonicity → hard-cap → proceed`) is documented in three byte-stable places: the A.9 invariant tail at `SKILL.md:1041`, the protocol body at `SKILL.md:1072-1079`, and the rf-task-builder halt-precedence-rule paragraph at `rf-task-builder.md:358-372`. Triple-anchoring makes accidental modification surface in at least one place under `make verify-sync`.
3. **X-003 explicit-rejection contract.** Per `roadmap.md:305` ("X-003 slow-convergence threshold remains REJECTED"), no slow-convergence threshold may be introduced into the regression check. This guarantees that legitimate slow convergence (`|F|=5,4,3,2`) NEVER triggers a regression halt, and that the regression rate signal is uncontaminated by false-positive halts on slowly-shrinking cohorts. Without X-003 rejection, OPS-005 would chase ghost rate breaches on slow but legitimate fix cycles; with it, the regression halts that fire are PASS↔FAIL flips on items by dedup-key, full stop.
4. **TEST-016 + TEST-022 cross-fixture invariant.** TEST-016 (PASS@1/FAIL@2 → regression halt with verbatim message BEFORE monotonicity) and TEST-022 (synthetic-dnsp same-`dedup_key` across cycles 1+2 → no regression halt, cycle 3 attempted) together pin the regression contract from both directions: the positive direction (a real PASS↔FAIL flip must halt with the byte-exact message and ordering) and the negative direction (a synthetic-dnsp cross-cycle re-emission must NOT halt — INV-012 preservation). Both fixtures must pass at every release-spec §8 pre-merge gate.

Secondary preventive measures:

- **Pre-merge gate.** Every PR that touches the FR-CONV.5 surface — `SKILL.md:1032-1095` (Retry Monotonicity Protocol), `SKILL.md:1058` + `:1060` (regression halt-string wire format), `SKILL.md:1972` Critical Rule #12, `rf-task-builder.md:358-372` (halt-precedence rule + monotonicity-guard wrapper + regression-check-first emitter) — MUST run `make verify-sync` (A-001), the FR-CONV.5 fixtures (TEST-014..017 + TEST-022 per `roadmap.md:323-326`), and a byte-diff confirmation that the API-004 wire-string contract at `roadmap.md:115` is unchanged.
- **MET-004 dashboard** (per `roadmap.md:441` + `roadmap.md:461`) — combined halt-rate metric tracks all 3 halt-message families (synthetic-dnsp, HALT-MONOTONICITY, regression-halt) with explicit per-trigger routing into OPS-002 / OPS-004 / OPS-005.
- **Release-spec §8.3 audit row** — every release's post-mortem inspects the regression-halt rate; the Engineering Lead maintains a rolling window log so trend lines (not just per-release point readings) feed the GA-tagging committee.
- **Spawn-template versioning.** Per-gate fix-cycle subagent spawn templates carry an explicit version identifier in the spawn payload; the template version is logged alongside every regression halt-emission. This makes §2.2.3.v ("identify the spawn-prompt template version and the concrete clause that allowed the regression") mechanical rather than archaeological.
- **PASS-ledger carry-forward as a first-class spawn-payload field.** Independent of any C1 remediation: spawn templates carry a `PASS_ledger` field by construction; the field's presence is checked at spawn-emission time and an empty field on a non-first-cycle spawn is itself a defect signal (precursor to C1).
- **Rubric-pinning as a first-class spawn-payload field.** Spawn templates carry the rubric by reference to a hash-stable block (`RUBRIC_v<hash>`); the field's hash is logged at spawn-emission and any cross-cycle hash mismatch within a batch is itself a defect signal (precursor to C3).
- **Audit-trail explicitness.** Every regression-halt emission carries (i) the regressed item `X.Y`, (ii) the prior-PASS cycle `N`, (iii) the cycle of FAIL re-emission `N+1`, (iv) the gate name, (v) the originating BUILD_REQUEST identifier, (vi) the spawn-prompt template version — making per-window aggregation per-gate-decomposable and per-template-version-decomposable from logs without re-running pipelines.
