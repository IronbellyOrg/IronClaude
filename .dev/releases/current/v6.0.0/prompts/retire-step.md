## Scope
Plan item PR 12, the retire step. This is NEW CODE, not a removal. The installer reinstalls what a release ships but never deletes what a release stops shipping, so a workspace upgraded from 5.0.0 keeps dead commands and skills (for example `/sc:roadmap`, which would call a `superclaude roadmap run` that no longer exists). Codex and Augment raised this on every removal PR (#617, #621, #622, #627, #632); the answer on each was "PR 12". Now build it.
What to build (model it on `src/superclaude/cli/install_retired_mcp.py`, which already does this for MCP registrations: read its module docstring and `run_retire_step`, `classify_*`, and how `superclaude install` calls it and never changes the exit code):
- When an existing install is upgraded (`superclaude install`, and `superclaude update`/`./update.sh`, which call the installers with force), remove from the user's `~/.claude/` the commands, skills and agents that 6.0.0 no longer ships, but ONLY files IronClaude can prove it wrote. Proof for a file = its content is byte-identical to the content some IronClaude release shipped (the sha256 of each file as shipped at the `v5.0.0` tag; installed commands and skills are plain copies, but check `install_commands.py`, `install_skills.py` and `install_agents.py` for anything that rewrites content or records a receipt, and use that if it exists). A skill is a folder: remove it only if EVERY file in it is provable; otherwise keep the whole folder.
- Anything not provable (edited by the user, an extra file in a skill folder, a name that is not on the list) is KEPT, and the installer prints one plain line per kept item saying why and the exact command that removes it (as the MCP step's Tier K does). Never touch a file or folder whose name is not on the generated list; never touch anything outside `~/.claude/commands/sc/`, `~/.claude/skills/` and `~/.claude/agents/`.
- The removed names are GENERATED from the difference between the `v5.0.0` tag and this tree (so no other PR edits a shared list). At this commit the difference is: commands `build`, `cli-portify`, `improve`, `index-repo`, `index`, `load`, `review-translation`, `roadmap`, `save`, `spawn`, `tasklist`, `validate-roadmap` (12); skills `sc-cli-portify-protocol`, `sc-review-translation-protocol`, `sc-roadmap-protocol`, `sc-tasklist-protocol`, `sc-validate-roadmap-protocol` (5); agents none (the mechanism must still handle agents). Verify this list yourself with `git ls-tree` against the tag before you use it. Commit the generated data (names plus the sha256 of each file at `v5.0.0`) as a small data module and keep the generator script in the repo, so the next release regenerates it from its own previous tag. A static test must check the data's shape (every listed name is absent from the shipped sources, every hash is 64 hex characters); do not make CI depend on the tag being present (skip with a clear reason if it is missing).
- Idempotent (a second run changes nothing and prints nothing alarming), safe when `~/.claude` does not exist, and a failure to delete one item is reported and never changes the install's exit code.
