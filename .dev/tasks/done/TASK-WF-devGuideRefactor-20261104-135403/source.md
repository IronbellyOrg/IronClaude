# Request (round 3): make the developer guide teach Orca-ready commands, skills and agents

## What to change and why

Refactor `docs/developer-guide/SuperClaude-Developer-Guide-Commands-Skills-Agents.md` so every future command, skill and agent is authored to run correctly under Orca orchestration (the `/orchestration` skill: an Orca coordinator session dispatching IronClaude `/sc:` commands to worker sessions).

Why: the Orca worker-contract work on this branch (commit 8db29f11) added `src/superclaude/core/WORKER-CONTRACT.md` (installed to `~/.claude/WORKER-CONTRACT.md`), an "Orca coordination" section at the end of `src/superclaude/core/HOW-WE-WORK.md` (mirrored byte for byte in `plugins/superclaude/skills/sc-recommend/refs/HOW-WE-WORK.md`), and `tests/skills/test_worker_contract.py`. The developer guide was never updated: it never mentions Orca, `--unattended`, `--report-dir`, the `## Unattended mode` section, the worker contract fields, the never-as-worker list, the nested propagation rule, the person-mode flag refusal, or WC-2, WC-4, WC-7, WC-8, WC-9, WC-10, WC-11.

This is the third request for the same change. Two earlier plans were reviewed before execution and both failed: round 1, `.dev/reflect/pre-TASK-WF-refactorDocsDeve-20261104-062532-20261104062951/adversarial/merged-verdict.yaml` (findings M-01 to M-17), and round 2, `.dev/reflect/pre-TASK-WF-devGuideRefactor-20261104-124528-20261104125026/adversarial/merged-verdict.yaml` (findings MF-01 to MF-12). ## Scope

One delivery file only: the developer guide.

- Add one new subsection, `### 7.6 Orca Orchestration: Commands as Workers`, after 7.5 and before the `---` that precedes `## 8. Development Workflow`. It holds: how the pieces fit (coordinator, workers, one command per worker, commands contain no Orca calls); the rollout state (at P0 no command accepts `--unattended` or `--report-dir`; a command gains its `## Unattended mode` section in the phase that converts its gates, from P1; without the flag every command behaves as it does today); deciding whether a new command can be a worker (the never-as-worker list); what a worker-capable command must do under `--unattended`; the `## Unattended mode` section a converted command carries; and how skills and agents under the command inherit the rules.
- Wire it into these existing touchpoints: the table of contents; 1. Introduction (installation locations and context loading: `WORKER-CONTRACT.md` is an installed core file read on demand, never `@`-imported); 3.1 command anatomy; 3.2 command archetypes; 3.6 registering a new command; 4.2 agent patterns; 5.9 input and output contracts; 5.10 skill-authoring checklist; 8.3 new-component workflow; 8.4 testing; 9.1 and 9.3 best practices; 9.7 anti-patterns; Appendix A skill skeleton; Appendix B command template; Appendix D path reference; Appendix E glossary.

## Corrections the plan must carry

- Worker fields and a command's own status (M-01, MF-05). In prose that explains the worker contract file (7.6 and 5.9), state both WC-4 cases in full: a command that already writes `return-contract.yaml` in the report directory itself keeps every existing field, including its own `status`, and adds the worker fields beside them; a command whose own contract lives elsewhere leaves that file unchanged, and the worker contract at `<report-dir>/return-contract.yaml` lists it in `artifacts`. Elsewhere (5.10, 9.3, 9.7, the glossary) a line that names "the WC-4 two-case rule" with a link to 7.6 or 5.9 is enough. No line anywhere states the first case without its condition.
- Who may ask whom (M-02). The agent-patterns text and 7.6 use separate sentences for three rules: only the top-level worker session sends lifecycle messages (heartbeat, ask, check, `worker_done`), never a subagent (WC-7); a command never calls `worker-start`, `dispatch` or `task-create`, so no agent inside it does (WC-8); under `--unattended` nothing asks the person, because each gate resolves by a documented default, a caller flag, or blocked (WC-2), and only the worker session may put a blocked question to the coordinator, and only when the brief allows it (WC-3). No sentence says or implies that a worker session, command or agent asks the person or the user. An acceptance criterion checks lines containing "the person", "the user" or "a person" and allows only lines that say nothing asks them.
