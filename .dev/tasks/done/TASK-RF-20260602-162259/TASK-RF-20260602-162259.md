# Durably Fix Tool-Write Schema roadmap_ids Drift via a Per-Step Family SoT + Assembler

## Task Overview

The `MD` spec family (`M\d+-D-?\d+`, matching milestone-prefixed deliverable IDs like `M1-D01`) lives in `superclaude.contracts.ID_PATTERNS` (added in commit cf3594d2, R5 remediation) and is threaded through the markdown path. However, the four tool-write JSON schemas under `src/superclaude/cli/roadmap/templates/tool_schemas/` (`extract`, `extract_tdd`, `generate`, `merge`) were authored concurrently in commit c542b6bf (R1.4) with their own hard-coded `roadmap_ids.items.pattern` regex, and **all four omit `MD`**. As a result, a roadmap carrying a `roadmap_id` of `M1-D01` is rejected at schema validation (`tool_writer.validate_tool_output`) in tool-write mode. Tool-write is non-default (cutover is R1.6 per commit 44f78a01), so this is latent and LOW-MED severity today, but it MUST be closed before cutover. Worse, the four guard tests that are supposed to catch this drift are structurally broken: they iterate a frozen tuple `("FR","NFR","SC","G","D")` that never included `MD`, and they use substring containment (`ID_PATTERNS[family] in pattern`) which can never distinguish arm boundaries — and because the `D` body `D-?\d+` is a literal substring of the `MD` body `M\d+-D-?\d+` (the MD⊂D trap), substring matching gives false safety. `arch_lint` enforces the contracts SoT for `.py` files only; the JSON schemas are entirely unguarded, which is the structural gap.

This task establishes a single derivation source for the schema patterns. Per the research VERDICT (research file 02, PASS at both research gates), the per-schema family-set differences are **INTENTIONAL per-step semantics** — extract_tdd's six extra families `{DM,API,COMP,TEST,MIG,OPS}` map exactly to its six typed entity arrays; extract carries only `{COMP,DM}` (component_inventory-backed, plus a fixture-backed DM arm); generate/merge add `OQ` which only legitimately arises from `milestones[].open_questions[].id`. Therefore the assembler MUST be **per-step-aware**, NOT one flat pattern. The fix adds a per-step family-set map (`TOOL_WRITE_ROADMAP_ID_FAMILIES`) + an entity-family-body registry (`ROADMAP_ENTITY_ID_FAMILIES`) + a per-step assembler (`roadmap_ids_pattern(step)`) to `superclaude.contracts`, leaving `ID_PATTERNS` UNTOUCHED as the six-spec-family SoT (promoting the extras would pollute `spec_parser.extract_requirement_ids` regex extraction — REJECTED). The four schema patterns are regenerated from the assembler (MD lands in all four; the COMP-before-DM ordering anomaly in extract is corrected). The four guard tests are rebuilt to iterate the LIVE family set and assert EXACT ARM-LEVEL membership (strip `^(…)$`, split on `|`, check each expected family body is an exact arm), with an explicit `M1-D01`-validates regression plus an `ID_PATTERNS["MD"]`-is-its-own-arm assertion. All work stays on branch `refactor/roadmap-pipeline-r0-r1-rewrite`, edits only `src/superclaude/` and `tests/`, and NEVER stages `.claude/`.
