## Normal Installer Skip Debate

Situation: Orca's normal safe install (no `--force`) exits 0 and skips an edited or foreign guide. All three SKILL.md files are present, IronClaude passes no `--force`, and nothing is overwritten. Runtime causation of issue #412 is not proven (plan:19).

**Does the nonforce early return survive for force=False?** Yes. Plan:45 allows the short-circuit "only when force is false", and plan:50 requires "Nonforce repeated setup still skips existing guides with no Orca calls". The existing test at `tests/cli/test_install_user_setup.py:288-294` already pins the no-call behavior for the default argument, so a change that broke it would fail an existing test. ADDRESSED (INV-001).

**Is the forced path guarded against the trivially passing presence check?** Partly. Everyone agrees on the mechanism (A-002, 3/3): with all three files present before the call, ius:257-258 cannot fail on count, so only `returncode` and the relayed output carry information. Plan:24 and plan:45 forbid letting a success summary stand in for a refresh, and R3-2's verifier (exit 0, three present, skip on stdout, "no refresh-success claim") was adopted unanimously. That covers the case where Orca reports something on stdout (INV-003, INV-004). Two cases are left open: a skip reported only on stderr (INV-005, MEDIUM), and empty output (INV-006, MEDIUM).

**Can a safe skip be reported as a refresh?** Not under the plan text. Plan:24, plan:45 and plan:51 together require the skip text to be visible and forbid using a success line as proof of refresh. The remaining paths to a false impression are verifier gaps, not plan gaps: (a) relaying stdout only when Orca puts the skip on stderr; (b) wording on the forced exit-0 path that says "refreshed" or "updated" when IronClaude only knows the files exist. Neither is HIGH, because plan:45 names stderr explicitly and plan:24 forbids (b) in so many words; an implementation doing either would break written plan text, which the post-implementation review checks.

**Is the "no --force" guard testable?** Yes. `subprocess.run` is already mocked to capture argv (`tests/cli/test_install_user_setup.py:264-287`), so `"--force" not in command` is a one-line assertion on the forced path. Plan:50 states the requirement. What a mock cannot show is Orca's own refusal to overwrite edited copies; that is documented help (`orca-discovery.md:21`), and plan:52 requires logs to keep mocked checks separate from actual Orca evidence. ADDRESSED (INV-007, INV-008).

**Is the empty-output case covered?** Not fully. V1's empty-output test was merged into C-001, but no card says what it must assert. On documented help an empty report means nothing was skipped, so a presence-only success line is defensible. "Refreshed"/"updated" wording is not, because IronClaude cannot tell an updated owned copy from an unchanged one. Fix the expectation before implementation (INV-006, MEDIUM).

**Sufficiency.** For an edited or foreign guide, the forced safe install will never refresh it; the honest outcome is a visible warning. The source asks for exactly that, and plan:19 and plan:52 keep the claims bounded, so this is not a gap (INV-020). The one new cost the review did not weigh is time: every forced run, including every `superclaude update` (`main.py:404`), now spends Orca probe and install time out of the 30 s budget it shares with `install_plugins` (INV-009, MEDIUM; nonfatal and reported as "(time limit)", so not HIGH).
