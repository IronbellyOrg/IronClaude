# Implement Sprint Run 429 / Account-Exhaustion Recovery (P1-P6)

## Task Overview

Sprint runs currently **silently halt** (`SprintOutcome.HALTED` + `break`) on a 429 with no recovery. A 429 means ONE routed CLIProxyAPI account hit its 5h/7d rate-limit window — roughly seven other accounts in the pool remain usable. Because every sprint subprocess is launched with `--no-session-persistence`, a new subprocess is a new session is a new routing decision is a chance at a *different* account. The correct recovery is **RE-ROUTING** (spawn a fresh subprocess, or switch the model alias), **never waiting**.

This task implements the reflect-validated design in `.dev/brainstorms/sprint-429-recovery-spec.md` across `src/superclaude/cli/sprint/` in six sequential phases:

- **P1 — Detection (zero behavior change):** a `detect_provider_failure(output_path) -> ProviderFailureSignal` detector + a `_provider_failure_from_text(text)` text-core + a `ProviderFailure` enum + a `ProviderFailureSignal` dataclass in `monitor.py`, plus 6 stream-json fixtures. Pure additive — nothing consumes the detector yet.
- **P2 — Taxonomy + status:** a new `TaskStatus.FAIL_PROVIDER_EXHAUSTED` infra status (a *failure* so resume re-runs it, but flagged-infra so it never trips product-bug remediation), 3 new `TaskResult` fields with back-compat `.get()` serialization, and the `_classify_transcript` 429 alignment so the offline classifier and live detector agree. Resume paths and the planner are ZERO-EDIT (auto-covered by the enum value-lookup + shared detector).
- **P3 — Policy + executor (HIGH RISK live concurrency):** a new `recovery_policy.py` with `SessionResetPolicy.decide`, the per-task re-spawn loop wrapping the unlocked spawn in `_run_one_task`, a global latch threaded at BOTH K>1 and K=1 call sites, and persistence of `halt_reason`/`exhausted_model`/`session_resets`.
- **P4 — Single-session phase path:** a `PhaseStatus.PROVIDER_EXHAUSTED` status, the single-session re-spawn loop, and the diagnostic-bundle guard so a single-session exhaustion halt never writes a spurious `phase-N-diagnostic.md` product-bug bundle (UX contract #4 regression guard).
- **P5 — Alias suggester + halt UX + CLI flag:** a new `aienv.py` `suggest_alternate_model`, a `build_account_exhaustion_halt` single-line resume-UX builder, a `--max-session-resets` flag wired through the 4-hop chain, and a doc⇆CLI parity test.
- **P6 — Events + nominator exclusion + docs:** `execution-log.jsonl` `session_reset` / `account_exhaustion_halt` events, the `rerun-tasks` nominator exclusion of `failure_class=="provider_exhaustion"`, and a KNOWLEDGE.md entry.

**Critical invariants (from the spec, reflect-validated, gate-confirmed):** re-route never wait; `FAIL_PROVIDER_EXHAUSTED` is infra not product-bug; `PhaseStatus.PROVIDER_EXHAUSTED` goes in `is_terminal` NOT `is_failure` (to avoid the `executor.py:2103` diagnostic bundle); the detector keys on the LAST `{"type":"result"}` event's `is_error` + `api_error_status` (NEVER `subtype`, which is `"success"` even on a 429); the K>1 storm bound is `≤ cap+(K−1)` AND `< K×cap` (NOT strictly `≤ cap`); and SoT discipline (`src/superclaude/` is source of truth, never stage `.claude/`, `uv run ruff format --check` before push, PR `--repo IronbellyOrg/IronClaude`).

## Key Objectives

1. **Add a zero-behavior-change provider-failure detector** — `detect_provider_failure`, `_provider_failure_from_text`, `ProviderFailure`, `ProviderFailureSignal` in `monitor.py`, mirroring the `detect_error_max_turns` read/OSError-tolerance shape and the `_classify_transcript` last-result-event parse, with 6 stream-json fixtures authored verbatim from spec §2.

3. **Implement the SessionResetPolicy + bounded re-spawn loop with a global latch** — a pure `decide` truth table in `recovery_policy.py`, the per-task re-spawn loop in `_run_one_task` (spawn unlocked, latch checked/tripped locked), threaded at BOTH call sites, with `halt_reason`/`exhausted_model`/`session_resets` persisted.
4. **Handle the single-session phase path without spurious diagnostics** — a `PhaseStatus.PROVIDER_EXHAUSTED` status in `is_terminal` (not `is_failure`), the single-session re-spawn loop short-circuiting before `_determine_phase_status`, and the `executor.py:2103` bundle guard.

6. **Emit execution-log events, exclude exhausted tasks from rerun nomination, and document** — `session_reset` / `account_exhaustion_halt` `logging_.py` methods, the `rerun-tasks` nominator `failure_class` exclusion (OQ-2 decided: option a — filter in `select_default_recoverable_tasks`), and a KNOWLEDGE.md entry.

### Key Constraints

- **Re-route never wait** — every recovery action is a fresh subprocess spawn or a model-alias switch suggestion; no sleeps, no backoff-waits.
- **`FAIL_PROVIDER_EXHAUSTED` is infra, not product-bug** — it is a *failure* (in `TaskStatus.is_failure`, so resume re-runs it) but must NEVER trip the `DiagnosticCollector`/`FailureClassifier` product-bug bundle. `PhaseStatus.PROVIDER_EXHAUSTED` therefore goes in `is_terminal` (so the phase loop stops) but NOT in `is_failure` (so the single-session diagnostic-bundle path skips the bundle), per FINDING F-1 / G-1.
- **Detector keys on `is_error` + `api_error_status` of the LAST `{"type":"result"}` event** — NEVER on `subtype` (a 429's `subtype` is `"success"`). The `api_retry` event's field is `error_status` (different field — do not confuse).
- **K>1 storm bound is `≤ cap+(K−1)` AND `< K×cap`** — NOT strictly `≤ cap`; the spawn is unlocked so up to K−1 workers may be mid-spawn when the latch trips. Tests assert the realistic bound.
- **Back-compat serialization** — `TaskResult.from_dict` is hard-keyed today; the 3 new fields MUST use `.get(default)` (mirror `HandoffRecord.from_dict`) so old `phase-N-result.json` round-trips.
- **SoT + toolchain discipline** — edit `src/superclaude/` only; UV-only (`uv run pytest`, never `python -m`); `uv run ruff format --check src/ tests/` AND `make verify-sync` after each phase's edits; never stage `.claude/`; OQ-1/OQ-2 are operator-DECIDED (P5 aienv = os.environ reader option A; P6 nominator exclusion = filter in `select_default_recoverable_tasks` option a) — implement the decided option, document the rejected alternative for provenance, no human-decision PENDING (a genuine technical blocker is still logged as `[BLOCKER]`).
