## Goal

While `/sc:pr-submit` waits on CI (Wave 8), a PR that turns conflicting is detected from the CI poll and the Wave 8a conflict step runs once more, limited by the existing router (`SYNC_CAP = 1`, Tier 0 and Tier 1 only; a late Tier 2 conflict halts). The protocol text, user docs and tests must agree with the code.

## Requirements

The header comment must not contain the word "force" or the literal text `gh pr checks --repo`, and must not mention `gh pr` or `gh api`.
- R-002 `src/superclaude/pr_submit/conflicts.py` gains `late_conflict_trigger(payload, wait_sha=None) -> bool`, next to `mergeability_hint`. It is true only when `payload` is a dict, `payload["merge_state"]` is a dict and `mergeability_hint(mergeable, status)` is `"conflicting"`; it is false for a missing key, wrong types, `unknown`, `behind`, `blocked`, `clean`, and when `wait_sha` is given and `payload["head_sha"]` is a different non-empty string (a payload for another head is not evidence); a `head_sha` or `wait_sha` that is empty or not a string gives no mismatch information, as in `classify_checks` (`ci.py:154`). It never raises. It is re-exported in `src/superclaude/pr_submit/__init__.py` (import list and `__all__`). `conflicts.py` is in the core-pure file set: its source may not contain the standalone words `gh` or `git` anywhere, docstrings and comments included.
- R-003 `src/superclaude/pr_submit/ci.py` and `classify_checks` are not edited. A payload that carries `merge_state` classifies exactly like the same payload without it, for pending, all-pass, fail, empty with `expect_checks` true and false, and a stale head; `state: polling` with no checks stays `polling` even when `merge_state` is conflicting. These tests pass on today's code; they are regression guards and are verified by mutation (a scratch copy of `classify_checks` that reads `merge_state` makes them fail).
- R-004 `SKILL.md` Wave 8: on every poll payload, before acting on its classification, the SKILL evaluates `superclaude.pr_submit.conflicts.late_conflict_trigger(payload, wait_sha=<the wait SHA>)`. When it is true and the late pass has not been confirmed yet (R-006), the SKILL runs Wave 8a once more with the same entering outcome (`conflict_action(hook="wave8a", entering=<review outcome>)`). No new hook label, event, router row or run-log field is added.
- R-005 The late pass is limited only by `conflict_action`. Its outcomes hold at every ordinal where the code says so and are pinned today, case by case, by `_WAVE8A_ROWS` in `tests/pr_submit/test_conflicts_core.py` (lines 929 to 1044) and `test_router_wave8a_tier1_preserved_column` (line 1064), are:
  - Plan tier unknown (probe failed or merge-tree unsupported): the CI wait ends with reason `probe_failed` or `merge_tree_unsupported`.
  - Tier 0: when the late read of GitHub is not conflicting the action is `none` with reason `no_conflict` and the CI wait continues; when GitHub reads conflicting the CI wait ends with `github_disagrees`.
  - Tier 1 with `--conflict-max-tier 0`: `tier_above_cap`, at every ordinal. With a cap of at least 1 and a conflict cycle already started: `sync_cap`, at every ordinal. Otherwise: at L3 `resolve_push` (push kind `sync`) after every entering outcome; at L2 `resolve_local` (status `halt_before_push`) after `clean` or `report_only`, and only a report (`tier1_l2_preserved`) after `halt_max_rounds` or `no_response`; at L1 a proposal (status `proposed`) after `clean` or `report_only`, and only a report (`tier1_l1_preserved`) after a preserved outcome.
  - Tier 2: `tier_above_cap` with a cap below 2, `late_conflict` with a cap of 2. Tier 3: `conflict_tier3`.
  - Status of the outcomes that halt or report (probe failed, merge-tree unsupported, `github_disagrees`, `tier_above_cap`, `sync_cap`, `late_conflict`, `conflict_tier3`): `terminal_halted` when the entering outcome was `clean` or `report_only`; when it was `halt_max_rounds` or `no_response` the action is `report`, the status stays unchanged and the retained terminal status is kept. Two outcomes that also end the CI wait have their own status: a Tier 1 proposal at L1 has status `proposed` and a Tier 1 local resolution at L2 has status `halt_before_push`. `resolve_push` at L3 does not end the CI wait, and neither does Tier 0 `none` with reason `no_conflict`.
  After a pushed sync the CI wait continues on the new head with `expect_checks`. The late pass spends no round and sends no re-trigger, reply or resolve.
- R-006 Once-per-run rule: the SKILL keeps a run-local "late pass confirmed" flag. It is set only when the late `conflict_action` returns something other than `none`, so Wave 8a acted or ended the wait; it is not persisted (a `--resume` may run one more late pass; pushes stay bounded by `SYNC_CAP`). A payload reading that Wave 8a does not confirm (hint `clean`, `behind`, `blocked`, or a `none/no_conflict` result) leaves the flag unset, ends that late check with no action and lets the CI wait go on; the trigger may fire again on a later poll. A fired trigger counts as "a hook this run read `conflicting`" for the end-of-wait `mergeable` re-read, so that backstop still runs. Cost accepted: a payload that stays conflicting while Wave 8a keeps reading clean re-runs Wave 8a on each poll (one read and one probe), bounded by the CI timeout.
- R-007 Wording of the cap everywhere it is described (SKILL text, refs, user docs, changelog): the late pass is allowed only when no conflict cycle (Tier 1 sync or Tier 2 merge) started earlier in the run, because the cap counts the distinct cycle ids in `conflict_cycles` (`run_log.py:186-188`, `refs/state-machine.md:164-165`), landed or not.
- R-008 Wording of the preconditions everywhere the late sync is promised (SKILL text, `refs/state-machine.md`, user docs, changelog): it needs `--conflict-max-tier` of at least 1 at every monitor level (with the default cap of 0 every level ends with `tier_above_cap`); with a cap of at least 1, monitor 1 only proposes and monitor 2 only leaves a validated uncommitted merge, both only after a `clean` or `report_only` review (after `halt_max_rounds` or `no_response` they only report), and only monitor 3 pushes the sync. A late Tier 2 conflict halts (`late_conflict` with cap 2, `tier_above_cap` below it), a Tier 3 conflict halts (`conflict_tier3`), and a conflict after a cycle started halts (`sync_cap`); after a preserved review outcome these are reported and the retained terminal status stays.
