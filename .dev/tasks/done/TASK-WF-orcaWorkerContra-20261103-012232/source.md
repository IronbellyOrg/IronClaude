## 1. Decision: Orca coordinates, commands stay the units of work

### 1.1 The decision
An Orca coordinator plans the work, creates Tasks, starts one worker per Task and reads each worker's report. Each IronClaude `/sc:` command stays a self-contained unit of work: one worker (a top-level Claude session in its own Orca terminal) runs one command and reports it with `worker_done`. Commands themselves contain no Orca calls. What changes in the commands is limited to the worker contract in section 2: a way to run without a person, a fixed report file, and a resume or safe re-run.

### 1.3 Rejected alternative: commands call Orca internally
In the alternative, a command would itself start Orca workers for its fan-out (for example one worker per `/sc:tdd` research agent), send its own `worker_done`, and call `orca orchestration ask` for its questions. It is rejected for these reasons:

| # | Reason | Evidence |
|---|---|---|
| R1 | It cannot run as a worker at the current setting. Nesting depth is 1 on this machine and "1 means a coordinator dispatches workers and those workers may not dispatch further", so a command that calls `worker-start` from inside a worker would be refused with `nested_worker_depth_exceeded`. Which call sites enforce the check was not traced; `worker-start` and `dispatch` are presumed (UNVERIFIED, `CAPS:103`). A new Run does not reset depth, and Orca's own advice is "Do the work in this terminal". Raising the depth would not make this design viable: R2-R5 still apply, and depth cannot reach a command's Agent-tool fan-out (D5). | `CAPS:97-101,103`; `orca-data.json:1` quoted at `CAPS:98` |
| R2 | It breaks standalone use. Commands are installed to `~/.claude/` and run in other projects. Without a running Orca every orchestration call fails with `runtime_unavailable`; outside an Orca terminal the caller must pass `--from`; and a session with no live preamble must not send lifecycle messages at all. | `CLAUDE.md:74`; `CAPS:147` (`cli-error.js:49-53`); `CAPS:148-149` (`[G]` line 41; `terminal-identity.js:213-215`) |
| R3 | A command cannot own the completion message. `worker_done` is accepted only from the dispatched pane, and the Task and Dispatch IDs exist only in the preamble given to the worker session, not in the command's arguments. | `CAPS:76`, `CAPS:150` (`[H:send]` line 40); `CAPS:148` (`[G]` line 38) |
| R4 | The executable name differs by platform and setup (`orca-ide` on Linux outside Orca terminals, an `orca` shim inside them), so command text that calls Orca would carry platform logic. | `CAPS:145` (`/opt/Orca/resources/bin/orca-ide:16`; `linux-orca-cli-shim/orca:2`) |
| R5 | It would create a second orchestrator below the coordinator. The inventories already mark the commands that orchestrate (`/sc:agent`, `/sc:pm`, `/sc:spawn`) coordinator-only because two controllers compete. | `INV-A:90`; `INV-B:285-286` |

What the alternative would have given, and how this spec gets it instead: per-unit liveness, Task records and independent retry for heavy fan-out. Orca keeps those records only for workers the coordinator starts (`CAPS:158`). Under this decision the coordinator gets them by splitting the work into separate worker Tasks (for example several `/sc:troubleshoot` workers, then one `/sc:adversarial` worker on their reports), not by commands calling Orca. The merge step follows the fan-in rule in section 2.3: it is created only after every input Task has settled and its contract has been read, and it runs only on inputs that rule admits.

### 1.4 How strong the evidence is
The evidence supports the decision. Three gaps are stated plainly:
1. **No command in scope has been run end to end as an Orca worker in this run.** Every verdict in both inventories comes from reading files (`INV-B:323`). The only end-to-end proof is the PR #329 run, and its brief told workers to run `/sc:adversarial` through an Agent-tool subagent (`.dev/codegraph-migration/orchestration/README.md:31`), so it proves the nested route, not the direct route this spec requires. Whether every such spawn succeeded is UNVERIFIED (`CAPS:156`, `CAPS:187`). Phase 0 (section 6) therefore starts with live smoke runs.
2. **The 60-second readiness evidence is narrower than it looks.** It concerns a question shown *before* Claude reached its input box (`EVIDENCE.md:39`, a shell wrapper's session-name prompt). A command's own `AskUserQuestion` or chat question comes *after* readiness, so it does not fail `worker-start`; Orca reports such a worker as waiting, "healthy, not failed" (`CAPS:52`, `CAPS:129`). The real failure mode for a command prompt is a silent stall with no `worker_done`, which the coordinator sees only through `worker-show`'s `agentWait` or a missing report. Section 2 covers both cases.
3. **Agent-tool fan-out inside a worker has no proven limit, but no proof of none either.** No Orca limit on subagents was found, and whether a subagent's Bash `send` would be accepted as the worker's own is UNVERIFIED (`CAPS:155`, `CAPS:159-160`, `CAPS:186`). The contract forbids subagents from sending lifecycle messages, so the design does not depend on that answer.

## 2. The worker contract

### 2.1 Terms
- **Worker run**: a session that received an Orca preamble carrying a Task ID and a Dispatch ID. Only such a session may send lifecycle messages; a session the user started, inside or outside Orca, is an ordinary session (`CAPS:148`, `[G]` lines 38 and 41).
- **Unattended mode**: the behaviour a command switches to when its caller passes `--unattended`. It is the only command-side change the contract asks for besides report files and resume. It names no Orca command, so the same mode serves any caller that has no person at the keyboard. The mode is selected only by the flag (decision D1, section 9: option (c) as amended). No command detects Orca, its preamble or its environment. The worker session separately applies the brief guard (section 2.1, "Brief guard").
- **Flag parse rule**: `--unattended` counts only as a standalone argument token outside any quoted argument. The same text inside a quoted prompt or topic (for example `/sc:troubleshoot "the worker ignores --unattended"`) is part of that argument and never switches the mode, so a person's run cannot be changed by the words they type (SA-1).
- **Person-mode flags are refused**: under `--unattended`, every command refuses the flags that exist to involve a person: `--interactive`, `--format interactive` (explain), `--mode socratic` (business-panel), `--watch` (test), `--monitor 1` (pr-submit). A refusal is a stop before any work: the command writes its contract with `worker_status: failed` and the refused flag in `reason` (WC-4), or, when no report directory is known, prints the refusal in chat only (WC-4, last sentence). This one rule applies to every command; section 3 rows repeat it only where the flag is the row's main gate.
- **Report directory**: the directory that holds the worker contract (WC-4). Under `--unattended` the brief passes exactly one: either the command's own existing directory-valued output flag (`--output <dir>` or `--output-dir <dir>`), or the new flag `--report-dir <dir>` (for a command without such a flag, or a brief that does not pass it). An output flag a section 3 row adds is file-valued, so those commands always take `--report-dir`. Passing neither, or both, is refused before any work (WC-4, last sentences).
- **Contract file**: one shared document, proposed as `src/superclaude/core/WORKER-CONTRACT.md`, installed to `~/.claude/WORKER-CONTRACT.md`. Core `.md` files install to `~/.claude/`: the installer copies every `*.md` in `core/` (`src/superclaude/cli/install_core.py:36,56,65-70`; `CLAUDE.md:83,408`). The new name is also added to `KNOWN_CORE_FILES` (`src/superclaude/cli/install_core.py:13-27`), which only controls which installed files `list_installed_core_files` reports (`install_core.py:12,155`); installation itself is checked by AC-0.1. The file holds the command-side rules (WC-2, WC-4, WC-8 to WC-11, the flag parse rule, the person-mode refusal above and the nested propagation rule below), the worker session's brief guard and the never-as-worker list below, and the coordinator's rules (WC-6 and section 2.3, including its brief template and the template's guard line). For the worker-session duties (WC-3, WC-5, WC-7, WC-12, WC-13 and heartbeats) it states only the IronClaude-specific rule (outcome mapping from `worker_status`, including WC-5's P0 brief override, top-level only, ask only when the brief allows it) and points to the dispatch preamble as the authority for Orca verb syntax and heartbeat cadence; it never copies them, because the preamble is issued per dispatch by the running Orca version (`CAPS:130`). Each changed command adds a short `## Unattended mode` section that lists only its own gate resolutions and report file and points to the installed contract path, so the shared rules are written once.
- **Brief guard** (worker session, from P1): it applies only in a session whose current prompt carries a live Orca preamble with Task and Dispatch IDs (see "Worker run"). Before invoking anything, the worker checks every `Command:` line of its brief (section 2.3, "Brief layout"), and only those lines. It decides case 3 from the command name alone. For the other cases it reads, as plain files, every existing copy of the command file: the project `.claude/commands/sc/<name>.md` in its worktree and `~/.claude/commands/sc/<name>.md`. It refuses, runs nothing, writes no contract, and sends `worker_done --outcome failed` with no `--report-path` and a body starting `guard refused:` when: (case 1) every existing copy has an `## Unattended mode` section and the line lacks a standalone `--unattended` (`guard refused: brief lacks --unattended`); (case 2) no existing copy has the section and the line has the flag (`guard refused: loaded command has no Unattended mode section (not converted at this phase, or the loaded copy is stale)`); the copies disagree (`guard refused: command copies disagree (stale copy): <paths>`); (case 3) the command is on the never-as-worker list. A command invoked by another command, through the Skill tool or the Agent tool, is never checked; the nested propagation rule governs it. The guard checks once, before the first run: a WC-3 re-invocation keeps every token of the brief's `Command:` line, `--unattended` included, and only adds the answer.
- **Never-as-worker list**: `/sc:agent`, `/sc:git`, `/sc:help`, `/sc:pm`, `/sc:spawn` and `/sc:swarm-wizard` (section 4), plus `/sc:pr-submit` while the answer to D3 keeps it off workers. The list changes only when section 4 or D3 changes, never per phase. If D3 adds a worker route for pr-submit, D3 also states how that route passes the brief guard.
- **Nested propagation rule**: under `--unattended`, a command that invokes another `/sc:` command or protocol skill, through the Skill tool or the Agent tool, passes `--unattended` when the invoked command accepts it at this phase, together with its own report directory `<caller report-dir>/nested/<command>-<n>/` (WC-4, WC-11). The caller lists the nested contract in its `artifacts`; only the top-level contract drives WC-5. When the invoked command does not accept the flag yet, that step must be gate-free per its section 3 row, or the caller skips it under `--unattended` and records the skip in its contract. Each command's `## Unattended mode` section names its nested invocations.

### 2.3 What the coordinator owes each worker
The contract only works if the brief carries what the command would otherwise ask a person. For each Task the coordinator's brief states: the exact command line, including `--unattended` where the command accepts it at this phase, and every flag section 3 lists as required, written as a `Command:` line in the layout below; the report directory, unique to this Task, so the contract path is known before dispatch (WC-4, WC-11); the blocked-gate policy line, `On a blocked gate: report blocked` or `On a blocked gate: ask the coordinator` (WC-3); whether the end-of-Task local commit is authorized, quoting the user's instruction word for word (D4); at P0 only, the command's report file and the outcome rule AC-0.4 gives for it (WC-5); no other outward action can be authorized; and the worktree placement: the shared feature worktree, or a child worktree created by Orca with `worker-start --worktree new-child --base-branch <feature branch>` when WC-11 requires one (`CAPS:115`). After `worker_done`, the coordinator opens the contract, then releases or reuses the worker (`CAPS:107-113`).

**Brief layout.** The brief puts the preamble-facing instructions and the guard line before the commands, and gives each command its own labelled `Command:` line in run order (for example `Command: /sc:load ...`, then the converted command), so the Task text never starts with `/sc:`. Guard line: `Guard: before running anything, check every Command: line below under the brief guard in ~/.claude/WORKER-CONTRACT.md; on a refusal run nothing and send worker_done --outcome failed with a body starting "guard refused:".` The coordinator decides whether a `Command:` line carries `--unattended` by the guard's own test, run on the copies the worker will see (the target worktree's project `.claude/commands/sc/` copy and `~/.claude/commands/sc/`), not on its own copy. A WC-3 re-invocation keeps every token of the `Command:` line and only adds the answer.

**Feature worktree and child worktrees.** Every worktree is created by Orca at Orca's default location, never with raw `git worktree add` and never under `.dev/worktrees/`. Each feature has one feature worktree on its feature branch, where the coordinator runs. A child is dispatched only after its setup has succeeded (`--setup run`); if that setup does not run `make sync-dev` (UNVERIFIED item 27), the coordinator runs it before dispatch. The coordinator keeps a placement map (which Task writes in which worktree, and whether it is the sole writer) in its run notes and in each `worker-start --comment`. A Task placed in a child gets an absolute report directory inside that child, which the coordinator reads by absolute path before merge-back; concurrent `/sc:implement` runs in different worktrees use distinct plan slugs. A resume runs in its existing child, selected with `--worktree id:<worktree id>`. After a child's result is admitted, the coordinator merges the child branch into the feature branch, then removes the child with `orca worktree rm` and deletes its branch; a discarded experiment is removed without merging; a merge conflict is stopped and reported, never resolved automatically. It never removes a worktree or branch that holds unmerged commits, an open PR, uncommitted changes, an unfinished `/sc:implement` ledger, or a report it has not read, without the user's instruction. It never runs one managed package in two worktrees at once.

**Git and GitHub ownership.** The coordinator performs every git and GitHub outward action, and every install, VM or paid run, in its own conversation, only when the user's instruction names that action, and confirms with the person at the moment of action unless that instruction is in its live conversation (`sk/sc-post-release-protocol/SKILL.md:351`). Every such action targets `IronbellyOrg/IronClaude`: never the SuperClaude upstream, and never through Orca's issue or PR linking while Orca records the project as the upstream. Progress posts (issue comments, project fields) are such actions, made from contracts the coordinator has read; workers report progress only through heartbeats and `worker_done` (WC-5, WC-10). PRs go only through `/sc:pr-submit --monitor 3` (`CLAUDE.md:50`), run as section 4 states. Before any push that would publish worker commits the person has not seen, the coordinator shows them to the person and pushes only on the person's go; no earlier pre-authorization waives this. A commit grant covers one Task and ends at that Task's `worker_done`. The coordinator commits or merges in a worktree only when no worker runs there and no `/sc:implement` Task there is frozen (below): it compares `git status --porcelain` with the settled contracts and reports unlisted paths, stages explicit paths plus `.dev/tasks` at every commit and again at the end of the run, which satisfies the repo's always-staged rule for worker sessions (`CLAUDE.md:37`), commits with `git commit --only -- <paths>`, treats "nothing to commit" as success, and stops and reports on any hook rewrite, hook failure or conflict, never `--no-verify` (`src/superclaude/core/HOW-WE-WORK.md:280`). The plan or brief records who owns each PR.

**Reading a result before anything depends on it.** Orca settles a Task on any valid `worker_done` (`CAPS:77`) and does not start ready Tasks itself (`CAPS:92`), so the coordinator decides what runs next:
- `succeeded`: dependents may start.
- `partial`: dependents do not start until the coordinator has read the contract's `report_path` and recorded, in its own run notes, whether the partial deliverable is usable; an unusable one is handled like `failed`.
- `failed` or `blocked`: dependents do not start; the coordinator retries per WC-6, answers per the example below, or reports the failure to the person. Exception: an `/sc:implement` Task follows "After an `/sc:implement` stop" below, because a WC-6 retry of a Ruling-halted plan would start an operator review by automation (`sk/sc-implement-protocol/refs/ledger.md:155-156`), which `refs/qa.md:283` forbids.
- No contract, and a `worker_done --outcome failed` body that starts `guard refused:`: a brief-guard refusal; nothing ran. The coordinator fixes the brief in a new Task (WC-6), never re-creates it unchanged, and allows at most 2 brief fixes for the same work (3 attempts); a third refusal escalates to the person.
- Every dependent Task is created only after all its inputs have settled and been admitted under the bullets above, with `--deps` naming the Tasks that actually succeeded (an original Task or its replacement). No dependent is created up front on an unsettled input, because every retry is a new Task (WC-6), a dependent created on the old Task stays blocked (`CAPS:90`), and Orca offers no way to re-point it (`task-update` changes only `--status` and `--result`, `task-update --help` line 3).
- The coordinator starts only Tasks it created itself. A ready Task it did not create is not started; it is reported to the person with its spec text. In its run notes the coordinator also records each follow-up Task it created because a worker's result showed work that could not be planned before dispatch, with the extra time that cost. This is the evidence D5's revisit trigger reads (section 9).

**After an `/sc:implement` stop (D2).**
1. *Freeze.* A plan is frozen when its latest implement contract is `blocked`, or `failed` with any STOP code other than `E-RESUME-NEEDED`. It is also frozen when the ledger's first non-complete task has `halt` or `blocked` as its last record with no eligible Ruling after it. While a plan is frozen:
   - The coordinator shows the person the contract and the full halt text, and dispatches no Task for that plan.
   - No Task that writes outside its own report directory is dispatched into the halted worktree.
   - No one runs a git command there that changes HEAD, the index or the working tree. The halted worktree is not merged or removed.

   `E-RESUME-NEEDED` alone may be re-run by the coordinator without the person, as the same command in the same worktree, and only when the ledger shows no freeze.
2. *Lifting the freeze.* The freeze lifts only when the person's explicit hand-back is recorded in the coordinator's run notes **and** the ledger shows the matching state:
   - "Ruling written" requires the check in item 3 to pass.
   - "session ended" (after (a)) requires the halted task to be `complete` and the ledger's last line to parse. The drift baseline is then re-recorded.

   After a stop with no halted task (for example `E-ARCHIVE-BLOCKED`), only the person's recorded instruction lifts it. After the hand-back the person makes no further edit in that worktree until the resume Task settles.
3. *Check before a resume Task under (c).* The coordinator reads the ledger and the worktree, never edits either, and dispatches only if all of the following hold. On any failure it tells the person which condition failed and sends them to (a).
   - (1) The worker has settled (WC-6).
   - (2) After the later of the halted task's latest `halt` and latest `blocked` record, the only new lines are one Ruling line per halted task named in the contract. Each line has that task's id, ends in `\n` with no `\r`, and matches `ledger.md:71`.
   - (3) No field is blank, whitespace-only, punctuation-only or an angle-bracket placeholder, and the line has exactly two ` — ` separators.
   - (4) The line is eligible under either clause of `refs/retry.md:498`.
   - (5) No `halt` after the task's latest `start` has `reason=dispute`; and the latest `halt` reason is not `no-evidence`, `no-snapshot` or `head-moved`.
   - (6) `HEAD` equals `<retries>/T<id>/q0-head`, and the paths in the `files=` field of the latest `blocked` line are unchanged against the tree its review graded. A missing `q0-head` or graded tree fails this condition.
   - (7) The resume brief has no `--force`.
4. *Placement.* The resume Task starts in the halted worktree by selector (`worker-start --worktree path:<absolute worktree path>`), never in a new or child worktree. Under (a) the person runs from that same worktree with the same absolute plan path.

**Fan-in rule (several workers, then one merge).** For N input Tasks feeding one merge Task (for example N `/sc:troubleshoot` workers, then `/sc:adversarial --compare`): wait until all N have settled. Admit an input only if its `worker_status` is `succeeded`, or `partial` judged usable as above. Each `blocked` input is answered and re-run as a new Task (WC-6) before the merge, or dropped with the reason recorded; each `failed` input is retried or dropped the same way. The coordinator plans N no larger than the merge command's maximum of 10 inputs (`cmd/adversarial.md:15`); a re-run replaces its input rather than adding one, so the admitted count never exceeds 10. Create the merge Task only when at least 2 inputs are admitted, and list every dropped input and its reason in its brief. With fewer than 2 there is no merge: the coordinator reports the single admitted result, or the failure, to the person.

## 8. Non-goals
1. **Commands calling Orca.** No command, skill or agent gains an Orca call, a `worker_done`, or Orca-specific branching (section 1.3, SA-2).
2. **Changing Orca or its settings.** Nesting depth stays 1 unless the user decides otherwise, and the coordinator is a session the person opened, never one started by `worker-start` (D5); no change to Orca's readiness limit, guides or code (`CAPS:98`).
3. **Building a coordinator program.** The coordinator is an Orca coordinator session following Orca's own guide (`CAPS:12-13`); this spec adds a brief template, not a new CLI, daemon or scheduler.
4. **Turning coordinator-only commands into workers** (section 4).
5. **Removing or weakening any interactive behaviour for people** (section 5). `--unattended` is opt-in.
6. **Changing the `/sc:implement` Ruling rule** unless the user chooses D2 option (b) (`sk/sc-implement-protocol/refs/qa.md:254`).
7. **Making Agent-tool subagents into Orca workers**, or letting subagents send lifecycle messages (WC-7).
8. **Fixing every defect the inventories list.** Only defects that stop a command working as a worker are in scope. Others stay recorded in the inventories, for example `/sc:agent`'s missing opening frontmatter line (`INV-A:36`) and the cleanup/improve rollback claims (`INV-A:118`).
9. **Remote workers, model and effort choice, and cost tuning.** `--on <environment>`, `--model` and `--effort` are coordinator choices Orca already supports (`CAPS:128`, `CAPS:135-139`); this spec does not set them.
10. **Implementing anything in this run.** This is a planning spec (`.dev/orca-command-refactor/README.md:6,30`).
