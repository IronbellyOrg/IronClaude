# Implementation workflow: multi-repo ruleset rollout tool (issue 838)

Source: ./source.md
Goal: Add `scripts/org_rulesets.py` with the subcommands `plan`, `apply` and `verify`, its offline tests and its operator page, so the owner can roll the three IronClaude rulesets out to the 17 allowlisted IronbellyGroup repos one repo at a time. No step of this work makes a live call to GitHub. This plan replaces a first plan that failed its review; the Revision 1 section at the end of `./source.md` lists what it fixes, and the task numbers there refer to that first plan.

## Constraints

- No task calls GitHub or touches any IronbellyGroup repo. Every GitHub call in a test goes through the `FakeRunner` of `tests/org_rulesets/conftest.py`; no test starts the real `gh`.
- `.github/rulesets/*.json`, the commands in `docs/developer-guide/branch-protection.md` and `tests/docs/test_branch_protection_rulesets.py` stay unchanged. The only edit to the guide is the one link line of Task 18. The existing test must keep passing.
- Python 3.10, standard library only; ruff rules `E,F,I,N,W,TID` at line length 88 as set in `pyproject.toml`.
- No real private repo name and no real org login is written in any tracked file. Tests use synthetic names such as `acme-one` and `acme-two`. The script holds no org or repo name, except the upstream org name it refuses.
- Only these paths may change: `scripts/org_rulesets.py`, `tests/org_rulesets/`, `docs/developer-guide/branch-protection-multi-repo.md`, `docs/developer-guide/branch-protection.md` (one link line) and `docs/developer-guide/documentation-index.md`. Nothing under `.claude/` or `.github/` changes.
- References such as "source.md section 6.3" name headings of `./source.md`; "R1-B3" names an item of its Revision 1 section.
- Test setup follows `tests/worktree_cleanup/conftest.py` (the fixture `wc` at lines 26 to 37 loads the script once for the whole session, and `RecordingRunner` at lines 68 to 88 subclasses the real `Runner` and overrides only `_execute`). `tests/org_rulesets/conftest.py` defines the session fixture `orr` (the script module) and every shared fixture exactly once. A test module never imports a fixture from another module, because CI lists fixtures with `pytest --fixtures` and a duplicate crashes it.
- Every location comes from one rule: the repo root is `Path(__file__).resolve().parent.parent` (the folder above `scripts/`), the rule files are read from `<root>/.github/rulesets/`, git runs with that root as its working folder, and the files `<repo>-before.json` and `<repo>-owner.json` live in the same folder as the `--targets` file. No function reads the current working folder.
- Where `./source.md` contradicts itself this plan takes the side listed in its Revision 1 section: `apply` with two repos exits `EXIT_USAGE` (64), and the gate G7 does not require a settled tag rule (an unsettled rule plans branch rulesets only). Both choices, and the one status transition this plan adds (`applied` or `verified` back to `checked` for a tag-only follow-up) and the fields it adds to the targets file (`allowlist`, `planned_set` with its third value `tags-only`, `branch_only_reason`, `hooks_keys`, `reset_by`, `reset_reason`, `org_facts.installations`) and to the owner file (`branch_only_interim`), are proposals for the owner's review. That review happens on the pull request, which refers to issue 838 and does not close it, because the live rollout is the owner's later work.
- Every task ends with the same two checks: `uv run pytest tests/org_rulesets/` passes (plus `tests/docs/test_branch_protection_rulesets.py` from Task 16 on) and `uv run ruff check scripts/org_rulesets.py tests/org_rulesets` reports nothing.

## Task 1: Create the script with render, branch_set, plan_set and payload_digest

Create `scripts/org_rulesets.py` with a module docstring, the constants `EXIT_OK = 0`, `EXIT_USAGE = 64`, `EXIT_FAILED = 69` (the values at `scripts/worktree_cleanup.py` lines 96 to 98), `ROOT` and `RULES_DIR` (location rule of the Constraints), the closed profile table (`branch`, `tags-full`, `tags-no-update`), and four pure functions, as in source.md sections 6.3 and 9 (rows FR-1 to FR-4). `render(profile, branch=None)` loads `protect-master.json` from `RULES_DIR` for the `branch` profile and sets `name` to `protect-<branch>` and `conditions.ref_name.include` to `["refs/heads/<branch>"]` and changes nothing else; `tags-full` returns `protect-release-tags.json` unchanged; `tags-no-update` returns it without the `update` rule. `branch_set(facts)` returns the default branch plus `master` and `integration` where they exist, without duplicates, and records `integration: absent` when it is missing. `plan_set(branches, tag_profile)` returns the rendered bodies of one repo in the FR-9 order (the tag ruleset, then `integration`, then `master`, then any other default branch); a `tag_profile` of `None` leaves the tag ruleset out (the branch-only set of R1-B9), and `tags_only=True` returns only the tag body (the follow-up of R1-B9 once the tag rule is settled). `payload_digest(rendered)` is the sha256 of the canonical JSON (sorted keys, fixed separators) of the bodies in that order.

Create `tests/org_rulesets/__init__.py`, `tests/org_rulesets/conftest.py` with the session fixture `orr` (loads the script with `importlib.util.spec_from_file_location("org_rulesets", ROOT / "scripts" / "org_rulesets.py")`, registered in `sys.modules`, the way `tests/worktree_cleanup/conftest.py` does), and `tests/org_rulesets/test_render.py`.

Acceptance criteria:
- `render("branch", "master")` and `render("branch", "integration")` equal the parsed `protect-master.json` and `protect-integration.json`.
- `render("tags-full")` equals the parsed `protect-release-tags.json`; `render("tags-no-update")` has rule types exactly `deletion` and `non_fast_forward`.
- An unknown profile raises an error; a branch name that is empty, contains `*` or `~`, or starts with `refs/` raises an error; no rendered body for any profile contains the text `~DEFAULT_BRANCH`.
- `branch_set` returns the expected set for three cases: default `master` only; default `main` with no `integration`; default `integration` with `master` present. The second case records `integration: absent`.
- `plan_set` returns the tag body first for a full set and no tag body for `tag_profile=None`; its order is tag, `integration`, `master`, other default branch; `tags_only=True` returns exactly one body, the tag body.
- `payload_digest` returns the same value for equal input and a different value when any body changes or the order changes.
- With the working folder changed to an empty temporary folder, `render` and `plan_set` return the same bodies (the location rule).
- `uv run pytest tests/org_rulesets/` passes and `uv run ruff check scripts/org_rulesets.py tests/org_rulesets` reports nothing.

## Task 9: Add the tag check

Depends on: Task 6, Task 8

It returns a record `{result, checked_at, evidence}` where `result` is one of: `tags-full` (clean scan and the owner evidence holds a `tag_statement`); `tags-no-update` (a moving-pattern hit, or a statement that tags move, and `tag_exception` is present); `deletes-tags` (any deletion-pattern hit, whatever `tag_exception` says, because `tags-no-update` keeps the `deletion` rule and would block that repo's own operation); `branch-only-interim` (a deletion hit and the owner evidence holds `branch_only_interim`); `unresolved` (a hit or statement without the needed exception, or no `tag_statement`); `incomplete` (a truncated listing or an unreadable file). An empty tag list proves nothing.

Extend `tests/org_rulesets/test_checks.py`.

- A clean scan with a `tag_statement` gives `tags-full`, including for a repo with no `v*` tags; the same repo without a `tag_statement` gives `unresolved`.
- A workflow containing `git tag -f` gives `tags-no-update` with a `tag_exception` and `unresolved` without it.
- A workflow containing `gh release delete` gives `deletes-tags` with a `tag_exception` and also without one; with `branch_only_interim` in the owner evidence it gives `branch-only-interim`.
- A truncated tag listing or an unreadable file (403) gives `incomplete`.
- The returned record carries `checked_at` equal to the `now` passed in.
