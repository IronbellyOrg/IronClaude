# Implementation workflow: multi-repo ruleset rollout tool (issue 838)

Source: ./source.md
Goal: Add `scripts/org_rulesets.py` with the subcommands `plan`, `apply` and `verify`, its offline tests and its operator page, so the owner can roll the three IronClaude rulesets out to the 17 allowlisted IronbellyGroup repos one repo at a time. No step of this work makes a live call to GitHub.

## Constraints

- No task calls GitHub or touches any IronbellyGroup repo. Every GitHub call in a test goes through the fake runner of `tests/org_rulesets/conftest.py`; no test starts the real `gh`.
- `.github/rulesets/*.json`, the commands in `docs/developer-guide/branch-protection.md` and `tests/docs/test_branch_protection_rulesets.py` stay unchanged. The only edit to the guide is the one link line of Task 17. The existing test must keep passing.
- Python 3.10, standard library only; ruff rules `E,F,I,N,W,TID` at line length 88 as set in `pyproject.toml`.
- No real private repo name and no real org login is written in any tracked file. Tests use synthetic names such as `acme-one` and `acme-two`. The script holds no org or repo name, except the upstream org name it refuses.
- Only these paths may change: `scripts/org_rulesets.py`, `tests/org_rulesets/`, `docs/developer-guide/branch-protection-multi-repo.md`, `docs/developer-guide/branch-protection.md` (one link line) and `docs/developer-guide/documentation-index.md`. Nothing under `.claude/` or `.github/` changes.
- References such as "source.md section 6.3" name headings of `./source.md`. Test files are loaded the way `tests/merged_pr_log/test_merged_pr_log.py` loads its script: `importlib.util.spec_from_file_location("org_rulesets", ROOT / "scripts" / "org_rulesets.py")`, registered in `sys.modules`.

## Phase 1: Pure rendering and comparison

## Task 1: Create the script with render, branch_set and payload_digest

Create `scripts/org_rulesets.py` with a module docstring, the constants `EXIT_OK = 0`, `EXIT_USAGE = 64`, `EXIT_FAILED = 69` (the values used by `scripts/worktree_cleanup.py`), the closed profile table (`branch`, `tags-full`, `tags-no-update`), and three pure functions, as in source.md sections 6.3 and 9 (rows FR-1 to FR-4). `render(profile, branch=None)` loads `.github/rulesets/protect-master.json` for the `branch` profile and sets `name` to `protect-<branch>` and `conditions.ref_name.include` to `["refs/heads/<branch>"]` and changes nothing else; `tags-full` returns `.github/rulesets/protect-release-tags.json` unchanged; `tags-no-update` returns it without the `update` rule. `branch_set(facts)` returns the default branch plus `master` and `integration` where they exist, without duplicates, and records `integration: absent` when it is missing. `payload_digest(rendered)` is the sha256 of the canonical JSON (sorted keys, fixed separators) of all rendered bodies of one repo in apply order.

Create `tests/org_rulesets/__init__.py` and `tests/org_rulesets/test_render.py`.

Acceptance criteria:
- `render("branch", "master")` and `render("branch", "integration")` equal the parsed `protect-master.json` and `protect-integration.json`.
- `render("tags-full")` equals the parsed `protect-release-tags.json`; `render("tags-no-update")` has rule types exactly `deletion` and `non_fast_forward`.
- An unknown profile raises an error; a branch name that is empty, contains `*` or `~`, or starts with `refs/` raises an error; no rendered body for any profile contains the text `~DEFAULT_BRANCH`.
- `branch_set` returns the expected set for three cases: default `master` only; default `main` with no `integration`; default `integration` with `master` present. The second case records `integration: absent`.
- `payload_digest` returns the same value for equal input and a different value when any body changes or the order changes.
- `uv run pytest tests/org_rulesets/test_render.py` passes and `uv run ruff check scripts/org_rulesets.py tests/org_rulesets` reports nothing.

Acceptance criteria:

- Rule order and bypass-actor order do not matter.
- `uv run pytest tests/org_rulesets/test_verify.py` passes.

## Task 8: Add the 90-day push check

Depends on: Task 3, Task 4, Task 6

Add `check_push(runner, org, repo, branches, owner_evidence, now)` to `scripts/org_rulesets.py` as in source.md section 8.1 (decision Decision 4 of the requirements). It computes one UTC cutoff of now minus 90 days and records it; reads the primary source `activity?ref=refs/heads/<b>&time_period=quarter` with pagination, counting `push`, `force_push` and `branch_deletion` as direct pushes and ignoring `pr_merge`; falls back to `commits?sha=<b>&since=<cutoff>` plus `commits/<sha>/pulls` per commit, where a commit with no merged pull request is a direct push; filters both sources by timestamp against the cutoff; and scans `.github/workflows` for `git push`. More than 500 pull-request lookups (named constant, decision DD-8) gives `incomplete`. Result `blocked` for any bot or workflow push; `incomplete` for unavailable history, truncated pagination or an unclassifiable commit; `pass` for zero direct pushes, or for named human pushes only when the owner evidence holds those names in `accepted_pushers` and a `push_statement`. `incomplete` is never turned into `pass`. The returned record holds `result`, `cutoff`, `source`, `checked_at` and `evidence`.

Create `tests/org_rulesets/test_checks.py` with the cases below.

Acceptance criteria:
- Zero direct pushes gives `pass`; a bot push and a workflow `git push` give `blocked`.
- A 403 on both sources, a truncated page chain and a commit whose pull-request lookup fails each give `incomplete`; 501 lookups gives `incomplete`.
- A named human push without owner evidence gives `incomplete`, and with `accepted_pushers` plus `push_statement` gives `pass`.
- Events older than the recorded cutoff are ignored by both sources.
- `uv run pytest tests/org_rulesets/test_checks.py` passes.

Depends on: Task 5, Task 7, Task 8, Task 9

## Task 12: Add apply_repo

Depends on: Task 2, Task 10, Task 11

Add `apply_repo(...)` to `scripts/org_rulesets.py` as in source.md section 7.2 steps 1 to 5 (requirements FR-7 to FR-9, S-6, decision DD-4). Preconditions, each refusing with the failed gate named: status is `checked`; the facts, both checks and the org read are under 24 hours old; the recomputed payload digest equals the planned one; `--confirm` equals that digest; no repo is `applied` but not `verified` and none is `partial` (G6); the applier and admin permission are valid (G8). On success of the preconditions record `approved_by` and `approved_at`, take the snapshot, then for each ruleset in FR-9 order (tags, `integration`, `master`, any other default branch): write the intent entry (action, name, digest, snapshot path), POST or PUT, add the returned id beside the intent, read the ruleset back by id, compare with `compare_bodies`, and store the last verified body. A same-name ruleset is managed only when its id is already in `ruleset_ids`; an unrecorded same-name ruleset, several candidates, inherited or org-level rulesets go to review and get no PUT. A timed-out POST is followed by a new list and a matching same-name ruleset is adopted; a POST is never repeated blindly. Before any PUT read the ruleset by id and compare it with the stored verified body, and stop on a difference. A non-success response stops the repo with status `partial`; a 403 after Step 0 passed stops the whole run. Success sets `applied`.

Extend `tests/org_rulesets/test_apply.py`.

Acceptance criteria:
- The recorded call order is tag ruleset, then `integration`, then `master`, and each is read back before the next write.
- `apply` with a repo not in `checked`, with stale facts, with a digest mismatch or with a wrong `--confirm` makes no write call and names the failed gate.
- A timed-out POST is followed by a list call before any other call and never by a second POST; an unrecorded same-name ruleset gets no PUT; a changed baseline stops a PUT.
- A failure after the first write leaves status `partial` with the written id recorded; a repeat run with nothing changed makes zero write calls.
- `uv run pytest tests/org_rulesets/test_apply.py` passes.
