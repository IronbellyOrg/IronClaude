## 2. Why (the corrected reasons)

1. The spec's original question and option (b) "describe the wrong thing" (D5/REC:8). No depth setting lets commands call Orca: R2-R4 (standalone use, ownership of `worker_done`, executable name) and R5 (second orchestrator) still apply (SPEC:37-41), and Orca's refusal fires at whatever maximum is set. Depth cannot reach a command's Agent-tool fan-out (D5/REC:46). So no setting revives rejected design 1.3.
2. Option (a) has a precondition the spec never stated before D5: the coordinator must be a depth-0 session the person opened. A coordinator started by `worker-start` is depth 1 and, at max 1, its own `worker-start` calls would be refused; a new Run does not reset depth (D5/REC:9,47). User-facing form: do not ask another Orca agent to start the coordinator (D5/REC:25).
3. The debate's headline reason ("depth 1 is a mechanical backstop") was not demonstrated: which Orca calls check depth had never been traced, and the worker's own session was bound by no contract rule (D5/REC:10). Fix: WC-13 (worker session never starts Orca work), a coordinator rule (starts only Tasks it created, SPEC:98), and three checks (AC-C6, AC-0.7, step-5 transcript scan) (D5/REC:10,52-61).
4. Machine-wide blast radius: the setting is per Orca profile, so a raise applies to every run on the machine, while a brief line restrains only IronClaude workers (D5/REC:48; option-a.md:9; option-b.md:13).
5. Strongest argument that lost (D5/REC:20): a worker that learns mid-run that its job should split could, under a raise to exactly 2 scoped by `Sub-workers: allowed, max N`, start sub-workers as Orca-tracked workers with their own records, liveness and retry. It lost because (i) a worker's brief carries one exact command line, so there is nothing for a worker to split (D5/REC cites SPEC:79; in the current spec the brief layout is at SPEC:86 and SPEC:79 is WC-11, so that citation has drifted; the claim itself holds, SPEC:84-86); (ii) the saving is one coordinator round trip; (iii) the cost is a second orchestrator sharing the coordinator's inbox plus a looser limit for every Orca run on the machine.

## 3. Options considered and their stated costs

### Option (a): keep depth 1 (recommended, approved), option-a.md:1-19
- Fan-out stays inside a command (Agent-tool subagents) or is split into separate Tasks by the coordinator (option-a.md:3).
- Safety: depth 1 is Orca's default and its fence against runaway fan-out; a malformed setting falls back to 1; a new Run does not reset depth (option-a.md:8, citing CAPS:97,100-101). Orca's advice at the limit: "Do the work in this terminal" (CAPS:99).
- Reliability: nothing in the spec needs depth 2; commands never call Orca (WC-8, SA-2); Agent-tool subagents are not counted by the fence (CAPS:155) (option-a.md:12).
- Day to day: no change; the coordinator plans fan-out as Tasks, e.g. N troubleshoot workers then one adversarial merge (option-a.md:16).
- Implementation cost: "Zero" (option-a.md:19) for commands; D5/REC:39 lists what it adds to the spec (one worker rule, one coordinator rule, a Phase 0 trace, a per-phase depth check, one live-check item, a wider file scan, wording fixes).
- Costs of (a) as stated in the approved text (D5/REC:47): gives up Orca Task/liveness/retry records for fan-out that stays inside one command run (WC-10's heartbeat gap stays accepted under either option), and one extra coordinator round trip when a worker's result shows work not plannable before dispatch.
- User-visible (D5/REC:26-27): a worker that finds its job should split says so in its completion message and the coordinator starts the extra workers; "one extra round of waiting"; a long single-command job (deep troubleshoot) shows as one worker with quiet stretches.
- Risks (D5/REC:32-34): Orca's refusal may not cover every route by which a worker could start another agent (traced later, section 7); the setting is shared across projects; a wrongly started coordinator has every worker start refused (likely) or, if the refusal is not enforced, workers run a level deeper silently.

### Option (b): raise depth (rejected). Two versions on record
- Original option-b.md:1-22 ("raise so a command running as a worker could start its own Orca workers"). Upside: per-unit Task/Dispatch records for heavy fan-out such as troubleshoot Tier 2 "+4-15 min" and the WC-10 gap (option-b.md:8); Orca's provenance rule "Never substitute a non-Orca subagent tool when Orca orchestration provenance was requested" (CAPS:158, option-b.md:9); one setting (CAPS:99, option-b.md:10). Costs: removes the runaway-fan-out fence and applies machine-wide (option-b.md:13); depth alone does not fix R2-R4 (option-b.md:16); more workers, Tasks and terminals to release (option-b.md:19); needs commands rewritten to call Orca, against SA-2 and non-goal 1 (option-b.md:22).
- Reframed (b) in the merged text, D5/REC:48, "Raise to exactly 2, scoped": a worker's top-level session may start sub-workers only when its brief says `Sub-workers: allowed, max N`; no command file changes; refusal fires at the new max, bad values fall back to 1. Stated costs: (1) a composite brief type the spec does not define; (2) the parent becomes a second orchestrator (R5) running the full coordinator loop (CAPS:92,107,113,116); (3) sub-worker questions would probably go to the coordinator's Run mailbox, not the parent (CAPS:59,92; UNVERIFIED); (4) WC-13 would have to be relaxed for briefs carrying the `Sub-workers:` line; (5) the brief line restrains only IronClaude workers while the value applies to every run under the profile. Saves one coordinator wake, read and `task-create` per run-time split.
- Cost to change later (D5/REC:37-38): raising is one desktop setting but does nothing alone: IronClaude would first need a new worker-brief type, rules and tests, and a check of where sub-worker messages land. Lowering it again while deeper workers run is unverified, so "raise it only after a real run shows the need".
