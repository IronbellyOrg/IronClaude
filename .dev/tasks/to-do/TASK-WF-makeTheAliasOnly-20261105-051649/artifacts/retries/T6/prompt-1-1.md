+# Model aliases and ccsession tiers
+
+Agents, commands, skills and the Python package pick models by the plain aliases
+`opus`, `sonnet` and `haiku`. They never name a ccsession picker id such as
+`claude-gw-tier1a`. Inside a ccsession tier workspace the aliases are mapped to
+tier models through three environment variables. Outside one nothing is set, so
+the aliases keep Claude Code's own meaning. Issue #384 records the decision.
+
+## What a primitive may name
+
+- A frontmatter `model:` is `opus`, `sonnet`, `haiku` or `inherit`.
+- A `--model` or `--models` value in a command, skill or script is an alias.
+- A Python string constant that selects a model is an alias, never a dated
+  model id such as `claude-opus-4-8`.
+- Allow-list: the three issue workers pin picker ids on purpose, because they
+  must run on a fixed tier (`issue-worker-t3` on `claude-gw-tier3`,
+  `issue-worker-t2` on `claude-gw-tier2`, `issue-worker-t1` on
+  `claude-gw-tier1a`). Outside a ccsession tier workspace they stop with
+  `E-TIER-UNAVAILABLE`; there is no alias fallback. The `sc-issue-protocol` skill
+  and the `ccsession-tag` launcher package may also contain tier ids.
+
+`tests/skills/test_model_alias_policy.py` enforces this. It scans the agent,
+command and skill files and the Python sources, and it lists every exception
+with its reason.
+
+## The mapping
+
+Owner decision of 2026-11-05. Inside a ccsession tier workspace:
+
+| Alias | Tier model it resolves to | Set by |
+|---|---|---|
+| `opus` | `claude-gw-tier1a` | `ANTHROPIC_DEFAULT_OPUS_MODEL=claude-gw-tier1a` |
+| `sonnet` | `claude-gw-tier1b` | `ANTHROPIC_DEFAULT_SONNET_MODEL=claude-gw-tier1b` |
+| `haiku` | `claude-gw-tier2` | `ANTHROPIC_DEFAULT_HAIKU_MODEL=claude-gw-tier2` |
+
+Outside a ccsession tier workspace none of the three is set by the launcher, so
+`opus`, `sonnet` and `haiku` keep Claude Code's meaning.
+
+The exports are:
+
+```text
+ANTHROPIC_DEFAULT_OPUS_MODEL=claude-gw-tier1a
+ANTHROPIC_DEFAULT_SONNET_MODEL=claude-gw-tier1b
+ANTHROPIC_DEFAULT_HAIKU_MODEL=claude-gw-tier2
+```
+
+Status: the ccsession launcher applies these exports in tier mode in a follow-up
+change, made after the #315 pull request merges. Until then the workspace
+defaults file (`/etc/aidev02/aienv.d/defaults.sh`) exports real model ids for the
+three variables, so the aliases resolve to those models and not to the tier ids.
+
+## Why aliases and not picker ids
+
+Claude Code resolves the model of a subagent in a fixed order (source:
+<https://code.claude.com/docs/en/sub-agents>, read 2026-11-05):
+
+- The Agent-call `model` parameter takes only the aliases `sonnet`, `opus`,
+  `haiku` and `fable`. It cannot carry a picker id, and it wins over the
+  agent's own `model:`.
+- The agent's frontmatter `model:` takes an alias, a full model id or `inherit`.
+  It is a literal value; the page documents no environment lookup there, so
+  `model: ${SOMETHING}` is not an option.
+- Next comes the `CLAUDE_CODE_SUBAGENT_MODEL` variable, then the main session's
+  model.
+- An alias is looked up in `ANTHROPIC_DEFAULT_OPUS_MODEL`,
+  `ANTHROPIC_DEFAULT_SONNET_MODEL` or `ANTHROPIC_DEFAULT_HAIKU_MODEL`, and those
+  variables may hold any id the gateway serves, tier ids included.
+
+The last point was checked on 2026-11-05 against the workspace gateway. See
+[the probe record](../../.dev/issues/384/analysis/probe-alias-remap.md): a
+subagent with `model: opus` ran on `claude-gw-tier1a` and one with
+`model: haiku` ran on `claude-gw-tier2`, while the main session kept its own
+model. Claude Code logs an `unrecognized_model` notice for each tier id but
+serves the request. That probe covered the frontmatter path and `--model`; it
+did not exercise the Agent-call parameter.
+
+## Known consequences
+
+- **Reflect reviewer diversity.** The reflect protocol counts how many distinct
+  model classes the three variables hold. Tier ids are three distinct strings, so
+  it sees three classes, but tier 1a and tier 1b both list Claude Sonnet 5.5
+  (`src/superclaude/skills/ccsession-tag/MODEL-TIERS.md`), so the reviewers are
+  less different than the count suggests.
+- **Sprint alternate-model suggestion.** `suggest_alternate_model` in
+  `src/superclaude/cli/sprint/aienv.py` still works when the failed model is
+  given as an alias (`opus` suggests `sonnet`). When the failed model is a real
+  model id taken from a cooldown message, for example `claude-opus-5-5`, it
+  matches nothing while the slots hold tier ids and returns `None`
+  (`aienv.py` lines 111-128).
+- **Roadmap names stay.** Step ids such as `generate-opus-architect` and
+  `best_model` values in recommendations keep their names, because the aliases
+  they use do not change.
+- **Implement retry ladder.** `refs/retry.md` of `sc-implement-protocol` named
+  its slot variables with an underscore after the tier digit, which the
+  workspace does not export. It now uses the exported names `T3Model01`,
+  `T2Model01`, `T2Model02`, `T1Model01` and `T1Model02`, so the primary ladder
+  activates wherever the four rung variables are set and replaces the alias
+  fallback ladder. In the current workspace that puts a non-Claude model on
+  rung 1, GPT models on rungs 0 and 2, and the Claude top rung on `T1Model01`;
+  the advisers it picks are `claude-opus-5-5` and `gpt-6.1-sol`. The full
+  account is in the Task 5 notes of the issue #384 plan package under
+  `.dev/tasks/`.
