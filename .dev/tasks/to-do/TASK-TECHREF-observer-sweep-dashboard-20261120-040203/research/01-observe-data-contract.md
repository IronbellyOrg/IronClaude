**Module docstring (adapter.py:1-7)** says "three argv shapes": the worker-list template (optional run/cursor pairs), the one-time discovery probe made by `_find_orca`, and "the one R2 message template for a single named Run (used only past the gate guard in `commands.py`)". ### 1.1 The three allowed argv shapes (after the binary)
| # | Shape | Defined at | Notes |

- Argv is passed as a list with no shell: `subprocess.Popen(argv, stdin=DEVNULL, stdout=PIPE, stderr=PIPE, start_new_session=True)` (adapter.py:232-238). [CODE-VERIFIED]

### 1.2 Forbidden-token list
`FORBIDDEN_PREFIXES` (adapter.py:34-50), a frozenset of 13 prefixes: `check`, `--ack`, `--wait`, `--retry-request`, `--peek`, `dispatch`, `inbox`, `run-use`, `run-create`, `send`, `ask`, `reply`, `reset`.
- Matching is `tokens[index].startswith(prefix)` for every index in `_option_positions` (adapter.py:121-132, 142-147); i.e. by prefix against every verb/flag position, "never against run or cursor values" (adapter.py:33 comment).
- Option values are excluded from matching: for worker-list, the value after each `--run`/`--cursor` (adapter.py:127-131); for the question shape, token indexes 1, 4 and 6 are removed from the checked set (adapter.py:124-126), i.e. the verb `check` (index 1 in tokens after the binary), the type value `question` (index 4) and the run id (index 6). So the question template is the one place where the otherwise-forbidden verb `check` is permitted, and only in that exact 8-token shape.
- Consequence to note: `--wait`, `--ack`, `--peek`, `--retry-request` are forbidden even in the question shape (they would sit at checked positions and also fail the 8-token shape).
- The docstring says "the set only ever grows" (adapter.py:6); that is an intent statement, not enforced by code (it is a frozenset literal). [CODE-VERIFIED as a test-pinned floor: test_adapter.py:178-192 asserts the set is a superset of the 13 names, see section 8.3; growth is permitted, shrinkage fails the test]

### 1.3 Caps, timeouts, kill behaviour
- `MAX_CALLS_PER_CYCLE = 5` (adapter.py:57); `MAX_OUTPUT_BYTES = 8 * 1024 * 1024` (adapter.py:58); `STDERR_KEEP_BYTES = 2048` (adapter.py:59); `PER_CALL_TIMEOUT = 10.0` with the comment "UNVERIFIED until the first permitted live read measures it" (adapter.py:60-62); `KILL_GRACE_SECONDS = 2.0` (adapter.py:63).
- `production_runner` (adapter.py:224-247) returns `(returncode, stdout, stderr)`; raises `RunnerFailure` with code `timeout`, `output-cap` or `spawn-error`. stdout is read on one thread in 64 KiB chunks; when running total exceeds 8 MiB it sets `overflow`, kills the whole process group (`os.killpg(..., SIGKILL)`, adapter.py:196-209) and stops (adapter.py:256-271). stderr is drained on its own thread and only its first 2 KiB kept (adapter.py:273-284). Timeout is `stdout_done.wait(timeout)` (adapter.py:296-298); after stdout closes the process gets `KILL_GRACE_SECONDS` to exit, else killed and reported as `timeout` (adapter.py:301-305).
- `cancel_active()` kills and reaps every in-flight Popen tracked in `_ACTIVE` (adapter.py:212-221); `LiveSource.cancel()` sets a cancelled event then calls it (adapter.py:362-365).
- Stderr is sanitized (`sanitize(diagnostic, "block")`) and truncated to 2 KiB in `_stop` (adapter.py:383-393).

### 1.4 Paging, stop codes (`LiveSource.read_pages`, adapter.py:395-467)
- Returns `SourceResult(state, pages, code, diagnostic, capped, calls)` (adapter.py:318-325); state is `OK`, `FAILED` or `PARTIAL`. `_stop` yields `PARTIAL` if any page was already read, else `FAILED` (adapter.py:386).
- Loop per call: stop with code `overrun` if the time budget is exhausted or cancelled (adapter.py:409-411); non-zero exit -> `exit:<n>` (adapter.py:435-436); JSON decode failure (including `RecursionError`) -> `json` (adapter.py:437-444).
- `_peek` (adapter.py:328-340) reads `result.page.hasMore/nextCursor/total` and `len(result.workers)` without validating them (strict checks are in parse.py).
- Special stop `empty-page`: zero workers on a page while `page.total` is a positive int (adapter.py:447-453).
- `hasMore is not True` -> `OK` (adapter.py:454-455). If `calls >= max_calls` and more remain -> `PARTIAL` with `capped=True` (adapter.py:456-457).
- Cursor checks: missing or empty `nextCursor` -> `cursor-stalled` (adapter.py:458-461); non-string -> `cursor-rejected` (adapter.py:462-463); a cursor already used this cycle -> `cursor-stalled` (adapter.py:464-466); a cursor the argv checker refuses -> `cursor-rejected` (adapter.py:414-417).
- Budget-limited timeouts are reported as `overrun` rather than `timeout` (adapter.py:418-430). Per-call timeout is `min(per_call_timeout, remaining)` (adapter.py:421).
- Discovery failure -> `SourceResult("FAILED", code="not-found")` (adapter.py:402-403).

### 1.5 Question read (`LiveSource.read_questions`, adapter.py:469-512)
- One call, no paging, same timeout and output cap; `max_calls` does not apply (single call, `calls=1`). Reply returned as `SourceResult("OK", (page,), calls=1)` (adapter.py:512).
- Error envelope handling: if the stdout decodes to a dict with `ok is False` and `error.code` is one of `consumer_fenced` / `no_active_terminal`, it returns source code `consumer-fenced` / `no-active-terminal` regardless of exit status (adapter.py:65-69, 496-507). Other failures: non-zero exit -> `exit:<n>` (adapter.py:508-509); undecodable or `ok:false` with an unlisted code -> `json` (adapter.py:510-511).
- Both error-code names come from Orca's own envelope; the file does not say where the names were verified. [UNVERIFIED against a live Orca; see fixtures section 8 for the recorded goldens]

### 1.6 Discovery in LiveSource
- `discover()` runs `self._discover()` (default `_find_orca`) at most once per `LiveSource` (adapter.py:367-372). `namespace` is `os.path.realpath(self.orca)` (adapter.py:378-381) - "observer-derived", i.e. the namespace tag on rows is the resolved Orca binary path, not anything Orca returned.

### Key Takeaways (adapter.py)
- Exactly three argv shapes; all argv built from literal templates; run ids and cursors are the only free values and are pattern/byte-checked.
- `check` is a forbidden verb everywhere except inside the one 8-token question shape; no acknowledge/wait/peek/retry flag can pass.
- Limits: 10 s per call, 8 MiB stdout, 2 KiB stderr kept, 5 calls per cycle (cap is a `read_pages` default argument and so can be overridden by the caller).
- Rows are namespaced by the resolved Orca binary path.

## 2. parse.py - strict envelope, lenient rows, UNKNOWN sentinel, merge (src/superclaude/cli/observe/parse.py, 836 lines)

### 2.1 UNKNOWN sentinel
- `class _Unknown` (parse.py:25-40) and the singleton `UNKNOWN: Any = _Unknown()` at **parse.py:43** [CODE-VERIFIED, matches the brief]. Docstring: "the single 'the source did not give this' value (never None, 0, False or '')". `__copy__`/`__deepcopy__` return self; `__reduce__` returns "UNKNOWN" so pickling preserves identity (parse.py:33-40).
- `_lookup` returns UNKNOWN when any key on the path is missing, any intermediate is not a dict, or the leaf is JSON null (parse.py:293-298). `_value` leaves UNKNOWN alone, sanitizes strings (mode `block` only for `stage_detail`, `stage_activity`, else `line`), and turns dicts/lists into sanitized sorted-key JSON text (parse.py:301-312, 91-93).

### 2.2 Verified worker-list keys read (`_FIELDS`, parse.py:58-90) - 31 attributes
dispatchId, taskId, runId, workerState, dispatchStatus, terminalState, resource.{id, ownershipState, releaseState, worktreeId, ownerDispatchId, originDispatchId, recoveryAttemptCount}, projection.{outcome, role, provider.id, host.{id,kind}, workspace.{id,kind}, stage.{worker,dispatch,activity,detail}, nextAction.kind, liveness.{verdict,source,observedAt}, evidence.{durable,liveStatus,lastObservedAt}}.
- Any other key is counted (`_count_unexpected`, parse.py:315-322, tallied in `Row.unrecognised_keys`, parse.py:155, 354) and its name and value dropped (docstring parse.py:3-4). Counting recurses only where both the known tree and the actual value are dicts.
- `Row` is a frozen dataclass (parse.py:109-161) with these extra non-source fields: `namespace`, `identity`, `cycle`, `last_seen_cycle`, `source_rank`, `absent_fields`, `flags`, `unrecognised_keys`, `reobserved`, `fixture_frozen` (set only by the fixture loader).

### 2.3 Strict envelope vs lenient rows (`parse_page`, parse.py:365-407)
- Strict: raises `ShapeError` unless `result` is an object (parse.py:369-371), `result.workers` is a list (372-374), `result.page` is an object (375-377) and `result.page.hasMore` is a real bool (378-380). The cycle is then `FAILED (shape)` (ShapeError docstring parse.py:51-52).
- Lenient: a non-object entry of `workers` is counted in `malformed_rows` and skipped (parse.py:384-388); missing/odd fields in a row become UNKNOWN and are listed in `absent_fields` (parse.py:325-337).
- `total` and `limit` use `_non_negative_int` (bool and negatives -> UNKNOWN) (parse.py:359-362, 399-400). `scope` and `counts` are kept only if dicts, passed through `_clean_json` (depth > 6 collapses to UNKNOWN; every string sanitized) and "never summed" (parse.py:173-174, 277-290, 401-402). `warnings`: list of str only, sanitized, first 50 (parse.py:403-405).
- Identity: `(namespace, dispatchId)`. A missing/blank/non-string dispatchId makes the row anonymous: identity `(namespace, UNKNOWN, cycle, rank)` plus flag `"identity unknown"` (parse.py:333-345).

### 2.4 Timestamps
- `parse_timestamp` accepts ISO 8601 (trailing Z handled; naive treated as UTC) or numeric epoch; numbers above 1e11 are treated as milliseconds ("PROPOSED") (parse.py:237-261). `format_utc_iso` writes whole-second `...Z` (parse.py:264-266).

### 2.5 Merge rules (`merge`, parse.py:654-744; helpers 613-651)
- Pure function over `(previous Snapshot|None, pages, stopped_by_cap, stopped_by_error)`; `clock` accepted and unused (parse.py:660-665). Raises `ValueError` on zero pages.
- Within one cycle: rows with the same identity are deduplicated (`duplicates` counted); the newer timestamp wins, comparing only like fields (`liveness_observed_at` vs `liveness_observed_at`, else `evidence_last_observed_at` vs the same) (parse.py:620-634, 672-682). No common timestamp keeps the first and flags `"order unknown"`. Anonymous rows are never deduplicated or matched (parse.py:674-675).
- Across cycles: same identity in the previous snapshot: newer or equal timestamp -> new row wins; older timestamp -> the previous row is kept (with `last_seen_cycle` updated) and flagged `"conflict (time went back)"` ("An older timestamp never overwrites a newer one", parse.py:637-651); no common timestamp -> newer cycle wins, flagged `"order unknown"` (parse.py:640-641).
- Rows present before but not returned this cycle are kept with `reobserved=False` (parse.py:723-728). Previous anonymous rows are dropped only after a complete (non-partial) cycle (parse.py:726-727). So rows are never deleted for absence; they are kept and marked not-reobserved. [CODE-VERIFIED]
- Output `Snapshot` takes `has_more/total/limit/scope/counts` from the LAST page read; warnings deduplicated across pages, cap 50 (parse.py:730-743).
- `Coverage` (parse.py:179-218): `state` is `PARTIAL` (cap hit, error, empty page, or has_more at stop), `MISMATCH` (complete but collected != reported total), else `COMPLETE`.

### 2.6 Fixture loader (parse.py:747-835)
- 10 `VARIANTS` names (parse.py:750-761) - base, uneven, shared-unmapped, historical, long-identifiers, source-loss, missing-fields, duplicate-out-of-order, empty, injection. The fixtures directory also holds files not in this tuple (golden-*.json, question-cap-100.json); see section 8.
- `fixtureOnly` marker keys are popped before parsing so "the live parser never sees it" (parse.py:828-833).

### Key Takeaways (parse.py)
- `UNKNOWN` (parse.py:43) is a dedicated singleton, distinct from None/0/False/"".
- Only 31 worker-list keys are read; everything else is counted and discarded without keeping its name or value.
- Merge never removes a row for absence and never lets an older timestamp overwrite a newer one.
- Row identity is `(resolved Orca path, dispatchId)`; there is no cross-namespace merge.

### 3.3 Single-flight and the polling loop
- Single flight: `run_once` holds `_cycle_lock` for the whole cycle (collector.py:156, 250), so a second caller waits; the published reference is replaced under a separate `_lock` (collector.py:155, 177-184). `latest()` returns the one immutable `CycleResult`.
- `start()` spawns one daemon thread `observe-collector` (collector.py:335-343); `_loop` runs `run_once`, exits permanently if state is `NOT_AVAILABLE` ("no Orca CLI validated: no cycle ever starts", collector.py:345-351), else waits `next_interval` (interruptible by the stop event). `stop()` sets the stop event, calls `source.cancel()` if present (kills an in-flight Orca call) and joins the thread for up to 5 s (collector.py:353-361).
- `run_once` first checks `source.available`; if no Orca is found it publishes one `NOT_AVAILABLE` result with code `not-found` and returns the same object on later calls (collector.py:252-270).

### 3.4 Backoff and recovery (collector.py:154, 186-189, 304-306, 321)
- `_wait` starts at `interval`. When no page could be parsed (first page failed, or first page shape error): `_wait = min(_wait * 2, max_backoff)` -> 15, 30, 60, 60... [CODE-VERIFIED collector.py:306]. Any cycle that parsed at least one page (including `PARTIAL`) resets `_wait = interval` (collector.py:321).
- On a failed first page the previous snapshot, coverage and last-success times are carried over unchanged (collector.py:307-316) - the observer keeps showing the last good rows.
- Question-read failures never touch the backoff or the row snapshot (comment "its failure touches nothing below", collector.py:290).
- Note: the cycle does not shorten the wait by the elapsed duration; `next_interval` is the full wait after the cycle ends, so the real spacing is cycle duration + wait. (Observation from the loop at collector.py:345-351; not asserted by any doc.)

### 3.5 STALE rule
- The collector does NOT decide staleness (collector.py:1-6 docstring and :39). The rule lives in `view.py`; see section 5.1.

### 3.6 Question source inside a cycle (`_question_fields`, collector.py:205-245)
- Questions are on only if `questions and run_id` (one named Run only; collector.py:152); link reading only if `link and questions` (collector.py:153).

## 4. questions.py - bounded question retention (src/superclaude/cli/observe/questions.py, 143 lines)

- Docstring (questions.py:1-12): store keyed by `(Run, message.id)` "until closure evidence is seen; no closure source exists, so nothing is ever closed". A question absent from a later successful read stays, marked `no longer in source window` (`NO_LONGER_IN_WINDOW`, questions.py:23); a failed read changes nothing; bounded at `RETENTION_BOUND = 1000` (questions.py:21). "The open total never falls": beyond the bound it reads `unknown (retention exceeded)` (`RETENTION_EXCEEDED`, questions.py:24, 66-67). [CODE-VERIFIED: merge_questions never removes a record except by the 1,000 bound, questions.py:105-129]
- Eviction: when more than 1,000 records, the oldest by created time are dropped (`ordered[:-RETENTION_BOUND]`, questions.py:125-129); `evicted` counts them and `evicted_keys` (newest 1,000) prevents double counting; an older evicted key that returns can be counted again (questions.py:46-49 "shortcut" comment). Ordering: oldest created first, unknown-created last (`_order`, questions.py:70-73).
- Anonymous (no id) rows are counted in `identity_unknown_rows` and not retained (questions.py:99-103, 136).
- `WINDOW_ROWS = 100`; `window_is_full(raw_count)` is true when exactly 100 messages came back because "the source gives no total" (questions.py:22, 140-142). `QuestionState.window_full` records it (questions.py:50).
- **Documented limit (questions.py:9-12):** `check --all` rows carry no read/acknowledged marker, so a question the coordinator already handled is listed again as open for as long as Orca still returns it; "seen is not resolved, and neither is handled". This is the code's own statement of the semantics; it is consistent with a non-acknowledging read but does not itself prove the verb never changes Orca state (see section 10).
- `QuestionState` properties: `retained` (len records), `open_total` (retained + evicted), `open_total_text` (questions.py:56-67).

### Key Takeaways (collector.py, questions.py)
- One daemon thread, one cycle at a time, 15 s interval, doubling to 60 s only when the first page fails; never gives up unless Orca is not found.
- Questions are opt-in per one named Run; at most 4 worker-list pages + 1 question call per cycle.
- Retention is bounded at 1,000 and nothing is ever closed, so "open" means "still returned by Orca or retained".

- The JSON snapshot is a flattened, closed (`additionalProperties:false`) subset of what the parser reads: 20 of the 31 worker-row source attributes are exported; `resource.*`, workspace and stage activity/detail are dropped.

## 12. Data flow, derived limits and facts for Sections 4 and 8 (observer rows)

Data flow (each hop code-verified above): `orca skills list --json` (discovery, once) -> `LiveSource.read_pages` (`worker-list`, 100 per page, up to 5 pages) [+ `read_questions` (one `check --all --types question --run <id> --json`)] -> `parse_page`/`parse_questions` (strict envelope, lenient rows, sanitized) -> `merge`/`merge_questions` (row set kept across cycles; questions kept to 1,000) -> `CycleResult` published by `Collector` -> `build_view` (adds STALE, ordering, display text) -> either the screen, `record_text` (stdout with `--once` or the `e` key) or `snapshot_json` (`snapshot.json`).
Derived arithmetic (not stated in code; computed from constants): worker rows readable per cycle = 5 pages x 100 = 500 with questions off, 4 x 100 = 400 with questions on (adapter.py:29, 57; collector.py:32-34, 273). The recorded live sample reported `total` 428 (test_golden_contract.py:49): at that size a full traversal needs 5 pages, so a questions-on cycle can never complete it (always `PARTIAL`, `stopped_by_cap`), and a questions-off cycle just fits. Pages arrive newest-first (`source_rank` comment, parse.py:117), so the oldest rows are the ones cut. Rows already read in earlier cycles are kept with `reobserved=False` (parse.py:723-728), which keeps them visible, but `merge` has no cap or expiry on that kept set (no pruning code in parse.py:654-744), so the in-memory row set can only grow for the life of the process. [observation from reading; not stress-tested]
Facts for the observer rows of Sections 4 and 8 of the technical reference:
- Read-only by construction: argv allow-list of three templates, forbidden-prefix list (13), `check` legal only inside the 8-token question shape, 10 s / 8 MiB / 2 KiB / 5-call caps, no shell, own process group, kill and reap on timeout/overflow/quit.
- Pull-based polling per observer process: 15 s interval, 15 s cycle budget, backoff 15 -> 30 -> 60 s on a failed first page; no push, no event stream, no shared service; HELP states several observers multiply load on Orca (commands.py:87-88).
- Questions are for exactly one named Run, only from the terminal that holds it, bounded best effort (100-row window; bursts over 100 rows between reads may be lost, measured loss recorded in release-gates.md blob line 42), `seen` is not `resolved`, nothing is ever closed.
- Output: one JSON snapshot (`schemaVersion` 1, additive-only policy, closed schema, "PROPOSED, not an Orca contract") overwritten each cycle in the per-user state dir (default `~/.local/state/superclaude/observe/snapshot.json`, 0600, atomic), plus plain-text records on demand; no history; the JSON carries 20 of the 31 worker-row attributes read and no question text; the text record carries question subjects.
- Row identity is `(resolved Orca binary path, dispatchId)`; message identity is `(Run, message.id)`; a `dispatchId` is never a question identity (parse.py:416-418; test_parse.py:660).
- The namespace tag is observer-derived (the resolved Orca CLI path), not an Orca-provided id (adapter.py:378-381).
