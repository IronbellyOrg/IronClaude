## 4. The living-report mechanism
**Entry files** live in `.dev/coordinator/orchestrated/<owner>__<repo>__<number>.json`, closed ones in `orchestrated/closed/`, information items in `orchestrated/info/<kind>__<key>.json` (common.py:133-137). One flat JSON object: `url,title,kind,group,priority`, written parts `state,next,what,state_text,done,todo,happened,recommend,needs,how` (+`suggested`,`priority_why` when priority Unset), `session_status{sid: "<status>: <reason>"}`, `assignees,human_assignee,author`, `orchestrator{id,tag,session_id,link,tier}`, `worker{session_ids,link,title,branch,tier}`, `pr_url,last_update`, and `closed_at,close_reason` added by refresh (common.py:139-149). Any missing field gets a plain fallback (common.py:150-151).
**Who writes entries:** per this skill's own comment, `superclaude orchestrator report-entry` (common.py:136); per docs/designs/orchestrator.md:510 that verb is in the not-yet-merged PR B package. This skill itself only **reads** them and **moves** closed ones to `closed/` (run.py:466-488) and **deletes** old ones (run.py:530-539). No code in the snapshot writes an active entry file (grep `report-entry|orchestrated/` over src/ = only AWR, sc-closeout settle.sh/refs). Tests build entry files by hand.
**exclude.py (Step 4b)** reads `coverage.json`, `github-items.json`, `sessions.json`; for each entry whose issue URL is in this run's open+assigned-to-`clayphi` issues of a repo read without error, it removes the issue, entry `pr_url`, and every `orca://session/<id>` the entry names (worker, orchestrator, `session_status` keys) from `github-items.json`/`sessions.json`, writes `excluded.json` (sorted URLs) and keeps `*-before-exclude.json` for idempotent reruns (exclude.py:59-103). Entries in `closed/` or `info/` exclude nothing; a ClickUp task linked to a held issue stays an item of its own (exclude.py:16-20). compare.py:128, match.py:157, render.py:335 read `excluded.json` so nothing reports the held item as new/lost/carried.
**run.py refresh** (run.py:644-840), no model call: (1) lock `refresh.lock` (flock, :637-641); (2) `reconcile_entries` calls `gh issue view` per active entry and moves it to `closed/` with GitHub `stateReason` or "no longer assigned to you"; a failed read keeps it (491-527); (3) `prune_old_entries` deletes `closed/`+`info/` files older than `info_ttl_days` (default 14, read from `repos.yaml` by regex; 438-452, 530-539); (4) base = given run's `overview.md` or latest completed run, else an empty overview (656-661, 843-865); (5) strips held URLs from "Needs you", "Your work by priority", "Other work in progress", "Likely yours", classification, items, carried and snapshot (680-730); (6) appends a "### Held by the orchestrator (N)" block of cards rendered by `render.entry(..., filed=e)`, information entries into "Other work in progress", closed lines into "Closed since the previous report" (749-805); (7) builds in a scratch folder `.refresh-build-*` via `page.main(cur)`, which writes the shared `.dev/coordinator/report.html`; never `<run>/report.html`, so the delivery gate is unchanged (807-832).
**Entry-to-card mapping** (`entry_record`, run.py:542-603): group fixed `assigned` (or `inprogress` for info), priority from entry else `Unset`, session `claude_running` true only if its status string starts `working`; "changed" = entry `last_update` > base run start.
**Safety:** symlinked entry folders/files are refused (common.py:164-209; run.py:466-488); `safe_url` blocks non-http(s)/orca links (common.py:173-180); tests at tests:3879-3983.

## 6. Relationship to and overlap with the observer and the sweep
**Direct links (facts):**
- The skill does **not** read the sweep report (`.dev/sweeps/`), `superclaude sweep` or `superclaude observe` output, and does not call them: grep of AWR/ for `sweep` finds only `clickup.py` "paged sweep" of ClickUp (clickup.py:13, 150); grep for `observe` finds no hit. Conversely `src/superclaude/cli/sweep/` has no reference to `agent-work-report`, `.dev/coordinator` or `orchestrated` (grep of cli/sweep for "work report|agent-work-report|orchestrated" = none; "coordinator" hits only gate-policy strings, classify.py:79,93,103). `observe/` mentions coordinator only for coordinator *questions* via Orca (commands.py:63-70, 90).
- It does call `orca` (bare binary), through its own wrapper `orca_term.py`, not through any shared module: sessions/terminals/automations/tab/worktree verbs listed in section 2. Sweep uses default binary `orca-ide` ("never bare orca", probes.py:43) and orchestration/worktree verbs (probes.py:50-59); observer discovers its binary via `_find_orca` (adapter.py:21, 352) and calls `orchestration worker-list` and `orchestration check --all --types question` (adapter.py:29-32). The three tools share no Orca verbs (AWR: `terminal`, `worktree list/set`, `automations`, `tab`, `eval`; sweep: `orchestration run-current/worker-list/worker-show/task-list`, `worktree ps`; observe: `orchestration worker-list/check`). Only `worktree list` appears in both AWR (sessions.py:310) and sweep (probes.py:56, "pinned, not called in Phase 1").
**Overlaps in purpose (stated as facts):**
1. *Per-session status classification.* AWR assigns each Claude session one of six statuses (working, progressed, waiting on you, stuck, stalled, done; common.py:240-247) with the **model** deciding from transcript facts (SKILL.md:140; sessions.py:7-8). Sweep assigns eight classes (waiting on a person, stalled (proved), fenced, working, finished, idle, person session (active), could not determine; sweep/models.py:50-59) by **ordered scripted rules** from Orca run/worker rows, contracts and transcript tails (classify.py:151-339, "first match wins" models.py:61).
2. *"Waits on a person".* AWR: a session "waiting on you" = last turn asks Clay something (any `?` in last 400 chars, sessions.py:260-263, QUESTION_TAIL=400) or a tool call waited over 15 min (SKILL.md:140); these become the only "Needs you" entries (SKILL.md:141). Sweep: `waiting on a person` from a blocked contract, non-null `agentWait`, frozen plan STOP codes, or a ready Task (classify.py:161-248). Observer: lists coordinator `question` messages of one Run (adapter.py:32) and the worker ledger's next-action kind (commands.py:83). Three different definitions of the same human-attention concept; none consumes another's output.
3. *Transcript reading.* AWR reads transcript bytes from a saved offset (first run 24 h/30 MB; sessions.py:47-49) and joins terminals via `~/.config/orca/agent-hooks/last-status.json` + `/proc/*/environ`. Sweep reads the last 256 KiB of each transcript (probes.py:88, 865-867) and joins via `<state>/ccsession/orca-tabs` map files (probes.py:870-895). Different join keys for the same terminal-to-transcript problem (UNVERIFIED which survives Orca changes).
4. *Held work vs sessions.* AWR's exclude.py drops sessions an orchestrator entry names; sweep has no such concept and classifies every session it can read (SKILL sc-sweep: "what each session is doing, which ones wait on a person", commands/sweep.md:3).
5. *Outputs.* Both publish one HTML/Markdown artifact under `.dev/`: AWR `report.html` in `.dev/coordinator/` (committed by Step 14); sweep report in `.dev/sweeps/` (commands/sweep.md:40). Sweep is explicit that it "adds no recommendation and takes no action" (sweep.md:57); AWR's model writes recommendations, suggested priorities and "Needs you" options (SKILL.md:141).
6. *Cadence and audience.* AWR: weekday 07:00 push to one named person via ClickUp DM and an Orca tab. Sweep: on demand, coordinator or person only (sweep.md:18). Observer: interactive terminal UI, poll one read every 15 s (commands.py:87).
7. *Scope of items.* AWR joins GitHub issues/PRs/boards and ClickUp tasks to sessions; sweep/observer cover Orca Runs/workers/worktrees only (no GitHub/ClickUp read found in cli/sweep or cli/observe: UNVERIFIED by exhaustive grep, based on module names and docstrings).
