**OQ-1 — CC1 regex consolidation. DECIDED: Rename + Promote + Import (synthesis).**

`artifact_layout.py:99` (`_EVAL_ID_RE = re.compile(r"^[A-Za-z0-9_.-]{1,64}$")`) is a **path-safety regex**. `loader.py:86-88` (`EVAL_ID_REGEX = re.compile(r"^[A-Z][A-Za-z0-9]*([0-9]+(\.[0-9]+)?)?$")`) is the **strict FR-SCH2 schema contract**. The two are deliberately separate defense-in-depth layers. Implementation:

1. In `artifact_layout.py`: rename `_EVAL_ID_RE` → `_EVAL_ID_PATH_SAFETY_PATTERN`. Add a docstring stating "Path-safety regex — NOT the FR-SCH2 schema (see EVAL_ID_PATTERN below for that)."
2. In `artifact_layout.py`: **promote a new public** `EVAL_ID_PATTERN = re.compile(r"^[A-Z][A-Za-z0-9]*([0-9]+(\.[0-9]+)?)?$")` constant alongside `_EVAL_ID_PATH_SAFETY_PATTERN`, with docstring `"""FR-SCH2 schema contract — see schemas/suite.schema.json"""`.
3. In `loader.py`: replace the local regex definition with `from .artifact_layout import EVAL_ID_PATTERN as EVAL_ID_REGEX`. The `EVAL_ID_REGEX` name remains in `loader.__all__` as an alias for backward-compat with `tests/cli/eval/test_eval_id_regex.py:32`.

**Why this synthesis:** Defense-in-depth at regex boundaries is genuinely valuable; consolidation reviewers often miss it. The deciding question is "if I tighten this regex, do I break a different invariant than if I loosen it?" Here yes — tightening path-safety breaks valid YAML; loosening the schema lets path-traversal through. So they ARE two gates. But the **schema regex** itself was duplicated (definition in loader.py + the implicit schema contract). Promoting it to a single public constant in artifact_layout.py and having loader.py import it eliminates the duplication of the schema contract while preserving the two-layer defense.

**Grep gate adjustment (Step 6.1 GATE 3):** `grep -cE "re\.compile" src/superclaude/cli/eval/ | grep -i eval` returns **≤2 hits permanently** (one path-safety in artifact_layout.py, one schema also in artifact_layout.py — loader.py no longer compiles its own).

**OQ-2 — CC2 exit-code consolidation. DECIDED: Consolidate via `exit_codes.py` with 3-4 canonical values + descriptive re-exports.**

Per R3 MAP 1, 11 named `*_EXIT_CODE: int = 2` constants exist across 6 files. The named constants are not magic numbers, but they DO duplicate the integer `2` in 11 places — making future convention changes (Click 9.0, BSD sysexits migration) an 11-site coordinated diff. Implementation:

1. **CREATE** `src/superclaude/cli/eval/exit_codes.py` defining exactly **4 canonical values**:
   ```python
   """cliEval canonical exit codes (Click/POSIX/BSD sysexits hierarchy)."""
   SUCCESS: int = 0
   FAILURES: int = 1            # one or more eval failures
   USAGE_ERROR: int = 2         # operator misuse / config error (Click convention)
   INTERRUPTED: int = 130       # SIGINT / Ctrl-C (POSIX signal+128)
   ```
2. Each of the 11 declarations becomes a re-export with the descriptive local name preserved:
   ```python
   from .exit_codes import USAGE_ERROR as RUN_USAGE_ERROR_EXIT_CODE
   from .exit_codes import USAGE_ERROR as HARD_FAIL_EXIT_CODE
   # ... (one re-export per the 11 R3 MAP 1 sites)
   ```
3. The existing `RUN_CLEAN_EXIT_CODE` (commands.py:570) and `RUN_FAILURES_EXIT_CODE` (commands.py:573) become re-exports of `SUCCESS` and `FAILURES` for symmetry. `RUN_INTERRUPTED_EXIT_CODE` (commands.py:577) already re-exports from a sibling — extend the pattern to all four canonical values.

**Why this implementation tightening:** The new `exit_codes.py` is **4 lines of constant declarations, not 11**. The 11 module-level constants become single-line re-exports that carry their descriptive names. This preserves locality-of-naming (each module's exit-code identifier reads naturally at its call site) while making the integer values a one-file change for any future convention shift.

**Grep gate adjustment (Step 6.1 GATE 5):** `grep -rEn "_EXIT_CODE.*=.*\b[0-9]+\b\s*$" src/superclaude/cli/eval/` (declarations of any *_EXIT_CODE constant directly to a literal integer) returns **0 hits** — only `exit_codes.py` defines the values, and only at the 4-canonical-name level (without the `_EXIT_CODE` suffix), so the regex misses it cleanly.

### Shell Environment Hygiene (one-time, applies to ALL `uv run` invocations in this task)

`uv` 0.9+ emits `warning: VIRTUAL_ENV=/lsiopy does not match the project environment path .venv and will be ignored; use --active to target the active environment instead` on every invocation when the shell has a stale `VIRTUAL_ENV` set. The warning is cosmetic (commands still execute against `.venv`), but it pollutes every captured EXIT_CODE file and may confuse rf-qa during PG-FINAL parsing.

**Mitigation (apply BEFORE Step 1.3 runs the first `uv run` command):** Run `unset VIRTUAL_ENV` once in the shell that will execute this task. The Bash tool's shell persists for the session, so a single unset at the start propagates through every subsequent `cd /config/workspace/IronClaude && uv run ...` invocation across Phases 1-6. If invoking via a fresh subshell (e.g. `/task` execution), prepend `unset VIRTUAL_ENV; ` to the first Step 1.3 command.

Operator-facing alternative: pass `--active` to each `uv run` invocation. This is invasive (25+ sites) and not recommended — the env-var unset is the lowest-touch fix.
