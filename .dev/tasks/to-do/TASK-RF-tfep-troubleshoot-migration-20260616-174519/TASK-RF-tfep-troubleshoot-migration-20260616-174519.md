# Replace /sc:forensic with /sc:troubleshoot as the TFEP Diagnostic Backend

## Task Overview

The Test Failure Escalation Protocol (TFEP) in the SuperClaude task pipeline currently hardwires an invocation of `/sc:forensic`, but that skill is unavailable/never-authored in this environment — an in-session TFEP trigger cannot invoke it. `/sc:troubleshoot` is a mature, available tiered-diagnosis backend, but it is broader and diagnosis-first and does not natively emit the forensic-shaped return contract the TFEP consumes. This task makes `/sc:troubleshoot` a drop-in TFEP backend via a thin adapter plus backend-neutral terminology, so test-failure escalation works end-to-end and future backend swaps touch only one declaration.

The migration is confined to a narrow live surface (verified by R-003's repo-wide sweep): the TFEP block in `src/superclaude/skills/sc-task-protocol/SKILL.md` (§4.5, lines 133–261), the single `forensic` reference in `src/superclaude/commands/task.md:48`, the troubleshoot command/skill surface in `src/superclaude/commands/troubleshoot.md` + `src/superclaude/skills/sc-troubleshoot-protocol/SKILL.md`, and the troubleshoot report-template at `src/superclaude/skills/sc-troubleshoot-protocol/refs/report-template.md`. ALL other `forensic` / `return-contract` / `task-unified` hits across `docs/`, `.dev/releases/archive/`, and `.dev/eval-workspaces/` are intentionally historical and MUST NOT be touched.

This is a docs/skill-prose editing task: there are NO Python source changes, so per MDTM I18 there are NO pytest items. Verification is `make sync-dev` → `make verify-sync` (src↔.claude mirror parity, exit 0) plus protocol read-through and per-phase lens-based QA on the edited prose. Every edit lands in `src/superclaude/`; the `.claude/` mirror is a sync-dev output and MUST NEVER be staged (CLAUDE.md ABSOLUTE RULE).

The 8 pipeline changes map to phases as follows: Change 1 (terminology rename + `diagnostic_backend:` declaration) → Phase 2; Change 3 (`--context`/`--caller` ingestion) → Phase 3; Change 2 (TFEP adapter `return-contract.yaml` for troubleshoot) → Phase 4; Changes 4/5/6 (remediation-ownership decision, consume troubleshoot output, preserve freeze) → Phase 5; Changes 7/8 (incident reporting rebind, escalation budget) → Phase 6; final residual-reference verification + completion → Phase 7. Each implementation phase is followed by a standard-intensity M3 lens-based QA gate.
