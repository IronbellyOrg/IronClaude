## 7. Recommendation

**Recommended approach:** **One Shared Review Panel Core: a Thin Shared Contract with Per-Module Engines.** (This design was named "One Review Panel Core with Module Profiles" before the adjudication fold; it is renamed because debate C-01 overturned the default that the v2 kernel is the single engine of the core. See 7.0.1.) One shared Review Panel core lives in the existing package `src/superclaude/cli/review/` and is reached by installed skills and commands only through the `superclaude review ...` CLI. What the core shares across every module is a thin contract: the finding id grammar (`_ID`), one limits-constants module and one repair step that both parsers call, one reference-token list (with `T<PP>.<TT>` added once), hash and identity helpers, panel and tier resolution from one reviewed tier file, the run record (per-run events, a manifest lock, a cross-run telemetry export), the dispatch contract (the core launches nothing; a reviewer is launched with its `launch` word) and a tested evaluation script set. What it does not share is one engine: the spec-review module keeps the v1 anchor parser, `findings.py`, `ledger.py`, `review-ledger/1` and v1 clustering, with the clearing and merge-policy rules of C-02 and C-03; reflect and later PR review use the v2 kernel (`findings_v2.py`, `cluster.py`, citations with role, path and lines), and the v2 kernel is NOT the engine of the spec loop. Every consumer (reflect, tasklist and workflow review through reflect UC-1, spec review for `sc:spec-panel` and later `sc:brainstorm` and `sc:design`, and later PR code review and rf-qa / rf-qa-qualitative replacement) is a thin module made of profile data (vocabularies, label maps, reference patterns, lens and role tables, cap), brief blocks, and an output adapter. The reflect module keeps contract 1.8.0, the pure `contract.derive_verdict` shell, its 36-test matrix and, for now, engine A's ensemble as the production Tier 2 engine; the panel enters reflect only behind the reflect call (C-04, C-05). No consumer copies core text; the brief limits, categories and constants are generated from the core. Convergence to one engine is a recorded later path with three triggers (T-a, T-b, T-c: 7.0.1), not the starting point.
