## 1. The position in one paragraph

Over-limit finding lines are repaired by one deterministic step that runs on the parsed JSON object before the unchanged validator sees it. The step cuts `anchor`, `anchor2` and a citation `quote` to the first 200 characters of their whitespace-flattened form (an exact prefix, so it still locates) and cuts `claim` to 300 characters. It touches no field the limits do not name. The real parser then validates the result; anything still invalid (bad severity, bad refs, bad JSON, an under-length anchor) gets exactly one bounded, stateless re-ask that carries only the reviewer's own block and the parser's per-line errors. Every repaired and every still-dropped line is recorded with reviewer, line, finding id, blocking flag, field and lengths, and the reviewer's report file is never edited. The point of the ordering is that the cheap, deterministic, no-model-call step removes 88 of the 92 measured drops, so the expensive, unmeasured step (re-ask) is left with at most 4 lines.

## 6. Effect on future PR code review and rf-qa replacement

- PR review and rf-qa produce exactly the lines that break the 200 limit: code hunks, long table rows and long lines (FX-1, S06:96). With one limits module and one repair step inside the shared parsers, every module inherits the same policy and the same dropped-line itemisation, and no module has to write its own drop or truncate rule. This is the stated reason both parsers share the step (C-01).
- For a PR module with citations as `path:line` plus an optional `quote`, the `quote` cut (section 3.2) keeps `verify-citations` working on a prefix. A PR finding that carries no anchor is unaffected, because the step cuts only fields that exist.
- The re-ask is stateless, so a caller with no resumable reviewer session can still use it. pr-submit runs in the main session (R13 P8, as quoted at S05:243) [UNVERIFIED here; `pr_submit` was not opened]; whether that caller can issue a second prompt to the same reviewer is the one thing a PR module must confirm.

- A PR or rf-qa module that wants a different limit declares it in its profile and passes it to the step; the constants are the defaults, not a hard-coding (CO-9, decided: spec-shaped hard-codings become module extension points).

## 7. The strongest objection and my answer

**Objection (Position B's principle):** a repaired line is not the reviewer's finding. The orchestrator "never edits, remaps or normalizes a reviewer's findings itself" (`SKILL.md:343`); truncating text puts a rewrite into the trust chain, a claim cut mid-sentence can lose meaning, a cut anchor can bind to an earlier occurrence, and the recovery figure is a derivation from a count of reasons, not a measurement. A re-ask keeps the reviewer's own words and an itemised drop report keeps the loss visible.

**Answer:**
1. *The reviewer's text is not edited.* The report file is never modified and its `report_sha256` is already recorded per reviewer (`ledger.py:146`). The repaired object is a derived copy that exists in memory and in the ledger row, with a per-field record of original and kept length. `SKILL.md:343` is addressed to "the orchestrator", an agent session that could otherwise paraphrase a finding. A pure function with a recorded diff and a no-op property is a different kind of act. That is a reading of the sentence, not a fact: if the owner reads the sentence as covering code, Position A is wrong as written and the sentence has to be amended (one sentence in the Normalize step) or the policy changes to B. I state the dependency instead of hiding it.
2. *Dropping is also an edit, and a larger one.* Today the line is deleted, with a first-error-only warning that names no id (`ledger.py:130-134`). That deletion removed 49 blocking lines in the study and flipped 3 verdicts to PASS (R02:100-101). The choice is between a shortened line that is recorded and a deleted line that is recorded only if the drop report is added; both change what the reviewer wrote.
3. *Meaning.* Severity, `blocking` and `category` are typed fields that the cut does not touch, and the verdict reads `blocking`, not `claim`. The claim is the reviser's reading aid and keeps its first 297 characters. Reference tokens are preserved by the copy-to-`refs` rule (section 5). The cut is marked (`...`) and recorded.
4. *Wrong occurrence.* A shorter prefix is more likely to match twice, and `locate` takes the first match. Of the three open exposures this is the one I cannot close from code: M1 measures it, and the C-01 outcome that surfaces anchor status per blocking row is the guard. If M1 shows many ambiguous repaired anchors, the step should keep the line but mark `anchor_ambiguous` and refuse to let that row clear on a `prior resolved` alone; that tightening is compatible with A.
5. *Unmeasured recovery.* True for both halves, and I do not claim otherwise. The positions differ on how much depends on it: under A, at most 4 of 92 lines (1 of 49 blocking) depend on re-ask recovery; under a re-ask-only policy, all 92 do.
6. *Two mechanisms.* One is a pure function with no I/O; the other is an attempt-2 record in a manifest that already supports it (`manifest.py:378-383`). The re-ask half can be switched off without touching the truncation half.
