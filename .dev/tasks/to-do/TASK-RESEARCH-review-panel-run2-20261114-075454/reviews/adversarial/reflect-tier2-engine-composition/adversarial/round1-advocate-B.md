## Position Summary

Variant 2 is the safer C-04 position because it changes no verdict-bearing code, makes no claim about a reviewer-layer seam that the code does not support, and states the measurements and trigger that would move it to a single engine. It has real defects (the CV-5 resolution, an incomplete CV-8 correction list, an overstated "reuse" claim) that a merge should fix; the strongest merged result is Variant 2's boundary with Variant 1's helper location, serializer allowlist, replay oracle and invariant table.

## Steelman of Variant 1

The strongest version of Variant 1 is narrower than its header. It says: engine A's `runner.py` shell is the only part of Tier 2 with a Python parent, so it is the only place a deterministic step can be made unskippable and fail-closed. Engine B's contract 1.8.0, findings-v2 and kernel are the only data model that can carry deviation classes and a remediation pointer. A reviewer-lane split (grounded agents versus headless swarm workers) then lets one shell serve both runtime conditions, and no capability on either engine's loss list is dropped (V1 E7). That is a real design: it is the only option that, if it works, also repairs the production gate's "PASS without a deviation audit" property and makes `--fix` reachable (V1 section 7, RE-3).

What Variant 1 genuinely gets right, which Variant 2 should not hide from:

1. It is more rigorous in three places. Its invariant table has 14 rows with Preserved/Endangered reasons (S-004); it names the conditions under which each adjudicated outcome stops holding (U-001: C-01 conditions (a)-(c), the C-02 `--fix` cross-round-identity trigger, three C-03 dependencies); and its M2 replay oracle over recorded `panel/` artifacts (U-003) is the best measurement in either file because it needs no new runs.
2. It reads the decided CV-5 row correctly. `synth-06-conflict-log.md:190` says the count-derived label "is non-conforming" [V]; Variant 1 says exactly that and also works out the slug consequence (`null-convergence` becomes `single-reviewer-fallback`, exit stays 11; U-004, V-09 holds).
3. It identifies GQ-067 correctly (V-32) and it states, in its own 4.3, that no code-written contract has ever run and that the design is an analysis, not an observation.
4. It places the 1.8.0 serializer where the frozen lists live (`cli/reflect/panel_lint.py`), which is the more coherent location than a kernel module (C-002).
5. Its INV-L rating (Endangered, HIGH) is the more candid one: moving a writer of authoritative shadow-run files into code is a real risk and it conditions the design on M2.

If Variant 1 were scoped to "the write-side helpers plus a shared serializer, on both lanes, with the grounded-lane routing left for later", it would be very close to Variant 2. The disagreement that remains is whether to describe and commit to the composition now (engine B's data model as the core of engine A's shell), which is where the code does not follow it.

## Weaknesses Identified in Variant 1

1. **No code seam for its grounded lane, and the routing change is not stated.** See Strength 1 (`runner.py:540-546`; V-07). Variant 1's headline "engine B's data model inside engine A's shell" has two readings at the reviewer layer (Variant 2 E10): text-only reviewers over swarm (no grounding, which is the property Variant 1 wants from engine B) or `claude -p` children spawning Agent subagents, which no run has exercised and whose feasibility nobody has probed (E9, C-022). Variant 1 assumes the second reading without a probe.
2. **"Unskippable" is claimed for a lane that has no Python parent.** See Strength 2 (X-002). The fail-closed guarantee Variant 1 invokes (INV-I, section 8 answer 4) applies to the headless lane only.
3. **CV-5 change collides with a witness test and is rated too low.** See Strength 3 (`test_ensemble_stub_integration.py:162` [V]; V-10). INV-B is "Endangered, MEDIUM" in Variant 1, but the verified pin is on the value, in a run with no disk-confirmed merge.
4. **Serializer allowlist drops a key the verdict map reads.** See Strength 4 (`contract.py:306`, `ensemble.py:793` [V]; V-11).
5. **Lint layout versus headless layout.** See Strength 5 (X-008, V-28).
6. **Reviewer-count rules are not reconciled.** `config.py:335` clamps `--reviewers` to `1` or `[2,4]` [V]; `panel.py:72` fixes `_REFLECT_LAUNCH` to three launch slots and the reflect profile caps at 3 (`panel.py:73`, [L, V-26]). Variant 1 section 3.1 says the kernel is "kept" and engine A's runner is "kept", but a run of 4 reviewers has no home in the kernel profile (A-004).
7. **The new surface is understated.** Variant 1 section 8 answer 2: "The new code is the write side only. The readers exist". The existing extractors return the convergence score, the status and `merged_output_path`; `SKILL.md:346` lists six fields for `merged-verdict.yaml` (`merge_method`, `verdict`, `convergence_score`, `base_variant`, `source_cards`, merged findings) so existing code covers about one of six (V-29). Variant 1 also adds a lens-template change on the headless lane and the first `cli/reflect` to `cli/review` import edge (its own section 3.3; V-01).
8. **The headless lens change meets an unmeasured first-pass compliance risk.** Variant 1 moves tool-less single-message workers from a markdown findings table to a findings-v2 block (section 3.4). Its own cited figures for the skill panel's first-pass findings-block compliance are 0.704 over 9 pilot runs and 0.867 over 15 combo runs (section 2 point (b), research/07 E1-F12, [UNVERIFIED] in Variant 1). No measurement shows proxy-model headless workers meet that format; this is inference, and M4 only checks that a stub run passes, and a stub does not exercise model compliance.

A design whose admissibility depends on an unrun replay is a hypothesis; Variant 2 is the same where it touches the legacy contract (its INV-L row), but over a narrower surface (one serializer, not two lanes and a lens).
10. **No trigger and no answer for the owner question.** See Strength 6 (C-008, C-009). "Valid under either answer" means the engine-B-switch answer would still leave engine A's whole headless apparatus and its added serializer, with no stated condition for removing it.
11. **Edit-fence inconsistency.** See Strength 8 (X-007, V-15).
12. **CV-8 answered by a model that depends on an undecided slot.** Variant 1's headless exclusion needs "a model-to-class map and therefore depends on the tier-source decision of slot C-09" (section 3.5). The documents (`sc-tasklist-protocol/SKILL.md:1141, :1152, :1165, :1170, :1177` [V: Grep lines] assert an executor-disjoint ensemble) stay false until that lands; Variant 1 does not say they are corrected now.
