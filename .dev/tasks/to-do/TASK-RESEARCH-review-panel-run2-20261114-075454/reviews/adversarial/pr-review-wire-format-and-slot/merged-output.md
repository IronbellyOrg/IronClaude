## 10. The strongest objection and the answer

<!-- Source: Base (original, modified) — base section 8 kept in shape; the "four fields" sentence, the "put the count in body" suggestion and the base's test-file count corrected per Change #8; the debate's outcome on the objection added -->
**Objection (the strongest form of position B).** An adapter is a second definition of the finding record. It drifts from findings-v2 and from `Finding`; each new key needs two edits; it loses information (a cluster of three reviewers becomes one `Finding`, and the other citations, the lens and the role are dropped), so verify and troubleshoot cannot use them; and a third reviewer name in `REVIEWERS` would give the panel the same presence, dedup and reporting treatment as the bots, in one place that reviewers and operators already read.

**Answer.**
- **Drift.** The converter reads a named, small key set from the cluster output and from the source lines joined on `(reviewer_id, id)` (section 2.2), and writes the dict `finding_from_comment` already validates (section 4.2). Conformance fixtures (section 8.2) pin both ends. Under B the `pr_submit` side must still read a v2 line into a `Finding` (section 4.1), so the number of definitions of "a PR finding from a panel line" is one in both designs; B's four extra line keys were withdrawn in Round 2.
- **Information loss.** `seed_troubleshoot` reads `path`, `line`, `body`, `category` and the route (`fsm.py:437-453`) and `dedup_groups` uses `(path, line)`, but a `Finding` is also read for `in_diff`, `verification_status` (`fsm.py:902-906`), `fix_key` (`models.py:196-207`) and `comment_id` and `thread_id` (`fsm.py:1064-1074, :1203-1205`), so the downstream set is larger than four fields (section 4.2). Beyond those, a second citation, the lens and the role reach no consumer today. `body` is the claim verbatim and nothing is appended: a support count or a second citation in `body` would change `fix_key` between rounds. If a future consumer needs a key, it is added in the converter first and promoted to the core only when a second consumer needs it (section 1.5). The debate did find one real loss in the cluster collapse: as A-R2 states the aggregation, a more severe member's text and line can be lost (B-R2 D1; probe INV-012). That point is unanswered (section 7.1).
- **Treating the panel like the bots.** The bots are external actors observed through GitHub (identities, markers, silence timeouts, re-trigger phrases; `reviewers.py:47-72, :322-424`); the panel is a local run that completes when a merge returns. The two share only "a list of findings enters the gate", which is the part `finding_from_comment` already normalises. A third name in `REVIEWERS` makes the panel inherit machinery that has no meaning for it (watermarks, re-trigger phrases, silence-deadline `absent`), needs carve-outs in five two-name functions and two guards in `merge_wait` (section 4.3), and B conceded the axis. If the owner wants one reporting surface, the `panel` field beside `reviewers` is an additive field; no test pins the `reviewers` row (47 `test_*.py` files; section 4.3), and its effect on the existing tests was not run.
- **What C10-R concedes.** It is weaker on a single, visible reporting surface; it adds a pre-step to the skill prose that no test pins until one is written; each consumer writes and tests its own converter; and if several consumers later need the same per-finding keys, the keys would have to be promoted to the core then, with the retrofit cost r13:210 predicts once formats are pinned.
- **How the debate left the objection.** B conceded the slot axis (B-R1 Concession 4) and withdrew the model-emitted keys; what remains of it is the aggregation and the other contested amendments (section 7).
