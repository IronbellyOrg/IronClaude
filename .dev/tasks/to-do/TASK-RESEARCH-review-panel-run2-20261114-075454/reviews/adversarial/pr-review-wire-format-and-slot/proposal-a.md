## 1. The position (A, in one paragraph)

The panel's PR output is converted to `pr_submit.Finding` by a pure adapter that lives on the `pr_submit` side and takes plain JSON (a cluster record from the v2 kernel), and the panel runs as a separate pre-step started by the main session, before the existing snapshot gate and its remap, verify, troubleshoot and push stages. `Finding`, `Severity`, the FSM, `REVIEWERS = ("augment", "codex")`, `merge_wait`, `reviewer_activity`, the single executable snapshot-gate block in `SKILL.md` and the Output Contract `reviewers` object are not edited. The core keeps findings-v2 as the panel's own line format (citations, module-declared vocabularies per the decided FX-5) and does not grow PR-only keys (`in_diff`, `confidence`, `original_line`, `reviewer`). The adapter owns every PR-local fact, so the dependency runs one way: `pr_submit` knows the adapter's input shape, the core knows nothing about `pr_submit`. The adapter is the only place where "PR" and "panel" meet, and a later move to one wire format stays open because the adapter's input is the cluster record, which a one-format design would also produce.

## 8. The strongest objection and my answer

Objection (the strongest form of position B): an adapter is a second definition of the finding record. It drifts from findings-v2 and from `Finding`; each new key needs two edits; it loses information (a cluster of three reviewers becomes one `Finding`, the other citations, the lens and the role are dropped), so verify and troubleshoot cannot use them; and a third reviewer name in `REVIEWERS` would give the panel the same presence, dedup and reporting treatment as the bots, in one place that reviewers and operators already read.

Answer:
- Drift: the adapter reads a named, small key set from a record the core already emits (3.5) and writes the dict `finding_from_comment` already validates (3.2). Conformance fixtures (6.2) pin both ends. Under B the `pr_submit` side must still read a v2 line into a `Finding` (3.1), so the number of definitions of "a PR finding from a panel line" is one in both designs; B places it inside `pr_submit` and also adds four keys to the core's line format, whose type and meaning must be chosen against the existing three meanings of `confidence` (3.4).
- Information loss: downstream only reads `path`, `line`, `body`, `category` and the route (`seed_troubleshoot`, `fsm.py:437-453`; `dedup_groups` uses `(path, line)`), so keys beyond those four never reach a consumer today. The adapter can place a second citation or the supporting reviewers' count in `body` as text. If a future consumer needs a key, it is added in the adapter first and promoted to the core only when a second consumer needs it.
- Treating the panel like the bots: the bots are external actors observed through GitHub (identities, markers, silence timeouts, re-trigger phrases; `reviewers.py:47-72, :322-424`); the panel is a local run that completes when a merge returns. The two share only "a list of findings enters the gate", which is exactly the part `finding_from_comment` already normalises. A third name in `REVIEWERS` makes the panel inherit machinery that has no meaning for it (watermarks, re-trigger phrases, silence-deadline `absent`) and changes code and pins (3.3). If the owner wants one reporting surface, A can add a `panel` field beside `reviewers` in the Output Contract without a third `REVIEWERS` entry; that is an additive field, and whether it breaks any of the 50 test files has not been run.
- What A concedes: it is weaker on a single, visible reporting surface; it adds a pre-step to the skill prose that no test pins until one is written; and if several consumers later need the same per-finding keys, the keys would have to be promoted to the core then, with the retrofit cost r13:210 predicts once formats are pinned.
