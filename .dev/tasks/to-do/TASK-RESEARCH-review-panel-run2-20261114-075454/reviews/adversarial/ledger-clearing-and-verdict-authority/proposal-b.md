## 1. The position in one paragraph

A finding leaves the loop only on evidence, and silence is not evidence. In a re-review, a row the ledger holds as `resolved_check` (claimed fixed by a fix-map line plus a hunk over its span) becomes `resolved` only when a reviewer whose findings block is valid answers that row with a `prior` line `resolved` that carries a quote, and the quote occurs in the document text the round was merged against. A row nobody answers stays `resolved_check`, counts as open in the verdict, and is listed in the report as "unverified". A `prior` answer `open` or `regressed` moves the row back; a re-find of the row's defect wins over any `resolved` answer. The `blocking` value of a finding is decided by a script predicate over the finding's typed fields, owned by the lens (the spec lens derives it from the severity and the category that the shipped grading check already names); the reviewer's typed `blocking` stays in the record as input and a disagreement is reported, and a blind grader against a frozen rubric is a module a lens may add, not a core dependency. The verdict is derived from the rows on every read and is never stored. `defer` needs an owner, a reason and an expiry, never changes a verdict, and a deferred blocking row stays counted as open: when only deferred rows remain the decision is ESCALATE, not PASS. This is the machine form of what the shipped master loop already states in prose (`spec-panel.md:260,262`): a re-review with no prior table fails, and a deferred finding counts as open.

- B1 Clearing. - B2 Who answers. Only a reviewer whose block is valid. The `block_ok` map exists (`ledger.py:129,147`) and the loop never reads it; B2 makes the docstring at `ledger.py:112` ("skipped for clearing") true by changing the loop, which is the reverse of editing the docstring (LG-3 leaves this choice to LG-1).
- B3 Evidence key. The prior line gains an optional `evidence` string. - B4 Text binding. A quote check against `doc_text` means nothing unless `doc_text` is the revision output. `apply_revision` records no hash of the new text and `merge_round` only hashes whatever it is given (`ledger.py:279,301-314`; research 03 1.1 variant B). - B5 Derived verdict. `verdict()` (`ledger.py:363-372`) reads the stored `rounds[-1]` fields; B computes from rows: `brief_ids` (blocking, `open` or `regressed`), `verify_ids` (blocking, `resolved_check`, no answer), `held_ids` (blocking, `deferred`). PASS only when all three are empty. Otherwise FAIL, with decision REVISE while `n < cap_reviews` and ESCALATE at the cap (`_decision`, `ledger.py:93-96`); when only `held_ids` remain the decision is ESCALATE at once because no reviser action exists. The Reviser brief carries `brief_ids` only; `verify_ids` are asked of the next review through the unchanged re-review brief. Exit codes stay 0/10/11 (`ledger_cmd.py:13,109`).
- B6 Blocking authority. A lens-owned pure function `blocking(finding) -> bool`, registered with the lens' category set (research 13 M2: vocabularies are module inputs). The typed `blocking` is stored as `blocking_typed`; a difference is reported in the merge output's `warnings`. For the spec lens the predicate reads severity and category: `CRITICAL` is blocking; `MAJOR` is blocking when the category is one of `contradiction`, `unpassable-check`, `data-loss`, `safety` (the three blocking cases of the grading check in `document_review_loop_prompts.md:31` [UNVERIFIED here: read in research/12 1.2, not re-read]); `missing-requirement`, `other` and `MINOR` are not blocking. The reflect lens keeps its existing script rule `blocking == (severity != "MINOR")`, enforced by the parser (`findings_v2.py:161-162` [CODE-VERIFIED]). A blind `finding-grader` against a frozen rubric (installed-only today: `stoprule.py`, `~/.claude/agents/finding-grader.md`, per research 14 7.2) is an optional per-lens stage that may overwrite `blocking_computed`; the core does not depend on it.
- B7 Defer. `defer` takes `--owner` and `--reason` (required) and is allowed only on a blocking row in `open`, `regressed` or `resolved_check`; it records the history entry, does not touch any round record (it no longer rewrites `last["verdict"]`, `ledger.py:356-360`), and the row is terminal for the machine. A re-find of a deferred row is recorded and surfaced in the merge output (`refound_deferred`), because the status cannot move. An expiry may be recorded; it has no machine meaning because a held row is already counted open.

## 7. The strongest objection and the answer

Objection. Explicit verification replaces a behaviour that is pinned as a feature with a behaviour nobody has measured. The only prior implementations are single-reviewer variant scripts with "Convergence not proven; no validated winner" (E14); every E2 ledger is round 1 only; B adds a reviewer answer per row at a cost no run has priced; and a reviewer who skips the prior lines turns every re-review into an escalation. A rubber-stamp "resolved" with a plausible quote would also clear a row as easily as silence does, so B could add cost without adding safety.

Answer.

- B does not claim that explicit verification makes loops converge; the variants' lack of a valid result is about convergence and about the surrounding machinery (sweeps, audits, models that changed mid-run, `research/14` 6.1), not about this transition rule. The claim is narrower: a row may not leave `open`-equivalent states on silence. The defect is reproduced at HEAD (E1) and was designed in with a docstring that says the opposite (`ledger.py:112` against `:254-258`).
- The two failure modes are asymmetric. If B's cost estimate is wrong, the result is more rows held and, at worst, an ESCALATE at the 3-review cap with the unanswered rows listed: bounded by `cap_reviews` (`ledger.py:93-96`), visible, and in the direction INV-I names as the repository's priority. If silence-clears is wrong, the result is a defect cleared and a PASS that no later step can see (E1, E4, E5). Without a measurement, the rule whose error is bounded and visible is the safer default.
- A quoted `resolved` is not proof of a correct fix, and B does not say it is. It is an attributed, mechanically checkable claim: the reviewer id and model are in the row history, the quote must occur in the new text (the test already used for anchors), and a quote that does not occur does not clear. Silence has none of these properties. M1 measures how much power the quote check adds; B names M1 as the result that would show it adds none (section 5).
- The cost is mostly already paid. The shipped re-review brief asks for one prior line per blocking row (E3, `INS_B`); the ledger throws the answers away. The new part is the `evidence` string, and the rows that need an answer are the blocking live rows only (E8, E16). Prior-line compliance in existing re-review reports (M2) can be counted before any code is written.
- The pins are a cost of any fix to D-1, not of B alone: `test_cleared_after_the_next_round_and_refound_stays_open` and `test_one_valid_block_is_enough_and_the_invalid_reviewer_is_reported` assert silence-clears by name (research 03 section 2, I-7).
- What B leaves open, stated so it is not read as claimed: one valid reviewer can still answer wrongly (quorum is C-03); the predicate of B6 can flip typed `blocking` values, to be measured by M3; a change in the meaning of `verdict` for stored `review-ledger/1` files is an INV-D question B does not settle (section 4).
