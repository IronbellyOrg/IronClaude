## 1. The position

Position A: the panel's process layer is script-first and advisory-only. Deterministic scripts (no model, stdlib only) build typed pre-pass items; each reviewer receives its assigned items with the script's tool output attached; the core's existing `{assigned, observed}` coverage sidecar and the `coverage_rows` link on a finding are the only assignment container and the only item-to-finding link; class cards (definition, question template, extractor, route, applies_to, instances, known weakness) are module-owned data files, never core constants; every post-run check (citation and quote checks of an item's evidence) is advisory exactly as `verify-citations` is today, so no finding is demoted and no finding the reviewer did not write is promoted; and the recipe text a reviewer reads is written for read-only tools (Read, Grep, Glob, codegraph), with every search that needs a shell done by the script instead. The core ships nothing process-specific that a module could not do without; a module adds a class by adding a card and, where the class is mechanical, one extractor. CB-2 ("list every defect, non-blocking too") is not adopted into the core: the brief's Medium and minor routing stays as shipped, and a module that wants CB-2 declares it in its own brief profile. Whether any extractor ships is decided class by class behind an offline gate that costs no model tokens (section 5), so Position A degrades, by construction, to "the core absorbs only the reusable pieces" if no extractor passes.

## 2. Design consequence for the shared core and the named modules

Shared core (what it contains, and what it deliberately does not):
- Keeps and reuses: the sidecar `{reviewer-<N>: {assigned, observed}}` written as `<output>/panel/coverage.json` and read by `cluster --coverage` and `verify-citations --coverage`; `findings_v2.coverage_context` and the `coverage_rows` check; `findings.flat` as the single normaliser (equal to `verify_cmd._norm`); `verify_cmd._check` as the single citation check. No second container, no second normaliser, no block named "ledger".
- Adds only: (a) a loader and validator for a card file format (fields as in MR2 3.0.3, relayed by research/10 Unit 5); (b) one CLI entry point that runs a module's extractors and writes the per-reviewer sheet and the sidecar's `assigned` lists; (c) an additive advisory flag family in `precheck.json` for item evidence (the evidence paths and quotes the script attached). All three are optional for a module and produce nothing when a module declares no cards.
- Does not add: a per-row verdict block, demotion, promotion, a lens-to-model binding, class constants, or any change to `findings_v1`/`findings_v2` grammar, to `review-ledger/1`, to `derive_verdict` or to the reflect contract.
- Item answers travel through what exists: a reviewer who finds a problem at an item writes a normal finding with `coverage_rows: [<item id>]` (v2 engine) or the same id under an open unknown key such as `probe` (v1 engine, relying on the C-01 outcome that unknown keys stay open); an item with no finding is reported in `observed` through the existing mechanism by which a card reports observed rows (`SKILL.md:345` says "the rows its card reports"; `coverage_context` accepts whatever the caller supplies, `findings_v2.py:196`).
- Telemetry: counts and ids only (`telemetry.py:3`). Item text and anchors live in the run's artifact directory next to `coverage.json`, never in a telemetry record.

Modules (each owns its own cards, extractors and search scope):
- Tasklist review: all eight classes are candidates; first extractors are the ones research/10 Unit 7 marks mechanical (C4 criterion command cannot match, C8 plan edits what a test pins) plus candidate listers for C5 and C2. The search scope (tests, root documents, plan-named paths; `.dev/` excluded) is a module parameter.
- Spec review: E1, E2, E5, E7 per scope slice 06 s19 [UNVERIFIED]; its engine stays v1 under C-01.
- Reflect: reuses its Wave 1B requirement-row extraction for C2 (one capability, not two: research/10 Unit 6 row "Row/item producer"); engine stays v2.
- PR review and rf-qa replacement: extractors E3 and E4 (reverse dependency and whole-tree search) per slice 06 s19 [UNVERIFIED]; for E3 the module may use codegraph callers in the script instead of grep.

## 7. Effect on future PR code review and on the rf-qa replacement

- PR review reads untrusted diffs and needs mechanically read-only reviewers (INV-G; synth-06 FX-8 lists `reflect-reviewer` as the only agent with `permissionMode: plan` and no Bash, [UNVERIFIED line cite; the agent file is verified]). - rf-qa agents run `bypassPermissions` and `/task` lens agents are report-only by prompt (synth-06 CO-31 text read in this session, row 234 [UNVERIFIED beyond that row]); a replacement that adopts the sidecar and the cards reuses the same container as reflect and PR review instead of a third one.

The cost is that each future module writes its own extractors: no extractor exists for any class at HEAD (3.1).

## 8. The strongest objection and the answer

Objection: A has the larger build and the weaker proof of compliance. No extractor exists (research/10 Unit 6 finds producers for none of C1, C3-C8; synth-05 rates the option XL with High risk), the crude selection counts say a blind pick finds the true line 6 to 10 percent of the time, three of the classes (C1, C3, C7) can only be listed, never decided, by a script, and a script that lists 12 items becomes a second source of false positives that occupies the reviewers' time. Without a per-row OK, PROBLEM or UNSURE answer, nothing shows that a reviewer looked at an assigned item: `observed` is a declaration, so a reviewer can rubber-stamp every item and A cannot tell.

Answer:
- Build size. A admits one extractor at a time behind M1, which needs no model run, and the first two candidates (C4, C8) are the classes research/10 Unit 7 marks mechanical and re-readable in recorded reports. If none passes, A has shipped the card loader and the sidecar entry point (synth-05's option 4), not an XL build. The unit of commitment is an extractor, not the design.
- Selection recall. It is the right thing to be afraid of, and it is the gate: M1 is a script run over recorded documents, which the per-row-verdict design cannot offer, because its first gate (`ledger_missing` at most 10 percent) needs a model spike (scope/06 section 6a "Pre-experiment checks") [UNVERIFIED as text]. Failing classes ship as card text only.
- Lister-only classes. A ships them as card text with no extractor and says so; the weaker claim for C1 and C3 is already E2's own (MR2:101, :103, relayed by research/10 Unit 5).
- Second source of false positives. The sheet's items are questions, not findings ("the script never writes a claim", MR2:378 [UNVERIFIED as text]), and advisory-only means a wrong item cannot create a blocking finding or remove one; it can only cost reviewer time, which M4 measures through the non-regression and wrong-blocker figures.
- Unobservable compliance. A per-row verdict is also a self-report: the scope/06 failure-mode rows record that a terse reviewer writes OK rows without doing the steps, and E2's remedy is a cross-check of the `ran` field against transcript tool calls (REQ-28, [UNVERIFIED as text]). In A the evidence is script-made and attached, an item missing from `observed` is visible, and effect is measured by item-linked findings against planted and recorded defects (M2, M3) rather than asserted per row. If M2 shows rubber-stamping, a module can add an optional per-row carrier later under a different noun; nothing in A's core forbids it. What A concedes: until then the core cannot prove that a given item was examined.
