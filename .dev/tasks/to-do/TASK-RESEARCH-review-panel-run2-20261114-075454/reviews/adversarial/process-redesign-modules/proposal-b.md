## 1. The position in one paragraph

The review panel gets a written process in front of the free review, in the shape of the E2 "Recipe Ledger": each reviewer slot is bound to a short list of class recipes (module data), the reviewer answers one row per recipe step in a separate per-reviewer row block (renamed; not "ledger"), a deterministic script checks the quotes in those rows, and the core allows two effects of a failed check: demoting the finding linked to an unsupported PROBLEM row and promoting a PROBLEM row that has no finding as a MINOR non-blocking line. Nothing runs before the review (no pre-pass, no extractor), so the process adds no script that has to be kept in step with each module's documents. The core owns the recipe-card schema, the row-block parser, the row check and the slot key that binds recipes to slots; modules own the cards, the bindings and the switch that turns demotion or promotion on. The recipes are rewritten for the read-only tool set. A third option, "adopt neither until extractors and a hold-out set exist", is not argued here.

## 3. Design consequence for the shared core and the named modules

Core (all optional and data-driven; a profile that sets none of it behaves as today):

1. Recipe cards as module data. Fields from the E2 card (`id`, `name`, `version`, `definition`, `recipe_text` of at most 120 words, `question_template`, `route`, `replicas`, `applies_to`, `instances`, `known_weakness`; [UNVERIFIED], r10 Unit 5, MR2:224-253) plus two this proposal adds: `search_forms` keyed by tool name and `requires_tools`. The `extractor` field is optional and unused. A card file lives with the module that owns the classes; the classes are evidence about one repository and one owner's plan pipeline (r10 Unit 7), so none is a core constant.
2. A slot key `recipes` (a list of card ids) added to `_SLOT_KEYS` (`panel.py:46`, [CODE-VERIFIED]: today `{slot_id, tier, count, strategy, seed}`) and accepted by the slot check that rejects unknown keys (`panel.py:214-216`). The binding is by `slot_id`, never by model name; reviewer ids are `<slot_id>-<i>` (`panel.py:668`). This answers GQ-131 for this position. The key is named `recipes` on purpose: `lens` already means a finding-level vocabulary (`findings_v2.py:36`), `cards` means reviewer cards (`verify_cmd` option `--cards`), `classes` is used for model classes in C-09, and `ledger` is shipped (`ledger.py:1`). (`recipe_name` exists in the swarm lens registry, `cli/swarm/lenses/_validate.py:12`, a different package; no `recipe` word appears in `cli/review` or `tests/review`, [CODE-VERIFIED] by grep.)
3. The brief renderer appends, for a slot with `recipes`, each card's `recipe_text` in the form its tool allowlist can run, and the instruction for the row block. A slot with no `recipes` gets a byte-identical brief.
4. The row block: a fenced block after the findings block with its own info string (provisional `rows-v1`; a grep of `src` and `tests` for `rows-v1`, `checks-v1` and `rowcheck` returns nothing, [CODE-VERIFIED]). Keys `row`, `recipe`, `verdict` (OK / PROBLEM / UNSURE), `quote_plan`, `quote_other`, `problem`, `ran`. The row ids a slot must answer are computed from its recipes (`assigned`); the answered ids are parsed from the block (`observed`). This feeds the existing sidecar `{reviewer_id: {assigned, observed}}` that `cluster` and `verify-citations` already read (`cluster_cmd.py:113-117, 148-151`). In the v2 parser an empty findings block is complete only when every assigned row is observed (`findings_v2.py:291-298`, [CODE-VERIFIED]), so "no findings and every recipe step answered OK" becomes a valid observation, and a reviewer that skips the row block with no findings is `block_ok` false and does not count toward the C-02 quorum. In the v1 parser there is no coverage rule (`findings.py:124-` returns `findings`, `priors`, `errors` only, [CODE-VERIFIED]), so for the spec loop a missing row block is counted as `rows_missing` and changes nothing else.
5. The row check: extend the precheck with a second output file (provisional schema `review-rowcheck/1`) that applies the same whitespace normalisation (`verify_cmd._norm`, `verify_cmd.py:28-29`, equal to `findings.flat`) to `quote_plan` against the candidate and `quote_other` against a snapshot file. `review-precheck/1` and its `reread_set` stay byte-identical. A `quote_other` that is a printed tool line cannot be checked by a file read, so its row gets `check_skipped` and is never demoted.
6. The overlay: a separate pure step reads the cards and `review-rowcheck/1` and writes an overlay file with (a) demotions (finding id, reason) and (b) promotions (a synthesized line: claim = the reviewer's own `problem`, anchor = `quote_plan`, MINOR, non-blocking, tag `src=rows`). Reviewer report files are never edited, nothing is dropped, and the merge reads the overlay only when the profile says `rowcheck: apply`. Rules: a CRITICAL finding is never demoted (C-02 floor); a demotion only lowers that reviewer's own flag; a promoted line is non-blocking so it cannot change a verdict.
7. Telemetry keeps ids and counts only (`rows_total`, `rows_problem`, `rows_missing`, `demoted_n`, `promoted_n`); quotes, `problem` text and anchors stay in run artifacts, not in `review-telemetry/1` (`telemetry.py:3`, [CODE-VERIFIED]: "No document text, quote, anchor or claim ever enters a record").

Modules:

- Spec review loop (v1 engine). The primary target. Gets recipe cards for the plan-review classes; the loop's brief file `document_review_loop_prompts.md` is untouched because the card text is added by the panel brief builder only for slots that carry `recipes`. Profile default `rowcheck: advisory`. CO-24: the grading rule and the Medium routing stay as shipped (brief lines 31-32 send Medium and minor findings to follow-up candidates, [CODE-VERIFIED]); the "list every defect, non-blocking too" aim of E2 CB-2 is carried by the row block, where a PROBLEM row without a finding is listed under follow-up candidates by the report builder (non-blocking rows are already listed, `ledger.py:468`) and promoted into the findings block only when the profile enables promotion. This is a [DESIGN] answer to CO-24, not a finding.
- Tasklist and workflow (via reflect UC-1). Same cards where the class applies. Medium handling stays with X-15.
- Reflect. No `recipes` in any packaged reflect template and `rowcheck: off`, so briefs, `coverage.json` content and verdicts do not change. `reflect-reviewer` already takes a free-form lens in its brief (`reflect-reviewer.md:56`, [CODE-VERIFIED]), so a later profile can pass card text with no agent change; that would be a new decision under INV-L.
- PR review and rf-qa: section 7.

Endangered or left open by this position:

- INV-G (HIGH). The E2 recipes R-C4 ("run it on a scratch string with Bash") and R-C8 (`git grep -l -F`) assume a shell that `reflect-reviewer` lacks (E10; r10 Unit 5). Rule: a card's `requires_tools` must be inside the module's declared reviewer tool list, and a test fails when a card is bound to a slot whose agent lacks a tool the card's only form needs. Cost, stated plainly: for a read-only slot C4 loses its script-run test and keeps only a Grep form of the same pattern, whose equivalence to the shell dialect is [UNVERIFIED]. The `ran` self-report cannot be cross-checked against tool calls until the transcript adapter of C-08 exists, so in this proposal `ran` is recorded and unverified.
- INV-I (fail-closed). Demotion moves a row toward the false-negative side. Containment: off by default, never on CRITICAL, only the demoted reviewer's own flag, `check_skipped` for unverifiable quotes, and the demoted finding stays visible in follow-up candidates with its reason. Whether that is enough is the objection in section 8.
- INV-C in the v1 engine only through the C-01 outcome: "observed is computed" works in the v2 parser (E7) and not in the v1 parser, so the spec loop gets a weaker check than reflect.
- INV-H at the file level: `rows-v1` content and `review-rowcheck/1` carry quotes and `problem` text. They are run artifacts. A test is needed that no telemetry record serialises them (INV-H is a convention today, enforced only for `context` values, `telemetry.py:243-251`, per r10).

## 7. Effect on future PR code review and rf-qa replacement

PR code review. The finding format has a closed lens vocabulary (`findings_v2.py:36`: `spec`, `reflect-pre`, `reflect-post`; `LENSES` check at `:143-145`, [CODE-VERIFIED]) and the `Finding` dataclass has no lens or row field (r13 line 41 [UNVERIFIED]). Under B, a code-review lens is a recipe card (for example a "changed code breaks a pinned test" recipe, the PR form of class C8, using `codegraph_callers` which is in the read-only list) bound to a slot through `recipes`; no new finding field is needed. Rows never reach `pr_submit`: the adapter of C-10 would take findings only, and a promoted `src=rows` line is MINOR non-blocking and can be discarded or mapped to a Low hint. This leaves `Finding`, `Severity` and the FSM untouched (INV-E).

rf-qa replacement. r13 lists three needs for the `/task` gate: a mechanically read-only reviewer, a checklist output mode with a computed confidence, and a per-slot lens with an agent-count rule (R1, R2, R3). B supplies the second and the lens half of the third with one mechanism: the row verdicts OK, UNSURE and a missing row map onto the rf-qa marks `[x]`, `[?]` and `[ ]` (E12), and `recipes` is the per-slot restricted checklist (E11). That mapping is a [DESIGN] inference, not a tested equivalence. B does not supply the agent-count floors, the read-only change of the `/task` lens agents (owner question Q3 of C-11) or the replay oracle; it neither blocks nor decides slot C-11. The rf-qa tool-engagement minimum (Read, Grep and Glob calls at least TOTAL, r13) needs the transcript adapter and is outside this proposal.

## 8. The strongest objection and the answer

Objection (the strongest form A can take): the Recipe Ledger asks the model to police itself. It adds a second per-reviewer duty in round 1, it can fail by compliance (`ledger_missing`) and by exactness (a row needs two quotes, and E2's own planning figure is 0.914 x 0.914 = 0.835 per row, [UNVERIFIED], r10 Unit 10), a class can live in one reviewer only, and the only consequence the core adds is demotion of a reviewer's flag on a failed quote check. That demotion can turn a real blocker into PASS because a quote lost a whitespace or an escape, which is the false-negative side that C-03 chose union and fail-closed to avoid, and promotion writes a finding the reviewer did not write, against a precheck that is advisory and a validator that alone drops (`verify_cmd.py:11-12`, [CODE-VERIFIED]). The Sweep Sheet has no such exposure: the script never writes a claim and checks are advisory.

Answer. (1) The core consequence is smaller than the objection assumes: B puts no behaviour in the core that a profile does not switch on. Demotion and promotion are reserved in the schema and off in every packaged profile; "allowed" means the core can carry them, not that any module uses them before M-B3 passes. (2) The exactness risk is a measured-later number, and the design already prefers the safe direction: only a file-checkable quote can demote; tool-line quotes are `check_skipped`; nothing is dropped, so the finding stays in follow-up candidates with the reason; CRITICAL is exempt; and under the C-03 union a second reviewer's blocking flag keeps the cluster blocking. The case left is a single-reporter, non-CRITICAL finding with a failing quote, and for that case the answer is the switch and M-B3, not an argument. (3) Compliance is no worse placed than the existing prior-line duty C-02 already accepts, it is spent in round 1 only, and a missing block is a counted event, not a failed round, except through the empty-block rule where it correctly refuses to count an unobserved empty report. (4) Promotion's conflict with "the validator alone drops" is not a conflict about dropping: a promoted line is MINOR, non-blocking, tagged `src=rows`, carries the reviewer's own words and cannot change a verdict. Whether the core may carry it at all is GQ-130 and remains open; this proposal's position is only that carrying it behind a switch costs less than rebuilding a second assignment container and normaliser later (r10 Unit 6). (5) What B cannot answer from evidence: that RL beats SS, that RL beats a plain checklist K, or that any threshold is right. No arm has run, and the answer to the objection is the arms in section 6.
