### 2.1 The row block

What it is. A record-only fenced block written by the reviewer, with its own info string `rows-v1`, one row per assigned item. The name is provisional and subject to the collision rule: `recipes` is excluded because `cli/swarm/recipes/` exists (F7); a grep for `rows-v1`, `rowcheck` and `row_block` over `src/superclaude` returned no hit [VERIFIED, advocate B, Round 2]. Row fields: `row`, `class`, `verdict` (OK, PROBLEM, UNSURE), optional `quote_plan`, `quote_other`, `problem`, `ran`.

Limits. The values below are Variant B's Round 2 proposal (R2B component 2): `quote_plan` 12 to 200 flattened characters; `quote_other` at most 200 and checked only when 12 or more; `problem` at most 300; the row cap per reviewer set by the module, with fixtures for 0, 1 and N rows. Advocate A did not accept or reject these values; A asked only that rows have their own limit and a rule for an over-length quote (R2A section 8 item 6). The boundaries are open (IP INV-009 and INV-010). A bad row line is an error line in the row parser's own output and never invalidates the findings block; a truncated row block never invalidates a complete findings block (R2A item 3; R2B component 2).

Placement. Before the findings block in the v1 spec loop: the loop prompt says "end the report with the findings block" (`document_review_loop_prompts.md:33`) and "The last section of every review report is `## Findings block` ... holding one JSON object per line and nothing else" (`:58`); the row block sits under its own heading (R2B section 4.1 (iii)). After the findings block in the v2 engine: precedent is the `reviewer_model_self_report` line appended after the block (`reviewer-spec.md:39`) and the fenced `yaml` calibration block written after it (`SKILL.md:344`), and `_blocks_after` keeps only fences whose info string equals the requested one (`findings.py:73`). D-4 (placement per engine) is CLOSED by agreement and is pinned by the G-0 test that a row fence leaves both parsers' results identical. The price in v1 is more truncation exposure for the findings block, mitigated by a row cap and one-line rows (R2B section 4.1 (iii), section 9 item 8); the residual path is IP INV-011.

`observed`. It is computed from the parsed rows and is never declared by an orchestrator (R2A item 3). Who runs that computation is open (2.2).

Consequence. The hard consequence of the rows exists only for an EMPTY findings block: `findings_v2.py:291-298` consults the observed rows only inside `if closed and not res["errors"] and not res["findings"]`, and the loop at `:264-290` checks `coverage_rows` against `assigned` and never against `observed` (F1). One finding plus zero rows is valid, so the row block does not prove that a reviewer examined an item (R2A section 8 item 1; R2B section 9 item 1). Proposal B's defence, which A did not contest: the floor sits at the clean report, the case that turns into a PASS, and a reviewer who writes one finding has at least shown reading (R2B section 3.2). In the v1 engine there is no coverage rule at all (`findings.py:124-` returns findings, priors and errors only, [CODE-VERIFIED] by Proposal B's author), so on the v1 loop nothing computes `observed` and nothing refuses a report (R2B component 18).

Open items. D-6: does UNSURE count as observed? Proposal B says yes, with `rows_unsure` visible; A did not decide (IP INV-008, LOW). Unaddressed gaps in the row grammar, each recorded by the invariant probe: INV-006 (no row-id grammar or type rule; recorded ids are 667 `INF-N`, 23 `FR-N`, slug ids, one containing `/` and one range token; a non-string id aborts a whole command); INV-007 (no row field carries the path or the quote kind, so snapshot membership and tool-line skipping cannot be decided from the row; `ran` has no bound; unknown row keys unspecified); INV-010 (three quote boundaries disagree: short literals below 12, whole-candidate test versus the line-window basis of the measured failure rates, and a short `quote_other` silently unchecked while a short `quote_plan` is an error); INV-014 (how a card yields a definite list of row ids, the loader outcome for a bad card, and the rule for a duplicate row id are not specified; both finding parsers reject duplicate ids).
