## 1. The position

The shared core launches nothing. It resolves a panel and prints, per reviewer, the intended model and a `launch` value that is one of the Claude Code class words (`sonnet`, `opus`, `haiku`, `fable`); the orchestrator turns that value into the `model` argument of one Agent call to a read-only reviewer agent (`reflect-reviewer` and agents built on its pattern). Gateway models are reachable in exactly two ways: as what a class word resolves to in the session environment (`ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL` set to a tier alias or a raw model id before the session starts), and through the swarm HTTP transport that already exists in the reflect engine. The `gateway` environment gets its missing `launch` entries by a data edit (model id to class word), the reflect profile ceiling (`panel.py:72`, three class words, three reviewers) stays as it is, and no `claude -p --model <raw id>` launcher, identity wrapper or fallback ladder is added to the core. Whether the model that ran is the model that was intended is answered after the fact from the transcript (`message.model` of the sidechain, with the Agent result `resolvedModel` as a collapse detector), and that capture is the work of slot C-08, not of a launcher. The position trades reach (any gateway model, any panel size) for the one property the research calls a HARD design point: reviewers that are read-only by construction, not by prompt.

## 7. The strongest objection and my answer

**Objection.** Class words cannot name tier-2b, tier-3, tier-4 or non-first-slot models (E6, E5); the same word means a different model in a different workspace (r04 section 3.5); the environment map is fixed when the session starts, so a panel's model choice depends on whoever launched the session; a seven-reviewer `live7` panel has seven models and four class words; and E2's best panels need gateway models that the product cannot launch. A core that stays class-word only keeps C-S6 unsolved: the product still cannot launch a gateway panel.

**Answer.**
1. Reach is not zero and is observed. Six recorded runs (D1-D3, E1-E3) served `gpt-6-luna` and, for a non-first-slot model, `claude-haiku-5-5` through the three class words (E4). The map is set by the launching environment, which is already how the shadow combos were run.
2. The launcher-side dependency is real and B says so: the resolver cannot make the session export the right `ANTHROPIC_DEFAULT_*_MODEL`. The check is after the fact: the resolution pins the intended model (`panel.py:674`) independently of any env variable (r04 section 4.1), and the served model is read from the transcript. A raw-id launch has the same after-the-fact limit, because the shim fails over named ids and E2's ladder overwrote its own expectation (E7).
3. The ceiling is not a gap for reflect: three reviewers and three class words are the same limit (E13), and E2's evaluated panels are three reviewers (E14). The `--env gateway` refusal comes from an empty data map, not from the ceiling, so the data edit removes it without relaxing the profile.
4. `live7` has no launcher under either position and no consumer reaches panel code today (CO-26); under B it is reachable only through the swarm transport, which is text-only and sees the tasklist body, not the diff or spec (`ensemble.py:601-630`, r04 option 3). B accepts that cost.
5. What B refuses is putting a launcher in the core. Raw-id reach already exists where an engine needs it (`ClaudeProcess` with `--model`, E9; the swarm transport). Under B it stays there, so the core's read-only claim can be checked by one rule (E1).
6. The residual B accepts: tool-grounded reviewers on more than three distinct gateway models are out of reach until an engine adds them, and any workspace that cannot export the class map before launch cannot run a gateway panel through the core.
