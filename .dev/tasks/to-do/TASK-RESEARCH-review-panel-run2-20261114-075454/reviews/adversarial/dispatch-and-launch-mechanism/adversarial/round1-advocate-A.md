## Position summary
Variant 1 is right that a class-word-only core cannot be the whole answer for gateway panels: a class word does not name a model, the binding is set per session, and nothing mechanical forces the orchestrator to pass it. Variant 2 is right about what reflect should ship first: the ceiling stays, and read-only comes from the agent file until a process-level probe passes. My calibrated end state is a staged hybrid: B's dispatch contract now, A's id-based adapters as data and a launcher that is not admitted past the reflect ceiling until M-2 passes.

## Steelman of Variant 2

The strongest version of Proposal B runs as follows. The one property the research calls HARD is that reviewers are read-only by construction (INV-G, HIGH). Exactly one path has it today: an agent file whose `tools:` allowlist has no Bash, Edit, Write or Task and whose `permissionMode` is `plan` (`src/superclaude/agents/reflect-reviewer.md:5-8` [VERIFIED]), pinned by a static test (`tests/cli/reflect/test_reviewer_readonly_tools.py:59-66, 78-86` [VERIFIED]). The raw-id launcher that exists as evidence runs `bypassPermissions` and disallows only `Edit Write NotebookEdit`, so Bash stays open (E2:48 [VERIFIED]). The process-level alternative (`--restricted`, `--tools`) has never been run against a gateway id (v1:33, [UNVERIFIED]).

The reach cost is smaller than it looks. The reflect profile is capped at 3 reviewers and 3 launch words (`panel.py:72-73` [VERIFIED]), and E2's evaluated panels also had 3 reviewers (v2:46, [UNVERIFIED by me]). In 15 recorded runs, class words did reach `gpt-6-luna` and the non-first-slot `claude-haiku-5-5` (`.dev/eval-workspaces/shadow-model-combos/results.jsonl`, field `reviewer_requested_served`, my `jq` [OBSERVED]). The `--env gateway` refusal comes from an empty `launch` map (`review-tiers.default.json:29`; `panel.py:153-156` [VERIFIED]), not from the ceiling. Filling the map is a data edit.

A raw-id launch has no identity advantage either. The shim fails over named ids, and E2's ladder reassigns `MODEL` (E2:74-77 [VERIFIED]). The check that catches either is a transcript read, which both paths can do. A raw-id substrate already exists where an engine needs it: `ClaudeProcess` adds `--model` (`src/superclaude/cli/pipeline/process.py:163-164` [VERIFIED]) and has a restricted `reviewer_profile` (`:150-154` [VERIFIED]). B keeps launching out of the core, so the core's safety claim is checkable by one rule. B also contributes things A lacks: a dispatch-error rule for a missing `model` argument, a collapse-detector replay with a prediction that can fail, and the only head-to-head experiment proposed. B is also right on three factual points against A: X-003, X-006 and C-007.

## Strengths claimed (Variant 1)
1. **A model id is the only stable address; a class word is a per-session alias.** In the 15 recorded combo runs the same word was served different models depending on how the launching session was set up: `haiku` was served `gpt-6.1-sol` (combos A and B), `claude-haiku-5-5` (C and D) and `gpt-6-luna` (E); `opus` was served `claude-opus-5-5` (A to C) and `gpt-6-luna` (D and E) (`results.jsonl`, `reviewer_requested_served`, my `jq` [OBSERVED]). A per-model-id adapter does not depend on that binding. B's single packaged `gateway.launch` map (v2:18) must pick one binding for every gateway session, and `select_env` returns `gateway` for any session that has `T3Model01` set (`panel.py:485-494` [VERIFIED]). The resolution would print `model: gpt-6-luna, launch: opus` in sessions where `opus` is `claude-opus-5-5`, and nothing in the core would notice.
2. **Reach is bounded by the enum, not by taste.** `docs/reference/model-aliases.md:48` says the Agent `model` parameter takes `sonnet`, `opus`, `haiku` or `fable` and cannot take a full model id [VERIFIED]. The packaged tier file lists 13 models in `classes` and one is Fable (`review-tiers.default.json:18-23` [VERIFIED]); the reflect profile excludes Fable (`panel.py:122-123` [VERIFIED]). So 12 models share 3 usable words. Tier 3 is `glm-5.3` and `Qwen3.8-max` only (`review-tiers.default.json:9` [VERIFIED]); a session can bind at most 3 of the 12 at once. B's observed reach (point 1 above) shows a hand-built session environment can bind three words; it does not show the product can name a given model.
3. **A launched `--model` argument cannot be dropped by the orchestrator.** Run A-r3 dispatched three reviewers with no `model` (`reviewer_requested_served` is `[null, claude-sonnet-5-5]` three times, `results.jsonl` row A-r3 [OBSERVED]). B's answer is a rule that a missing argument is a dispatch error (v2:19), and no code anywhere enforces it: the product launches nothing, so the rule lives in prose that an orchestrator must follow. With `claude-p` the id is in argv, set by Python. A closes this failure for gateway reviewers; B closes it only after the fact by a replay (v2:81).
4. **The additive `adapters` form moves no frozen test.** `tests/review/test_review_panel.py:303-308` pins `launch is None` for every gateway reviewer [VERIFIED]; A leaves `gateway.launch` as `{}` (`review-tiers.default.json:29` [VERIFIED]) so the pin passes as written (X-002). `test_review_panel_reflect_profile.py:183-189` (a `fable` launch is rejected) is unaffected [VERIFIED]. B edits the gateway pin (v2:72).
5. **The reflect ceiling is a template-class rule, not a limit of `resolve`.** A generic panel already resolves `"launch": {"acme-1": "acme-launcher"}` (`test_review_panel.py:243-257` [VERIFIED]); only `reflect-*` checks `launch` against `_REFLECT_LAUNCH` (`panel.py:153-156` [VERIFIED]). A new launch kind is therefore an extension that existing generic code paths already accommodate, not a new idea in `resolve`.
6. **A names a falsifiable probe for the HIGH invariant and says what it does if the probe fails.** M-2 (v1:68) runs a brief that tells the reviewer to run a shell command and write a file, on a gateway id and on `sonnet`, and checks the transcript and `git status`. B proposes no dynamic read-only test for any path: `test_reviewer_readonly_tools.py:12` itself says the dynamic no-mutation test is "deferred (producer absent)" [VERIFIED]. M-2 is worth adopting even if B's dispatch wins, because it tests the agent-class path too.
7. **Identity is judged per attempt against the id requested for that attempt.** `E2:56` compares the observed model with the current `$MODEL` and `E2:58` records it. The product launcher records `model_requested` and `model_observed` per attempt, including the fields CO-11 already decided (v1:19). The orchestrator-written `model_observed:` header on a shadow card (`SKILL.md:341` [VERIFIED]) is a prose instruction, not a recorder; no Python source in `src/superclaude` reads `model_observed` except as a SQL column (`telemetry.py:364,378` [VERIFIED]).

## Weaknesses identified in Variant 2
1. **The map B fills is a static claim about a dynamic binding, and the resolver would pin the wrong intended model.** B's data edit puts model-to-word pairs "that the launching environment exports" in the packaged file (v2:18). The shadow protocol copies `model:` verbatim from `reviewers[N].model` of the resolution and treats the harness-reported model only as an extra `model_observed:` line (`SKILL.md:341` [VERIFIED]). Strength 1 shows the binding differs between sessions, so under B a mismatch between pinned and observed is built in whenever the session binding differs from the packaged map. B has no test that the session binding matches the map; its test list (v2:78-85) checks that `launch` is present, not that it is true.
2. **Nothing checks that the map is one-to-one.** `_check_reflect_resolution` only tests that each `launch` is in the allowed set (`panel.py:147-156` [VERIFIED]). `distinct_across_slots` excludes a repeated model id, not a repeated launch word (`panel.py:631-635` [VERIFIED]). If two distinct gateway models are mapped to the same word, the panel has distinct ids on paper and one served model in fact, which is the A-r3 collapse made systematic. With 12 usable models and 3 words (Strength 2), a one-to-one map cannot cover the file, so collisions are likely unless a test forbids them. B proposes no such test.
3. **The dispatch-error rule has no enforcer, and the only observed failure of it was a prose-level miss.** The rule (v2:19) is addressed to an orchestrator model. A-r3 is the recorded case of the orchestrator omitting the argument [OBSERVED]. B's detector (v2:81) is a replay over finished logs; it runs after the panel has voted. B's own count of "0 of 12 under the tier-1b orchestrator" is [UNVERIFIED by me]; with n=15 and 1 failure the sample is too small to call the failure rare.
4. **B's after-the-fact identity capture is unbuilt and unverified, so B's identity story is currently a plan.** B routes it to C-08 through `SubagentStop` (`agent_transcript_path`) and marks it [UNVERIFIED] (v2:47, 84). `hooks.json:179` registers `SubagentStop` for a freshness counter only (`src/superclaude/hooks/scripts/freshness-subagent-stop.sh:2` [VERIFIED]); no file under `src/superclaude/hooks` captures a transcript path (`grep SubagentStop` over that directory returned only those two hits [VERIFIED]).
5. **The reach B accepts leaves a real consumer unserved.** B concedes `live7` and any PR panel with more than 3 or 4 gateway models are out of reach (v2:102, 104). `live7` lists 7 reviewers over tiers 1b, 2, 2b, 3 and 4 (`src/superclaude/cli/review/data/review-panel.live7.json:5` [VERIFIED]). That is a shipped template that resolves in gateway and cannot be launched by the product under B.
6. **B's read-only claim is narrower than it sounds.** It is true for agent files; B itself lists the `ClaudeProcess` children (restriction is a permission-flag omission, effective surface unrun) and `/task` lens agents as open (v2:41, 64). `process.py:150-154` passes no tool allowlist in the reviewer profile [VERIFIED], so what such a child may run depends on the user and project settings that apply (my inference from the argv, not run). So "checkable by one rule" holds for the agent-file path only; for every other path B hands the risk to whoever owns that engine.
7. **Two factual misstatements about A.** X-002: B says A rewrites the gateway-null test (v2:72); A's additive form leaves it passing (`test_review_panel.py:303-308` [VERIFIED]). X-007: B says it found no test for the reviewer tools list (v2:83); `tests/cli/reflect/test_reviewer_readonly_tools.py` exists [VERIFIED]. These are minor, but they show B was not checked against the test tree.

## Concessions
1. **X-009 is a real defect in A and the fix is small.** `_check_reflect_resolution` as A specifies it accepts any reviewer whose `adapter` is `claude-p` (v1:18). It does not read `read_only`, so the reflect module, whose reviewer is defined as unable to mutate the repo, would admit an unproven reviewer. A's prose promises a module-level refusal but names no code location. The fix is to accept `claude-p` at `panel.py:153-156` only when the data marker says `read_only: proven`, and until M-2 passes to leave `_REFLECT_LAUNCH` as it is. That fix makes A's reflect behaviour identical to B's for now.
2. **X-008 is real: the E2 identity evidence does not transfer to the read-only adapter.** E2's command is `--permission-mode bypassPermissions --disallowedTools Edit Write NotebookEdit` (E2:48 [VERIFIED]). Per the research file as quoted in the diff analysis, `--restricted` refuses `bypassPermissions` (da:45, w02:124 [UNVERIFIED by me]). If so, M-1 has to be run with the restricted flag set, and A's cited G14 audit result (v1:29) says nothing about it. M-1 is not yet evidence for the adapter A actually proposes.
3. **A overstated the E2 ladder defect (X-005).** In E2, `run_attempt` records `expected_model` as the current `$MODEL` (E2:58) and the ladder writes `FALLBACK $MODEL -> $NEXT` to a log (E2:75 [VERIFIED]); the reassignment is at E2:76 [VERIFIED]. A fallback is therefore not silent. What is lost is the original slot id in the per-attempt meta file, which makes `MODEL_OK` mean "served what this attempt asked for" and not "served what the panel asked for". A's wording "judged against itself" (v1:30) is right but "a silent swap passes" is too strong.
4. **A's "no check at all today" for the class-word path (v1:78) is too strong.** The shadow protocol already tells the orchestrator to write an extra `model_observed:` line when the harness reports a different model (`SKILL.md:341` [VERIFIED]), and the results table was built by reading sidechain transcripts of the Agent path. The claim that survives: no code in the product records or validates it (`telemetry.py:364,378` hold only a column; `grep model_observed src/superclaude` finds no writer [VERIFIED]).
5. **A's `agent-class` adapter is not a launcher.** The Agent call is made by the orchestrator, not by Python. A's "launcher module takes one resolved reviewer, runs the adapter and returns one outcome row per attempt" (v1:19) is implementable for `claude-p` only. For `agent-class`, the module can at most read a transcript. This was not flagged by the diff analysis. It means A's closed set of two adapters is, in code, one launcher plus B's dispatch rule, and A's cost for the agent-class half of the design is zero new code.
6. **X-003: A's wording on D4 is partly wrong.** `SKILL.md:320` lists "gateway" as its own unsupported cell, separately from "a null `launch`" [VERIFIED]. Filling `gateway.launch` would not by itself stop D4 firing. And since D4 lists gateway, A's additive design also needs a D4 edit before a gateway cell launches in reflect (A-005). A is right that the additive form moves no pin; B is right that D4's trigger is not solely `launch`.
7. **C-007: A should build on `ClaudeProcess`, not on a rewrite of E2's shell.** `ClaudeProcess.build_command` already passes `--model` (`process.py:163-164` [VERIFIED]) and `ensemble.py:541` and `runner.py:553` already use it with `model=config.model` [VERIFIED]. A's statement that `cli/review` "gains its first model-launching subprocess" (v1:49) is true only of that package. A new launcher that duplicates `ClaudeProcess` is avoidable code.
8. **Until M-2 passes, A and B ship the same thing.** A says so itself: PR review uses `agent-class` until M-2 (v1:61), and if M-2 fails A is "close to Position B's end state plus an unused launcher" (v1:68). A's advantage is the option value of an id-addressed path, paid for by an unmeasured launcher (M-4 cost not run) and by `claude -p` children that load the host's hooks (v1:61, [UNVERIFIED by me]).
9. **A also leaves `live7` unserved for any module that needs read-only reviewers** (INV-G), until M-2 passes. It is not a point against B alone.

## Shared assumption responses
- **A-001 (Claude Code behaviours the repo does not pin): QUALIFY.** Both variants depend on it, but not equally. B's path additionally depends on a session-level environment (`ANTHROPIC_DEFAULT_*_MODEL`) that the resolver cannot set or read, and that varied across the 15 combo runs (Strength 1). A's `claude-p` path depends on flag behaviour and the transcript field. Neither has a pin; the class-word path carries one more unpinned input.
- **A-002 (`message.model` is a truthful served-model signal, no second source needed): QUALIFY.** The combo table shows the field is not an echo of the request (requested `haiku`, observed `gpt-6.1-sol`; `results.jsonl` [OBSERVED]), which is evidence it carries the served id. It is not proof it survives shim failover; the audit that found two `luna2` runs served by `terra` is not committed at raw level (v1:29, [UNVERIFIED]). Any independence claim built on it (C-03 condition 5) needs a second check, for example the shim's own log, before it is a gate. Both variants share this gap.
- **A-003 (a static allowlist or flag keeps a non-Claude served model from mutating the repo): QUALIFY.** Plausibly true because the harness filters tools client-side, but nobody has run it. The only repo guard is static: `test_reviewer_readonly_tools.py:12` says the dynamic test is "deferred (producer absent)" [VERIFIED], and the test does not check `permissionMode` (no match for it in the file [VERIFIED]). A tests it for `claude-p` only (M-2); B for neither path. Run M-2 on the agent-class path as well; it costs one extra launch.
- **A-004 (three reviewers is the right cap): QUALIFY.** Accept the cap (`panel.py:73` [VERIFIED]). Reject the way B uses it: B needs the number of reviewers to equal the number of usable class words (3) and a one-to-one map from 12 non-Fable models onto them (`review-tiers.default.json:18-23` [VERIFIED]), and no test requires the one-to-one part (Weakness 2). A keeps the cap but does not depend on that coincidence.
- **A-005 (shadow runs use `--env anthropic-only`, so neither change is exercised by shadow evidence; D4 lists gateway): ACCEPT.** Shadow step 1 passes `--env anthropic-only` literally (`SKILL.md:340` [VERIFIED]), and D4 lists gateway as unsupported (`SKILL.md:320` [VERIFIED]). Neither the `adapters` map nor a filled `gateway.launch` is exercised by shadow, and neither proposal says who edits D4. Evidence for either design must come from a gateway-env test and the head-to-head, not from shadow runs.
- **A-006 (the orchestrator reliably carries out the dispatch rule): REJECT as stated, and it is a point for A on the `claude-p` path only.** Run A-r3 contradicts it (`[null, claude-sonnet-5-5]` three times, `results.jsonl` [OBSERVED]). A makes the model argument mechanical for `claude-p` (Python builds argv). For the `agent-class` path A has the same dependence as B, and neither makes it mechanical; the only enforcer on offer is a replay detector (B) or a post-launch transcript check (A).
