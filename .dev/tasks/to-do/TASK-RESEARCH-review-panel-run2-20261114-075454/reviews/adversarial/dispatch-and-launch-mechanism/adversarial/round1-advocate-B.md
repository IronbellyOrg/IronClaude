## Position summary

Variant 2 is the better core for the consumers that matter first (reflect and rf-qa replacement), because those need reviewers that cannot mutate the repo, and the only path with a repo-owned, test-pinned read-only property is the agent-file path; Variant 2 keeps the core launch-free and fixes the `--env gateway` refusal with one data edit. Variant 1 is better on reach (any gateway id), on being concrete about served-model recording, and on how it formats its tests; I concede those, and I concede that Variant 2 misdescribed Variant 1 on the test pin (X-002) and missed an existing read-only test (X-007). The calibrated end state is Variant 2 now, with Variant 1's M-1/M-2 probes kept as the entry gate for any later raw-id adapter.

## Steelman of Variant 1

The strongest version of Proposal A: the product today can resolve a gateway panel but cannot launch one, and the class-word path is a poor stand-in for model choice. A class word is an environment-dependent alias, not a model. In the recorded combo runs the same word was served different models (`haiku` served `gpt-6.1-sol` in five calls, `opus` served `gpt-6-luna`), and run A-r3 collapsed six dispatches onto one model after the orchestrator dropped the `model` argument while the contract still said `calibrator_diversity: full` [CARRIED from variant-1 point 4 and variant-2 E5/E11]. The Agent `model` argument is an enum of four words, so tier-2b, tier-3, tier-4 and non-first-slot models cannot be named at all [CARRIED, variant-1 point 3; variant-2 E6 concedes it]. A raw-id launcher names the model, and E2 showed it can read `message.model` per attempt and compare it to the id requested for that attempt (`run-reviewer.sh:51,56`, [VERIFIED] this session via `git show 6c09843`). A also does something B does not: it names the read-only cost honestly. It marks `claude-p` as `read_only: unproven`, makes the module that needs INV-G refuse such a reviewer, keeps `agent-class` as the default for untrusted diffs, and puts a falsifiable probe (M-2) in front of the claim. Its additive `adapters` map is a careful way to add a concept without moving the pinned gateway-null test (`tests/review/test_review_panel.py:303-308`, [VERIFIED]). What it gets right that B cannot match: if an owner wants a panel built from more than three or four distinct gateway models, or from a workspace that cannot export the class map before launch, only a raw-id path reaches it, and A is the only position that designs for that and for the shim failover on named ids (variant-1 point 7, [CARRIED]).

## Strengths claimed (Variant 2)

1. **Read-only by construction is repo-owned and test-pinned on the path B keeps.** `reflect-reviewer.md:5-8` has a `tools:` allowlist with Read, Grep, Glob and read-only search/codegraph tools and no Bash, Edit, Write or Task, plus `permissionMode: plan` [VERIFIED]. `tests/cli/reflect/test_reviewer_readonly_tools.py` pins the allowlist: mutator set `{Bash, Edit, Write, NotebookEdit, Task}` (`:30`), required core `{Read, Grep, Glob}` (`:32`), guard `_is_readonly_safe` (`:59-66`), composite test (`:100-103`) [VERIFIED]. Variant 2 said it found no such test; that was wrong for the tools list (see Concessions), and the correction makes B's strongest claim stronger, not weaker. The same file says the dynamic no-mutation test is deferred (`:12`), so the pin is static [VERIFIED].
2. **The gateway refusal is a data gap, not a ceiling.** `_REFLECT_LAUNCH = ("sonnet", "opus", "haiku")` and `_REFLECT_MAX_REVIEWERS = 3` (`panel.py:72-73`); `_check_reflect_resolution` rejects any reviewer whose `launch` is not in that tuple (`panel.py:153-156`); `environments.gateway.launch` is `{}` (`review-tiers.default.json:29`) while `anthropic-only.launch` shows the intended form (`:35`) [VERIFIED]. Filling the map removes the refusal with no code change and no relaxation of the 3-cap, Fable, or classes rules (`panel.py:143-152`).
3. **Class words have reached gateway models in practice.** B's `jq` over `results.jsonl` shows runs D1-D3 and E1-E3 serving `gpt-6-luna` through `opus`, and `claude-haiku-5-5` (the second model of tier 4) through `sonnet` [CARRIED from variant-2 E4; I did not re-run the `jq`]. 4. **The identity check is not a property of the raw-id path.** Both paths read the same transcript field. E2 reads `message.model` at `run-reviewer.sh:51` [VERIFIED]; B's served-model table was read from sidechain transcripts of the Agent path [CARRIED, variant-2 E4]. In product code neither exists: the only `model_observed` hits under `src/superclaude/cli` are two SQL column references in `cli/review/telemetry.py:364,378`, and no `message.model` read exists [VERIFIED by grep this session, negative]. 5. **The raw-id path does not buy identity assurance as built.** `run-reviewer.sh:75-76` logs `FALLBACK` then sets `MODEL="$NEXT"`; `:58` writes `expected_model=$MODEL` (the fallback) and `:56` compares against the current `$MODEL`, so `MODEL_OK` is relative to the ladder step [VERIFIED]. The shim also fails over named ids [CARRIED, variant-1 point 7 and variant-2 E7], so a raw id is a request, not a guarantee.
6. **A's own evidence does not transfer to A's own read-only adapter (X-008).** The E2 identity check ran under `--permission-mode bypassPermissions --disallowedTools Edit Write NotebookEdit` (`run-reviewer.sh:48`, [VERIFIED]). The candidate read-only flag `--restricted` "refuses `bypassPermissions`" and "loads only managed settings and `--settings`" (`research/web-02-claude-code-hooks-headless.md:124`, [VERIFIED]; `:125` says the version gate was not checked locally). So the identity results from E2 cannot stand in for a restricted launch; M-1 would have to be rerun under the restricted flags, which A's M-1 does not say.
7. **The core stays launch-free and deterministic.** `resolve` is pinned as byte-identical for equal inputs (`tests/review/test_review_panel.py:294-300`, [VERIFIED]) and `cli/review` has no model-launching subprocess (negative evidence from variant-2 E10 and the diff analysis [CARRIED]; the `ClaudeProcess` callers I read are in `cli/reflect`). Adding a launcher module, a second map, a second constant, a `read_only` marker and a probe is a larger change surface than one data edit and one test rewrite.

If a raw-id reviewer is ever needed, the extension point is that class, not a second copy of E2's script in the core. (Scope limit in Concessions.)

## Weaknesses identified in Variant 1

1. **The `agent-class` adapter has no executor in A's design.** A section 1 defines `agent-class` as "the orchestrator's Agent call"; A section 2 says the new launcher module "takes one resolved reviewer, runs the adapter, reads the transcript, and returns one outcome row" and that "every launch, under either adapter, ends in a transcript identity check". A Python module in `cli/review` cannot make an Agent-tool call (the Agent call is made by the orchestrating model in-session; the only subprocess in `cli/review` is `git rev-parse`, [CARRIED, variant-2 E10]). So for `agent-class` the module can at most read a transcript afterwards, which is B's position plus a recorder; the "closed set of two adapters, chosen per reviewer" is one code path and one prose rule. [INFERENCE from A sections 1-2 and the Agent tool's nature; A does not say which code runs `agent-class`.]
2. **A widens the reflect ceiling before the read-only condition is checked (X-009).** The current check reads only `launch` (`panel.py:153-156`, [VERIFIED]). A's change accepts `adapter == claude-p`; A does not say that the check reads the `read_only` marker, only that "a module that requires INV-G must refuse such a reviewer" (variant-1 section 4), without naming where in code. Reflect's reviewer is the module defined as unable to mutate the repo (`reflect-reviewer.md:3` description, `test_reviewer_readonly_tools.py` docstring `:1-12`, [VERIFIED]). Until M-2 passes, the widened ceiling admits a reviewer the module's own contract forbids.
3. **Identity evidence does not carry to the read-only adapter (X-008).** See Strength 6. A's M-1 (five gateway ids, three attempts) is specified for `claude-p` but E2's verified flags (`run-reviewer.sh:48`) cannot be the flags of the read-only adapter, because `--restricted` refuses `bypassPermissions` (`web-02:124`, [VERIFIED]). So for reflect, PR review of untrusted diffs and rf-qa, the three INV-G consumers, the `claude-p` launcher has no admissible use today; it serves modules that do not need read-only. The remaining reason for the additive key is the test pin, and that pin (`test_review_panel.py:303-308`) records a defect (gateway has no dispatch), which rule D of the synthesis says is rewritten with the fix [CARRIED, variant-2 section 4].

2. **X-007: B's absence claim was wrong.** `tests/cli/reflect/test_reviewer_readonly_tools.py` exists and pins the `tools:` allowlist (see Strength 1). What it does not do: it does not assert `permissionMode: plan` (no such string in the file as read, [VERIFIED]) and its dynamic no-mutation test is "deferred (producer absent)" (`:12`). So B's static claim is supported; B's `permissionMode` claim has no pin.
3. **X-006 scope: B's substrate evidence overreaches for multi-model use.** `ensemble.py:537-548` is the single-model Mode-A adversarial scorer (`model=config.model`) and `runner.py:549-566` is the Tier-1 audit child (`model=config.model`) [VERIFIED]. Neither launches several differently-modelled reviewers. So "raw-id substrate already exists" is true for one model per run; it is not a ready multi-reviewer launcher. A's "first model-launching subprocess in `cli/review`" is true at its scope.

B's rule "a missing argument is a dispatch error" is enforced by nothing in code today; B's replay detector is after the fact. A has the same exposure on its default `agent-class` path (A-006).
7. **No incident shows a mutation.** E2's launcher runs with `cd /tmp/evalsb/repo` (`run-reviewer.sh:48`, [VERIFIED]), a sandbox copy, so its open Bash was not pointed at the live tree, and B records no recorded mutation (variant-2 section 3.2). B's read-only argument is about what is possible, not an observed harm.
8. **`permissionMode: plan` as a second layer is unverified.** B leans on it (`reflect-reviewer.md:8`) but I have not seen evidence that a subagent's frontmatter mode survives a parent session started with a bypass mode [UNVERIFIED]. The `tools` allowlist is the layer I rely on; I withdraw any claim that `permissionMode` is an independent control.
9. **If M-2 passes, B's read-only edge narrows.** `--restricted` is documented as the closest official analogue of a read-only reviewer process (`web-02:124`) and `claude --help` on this host lists it per the diff analysis [CARRIED, not re-run by me]. If it holds on gateway ids, the difference becomes "one repo-owned allowlist and test" versus "a per-environment probe", which is a smaller gap than my variant states.
10. **Evidence format and tests (S-003).** A's four measurements each carry an explicit right/wrong rule and say what A becomes on failure; only B's item 1 does. B should adopt that format for its items 2 to 5.
