## 1. The position in one paragraph

The core of the Review Panel is ONE finding schema, findings-v2 taken as the superset of what exists. A finding locates itself by citations (`role`, `path`, `line_start`, `line_end`, optional `quote`), by a quoted `anchor`, or by both; the lens and the module declare which one is required. The merge and ledger path stops requiring an `anchor`: `annotate` becomes locator-agnostic and ledger rows are keyed by a span that is derived from either locator. The re-review contract becomes a typed line kind of the same grammar, replacing the v1-only `prior` line. New ledgers cluster with the v2 clustering (chain flag, roles, refs); existing ledgers stay on the v1 clustering. Unknown keys stay open, so the E2 in-line `origin` tag and any other module key keep working. The v1 anchor loop (spec review, `findings-v1`, `review-ledger/1`) is not removed: it becomes the `spec-loop` module profile of the one engine, and its pinned grammar, ledger schema string and command group stay byte-compatible.

## 2. Design consequence for the shared core and the named modules

Shared core (one pipeline, written once).
- Parser: one line parser with one set of limits, one id grammar and one drop rule. The info strings `findings-v1` and `findings-v2` select a profile of this parser. The profile is data: allowed location types, required location type, category set, lens set, severity set, rejected keys, whether `prior` lines are accepted. The `findings-v1` profile is exactly today's contract (anchor required, 6 categories, `prior` lines accepted, `calibrated_confidence` accepted). The `findings-v2` profile is today's v2 contract.
- Locator: a finding yields a span (half-open, 0-based line range, the unit `locate` returns, `RV/findings.py:302`) from its anchor (`locate`, first occurrence, `RV/findings.py:276-304`) or from the citation whose role is the module's primary role (`PRIMARY_ROLES`, `RV/cluster.py:67-71`) and whose path is the document under review (span = `line_start - 1` to `line_end`). A finding with both uses the citation range as the primary span and the quote or anchor as the check. [design inference]
- Ledger: row matching, `apply_revision`, `hunks_touch` and `map_span` already work on `span` and `span2` only (`RV/ledger.py:77-83`, `:331-346`), so rows stay span-keyed for single-document modules and gain an additive `citations` list. For multi-document modules (reflect, PR) the row key is (path, line range). The ledger header keeps `schema: "review-ledger/1"` (`RV/ledger.py:17`, `:38`, `:47-48`) and gains one additive marker naming the clustering that built it, absent meaning v1. [design inference]
- Clustering: `cluster_v2` and `same_defect_v2` (`RV/cluster.py:161-181`) for ledgers created after the change; `findings.cluster` and `same_defect` (`RV/findings.py:367-407`) for ledgers that carry no marker.
- Unknown keys: accepted and carried by both profiles (the status quo, `RV/findings.py:193-195` per r02 section 3 and `RV/findings_v2.py:84-173` re-read, no key whitelist there). The only rejected key stays a per-profile option: the reflect lenses reject `calibrated_confidence` (calibration lives in a sidecar block of the card), the `spec-loop` profile accepts it as v1 does. A module that wants `origin` carries it as a passthrough key; the ledger member record is extended to keep declared passthrough keys, because today it keeps only round, reviewer id, finding id and `blocking` (`RV/ledger.py:172-180`).
- Re-review: the grammar gets a typed line kind for "this prior row, this status", used by any module that has a ledger. The v1 `{"prior": "L3", "status": "resolved"}` line is its first spelling. What the ledger DOES with the line (clear, keep open, require a quote) is the question of slot C-02 and is not decided here.

Named modules.
- `spec-loop` (spec review, `/sc:spec-panel` Review Loop, E3 shipped source): profile of the engine. Brief text, six categories (`RV/findings.py:15-22`), anchor locator, `review-ledger/1` statuses (`RV/ledger.py:19`), cap, and the reviewer-typed `blocking` rule stay as they are.
- `reflect` (E1 shadow, Tier 2 prompt path): uses the `findings-v2` profile, `lens` reflect-pre / reflect-post, `reflect_category`, `deviation_class`, `coverage_rows`. The engine it already uses is the engine of the core. `cli/reflect` (contract 1.8.0, `derive_verdict`) is not edited by this position.
- `pr-review` and `rf-qa` (future modules): declare their vocabularies, require citations, and enter the same ledger; PR review additionally converts to `pr_submit.Finding` in an adapter (slot C-10).
- `tasklist` and `workflow`: modules that supply their own reference grammar (the `T01.02` gap, `RV/findings.py:29`) as module data; they are consumers, not part of this decision.

What this position does not decide (other slots): the repair policy for an over-limit line (C-06), the clearing and verdict rules (C-02, C-03), the PR wire format (C-10), which reflect engine feeds the core (C-04).

T2. Differential replay (right or wrong). Feed the same reviewer reports, anchor-only, through the current v1 path and through the `spec-loop` profile, and compare the ledger file: rows, `span`, `status`, `members`, `verdict`, `decision`. The expected result is equality apart from the additive keys. The chain case (one row of three members at lines 3, 6, 9, r17 DR-004) and the same-ref-in-two-sections case are the two cases where a clustering change would show. The corpus to use is a design question: the E2 raw reviewer reports are not committed (2,916 files, about 1.48 GB, r16 per synth-06 FX-18 [UNVERIFIED]), so the committed fixtures of `tests/review/test_review_ledger.py` are the corpus that exists.

T3. Locator comparison (the missing measurement that the evidence cannot supply). Take the three E2 plan packages and the same reviewers. Give one arm the anchor brief and one arm a brief that asks for citations with an optional quote. Per finding record: anchor found exactly once; citation path in the snapshot the core built; line range inside the file; quote found inside the range. This is the measurement the row says does not exist ("no measurement says which location type reviewers produce reliably"). A result in which citations resolve materially worse than anchors does not refute position A, because A accepts both locators; it would show that the `spec-loop` profile should keep requiring an anchor. A result in which citations resolve well strengthens the case for requiring them in the `reflect`, `pr-review` and `rf-qa` profiles. The position is refuted only if neither locator resolves reliably enough for any module, which no evidence in hand suggests.

T4. Crash probe turned into a regression test. A citation-only finding through `merge_round` must produce a row with a span, or an explicit unlocated row, and never `KeyError`. No test covers this today (r17 DR-113 lists none).

T5. Row-clearing probe for D-4. A finding whose anchor is missing (`span None`) and a finding with a citation range inside the file, both named as applied in a fix map whose hunk touches the cited lines: the second must reach `resolved_check`; the first stays `named_not_touched` (`RV/ledger.py:331-339`). This measures whether citations remove a verified stuck-row defect.

## 7. Effect on future PR code review and rf-qa replacement

PR code review. `pr_submit.Finding` needs a path and one positive integer line, and it drops a finding without one (`fsm.py:364-372` per r13 section 1 [UNVERIFIED], not re-read). Under A a panel finding already carries `citations[{path, line_start, line_end}]`, so the adapter of slot C-10 is a pure mapping from `citations[0]`, and the PR passthrough fields (`in_diff`, `confidence`, `original_line`, `reviewer`: r13 M3) ride on open keys that the ledger member record keeps by declaration. The ledger, rounds and `blocking` rule are then available to a PR module without a second engine. What A does not yet give: `apply_revision` remaps one old and one new text (`RV/ledger.py:301-347`), so a ledger across pushes of a multi-file PR needs per-path remapping that does not exist.

rf-qa replacement. The rf-qa fixes in place and its documents are markdown, tasks and plans; findings on tasks and code need file:line, and the swap needs a behavioural oracle (r13 R10, M13 [UNVERIFIED], not re-read). Under A there is one pipeline to give a replay fixture to, one set of limits to state in one brief, and module-declared category, lens and severity sets (r13 M2) are profile data. The first rf-qa module would use the `findings-v2` profile with lens and categories of its own; it would not need the spec categories (`RV/findings.py:15-22`), which `check_finding` enforces for every line today (`RV/findings_v2.py:109-110`).

M-items of r13 section 8 that this position carries: M1 (citation list, optional anchor, locator-agnostic `annotate`, citation-keyed rows), M2 (vocabularies as inputs), M3 (passthrough fields). Not carried here: M4 and M5-M14 (slot templates, read-only reviewers, reviser, caps, purity, adapter, replay, plugin), which other slots decide.

## 8. The strongest objection and the answer

Objection. Position A rewrites the code that is pinned and that has the only measured evidence against it, and it does so before anyone knows which location type reviewers produce reliably. The anchor path has a measured recovery story (92 dropped lines, 49 of them blocking, 88 of 92 addressable by truncation); the citation path has an E1 pre-check that flagged a large share of citations (the quoted figure is 48.7 percent, 92.5 percent of those `not-in-snapshot`). Moving the loop onto the v2 kernel could trade a known, bounded loss for an unmeasured one, in the code that decides whether a spec passes. Keeping the v1 engine as it is, and sharing only ids, hashes, panel resolution, the run record and the eval harness, avoids that exposure and costs only that shared defects are fixed twice.

Answer. Three points.
1. A does not choose a location type for the loop. The `spec-loop` profile keeps requiring an anchor and keeps today's recovery story, because the v2 parser already accepts `anchor` OR `citations` (E1). What A changes is that the choice stops being structural: a module can require citations without a second engine, and a finding with both locators is checkable two ways. The measurement of T3 sets each module's default; it does not decide the core shape.
2. The E1 flag figure is mostly path plumbing, not reviewer line errors. 372 of the 400 recorded flags are `missing-file` (A1: all 62 checked citations carried `not-in-snapshot`), the cause being read in run A3's notes as an orchestrator-built snapshot argument; 28 flags concern a range or a quote (E13). In the ledger path the core knows the one document under review and supplies the snapshot itself (E14), so the plumbing fault has no counterpart there. The causes are [UNVERIFIED] in the skill text and the 28 has no stated denominator, so this is a reason to run T3, not a measured advantage.
3. The cost the objection names is real and A does not hide it: the parser and ledger path are rewritten behind pins, effort is L in synth-05 6.1, and the defects of the v1 ledger (D-1, D-2, D-11, D-13) are not fixed by this slot. The rewrite is bounded by a measurable acceptance rule (T1 and T2: unmodified pins and an equal ledger on anchor-only input), and its blast radius is five source files inside one package (E10). Against that, the loss that does not go away if the engines stay separate is the one the evidence reproduces today: a v2 citation-only finding crashes the ledger path (E2), a missing anchor produces a row that can never clear (E11), and every future fix to the limit, repair or locator policy has to be made in two parsers.
