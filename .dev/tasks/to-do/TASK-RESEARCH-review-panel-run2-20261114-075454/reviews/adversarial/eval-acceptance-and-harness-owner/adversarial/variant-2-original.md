## 7. Strongest objection and answer

Objection. Position B accepts a design on evidence that cannot show quality. Tier S measures orchestration (the Stage 2 exit scores file naming and copy discipline; 20 clean runs would not show quality: research/06 s6, research/07 N-1, N-2 [UNVERIFIED by me]); any-severity coverage over three packages is carried 89% by three easy defects (E6); E1 and E2 are one evidence family (E11); and every written rule reached git with its data (E7). Without a kernel `verify-run`, nothing forces the audits to run before a table is produced, so the classes of defect that E2 hit (prefix mapping, unchecked judge completion, an unaudited batch, a fallback that overwrote `expected_model`) will recur and no tier G evidence will ever arrive.

Answer.
1. Scope of the claim. Position B does not accept the design as better. It accepts it as not worse on what is pinned (E1, section 4) and labels quality numbers as leads. C-03's adjudication states the same limit for the merge default ("not on measured superiority"), and C-02's states that the guard's strength is unmeasured. A claim of superiority needs tier G in any case; Going by the row text, the two positions differ on whether that evidence is a condition of the unification or of each module's adoption, not on whether it is needed.
2. The concentration objection applies to the alternative as well. The three easy items carry 131 of 147 catches under any metric (E6). A metric over the 8 blocking-in-implement items starts from a smaller denominator than one over the 14 defect-rich items, the study's real-blocking recall was at most 3 of 8 per family (research/08:135 [UNVERIFIED by me]; the per-row maximum of 3 is E5), and the severity-typing path it rests on is the one C-02 changes (E4). Presence.txt does not say which of the three easy items are blocking in implement, so I make no claim about that split.
3. Location is not the cause of the harness defects. The defects sit in scripts with no tests and hard-coded paths (E8: 0 test files under `A1/`). The same branch's later harness carries 89 test files, a sha-pinned judge wrapper and a tool-input audit, so the failure class is fixable in place. A kernel `verify-run` could not have caught the identity and tool-use classes either, because the records it needs do not exist (E9) until C-08 decides them.
4. The rule-before-data failure is commit discipline (M3), which no command enforces; a verifier in the kernel would still be run by the same operator.
5. What Position B concedes. It leaves the identity gap (section 4) open until C-08, and it leaves harness tests outside CI. If the owner weighs a kernel-level served-model check above avoiding a new CLI surface, that is a reason to prefer Position A's design; the evidence in this file does not decide that weighing.
