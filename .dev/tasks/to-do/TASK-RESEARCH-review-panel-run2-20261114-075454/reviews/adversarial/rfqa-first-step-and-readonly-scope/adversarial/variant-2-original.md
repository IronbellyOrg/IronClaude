## 1. The position in one paragraph

The first rf-qa change should not replace the `/task` phase-gate lens agents and should not touch their permission mode. It should enter rf-qa at the document-type level: one single-document gate (a document type that rf-qa-qualitative already reviews, for example PRD, TDD, technical reference or README), where the artefact is one file, one candidate text exists, and the settled spec-review loop shape (C-01 hybrid) fits without a new locator. Mechanical read-only enforcement applies to every reviewer the panel adds, from its first line (INV-G is a contract on new reviewers and FX-8 is decided). The existing `rf-qa` and `rf-qa-qualitative` agent files, the ten primitives that carry the S1-S3 cap text, and `task/SKILL.md` stay byte-identical in the first change, so the `/task` lens agents keep `permissionMode: bypassPermissions` for that change. Hardening them, and replacing the gate, is a later, separate change that needs a behavioural oracle first. The spawn-site census (44 structured lines, about 175 prose lines, 7 skills) is the unit of that later migration, not of the first change. The position has three separable clauses: B-1 the first step is not the `/task` gate; B-2 it is a document type (or, as the weaker alternative inside the same position, a skill's spawn sites); B-3 the `/task` lens agents' tools and mode are not changed in the first change.

## 8. The strongest objection and my answer

Objection: "The `/task` lens agents are the one known place where the mechanical read-only requirement (INV-G, HIGH; r13 R1 HARD) is violated today, on a gate that runs after every phase. Leaving them on `bypassPermissions` in the first change keeps a known HIGH exposure alive and delays the fix, while the oracle and the panel work could include it. A document-type start also tests little: spec-panel already reviews spec-like documents, so the first step adds nothing the repository lacks."

Answer, in three parts.
1. The exposure is real in design and unproven in practice. The documented control is a prompt parameter (`fix_authorization: false`, `task/SKILL.md:225, 241`), not a mechanism, and I found no evidence either way of a violation (section 3.1 item 6). M-B1 turns that into a measurement before the first change. If M-B1 finds a write, B-3 is wrong and I would move the hardening in; the proposal says so.
2. The fix is not small. It needs a second agent definition (the fixer shares the file with the lens agents), orchestrator-side report persistence plus a rewritten missing-report check, loss of Bash and web tools that `rf-qa.md:133` and `:518` name as verification surface, and a change to a gate whose floors and lens names have no pins and whose halt paragraph and stance wording have. Done in the same change as an engine-boundary decision (C-01 T-a) and a quorum-owner decision (C-03 INV-003), it couples four open questions in one change to the highest-traffic path. INV-G is already met by construction for everything the panel adds; the legacy agents are an existing exposure, not one the first change creates.
3. The document-type step is thin on purpose. Its output is evidence (an oracle, a read-only reviewer pattern, a persistence pattern) rather than new capability, and the cost is stated in section 7. B does not claim the document step is the final design; it claims the order.

Other objection that I accept as stated: B's three clauses are alternatives in the conflict row, and B-2 has two variants (document type, skill spawn sites). The evidence in section 3 supports the document type better than the spawn-site variant, because a spawn site in one skill is still a gate over that skill's phase outputs. I keep the spawn-site variant only as a fallback if no document type has a usable seeded-defect set.
