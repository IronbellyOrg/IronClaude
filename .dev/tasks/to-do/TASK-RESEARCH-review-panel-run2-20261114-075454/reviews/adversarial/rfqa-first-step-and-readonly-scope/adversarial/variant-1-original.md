## 1. The position (one paragraph)

The first rf-qa replacement change starts at the `/task` phase-gate QA (`src/superclaude/skills/task/SKILL.md:188-286`) and makes the lens reviewers of that gate panel reviewers that are mechanically read-only: a Read/Grep/Glob tool allowlist with no Bash, Write, Edit, NotebookEdit or Task, the pattern `reflect-reviewer` already has (`agents/reflect-reviewer.md:5-8, 38-40`). The single `rf-qa` fix agent with `fix_authorization: true` stays as the one writer and is the Reviser (`task/SKILL.md:254`), so the lens agents' "report-only" prompt convention (`fix_authorization: false` while spawned with `mode: "bypassPermissions"`, `task/SKILL.md:225, 241`) becomes a property the runtime enforces. To make that possible the panel gains three things and no more: (a) an optional free-text `lens` on a panel slot, delivered to the reviewer in its brief (the `persona_lens` pattern, `reflect-reviewer.md:56`); (b) a checklist-and-confidence output mode, a separate fenced block whose rows are VERIFIED / UNVERIFIABLE / UNCHECKED with the confidence computed by a script as `VERIFIED / (TOTAL - UNVERIFIABLE) * 100` (`rf-qa.md:484-534`); (c) a replay oracle built BEFORE the swap, so the change has something to be measured against (rf-qa has none, r13 section 5). The first change does not touch the seven skills' spawn lines, the `rf-qa` and `rf-qa-qualitative` agent files, the rf-qa-qualitative document-type checks, the intermediate gates that use `rf-analyst`, `pr_submit`, or anything under `cli/reflect`. The `/task` lens agents are made read-only IN the first change (this is the owner question Q3 / GQ-181, answered yes), because the point of starting at this gate is that it is the one place where read-only reviewers and a single writer are already separated in the text.

## 2. Design consequence for the shared core and the named modules

Shared core (`src/superclaude/cli/review/`), additive only, v1 engine unchanged per C-01:

1. `panel.py`: `_SLOT_KEYS` (`panel.py:46`) gains an optional `lens` (a string with a length bound). 2. A new pure module for the checklist block (`checklist.py`, parse and compute only). It does not edit `findings.py`, `findings_v2.py` or `ledger.py`. A reviewer's report ends with its findings block (v1, unchanged) and a second fenced `checklist-v1` block. The script computes TOTAL, VERIFIED, UNVERIFIABLE, UNCHECKED and the confidence by the `rf-qa.md:503-505` formula and the eligibility rule of `rf-qa.md:509` (confidence at least 95 and UNCHECKED zero). A reviewer whose checklist leaves UNCHECKED above zero is recorded as not complete for the quorum; that is a module-declared completion predicate added on top of C-03's "block valid" notion and is the one place this proposal adds a completion state C-03 did not conclude. The tool-engagement minimum (`rf-qa.md:532-534`, Read+Grep+Glob calls at least TOTAL) cannot be computed from a report; it stays a reviewer-declared line that is recorded and does not gate (the same treatment C-02 gave the evidence quote).

## 5. The test or measurement that would show position A right or wrong

Built first, before any `/task` text changes. Shape follows `scripts/reflect_stage0a_replay.py` with its test (synthetic directories in `tmp_path`, replayed without a model).

M1. Static guards (no model): the new reviewer agent passes a copy of `tests/cli/reflect/test_reviewer_readonly_tools.py:30-66` (tools present, non-empty, include Read/Grep/Glob, intersection with {Bash, Edit, Write, NotebookEdit, Task} empty, negative fixture with the tools line stripped). A second static check asserts that the gate text of `task/SKILL.md` no longer says `mode: "bypassPermissions"` for a lens reviewer. Existing suites pass unmodified: `tests/skills/test_review_severity_rule.py`, `test_review_prompt_overrides.py`, `test_worker_contract.py`.

M2. Template and golden: a template with `lens` slots validates; a slot with an unknown key other than `lens` is still rejected (`test_review_panel.py:65`); `lens` over its bound is rejected; the resolution JSON of every existing template (default, `live7`, the seven reflect files) is byte-identical to a stored golden; a slot with no `lens` yields a reviewer dict with no `lens` key.

M3. Checklist script: a truth table over (VERIFIED, UNVERIFIABLE, UNCHECKED) including the 95 boundary, UNCHECKED above zero, and TOTAL equal to UNVERIFIABLE. The formula `VERIFIED / (TOTAL - UNVERIFIABLE) * 100` is undefined there; `rf-qa.md:503-511` does not say what happens, and the rule must be fixed in the test before the first run (this proposal's reading: not eligible). Property: confidence is a function of the counted rows only.

M4. Replay oracle, deterministic arm (no model): frozen reviewer reports (findings blocks plus checklist blocks) and a fixed document, replayed through resolve, merge and ledger to assert: union of blocking rows over lens reports; a missing lens report refuses the merge; the cap gives ESCALATE at review 3 and the Reviser brief is omitted there (`ledger.py:96`, `:476-483`); a typed `prior ... resolved` from the verification pair clears a row and silence does not (C-02); a one-document ledger per output file.

M5. Replay oracle, model arm (seeded defects): document sets with one planted defect per lens dimension (placeholder left, a count that disagrees between two tables, a path that does not exist, a scope item silently dropped, an untestable criterion, a percentage sum that is wrong, a broken requirement-to-test chain, a claim that contradicts the code) plus a clean twin of each. Two arms on identical inputs: arm 0 the current gate lens agents; arm 1 the panel gate with read-only reviewers and the same lens text. Pre-registered before the first run (no threshold is proposed here because no measurement exists to calibrate one): per-lens recall of the planted defect in a blocking row; wrong blockers on clean twins; a tree-hash check that no reviewer changed any file; the share of lens checklist items answered UNVERIFIABLE in arm 1 against arm 0; tokens and wall-clock per gate.

Position A is shown RIGHT if, under the registered rule, arm 1 is not worse than arm 0 on recall and wrong blockers, mutates nothing, and keeps UNVERIFIABLE share within the registered bound. ## 7. The strongest objection and the answer

Objection. Position A starts at the place with the largest blast radius and the weakest oracle. Every MDTM task passes the gate after every phase but the first (`task/SKILL.md:192, 286`), so a fault in the new path stops all task execution. The gate is also the place where the v1 engine fits worst: phases often produce code or several files, the reachability rules need file:line (`task/SKILL.md:277-284`), the v1 ledger takes one document (`ledger.py:37-38, 107`), and the panel allows 8 reviewers against floors of 10 and 12 (`panel.py:247-248`; `task/SKILL.md:196-201`). The change also moves a gate whose behaviour is, by r13's own count, specified only in prose and checked by no test of its floors or lenses (E9). Nothing measured says the panel gate finds more than the lens agents do, and the first change would make cross-model reviewers, a ledger and a checklist parser depend on a prose coordinator.

Answer, in four parts.

1. The objection is right that A has no outcome evidence, and A does not claim any. S05's axis status for 6.11 and the C-11 row say the evidence cannot decide; A's claims are structural: the gate already has the reviewer, single writer, verification and cap shape (E1-E4), the read-only pattern already exists with a guard test (E5), and the first change touches the fewest pinned files (3.2). The blast radius is real (section 4.2, HIGH) and it is the reason the oracle (section 5) is built first and measures arm 0 as well as arm 1.

2. The two halves of the change are separable, and only the second carries the fit risk. Half 1: spawn every lens reviewer, document or code, as the new read-only agent, with the executor persisting the returned reports and consolidating them in prose as today. This is an agent-type change at the spawn sites of steps 3-5, needs no panel code beyond what a read-only agent file needs, and is what answers Q3. Half 2: replace the prose consolidation, fix hand-off and verification (steps 6-9) with resolve, merge and ledger, for document-output gates only. Code-output gates, and any cross-file finding, stay on Half 1 until trigger T-a of C-01 fires, which is the consistency position of section 0. So the objection that the v1 engine fits code phases badly is accepted as a boundary of Half 2, not as an argument against Half 1.

3. The cap objection is a limit of the first template, not of the position: one template covers the 6-agent and 8-agent tiers, and the 10 and 12 tiers keep the partitioning the gate already specifies (`task/SKILL.md:264-275`) or wait for a core decision on the 8 cap. Raising the cap is not part of this proposal because other templates inherit it.

4. The coordinator risk is the C-02 INV-003 risk and is closed the same way C-02's merged text closes it: the gate text names the `next` field as the thing the executor reads. A prose coordinator is what runs the spec loop today (`spec-panel.md:256-265`), so this is a known operating condition, not a new one.

Residual that the proposal does not remove: whether lens items that need Bash are many enough that read-only reviewers lose recall. Only the model arm of section 5 (M5) can show it. This proposal does not claim that starting at the document-type level or at the spawn sites is wrong; it claims this is the smallest start that settles Q3, produces an oracle and leaves both future uses open.
