## 1. The position in one paragraph

The unified Review Panel is a delivery vehicle behind `/sc:reflect`, not a new thing that `sc:workflow` and `sc:tasklist` call. Both consumers keep exactly one review call shape, `/sc:reflect --mode pre ...`, with their flags, output directories and return keys untouched. Which Tier-2 engine runs inside that call (today `legacy`, `--t2-engine shadow` for measurement, later `panel`) is reflect's decision, made after the depth, tier and rubric decisions. At generation time the review stays advisory: the bundle or plan ships whatever the verdict, and the verdict is shown through the existing `reflect_status` closed enum. The blocking effect stays where it already is: the per-phase execution gate (T5, `superclaude reflect run`, fail-closed 0/10/11/2 map) and the structural gates of the tasklist skill. The panel earns a consumer-visible effect only by passing the same reflect contract the consumers already read. No plugin copy of the panel or of `sc-reflect-protocol` / `sc-tasklist-protocol` is made, because the plugin does not carry them today and no test requires it; plugin delivery of the shipped skills is a separate, explicit later decision.

## 7. Effect on future PR code review and rf-qa replacement

A keeps both independent of the consumer entry. PR review (slot C-10) and the rf-qa/`/task` gate (slot C-11) reach the shared core through their own modules; neither reads `reflect_status`, and `reflect` is not their gateway. The panel's reviewers for those modules are the mechanically read-only kind that the core already supports (INV-G), so A does not constrain the rf-qa first step at the `/task` phase gate. Two interactions: (1) because A never adds panel flags to workflow or tasklist, the future PR and rf-qa modules cannot copy a "direct panel call" pattern from them; each defines its own call shape, which is the structure C-10 and C-11 already assume. (2) A's "no plugin copy" leaves the plugin without `rf-qa`, `rf-qa-qualitative`, `reflect-reviewer` and the review skills; a future rf-qa replacement that wants plugin delivery meets the same missing-skill gap that A leaves open and must schedule the mirror work explicitly (r12 5.3 item 148). This is a cost carried forward, not created by A.

## 8. The strongest objection and the answer

Objection 1 (the strongest). "Behind reflect the panel stays advisory at generation time, so a defect found by the panel never changes the tasklist or plan that ships; the owner wants the panel to improve the bundle, and the E2 loop (review, revise, re-review) can only do that through a direct call. Reflect UC-1 is also a single pass with no cap and no ledger, so the panel's loop value is discarded."

Answer. The effect at generation time is already the product's choice, not a limit of the entry: Stage 10.5 is "audit-first", and the one blocking edge is a human-decision HALT; workflow's rule is "never edit the plan from findings" (`SKILL.md:93`, tasklist `:1640`). A direct call would add a new revise loop beside two existing remediation surfaces: the Stage 7-10 patch loop with its own cap of 2 passes and a disjointness predicate with Stage 10.5 (`tests/tasklist/test_tasklist_cli.py:573-580`), and the `--remediate` Tier-3 offer. Reconciling a third loop with the 3-review cap and those fences is the larger change (r11 2.2) and no data says it improves outcomes. A keeps the fix path where it is (`sc:task`, never the orchestrator) and uses reflect's existing Tier-3 hand-off for remediation. If the owner wants a panel-driven revise loop at generation time, A allows it as a later, separate module change on top of reflect's contract; it does not close that door, it declines to build it before it is measured.

Objection 2. "Quick-depth phases (score 0-3) and `--no-reflect` never reach the panel, so the consumers get a panel only on some phases." Answer: true (D1, `SKILL.md:317`; tasklist `:1644`). It is the existing cost/coverage policy of Stage 10.5 and the measurement in section 6.2 shows whether it matters. A direct call would face the same cost decision and add a new depth policy.

Objection 3. "Nobody passes `--t2-engine`, so A leaves the panel dormant for consumers for as long as reflect's default is `legacy`." Answer: the dormancy is the verified current state (item 1), and A's route to activation is one controlled change at reflect's default, gated by the section 6.1 and 6.3 measurements and the fence-test update. B's direct call would also stay dormant until its new flags, keys and pin rewrites land.

Objection 4 (plugin). "Without a plugin copy, plugin-only users never see the panel." Answer: they do not see reflect or its review today either (item 9); a plugin copy of the panel alone cannot work without `sc-reflect-protocol`, the reviewer agents and the pins; the shipped plugin skills are a separate product decision (r18 gap 6) that A leaves to the owner explicitly rather than half-doing.
