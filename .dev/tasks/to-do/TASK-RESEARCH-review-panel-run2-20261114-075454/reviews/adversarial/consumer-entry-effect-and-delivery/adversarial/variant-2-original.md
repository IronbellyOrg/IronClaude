## 1. The position (B)

Tasklist and workflow call the panel directly, through a delegate-only skill entry of their own (the same shape as the `sc:reflect-protocol` Skill call they make today), with a new flag set and new return-contract keys beside `reflect_status` and `reflect_report_path`. A tasklist review is allowed to fail at generation time and to drive a revise loop, with the panel's reviewers as the review side and the existing separate fixer (`sc:task` through the PatchChecklist) as the revise side. The shipped skills the direct call needs (and the read-only reviewer definition they dispatch) get a plugin copy with a parity pin. Position B has two forms that share this design: B-add keeps today's reflect UC-1 call and adds the direct call beside it; B-replace swaps the call at `sc-workflow-protocol/SKILL.md:89` and `sc-tasklist-protocol/SKILL.md:1630` (synth-05 6.8.b option (b)). The three parts (entry, effect, delivery) are separable in code; this proposal argues all three, and says in section 8 which part carries which argument.

## 3. Design consequence for the shared core and the named modules

Shared core (what B asks of it, all of it already inside the C-01 to C-03 outcomes):
- A consumer module is data plus a thin skill: a profile (lens and category sets, id grammar, `effect: advisory | blocking`, quorum floor, cap, halt-reason enum), an input manifest by role (spec and roadmap as driving documents, the phase tasklist as candidate), and a return-contract fragment. The core never names tasklist or workflow. B is the first non-spec, non-reflect consumer to exercise this seam.
- `effect` is module data, not a core constant. The core carries only the boolean `blocking` as the verdict-driving field (the working default of synth-06 C-S3). Whether a module's failing verdict blocks anything is the module's choice under repo rule S1-S5.

Named modules:
- `tasklist-review` module (new): lenses are the five Stage 7 dimensions (Drift, Contradictions, Omissions, Weakened criteria, Invented content, `sc-tasklist-protocol/SKILL.md:1378-1382` per research/11 section 2, [UNVERIFIED] here); location is a text anchor with the task id in `refs` (`T<PP>.<TT>`); the severity table maps High to blocking and Low to a note. ## 8. Strongest objection and the answer

Objection: the only measured results say a blocking panel is wrong more often than right. Real blocking was 0 of 8 in every pilot arm and wrong blockers ran from 0 to 3 (E11); the judge's "blocking" is mis-defined, ledger rows are round 1 only, and a revise loop that patches non-defects mutates phase files through `sc:task`. Advisory-at-generation, blocking-at-execution (position A) loses nothing measured and cannot corrupt a bundle.

Answer:
1. B does not add generation-time blocking. It already exists in Stages 8-10, with homogeneous reviewers, no quorum, High and Medium both blocking, and no measurement either (E3). The choice is which reviewers feed that block, not whether a block exists.
2. The E2 wrong-blocker figures are upper bounds: the judge counts 65 as blocking where 38 are blocking in implement (E11), and ground truth contains only defects that surfaced during implementation, so a true novel defect scores as a wrong blocker (research/08 key takeaways item 2, citing `PR:79`, [UNVERIFIED] here).
3. The fixer is already a separate role that rejects or applies rows, and C-02 plus C-03 give a rejected row a path (`defer`, owner and reason), though C-03 condition 2 says that exit is human today. This is the weakest link in B, and B states it rather than hiding it: until the replay in section 6 item 3 runs, B's blocking effect is a hypothesis, and B-add with `effect: advisory` is B's own safe starting form.
4. Which part carries which argument: the entry argument (E4 to E7, E10, section 7) stands even if the effect stays advisory; the effect argument (E2, E3, E8) stands even if the entry stays on reflect; the delivery argument (E9) is the one B cannot separate from the entry, because only a changed workflow skill forces a plugin edit, and under A the call sites do not change.

Second objection: B-add reviews each plan or phase twice, and B-replace degrades the readers of `reflect_status`. Answer: both costs are real and are the reason B has two forms; the replay's cost column (section 6 item 4) is what decides between them.

Third objection: the plugin copy helps only where the `superclaude` CLI the panel needs is on the path. Whether a marketplace plugin install has the CLI is [UNVERIFIED] here (the wheel force-includes `plugins/` into `superclaude/_plugins`, research/18 section 7, but the marketplace copy is a separate repo target). Answer: where the CLI is absent the skill's hard gate returns `skipped` with a null path, which is exactly today's plugin result, so the copy cannot make a plugin install worse; whether it is worth the maintenance is the product decision this slot calls it.
