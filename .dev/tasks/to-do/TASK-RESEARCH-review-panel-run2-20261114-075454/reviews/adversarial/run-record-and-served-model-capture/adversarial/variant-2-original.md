## 1. The position

Slot C-08 asks where the run record lives and who writes it. Position B: the record of what a run cost and which model served it already has two homes in the code, and each needs a small change rather than a new file. (1) The per-run, per-agent facts go into the run manifest `<out>/panel/manifest.json`, which today hashes each attempt payload and throws the payload away (`manifest.py:348-354`): its attempt entries keep a closed-key `usage` and `model` object, and its `published` and `failed` stage records keep one `agents[]` list that a transcript adapter reads once, from the harness transcript and never from the orchestrator. (2) The cross-run, per-reviewer record stays in `review-telemetry/1`, whose reviewer record already has a `model.observed` field and a five-counter cost group (`telemetry.py:49`, `:74-80`) and whose writer already appends one line per record, never rewriting (`telemetry.py:287-307`); it gets a producer in the merge step (loop path) and at the published commit (Tier 2 path). (3) The manifest gets a lock and a revision check, and the telemetry append gets a lock. (4) Memory keeps its writer. There is no `events.jsonl`, no `review-run-event/1` schema id, no `review record add/export` pair, and no `review-telemetry/2` unless the owner decides value tightening needs a version bump. The cost this accepts: orchestrator-inclusive cost is a read of the transcript at commit time, not a stream of rows during the run.

## 4. How B meets the decided requirements of the slot

The decided requirements (CO-19, CO-20, CO-11, C-S10, FX-16, FX-19) are: served model from the transcript and never from the orchestrator; cost on one row per agent attempt and reported on two labelled bases; LLM-written numbers are estimates; concurrent writes need serialising; telemetry holds no document text; strata become a module list; the writer of memory moves to one step at publish with a study switch (the facts are decided, the owner and flag shape is C-08).

- Served model from the transcript: the adapter writes `model.observed` into the attempt entry or `agents[]`; the orchestrator passes a file path, never a number. Where the transcript is unreadable the value is `null`.
- Cost on one row per agent attempt: per reviewer and calibrator attempt on the manifest attempt entry (stage `collected`, `calibrated`); for every other agent, including the debater, validator and orchestrator session, on `agents[]` of the `published` or `failed` stage. Cost lives in no outcome record and in no verdict, so the D-17 fan-out cannot arise from a second copy.
- Two labelled bases: reviewer-only comes from `reviewer_run` records (`model_scores`), all-agents from `manifest summary`. A cross-run all-agents figure reads manifests, not the telemetry store; this is a stated cost of B.
- Serialising: flock plus `rev` on the manifest, flock on the telemetry append.
- No document text: closed key sets on the new manifest objects, type checks at telemetry append (INV-H, section 5).
- Strata: module-registered list in `telemetry.py` (`:112`, `:267-268`).
- Memory: B leaves the writer and says why in section 7, objection 3.

## 6. Effect on future PR code review and on the rf-qa replacement

- PR code review. A PR panel is a set of reviewer sessions over a diff, so a `reviewer_run` record per reviewer fits with no schema change: `doc_sha256`, `doc_bytes` and `doc_lines` take the diff's values, while `language`, `doc_format` and the RFC-2119 counters stay spec-shaped (FX-16, already decided as an exposure) and strata become a module list (C-S10). The producer for that module sits in its own adapter step (the pure conversion step of slot C-10), not in the manifest: `STATES` is the fixed tuple `frozen ... published` (`manifest.py:40-50`) and has no PR-shaped stages, so a PR panel would reuse the manifest only if its stages happen to match. Consequence: under B a PR panel gets reviewer-only cost and served model; its non-reviewer agents (fix, troubleshoot, verify) are outside the record unless the PR module also keeps a manifest, or the owner later adds an `agent_run` kind (R15 §8.5), which B does not preclude because it adds no key that an `agent_run` kind would collide with.
- rf-qa replacement. rf-qa is a single agent per check; its cost and served model are one `reviewer_run` on the reviewer-only basis through the same adapter. B does not give rf-qa a per-check stage record.
- Gateway models. The adapter is the only part that must see non-Claude reviewers' served ids (`message.model` of the sidechain; the Agent result `resolvedModel` is the requested alias, not identity proof: R04 §4.2, [UNVERIFIED]). Both positions depend on it equally; it does not decide the dispatch mechanism (C-07).
- Studies (E2-style rows). The per-design counters in E2's R-23 (about 25 per-reviewer fields) have no place in `reviewer_run` or the manifest under B. If slot C-12 builds an exchange capability, those counters need a per-run stream and B's "no new per-run file" stops holding for that module. B's position is for the present scope; slot C-12 is not yet adjudicated, and its synth-06 row names the static kit with no exchange as the unconditional layer.

## 7. The strongest objection and the answer

### 7.1 The strongest objection (objection 1)

The manifest is the wrong carrier for a run record. It is a stage state machine rewritten whole on every call; it refuses attempts once a stage is committed or is not next (`manifest.py:371`); it has no row for any agent outside `dispatched`, `collected`, `calibrated` (`manifest.py:53`); and in 9 of 29 real manifests the orchestrator advanced a stage before recording, so the attempts were refused or never recorded (B-18, [UNVERIFIED]). A record that depends on the orchestrator calling the CLI in the right order loses exactly the late, killed and non-reviewer rows where cost leaks, and orchestrator cost is final only after `published`, when a committed manifest should not change. An append-only stream accepts a row at any time.

### 7.2 The answer

1. Usage does not ride on the calls the orchestrator may mis-order. The reviewer's usage is attached to its `collected` attempt, and all 29 manifests hold every reviewer's `collected` attempt (B-18); the missing rows in the 9 are the `dispatched` marker rows, which carry no usage. Every other agent (calibrator, debater, validator, helper children, and the orchestrator session through publish) is read in one pass from the transcript into `agents[]` when `published` or `failed` is committed, so no per-agent call from the orchestrator is needed and ordering errors cannot lose them. A killed attempt is recorded with a completion state the manifest already has (`failed`, `timed_out`: `COMPLETIONS`, `manifest.py:52`) and `usage_complete: false`.
2. The orchestrator's tail after `published` is not in the manifest; B says so and labels the all-agents figure "through publish". Where a study needs the tail, it reads the same transcript with the same adapter at analysis time, which is what the E1 extractor already does (`analysis/extract.py:42-81`, [UNVERIFIED]).
3. Residual B does not close: a run killed with no process left to commit `published` or `failed` leaves no `agents[]`; an append-only stream would hold the rows written before the kill. The adapter can be run later over a manifest left in a non-terminal state, but that is a recovery action, not a record written during the run.
4. A lock and a revision check are needed under either position (R15 gap 6: events do not cover stage commits), so the lock is not a cost that separates B from the other position.

### 7.3 Secondary objections

2. Two producers (merge step, published commit) mean two places to keep in step. Answer: both write the same `reviewer_run` shape through the same `append_record`; the loop has no manifest (B-8) and the reflect path never calls `review merge` (B-8: 0 hits in its SKILL), so no run has both today. Under C-01's convergence triggers (T-a to T-c) the two converge on one producer; the record shape does not change.
3. Memory stays an LLM write, so a lost update and a study contaminant remain possible. Answer: the observed contamination is on the read side (`memory_hits` 2 versus 1 across arms of one experiment, R15 §6.2, [UNVERIFIED]), which a read-freeze addresses without moving the writer; the one missing section is an orchestrator decision recorded in a contract field, not a race (B-20); moving the writer changes `### 6.3` of the reflect SKILL, which is outside the shadow edit fence (B-11) and is a change to Waves 0 and 5 behaviour rather than to shadow telemetry. A script writer that files an LLM-authored entry (such as the existing `artifacts/memory-entry.md` of the run that froze memory) remains available as a later step if a lost update among concurrent writers is ever observed. This is a position on evidence, not a claim that the script is wrong.
4. Run id for the loop path. `reviewer_run` needs a `run_id` (`telemetry.py` `REVIEWER_TOP`), the ledger carries none, and the resolution JSON does (`panel.py:696`). Answer: the producer takes `run_id` from `--resolution`; a loop run without `--resolution` has no models either, and writes no record (the same condition under which C-03's refusal needs `--resolution`). [UNVERIFIED] whether every packaged loop prompt passes `--resolution`; C-03 records the version-skew case as its INV-013. The loop prompt does pass `--run-id <loop id>` to `panel resolve` (`document_review_loop_prompts.md:70`) and the resolution JSON stores it (`panel.py:696`) [CODE-VERIFIED].
