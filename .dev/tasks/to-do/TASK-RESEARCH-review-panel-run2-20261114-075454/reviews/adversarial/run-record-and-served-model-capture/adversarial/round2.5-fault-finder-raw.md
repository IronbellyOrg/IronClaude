ID: INV-001
CATEGORY: state_variables
ASSUMPTION: The writer assigns `seq` by reading the current end of `events.jsonl` under `events.lock`, the file is always a sequence of complete JSON lines, and "closed-key check on write and on every read, an unknown key is an error, not skipped" (B 4.1 item 3, agreed by A) is safe to apply to every reader (`export`, `summary`, the aggregator gate).
STATUS: UNADDRESSED
SEVERITY: HIGH
EVIDENCE: Neither resolution says what the writer does when the last line is torn (a process killed mid-write leaves a final line with no newline, or half a JSON object). Two consequences follow from the text as written. (1) `seq` assignment reads the last line: a torn tail either raises, or restarts `seq` at an arbitrary value (duplicate seq), or the next append is glued onto the unterminated line so that two rows share one line. (2) Under B's "unknown key is an error" read rule, one torn or glued line makes `record export`, `record summary` and the aggregator gate fail for that run, permanently, because the file is "append-only, never rewritten" (A item 3) and no repair command exists. Compare the manifest, which is protected against this by write-temp-then-`os.replace` (`src/superclaude/cli/review/manifest.py:156-163` `save` ending in `os.replace` [grep-confirmed], publish_files at :476-518 [RE-READ]), and `telemetry.append_record`, whose one-string append (`telemetry.py:305-306` [RE-READ]) is the model A copies but gives no torn-line recovery either. The case "a run killed mid-line" (this probe's category 4) has no sentence in either section 4. Needed: a rule that the reader ignores (and counts) a final line without a newline, the writer starts a new line after one, `seq` is derived from the last parsable row, and the gate treats a counted torn line as `unverified` not as `requested-pinned`.

ID: INV-002
CATEGORY: state_variables
ASSUMPTION: One immutable `agent` row per sidechain keyed by tool-use id, "re-running ingest skips keys already present, so it is idempotent and can run at any time, more than once" (A item 5), is safe because "a finished sidechain's usage is final" (A C3/N3).
STATUS: UNADDRESSED
SEVERITY: HIGH
EVIDENCE: "Can run at any time" includes while a sidechain is still running or after it was killed. The interactive harness marks this explicitly: every `subagents/agent-<id>.meta.json` carries `"finished": true|false` and `"requestShape":"background"` for background agents [MEASURED, e.g. subagents/agent-a1c59abd5fb8f5051.meta.json]. The adapter text reads neither field. A row written for an unfinished sidechain gets `usage_complete: false` (A item 5) and, because keys already present are skipped, a later `ingest` can never replace it: the partial figure is frozen. The same freeze applies one level up: `export` uses a deterministic `record_id` and "skip-if-present" (A item 8, B 4.1 item 8), so a reviewer_run exported from a partial row is never corrected, and `INSERT OR IGNORE` on `record_id` at load (`telemetry.py:417-424` [RE-READ]) keeps the first one. A is conflating "finished sidechain" with "ingested sidechain". Needed: ingest must skip (not write) a sidechain whose `finished` is not true, or a row must be replaceable by a later row with `usage_complete: true` under the same key (a supersede rule, with read-time resolution as for `orchestrator_snapshot`).

ID: INV-003
CATEGORY: state_variables
ASSUMPTION: The `orchestrator_snapshot` row "of which the last one wins at read time" (A item 5, N3) always represents the largest/latest orchestrator usage.
STATUS: UNADDRESSED

EVIDENCE: "Last" is defined by events-file order (`seq`, assigned under `events.lock`), not by transcript position.
