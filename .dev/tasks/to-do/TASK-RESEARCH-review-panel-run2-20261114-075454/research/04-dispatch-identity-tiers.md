## Summary

The product `superclaude review` package only resolves reviewers: it prints a model per slot, a tier alias and a `launch` class word (empty under `gateway`, so a `reflect-*` gateway panel is refused by `panel.py:153-156`), and it launches nothing; three real dispatch mechanisms exist outside it (E1's orchestrator Agent call by class word, E1's code engine over HTTP by raw id, E2's `claude -p --model <raw id>`), and E3's loop names none. No product code records the served model: parity, diversity, judge-collision and identity telemetry are all functions of requested values, and the only truth is the Claude Code transcript, which E1's `extract.py` and E2's `run-reviewer.sh` read by hand (the A-r3 run, 3 reviewers collapsed onto Claude Sonnet 5.5 after the orchestrator omitted the `model` argument, still reports `calibrator_diversity: full`). `T2bModel01` is a ccsession slot name and an implement-retry rung used in 11 lines of 8 files in the assigned scope and by no panel code (the E2 run-2 note is wrong), and `muse-ember-1.0` is absent from every tier data file at HEAD even though the live workspace env carries it as `T4Model04`. For the shared core this means dispatch identity (requested class, resolved alias, served model) must become explicit fields fed from the transcript, one owner must define "class" and "vendor", and the tier lists need a single source instead of three hand-kept copies.
