## 4. Open item (c): the tasklist id grammar `T01.01` against `_REF_TOKEN` and `_ID_TOKEN`

Two different grammars are in play; they fail differently.

**4.1 Finding id (`_ID`, `findings.py:26`) accepts `T01.01`.** Executed: `_ID.match("T01.01")` True (6 characters); `"T01.01"+"x"*10` (16 characters) True, 17 characters False; `P2-F12` True. The finding-id grammar allows letters, digits, `.`, `_`, `-` after the first alphanumeric character, so a finding may be NAMED `T01.01`. This is NOT where it fails. [CODE-VERIFIED by execution]

**4.2 Reference token (`_REF_TOKEN`, `findings.py:29`) does not match `T01.01`.** The pattern is `\b(?:[A-Z]{1,4}-[0-9]+(?:\.[0-9]+)*|P[0-9])\b`: it needs 1 to 4 capital letters, then a HYPHEN, then digits with optional dotted tail, or `P` plus one digit. `T01.01` has no hyphen after its letters, so the first branch fails; the second branch is `P`+digit and does not apply. Executed: `_REF_TOKEN.findall("Task T01.01 AC-0.4 R-012 D-0003 T01.01-x P1 T1-2")` returned `['AC-0.4', 'R-012', 'D-0003', 'P1']`. `T01.01`, `T01.01-x` and `T1-2` are all missed, because the pattern needs capital letters IMMEDIATELY before the hyphen and these tokens have a digit there. A separate call showed `refs_norm` returns `[]` for refs `["T01-01"]` as well. So tasklist task ids in the dotted form `T<PP>.<TT>` (or with a hyphen after the digits) are dropped, while roadmap ids `R-012` and deliverable ids `D-0003` (also tasklist ids) are kept. [CODE-VERIFIED by execution]

**4.3 How the loss reaches the contract.** `refs_norm` (`findings.py:321-337`) builds the normalised refs from `anchor`, `anchor2`, `claim` and every `refs[]` string via `_REF_TOKEN` (332-333), plus bare section numbers from `refs[]` entries that fully match `_SECTION_REF` (`^\d+(?:\.\d+)*$`, `findings.py:30,334-336`). `T01.01` matches neither, so `refs_norm` returns `[]` for a finding whose only refs are task ids: executed `refs_norm({"anchor":"x"*12,"claim":"c","refs":["T01.01","T01.02"]})` -> `[]`. The finding line itself is NOT rejected (`refs` only has to be a list of at most 8 strings, `findings.py:111-117`; `T01.01` is a string); the id is silently ignored by clustering. [CODE-VERIFIED by execution]
- v1 effect: `fingerprint` (`findings.py:340-343`) becomes `sha256("v1|" + section + "|")[:16]` with an empty refs list, and `same_defect` (`findings.py:371`) requires `a.get("refs_norm")` non-empty before the fingerprint match counts, so the fingerprint path is disabled; the span path (`findings.py:373-378`) then applies when both ref sets are empty, which means findings merge only by being within 3 lines of each other (inline constant 3, `findings.py:377`). [CODE-VERIFIED]
- v2 effect: `cluster.annotate` calls the same `refs_norm` (`cluster.py:64,137-141`), so the loss is inherited. Executed: a v2 finding with `refs ["T01.01","T01.02"]` and claim naming `T01.01` annotated to `refs_norm []` but `fp` still computed (`cluster.py:143-147`). `same_defect_v2` then ignores the fingerprint path (`cluster.py:163` needs non-empty `refs_norm`) and falls to the citation path: compatible deviation classes, both ref sets empty, resolved citations on one path within `SPAN_TOLERANCE = 3` lines (`cluster.py:72,165-180`). So in v2 "same primary path plus same requirement ref" is one defect at ANY distance. [CODE-VERIFIED by execution]

**4.4 `telemetry.py:23` `_ID_TOKEN`.** Verified text: `_ID_TOKEN = r"(?:[A-Z]{1,4}-[0-9]+(?:\.[0-9]+)*|P[0-9])\b"` (`telemetry.py:23`) is a plain STRING, not a compiled regex (my first call `_ID_TOKEN.findall` raised `AttributeError: 'str' object has no attribute 'findall'`); the compiled forms are `_ID_RE = re.compile(r"\b" + _ID_TOKEN)` (`telemetry.py:24`) and `_BOLD_DEF = ^\s*(?:[-*+]\s+)?\*\*(<_ID_TOKEN>)` (`telemetry.py:27`). `_ID_RE` therefore compiles to the same pattern as `findings._REF_TOKEN` (`\b(?:[A-Z]{1,4}-[0-9]+(?:\.[0-9]+)*|P[0-9])\b`). Executed: `_ID_RE.findall("Task T01.01 AC-0.4 R-012 D-0003 T01.01-x P1")` -> `['AC-0.4', 'R-012', 'D-0003', 'P1']` (same miss). **4.5 Where the `T<PP>.<TT>` grammar comes from.** Slice 02 section 3.2 R-1 cites `sc-tasklist-protocol/SKILL.md:340` ("Task IDs are zero-padded: `T<PP>.<TT>`"). Checked in section 7 below. **Key Takeaways (section 4)**
- `T01.01` is a legal finding id (`_ID`) but is NOT a recognised ref (`_REF_TOKEN`, `_ID_TOKEN`, `_SECTION_REF`); the finding is kept, the ref is ignored, no error is emitted.
