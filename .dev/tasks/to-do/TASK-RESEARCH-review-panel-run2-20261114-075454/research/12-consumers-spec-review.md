## 8. What severity scale and cap policy the core carries (synthesis for the research question)

Evidence-backed statements first, then the design inference (marked).

Evidence
- E-a. The schema already carries a boolean `blocking` and a three-label severity (`findings.py:14,96-101`); a MINOR finding cannot be blocking and a MAJOR finding may be non-blocking (the parser rejects only MINOR + blocking). Consequence: "Medium" has NO schema value anywhere in `cli/review` (the only file in `src/superclaude/cli/review/` with the word is `card_convert.py`, 3 hits per `grep -c`); it exists only as prompt text and as the report section `follow-up candidates`. A Medium finding in the loop is represented as `severity: MAJOR, blocking: false`. [CODE-VERIFIED]
- E-b. v2 (reflect lens) is stricter: with `reflect_category` set, `blocking` must equal `severity != "MINOR"`, so a MAJOR is always blocking (`findings_v2.py:155-162`); without `reflect_category` it behaves like v1. v2 imports `SEVERITIES`, `CATEGORIES` and `_ID` from v1 (`findings_v2.py:15-21,103,109`). [CODE-VERIFIED] So inside the one package there are already two severity-to-blocking rules selected by lens: spec (consequence-graded, MAJOR may be non-blocking) and reflect (label-determined). The core must make this rule a property of the module or lens, not a constant.
- E-c. The repo-wide canonical rule is binary (blocking/minor), 2 fix cycles, pinned across ten primitives and by `test_review_severity_rule.py` (section 2.1). [CODE-VERIFIED]
- E-d. Consumers that cannot adopt a 3-label severity without a mapping: tasklist skill (High/Medium/Low with Medium blocking; the tasklist CLI gates only on High), pr-submit and auggie (5 tiers that carry routes), `/sc:implement` (derived blocking/minor/note, explicitly allowed by S4). [CODE-VERIFIED, sections 2 and 3]

Design inference (not code facts; tagged as recommendation)
- Severity scale the core carries: the existing CRITICAL / MAJOR / MINOR labels plus the `blocking` boolean as the ONLY field that drives verdict, ledger brief and cap decisions; no `Medium` token in the core schema (a Medium finding is `blocking:false` with a `follow_up` marker, or MAJOR + `blocking:false` as today). Rationale: it is the schema both E3 (v1) and E1 (v2) already validate, it satisfies the binary canonical rule S1-S2 and S5 by construction, and it avoids M1-M6 collisions.
- Modules supply an explicit label map into that pair: spec = identity with the consequence sentence; rf-qa/`/task` = IMPORTANT -> blocking, graded by definition (S5); tasklist = High and (per the skill) Medium -> blocking, Low -> MINOR, with the skill-vs-CLI conflict (M4 vs M5) to be settled by the module owner; PR review = category-floor re-grade (`severity_router.py:34-53`) then a documented mapping of the five tiers to `blocking` (the code currently has no such mapping: tiers drive routes only; open question below); `/sc:implement` = exempt (S4).
- Cap policy the core carries: `max_fix_cycles = 2` default (reviews = cycles + 1), halt reason enum, escalation with the open blocking findings; a module may declare a documented override (pr-submit hard cap 5; `/sc:implement` exempt). Rationale: S3 plus `test_f`; the master loop, the CLI ledger (3 reviews), rf-qa, `/task`, pr-submit's default and (on my reading) the tasklist P2 loop already equal 2 fix cycles (section 4).
- Category set: per module (6 spec categories in the spec module and reflect's six-to-six map; 18 code categories in the PR module); the core validates a module-declared closed set rather than owning one.

The repo already has a canonical binary review rule (blocking vs minor, Medium as a non-blocking warning, 2 fix cycles) copied into ten primitives and pinned by tests, and the CLI schema already encodes it as CRITICAL/MAJOR/MINOR plus a `blocking` boolean with no Medium value; that pair, not a new scale, is what the core should carry, with each module (tasklist, PR, rf-qa) supplying an explicit label map and the reflect lens keeping its stricter `blocking == severity != MINOR` rule. "Medium" has at least six conflicting uses, the sharpest being tasklist skill (blocking) versus tasklist CLI (not gating), so it must not be a shared token. Caps agree at 2 fix cycles in the repo's unit for the loop, rf-qa, `/task`, pr-submit's default and (on my reading) the tasklist P2 loop; the genuine outliers are pr-submit's hard cap of 5 and `/sc:implement`'s exempt five-attempt ladder. A spec module and a tasklist module cannot share brief text: they differ in document roles, location type, id grammar and brief delivery, while the placeholder idiom, the one-sentence hard gate, the anti-inflation lint and the findings and fix-map containers can live in the core.
