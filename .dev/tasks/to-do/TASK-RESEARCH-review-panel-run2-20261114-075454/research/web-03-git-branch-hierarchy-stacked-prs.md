## A. Documented rules of `git check-ref-format`

### A1. Official rule list (reliability: official docs)
- Source: https://git-scm.com/docs/git-check-ref-format
- Key information: A reference is how Git names branches and tags. Branch heads live in the `refs/heads` hierarchy, tags in `refs/tags` (typically as files under `$GIT_DIR/refs/heads` and `$GIT_DIR/refs/tags`, or as entries in `$GIT_DIR/packed-refs` once `git gc` packs them). Rules: (1) `/` allows hierarchical (directory) grouping, but no slash-separated component may begin with `.` or end with `.lock`; (2) at least one `/` is required unless `--allow-onelevel`; (3) no `..` anywhere; (4) no ASCII control characters, DEL, space, `~`, `^`, `:`; (5) no `?`, `*`, `[` (except with `--refspec-pattern`); (6) cannot begin or end with `/` or contain consecutive slashes (exception with `--normalize`); (7) cannot end with `.`; (8) cannot contain `@{`; (9) cannot be the single character `@`; (10) cannot contain a backslash.
- Notable gap: the rule list on this page does NOT state the "a name cannot be both a leaf and a prefix of another name" constraint. `git check-ref-format` validates a single name in isolation; it cannot flag that `feat/review-panel` is incompatible with an existing `feat/review-panel/<name>`. The conflict is only detected when Git tries to create the ref (see B).
- Relation to codebase: `feat/review-panel` and `feat/review-panel/<name>` each pass `check-ref-format` individually (no rule above is violated by either name). The failure is a ref-store conflict, not a naming-syntax violation. Extends the framing of research item 2.18 (scratch-repository test); the item 2.18 result in `research/18-repo-constraints-and-branching.md` takes precedence over this summary.
- Relevance: HIGH

## B. How Git stores refs and why a name cannot be both a leaf and a prefix

### B1. Loose refs are files in a directory hierarchy; packed-refs is a flat file (reliability: official docs)
- Sources: https://git-scm.com/docs/git-pack-refs ; https://git-scm.com/docs/gitrepository-layout
- Key information: Traditionally each ref is one file per ref in a (sub)directory under `$GIT_DIR/refs` (git-pack-refs DESCRIPTION). `git pack-refs` stores refs in a single file `$GIT_DIR/packed-refs`; "When a ref is missing from the traditional `$GIT_DIR/refs` directory hierarchy, it is looked up in this file and used if found." "Subsequent updates to branches always create new files under `$GIT_DIR/refs` directory hierarchy." `refs/heads/<name>` records the tip commit of branch `<name>` (gitrepository-layout). The BUGS section of git-pack-refs notes older docs say ".git/refs/heads/ file exists" when they mean "branch exists".
- Inference (not stated in these pages, derived from the one-file-per-ref model): a branch `feat/review-panel` is the file `refs/heads/feat/review-panel`; a branch `feat/review-panel/x` needs `feat/review-panel` to be a directory. A path cannot be both. The packed-refs file has no such filesystem limit by itself, but Git still enforces the same rule across loose and packed refs (see B3).
- Relation to codebase: explains the constraint stated in the task (`feat/review-panel` and `feat/review-panel/<name>` cannot both exist). Supports (does not contradict) research item 2.18; its scratch-repo result takes precedence.
- Relevance: HIGH

### B2. Exact error text, directory/file conflict (reliability: forum/community thread, corroborated by a blog post; one vendor guide)
- Sources: https://news.ycombinator.com/item?id=38844343 (Hacker News thread quoting a reproduction with Apple Git 2.39.3); https://oneuptime.com/blog/post/2026-01-24-git-cannot-lock-ref-errors/view ; https://stackoverflow.com/questions/45141188/git-fatal-cannot-lock-ref
- Key information, creating the parent after the child exists (quoted from the HN reproduction): `fatal: cannot lock ref 'refs/heads/foo': 'refs/heads/foo/bar' exists; cannot create 'refs/heads/foo'`. Creating the child after the parent exists produces the mirror form (the HN thread shows `... 'refs/heads/test' exists; cannot create 'refs/heads/test/1'`; the oneuptime post shows `error: cannot lock ref 'refs/heads/feature/login': 'refs/heads/feature' exists`). So the text is `cannot lock ref '<new ref>': '<existing conflicting ref>' exists; cannot create '<new ref>'`; the `error:` or `fatal:` prefix depends on the command (`git branch` / `git checkout -b` / `git fetch`). The HN thread shows `find` output where `foo` is a directory (holding `bar`, `qux`) and `test` and `main` are ASCII text files. A Stack Overflow comment confirms the file/directory explanation and the fix: delete or rename the conflicting shorter branch, then the longer names can be created.
- Caveat: the message is shown here only through community reproductions on Git 2.39.3 (Apple) and blog posts, not through the Git manual. The exact wording can vary by Git version and ref backend; verify against the repository's Git version.
- Note: the same error text is also used for a different cause (stale `.lock` files, `Unable to create '...lock': File exists`). Only the `exists; cannot create` form is the name-hierarchy conflict.
- Relation to codebase: matches the failure the task expects for `feat/review-panel` versus `feat/review-panel/<name>`. If research item 2.18 recorded different exact wording, that scratch-repo output takes precedence.
- Relevance: HIGH

### B3. Conflict also detected against packed refs, and git fetch hints at `git remote prune` (reliability: Git commit message quoted in a Stack Overflow answer)
- Source: https://stackoverflow.com/questions/10068640/git-error-on-git-pull-unable-to-update-local-ref (quotes a Git commit by Ivan Tse, acked by Patrick Steinhardt, "refs: return conflict error when checking packed refs")
- Key information: `TRANSACTION_NAME_CONFLICT` is the internal error code for failing to create a ref due to a name conflict with another ref; the commit's example is a directory/file conflict between ref names `A/B` and `A`. `git fetch` uses it to recommend `git remote prune` to remove refs deleted on the remote. The commit fixes the case where the conflicting ref lives in packed refs, so the conflict is enforced whether the existing ref is loose or packed.
- Relation to codebase: extends the claim. Deleting the conflicting branch on the fork does not remove a stale remote-tracking ref in a local clone; run `git fetch --prune` (or `git remote prune origin`) before creating the other form. Relevant to this fork because Orca worktrees and several clones share `origin`.
- Relevance: MEDIUM

### B4. Same constraint applies to remote-tracking refs (reliability: blog posts, lower)
- Sources: https://dev.to/cristiansifuentes/git-remote-ref-lock-errors-advanced-diagnosis-and-recovery-1jmp ; https://medium.com/@nirbhaysingh281/error-cannot-lock-ref-refs-remotes-origin-release-exists-cannot-create-42230d262e23 (paywalled excerpt only)
- Key information: after a remote branch is renamed from `x` to `x/y`, a local fetch fails with `error: cannot lock ref 'refs/remotes/origin/<x>': ... exists; cannot create` because `refs/remotes/origin/x` is still a file; fix is `git fetch --prune` / `git remote prune origin` or removing the stale ref.
- Relation to codebase: practical risk if the review-panel branch name is renamed later (from `feat/review-panel` to `feat/review-panel/<name>`). Extends; no contradiction.
- Relevance: MEDIUM

### B5. Alternative ref backend: reftable (reliability: official docs for the option; blog for the motivation)
- Sources: https://git-scm.com/docs/git-refs ; https://tomodahinata.com/en/blog/git-internals-object-model-refs-index-packfile-guide ; https://gitperf.com/chapter-17.html
- Key information: `--ref-format=files` (loose files plus packed-refs) is the default; `reftable` is the alternative (git-refs migrate docs). The blog says Git's `BreakingChanges` document announces reftable as the default for new repositories in Git 3.0 and that reftable does not encode ref names as filesystem paths (so case-fold collisions disappear). gitperf.com says reftable is still marked experimental. UNVERIFIED by me: whether reftable also removes the leaf-versus-prefix restriction; none of the fetched pages states that, and I have not read git's reftable documentation for it. Do not assume it.
- Relation to codebase: the repo's ref backend is expected to be `files` (default); research item 2.18 tested the rule in a scratch repository and takes precedence for the actual behaviour.
- Relevance: LOW

## C. Naming conventions that avoid the conflict

### C1. Slashes group branches, but a group name cannot also be a branch (reliability: forum answer, widely cited; plus maintained knowledge-base page)
- Sources: https://stackoverflow.com/questions/273695/what-are-some-examples-of-commonly-used-practices-for-naming-git-branches ; https://idiv-biodiversity.github.io/git-knowledge-base/branch-naming-conventions.html
- Key information: The Stack Overflow answer recommends grouping tokens at the start of branch names and slashes to separate parts, with this caveat: "slashes can cause problems. Because branches are implemented as paths, you cannot have a branch named 'foo' and another branch named 'foo/bar'." The knowledge-base page recommends dashes between words, slash-separated grouping prefixes (`topic/`, `release/`, `hotfix/`, `wip/`), and lets prefixes combine (for example `hotfix/42687/buggy-thing`). Several blog posts (pullpanda.io, deepsource.com, conventionalbranch.org) recommend `<type>/<short-hyphenated-description>`, lowercase, hyphens; none of them (in the excerpts read) addresses the leaf-versus-prefix conflict.
- Practical rules that follow (derived, consistent with the sources): (1) a grouping prefix is never itself a branch name, so never create a branch named `feat/review-panel` if sub-branches `feat/review-panel/<name>` are wanted; (2) if one umbrella branch plus per-piece branches are wanted, use a hyphenated sibling form instead of nesting, for example umbrella `feat/review-panel` and pieces `feat/review-panel-<name>` (hyphen, not slash), or umbrella `feat/review-panel/main` (or `/base`, `/umbrella`) with pieces `feat/review-panel/<name>`; (3) choose the umbrella-versus-pieces layout BEFORE the first push, because renaming later leaves stale remote-tracking refs (B4) and any open PR on the old branch name has to be re-created or retargeted; (4) never use bare numbers as the leading part.
- Relation to codebase: the repo's current convention (`feature/*`, `fix/*`, `docs/*` off `integration`) has one slash level, `<type>/<name>`. That layout cannot hit the conflict as long as no branch is named just `feature`, `fix` or `docs`. The conflict appears only when a second slash level is added under an existing leaf branch. Extends the codebase finding; research item 2.18 takes precedence on what the repo's actual branches are.
- Relevance: HIGH

## D. GitHub native stacked pull requests

### D1. GitHub documentation (reliability: official docs)
- Sources: https://docs.github.com/en/pull-requests/get-started/about-stacked-prs ; https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/merging-stacked-pull-requests ; https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available
- Key information (docs): In a stack, "each pull request in the stack targeting the branch of the pull request below it", trunk at the bottom. Branch protection rules (such as CODEOWNER approvals) are enforced on every pull request in the stack, even mid-stack ones that do not target the default branch; CI checks triggered by pull requests on the default branch run for all pull requests in the stack, not just the bottom one. Merging is bottom-up only: a contiguous group starting from the lowest unmerged PR can merge together, a mid-stack PR cannot merge in isolation, and the PRs above "stay open and automatically re-target the stack's base branch". Merge requirements: all PRs below approved with passing checks, linear history, protection requirements met; otherwise a "Rebase stack" button appears (server-side cascading rebase; the docs say it retains approvals if the diff is unchanged). Merge commit, squash and rebase merge methods are supported, and stacks are merge-queue aware. Programmatic access exists (webhooks, REST, GraphQL); the CLI extension is `gh stack`. Once every PR in a stack has merged, the stack cannot be extended; new branches pushed with `gh stack submit` start a new stack.
- Key information (changelog, dated 2026-10-06 in the URL): the feature became generally available; branching stacks retarget automatically when the stack's base branch is deleted; Rebase stack preserves approvals for unchanged code.
- LIMITATION that matters here (docs, "Note"): "Stacked pull requests require all branches to be in the same repository. Cross-fork stacks are not supported." Not supported in GitHub Desktop.
- Relation to codebase: the fork `IronbellyOrg/IronClaude` is the only PR target and every branch would live in that one repository, so the same-repository rule is satisfied for fork-internal stacks (not verified against the repo's actual PR-creation path; `/sc:pr-submit --monitor 3` creates PRs with `gh pr create --repo IronbellyOrg/IronClaude` according to the task context, and I did not check whether it can set a non-default base or create stack links). Do not assume `gh stack` can be used from `/sc:pr-submit`; that is a codebase question for research item 2.18 and the pr-submit findings, which take precedence.
- Date caution: these pages carry 2026 dates; they were fetched on 2026-11-14 and match the current date context. The feature is new, so behaviour may still change.
- Relevance: HIGH

### D2. Community reports on rough edges (reliability: blog posts and a GitHub community discussion; lower)
- Sources: https://github.com/orgs/community/discussions/201439 (public-preview discussion, comments up to Nov 4, 2026) ; https://alphasignal.ai/news/github-ships-stacked-pull-requests-so-developers-stop-rebasing-branches-manually ; https://diffox.ai/blog/github-stacked-pull-requests ; https://www.dandoescode.com/blog/github-stacked-pull-requests
- Key information: (a) A commenter reports a stack misbehaving when the bottom branch is merged by squash and the stack was created from a not-yet-merged branch, and that `gh stack rebase --no-trunk` did not recover; (b) a bug report says the top PR of a squash-merged 3-PR stack went to `REVIEW_REQUIRED` / `DIRTY` after the merge even though it was approved on an unchanged head commit; (c) AlphaSignal (written during the preview period, so possibly out of date after the 2026-10-06 GA) says squash or rebase default merge settings break stack identity tracking after the first merge and suggests merge commits for stacked workflows; (d) diffox.ai says a hand-built chain after a squash needs `git rebase --onto`, and that with a hand-built chain branch protection and CI often trigger only for the bottom PR; (e) dandoescode.com says that even without the stack feature GitHub auto-retargets an open PR to `main` when its base branch is merged and deleted, and that merging stacked PRs one at a time with squash, without the tooling, rewrites the base the next PR was built on and can cause a mess.
- Treat (a)-(e) as unverified single-source reports; (c) and (d) conflict with the GA docs in D1 on whether squash is supported (the docs say it is). Prefer the docs; test before relying on either.
- Relation to codebase: extends. If the fork squash-merges (not confirmed in the codebase by me), a stack of review-panel PRs needs either the GitHub stack tooling or a manual `git rebase --onto` after each lower merge.
- Relevance: MEDIUM

## E. Manual stacked-branch practice: retargeting and `git rebase --onto`

### E1. `git rebase --onto` transplants the dependent branch after the lower branch is squash-merged (reliability: official docs for the option's existence; Stack Exchange and blogs for the recipe)
- Sources: https://git-scm.com/docs/git-rebase (has a section "TRANSPLANTING A TOPIC BRANCH WITH --ONTO"; the fetched excerpt did not include that section's body, so the recipe below rests on the community sources) ; https://softwareengineering.stackexchange.com/questions/365658/does-squashing-pull-requests-break-gits-merging-algorithm ; https://www.nutrient.io/blog/how-to-handle-stacked-pull-requests-on-github ; https://mreigen.medium.com/git-rebase-onto-the-trick-i-wish-id-known-for-stacked-pull-requests-275e7a5b661c (excerpt only)
- Key information: after `feature1` is squash-merged into `master` as a new commit `S`, `feature2` still carries `feature1`'s original commits, which are different commits from `S`. The recipe: `git rebase --onto master feature1 feature2` (a Stack Exchange comment notes the third argument avoids a prior checkout and that, if `feature1` was deleted, `git rebase --onto master HEAD~1 feature2` works by naming the boundary commit). Nutrient shows the same with `git rebase --onto main A` followed by `git push --force-with-lease`; after that the PR page shows only the changes not in `main`. Reason given: plain `git rebase` skips commits whose content is already upstream only when the patches are identical, so conflict-resolved duplicates survive and cause repeated conflicts; `--onto` names the exact boundary and avoids that.
- Retargeting: per dandoescode.com (D2), GitHub re-points an open PR to `main` automatically when its base branch is merged and deleted. The "Automatically delete head branches" repository setting is recommended for stacks by pullnotifier.com (F3, blog). I have not verified these two claims against GitHub's own non-stack documentation.
- Relation to codebase: extends. Applies if review-panel pieces are stacked by hand under `/sc:pr-submit --monitor 3` (which, per the task context, pushes fixes without asking: a force-push after `--onto` would need its own check; not verified here).
- Relevance: HIGH

### E2. `rebase.updateRefs` / `--update-refs` for stacks (reliability: blog posts; the option is documented in the git-rebase page, not fetched in the part returned)
- Sources: https://pullnotifier.com/tools/stacked-prs ; https://andrewlock.net/working-with-stacked-branches-in-git-part-1
- Key information: pullnotifier.com recommends at minimum `git config --global rebase.updateRefs true` so that rebasing the top branch of a stack also moves the intermediate branch refs; andrewlock.net shows an interactive rebase todo list containing `update-ref refs/heads/feature/part-1` lines, i.e. the todo-list command behind that feature. Neither page was read in full; the git-rebase manual excerpt I fetched did not include the option's text. Mark as UNVERIFIED against the official manual.
- Relation to codebase: none verified; a possible low-tooling option for hand-built stacks. Note the branch names in andrewlock's example (`feature/part-1`) use one slash level.
- Relevance: LOW

## F. Stacking tools: how each names branches and where it pushes

### F1. `gh stack` (GitHub CLI extension) (reliability: official repository and GitHub docs)
- Sources: https://github.com/github/gh-stack ; https://github.com/github/gh-stack/releases ; https://docs.github.com/en/pull-requests/reference/stacked-prs-cli-commands ; https://docs.github.com/enterprise-cloud@latest/pull-requests/get-started/stacked-prs-quickstart
- Key information: install with `gh extension install github/gh-stack`; requires GitHub CLI v2.0+ and Git 2.36+. Commands in the docs table: `gh stack init`, `add`, `view`, `checkout`, `modify`, `unstack` (plus `push`, `submit`, `rebase`, `sync` used in the quickstart and README). `submit` creates each PR with the correct base (first branch targets the trunk, each next branch targets the one below). `gh stack init` adopts existing branches and uses the repository default branch as trunk unless `--base` is given. A separate command creates or updates a stack from branch names or PR numbers without touching local tracking state, aimed at users of jj, Sapling or git-town. Release notes (two entries that disagree depending on version): one says the branch-name prefix and `--numbered`/`--prefix` flags were removed so names are used exactly as given (`gh stack add refactor/foo` creates `refactor/foo`); another says `--prefix` is the opt-in for a prefix. Verify the installed version's behaviour before relying on either.
- Relation to codebase: relevant to the naming conflict because the tool takes explicit branch names literally, so a stack such as `feat/review-panel/a`, `feat/review-panel/b` works only if no branch is named `feat/review-panel`; a stack whose bottom branch IS `feat/review-panel` must name its upper layers without a `feat/review-panel/` prefix. Whether `/sc:pr-submit` can drive `gh stack` is a codebase question (not checked here).
- Relevance: HIGH

### F2. Graphite (`gt` CLI) (reliability: vendor documentation; commercial product)
- Sources: https://graphite.com/docs/github-configuration-guidelines ; https://graphite.com/docs/create-submit-prs ; https://graphite.com/docs/command-reference ; https://graphite.com/docs/multiple-trunks ; https://www.learncursor.dev/compare/github-stacked-prs-vs-graphite-vs-origin (third-party comparison, lower)
- Key information: `gt submit` pushes every branch of the stack atomically and creates or updates one PR per branch (`gt submit --stack` includes descendants; `gt ss -np` is the short form); the docs say it pushes "all branches in your stack (and potentially a temporary base branch for each) atomically", so a GitHub setting that limits atomic push size can block large stacks. Graphite projects branch protection from the stack's base branch and REQUIRES the branch protection setting "Dismiss stale pull request approvals when new commits are pushed" to be Disabled. The comparison page adds a second setting Graphite asks to turn off (require approval of the most recent reviewable push) and a price list (free Hobby, $20 Starter, $40 Team per user per month, annual billing) that I did not verify against Graphite's own site. Graphite supports multiple trunks and merges stacked PRs only into their trunk. Own reports that a CI check can prevent merging a PR before its lower PRs have merged (dev.to guide from Semgrep, https://dev.to/semgrep/a-guide-to-using-graphites-stacked-prs-for-github-users-5c47, blog).
- Relation to codebase: extends. A commercial tool and its repository-setting requirements (stale-approval dismissal off) would change fork-level settings; not a fit for a fork where PR review and approvals are bot-driven (the codebase mentions Augment and Codex reviews through `/sc:pr-submit`; I did not verify how those bots treat stale approvals).
- Relevance: MEDIUM

### F3. ghstack (reliability: official repository README)
- Source: https://github.com/ezyang/ghstack
- Key information: every local commit becomes its own PR and is pushed to three branches: `gh/<username>/<n>/base`, `gh/<username>/<n>/head` and `gh/<username>/<n>/orig`. `base` and `head` are never force-pushed (rebases add merge commits on top of `base`). Because the branch bases are not `main`, these PRs cannot be merged with the normal GitHub merge button; the README says to use `ghstack land <PR URL or #N>` (or a bot). Design constraints stated by the README: a PR is always created in the repository holding the base branch, so branches must be pushed to the upstream repository where the PRs are wanted, which leaves stale branches that need a separate pruning mechanism; branch names do not carry the PR number because a number cannot be reserved in advance.
- Note on naming: the `<n>/base`, `<n>/head`, `<n>/orig` layout puts leaves under a per-change directory, which never makes a parent also a branch, so by construction it does not trigger the leaf-versus-prefix conflict.
- Relation to codebase: ghstack's "never mergeable via the GitHub merge button" constraint conflicts with the fork's PR path through `/sc:pr-submit --monitor 3` (a codebase fact stated in the task context; not re-verified). Treat as a negative fit unless pr-submit research says otherwise.
- Relevance: MEDIUM

### F4. git-branchless and related commit-stack tools (reliability: official repository README; blog for PR creation)
- Sources: https://github.com/arxanas/git-branchless ; https://olivernguyen.io/w/stacked.prs ; https://benjamincongdon.me/blog/2021/12/07/Branchless-Git
- Key information: git-branchless is a suite of tools (`git undo`, smartlog, `git restack`, `git sync` to rebase all local stacks without checking them out, `git move` to move subtrees). It is branch-optional ("100% compatible with branches"). The README excerpt I read does not describe creating GitHub PRs; olivernguyen.io pairs it with a separate tool, `git-pr`, which creates one PR per commit and appends a `Remote-Ref:` attribute to each commit message (needs a blank line before it). Benjamin Congdon names ghstack, `epage/git-stack` and Stacked Git as related tools.
- Relation to codebase: no branch-name conflict by design (commit-based); not integrated with `/sc:pr-submit` as far as I know (not verified).
- Relevance: LOW

## G. How reviews and CI treat stacked PRs

### G1. Review and approvals (reliability: official docs plus vendor blogs)
- Sources: https://docs.github.com/en/pull-requests/get-started/about-stacked-prs ; https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available ; https://pullnotifier.com/tools/stacked-prs ; https://graphite.com/docs/github-configuration-guidelines

A stack is a way to land a multi-piece unified review panel in dependency order while each piece is reviewed alone; the lower piece gates the upper one under GitHub's bottom-up merge rule. Whether the repo's review bots (Augment, Codex) review the diff against the stack base or against `master` is not verified here.

## Key External Findings

1. (HIGH, official docs) Git stores a branch as a ref path; loose refs are one file per ref under `$GIT_DIR/refs/heads`, with `packed-refs` as a flat fallback (git-pack-refs, gitrepository-layout). `git check-ref-format` lists the syntax rules and none of them forbids `feat/review-panel` or `feat/review-panel/<name>` individually; the conflict is a ref-store constraint found only at creation time.
2. (HIGH, community reproductions) Error text: `cannot lock ref 'refs/heads/<new>': 'refs/heads/<existing>' exists; cannot create 'refs/heads/<new>'`, with `error:` or `fatal:` prefix by command. Seen on Git 2.39.3; exact wording can differ by version. The same "cannot lock ref" phrase is also used for stale `.lock` files, a different cause.
3. (MEDIUM) The conflict is also enforced against packed refs and remote-tracking refs; after a remote rename, `git fetch --prune` / `git remote prune origin` is the documented hint.
4. (HIGH) Naming rule: a path used as a branch can never also be a group prefix. Pick umbrella-versus-pieces layout before the first push: either hyphenated siblings (`feat/review-panel`, `feat/review-panel-<name>`) or a named umbrella leaf under the group (`feat/review-panel/main` with pieces `feat/review-panel/<name>`). The repo's one-slash `feature/<name>` layout cannot hit the conflict unless a branch is named just `feature`.
5. (HIGH, official docs) GitHub native stacked PRs are generally available (changelog dated 2026-10-06): each PR targets the branch below, merges are bottom-up only, upper PRs auto-retarget, branch protection and CI evaluated for every layer, "Rebase stack" keeps approvals for unchanged diffs, merge commit/squash/rebase and merge queue supported. Hard limit: all branches must be in the same repository; cross-fork stacks are not supported.
6. (HIGH) Hand-built stacks after a squash-merge of the lower PR need `git rebase --onto <trunk> <old-lower-branch> <upper-branch>` plus `git push --force-with-lease`; GitHub (per a blog, unverified against GitHub docs) re-points the upper PR to `main` when its base branch is merged and deleted.
7. (MEDIUM) Third-party tools: Graphite needs "dismiss stale approvals" off and pushes atomically (possibly with a temporary base branch per PR); ghstack uses `gh/<user>/<n>/{base,head,orig}` branches and its PRs cannot be merged with GitHub's merge button; git-branchless is commit-based and needs another tool for PRs.
8. (MEDIUM) Reviews and CI: reviewers see per-layer diffs; each layer runs CI, so a lower-layer change re-runs pipelines for the whole stack (CircleCI blog). Source conflicts between older blogs (no squash on intermediate PRs, merge queue cannot order dependent PRs) and GitHub's GA docs are flagged in G3; prefer the docs.

## Recommendations from External Research

These are options from external sources; the codebase (research item 2.18 and the pr-submit findings) takes precedence wherever it disagrees.

1. Name the unified Review Panel branches so that no branch name is also a prefix of another: either hyphenated siblings, or an explicit umbrella leaf (for example `feature/review-panel/base`) when several `feature/review-panel/<piece>` branches are wanted. Decide before the first push; renaming later leaves stale remote-tracking refs and re-opens or retargets PRs.
2. If the pieces land as a dependency-ordered series, the GitHub-native stack (same-repository only, satisfied by fork-internal branches) is the lowest-friction option, but first confirm in the codebase that `/sc:pr-submit --monitor 3` can create stacked PRs or set a non-default base. If it cannot, the alternative is sequential PRs, each opened only after the lower one merges and the upper branch is rebased with `git rebase --onto`.
3. If PRs are stacked by hand, check the repository's CI workflow `branches:` filters first: a PR whose base is another feature branch may not trigger `master`/`integration`-filtered workflows (unverified, see G2).
4. Avoid ghstack for this repository (PRs not mergeable through the normal merge button) and avoid Graphite unless the repository settings it needs (stale-approval dismissal off) are acceptable.
5. For Section 5.3 (sequence-and-gates): treat bottom-up merge order as a gate (a lower piece must be approved and green before an upper piece can merge) and plan CI cost: each lower-layer fix re-runs checks for all layers above it.
