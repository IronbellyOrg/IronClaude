## 1. Overview

Supervised orchestration is the way an Orca *coordinator* session, opened by a person, plans work, creates Orca Tasks and starts one *worker* session per Task, where each worker runs the `Command:` lines of its brief in order (usually one IronClaude `/sc:` command; chained lines are governed by WC-7, WC-14 and WC-15, `WORKER-CONTRACT.md:60,63,64`), each with the `--unattended` flag, and reports back once per Task. The rules for this live in one normative file, `src/superclaude/core/WORKER-CONTRACT.md` (terms, command-side rules WC-2 to WC-15, the worker's duties, the coordinator's rules and a brief template), which the installer copies to `~/.claude/WORKER-CONTRACT.md`. NORMATIVE, `WORKER-CONTRACT.md:3,5`. The dispatch preamble that Orca gives each worker, not this repo, is the authority for Orca verb syntax and heartbeat cadence (`WORKER-CONTRACT.md:7`); the generator is `buildDispatchPreamble` in the Orca source (`IronOrca/src/main/runtime/orchestration/preamble.ts:52-152`, ORCA-CHECKOUT, per `research/gap-P3-G01.md` S1).

Almost all authority in this system is instruction text read by language-model sessions. The IronClaude code that exists around it is narrow: one lexical PreToolUse hook that blocks `orca worktree create` without `--agent` (and only when the command word is `orca`); a launch-level guard and a job-identity helper that govern only sessions launched by the `/sc:issue --claim` script; Python launchers (the claim script and the issue watcher) that start non-worker Claude sessions (not supervised workers) through `orca agent launch`; and an installer and doctor that copy the contract, hooks, ccsession and (by asking Orca) the Orca skills. CHECKOUT, `research/01` sections A, C; `research/03` sections A, F; `research/04` F4. No IronClaude code runs the coordinator loop, detects a worker run, writes or reads a worker result, or distinguishes a coordinator from a worker (`research/02` section 7 takeaways 1-2; `research/gap-P3-G04.md` 4.4; `research/01` G1). The contract is installed (`src/superclaude/cli/install_core.py:27` lists it) and pointed to from `HOW-WE-WORK.md:398-403`, but it is not `@`-imported (`core/CLAUDE.md:3` imports only `BASH_INSPECTION_POLICY.md`; the file has no other reference to it), and no hook or startup step that loads it into a coordinator session was found (search limited to the three guard scripts and `hooks.json`; other hooks and ccsession [UNVERIFIED]), so section 4 binds a coordinator only if that session reads the file (`research/02` 6.1). Orca itself contributes some machine-side controls (worker-start scope, a nested-worker depth cap, a narrow Run-binding refusal) whose defaults differ by build and whose effective setting on the running Orca is [UNVERIFIED] (`research/05` section 5.2).

Two boundaries frame every statement in this document. Subordinate (sub-orchestrator) mode is deferred and not implemented: no command, skill, flag or contract role exists, worker fan-out is barred by WC-13 (`WORKER-CONTRACT.md:62`, text), and the related design question is owned by open issue #444 (re-read 2026-11-12: OPEN, as are #339, #423, #431). The ownership wording clarification ("The eligible session that creates a worktree owns its agent(s). ... A supervised orchestrator's coordinator is person-opened", `src/superclaude/core/CLAUDE.md:57-61`) exists only as an uncommitted edit set in this worktree; HEAD, `origin/master` and the HOST-INSTALLED `~/.claude/CLAUDE.md` still carry the older wording "becomes its orchestrator, or a coordinator under another orchestrator", and the clarification does not resolve the future-role question or claim any rollout (`research/01` A.1, `research/06` F5-F6, `gaps-and-questions.md` section B last bullet).

The terms and codes used below (WC-n, S0-S11, ESCAPE, the guard levels, IR-4, IR-7, L2, T-SPD-5, SD-1, `LL-*`, ccsession, shim check) are defined in section 16 (Glossary).

**What it does:** Defines and partly enforces how an Orca coordinator (person-opened) dispatches IronClaude commands to unattended worker sessions, keeps workers from fanning out or acting outward, and launches non-worker claim and watcher sessions, the claim-launched ones under a launch-level guard.

**Who uses it:** A person who opens an Orca coordinator session and the LLM coordinator that follows `WORKER-CONTRACT.md` section 4; worker sessions that follow sections 1-3; the `/sc:issue --claim` flow and the issue watcher (non-worker launched sessions); maintainers of the hooks, installer and contract. Orca (a separate product) supplies the runtime, preamble and mailbox.

**Where it lives:** Contract and guidance in `src/superclaude/core/`; guards in `src/superclaude/hooks/` (installed flat to `~/.claude/hooks/`); launchers in `src/superclaude/skills/sc-issue-protocol/scripts/orca_worktree.py` and `src/superclaude/cli/issue_watch/launch.py`; ccsession in `src/superclaude/skills/ccsession-tag/`; installer in `src/superclaude/cli/install_*.py`; per-command rules in `src/superclaude/commands/*.md`. Orca-side behavior is documented from `IronOrca/src/main/runtime/` (external) and `/opt/Orca/resources/app.asar.unpacked/out/` (installed files).

**Key numbers:** 2 session roles (coordinator, worker) plus the person; 5 owner decisions D1-D5 (historical record `.dev/orca-command-refactor/decisions/APPROVED.md:8-12`); contract rules WC-2 to WC-15 (there is no WC-1) in a 327-line contract; 31 of 46 command files carry `## Unattended mode` (16 in phase P1, 15 in P2; re-counted 2026-11-12: 31), 8 command names are barred from workers; 3 guard scripts with 4 registrations in `hooks.json` (one PreToolUse hook per script, the launch-level guard also on UserPromptSubmit; timeouts 3 s for the worktree gate, 5 s for the guard and the identity hook); 7 uncommitted modified files (`CLAUDE.md`, `src/superclaude/core/CLAUDE.md`, `src/superclaude/skills/ccsession-tag/README.md`, both copies of `require-orca-worktree-agent.sh`, `tests/core/test_orca_session_launch_guidance.py`, `tests/hooks/test_require_orca_worktree_agent.py`; `git status --short` re-run 2026-11-12); 2 Orca builds in play (checkout 1.4.214 and installed files 1.4.245-aidev02.9cfecdd30b2a); test runs on record: 739 + 5 passed, 12 live observations skipped.
