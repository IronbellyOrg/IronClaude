**Q1. Timeout behavior (command hooks on PreToolUse)**

- Quote: "Claude Code cancels a `command`, `http`, or `mcp_tool` hook that reaches its `timeout`, discarding the hook's output, so on most events a timed-out hook renders no decision."
- Quote: "On `PreToolUse`, a timed-out `command`, `http`, or `mcp_tool` hook doesn't block the tool call, except for hooks whose failure blocks the action. The call continues through the normal permission flow, so don't count on a stalled hook to act as a gate."
- Quote ("Block the action when a hook fails" section): "On most events, when a hook fails or times out, Claude Code still carries out the action. A policy hook with a wrong path or a crashing script then lets everything through. To block the action instead, set `\"onFailure\": \"block\"` on a `command` or `http` hook. Requires Claude Code v2.1.295 or later."
- Exception named in that section: "On Windows without Git Bash, a shell-form `PreToolUse` or `PermissionRequest` command hook that fails with `onFailure` unset can instead block the tool call." (the Windows case is out of scope for this Linux host; recorded so the reference does not over-generalize)
- Other events differ: `PreModelSwitch` "a hook canceled at its timeout blocks the model switch"; for `UserPromptSubmit`, a command hook at its timeout "is canceled and its output ... is discarded. The prompt still reaches Claude without that context." Default timeouts: `UserPromptSubmit` 30 s; "the 600-second default for those types on most other events".
- Contrast for SDK callbacks: "An Agent SDK callback hook that exceeds its timeout blocks the tool call" (callback hooks are a different mechanism from the shell-command hooks registered in `hooks.json`).
- Not stated in the chunks read: which signal cancels the process (TERM or KILL), whether the user sees any message for a timed-out PreToolUse hook (the docs say a non-blocking error shows a `hook error` notice on events such as `PreToolUse`, see Q2, but the chunks do not say a timeout counts as such an error), and the unit of the `timeout` field (the "600-second default" and "30 seconds" wording imply seconds). [UNVERIFIED for the signal and for the message]
- Support for the code-side statements: SUPPORTS the design's harness fact V8 ("a crashing or timed-out hook does not block", `research/gap-P3-G06.md:56,62,110`) as DOCUMENTED host behavior for `command` hooks on `PreToolUse` when `onFailure` is unset. It adds a fact the code-side files do not state: the `onFailure: "block"` field makes a timeout block (v2.1.295 or later). `merged-requirements.md:98,694,701` (cited at `gap-P3-G06.md:57`) says `onFailure: "block"` "is not set on either registration: it would block ordinary sessions whenever the hook breaks (V8)": the docs agree that the field blocks on failure and on timeout, so the design's rejection and its reason match the docs. **Q2. Exit-code contract and JSON decision output**

- Exit 0 (quote): "Success: your hook exits 0. Claude Code applies any JSON output fields your hook printed, and the action goes ahead unless those fields block or deny it."
- Exit 2 (quote): "Blocking error: your hook exits 2. On events that can block, Claude Code stops the action: a `PreToolUse` hook blocks the tool call". "The message that comes with the block is your hook's stderr. If your hook also printed JSON that makes a blocking decision, Claude Code uses that decision's reason instead. Exit 2 blocks even when your hook prints JSON".
- Other non-zero (quote): "Non-blocking error: your hook exits with any other code, or fails in some other way, such as not starting or printing invalid JSON. The action goes ahead, except for hooks whose failure blocks the action, for example a hook with `onFailure` set to `\"block\"`. On events such as `PreToolUse`, you see a `hook error` notice in the transcript." (the current page, re-fetched 2026-11-12, words the notice `<hook name> hook error`)
- Qualification, same section ("Exit code output" and its table, re-fetched 2026-11-12 by WebFetch): "What your hook prints to stdout can change the outcome. For example, when a `PreToolUse` hook exits 1 but prints JSON that passes validation, that JSON can still decide what happens." Table, column "Any other exit code": schema-valid JSON object = "Success. Claude Code ignores the exit code, and the fields alone decide" (for hooks whose failure blocks the action the run counts as a failure instead); JSON that cannot be parsed or fails schema validation = "Non-blocking error"; plain text or nothing = "Non-blocking error. The notice carries the first line of your stderr". Column "Exit 2" with schema-valid JSON: "Blocking error. Claude Code still reads the fields, but they can't override the block". Subsection "Other exit codes": "Exit code 1 without valid JSON output is a non-blocking error unless the hook is one whose failure blocks the action, even though 1 is the conventional Unix failure code. If your hook is meant to enforce a policy, use `exit 2`." So "any other code is a non-blocking error" holds only when stdout is plain text, empty or invalid JSON.
- Stderr visibility (quote): "Claude never sees stderr from a hook that exits 0."
- PreToolUse JSON output: `hookSpecificOutput` with `permissionDecision` (`allow`, `deny`, `ask`, `defer`) and `permissionDecisionReason`. Quote: "PreToolUse previously used top-level `decision` and `reason` fields, but these are deprecated for this event ... The deprecated values `approve` and `block` map to `allow` and `deny` respectively."
- `updatedInput` (quote): "Modifies the tool's input parameters before execution. Replaces the entire input object, so include unchanged fields alongside modified ones. Claude Code evaluates permission rules and a Bash command's auto-background eligibility against the input your hook returns, not the input Claude sent. Combine with `allow` to auto-approve, or `ask` to show the modified input to the user. For `defer`, ignored. With no `permissionDecision`, auto mode can deny the changed call."
- Auto mode (quote): when a hook returns `updatedInput` with no `permissionDecision` in auto mode, "Claude Code can deny the changed call. The server reviewed the input Claude wrote, not the input your hook returned"; the denial text is "a hook changed this call's input after auto mode reviewed it" (in interactive terminal sessions and VS Code sessions on a direct connection to the Anthropic API); "Claude can issue the changed call again so that the server reviews it." The same section continues (hooks reference, "PreToolUse `updatedInput` in auto mode", re-fetched 2026-11-12 by WebFetch): "In the sessions that show this text, a `command` hook in settings or a plugin's hooks file can change Bash, PowerShell, Monitor, Edit, Write, and NotebookEdit calls without this denial. The denial can still appear, such as when any hook changed an earlier call in the same Claude response or a Bash command asks to run outside the sandbox." On a repeated call: "If Claude repeats the changed input exactly in its next response, your hook still runs: It can deny the call or send it to the permission prompt; Any `updatedInput` it returns is dropped, so what runs is what the server reviewed." ("Dropped" refers to a repeated changed call only.)
- `deny` and exit 2 in every permission mode (ADDED in fix cycle 1; Source 2, the hooks guide, "Limitations and troubleshooting" > "Hooks and permission modes", re-fetched 2026-11-12 by WebFetch; official; relevance HIGH for the guards' design). Verbatim: "**`"deny"` in every permission mode**: a hook that returns `permissionDecision: "deny"` blocks the tool even in `bypassPermissions` mode or with `--dangerously-skip-permissions`. `PreToolUse` hooks fire before any permission-mode check, in every permission mode, including `dontAsk`. This lets you enforce policy that users can't bypass by changing their permission mode." Exit 2 routes the same way (hooks reference, "PreToolUse decision control", re-fetched 2026-11-12): "A hook that blocks by exiting 2 routes the same way as `"deny"`: Claude sees the stderr message as the denial reason." Caveat kept on `allow` (same guide section): "a hook returning `"allow"` doesn't bypass deny rules from settings, and it can't suppress the prompt for" network-path reads, MCP tools marked `requiresUserInteraction`, tools an Agent SDK app marks `always_ask`, and connector tools an organization set to `ask`. Relation to the code side: SUPPORTS, as DOCUMENTED behavior, the design's harness facts V2 and V3 ("a PreToolUse exit 2 blocks, also with permission prompts off", `research/gap-P3-G06.md:56`) and bears on the Orca prompt-carrying launches that pass `--dangerously-skip-permissions` (`research/gap-P3-G05.md:170`): per the docs a guard's `deny` or exit 2 still blocks there. Documented, NOT observed on this host: it does not close the pending live observations (OB-H1 items, OB-H2, OB-H3) and says nothing about the installed build.
- Support for the code-side statements: SUPPORTS the Orca hook's decision contract at `research/03-guards.md:23` ("allow = exit 0; block = one message on stderr + exit 2; never exit 1"): exit 2 with stderr is the documented block; exit 1 WITHOUT schema-valid JSON on stdout would be a non-blocking error (the call goes ahead and a `<hook name> hook error` notice shows), and exit 1 WITH schema-valid JSON on stdout is decided by the JSON fields, the exit code being ignored. **Q3. Parallel or sequential, and conflict resolution**

- Parallel (quote): "When an event fires, its matching hooks run in parallel. If more than 12 of them are prompt or agent hooks, 12 of those run at once and the rest start as running ones finish. Each waiting hook's `timeout` starts counting when that hook starts."
- Deduplication (quote): "If you define the same handler in more than one settings file, it runs once. A plugin's or skill's copy of the same handler stays separate."
- Decision conflicts (quote): "When multiple PreToolUse hooks return different decisions, precedence is `deny` > `defer` > `ask` > `allow`. A hook that blocks by exiting 2 routes the same way as `deny`: Claude sees the stderr message as the denial reason."
- Conflicting `updatedInput` from several hooks: NOT STATED on this reference page (the precedence sentence covers `permissionDecision` values only), but ANSWERED in Source 2 (the hooks guide, "Limitations and troubleshooting" > "Limitations"): "When multiple `PreToolUse` hooks return `updatedInput` to rewrite a tool's input, Claude Code doesn't merge the rewrites or guarantee which rewrite the tool runs with. Avoid having more than one hook rewrite the same tool's input." Quote re-confirmed verbatim in fix cycle 1 (2026-11-12, WebFetch of https://code.claude.com/docs/en/hooks-guide). Documented answer: no merge, no guaranteed winner. Only the behavior OBSERVED on this host stays [UNVERIFIED].
- Support for the code-side statements: ANSWERS the open question at `research/03-guards.md:103,328` ("whether Claude Code runs the matching hooks serially or in parallel"): the docs say parallel. This means the array order in `hooks.json` (`research/03-guards.md:103` "The registration gives an array order") is not documented as an execution order for matching hooks; the docs do not say array order has any effect. Note a consequence the code-side files should state with care: with parallel execution, a `deny` or exit 2 from the worktree gate or the guard wins over any `allow` from another hook by the documented precedence, but a rewrite by `launch-job-identity.sh` and a block by another hook are decided independently (no documented ordering between them). ## Key findings

1. A `command` hook on `PreToolUse` that reaches its `timeout` is canceled, its output is discarded, and the tool call is NOT blocked; it continues through the normal permission flow, unless the hook sets `"onFailure": "block"` (documented as requiring Claude Code v2.1.295 or later). The docs say "don't count on a stalled hook to act as a gate". Source 1. This is documented host behavior and matches the design's V8.
2. Other failures: a hook that cannot start, invalid or schema-failing JSON, and any exit code other than 0 or 2 with plain-text, empty or invalid-JSON stdout are non-blocking errors for a hook with `onFailure` unset; the action goes ahead and a `<hook name> hook error` notice shows (first stderr line). Exception: any other exit code WITH schema-valid JSON on stdout is not an error; the exit code is ignored and the JSON fields alone decide ("when a `PreToolUse` hook exits 1 but prints JSON that passes validation, that JSON can still decide what happens"). Source 1, "Exit code output" (re-fetched 2026-11-12).
3. Exit 2 blocks the tool call and the message is the hook's stderr; exit 2 blocks even when the hook also prints JSON; exit 0 applies any JSON the hook printed. Source 1.
4. JSON decisions for `PreToolUse` use `hookSpecificOutput.permissionDecision` (`allow`, `deny`, `ask`, `defer`) plus `permissionDecisionReason`; top-level `decision`/`reason` are deprecated for this event. `updatedInput` replaces the whole input object and permission rules are evaluated against the rewritten input; in auto mode a rewrite with no `permissionDecision` can be denied, but the same section says a `command` hook in settings or a plugin's hooks file can change Bash (and PowerShell, Monitor, Edit, Write, NotebookEdit) calls without this denial in the sessions that show the denial text; the denial can still appear when any hook changed an earlier call in the same response or a Bash command asks to run outside the sandbox; on a repeated changed call any `updatedInput` the hook returns is dropped. Relation to the repo's identity hook (a settings `command` hook that rewrites Bash): partly answered, documented only, host behavior UNVERIFIED (Q2). Source 1, re-fetched 2026-11-12.
5. Matching hooks run in parallel and completion order is non-deterministic; every matching hook runs to completion (a sibling's `deny` does not stop it); decisions merge by `deny` > `defer` > `ask` > `allow`; `additionalContext` from every hook is kept. Sources 1, 2, 3.
6. Several `updatedInput` rewrites are not merged and the docs give no guarantee which one the tool runs with. Source 2 (hooks guide).
7. Hooks from settings, managed policy and plugins run inside subagents with `agent_id` and `agent_type` in the input. Source 1.
8. Documented (fix cycle 1, re-fetched 2026-11-12): a `PreToolUse` hook that returns `permissionDecision: "deny"` blocks the tool "even in `bypassPermissions` mode or with `--dangerously-skip-permissions`", because "`PreToolUse` hooks fire before any permission-mode check, in every permission mode, including `dontAsk`"; a hook that blocks by exiting 2 "routes the same way as `"deny"`". An `allow` is weaker: it does not bypass settings deny rules or suppress the prompts the guide lists. Sources: Source 2 (hooks guide, "Hooks and permission modes") and Source 1 (hooks reference). Documented behavior, not observed on this host.

## Summary

Anthropic's own Claude Code hooks reference says a `PreToolUse` command hook that reaches its timeout is canceled, its output is discarded and the tool call is not blocked, unless the hook sets `onFailure: "block"` (v2.1.295 or later); this is documented behavior consistent with the design's harness fact V8, not an observation of this host. Exit 2 blocks (stderr is the reason), exit 0 applies the JSON, and any other code with plain-text, empty or invalid-JSON stdout, or a failure to start, is a non-blocking error with a `<hook name> hook error` notice (any other code with schema-valid JSON is decided by the JSON); `PreToolUse` JSON uses `hookSpecificOutput.permissionDecision` and `updatedInput` replaces the whole input, with a documented auto-mode denial that settings `command` hooks are exempt from in the sessions that show it. Matching hooks run in parallel with non-deterministic completion order, all run to completion, decisions merge by `deny` > `defer` > `ask` > `allow`, and several `updatedInput` rewrites are neither merged nor ordered, so the `hooks.json` array order is not a documented execution order. Hooks also run inside subagents, and a `PreToolUse` `deny` or exit 2 blocks in every permission mode including `bypassPermissions` (documented, not observed on this host). Still undocumented in what was read: the cancel signal, any message for a timeout with `onFailure` unset, the `session_id` of subagent payloads, and the installed build's version.
