### A.2 `_find_orca() -> str | None` (`:198-221`)

1. For each name in `_ORCA_CLIS` (`:204`) take `shutil.which(name)` (`:205`); skip when absent (`:206-207`).
2. Probe `[path, "skills", "list", "--json"]` with `capture_output`, `text`, `timeout=10`, `stdin=DEVNULL` (`:209-215`), then `json.loads(probe.stdout).get("topics", [])` (`:216`). `OSError`, `subprocess.SubprocessError` (this includes `TimeoutExpired`), `ValueError`, `AttributeError` raised inside that `try` skip the candidate (`:217-218`).
3. Accept the candidate only when `probe.returncode == 0` and some topic has `t.get("name") == "orca-cli"` (`:219-220`); otherwise try the next name; return `None` after both (`:221`). The docstring `:199-202` gives the reason: on Linux a bare `orca` is usually the GNOME screen reader, so each candidate must prove it answers `skills list` like Orca.
4. [CODE-VERIFIED] Edge case outside the `try`: line `:219` reads `topics` after the `try` block. A probe that exits 0 with a `topics` value that is null, an int, a bool, a non-empty string, a non-empty object, or a list whose first non-matching element is not an object raises `AttributeError` or `TypeError` out of `_find_orca`. `tests/issue_watch/test_find_orca_parity.py:1-19` and `:173-188` pin exactly this ("the original raises") as the one deliberate difference from `launch.find_orca`. `install_orca_skills` calls `_find_orca()` at `:240` with no `try`, `install_user_setup` calls `install_orca_skills` at `:456` with no `try`, and `main.install` calls `install_user_setup` at `main.py:236` with no `try`. So a malformed `skills list --json` reply from an `orca-ide` on PATH would abort `superclaude install` with a traceback at step 7, before the codegraph phase and the retire step run. Reachability with a well-formed Orca: none seen; Orca's own handler returns `{"topics": [{"name", "description"}, ...]}` (`/home/coder/workspaces/IronOrca/src/cli/handlers/skills.ts:8-19`, Orca development checkout). Reachability with a different program named `orca-ide`: [UNVERIFIED].
5. `_find_orca` is run for every non-skipped call, so it spends up to 10 s per candidate (20 s worst case) before the install request starts, and that time counts against the deadline (A.3).

## H. Key takeaways

1. The three Orca guides are produced only by Orca; IronClaude contributes exactly one thing, a request to `skills install` made during step 7 of `install`/`update`, which can never fail the command and is skipped with a one-line notice when no working Orca CLI is found (A.3, F.1). Feeds 8.3.
2. `install` skips the request when all three files exist; `update` and `install --force` always make it, but never ask Orca to overwrite an edited copy (A.3). Feeds 8.3 and 9.1.
3. The Orca step shares a 30 s deadline with the plugin step; with the probes it can use all of it (A.3, E). Feeds 9.1.
4. The installer checks `~/.claude/skills` while Orca follows `CLAUDE_CONFIG_DIR`; the installation guide's "always writes under `$HOME/.claude/`" does not hold for this step (A.5, E). Feeds 9.1 and 14.
5. `install_orca_skills` is non-fatal, but its helper `_find_orca` can raise on a malformed reply and nothing above it catches (A.2 item 4). Feeds 8.3 and 10.
6. `wire_ccsession` links `ccsession-orca` but does not configure Orca; the doctor requires the link while the installer tolerates its absence (B.1, C.2). Feeds 8.3 and 14.
7. The doctor does not check the Orca skills, an Orca CLI, the guard hooks or the contract file (C.2, C.3). Feeds 14.
8. The host stubs are Orca-shipped text identified by digest; their writer on this host is not established (F). Feeds 15.
