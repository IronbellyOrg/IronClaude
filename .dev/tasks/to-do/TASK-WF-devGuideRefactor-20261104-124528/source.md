Refactor `docs/developer-guide/SuperClaude-Developer-Guide-Commands-Skills-Agents.md` so every future command, skill and agent is authored to run correctly under Orca orchestration (the `/orchestration` skill: an Orca coordinator session dispatching IronClaude `/sc:` commands to worker sessions).

Why: the Orca worker-contract work on this branch (commit 8db29f11) added `src/superclaude/core/WORKER-CONTRACT.md` (installed to `~/.claude/WORKER-CONTRACT.md`), an "Orca coordination" section at the end of `src/superclaude/core/HOW-WE-WORK.md` (mirrored byte for byte in `plugins/superclaude/skills/sc-recommend/refs/HOW-WE-WORK.md`), and `tests/skills/test_worker_contract.py`. The developer guide was never updated: its last change was 2f10a0e1 and it never mentions Orca, `--unattended`, `--report-dir`, the `## Unattended mode` section, the worker contract fields, the never-as-worker list, the nested propagation rule, the person-mode flag refusal, or WC-2, WC-4, WC-7, WC-8, WC-9, WC-10, WC-11.

This request replaces the earlier inline request for the same change (package `.dev/tasks/to-do/TASK-WF-refactorDocsDeve-20261104-062532/`). ## Corrections the plan must carry

These come from the review of the earlier plan. Each is a requirement on the new plan.

- Worker fields and a command's own status (review M-01, blocking). Every place the guide talks about the worker contract file states both WC-4 cases: a command that already writes `return-contract.yaml` in the report directory itself keeps every existing field, including its own `status`, and adds the worker fields beside them; a command whose own contract lives elsewhere leaves that file unchanged, and the worker contract at `<report-dir>/return-contract.yaml` lists it in `artifacts`. No sentence says "add `worker_status` beside `status`" without the first case's condition. Appendix A's `## Return Contract` is a table of fields a skill returns to its calling command, not a report file; its new comment only points to 5.9 and states no rule about this table.
- Who may ask whom (review M-02, blocking). The agent-patterns text uses separate sentences for three rules: only the top-level worker session sends lifecycle messages (heartbeat, ask, check, `worker_done`), never a subagent (WC-7); a command never calls `worker-start`, `dispatch` or `task-create`, so no agent inside it does (WC-8); under `--unattended` nothing asks the person, because each gate resolves by a documented default, a caller flag, or blocked (WC-2), and only the worker session may put a blocked question to the coordinator, and only when the brief allows it (WC-3). No sentence says or implies that the worker session asks the person. An acceptance criterion checks for that false reading.
- Rule anchors (review M-03, M-12). Agent rules cite WC-7 and WC-8, not WC-13 (WC-13 binds the worker's top-level session). "A command's own Agent-tool fan-out stays as it is" is cited to WC-7. WC-7 is presented as a worker-session duty, not a command-side rule. `blocked_question` and `reason` are described as conditional fields (`blocked_question` when blocked; `reason` when failed, and for `/sc:implement` also when blocked).
- Report directory flag (review M-06). Wherever the guide lists `--report-dir`, it carries WC-4's condition: a command uses its own directory-valued `--output` or `--output-dir` as the report directory; `--report-dir` is for a command without such a flag, or for a brief that does not pass it; passing both, or neither, is refused before any work.
- Status mapping (review M-09). The 5.9 mapping either lists all five WC-4 cases (`success` to `succeeded`, `partial` to `partial`, `failed` to `failed`, `stopped-precondition` to `failed` with the precondition in `reason`, and the flag-STOP `blocked` of impact and graph to `failed` with the STOP in `reason`) or is marked as examples and points to WC-4.
- Archetype worker notes (review M-05, M-11). The 3.2 notes state only sourced facts: `/sc:spawn` is on the never-as-worker list; `/sc:adversarial` is in the contract's ready-with-brief-constraints table; a command gets `--unattended` only after each of its gates has an unattended resolution. No "natural worker" claim.
- Write-verb audit (review M-07). 8.4 describes the audit exactly: it scans skills, commands and agents for `git add`, `commit`, `push`, `merge`, `stash`, `update-ref`, `worktree add` and `worktree remove` (also with `-C <path>`), and for every `gh pr` and `gh api` line, reads included; each matching line needs an entry in `WRITE_VERB_CLASSIFICATION` with a category and reason, and an entry whose line was edited or removed fails the stale-entry test. Adding a `## Unattended mode` section to a command also requires adding it to `UNATTENDED_COMMANDS`. Names are confirmed in `tests/skills/test_worker_contract.py` before they are written.
- Appendix B fences (review M-08). Appendix B's outer template fence is already closed early by its inner bash block, so part of the template renders as live guide text and the next fence swallows the Appendix C heading. The plan changes Appendix B's outer fence to four backticks before adding the optional `## Unattended mode` slot, and checks that Appendix B opens with a four-backtick markdown fence, closes with four backticks, and that `## Appendix C` is outside any fence. The same nested-fence pattern elsewhere in the guide is reported, not fixed.
- One home for lists and numbers (review M-15). The never-as-worker list, the person-mode flags, the 4-minute wait limit, the `worker_status` values and the WC-4 error are written out once, in 7.6. Every other touchpoint names the rule ID and links to 7.6. The WC-4 error is described, not quoted. 3.6 paraphrases the "Orca coordination" rule (check the command file for the section, not a list) instead of quoting it.
- Source labels (review M-04). Claims from the planning spec (rollout phases, coordinator-only reasons, "no command, skill or agent runs an `orca` or `orca-ide` command or requires Orca") are labelled as coming from the rollout plan. "Adding a command to the never-as-worker list is a maintainer edit of `src/superclaude/core/WORKER-CONTRACT.md` and of `NEVER_AS_WORKER` in `tests/skills/test_worker_contract.py`" is stated as a maintainer step, with no extra process claim.
- Brief guard timing (review M-14). Every mention of the brief guard says it applies from P1. The Installation Locations block names the core folder on both sides: the source `src/superclaude/core/` and the installed `~/.claude/` core files.
- Checks (review M-10, M-13). The no-dash rule is checked once over all added lines of the guide's `git diff` in the last task, with a UTF-8 safe pattern. The gating test command is `uv run pytest tests/docs tests/skills/test_worker_contract.py`; `tests/core` may run too and is recorded, with its reason (it pins `HOW-WE-WORK.md` and `CLAUDE.md`, which the guide cross-references).
