## 1. Problem Statement

`/sc:recommend` now reads a governing routing guide before selecting commands. That repaired several older discovery problems, but makes stale guide decisions authoritative: a matching guide row bypasses cache lookup and semantic ranking.

The guide still sends ordinary implementation to task-builder because work spans many files, another session, or requires protection against drift. Those conditions contradict the user's requested policy and unnecessarily exclude existing workflow/implement capabilities.

A second problem is outcome confusion. Generic phrases such as “no changes wanted,” “error,” “review,” and “tasklist” overlap specialized reporting and artifact-generation requests. Specialized commands placed only in “Other commands” cannot compete once a generic routing row has matched.

Verification also has concrete gaps:

- Many active commands declare their options in formal Usage syntax, while recommendation rules accept only an options table or argument hint.
- Commands are incorrectly generalized as thin skill dispatchers, despite self-contained commands and TDD's differently headed skill invocation.
- Reading a dispatcher does not establish that its backing skill exists or agrees with its interface.
- A cache hit can return another request's stored envelope without current-request binding or complete current-source verification.
- Removed framework commands remain readable in installed locations.
- Plugin recommendations can encounter missing protocols or materially older command contracts.
- Advisory hook reminders are described more strongly than their actual implementation warrants.

## 2. Solution Overview

Keep the existing architecture: one governing routing guide, live capability discovery, source-backed handoffs, and optional cache infrastructure.

Change the decision order and its interpretation:

1. Preserve the requested outcome, explicit command selection, supplied artifact, and authorization ceiling.
2. Apply specialized command ownership before generic implementation-size heuristics.
3. For actual implementation, retain the existing direct-change limit.
4. Use workflow/implement for most planned implementation.
5. Use task-builder/task only for explicit MDTM intent or an exceptionally complex, long-running program whose required phase/checklist/reviewer machinery justifies it.
6. Resolve and verify the actual callable surface and relevant dependencies.
7. Emit a current-request handoff, never an unchecked cached answer.
8. Stop at the requested deliverable.

### 2.1 Key Design Decisions

| Decision | Choice | Rejected alternative | Rationale |
|---|---|---|---|
| Routing authority | Existing guide remains the only fixed routing source. | New keyword table in recommendation or CLI. | Avoids repeating the failure that prompted the earlier rewrite. |
| Implementation default | Workflow plus implement for most planned work. | MDTM based on file/session/spec counts. | Follows user policy and existing documented capabilities. |
| MDTM threshold | Explicit MDTM or exceptional complexity plus long-running phase coordination with a concrete machinery need. | Automatic escalation for risk, breadth, auditability, or resume alone. | Distinguishes useful process from proxies. |
| Explicit choice | Preserve it unless unavailable, contradictory, or prohibited; report the limitation. | Silently substitute a supposedly better command. | Recommendation does not override intent or safeguards. |
| Specialized operations | Keep their owned lifecycle. | Prepend generic planning whenever they write multiple artifacts. | Artifact generation, review, builds, and release follow-through are distinct jobs. |
| Cache safety | Treat cached targets/templates as advisory inputs; perform current verification and current-request binding before emission. | Verbatim hit replay. | Existing dispatch cannot establish request compatibility or transitive freshness. |
| Cache implementation | Reuse existing schema and source hash mechanisms initially. | New cache schema/dependency engine. | Mandatory re-verification closes the safety gap without new infrastructure. |
| Retired commands | Explicit lifecycle guidance and verified provenance; retain custom-command exceptions. | Reject every installed-only command. | Source absence alone does not prove retirement. |
| Contradictions | Surface them; withhold unsupported runnable claims. | Union incompatible option sets. | Prevents fabricated interfaces. |
| Plugin drift | Verify the actual plugin/installed capability; mark missing or incompatible capabilities. | Assume checkout behavior exists everywhere. | Broad plugin repairs are not authorized by this research. |

### 2.2 Workflow / Data Flow

```text
User goal
  -> requested deliverable + explicit choice + supplied artifact + mutation ceiling
  -> current guide
  -> specialized route or implementation-level decision
  -> live surface resolution
  -> candidate + activation dependency + relevant contract verification
  -> optional cache hint, never a verification bypass
  -> current-request handoff with applicable conditional flags
  -> stop; user decides whether to execute
```

Missing guide or unavailable cache CLI must degrade to current live verification, not stale replay. A matched guide row continues to bypass cache lookup/write-back.

## 5. Interface Contracts

### 5.1 Public Recommendation Interface

No new public flags.

Supported recommendation controls remain `--plugin`, `--eval none|quick|normal|deep`, and `--minstar N`. Evaluation remains opt-in. Plugin search retains its current popularity filtering, unranked credible-candidate handling, and authentication boundaries.

Verified ordinary planning handoff shape:

```text
/sc:workflow "<goal, constraints, code areas and acceptance expectations>" --depth standard --handoff none
```

Then read the actual printed plan and review result before:

```text
/sc:implement <actual-printed-plan-path>
```

Quick is appropriate for smaller checked plans; standard is the existing default. Deep or enterprise reflects requested planning detail, not an invented file/session threshold. Do not emit a workflow destination override or fabricate a package identifier.

### 5.2 Conditional Output Contract

Retain the existing eight routing columns and return-contract fields where possible.

Interpret ordered steps as a sequence **after** resolving their conditions and the user's requested scope:

- Preserve applicable prerequisite/read/review steps.
- Select exactly one alternative branch.
- Do not include implementation/shipping steps beyond a report-only goal.
- Apply supported explicit choices before ordinary defaults.
- Omit unsupported flags with an accurate explanation.
- Keep genuinely missing capabilities visibly unavailable.
- Describe material contract disagreement as `contract gap`, not simply `not installed`.
- Do not synthesize a runnable union of incompatible interfaces.

For PR rows, represent monitor alternatives with separate labeled conditional branches inside the existing mechanism. Do not retain unconditional `mandatory_flags: --monitor 3` on every branch.

### 5.3 Verification Record

Extend the existing per-invocation record in prose only as needed:

- Canonical target and kind.
- Resolved source path and provenance.
- Actual active copy when different from research authority.
- Self-contained or skill-indirected activation.
- Resolved skill path and relevant references read.
- Supported interface evidence and exact values.
- Required inputs and prerequisites.
- Requested deliverable and mutation/external-effect boundary.
- Lifecycle status.
- Contract disagreement or missing-dependency limitation.

This is not a new durable database.

### 5.4 Authorization Contract

Recommendation never executes its handoff.

Planning does not authorize execution. Review does not authorize posting. Posting does not authorize source edits. PR monitor ordinal and project policy control the actual later command. Suggesting an install command does not authorize installation.

The research request itself authorizes no source implementation, sync, commit, push, or network publication.
