## 2. How the spec-panel Review Loop drives the review CLI (master state)

Key structural fact: `spec-panel.md` itself never names `superclaude review` (Grep for `superclaude review` in it: 0 hits). The command only says "read `~/.claude/rules/prompts/document_review_loop_prompts.md` in full ... if it cannot be read, return `incomplete`" (`spec-panel.md:266-268`). All CLI wiring lives in the prompts file's `### Review panel` paragraph (`document_review_loop_prompts.md:68-70`). The coordinator (the session running the loop), not the reviewer, runs the CLI.

Sequence per loop (`<loop id>` = run id):

1. **Pick reviewers.** `superclaude review panel resolve --run-id <loop id> --kind first|re-review` (`document_review_loop_prompts.md:70`; options at `cli/review/panel_cmd.py:18-60`: `--template` file or `@NAME` packaged such as `@live7`, `--tiers`, `--env` default `$SUPERCLAUDE_REVIEW_ENV` / gateway when `T3Model01` set / else anthropic-only, `--kind` choice first|re-review, `--seed`, `--sequence`, `--hard-exclude-class` repeatable, `--strict-distinct`). Default: a panel for a first review, one reviewer for a re-review (`prompts:70`). Each reviewer runs in a fresh context with the same brief and sees no other report (`prompts:70`).
2. **Brief.** FIRST-REVIEW brief (`prompts:27-33`) or RE-REVIEW brief with the fixed CANDIDATE/BASELINE/PRIOR role table, Step 1 `diff -w BASELINE CANDIDATE` evidence block, review number N = prior N + 1, `grep -nF` self-check (`prompts:35-49`). Every report ends with `## Findings block` fenced `findings-v1` JSON lines (`prompts:56-62`): `id, severity (CRITICAL|MAJOR|MINOR), blocking, category (contradiction|unpassable-check|data-loss|safety|missing-requirement|other), anchor (12-200 chars copied exactly from the candidate), anchor2, refs, claim`; re-reviews add prior lines `{"prior": "L3", "status": "resolved|open|regressed"}`.
3. **Merge (round n).** `superclaude review merge` "also for a single reviewer" (`prompts:70`). Options (`cli/review/merge_cmd.py:22-69`): ledger file (created by round 1), the candidate reviewed, review number 1-3, repeatable `REVIEWER_ID=PATH`, panel resolution JSON (model per reviewer), merged report output, review cap used when round 1 creates the ledger. A merge refuses a round in which no reviewer produced a valid findings block (`prompts:70`).
4. **Ledger rounds.** Ledger schema `review-ledger/1`, statuses `open, resolved_check, resolved, regressed, deferred` (`cli/review/ledger.py:17-19`). On each merge: a finding re-found by anchor clustering whose row was `resolved_check`/`resolved` becomes `regressed` (`ledger.py:235-238`); a `resolved_check` row nobody re-found becomes `resolved` (event `cleared`, `ledger.py:254-258`); reviewer prior lines are only recorded as `prior_note` history, they do not change status (`ledger.py:259-272`). Verdict = FAIL iff the Reviser-brief id set is non-empty (`ledger.py:273-274`). Per-row `confidence` is `overlap` when 2+ reviewers hit it in one round, else `single` (`ledger.py:86-90`).
5. **Revise.** REVISE brief limited to the blocking `{{IDS}}` from the Reviser brief; reviser ends with `## Fix map` fenced `fixmap-v1` (`{"id","action":"applied|rejected","reason"}`) (`prompts:51-54, 64-66`; Reviser contract `spec-panel.md:263`).
6. **Record the revision.** `superclaude review ledger revise --ledger <ledger> --old <before> --new <after> --fixmap <reviser output>` moves rows the fix map names `applied` AND a diff hunk touches to `resolved_check` (`prompts:70`; `cli/review/ledger_cmd.py:36-71`). Without it, corrected findings stay open and the next review still fails (`prompts:70`). "Only these scripts change a finding's status" (`prompts:70`; `ledger_cmd.py:33`).
7. **Stop rule.** `_decision`: PASS if verdict PASS, else REVISE if `n < cap_reviews`, else ESCALATE (`ledger.py:93-96`). `superclaude review ledger verdict` exits 0 PASS / 10 REVISE / 11 ESCALATE (`ledger_cmd.py:94-109`). Prose cap: at most 2 fix cycles = 3 reviews, `review: N of 3`, prior at `review: 3` + FAIL means HALT and escalate (`spec-panel.md:261`). Human-only override: `review ledger defer --lid --reason` (`ledger_cmd.py:74-91`). `review ledger capture --round` exports a `review-capture/1` matrix (`ledger_cmd.py:112-127`; `ledger.py:18`).
8. **Fallback.** If `superclaude` is not installed: run one reviewer and say so in the loop summary (`prompts:70`). So the CLI is optional for the command; the prose rules in `spec-panel.md:256-264` must stand alone.

**Verify-only** does NOT exist in the master loop: the master ledger re-finds every round from fresh full findings blocks and clusters by anchor. Verify-only is the experiment `sc-review-ledger` design ("find once at review 1, then only verify ledger rows at reviews 2 and 3, one sweep after the loop", `~/.claude/skills/sc-review-ledger/SKILL.md:3`; `verify` input with `result resolved|open|regressed|cannot-verify` and required `evidence` quoted from the new snapshot, SKILL.md:60; transitions SKILL.md:63-70; phases find/revise/verify/terminal/swept, SKILL.md:44). Its only profile is `spec-panel` with a hard-coded blocking predicate `grade == CRITICAL or rule in {FR-8, FR-9} or (grade == MAJOR and wrong_outcome non-empty)` and `CAP_REVIEWS = 3`; the SKILL itself notes that `status` metrics and the `close` tail name grades outside `PROFILES` (SKILL.md:46-52). The stoprule variant instead hands blockingness to the blind `finding-grader` (B1-B3 rubric, `finding-grader.md:17`; reply `{"cid","blocking","q2","why"}`, :28-35).

Two blocking rules coexist on master: the prose rule (MAJOR blocking only with a concrete wrong outcome or security/data-loss/safety risk, `spec-panel.md:259`; same grading-check sentence `prompts:31`) and the parser rule in findings-v2 where, when `reflect_category` is set, MAJOR/CRITICAL must be blocking and MINOR must not (`findings_v2.py:161-162`). A unified contract must pick one.
