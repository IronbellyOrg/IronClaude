### 8.4 Branch-structure options

**Git constraint (applies to every layout that uses a slash).** `feat/review-panel` and `feat/review-panel/<name>` cannot both exist: a ref name cannot be both a branch and a directory of branches, because git stores `refs/heads/feat/review-panel` as a file and `refs/heads/feat/review-panel/<name>` needs a directory of the same name. A layout therefore either has an umbrella branch `feat/review-panel` with children named without a slash after `review-panel` (for example `feat/review-panel-m1-core`), or has namespaced children `feat/review-panel/<name>` with no branch called `feat/review-panel`.

**Facts that shape the options** (all from the research files; ownership is owner item O-4, G-92): the `cli/review` package on this branch equals `origin/master`, so the E1 kernel is master code after #519 and the branch `ironbelly/shadow-runs` is 3 commits ahead of `origin/master` touching only `SKILL.md`, `refs/reviewer-spec.md`, two reflect tests and documents (`research/09` section 1.1; GQ:D-72); the local `master` ref is stale, so any new branch is cut from `origin/master` (project rule: fetch and rebase onto `origin/master` before pushing); PRs go only to the fork `IronbellyOrg/IronClaude` through `/sc:pr-submit --monitor 3`, never to the upstream; worktrees are created through Orca with an agent; `.claude/` mirrors are never staged and `.dev/tasks/` is always staged; the reflect pins C1, C6, C14 compare with HEAD, so changes to the reflect skill text are kept in separate commits from changes to the pinned sections and G8 is run before each commit; the live7 test couples `review-tiers.default.json` to `ccsession-models.json`, so tier edits and that file change in one PR (GQ:G-90); both panel goldens regenerate on any tier-file byte change, so two branches that edit the tier file or the resolution record conflict. This section states layouts and trade-offs only; it commits to no order, date or sprint.

| Option | Branch layout | Pros | Cons |
|---|---|---|---|
| A. Flat sibling branches, no umbrella | One branch per track or per group of steps cut from `origin/master`, named without a slash after `review-panel`: `feat/review-panel-m1-contract`, `feat/review-panel-m1-resolver`, `feat/review-panel-m2-reflect`, `feat/review-panel-m3-post-gate`, `feat/review-panel-m4-pr`; each PR targets master directly | Satisfies the git constraint trivially; each PR is reviewed and gated alone (G-all green per PR); matches the "branch from master, PR to the fork" rule; M3 post-gate repairs (code-only, G9) do not wait on M1 | Shared files (`findings_v2.py`, `panel.py`, both goldens, `test_review_cluster.py:784-795`) conflict between siblings; reviewers see a half-unified core between merges; cross-track dependencies (M2 on M1-02, M1-06, M1-09) need the earlier PR merged or a stacked rebase |
| B. Keep `ironbelly/shadow-runs` for reflect only, core on separate branches | Continue the existing branch (M2 work and the shadow-run evidence) and cut the M1 core and M3/M4 work onto new flat or namespaced branches from `origin/master` | Preserves the shadow-run history and the evidence documents (`.dev/tasks/` stays staged); no rename of a branch that other worktrees use | Two lineages touch `sc-reflect-protocol/SKILL.md` and the pinned tests, so C1/C6/C14 runs must be repeated on each; the shared kernel is on master already, so M2 steps that need new M1 pieces must wait for those PRs (a dependency, not an order); the branch is 3 commits ahead of `origin/master`, so it must be rebased before any push |
