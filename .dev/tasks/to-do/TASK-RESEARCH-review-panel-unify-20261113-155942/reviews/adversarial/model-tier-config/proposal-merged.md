# Merged proposal for C03: staged class-launch core with gated gateway pieces

<!-- Source: Base (original, modified) - Position rewritten per the merge-executor brief (step 6); content follows Changes #1, #2, #6, #11, #14 and Group U. **Position.** Ship the class-launch core first, in staged pull requests. A reviewer is started by passing a class name (`sonnet`, `opus` or `haiku`) to the in-session Agent call, the one launch form an in-session orchestrator can execute today. Gateway models are reached by binding a class to a gateway model through the three `ANTHROPIC_DEFAULT_*_MODEL` variables before the session starts, and the binding is recorded. The tier-file guards come next, in PR 2 or soon after: minimal provenance with a coupling test, a closed parse of the launch grammar, a command-layer slot and drift check, and a `panel verify` command with V1, V2 and V4 and a warn-only V3 (stages in `## Cost`; the timing of the closed parse and of the slot check is open between PR 2 and the dispatcher PR). Gateway `cli-model` entries, the `swarm:` adapter, `tier0` and `muse-ember-1.0` data, and V3 as anything more than a warning stay out until the C09 dispatcher exists and the owner decides O-2 (the target environment). The gateway environment keeps `launch: {}`, and a consumer that selects it runs the legacy path and records the reason (reflect rule D4, `SKILL.md:320`). The sufficiency claim of the core is limited: C03 alone enforces nothing, because no consumer reads `launch` today (the loop prompt has no instruction to pass `model` from `launch`, and reflect's dispatch is the legacy dispatch), so the default flip is a relabel for the loop unless it ships with a loop consumer. Whether the flip ships with that consumer, ships alone with a narrowed claim, or is withheld is an unresolved item. Convergence of the debate behind this text was not declared (status BLOCKED_BY_INVARIANTS); the open items are listed in `## Open items and unresolved conflicts`.

## How it works

### Data flow for one run

1. The consumer starts a session. The operator's environment fixes the class bindings (`ANTHROPIC_DEFAULT_SONNET_MODEL`, `_HAIKU_`, `_OPUS_`). Wave 0 reads them once and treats that set as canonical for the run (`SKILL.md:232`, `:1507`). <!-- Source: Base (original) -->
2. The consumer runs `superclaude review panel resolve --template @<name> --run-id <id> --kind first|re-review [--env anthropic-only] [--hard-exclude-class <executor class>] [--strict-distinct]`. With no `--env`, the result is the anthropic-only cell if the default flip of Core item 2 ships; otherwise `select_env` decides as it does today (`gateway` where `T3Model01` is set). The resolver is unchanged: pure, sha256-frozen, stdout only (`panel.py:565-707`, `panel_cmd.py:18-108`). <!-- Source: Base (original, modified) - "With no --env, the result is the anthropic-only cell" made conditional on the flip, because the flip is open item C-001 (Change #14). -->
3. The resolution lists each reviewer with `model` (the pin in the tier file's terms), `launch` (a class), `fallbacks` (empty in this cell, `04 §4.1`) and `stand_in`. <!-- Source: Base (original) -->
4. The orchestrator advances the manifest stage `resolved` with `{"reviewers_requested": N, "reviewers_resolved": M, "launch_binding": {"sonnet": "<value>", "haiku": "<value>", "opus": "<value>", "parent_model": "<id or unverified>"}}`. The payload holds raw values only (Core item 4). `advance_stage` raises `Invalid` when `reviewers_resolved > reviewers_requested` (`manifest.py:312-315`). The skill does not say which count `reviewers_requested` is: `N_eff = min(--reviewers, alias count, 3)` is the legacy count (`SKILL.md:321`), `resolve` does not apply it (`SKILL.md:340`), and the skill never says whether `reviewers_requested` records `N_eff` or the resolution count (invariant probe INV-005). The merged design requires the skill text to state which count `reviewers_requested` records and which reviewers are dropped when `N_eff` is below the resolution count. The sources do not choose, so the choice is a required decision (`### Decision points` in `## Cost`); test 12 pins the chosen mapping. <!-- Source: Base (original, modified) - payload shape per Change #13 (INV-001); reviewer-count mapping per Change #17 (INV-005). -->
5. The dispatcher makes one Agent call per reviewer, under a rule that depends on the engine mode. In shadow mode the call passes an explicit `model` equal to the class the legacy rotation selected, so the frontmatter default can never replace the panel while `panel_parity` still compares the resolution with the legacy rotation as it ran (`SKILL.md:341-342`). At `engine=panel` (Stage 3, not shipped) the call passes `model = reviewers[i].launch`, and the dispatcher refuses to dispatch a reviewer whose `launch` is null or outside the class set (a dispatch error, not a frontmatter default; `results.md:35` shows the collapse this prevents). The split was proposed in the refactoring plan and was not debated (invariant probe INV-009; open items); test 10 pins that parity stays independent in shadow mode. The loop dispatches by `launch` only under option (i) of Core item 2. Which reviewers are dispatched when `N_eff` is below the resolution count is the count rule of step 4. <!-- Source: Base (original, modified) - "every Agent call carries model == launch" replaced by the engine-mode split per Change #12 (INV-009, orchestrator-verified at SKILL.md:336-342); count reference per Change #17. -->
6. Observation, where the run is driven through `claude -p --output-format stream-json`: the served model of each Agent call is the most common `message.model` among events whose `parent_tool_use_id` is that call's id (`.dev/eval-workspaces/shadow-model-combos/analysis/extract.py:56-58`). It is stored as `observed` next to `requested` and `launch` (C08). Where no stream is available, `observed` is `unknown` with `identity_source: requested-pinned`, and the record says so (`SKILL.md:348`). <!-- Source: Base (original) -->

## Correctness argument

<!-- Source: Base (original, modified) - intro narrowed per Change #11 (INV-013); steps 1 and 2 rewritten per Change #11 (INV-013, INV-010; debate Round 2 "Staging test"); step 4 one sentence added (INV-014, Change #13); step 5 first-person phrasing removed; step 6 rewritten per Change #2; steps 3 and 7 Base (original); closing paragraph extended per Change #19. -->
The claim is limited. Option A is the smallest design in which a consumer that dispatches by `launch` gives every reviewer a launch value the platform accepts, with a recorded binding that says what the value means on this machine and no silent default. The core alone does not make any consumer dispatch by `launch` (A-001, INV-013). Each step below rests on the evidence items named.

1. **The launch value is valid by construction for a consumer that reads it.** The in-session Agent call takes only a class alias (EV-5), and the cell this option supports fills `launch` with exactly those aliases (EV-6). The dispatcher rule (launch must be a class and, where the engine mode requires it, the call's `model` must equal it) turns the three observed failure shapes into errors: a `launch: null` reviewer (EV-1), a missing class that falls to the frontmatter default (EV-12, A3), and a Fable value where a profile forbids it (existing test, `test_review_panel_reflect_profile.py:183-186`). The rule has an executing site only where a consumer reads `launch`. Reflect step 3 is the legacy dispatch today (`SKILL.md:342`), and the loop prompt has no instruction to pass `model` from `launch` (`document_review_loop_prompts.md:70`). Until a consumer changes, the rule is a design statement and not behaviour (invariant probe INV-013, orchestrator-verified against `SKILL.md` and the loop prompt).
2. **The default cell is a dispatchable cell, and that is a statement about the record.** Today a consumer that omits `--env` on a ccsession machine gets `gateway` and a panel with no launch instruction (EV-1, EV-3, EV-20). If the `select_env` change ships (open item C-001), the resolution printed for an omitted `--env` is a dispatchable one. The change alters what is dispatched only for a consumer that passes `launch`, and today none of the loop's text does: reflect passes `--env anthropic-only` itself, so the flip never reaches it (INV-010), and the loop prints different names and dispatches as before. "Forgetting `--env` yields a panel that can run" therefore holds for the record and not for dispatch, unless the flip ships with a loop consumer (option (i) of Core item 2). The unsupported cell is reached only by naming it (`--env gateway`, `SUPERCLAUDE_REVIEW_ENV=gateway`), where reflect templates still fail closed (EV-2); for the loop, a null launch there is handled by the recovery rule of Core item 1 (INV-004). The B advocate's staging test in debate Round 2 reaches the same reading: without a loop consumer the flip is a relabel. The falsifying conditions and the gates, as the invariant probe enumerated them (INV-013, orchestrator-verified):
   - **Falsifying condition 1.** The loop prompt has no instruction to pass `model` from `launch`. After the flip the loop prints "sonnet plus 3x haiku" and dispatches as before, so the record describes something that did not run (the X-003 defect).
   - **Falsifying condition 2.** Reflect never reaches the flip (INV-010), and its dispatch is legacy (`SKILL.md:342`), which also conflicts with a forced `model == launch` rule (INV-009).
   - **Gate 1, the `select_env` flip.** `panel_cmd.py:96` is the only caller and only the loop prompt reaches it; the flip is not shown to reach a dispatch consumer.
   - **Gate 2, `resolve`.** The anthropic-only launch map is complete (`review-tiers.default.json:35`) and the goldens show a launch for every reviewer. Shown to pass.
   - **Gate 3, the consumer.** The loop has no reader and reflect step 3 is the legacy dispatch. No gate passed (A-001).
   - **Gate 4, the Agent tool.** A family alias resolves to the parent's exact model when the parent is in that family (A-002). The parent here is `claude-gw-tier1b[1m]`, equal to the SONNET binding, so sonnet is benign; haiku and opus are UNVERIFIED and no in-session observation exists (`SKILL.md:348`, `requested-pinned`).

3. **Gateway models stay reachable without a second dispatch path.** A class can be bound to a raw gateway id, and the runs show the bound model serving the slot (EV-9). E2's best real-blocking shape is expressible this way (EV-10).
