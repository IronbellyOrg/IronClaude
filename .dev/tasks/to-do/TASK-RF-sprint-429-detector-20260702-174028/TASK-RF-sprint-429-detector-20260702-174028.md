# Harden sprint 429/account-exhaustion provider-failure detector for Shape-2 transcripts

## Task Overview

PR #183 shipped a full sprint 429 recovery subsystem, but on the real July incident the detector's entry predicate at `monitor.py:323` (`if is_error and api_error_status == 429:`) required a structured `api_error_status == 429` field that the real CLIProxyAPI transcript does not carry. The Shape-2 transcript has `is_error:true` but NO `api_error_status` key at all; its 429 is text-only inside a nested `rate_limit_error` envelope. So `_provider_failure_from_text` returned `ProviderFailure.NONE`, recovery never engaged, and every task in the phase cascaded to `FAIL_TERMINAL`. This has been EMPIRICALLY VERIFIED: the current unpatched detector returns `ProviderFailure.NONE` on the verbatim Shape-2 transcript at `research/shape2-verbatim-transcript.jsonl`; the loosened C8 regex captures model `gpt-5.5`.

This task applies the two mandated production hunks to ONE file (`src/superclaude/cli/sprint/monitor.py`) exactly as the merged-requirements spec specifies — HUNK 1 widens the entry predicate to also open on `"rate_limit_error" in body`, and HUNK 2 loosens the `_RE_ALL_ACCOUNT` regex to drop the `via provider` suffix — then adds the fixtures, the detection-contract table test, the live/offline parity assertions, and the timeout-unreachability guard that would have caught the incident. The verification surface is authored RED-first (tests fail against the unpatched detector, proving they exercise the real gap), then confirmed GREEN after the two hunks land. Both live (`detect_provider_failure`) and offline (`_classify_transcript`) paths are fixed by the single inner-function edit because they share `_provider_failure_from_text`. This is a narrow production change (2 hunks) plus a medium verification surface; nothing else in monitor.py or the consumer chain is touched.
