## Q1. How a worker's question reaches the coordinator

**Answer.** The worker runs a blocking `ask`; the question becomes a durable message in its owning Run's mailbox (`run:<id>`); the coordinator's `check --wait --types "worker_done,escalation,question"` wakes on it and returns it inside a whole FIFO Delivery; the coordinator answers with `reply --id <message_id> --body ...`. A timed-out `ask` leaves the same question pending and is resumed by its message ID.

**Evidence.**

## Q3. How peer sessions appear

"Peer session" here means an agent session that is not a supervised worker of the coordinator's Run: a session a person started (inside or outside Orca), or one launched with `orca-cli` `agent launch` / `worktree create --agent`.

**Answer.** Peer sessions do not appear in `orchestration worker-list` (which lists supervised worker terminal accounting, plus context-only `dispatch` rows) and have no Run mailbox. Their address is a terminal handle or an `orca_session_id:<id>` mailbox. A session knows its own Orca session ID only from `status --json` `caller.orcaSessionId`, which is omitted when the agent is not running as an Orca session.

## Q4. What a frozen worker looks like

Three different states are easy to confuse; Orca names only two of them.

**Answer.**

1. **Frozen `/sc:implement` plan (IronClaude decision D2).** This is not an Orca state. Orca sees a settled Task: the worker sent `worker_done --outcome failed` (WC-5, `WORKER-CONTRACT.md:58`), so the Task and Dispatch are settled and the worker terminal is `reclaimable`, `retained` or `released`. The freeze is visible only in IronClaude files: the latest implement contract is `blocked`, or `failed` with a STOP code other than `E-RESUME-NEEDED`, or the ledger's first non-complete task ends in `halt`/`blocked` with no eligible Ruling (`WORKER-CONTRACT.md:133`). While frozen, no Task is dispatched for that plan, nothing writing outside its report directory goes into that worktree, and no HEAD/index/working-tree git command runs there (`WORKER-CONTRACT.md:134-136`). [CODE-VERIFIED as repo text]
2. **Worker waiting on a person (healthy).** Orca shows this as `worker-show` `observation.agentWait` non-null: `[H:worker-show]:16` "observation.agentWait names a worker parked on a prompt only a human can answer, with the evidence that proved it (hook, prompt-text, or title). Null means Orca looked and found no wait. An absent field means it never looked — an older host, an unverifiable worker identity, an unreadable pane, or an agent probe that did not answer in time — and never means the worker is not waiting. A waiting worker is healthy, not failed." [CODE-VERIFIED]. Under WC-3 a correct worker never parks on a local prompt (`WORKER-CONTRACT.md:52`; `[G]:81-83` "Never open a local question TUI the coordinator cannot answer"), so a non-null `agentWait` on a worker may be a contract breach; a worker blocked in `ask` is a pending Run message, not an `agentWait` (inference from Q1; [UNVERIFIED] whether Orca also sets `agentWait` during `ask`). ## Summary

A worker's question reaches the coordinator as a durable `run:<id>` message from a blocking `ask` (default timeout now documented as 10 minutes), woken by `check --wait --types ...question` and answered with `reply --id`; under WC-3's default policy a person-question never enters Orca and lives only as `blocked_question` in the worker contract. Reading is destructive in the consuming path (plain `check` is called "consuming" and `--ack` drains the inbox), while `check --peek` and `check --all` are documented as non-marking but capped at 100 rows with no cursor, and `inbox` and `--unread` are undocumented, so a read-only sweep must use only `--peek`/`--all` and say "could not determine" at the cap. Peer sessions are invisible to `worker-list` and appear only in `orca-cli` views (`worktree ps --agent-wait`, `reference find`), whose agent-wait probe side effects are not documented. A "frozen" worker in the D2 sense is an IronClaude contract-plus-ledger state that Orca shows only as a failed, settled Task, while Orca's own signals (`agentWait`, `projection.liveness`) distinguish waiting-on-a-person from stuck only on positive evidence. Every behaviour above rests on CLI 1.4.245 help and bundled guides, not live calls; items 1-15 in Gaps need a throwaway-Run test or a handler read before the sweep relies on them.

**Gate fix update (2026-11-07, B-10, B-15 to B-18, B-22 to B-24, B-28).** The CLI `check` handler was read (`07-gate-gap-fill.md` Section C): every `check` is a mutation call, `--unread` consumes and is forbidden, `--peek` is ignored by older runtimes, a `compatibilityAck` follow-up can acknowledge messages, and `--format` is a local text switch (Gaps 3 and 15 resolved; new Gaps 17-19). A plain `check` is potentially draining (a Delivery ends on `--ack` or once all its messages are marked read). The G-B answer for the sweep is therefore: Orca question enumeration is "could not determine", the sources for "waiting on a person" are the contract fallbacks (`blocked_question`, non-null `agentWait`, frozen plan), answered state is "could not determine", `--agent-wait` is excluded, a non-null `agentWait` is "waiting on a person" (not a breach), and the report header states partial message coverage. Class names follow `research-notes.md` Section C.
