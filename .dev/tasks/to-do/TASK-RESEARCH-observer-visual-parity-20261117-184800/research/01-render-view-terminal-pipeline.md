### Console behaviour that matters for styled Text (probe, Rich 15.0.0)
Using the exact `make_console` arguments with a `StringIO` file:
- `console.print(Text("hello world", style="bold #ff8800"))` wrote `\x1b[1;91mhello world\x1b[0m\n` to the buffer. So (1) escape codes ARE emitted into a non-terminal `StringIO` because `color_system="standard"` is explicit (not "auto"), and (2) an RGB style is downsampled to a 16-colour ANSI code (`#ff8800` became bright red `91`). With `no_color=True` and `color_system=None` the buffer was plain `hello world\n`.
- A plain-text guarantee is therefore NOT provided by the StringIO. Tests that capture with `printed()` (test_render.py:45-52, release1_surface.py:34-38) will start to contain escape bytes the moment any style is added. See "Tests that pin the plain output" below.
- `cell_len("\x1b[1;38;5;208mX\x1b[0m")` is 16 (the printable part of an escape run counts as cells), so test_render.py:73-77 (`cell_len(line) <= width for line in out.splitlines()`) would fail on styled `printed()` output unless the helper strips ANSI first.

### Key Takeaways (call chain)
- `screen_lines` is a pure string pipeline; `render` only wraps each string in an unstyled `Text`. All styling work has to be introduced either by (1) producing `Text` objects with spans in a new parallel function, or (2) re-deriving spans from the strings.

- Rich emits ANSI into any file object once `color_system` is explicit; the tests' `printed()` capture is not style-free once styles exist.

## 7. Colour depth (Q4), measured

Fresh-process probes of Rich 15.0.0 (`Console(file=StringIO(), width=40, color_system=X, highlight=False, markup=False, emoji=False)` printing `Text("x", style="bold #ff8800")`):
- `standard` -> `\x1b[1;91mx\x1b[0m` (the amber collapses to bright red 91). This is what `make_console` builds today (terminal.py:121).
- `256` -> `\x1b[1;38;5;208mx\x1b[0m`; `truecolor` -> `\x1b[1;38;2;255;136;0mx\x1b[0m`.
- `auto` (with COLORTERM=truecolor, TERM=xterm-256color, but a StringIO file) -> `color_system` resolved to `None` and the output was plain `x\n`: Rich's auto-detection returns no colour for a non-terminal file. On a real terminal `auto` would read COLORTERM/TERM.
- Rich caches a `Style`'s ANSI codes on the Style object, so inside ONE process the first colour system used for a given Style wins (an in-process probe that tried `standard` first returned `91` for later `256` and `truecolor` consoles). Not an issue for a single `make_console` call per process, but test helpers that build consoles with different systems in one process can see stale codes. [observed in this session]
- Any theme with more than the 8 plain + 8 bright ANSI hues must either pick `standard`-safe named colours (e.g. `cyan`, `yellow`, `bright_black` for muted/slate, `green`, `red`, `magenta` for violet) or change `make_console` to detect depth. Roles that are distinct in 24-bit amber / cyan / slate / green / red / violet map to ANSI as: amber has no standard colour (nearest `yellow`/`bright_red`), slate and muted both land on greys (`bright_black`/`white`): these two roles can collapse (G-2). [Inference from the colour model; the mapping table itself is a design choice not yet in code.]
- Colour and ASCII stay independent decisions (terminal.py:83-85 and 121-123); NO_COLOR gives `color_system=None` AND `no_color=True`, and with those arguments the earlier probe printed `Text("hello world", style="bold #ff8800")` as plain `hello world\n`: bold is dropped together with colour. [CODE-VERIFIED by probe with the `make_console` arguments.] Under NO_COLOR the hierarchy therefore has to be carried by text and glyphs, as G-1 already says; `Style(bold=True)` will not survive NO_COLOR with the current console.

### 8.2 Candidate insertion points and their width arithmetic (k)
Common numbers: every candidate frame or tile glyph measured 1 cell in Rich 15 (`╭ ╮ ╰ ╯ ┏ ┓ ┗ ┛ │ ┃ ─ ━ █ ▌ ▸ · ◆` all `cell_len == 1`; probe). CJK text is 2 cells per char (`"ab世界cd"`: 6 characters, 8 cells), and Rich `Text` spans are CHARACTER indexes while widths are CELLS, so offsets derived from column widths drift after a wide character unless a line is built by appending segments in order. In ASCII mode `ascii_safe` replaces wide characters with `?` (1 cell each).

1. Style map (roles) over unchanged strings. Insert in `render()` (render.py:524-531): build each `Text` and apply spans from a role table. Pros: `screen_lines` and all string goldens stay valid; text identical in NO_COLOR and ASCII. Problems: (a) matching by regex or token (`unknown`, `unavailable (no source)`, worker state words, `FROZEN`, `reason unknown`) can hit free text and worker-controlled strings; (b) column colouring by offset needs the column layout (`_columns`) to be replayed in `render()`, and offsets must come from segment building, not from cell widths (wide characters); (c) the `printed()` capture changes (see section 6).
2. Segment-returning builders. Make the line builders return `Text` pieces (or `(text, role)` segments) and derive `screen_lines` as `[t.plain ...]`. Pros: exact styling with no regex; `.plain` keeps the goldens. Cons: widest refactor (`wrap`, `clip`, `_cell`, `_pad`, `counts_lines`, `_panel_lines`, `_desk_lines`, `_row_line`, `_header_lines` all return `str`), and `wrap`/`clip` have their own cut markers (`>`, `...`) that Rich `Text.truncate` or `Text.wrap` would not reproduce, so they must stay the wrapping authorities, operating on `.plain` and re-applying spans.
3. Hand-built frame helper emitting `str` lines. New helper (for example `frame(title, lines, width, policy)`) next to `_pad`/`_cell` (render.py:83-88): `top = corner + title + hrule*n + corner`, `side = vertical + _pad(text, inner) + vertical`, using new `GLYPHS` entries (terminal.py:30-34) with ASCII forms `+`, `-`, `|`. Inner width = pane width minus 2 (border) or minus 4 (border plus one-cell padding). ## Summary

The observer screen is a pure string pipeline: `build_view` makes a `View` of plain strings, `screen_lines` (render.py:390-521) lays them out into `list[str]` with all width maths in `cell_len`, and `render` (524-531) wraps each line in an unstyled `Text(no_wrap=True, overflow="crop")`, so no span, border or column exists anywhere today. Colour is a fixed 16-colour `"standard"` console (terminal.py:121) that Rich drops entirely under NO_COLOR (bold included), `safe_box` does not turn a Rich Panel into ASCII borders, and Rich emits ANSI even into a `StringIO`, so adding any style will change the `printed()` captures that T47 and the NO_COLOR parity test compare byte for byte. The text records and JSON snapshot are independent of render.py (`record_text`, `snapshot_dict` read `View` fields directly), but the pinned screen goldens (T47, T64) fix the plain output of the questions-off and link-off screens, so the safest route is a render-only style and frame layer, or a gated look with deliberately regenerated goldens. Each finding M-01 to M-18 maps to a named function in render.py (table in section 8.1); M-09 only applies to the full layout and the desk because 116 and 80 columns have no worker-state or dispatch-status column, and the 160-column table already uses all 160 cells, so a frame needs the elastic `flags` column to give up 2 to 4 cells.
