# Web Research 01: Rich composition and colour for a terminal dashboard

Date: 2026-11-17
Status: Complete

Topic: Rich (Python) Panel/Table/Columns/Layout, box styles, Text spans, color_system detection, NO_COLOR/FORCE_COLOR, export_text/svg/html, Live screen=True, cell_len, line-based model plus styling.

## What we already know from the codebase (executor summary)
1. render.py `screen_lines` returns plain list[str]; `render` wraps each in unstyled `Text(line, no_wrap=True, overflow="crop")`.
2. `make_console` uses `color_system=None if NO_COLOR else "standard"`.
3. Rich 15.0.0; Panel prints identical Unicode borders with or without `safe_box`; `box=rich.box.ASCII` needed under `--ascii`.
4. One-shot `--once --width` calls `console.export_text()` (commands.py:242), default styles=False; `export_text(styles=True)` ignores NO_COLOR and 16-colour downgrade.
5. LiveScreen uses `Live(screen=True)`: alternate screen, rows padded, rows past height dropped silently, styles kept as SGR.
6. Tests require one renderable per line; forbid `Console(` and `sorted(` in render.py.
7. 16-colour downgrade maps muted, green, red, violet to index 7; slate to 8.

## Findings

### A. Console.color_system values and detection (Rich v15.0.0 / master)
Sources (official docs and source): https://rich.readthedocs.io/en/stable/console.html ; https://github.com/Textualize/rich/blob/v15.0.0/rich/console.py ; Context7 /textualize/rich (docs/source/console.rst). Reliability: official docs + library source (highest).
- Values: `None` (no colour), `"auto"` (default), `"standard"` (8 colours + bright = 16), `"256"`, `"truecolor"`, `"windows"` (legacy Windows 8 colours). Docs warn that forcing a higher system than the terminal supports can make text unreadable. Relevance: HIGH (Q4).
- Auto detection (`_detect_color_system`, from source): notebooks get truecolor; a non-terminal or dumb terminal gets None; on Windows the choice depends on detected console features; elsewhere `COLORTERM` of `truecolor` or `24bit` gives truecolor, otherwise the last hyphen-separated part of `TERM` (e.g. `xterm-256color` gives 256) picks the palette, defaulting to standard. Relevance: HIGH. Supports the code finding that the code pins `"standard"`: that is a deliberate floor, not Rich's default. Extends: detection is cheap (`color_system="auto"`), so a 256/truecolor tier is a small change plus tests.
- Terminal detection order (`is_terminal`, from source): explicit `force_terminal`; IDLE rejected; notebook rejected; `TTY_COMPATIBLE` 0/1; `FORCE_COLOR` present and non-empty means true (empty means false); else the stream's `isatty`. Relevance: MEDIUM. Because our console pins `color_system`, the `"auto"` TERM/COLORTERM logic is bypassed, but `is_terminal` still governs whether escape codes are written to a stream.

### B. NO_COLOR and FORCE_COLOR
Sources: https://rich.readthedocs.io/en/stable/console.html (Environment variables section, via Context7); https://github.com/Textualize/rich/blob/v15.0.0/rich/console.py. Reliability: official docs + source.
- Docs: `TERM=dumb|unknown` disables colour/style and cursor features; non-empty `FORCE_COLOR` enables colour regardless of TERM; `NO_COLOR` set disables all colour and takes precedence over `FORCE_COLOR`. Relevance: HIGH.
- Docs NOTE: `NO_COLOR` removes colour only. Bold, dim, italic, underline are preserved. Source: `no_color` is the constructor arg, else true when the NO_COLOR env var is non-empty; when active and a colour system exists, buffered segments go through `Segment.remove_color` before style rendering. Relevance: HIGH. EXTENDS the code finding: our code passes `color_system=None` under NO_COLOR, which is stronger than Rich's own NO_COLOR (it also drops bold/dim). That is a project choice, not Rich behaviour; if the redesign wants bold/dim to survive NO_COLOR it would keep a colour system and set `no_color=True` instead.
- Style.render (v15.0.0 style.py, https://github.com/Textualize/rich/blob/v15.0.0/rich/style.py): returns text unchanged when `color_system is None` (no SGR at all, including bold/dim). `Style.without_color` clears fg and bg but keeps bold/dim. Dim is SGR 2. Relevance: HIGH (the two NO_COLOR routes differ; dim is a usable role marker at 16 colours when colour is on).

### C. export_text, export_html, export_svg, record=True
Sources: https://rich.readthedocs.io/en/stable/reference/console.html ; console.py v15.0.0. Reliability: official.
- `export_text(clear=True, styles=False)`: needs `record=True`; `styles=True` includes ANSI codes; default is plain text. Relevance: HIGH (Q5). Supports code finding that one-shot output has no styles because `export_text()` uses `styles=False`.
- Source behaviour: with styles requested each recorded segment is rendered through its style object; without styles it concatenates segment text and skips control segments. Recording happens when the outermost buffer context flushes; `quiet` discards pending segments first; the export clears the buffer by default. Relevance: HIGH. Consistent with the code finding that `export_text(styles=True)` ignores NO_COLOR and the 16-colour downgrade (recorded segments keep their original styles; the downgrade applies at write time). A styled-capture gate must capture the written stream (Console `file=` a StringIO with `force_terminal=True` and the production `color_system`), not `export_text(styles=True)`. This is my inference from the source reading, to be verified by a one-line experiment in the codebase.
- `export_html` / `export_svg` work on recorded segment styles and a terminal theme (fixed default palette), not on NO_COLOR or the colour system. Relevance: MEDIUM; useful for review artefacts (a styled picture to compare with mockups), not as the NO_COLOR test.

### D. Live and screen=True
Sources: https://rich.readthedocs.io/en/stable/live.html ; https://github.com/Textualize/rich/blob/v15.0.0/rich/live.py ; https://github.com/Textualize/rich/blob/v15.0.0/rich/screen.py. Reliability: official.
- Docs: `screen=True` shows the display in the alternate screen and restores the prompt on exit; combine with `Layout` for full-screen apps. `vertical_overflow` default is `"ellipsis"` (last terminal line replaced by an ellipsis); `"crop"` hides the rest; `"visible"` shows everything but cannot clear properly. Relevance: HIGH (Q5, Q7).
- live.py: `screen=True` makes the display transient and wraps the renderable in `Screen`; the home-cursor control replaces the live renderer's cursor repositioning; on stop `vertical_overflow` becomes `"visible"`.
- screen.py: `Screen` renders children with `pad=True` and applies `Segment.set_shape(lines, width, height, style)`, so extra rows beyond the height are cropped, and short rows are padded to full width. Relevance: HIGH. DISCREPANCY NOTE: Rich docs say `Live` ellipsises overflow by default, but under `screen=True` the Screen wrapper crops rows past the height. This matches the codebase finding (rows dropped silently, no ellipsis), so the codebase finding stands; do not rely on an ellipsis marker. A taller redesign must either fit the console height or add its own "N more lines" row.
- Styles survive Live drawing: segments keep their style and are written as SGR, subject to the console's `color_system`. Padded cells use the console/background style passed to `set_shape`.

### E. Cell width (cell_len)
Source: https://github.com/Textualize/rich/blob/v15.0.0/rich/cells.py. Reliability: official source.
- `cell_len` sums per-code-point widths from a Unicode table (binary search); unlisted code points default to 1; wide East Asian characters are 2; combining and most control characters are 0. There is no locale-sensitive handling of East Asian "ambiguous" width: the table decides (ambiguous characters such as box drawing and many symbols count as 1). A ZWJ makes the next code point be skipped; VS16 can add one cell after certain narrow-to-wide characters. Strings made only of single-cell characters (printable ASCII and some more ranges) take a fast path and return `len`; results for strings under 512 characters are cached. Relevance: HIGH. Risk: terminals that render ambiguous-width glyphs (some status symbols, arrows, dots) as 2 cells will misalign borders against Rich's count; keep chrome characters to box drawing, plain ASCII and a short vetted symbol set, and avoid emoji.
- Relevance for widths 160/116/80: Rich measures by cells, so an f-string padded by `len()` differs from Rich for any wide or zero-width character; the line model should pad with `cell_len` (from `rich.cells`) if non-ASCII data (agent names, titles) can appear.

### F. Text overflow, wrapping and a long unbroken token (Q7)
Source: https://github.com/Textualize/rich/blob/v15.0.0/rich/text.py ; https://rich.readthedocs.io/en/stable/text.html. Reliability: official.
- `Text.truncate` works in cell width; modes: `fold` and `crop` trim to width, `ellipsis` reserves one cell for the ellipsis, `ignore` skips shortening and padding. For `Text.wrap`, a single long word with no spaces is split across lines under `fold` and clipped under `crop`. `no_wrap=True` stops line breaking but not truncation; `overflow="ignore"` bypasses width enforcement. Relevance: HIGH. Supports the code finding: `Text(line, no_wrap=True, overflow="crop")` clips a long token silently at the console width. Option: `overflow="ellipsis"` gives a visible truncation marker per line (costs one cell) without changing the line model.
- Spans: `Span(start, end, style)` with an exclusive end offset; `Text.append(str, style)`, `Text.stylize(style, start, end)`, `Text.assemble((str, style), ...)`. Overlaps combine with later spans winning. `Text.from_ansi` parses ANSI strings. Relevance: HIGH (Q1).

### G. Composition: Panel, Table, Columns, Layout, box styles
Sources: https://rich.readthedocs.io/en/stable/appendix/box.html ; https://rich.readthedocs.io/en/stable/reference/box.html. Reliability: official docs.
- Box docs: "Safe Box" is a legacy Windows cmd.exe raster-font safeguard; unsafe boxes are replaced automatically unless `safe_box=False` (Console) or the Table option. Our code finding (identical Unicode borders with or without `safe_box` on this platform) is consistent: it only matters on legacy Windows. The fetched docs page does not enumerate which box constants are ASCII-safe in text; the codebase finding that `box.ASCII` is needed under `--ascii` stands as the source of truth. Docs confirm: boxes are constants imported from `rich.box` and passed as `box=` (to `Table` or `Panel`); `Panel` defaults to `box.ROUNDED`; `Panel(safe_box=True)` default; `expand=True` stretches to console width; `border_style` styles only the border. Source: https://rich.readthedocs.io/en/stable/panel.html and https://rich.readthedocs.io/en/stable/reference/panel.html. The names `ASCII`, `ASCII2`, `HEAVY` are not listed in the fetched doc text (only `SQUARE` and `ROUNDED` are); the box list is shown as an image, so existence of `box.HEAVY` and `box.ASCII` should be confirmed by `dir(rich.box)` in the installed 15.0.0 (the codebase finding already uses `box.ASCII`). Relevance: MEDIUM.

### G2. 16-colour downgrade (Q4)
Sources: https://github.com/Textualize/rich/blob/v15.0.0/rich/color.py ; https://rich.readthedocs.io/en/stable/appendix/colors.html. Reliability: official source/docs.
- Truecolor to 256: RGB goes to HLS; saturation under 15 percent is treated as grey and mapped to the grey ramp (indices 16, 231, 232-255); otherwise each channel is quantised to the 6-level cube (index 16 + 36r + 6g + b). Arithmetic, no perceptual distance. Truecolor to standard: the RGB triple is matched against `STANDARD_PALETTE` (matching metric not shown in the fetched excerpt). The first 16 colours are defined by the user's terminal theme, so even correct indices look different per terminal (docs note this). Relevance: HIGH. Supports the code finding (muted, green, red, violet all collapse to index 7; slate to 8): this collapse is a property of the downgrade, so the 16-colour tier must be designed with named ANSI colours (`red`, `green`, `bright_black`, `magenta`, `dim`, `bold`) rather than hex values that get downgraded. Not found: any Rich-documented guidance for keeping several muted roles distinct at 16 colours; the usual approach is to carry role meaning in dim/bold/underline and glyph/label text as well as colour (this is an inference, not a source claim).
- Layout/Columns/Table/Panel all measure children with `cell_len` and render to Segment lists, so none breaks a one-renderable-per-line rule by itself, but they would replace the "one `Text` per line" structure the tests require. Relevance: HIGH (Q1): see Recommendations.

### H. Keeping a line-based text model while styling it
Not found as a documented Rich pattern; derived from the sources above. Relevance: HIGH (Q1, Q4).
- Rich separates content from style: `Text` holds plain text plus `Span`s. A line model can stay `list[str]` if styling is derived by a pure function `style_spans(line, role) -> Text`, where the role comes from a line's position/prefix, or if `screen_lines` returns `list[Text]` whose `.plain` equals today's strings. Both keep `str(line)` identical for text records and JSON.
- Text records and one-shot plain output should use `Text.plain`, never a styled capture, so styling cannot leak into them.

## Key External Findings
- Rich keeps content and style separate (`Text` plus `Span`s), so a styled line can keep an unchanged plain string. [HIGH] (https://github.com/Textualize/rich/blob/v15.0.0/rich/text.py)
- `color_system` accepts None, "auto", "standard", "256", "truecolor", "windows"; "auto" reads `COLORTERM` (truecolor/24bit) then the last part of `TERM`, defaulting to standard. [HIGH] (https://rich.readthedocs.io/en/stable/console.html)
- Rich's own NO_COLOR removes colour only and keeps bold/dim/italic/underline; `color_system=None` (our code) removes all SGR. `NO_COLOR` beats `FORCE_COLOR`. [HIGH]
- `export_text(styles=False)` is plain text by default; `styles=True` renders recorded styles without NO_COLOR or downgrade applied at write time (source reading, inference to verify). [HIGH]
- `Live(screen=True)` wraps in `Screen`, which pads rows to width and crops rows beyond height (no ellipsis); Rich docs' "ellipsis" default applies to non-screen Live. [HIGH]
- `Text` with `no_wrap=True, overflow="crop"` clips a long unbroken token silently; `overflow="ellipsis"` costs one cell and marks truncation; `fold` splits the token over lines (breaks one-line-per-row). [HIGH]
- `cell_len` is table-based: wide characters 2, combining 0, no locale rule for ambiguous width, ASCII fast path and cache. [HIGH]
- Truecolor to 16 colours is arithmetic palette matching, and the first 16 colours are terminal-theme dependent, so distinct hex roles can collapse. [HIGH]
- `Panel` default box is ROUNDED, `expand=True`, `safe_box` only matters on legacy Windows. [MEDIUM]

## Recommendations from External Research
- Q1 (composition): keep the line model as the source of truth and add styling as a thin pure layer (`Text.assemble` or `stylize` with spans per role), returning `Text` whose `.plain` equals today's line. Prefer this over Table/Layout/Columns, which would replace the one-renderable-per-line structure the tests pin. Use Panel/box only if borders are drawn as text lines in the model; otherwise keep hand-built border characters and select ASCII glyphs under `--ascii`. Confirm `dir(rich.box)` in 15.0.0 before relying on `box.HEAVY`/`box.ASCII`.
- Q4 (colour depth): `color_system="auto"` is a cheap upgrade path to 256/truecolor, but the 16-colour floor must stay legible: define roles with named ANSI colours plus dim/bold/underline and a text or glyph cue, not only hex, since downgrade collapses nearby hues (matches the code finding). Keep `color_system=None` for NO_COLOR (strictest) unless the owner wants bold/dim kept, in which case use `no_color=True` instead. Treat `FORCE_COLOR`/`TERM=dumb` as Rich-handled once `auto` is used.
- Q5 (capture gate): do not use `export_text(styles=True)` to test NO_COLOR or the 16-colour downgrade. Capture the written stream from a Console writing to a StringIO with `force_terminal=True` and the production `color_system`, then assert on SGR sequences (none under NO_COLOR; only 30-37/90-97/2/1 style codes at standard). Keep `export_text()` (plain) for the one-shot text and snapshot tests. Alternate-screen drawing keeps SGR, so the same stream capture applies to LiveScreen.
- Q7 (long token): current `crop` clips silently at width; consider `overflow="ellipsis"` per line for a visible marker, and measure with `cell_len` not `len` wherever padding is hand-computed. Anything taller than the console height is silently dropped under `screen=True`, so the layout must reserve its own overflow indicator.
- Discrepancy notes: (1) Rich docs say Live defaults to an ellipsis on overflow, but under `screen=True` rows are cropped (the code finding is correct). (2) Rich's NO_COLOR keeps bold/dim; our code's NO_COLOR drops them (project choice, not a conflict). The codebase remains the source of truth.
- Not found: a documented Rich pattern for a line-model-plus-styles design, and Rich-specific guidance for keeping many muted roles distinct at 16 colours; both are inference above.
