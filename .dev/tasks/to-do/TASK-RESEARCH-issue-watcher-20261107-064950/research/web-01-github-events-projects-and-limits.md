## 4. REST rate limits (question 6, part 1)

Source: https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api (retrieved 2026-11-07). Reliability: official.

- Authenticated user primary limit: normally 5,000 requests/hour, shared across personal tokens and apps acting for that user. [EXTERNAL-VERIFIED] Relevance: HIGH. Important for A: several tools running as the same login share one 5,000/hour allowance.
- Enterprise Cloud user auth through an enterprise-owned GitHub App/OAuth app: 15,000/hour; but higher-limit app traffic still consumes the user's lower allowance. [EXTERNAL-VERIFIED] Relevance: LOW.
- GitHub App installation: 5,000/hour base; outside Enterprise Cloud +50/hour per repository beyond 20 and +50/hour per organization user beyond 20, capped at 12,500/hour; Enterprise Cloud org installations 15,000/hour. [EXTERNAL-VERIFIED] Relevance: MEDIUM (B/C).
- Actions GITHUB_TOKEN: 1,000 requests/hour per repository (15,000 for Enterprise Cloud accounts' resources). [EXTERNAL-VERIFIED] Relevance: MEDIUM (C).
- Secondary limits: max 100 concurrent requests (REST + GraphQL combined); 900 points/minute for REST endpoints and 2,000 points/minute for GraphQL; most REST reads cost 1 point and writes 5; content creation generally 80 requests/minute and 500/hour. [EXTERNAL-VERIFIED] Relevance: MEDIUM.
- Response headers: x-ratelimit-limit, x-ratelimit-remaining, x-ratelimit-used, x-ratelimit-reset (UTC epoch seconds), x-ratelimit-resource; exhausted primary limit requires waiting for the reset timestamp; honor any retry-after header on throttling. [EXTERNAL-VERIFIED] Relevance: HIGH for the poller's backoff design.
- Conditional requests: not covered in the fetched excerpt of this page; see the next section (separate page).

## 5. Conditional requests and polling guidance (question 6, part 2)

Source: https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api (retrieved 2026-11-07). Reliability: official.

- Keep the response `etag` and send it as `if-none-match` on the next GET (or `last-modified` as `if-modified-since`). An unchanged resource returns `304 Not Modified`, and that result "consumes no primary-rate-limit allowance when authentication through the Authorization header is correct" (paraphrase of the page's statement; the fetch tool returned a summary, so the quoted phrase is the tool's wording). [EXTERNAL-VERIFIED] Relevance: HIGH for A. A REST-based poller that stores one ETag per query makes idle cycles free of primary quota.
- Polling advice: the page recommends subscribing to webhooks instead of polling; when polling is unavoidable, use a regular cadence no faster than necessary, honor any `x-poll-interval` minimum, authenticate conditional GETs, and keep filters, pagination and ordering stable so cache reuse works. [EXTERNAL-VERIFIED] Relevance: HIGH (this is the official statement that webhooks are preferred; it is the revisit argument for B/C, but a 5-minute poll is within the "polling when unavoidable" guidance).
- Secondary-limit precautions: make calls sequentially (optionally via a queue); leave at least one second between POST/PATCH/PUT/DELETE calls; on throttling, honor retry-after or the reset time, otherwise wait at least a minute, back off exponentially and cap retries. [EXTERNAL-VERIFIED] Relevance: HIGH for the poller's per-cycle launch cap and retry cap (gap 15).
- GraphQL and ETag: see the next section. The best-practices page speaks of REST GETs; it does not say GraphQL supports `if-none-match`.

## 6. GraphQL rate limits (question 6, part 3)

[EXTERNAL-VERIFIED] Relevance: HIGH.

The page's example: 5,101 requests cost 51 points. `first`/`last` must be 1 to 100 per connection. "Individual calls cannot request more than 500,000 total nodes." [EXTERNAL-VERIFIED] Relevance: HIGH. A single-connection query with `first: 100` costs 1 point.

- Secondary: 100 concurrent requests (REST + GraphQL); GraphQL 2,000 secondary points/minute (1 per non-mutation call, 5 per mutation); CPU budget of 90 seconds per 60 seconds (at most 60 seconds for GraphQL); content creation about 80/minute and 500/hour; "additional compute-related or unpublished restrictions may apply". [EXTERNAL-VERIFIED] Relevance: MEDIUM.

### 14.2 What 12 requests per hour per workspace costs

- Per-user allowance is 5,000 REST requests/hour or 5,000 GraphQL points/hour, shared across all tokens and apps of that login (sections 4 and 6).
- One call per 5-minute poll is 12 requests/hour: 0.24% of 5,000. Three calls per poll (one issue or items listing, one issue-events lookup per candidate, one pre-launch re-read) is 36 requests/hour: 0.72%.
- Poll interval comparison for a single call per poll: every 1 minute 60/hour (1.2%), every 5 minutes 12/hour (0.24%), every 15 minutes 4/hour (0.08%). With N developers each on their own login the allowances are separate, so the cost does not add up across developers; it adds up only across workspaces sharing one login: W workspaces x 12 x calls-per-poll (for W = 5 and 3 calls: 180/hour, 3.6%).
- Paginated Project reads: a Project with 1,000 items listed 100 per page is 10 REST calls per poll, 120 requests/hour at 5-minute cadence (2.4%). In GraphQL, one items page of 100 with 8 field values per item estimates to about 9 points (section 7), so about 90 points per poll for 1,000 items, 1,080 points/hour (21.6%); the REST route with `q` and `fields` limited to the Status field is cheaper. A server-side `q` filter (section 8) shrinks the result to the Backlog set.
- Exhaustion would need roughly 400 calls per poll at 12 polls/hour, so it is not a realistic revisit trigger under A unless many workspaces share one login or the Project is very large and unfiltered.
- Idle polls can be free on primary quota with ETag + `if-none-match` on REST GETs (a 304 with correct authentication is not charged, section 5). GraphQL conditional requests are not documented (section 6), so a GraphQL poller pays every cycle. `gh` does not expose ETag handling on its high-level commands as far as the manual pages fetched show [UNVERIFIED]; using `gh api` with an `If-None-Match` header is a generic mechanism, not documented on the pages fetched here [UNVERIFIED].
- Secondary limits: sequential calls from one poller sit far below 900 REST points/minute and 100 concurrent requests; issue search stays far below 30 requests/minute. The poller must still be sequential, honor retry headers and cap retries (section 5).

### 14.3 Cheapest correct filter for "tagged, human-approved, in a Project, Status Backlog"

- Issue search can express: label, `project:ORG/NUMBER`, assignee, open, is:issue, but NOT Status (section 10). So search alone is not correct for the Backlog test.
- The Project items route / `gh project item-list --query` can express `status:Backlog`, `label:`, `assignee:` and `is:issue` in its documented filter syntax (sections 7 and 8), which makes it the single call that covers tagged + in Project + Backlog (+ owner); returns item and content fields; needs the Project read token. Candidate fields to request: Status, plus the issue number from `content`.
- "Human-approved" is not a queryable state: it must be derived from who applied the approval label (latest `labeled` event `actor` from the issue events or timeline API, section 11) and checked against an allow-list, one extra call per surviving candidate. Cost: bounded by the number of candidates per poll (cap it). A cache keyed by issue number and label-event id avoids repeats.
- Suggested minimal sequence (design proposal, not a page fact): (1) one Project items query with `q` for Backlog + trigger label + owner filter, `per_page` 100; (2) per candidate, one issue-events call for the approval label's latest actor; (3) one fresh issue read right before launch (state open, assignee unchanged); then launch. About 1 + k + k calls per poll for k candidates, zero when there are no candidates.
- Fallback if the Project read is not available: a label-only selection (trigger label + approval label + `assignee:@me`, via issue search) avoids Projects entirely, at the cost of losing the Status check (the notes already flag this as the label-only option, gap 5). Status Backlog then needs another proxy (for example the claim marker or a state label).

## Recommendations from External Research

1. The evidence supports the owner-decided option A: nothing found makes a per-workspace 5-minute poller unworkable. The only hard prerequisite is that each polling login can read the org Project (add `read:project`, or issue a fine-grained token with org Projects Read); this matches brief fact 9 (the observed token lacks it).
2. Use one Project items call with a server-side filter (`gh project item-list <n> --owner <org> --query "..." --format json -L 100`, or the REST items route with `q`) for tagged + in Project + Status Backlog + owner in one request, because issue search cannot express Status. Always pass an explicit limit (default is 30). Confirm in the owner-run live test that `--query` accepts the intended filter (gap 11).
3. Derive "human-approved" from the latest `labeled` event actor of the approval label (issue events or timeline API), checked against a named allow-list; Triage-or-above can apply labels, so role alone is too weak. One call per surviving candidate, capped per cycle.
4. For the intended-owner filter prefer assignment to the polling login (`assignee:@me`) or a per-person label: both are part of the same query at no extra cost. First-come unassigned claiming (candidate 4) is the only option with a race; pair it with a pre-launch re-read and an at-most-once dispatch record, and treat the claim's lack of mutual exclusion (brief fact 2) as the residual risk.
5. Poller hygiene taken from GitHub's guidance: sequential calls, honor `retry-after` and `x-ratelimit-reset`, back off exponentially with a retry cap, and treat `incomplete_results: true` as "unknown", not "empty". Where REST is used, store ETags so idle cycles are free.
6. Record B/C revisit triggers as in section 14.5 (token cannot read Project, need for seconds-level latency, shared-login exhaustion, double-claim incidents, need for Status-change history). Note that a push design inherits "no automatic redelivery", which is worse for a stopped workspace than a pull poller.
7. Do not rely on a scheduled Action as an alternative poller: it needs a PAT/App secret for the org Project, may drop runs, and still needs a path into the workspace.

## Summary

Confirmed on official GitHub pages today (2026-11-07): scheduled Actions have a 5-minute floor with possible delay and dropped runs; no workflow trigger reacts to a Project Status change; the Projects v2 webhook exists only as an organization-availability event needing an App with "Projects" read. Reading an org Project needs `read:project` (classic), org Projects Read (fine-grained or App), not GITHUB_TOKEN; a REST items route with a `q` filter and `gh project item-list --query` can filter by Status, label and assignee in one call, while issue search cannot filter by Status.

For owner-decided option A the cost is negligible: 12 polls per hour is about 0.24% of a user's 5,000/hour per call type, separate per developer login; the main prerequisites are the per-login `read:project` scope, an explicit item limit above 30, and verifying the server-side filter live. The intended-owner filter is cheapest as `assignee:@me` or a per-person label; unassigned first-come is the only racy choice. Revisit triggers for B/C: a token that cannot read the Project, a need for seconds-level latency, many workspaces sharing one login, double-claim incidents, or a need for Status-change history. The 15 gaps above, mostly closable by one owner-run live call, remain open.
