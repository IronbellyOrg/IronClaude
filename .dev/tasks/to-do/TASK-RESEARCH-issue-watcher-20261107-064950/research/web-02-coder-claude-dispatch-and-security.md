## A. Gap 9: where a 5-minute poller runs in a Coder workspace, and what survives

### A1. `coder_script` supports `cron` (six fields, seconds first) and `run_on_start` -- relevance HIGH
- Source (primary, official Terraform provider docs; retrieved 2026-11-07): https://registry.terraform.io/providers/coder/coder/latest/docs/resources/script ; same text in the provider repo: https://github.com/coder/terraform-provider-coder/blob/main/docs/resources/script.md (fetched via the raw URL). provider=WebSearch/WebFetch reason=tavily-unavailable.
- Facts [EXTERNAL-VERIFIED: the two URLs above]: `coder_script` runs shell content through a workspace's `coder_agent`. Arguments: `agent_id`, `display_name`, `script` (required); `cron` (optional, "seconds minutes hours day-of-month month day-of-week", i.e. six fields, seconds first, unlike Unix cron); `run_on_start` (runs when the agent starts; the script must exit to signal readiness); `run_on_stop` (runs at agent shutdown); `start_blocks_login`; `log_path`; `timeout` (seconds; default 0 = no limit; on exceeding it the agent lifecycle gets a timeout status). Scripts on one agent run concurrently unless sequenced with `coder_script_order` (needs Coder v2.39 or newer).
- The page's own example is exactly our cadence: a "periodic health check" with `cron = "0 */5 * * * *"` (every five minutes). A cron entry such as `0 */5 * * * *` is therefore the documented way to run a 5-minute poller inside a workspace without systemd or system cron.
- Related: the overview page https://coder.com/docs/admin/templates/extending-templates says `coder_script` handles startup, shutdown and "periodic jobs" and replaces the deprecated `coder_agent.startup_script`; "All processes on the workspace are then spawned from the agent." It does NOT say that cron runs stop when the workspace is stopped, and does NOT discuss overlapping runs of a cron script or its timeout behaviour. [UNVERIFIED]: whether a still-running previous cron invocation blocks or overlaps the next one (the poller should therefore take its own lock, e.g. `flock`, [PROPOSAL]).
- Relation to codebase: the brief (item 13) leaves the poller host open; this establishes a documented mechanism. The `coder_script` lives in the Coder template (Coder repo), not in IronClaude, so IronClaude ships only the poller script and the setup instruction; the template wiring is a follow-up in the Coder repo. Supports option A's "no new inbound port".

### A2. A script/process in the workspace only exists while the workspace is running -- relevance HIGH
- Source: https://coder.com/docs/user-guides/workspace-lifecycle (shows "v2.39, Mainline") and https://coder.com/docs/admin/templates/extending-templates/resource-persistence (retrieved 2026-11-07).
- Facts [EXTERNAL-VERIFIED]: resource-persistence page: "By default, all Coder resources are persistent"; resources are made disposable by tying Terraform `count` to the workspace start-count (0 when stopped, 1 when running), so the illustrated Docker container is removed on stop and recreated on start, while "persisting user data like filesystem volumes" is the recommended balance. Lifecycle page: "ephemeral resources are destroyed and recreated on restart"; persistent infrastructure stays allocated during shutdown.
- Inference [PROPOSAL, from the two facts above, not stated verbatim by Coder]: when a workspace stops, the container and the agent and therefore every cron script and background process die; when it starts again the agent starts, runs `run_on_start` scripts again and resumes `cron` scheduling. So a poller defined as `coder_script` with `cron` (and optionally `run_on_start`) is restarted automatically by every start/restart, and polls only while the workspace is running. A stopped workspace polls nothing: issues approved while all of a developer's workspaces are stopped wait until one starts (acceptable for a pull design, but must be stated in the design doc).
- [UNVERIFIED] on a primary page: that the agent process and children are killed on stop in every template type (depends on the template; the Docker example above deletes the container).

### A3. Autostop and inactivity: the poller does not keep a workspace alive -- relevance HIGH
- Source: https://coder.com/docs/user-guides/workspace-scheduling and https://coder.com/docs/admin/templates/managing-templates/schedule (retrieved 2026-11-07).
- Facts [EXTERNAL-VERIFIED]: autostart needs admin permission in the template, then users choose time, weekdays and timezone; autostop is a user-configured runtime (hours) that "active use" postpones; no numeric default TTL is stated on the page; the "activity bump" default is one hour (template-admin controlled). Qualifying activity: VS Code (code-server / remote extension), JetBrains, browser terminal, SSH via `coder ssh` or ssh config, and "a coding agent reporting that it is working" (extends the stop deadline). The page excludes "Accessing ports through direct URLs without an active session", browsing workspace pages/logs, and routine agent-statistics reporting. Premium features: mandatory (maintenance) stops at the user's quiet hours despite activity; dormancy (stopped workspace, automatic start blocked, manual reactivation needed) and optional deletion of dormant workspaces; failed-workspace timeout.
- Consequences for a 5-minute poller [PROPOSAL derived from the facts]: (a) a cron script or background process is not on the list of qualifying activity, so it neither prevents autostop nor inactivity shutdown; (b) a workspace left idle past its deadline stops and the poller stops with it; (c) a session started by the poller via `orca agent launch` is not documented as activity either, unless it reports as a coding agent through Coder's task-status mechanism [UNVERIFIED for Orca-launched Claude sessions]; (d) with Premium dormancy a long-unused workspace can become dormant and will not be auto-started, so the poller is silent until a human reactivates it.
- The scheduling page does not say whether connecting with `coder ssh` to a stopped workspace auto-starts it; the CLI reference does (see B2: auto-start unless `--disable-autostart`). This matters only for push options B/C, not for A.

### A4. Durable state: where a dispatch record may live -- relevance HIGH
- Source: https://coder.com/docs/admin/templates/extending-templates/resource-persistence (retrieved 2026-11-07).
- Fact [EXTERNAL-VERIFIED]: persistence is a per-template Terraform decision; volumes are the pattern for data that must survive stop/start; the Docker example's container (and its writable layer) is replaced on every start. The page does not name "home directory" explicitly. [UNVERIFIED]: whether the target template (the sibling Coder repo's `templates/VSCode-AIDev02`, read only via the issue text) mounts `$HOME` on a persistent volume. The design must treat a path outside a persisted volume as ephemeral.
- [PROPOSAL] Three-tier state design, from most to least trustworthy for at-most-once: (1) GitHub itself (assignee equal to the poller's login plus a claim marker comment, as `/sc:issue --claim` already writes marked comments and is idempotent for the same assignee per the brief items 1 and 11) -- survives workspace loss and is visible to every workspace; (2) a small dispatch record file under the persisted home volume (for example `~/.local/state/<tool>/dispatched.json`, atomic write via temp file plus rename) -- survives stop/start only if `$HOME` is persisted; (3) never rely on `/tmp` or container-layer paths. A lost local record must fail safe: on a missing record the poller re-derives state from (1) and does not re-launch an issue that already has the claim marker.
- Relation to codebase: extends gap 15 (local dedupe versus "assigned to my login and no claim marker comment of mine"); supports the second because it is the only record that survives an ephemeral container.

## B. Coder question (1): reachability, CLI, REST API, tokens, external auth

### B1. Agents connect outbound; no fixed inbound workspace port -- relevance HIGH
- Source: https://coder.com/docs/admin/networking (retrieved 2026-11-07; no page date shown). provider=WebSearch/WebFetch reason=tavily-unavailable.
- Facts [EXTERNAL-VERIFIED]: workspace agents initiate HTTP/HTTPS connections to the control plane's `CODER_ACCESS_URL` (proxies must support WebSocket); the page specifies no fixed inbound workspace port to expose. Direct user-to-workspace connections use a WireGuard tunnel (CLI, VS Code, JetBrains) that needs bidirectional UDP between the two ends (STUN on UDP 3478, high ephemeral ports for the tunnel); when direct fails, traffic goes through the DERP relay built into the control plane (or Tailscale/custom DERP). "Direct connections via the web browser are not supported." "All user-workspace connections are end-to-end encrypted."
- Meaning for our design [PROPOSAL, inference]: an external system (GitHub Actions runner, a microservice) has no public address to call on a workspace; it can only get in through the Coder control plane (CLI `coder ssh` / `coder port-forward`, the app proxy, or the REST API), each authenticated with a Coder session token. This is the factual basis for the owner's choice of option A (pull) and for recording B/C as needing Coder-side machinery (Coder#477).
- Related page https://coder.com/docs/admin/infrastructure/architecture only says the agent runs inside the workspace and `coderd` handles agent registration; it does not state connection direction. [UNVERIFIED] there; the networking page above is the source.

### B2. `coder ssh`, `coder port-forward`, `coder external-auth access-token` exist (verified before naming) -- relevance HIGH
- `coder ssh [flags] <workspace> [command]` "opens an interactive workspace session or executes a remote command"; insert `--` before the command to pass its flags; no pseudo-terminal for commands unless `-t`. A stopped workspace "starts automatically unless `--disable-autostart` is enabled" (default false); `--no-wait` / `--wait` control whether to wait for agent init scripts. [EXTERNAL-VERIFIED: https://coder.com/docs/reference/cli/ssh] This corrects the "not established" remark in A3: the CLI reference does say `coder ssh` auto-starts a stopped workspace (the scheduling page did not). Relevance for B/C: a push from outside could start a stopped workspace with `coder ssh`, at the cost of a start-up delay and a Coder token.
- `coder port-forward [flags] <workspace>` (alias `tunnel`) "Forward ports from a workspace to the local machine"; flags `-p/--tcp`, `--udp`, `--disable-autostart`; reverse direction is `coder ssh -R`. [EXTERNAL-VERIFIED: https://coder.com/docs/reference/cli/port-forward]
- `coder exec`: not looked up and not named by us; the task prompt's "`coder exec`-style" command is not shown to exist; the verified equivalent is `coder ssh <workspace> <command>`. [UNVERIFIED that a `coder exec` subcommand exists]
- `coder external-auth access-token [flags] <provider>`: validates and prints the provider access token on stdout (exit 0); if no valid token it prints an authentication URL and exits 1; `<provider>` examples are `github` and `slack`; flags `--extra`, `--output text|json`, `--agent-token` (env `CODER_AGENT_TOKEN`), `--agent-token-file`, `--agent-url` (env `CODER_AGENT_URL`), `--auth`, `--agent-name`. [EXTERNAL-VERIFIED: https://coder.com/docs/reference/cli/external-auth_access-token] The parent command is "authentication to third-party services from within a workspace" (https://coder.com/docs/reference/cli/external-auth). The agent token is the credential for the workspace, not the GitHub token.

### B3. External auth ties a workspace to the owner's linked GitHub account, but the page does not guarantee it -- relevance HIGH (gap 19)
- Source: https://coder.com/docs/admin/external-auth (retrieved 2026-11-07).
- Facts [EXTERNAL-VERIFIED]: the administrator supplies the GitHub integration's client ID and secret; each user authorizes through GitHub and Coder stores that user's OAuth token (not one deployment-wide token). The detailed GitHub walkthrough creates a GitHub App with repository permissions. A `coder_external_auth` data block (Terraform) references the provider ID and exposes `access_token`. Inside a workspace the token is read with `coder external-auth access-token <ID>`; for HTTPS git Coder configures `GIT_ASKPASS`; SSH remotes use keys instead.
- NOT established on the page [UNVERIFIED]: that the token lookup always uses the workspace owner's identity (the page does not state it); token refresh and expiry handling. Therefore the statement "the workspace's `gh` login equals the Coder workspace owner" is an assumption (gap 19); the safe record is that `gh` in the workspace holds whichever account authenticated it, and the poller should read its own login with `gh api user -q .login` rather than assume. [PROPOSAL]
- Supports the brief (item 1, 11): `@me` in `/sc:issue --claim` is the `gh` login of the running session, so identity under option A is the workspace's `gh` login, not a Coder-side mapping.

### B4. Coder REST API and API tokens -- relevance MEDIUM
- Sources: https://coder.com/docs/reference/api (header `Coder-Session-Token: <your-token>`, base path `/api/v2`, tokens at `https://<deployment>/settings/tokens`) and https://coder.com/docs/admin/users/sessions-tokens (retrieved 2026-11-07). [EXTERNAL-VERIFIED]
- Facts: users create tokens for their own accounts (dashboard, or `coder tokens create --name=my-token --lifetime=720h`; `720h` is an example, not a default); creating one for another user requires the `Owner` role (CLI `--user <username>` from v2.17); a token acts as its user, bounded by the user's permissions, and is invalidated if the user is removed; `--scope` (repeatable) and `--allow` (resource UUIDs or wildcards) narrow a token, child tokens cannot exceed the creator and cannot outlive it (403 otherwise); administrators can cap lifetime with `CODER_MAX_TOKEN_LIFETIME`.

### C2. Flags and permission behaviour in `-p` -- relevance HIGH
- Source: https://code.claude.com/docs/en/headless and https://code.claude.com/docs/en/cli-reference (both retrieved 2026-11-07). [EXTERNAL-VERIFIED]
- `-p/--print` runs non-interactively; `--output-format text|json|stream-json` (`json` carries session id, result, cost; `--json-schema` yields `structured_output`); exit code 0 on success, non-zero on failure, 143 on SIGTERM; `--max-turns` (print mode only; no limit by default); `--max-budget-usd` cap; `--no-session-persistence` (print mode only); `--continue`/`--resume <id>`.
- Permissions: `--allowedTools "Bash(git diff *),..."` uses permission-rule syntax with prefix matching. Documented default (Claude Code v2.1.302 or later): `claude -p` runs start in Manual mode when nothing sets a permission mode, and "a call that needs approval is denied unless something approves it" (a `PermissionRequest` hook or `--permission-prompt-tool`). `--permission-mode` accepts values such as `auto`, `dontAsk`, `acceptEdits` (and `bypassPermissions`, which `--dangerously-skip-permissions` is documented to equal). `dontAsk` "denies every call that would otherwise prompt"; `--permission-prompts none` (v2.1.259 or later) denies anything that would prompt and removes tools needing a human such as `AskUserQuestion`.
- `--bare` skips auto-discovery of hooks, skills, custom commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md; the page says `--bare` "is the recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release". Meaning for this repo: under `--bare` the `/sc:issue` custom command and the repo's hooks would NOT load; a `-p` run for `/sc:issue --claim` must not use `--bare` unless the command file is supplied another way. [PROPOSAL inference from the two facts]
- Security-relevant documented behaviour: without `--bare`, "a `-p` session runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted. A `-p` session shows no workspace trust dialog and no per-server approval prompt." Relevance for a watcher: the working directory content (the repo) is trusted implicitly; the poller must launch only in a checkout it controls. Details: https://code.claude.com/docs/en/permissions.md#what-runs-before-you-trust-a-folder (linked from the page, not read).
- Difference from an interactive session for this repo's skills [PROPOSAL, derived]: `-p` is single-shot (no follow-up turns unless `--continue`), cannot ask the user (`AskUserQuestion` removed with `--permission-prompts none`), and denies un-allow-listed Bash. `/sc:issue --claim` never prompts (brief item 1) and needs `gh`, `git`, file writes under `.dev/issues/`; those would have to be allow-listed. The repo's own Orca note (brief item 10) that Orca sessions run with `--dangerously-skip-permissions` is a different, broader permission posture than `-p` Manual mode.

### C3. Where this leaves the "headless route" -- relevance MEDIUM

## D. Claude Code GitHub Action, `anthropics/claude-code-action` (question 3)

### D1. Triggers, runtime and authentication -- relevance HIGH
- Source (primary, official; retrieved 2026-11-07; no date shown): https://code.claude.com/docs/en/github-actions . provider=WebSearch/WebFetch reason=tavily-unavailable. [EXTERNAL-VERIFIED]
- The action "runs Claude Code inside your repository's workflows" on GitHub-hosted runners (consumes Actions minutes plus API tokens). Two modes: interactive (no `prompt` input; waits for the trigger phrase `@claude` in an issue or PR comment, a PR review, or in the body or title of a newly opened issue) and automation (a `prompt` input; runs on any GitHub event, including `schedule`; results go to the run log unless the prompt and tools post to the issue/PR). The `prompt` input accepts a skill invocation (`/skill-name`; repository skills need `actions/checkout` first).
- Authentication: repository secrets `ANTHROPIC_API_KEY` (API key) or `CLAUDE_CODE_OAUTH_TOKEN` (subscription token from `claude setup-token`; tied to the subscription of the person who ran it); or workload identity federation exchanging the workflow's GitHub OIDC token for Claude API access via a Console service account (inputs `anthropic_federation_rule_id`, `anthropic_organization_id`, optionally `anthropic_service_account_id`, `anthropic_workspace_id`; needs `id-token: write`). Amazon Bedrock, Google Cloud Agent Platform and Microsoft Foundry are supported through OIDC federation.
- Permissions model: the Claude GitHub App needs Contents, Issues, Pull requests (read and write); the official shared app is granted a larger set (Actions, Checks, Discussions, Workflows, Repository hooks read/write, Administration/Members/Merge queues read, etc.) and "GitHub doesn't let you accept a subset"; an organization that wants only three permissions must create a custom GitHub App. Scheduled workflows run only from the default branch and, "in public repositories, disables the schedule after 60 days without repository activity" (relevant if a cron-driven Action were ever used; our fork is public).
- Relation to codebase: the repo has no workflow with `schedule:` or issue events (brief item 6). An Action would run on a GitHub runner, outside the developer's Coder workspace, and could not start a local Orca session; it cannot satisfy "the developer's workspace starts a session running `/sc:issue --claim <N>`" by itself, and `/sc:issue --claim` assigns `@me` of the runner's identity (the `GITHUB_TOKEN` or App), not the developer. It can serve only as the selector/notifier half of B/C (the "watcher"), which agrees with the owner's decision for A (no Action needed). [PROPOSAL inference]

### D2. Documented security guidance -- relevance HIGH
- Sources: https://code.claude.com/docs/en/github-actions ("Who can trigger runs", "Protect your credentials") and https://github.com/anthropics/claude-code-action/blob/main/docs/security.md (fetched via raw URL, retrieved 2026-11-07). [EXTERNAL-VERIFIED]
- Who can trigger: "The action can only be triggered by users with write access to the repository" (checks on issue, PR, comment and review events; for `workflow_run` both the workflow actor and the upstream initiator); `allowed_non_write_users` bypasses this, requires the `github_token` input and the docs say to use the job-scoped expiring `secrets.GITHUB_TOKEN`, not a PAT; bots are rejected unless listed in `allowed_bots` ("Prefer an explicit list over '*'", because a wildcard can expose public-repository workflows to attacker-controlled Apps). Dispatch and schedule events get no separate check.
- Injection defenses: the action sanitizes HTML comments, invisible characters, image alt text, concealed HTML attributes and HTML entities; the security page itself warns that "these defenses can miss new techniques", and that subprocess secret scrubbing and PID isolation are "partial protection, not immunity to injection". Untrusted checkouts must not be placed in the workspace root for `pull_request_target`/`workflow_run`; only a specified set of Claude-related paths is restored from the base branch, other files stay PR-controlled so trusted hooks can run attacker-modified scripts. Tool limits: narrow the allowlist via `claude_args`; validate generated results. App credentials are short-lived and scoped to the current repository. Commits are unsigned unless `use_commit_signing` or `ssh_signing_key` is set. The lower-level `claude-code-base-action` lacks the actor checks and base-config restoration.
- Cost guards documented: `--max-turns` in `claude_args`, workflow-level timeouts, GitHub concurrency controls.
- Lessons for our watcher [PROPOSAL, derived]: (1) mirror the "write access" gate: only act on issues whose approval was applied by an allow-listed account (gap 14); (2) the vendor's own defenses are explicitly partial, so the integer-only prompt (Q3) plus no sensitive secrets in the launched session remain the main controls; (3) use an explicit allowlist, never a wildcard, for any approver or bot list.

### H1. Signed requests: HMAC over the body plus a timestamp -- relevance HIGH
- Sources (primary vendor docs): https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries (GitHub) and https://docs.stripe.com/webhooks (Stripe, section "Verify webhook signatures manually" and "Preventing replay attacks"). [EXTERNAL-VERIFIED]
- GitHub: signature in `X-Hub-Signature-256`; HMAC-SHA-256 hex digest keyed with the webhook secret over the original unmodified request body, prefixed `sha256=`; compare with a constant-time function; verify before parsing; keep a high-entropy secret in secure storage ("Never hardcode a token into an application or push a token to any repository"). The GitHub page gives NO replay protection (no timestamp; it does not mention `X-GitHub-Delivery` deduplication).
- Stripe: `Stripe-Signature: t=<unix time>,v1=<sig>`; `signed_payload = timestamp + "." + raw body`; HMAC-SHA-256 with the endpoint secret; constant-time compare; reject if the timestamp is outside a tolerance (libraries default to 5 minutes; "Don't use a tolerance value of `0`"); ignore schemes other than `v1` (downgrade protection); the raw body must not be modified; rotation: "roll" the secret and keep the old one active up to 24 hours, during which one signature per active secret is sent; duplicates are handled by logging processed event ids.
- Who holds the secret: both sides (shared secret). Rotation: manual overlap window (Stripe). Rejection: HTTP 4xx before processing (Stripe example returns 400 on verification failure).
- Meaning for B/C [PROPOSAL]: HMAC over `timestamp + "." + body` with a per-workspace secret (not one global secret) gives sender authentication and bounded replay (tolerance window), but the secret must live both with the sender (a GitHub Actions secret or a central service) and in the workspace; a leaked sender secret lets the holder trigger sessions on every workspace that shares it, hence per-workspace secrets.

### I2. Can a non-human caller with an API token reach an app? -- relevance HIGH
- Source (primary, Go package documentation of Coder's own code, v2.39.0 file referenced): https://pkg.go.dev/github.com/coder/coder/v2/coderd/workspaceapps . [EXTERNAL-VERIFIED for the statement; it is source documentation, not a user guide]
- Path apps use cookie `coder_path_app_session_token`, subdomain apps `coder_subdomain_app_session_token_{unique_hash}`; `AppCookies.TokenFromRequest` prefers the access-method-specific cookie and then falls back to Coder's standard token extraction, "including query parameters and the `Coder-Session-Token` header". `SignedTokenProvider.Issue` authenticates and authorizes access to the requested app with a long-lived session token and issues an app ticket; failure produces an error page.
- So a script can present `Coder-Session-Token: <token>` to a subdomain app URL and be authenticated as that token's user. The Coder user-guide pages read (port-forwarding, admin port-forwarding) do NOT document this programmatic path and name neither the header nor a query parameter for apps. [UNVERIFIED as a supported user-facing feature; it is visible in the implementation docs only]
- Consequence for "no unauthenticated port exposed" [PROPOSAL]: keep the listener's `coder_app.share = "owner"` (or `"authenticated"` at most; never `"public"`), so every request must carry a valid Coder session for the workspace owner (or a signed-in user), and add the application-level signature/idempotency checks from sections H and J as defense in depth. With `share = "owner"` the sender's Coder token must belong to the workspace owner, which is also the account-binding: only the owner's own token reaches the owner's workspace. With `"authenticated"` any signed-in deployment user's token passes the proxy, so the listener must then verify the sender itself (HMAC/OIDC).
- Relation to Coder#477: its requirement "authorized monitor requests reach the intended workspace ... no unauthenticated port exposed" can be built from `coder_app` with `share = "owner"` plus a per-owner token, or from `coder ssh`/`coder port-forward` with a token (B2); each needs a privileged or per-user Coder token held outside the workspace. Option A needs none of this.

## J. Minimal watcher-to-listener contract for B and C (question 9) and conditions to revisit A

Everything in this section is a [PROPOSAL] derived from sections B-I and from the sibling issue's stated requirements (read from the task brief, not re-read); where an element has a documented basis it is cited. The listener, registration and transport are Coder-repo work (Coder#477); IronClaude would own only the sender (selector/dispatcher) side and this contract text.

### J1. Request [PROPOSAL]
- Transport: HTTPS POST to a per-workspace listener reachable only through the Coder control plane (I1, I2); authenticated by Coder session/API token (H4) and, inside the listener, by a signature (H1) or OIDC token (H2).
- Body (JSON) with only fixed, validated fields: `repository` (string, `owner/name`, must equal an allow-listed repository), `issue_number` (integer, 1 to 999999999), `approval_event_id` (integer, the GitHub `labeled` event id from the issue events API, G2), `requested_at` (UTC timestamp), `request_id` (UUID). No issue title, no body, no comment text, no free-form field (owner decision Q3; OWASP segregate untrusted content, F2).
- Headers: `Coder-Session-Token` (proxy authentication, H4/I2); `Idempotency-Key: <sha256 hex of repository|issue_number|approval_event_id>` (G3: derived, so a retry or a second sender produces the same key); `X-Signature: t=<unix>,v1=<hmac-sha256 hex>` over `t + "." + raw body` (H1) or `Authorization: Bearer <OIDC JWT>` (H2). Receiver tolerance: 5 minutes (Stripe default, H1) [PROPOSAL value].
- Idempotency key to at-most-once mapping: the listener stores `(key -> state)` durably (home volume, A4) and answers a repeat of the same key with the stored outcome and never starts a second session (G3); a claim already made by this workspace's login is also visible on GitHub (G6).

### J2. Responses [PROPOSAL; status codes follow the Idempotency-Key draft where it defines them]
| Situation | Code | Notes |
|---|---|---|
| accepted, session start scheduled | 202 | body: `{"status":"accepted","request_id":...}`; start is asynchronous, the sender does not wait for the claim |
| duplicate of a completed request (same key and fingerprint) | 200 | returns the stored outcome (G3: "a response consistent with the request being completed") |
| same key currently in progress | 409 | G3 |
| same key with a different payload | 422 | G3 |
| missing/invalid signature, OIDC token or Coder token, wrong audience, stale timestamp | 401 | no processing; audit entry |

| invalid payload (not an integer, out of range, extra fields) | 400 | extra fields rejected, not ignored |
| workspace not running | n/a at the listener (nothing runs); the Coder front end answers with an error or the sender sees a connection failure; the sender must treat "unreachable" as "not delivered, retry later" and may start the workspace with `coder ssh` auto-start or the build API [UNVERIFIED which] (B2) | idempotent retry is safe |
| listener busy / rate limited | 429 | per-cycle launch cap (gap 15) |
- Audit fields to log on both sides [PROPOSAL; Coder#477 asks for an audit trail of routing and access decisions]: `request_id`, `idempotency_key`, `repository`, `issue_number`, `approval_event_id`, approver login (from the event actor), sender identity (Coder user id or OIDC `sub`/`job_workflow_ref`), target workspace id, source address as seen by the proxy, received time, decision (accepted/duplicate/401/403/400/409/422), launch outcome, and the orca launch id or session id if returned.

### J3. Conditions under which the owner should revisit option A in favor of B or C [PROPOSAL]
1. Workspaces that are mostly stopped, so approved issues wait too long for a poll (A2/A3); B/C could wake a workspace through the Coder control plane (`coder ssh` auto-start, B2) at the price of a privileged token.
2. Poll latency or GitHub API rate use becomes a problem (many workspaces polling every 5 minutes with their own login); a push or a single central selector would reduce calls. (The rate limit numbers were not researched here: [UNVERIFIED].)
3. A requirement for central audit and a single approver policy that cannot be enforced consistently by per-workspace pollers (each poller has its own copy of the allow-list).
4. The same login in several workspaces causing duplicate claims that the best-effort checks do not prevent (G1, gap 3), where a central dispatcher with a single decision point would fix it.
5. Coder ships (or the Coder repo builds) the workspace-to-account binding as a platform feature (E1 shows the pieces already exist in `create-task-action`), making B/C cheap.
6. The workspace `gh` token cannot read the needed Project fields (gap 5) while a central service holds a suitable token.
If none of these holds, option A stays; Coder#477 is unnecessary under A (owner decision).

## K. Polling budget on GitHub's side (supports option A, gap 9/11) -- relevance MEDIUM
- Source (primary): https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api (retrieved 2026-11-07). [EXTERNAL-VERIFIED]
- Authenticated users get "5,000 requests per hour", shared across personal tokens and apps acting for the user; secondary limits: 900 points per minute for REST, up to 100 concurrent requests across REST and GraphQL, 80 content-creating requests per minute and 500 per hour; after a rate-limit rejection honor `retry-after`/reset or wait at least 60 seconds, and use exponential backoff with a finite retry cap on repeated secondary-limit failures. The page prescribes no polling frequency and (in the text returned) does not discuss ETag/304 handling [UNVERIFIED here].
- Arithmetic [PROPOSAL]: a poll every 5 minutes is 12 per hour; even at 10 REST calls per poll that is 120 requests per hour per login, about 2.4 percent of 5,000. Because the quota is per user and shared across that user's tokens, several workspaces of one person add up (for example 5 workspaces x 120 = 600 per hour, 12 percent). The poller should cap calls per cycle and back off on `retry-after`. Fine for option A.
- Project access: `gh project item-list [<number>] --owner <login> --format json --limit N` exists (https://cli.github.com/manual/gh_project_item-list); the page states no required token scope and no JSON field schema [UNVERIFIED], so the brief's observation (item 9, missing `read:project`) cannot be resolved from the manual; keep a label-only selection as the documented-safe baseline (gap 5, gap 12).

## Summary
- Option A is workable on documented Coder primitives: a `coder_script` with `cron = "0 */5 * * * *"` (the provider's own five-minute example) runs the poller while the workspace runs; it stops on autostop and is not itself "activity"; durable state should be GitHub (assignee plus claim marker) with a local throttle file that is safe to lose.
- The Claude Code docs say `claude -p "/skill-name ..."` expands custom commands and skills; permissions default to Manual in `-p`; the Orca launch route is not covered by Claude docs and still needs one live test. No GitHub primitive gives atomic exclusion across logins; achievable is best-effort at-most-once through assignee, claim marker, a derived idempotency key and a finite retry cap. Prompt-injection guidance (OWASP, Anthropic, GitHub) supports the integer-only prompt, allow-listed approvers and least privilege, and warns that permission prompts are not a control under Orca's skip-permissions default.
- For the documented alternatives B/C, the pieces exist (outbound-only agents, `coder_app` share levels with `owner` default, Coder tokens, GitHub OIDC, HMAC with timestamp, Coder's `create-task-action` user mapping) and section J gives a minimal contract and the conditions to revisit A; all of that lives in the Coder repo (#477), and nothing here proposes listener code in IronClaude.
