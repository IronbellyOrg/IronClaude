### 1.3 The B-CTX gate, exactly
- Defined at design section 19.1 (lines 491-506). Problem: Git's pre-push hook receives remote name/location and ref-update records but no Claude session id (line 493), so a structural pre-push layer (L2) cannot tell an agent's push from the human's push in the same worktree. Invariant (line 493): "an ordinary human push in the same worktree is never restricted by launch policy"; an environment value, `CCSESSION_LAUNCH_ID`, `CLAUDECODE`, pane key, branch or path "is never sufficient authority".
- Completion evidence (line 504): a log-only probe (OB-CTX) must capture the process trees for main/subagent/nested/background Bash and Monitor-to-Git, a same-worktree human terminal, detached/reparented jobs, PID reuse, resume in a new process, /clear/fork, and release while a job is alive. "No single PID-label lookup is accepted".
- Verdict (line 506): "B-CTX remains OPEN/BLOCKING for the earlier plan's complete lifecycle coverage." The scoped job-identity integration (19.7) is "not a retroactive PASS". Order of work step 0 (line 359) makes B-CTX "the first required task in downstream workflow planning".
- Relevance to the watcher: B-CTX gates only the pipeline levels W/WA/F/FS. A claim without `--pipeline` is unaffected (design line 349 "nothing for `--pipeline none`"; line 355 "No-pipeline claims stay unaffected"). A claim-only watcher therefore is not blocked by B-CTX; B-CTX blocks only a later extension that wants governed levels.

### Key Takeaways
- The only implemented piece is the per-Bash-job identity adapter (`launch-job-identity.sh`). The guard that would decide allow or block (`launch-level-guard.sh`), the claim `--pipeline` interface, the marker/nonce binding and L2 pre-push do not exist in code.
- The adapter never denies a call on policy grounds (it rewrites the command, or exits 2 only when it cannot wrap a positively governed call, lines 484-486) and it acts only when `~/.claude/state/launch-level/sessions/<sid>` already exists; nothing in the repo creates that file. So today no launch level constrains a session started by any trigger.
- The design excludes a deliberately hostile or prompt-injected agent from scope (TH3 line 32; R12 "hostile agent: out of scope", line 450).

- The repository is **PUBLIC**: `gh repo view IronbellyOrg/IronClaude --json visibility,isPrivate,isFork` -> `visibility: PUBLIC, isPrivate: false, isFork: true` (2026-11-07). ## Summary

The only launch-governance code that exists is the per-Bash-job identity adapter (`launch-job-identity.sh`), which is dormant until a governed session record exists and is not even installed on this workspace; the guard script, the claim `--pipeline` interface, the marker binding and the pre-push layer are design only, and B-CTX blocks only those pipeline levels, not a claim-only watcher. Nothing registered today constrains a watcher-started session: there are no permission rules, no hook covers `gh`, `git` or file reads, ccsession launches with permissions bypassed by default (and Orca's default `--dangerously-skip-permissions` still applies even when `CCSESSION_PERMISSIONS=default` is set, `ccsession-tag/README.md:534`), the `gh` token (scopes `repo, workflow, read:org, gist`) is a readable file, and `master` is unprotected, on a repository that is public. The integer-only prompt rule is necessary but not sufficient: `/sc:issue --claim` itself reads title, body and all comments through `gh issue view` in Wave 1 and Wave 4 and posts worker-written files to the issue without review, so approval of an issue does not freeze the text the claim reads. Approval and routing authority sit entirely on GitHub roles (Triage or higher can label and assign; 3 such accounts exist), with the label-event actor available for a poller-side approver check and the assignee as the one routing input the claim already enforces; at-most-once, approver allow-listing, pre-launch integer validation and a permission-mode decision must all be built into the poller and its launch, because the claim, the Worker Contract (which does not govern a plain `orca agent launch` session) and the hooks provide none of them.
