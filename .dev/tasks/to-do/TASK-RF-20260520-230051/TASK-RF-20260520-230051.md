### OQ-1: Prefilter false-positive on contrived Bash command strings — STATUS: known-and-accepted

**Question:** The Fix 1 substring case pattern `*'"command"'*'gh'*'pr'*'create'*` has a known false-positive: a Bash command like `echo '"command" gh foo pr create'` (or any command containing those substrings in that order) would match and proceed past the prefilter into the downstream `jq` extraction and regex match.

**Resolution:** Accepted as known-and-accepted. Rationale: (a) the downstream regex at offer-pr-review.sh L29 (`[[ "$CMD" =~ ... ]]`) is the precise gate that decides whether the offer is actually emitted, (b) the prefilter's job is to skip the ~99% of Bash invocations that aren't `gh pr` at all and save three `jq` invocations on those — it is intentionally NOT a tight matcher, (c) the cost of a false-positive is one additional `jq` extraction cycle, not a wrong action (the precise regex still rejects), and (d) the alternative — using a regex-based prefilter — would defeat the cheap-POSIX-case design purpose. No further action required.

### OQ-2: Assertion DSL defined but no harness reads it — STATUS: deferred-by-design

**Question:** The Fix 3 assertion DSL is defined in evals.json (file_exists, report_contains, no_hallucinated_citations types with `text` field per Anthropic skill-creator convention) but no runtime harness currently consumes these assertions. No code path reads `src/superclaude/skills/sc-auggie-review-protocol/evals/evals.json`.

**Resolution:** Deferred-by-design. Rationale: (a) wiring a harness is explicitly out of scope per BUILD_REQUEST ("Fix 3 IS the test infrastructure (it adds assertions). There is no existing harness to run; harness wiring is out of scope (deferred to a separate future task)."), (b) the DSL is made self-documenting via the `text` field so a future implementer can wire it up without needing to re-derive intent, (c) the Anthropic skill-creator convention is the canonical authority for this file's shape and external skill-creator tooling can render these assertions in benchmarks today even without an in-repo harness. The `evals.json` file now provides forward-compatible harness-ready assertions; runtime enforcement is a separate future deliverable.
