# Requirements: pr-submit late conflict re-sync during the CI wait (P3 of #305, issue #361)

Source of the request: .dev/issues/361/issue-summary.md (accuracy check: the issue is current; none of P3 is on master).
This document restates that request as numbered requirements and records the corrections found by the advisory review of the first plan (.dev/reflect/pre-TASK-WF-issueSummary-20261107-064423-20261107064750/REPORT.md). Every repo fact below was read from the code on this checkout.

## Goal

While `/sc:pr-submit` waits on CI (Wave 8), a PR that turns conflicting is detected from the CI poll and the Wave 8a conflict step runs once more, limited by the existing router (`SYNC_CAP = 1`, Tier 0 and Tier 1 only; a late Tier 2 conflict halts with reason `late_conflict`). The protocol text, user docs and tests must agree with the code.

## Requirements

- R-001 `src/superclaude/skills/sc-pr-submit-protocol/scripts/poll-ci-checks.sh`, in `--pr` mode, reads `mergeable` and `mergeStateStatus` with both `gh pr view` calls (lines 71 and 108) and appends `merge_state` after `checks` in its JSON line as an object `{"mergeable": <string>, "status": <string>}`; the early-return payload (first view fails) carries two empty strings; the existing keys keep name, value and order; evidence mode and every `--repo` scoping are untouched. The header comment must not contain the word "force" or the literal text `gh pr checks --repo`.
- R-002 `src/superclaude/pr_submit/conflicts.py` gains `late_conflict_trigger(payload, wait_sha=None) -> bool`, next to `mergeability_hint`. It is true only when `payload` is a dict, `payload["merge_state"]` is a dict and `mergeability_hint(mergeable, status)` is `"conflicting"`; it is false for a missing key, wrong types, `unknown`, `behind`, `blocked`, `clean`, and when `wait_sha` is given and `payload["head_sha"]` is a different non-empty string (a payload for another head is not evidence). It never raises. It is re-exported in `src/superclaude/pr_submit/__init__.py` (import list and `__all__`). `conflicts.py` is in the core-pure file set: its source may not contain the standalone words `gh` or `git` anywhere, docstrings and comments included.
- R-003 `src/superclaude/pr_submit/ci.py` and `classify_checks` are not edited. A payload that carries `merge_state` classifies exactly like the same payload without it, for pending, all-pass, fail, empty with `expect_checks` true and false, and a stale head; `state: polling` with no checks stays `polling` even when `merge_state` is conflicting.
- R-004 `SKILL.md` Wave 8: on every poll payload, before acting on its classification, the SKILL evaluates `superclaude.pr_submit.conflicts.late_conflict_trigger(payload, wait_sha=<the wait SHA>)`. When it is true and the late pass has not been confirmed yet, the SKILL runs Wave 8a once more with the same entering outcome (`conflict_action(hook="wave8a", entering=<review outcome>)`). No new hook label, event, router row or run-log field is added.
- R-005 The late pass is limited only by `conflict_action`. Documented outcome table (all verified in `src/superclaude/pr_submit/conflicts.py:960-1002` and `tests/pr_submit/test_conflicts_core.py`): L3 Tier 1 with no conflict cycle started earlier gives `resolve_push` (push kind `sync`), also after `halt_max_rounds` and `no_response`; L3 Tier 1 with a cycle already started gives `sync_cap`; Tier 1 with `--conflict-max-tier 0` gives `tier_above_cap`; L1 proposes and L2 leaves a validated uncommitted merge; Tier 0 with GitHub reading conflicting gives `github_disagrees`; Tier 2 with `--conflict-max-tier 2` gives `late_conflict`, with a lower cap `tier_above_cap`. For every halting reason the status is `terminal_halted` when the entering outcome was `clean` or `report_only`; after `halt_max_rounds` or `no_response` the action is `report` and the retained terminal status stays. After a pushed sync the CI wait continues on the new head with `expect_checks`; every other result ends the CI wait with the status `conflict_action` returns. The late pass spends no round and sends no re-trigger, reply or resolve.
- R-006 Once-per-run rule: the SKILL keeps a run-local "late pass confirmed" flag. It is set only when the late Wave 8a reads `conflicting` or a persistent `unknown`, and it is not persisted (a `--resume` may run one more late pass; pushes stay bounded by `SYNC_CAP`). A payload reading that Wave 8a does not confirm (hint `clean`, `behind`, `blocked`) leaves the flag unset, ends that late check with no action and lets the CI wait go on; the trigger may fire again on a later poll. A fired trigger counts as "a hook this run read `conflicting`" for the end-of-wait `mergeable` re-read, so that backstop still runs.
- R-007 Wording of the cap everywhere it is described (SKILL text, refs, user docs, changelog): the late pass is allowed only when no conflict cycle (Tier 1 sync or Tier 2 merge) started earlier in the run, because the cap counts the distinct cycle ids in `conflict_cycles` (`run_log.py:186-188`, `refs/state-machine.md:164-165`), landed or not.
- R-008 Wording of the preconditions everywhere the late sync is promised: it needs L3 (monitor 3) and `--conflict-max-tier` of at least 1. With the default cap of 0 a late conflict halts `tier_above_cap`; L1 proposes; L2 leaves an uncommitted merge. A late Tier 2 conflict, or a conflict after a cycle started, halts.
