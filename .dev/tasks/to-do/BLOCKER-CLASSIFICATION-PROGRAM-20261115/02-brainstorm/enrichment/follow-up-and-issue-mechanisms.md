- Inputs of `--create` (issue.md:9, :31, :36-42): `"<description>"` as free text, or `@path` to a file holding the description (a single description, not a list); `--depth quick|standard|deep` (default quick); `--mode feature|bug`; `--type cicd|command|skill|agent|hook|cli|core|docs|tests|install|other`. No `--repo`, no dry-run, no preview (issue.md:46). `--pipeline`/`--submit` are claim-only (STOP `E-CLAIM-ONLY-FLAG`).
- Batch/ledger input: not supported. `@path` is read as one description (refs/create.md:16) and produces ONE issue. Nothing parses rows, N findings or a ledger.
- Type / mode picking: `--mode` picks feature vs bug template, the Feature or Bug issue type and the `enhancement` / `bug` label; when omitted a worker chooses (issue.md:41-42; refs/create.md:26-33). Issue type rule: bug = Bug, feature in area `tests` = Test, any other feature = Feature; Task is never chosen (refs/labels.md:18-26). Label is applied only if it already exists; the command never creates labels, types or fields (labels.md:7).
- Complexity field and mode label: Complexity follows depth: quick = Simple, standard = Medium, deep = Complex (refs/create.md:36; labels.md:30-36); written with `gh api -X POST repos/<R>/issues/<N>/issue-field-values` (create.md:72). The "mode label" is the `enhancement`/`bug` label. Complexity is not independent of depth: a cheap issue about a complex thing cannot be expressed except by changing `--depth`, which also changes the worker tier and body template.
- Templates: four body templates (feature/bug x simple/complex) in the skill's templates/ (SKILL.md:45-48). Feature-simple headings: Feature Summary, Problem Statement, User Story, Proposed Solution, Acceptance Criteria, Out of Scope, Components Affected (from `/sc:analyze`), Related Issues/PRs (templates/issue-feature-simple.md). issue.md:21 says these four REPLACE ISSUE-HANDOFF.md / ISSUE-BACKLOG.md for issues filed through `/sc:issue --create`.
- Unattended: no. `/sc:issue` is on the never-as-worker list (src/superclaude/core/WORKER-CONTRACT.md:23) and its command file has no `## Unattended mode` section (grep of ~/.claude/commands/sc for that heading does not list issue.md). It has a person-blocking step: `AskUserQuestion` "keep all / drop the new material / edit" whenever `draft-notes.md` lists new material or a contradiction (refs/create.md:59-61); with nothing listed it posts with no prompt. It posts directly with no approval (SKILL.md:76; issue.md:19). It spawns tier-pinned worker agents (T3 lookup, T2/T1 flags and body) and needs `gh auth` (STOP `E-GH-AUTH`).
- Rule 10 (CLAUDE.md:43): "before filing a GitHub issue, copy the matching template (`~/.claude/ISSUE-HANDOFF.md` for work handed to another person or agent, `~/.claude/ISSUE-BACKLOG.md` for parked work) to a temporary file, fill every section in the copy, then run `gh issue create --title "<title>" --body-file <the copy>`; never edit the installed template". - Convention: `/sc:issue` writes under `.dev/issues/draft-<YYYYMMDD-HHMMSS>-<slug>/` and renames to `.dev/issues/<N>/`; it never stages or commits `.dev/issues/` (SKILL.md:77, :192).

### How a batch issue of N follow-ups is filed today
Two manual routes, neither automatic:
1. `/sc:issue --create @<file> --mode <bug|feature> --type <area> --depth standard`, where the user (or the session) first hand-writes one description file that lists the N follow-ups. Result: one issue, one Complexity (from depth), one type/label for all N, body drafted by a worker from that prose; possible user prompt about new material.
2. Rule 10 by hand: copy ISSUE-BACKLOG.md to a temp file, fill the four sections, `gh issue create --repo IronbellyOrg/IronClaude --title ... --body-file <copy>`. No type, no Complexity field, no mode label set.

Missing for a ledger-driven batch: (a) a ledger input (`--create` takes only a description); (b) a batch mode or per-row fan-out (N issues vs one umbrella issue with a checklist); (c) an independent Complexity/priority per row; (d) a way to mark each ledger row as filed (issue number written back) so a re-run does not duplicate; (e) an unattended path (the command is never-as-worker and has an interactive question) so filing must be done by the top-level session or coordinator after the user says yes; (f) a template that fits "N findings with evidence" (the four templates are single-feature/bug shaped; BACKLOG fits a parked list better than the feature template); (g) a rule on whether `.dev/issues/` drafts for a batch are kept or discarded.

## 4. Unattended behaviour (src/superclaude/core/WORKER-CONTRACT.md, same text installed at ~/.claude/WORKER-CONTRACT.md)

- WC-2 (line 31): under `--unattended` a command never calls `AskUserQuestion`, never ends its turn on a chat question or `[yes / no]` offer, never says STOP AND WAIT. Each gate resolves as (a) a documented default, (b) a caller-supplied flag value, or (c) blocked: contract written with `worker_status: blocked` and the exact question in `blocked_question`, then stop. The brief's policy line decides what the worker does next (WC-3, line 53-57): `report blocked` (default) or `ask the coordinator` (at most once per Task).
- A "once per loop, ask the user whether to open an issue" step is exactly an offer WC-2 forbids; under `--unattended` it must resolve as (a) a default. The existing pragmatic.md:230 default is "only records the list", which fits option (a). It is not blocked and not asked.
- Contract fields (WC-4, line 33): `worker_contract_version` ("1"), `worker_status` (succeeded|partial|failed|blocked), `command`, `report_path` (main human-readable deliverable), `artifacts` (every other file written), `blocked_question` when blocked, `reason` when failed. There is no follow-up field today and no field for "findings recorded but not filed".
- What "record only" looks like in a contract: the command writes its follow-up ledger inside `<report-dir>` (WC-11: per-Task report directory, never shared), lists the ledger path in `artifacts` (git-ignored paths and paths outside the repo are excluded, WC-4 line 34), keeps `worker_status: succeeded` (or `partial`) because follow-ups never fail a review, and the report names the ledger. A minimal addition would be one optional top-level key (for example `follow_up_ledger: <path>` plus a count) added beside the existing keys; WC-4 line 35 already lets a command add fields beside its own contract keys and says consumers must tolerate unknown fields (SKILL.md of reflect §9.4 says unknown top-level fields are read-and-ignore, sc-reflect-protocol SKILL.md:1038). No such field exists now, so this is a proposal.
- How the path reaches the coordinator: the worker passes only the contract path as `worker_done --report-path` (WC-4 line 39, WC-5 line 59); the coordinator opens the contract and reads `report_path` and `artifacts`. A ledger path therefore reaches it through `artifacts` (or a new field); the worker never sends it separately. The coordinator, not the worker, performs the issue filing, because workers get no outward action (WC-9 line 41; "Outward actions: none" in the brief template line 305) and `/sc:issue` is never-as-worker (line 23). Coordinator then asks the person (coordinator rules, "Git and GitHub ownership", line 240: acts only when the user's instruction names the action, every action targets IronbellyOrg/IronClaude).
- Reading rule for results: `partial` requires the coordinator to read `report_path` first (line 253); a ledger listed in `artifacts` is not read automatically. Without a rule, nothing makes the coordinator look at it.
- spec-panel's Unattended section already shows a per-command contract shape that lists extra files in `artifacts` (src/superclaude/commands/spec-panel.md:461).
