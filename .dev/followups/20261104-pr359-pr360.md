## PR #359: bare-python hook (issue #357)

Two Codex findings from the last review round were confirmed against bash and left unfixed at
merge. The hook parses bash itself, so each review round finds new rare syntax; these do not
affect the `python3 -c` habit the hook targets.

1. **Unquoted heredoc fed to a shell** (Codex 4470604501). `bash <<EOF` with a body like
   `echo '$(python3 -c 1)'` gets through, because the outer shell expands `$( )` inside the
   unquoted heredoc first.
   Evidence: no copied folder diagnoses this finding; it was confirmed against bash in the PR
   review thread. The same class of scanner grammar gap is diagnosed in the three round folders
   above; see [round 3](../troubleshoot/bug-pr359-round3-hook-findings-20261104164446/REPORT.md),
   whose source survey notes the hook header's accepted heredoc false positive.
2. **`coproc` with a name** (Codex 4470604520). `coproc worker { python3 -c 1; }` gets through,
   because the coprocess name hides the body from the hook.
   Evidence: no copied folder diagnoses this finding; confirmed against bash in the PR review
   thread. Same grammar-gap class as the
   [round 1](../troubleshoot/bug-pr359-bare-python-hook-findings-20261104150317/REPORT.md),
   [round 2](../troubleshoot/bug-pr359-round2-hook-findings-20261104153447/REPORT.md) and
   [round 3](../troubleshoot/bug-pr359-round3-hook-findings-20261104164446/REPORT.md) folders.
3. **Augment thread 4469559023: a newline after `]]`.** Still open on the PR, but not a real gap:
   the hook already blocks that case. Action: none beyond resolving the thread.
   Evidence: no copied folder; the `[[ ]]` handling it refers to is diagnosed in
   [round 1](../troubleshoot/bug-pr359-bare-python-hook-findings-20261104150317/REPORT.md) and
   [round 2](../troubleshoot/bug-pr359-round2-hook-findings-20261104153447/REPORT.md).

Already listed in the PR #359 body as known limits (not new follow-ups): `bash -c`, `eval` and
`env -S` strings; `xargs` and `find -exec`; a heredoc piped into a shell; `${...}` expansions;
nested backticks; versioned names such as `python3.12`.

## PR #360: Ponytail pin (issue #330)

Three Medium findings from the round-2 re-review were open at merge. All are in
`src/superclaude/cli/install_user_setup.py`.

**Status: all three are being fixed by the in-flight branch `ironbelly/pr360-followups`** (an Orca
worktree at `pr360-followups`; it had no commits yet when this note was written).

4. **Symlink loop aborts the install** (Augment, line 292). `Path.resolve()` in
   `_is_our_catalog` can raise on a symlink loop and abort `superclaude install`.
   Fix: catch `OSError`/`RuntimeError` and treat the catalogue as not ours, plus a test.
   Evidence: [security-verify-the-ironclaude-marketplace-source-20261104161841](../troubleshoot/security-verify-the-ironclaude-marketplace-source-20261104161841/REPORT.md)
   designed `_is_our_catalog`; its
   [quality-engineer hypothesis](../troubleshoot/security-verify-the-ironclaude-marketplace-source-20261104161841/tier2-quality-engineer-hypothesis.md)
   expected a dangling or looping symlink to be refused (fail closed); the Augment finding says
   the merged code raises instead.
5. **Stale-pin check accepts any scope** (Codex P2, line 329). The check accepts an installed
   record of any scope, so a project-scope copy at the pin can hide a stale user-scope copy.
   Fix: compare only `scope == "user"` records, plus a test.
   Evidence: no copied folder diagnoses this finding; the source is the PR #360 review. The
   [security folder's observation](../troubleshoot/security-verify-the-ironclaude-marketplace-source-20261104161841/tier1-observation.md)
   shows the installer installs with `--scope user`.
6. **Registry read from the wrong profile** (Codex security P2, line 345). `install_plugins` reads
   `$HOME/.claude/plugins/known_marketplaces.json`, but the `claude` subprocesses inherit
   `CLAUDE_CONFIG_DIR`, so the check and the commands can use different profiles.
   Fix: read the registry from `CLAUDE_CONFIG_DIR` when it is set, or refuse pinned plugins on a
   mismatch. Check with the real CLI where plugins live under `CLAUDE_CONFIG_DIR`.
   Evidence: [security-verify-the-ironclaude-marketplace-source-20261104161841/REPORT.md](../troubleshoot/security-verify-the-ironclaude-marketplace-source-20261104161841/REPORT.md)
   (Follow-up tasks) and the
   [security-engineer hypothesis](../troubleshoot/security-verify-the-ironclaude-marketplace-source-20261104161841/tier2-security-engineer-hypothesis.md)
   (evidence row E3), which flagged the hard-coded registry path before merge.
