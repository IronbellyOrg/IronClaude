## Area 1: Skill locations, precedence and live discovery

Source: https://code.claude.com/docs/en/skills (first 100000 of 118986 characters read). Reliability: official docs.

### 1.1 Where skills are discovered  (relevance: HIGH; relation: extends)

- Table "Choose where skills load": personal `~/.claude/skills/<skill-name>/SKILL.md` ("All your projects on this machine, but not Cowork or cloud sessions"); project `.claude/skills/<skill-name>/SKILL.md` ("Sessions in this repository, but not cloud threads in a project"); enterprise (a `.claude/skills/` in the managed settings directory); plugin (`<plugin>/skills/<skill-name>/SKILL.md`, namespaced `/plugin-name:skill-name`).
- Relation to codebase: extends G-02 (user-level skills load in every project on the machine). Per gaps-and-questions.md the user-level `~/.claude/skills` is where option B would place a stub, so a user-level stub is visible in every project the user opens, including projects that have no BMAD.

### 1.2 Name collisions  (relevance: HIGH; relation: extends)

- Section "Resolve skills that share a name": "Enterprise over personal, and personal over project." and "With `deploy` in both `~/.claude/skills/` and the project's `.claude/skills/`, `/deploy` runs the personal one".
- Consequence for BMAD: a user-level skill named like a BMAD skill (for example `bmad-help`) would WIN over the project copy that `bmad install` writes into `.claude/skills/`. A user-level stub must therefore use a name that does not equal any of the 46/47 `bmad-*` skill names, or it will shadow the real skill after install. (Inference from the quoted precedence rule; not tested.)
- A skill versus a same-named `.claude/commands/` file: the skill wins (table entry "The skill").

### 1.3 Live pickup of skills created after the session started  (relevance: HIGH; relation: extends; answers (a))

- Section "Edit a skill during a session": "Claude Code watches skill directories for file changes, except in bare mode."
- Same section: "When you add, edit, or remove a skill under `~/.claude/skills/`, the project `.claude/skills/`, or a `.claude/skills/` inside an `--add-dir` directory, Claude Code picks up the change within the current session, without a restart."
- Exception that matters for a project that never had BMAD: "If you create a top-level skills directory that didn't exist when the session started, run `/reload-skills` to pick up the skills you put there." and "Claude Code isn't watching that directory yet, so run `/reload-skills` again after each later change there."
- Limit: "Live change detection covers `SKILL.md` text only."
- Answer to (a): a project `.claude/skills/` that did NOT exist at session start is NOT watched; the skills in it appear only after `/reload-skills` (a user-typed command) or a restart. A `.claude/skills/` that already existed at session start is watched and picks up new skills live. In a project that never had BMAD, `.claude/skills/` usually does not exist, so first-use creation in an open session needs `/reload-skills` (see Area 2 for a hook-side `reloadSkills` output that may do this automatically).
- Relation to codebase: extends G-01 / Q-1 (gaps-and-questions.md: "The settings page does not say; skills docs not fetched"). It now answers the question from the skills page itself.

### 1.4 Skills in subdirectories  (relevance: MEDIUM; relation: extends)

- Section "Load skills in monorepos and subdirectories": "Claude Code loads project skills from `.claude/skills/` in the directory where you start it and in every parent directory up to the repository root".
- Same section: "Skills in a `.claude/skills/` directory below where you started don't load at startup." They load "the first time Claude reads or edits a file in that subdirectory"; "To load them sooner, run `/add-dir` with the subdirectory's path, which requires Claude Code v2.1.257 or later."
- Relation: relevant to D-3 in gaps-and-questions.md (which directory is "the project" when the user opens a subfolder): a BMAD install into the repository root is found from a subfolder start (parents up to the repository root are scanned); an install into the subfolder is not found from the root until a file there is read.

### 1.5 Bundled scripts and shell commands  (relevance: HIGH; relation: extends; answers (c), first half)

- Section "Add supporting files": "Skills can include multiple files in their directory." The example tree contains `scripts/helper.py (utility script - executed, not loaded)`.
- Section "Available string substitutions": `allowed-tools: Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)` and "Run `${CLAUDE_SKILL_DIR}/scripts/render.sh <csv-file>` to render the chart." So a skill can bundle a script and refer to its own directory with `${CLAUDE_SKILL_DIR}`.
- Section "Inject dynamic context": "The `` !`<command>` `` syntax runs shell commands before the skill content is sent to Claude." and "The command output replaces the placeholder, so Claude receives actual data, not the command itself." Limit stated there: "Claude Code doesn't run these commands on your machine when the skill is synced from your claude.ai account."
- Section "Pre-approve tools for a skill": "The `allowed-tools` field grants permission for the listed tools during the turn that invokes the skill, so Claude can use them without prompting you for approval." and "It does not restrict which tools are available: every tool remains callable, and your permission settings still govern tools that are not listed."
- Answer to (c), skill half: yes, a user-level skill can bundle a script and run it, either by Claude calling Bash (permission rules govern; `allowed-tools: Bash(<pattern>)` pre-approves the listed pattern for that skill's turn) or by `` !`command` `` which runs before Claude sees the content. The page text read does not say whether the `` !`command` `` form is itself subject to the permission rules or to `allowed-tools`: UNVERIFIED until the permissions page is read (Area 5).

### 1.6 Custom commands versus skills  (relevance: MEDIUM; relation: extends; answers (b), command half)

- Opening note of the skills page: "Custom commands have been merged into skills." and "A file at `.claude/commands/deploy.md` and a skill at `.claude/skills/deploy/SKILL.md` both create `/deploy` and work the same way." and "Your existing `.claude/commands/` files keep working."
- The page text read names `~/.claude/` personal command files only in passing ("If one of your personal skills or command files in `~/.claude/` uses the name ..."); an explicit `~/.claude/commands/` path table row was not in the text returned: UNVERIFIED on this page (checked against other pages in Area 5 if found).
- Relation: a user-level command is no cheaper than a user-level skill for option B: both are discovered the same way and both create a slash name.

### 1.7 Statement on skills modifying project files  (relevance: MEDIUM; relation: extends; answers (f), skill half)

- Section "Run and verify your app": "When it has to build and drive your app without a recorded recipe, it writes what worked to `.claude/skills/verify/SKILL.md` at the repo root, or in the touched package directory in a monorepo, so later runs and other agents follow the same steps." This is an official example of a skill's workflow writing a new project skill directory.
- Section "Run skills in a subagent": "The skill's edits to other files stay, so use git to revert them." and "A forked skill that runs in the background applies its edits outside your session's checkpoints."
- Answer to (f), skill half: the docs do not forbid a skill from modifying the project directory and describe skills that do (edits stay; revert with git). No statement was found that a skill needs a special permission beyond ordinary tool permissions; the file edits and Bash calls a skill triggers go through the permission system (permission specifics: Area 5).

## Area 2: Hook inputs, outputs and what a SessionStart / UserPromptSubmit / PreToolUse hook can do

Source: https://code.claude.com/docs/en/hooks (289837 characters; characters 0 to 200000 read through targeted fetches, plus the "Security considerations" slice around characters 200000 onward saved by the tool; the rest not read). Reliability: official docs.

### 2.1 Events and common input  (relevance: HIGH; relation: extends; answers (d), input half)

- Event table: SessionStart "When a session begins or resumes"; UserPromptSubmit "When a prompt is submitted, before Claude processes it."; PreToolUse "Before a tool call executes."
- Section "Common input fields": "For command hooks, this JSON arrives via stdin." Fields include `session_id` ("Current session identifier"), `transcript_path`, `cwd` ("Current working directory when the hook is invoked"), `hook_event_name`, `permission_mode`, `prompt_id`, `scratchpad_dir`, `effort`.
- Section "SessionStart": "In addition to the common input fields, SessionStart hooks receive `source` and optionally `model`, `agent_type`, and `session_title`". `source` is `"startup"` for new sessions, `"resume"`, `"clear"` after `/clear`, `"compact"` after compaction, or `"fork"`.
- Section "UserPromptSubmit": "In addition to the common input fields, UserPromptSubmit hooks receive the `prompt` field containing the submitted text." (example JSON has `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `prompt`).
- Section "PreToolUse" (common input example): `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `tool_name`, `tool_input` (for Bash: `command`, `description`, `timeout`, `run_in_background`), `tool_use_id`.
- Project directory: section "Reference scripts by path": `${CLAUDE_PROJECT_DIR}` is "the project root where the session started." and "Both forms support the same path placeholders, and both export them as the environment variables `CLAUDE_PROJECT_DIR`, `CLAUDE_PLUGIN_ROOT`, and `CLAUDE_PLUGIN_DATA` on the spawned process". Also "Handlers run in the current directory with Claude Code's environment."
- Answer to (d), input half: a hook receives `cwd` in its stdin JSON and gets `CLAUDE_PROJECT_DIR` in its environment; `prompt` is received only by UserPromptSubmit. `cwd` and `CLAUDE_PROJECT_DIR` can differ (the project root is where the session started; `cwd` is the working directory when the hook is invoked): UNVERIFIED how they differ in a Coder workspace; the stub or hook should read `CLAUDE_PROJECT_DIR` for "the project" and treat `cwd` as a hint. Relation: extends G-08 (hook cwd) and D-3 (which directory is the project).

### 2.2 Output: adding context, blocking  (relevance: HIGH; relation: extends; answers (d), output half)

- Section "Exit code 0": for `UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, and `PostModelSwitch`, "Claude Code adds plain-text stdout as context that Claude can see and act on." and "Claude never sees stderr from a hook that exits 0."
- Section "SessionStart": "A hook that only adds context can print it without building JSON, because Claude Code adds a SessionStart hook's plain-text stdout to Claude's context."
- Section "UserPromptSubmit": "Plain stdout and the `additionalContext` value are each injected as a system reminder that starts with the hook's name; Claude reads both." and "`UserPromptSubmit`: can't replace the prompt; it only injects `additionalContext` alongside it".
- JSON form: "Return `additionalContext` inside `hookSpecificOutput` alongside the event name" (UserPromptSubmit example: `hookSpecificOutput.hookEventName`, `additionalContext`, `sessionTitle`, `suppressOriginalPrompt`).
- Blocking, UserPromptSubmit: "To block a prompt, return a JSON object with `decision` set to `"block"`" and exit 2: "a `UserPromptSubmit` hook rejects the prompt." / "The message that comes with the block is your hook's stderr."
- Blocking, SessionStart: no decision control. Quote: SessionStart exit-2 row "Shows stderr to user only" and, in Decision control, "No blocking or decision control". So a SessionStart hook can add context but cannot block.
- Blocking, PreToolUse: "`"deny"` prevents the tool call.", "`"allow"` skips the permission prompt, except for actions no mode auto-approves and reads from network paths.", "`"ask"` prompts the user to confirm."; "Deny and ask rules are still evaluated regardless of what the hook returns" (also stated on the permissions page, "Precedence among rules, hooks, and mods": "a matching deny rule blocks the call, and a matching ask rule still prompts even when the hook returned `"allow"` or `"ask"`"). `updatedInput` under `hookSpecificOutput` "replaces a tool's arguments before it runs." Precedence among multiple hooks: "deny > defer > ask > allow".
- Answer to (d), output half: SessionStart and UserPromptSubmit can add context (plain stdout or `additionalContext`); only UserPromptSubmit and PreToolUse can block (SessionStart cannot). Non-JSON stdout is plain text, not a failure ("Plain-text stdout from a command hook isn't a failure.").
- Relation: extends options B/D. A SessionStart or UserPromptSubmit hook can tell Claude "this project has no BMAD; run <install>" without blocking anything, so the model, not the hook, would decide to run the install (or the hook runs the install itself, see 2.4 and Area 4).

### 2.3 Timeouts  (relevance: HIGH; relation: extends; answers (d) timeout part, G-04, G-08)

- Section "Common fields", `timeout`: "Seconds before canceling." "Defaults: 600 for `command`, `http`, and `mcp_tool`; 30 for `prompt`; 60 for `agent`." "Claude Code lowers the `command`, `http`, and `mcp_tool` default to 30 on `UserPromptSubmit`, `PreModelSwitch`, and `PostModelSwitch`, and to 10 on `MessageDisplay`."
- So a SessionStart command hook defaults to 600 s; a UserPromptSubmit command hook defaults to 30 s unless a larger `timeout` is set in its entry. Per gaps-and-questions.md the prior memlog figure for a first install is "about 4s" and CI cold `bmad` is 374 to 392 ms, which fits inside 30 s, but the real first-install duration in a workspace is still UNVERIFIED (G-09).
- Relation: extends G-04 / G-08 (hook timeout versus install time): the default does not by itself make a first install impossible in either event, but UserPromptSubmit's 30 s default is the tighter bound and would need an explicit `timeout` for a slow network run.

### 2.4 SessionStart can ask Claude Code to re-scan skills  (relevance: HIGH; relation: extends; strengthens answer to (a))

- Section "SessionStart decision control": "`reloadSkills`: When `true`, Claude Code re-scans the skill and command directories after the SessionStart hooks complete." and "Skill discovery normally runs before SessionStart hooks finish, so without it, files a hook writes into `~/.claude/skills/` or `.claude/skills/` can be missing when the first prompt runs."
- Same section: SessionStart also accepts `initialUserMessage`, `watchPaths` ("Array of absolute paths to watch for FileChanged events during this session"), and `sessionTitle`. The slice read gave no minimum Claude Code version for `reloadSkills`: UNVERIFIED; the installed version in the Coder image is also unverified.
- Official statement relevant to (f), hook half: the docs describe a hook writing into `.claude/skills/` and provide a field so Claude Code picks the files up, i.e. a hook that creates project skill files at session start is an anticipated pattern.
- Consequence: with a SessionStart hook that installs BMAD into the project and returns `{"hookSpecificOutput":{"hookEventName":"SessionStart","reloadSkills":true}}`, the new `.claude/skills/bmad-*` should be visible for the first prompt of that same session. Placement confirmed on a second fetch of the subsection "Reload skills that a hook installs": the official example prints `echo '{"hookSpecificOutput": {"hookEventName": "SessionStart", "reloadSkills": true}}'` (its quoted sentence: "To make skills that a SessionStart hook installs available in the same session, return `reloadSkills`."). The same subsection's example writes into `~/.claude/skills/`; the sentence above names `.claude/skills/` as well. No minimum version was in the text returned.
- Timing note, section "SessionStart decision control" background-running text: "When you start an interactive session ... SessionStart hooks run in the background. You can type right away ... Claude's first response still waits for the hooks to finish, so their context reaches Claude." So a slow SessionStart install does not freeze typing but delays the first response.
- This only helps option D with a SessionStart trigger. For a UserPromptSubmit trigger (or option B at the moment of the user prompt) `reloadSkills` is not available, so the manual `/reload-skills` from 1.3 applies. Relation: extends G-01, changes how D should be shaped (SessionStart + `reloadSkills`, not UserPromptSubmit).

## Area 3: Where hooks live, whether they run in every project, and how scopes merge

Sources: https://code.claude.com/docs/en/hooks (section "Hook locations", "Hook handler fields"), https://code.claude.com/docs/en/settings (sections "Settings files and who they affect", "Settings precedence", "Lists merge instead of overriding", "When edits take effect"), https://code.claude.com/docs/en/managed-settings (sections "Split a file-based policy across teams", "How Claude Code combines managed sources"). Reliability: official docs.

### 3.1 Hook scopes  (relevance: HIGH; relation: extends; answers (d) "every project?" and (e), first half)

- Hooks page, "Hook locations" table: `~/.claude/settings.json` = "All your projects"; `.claude/settings.json` = "Single project"; `.claude/settings.local.json` = "Single project"; "Managed policy settings" = "Organization-wide"; plugin `hooks/hooks.json` = "When plugin is enabled"; skill frontmatter = "The rest of the session once the skill is invoked"; subagent frontmatter = "While that subagent is running".
- Settings page, scope table: User `~/.claude/settings.json` = "You, in every project on this machine".
- Answer to (d), "do user-level hooks run in every project": yes, hooks in `~/.claude/settings.json` apply in all projects, with the trust caveat in 4.1. Consequence per gaps-and-questions.md G-02: a user-level hook fires in every project, including repositories where BMAD must not be installed; the hook itself must carry the "is this a project that wants BMAD, and does it lack `_bmad/`" test.
- Skill-frontmatter hooks: "Hooks that Claude Code registers when the skill is invoked and keeps running for the rest of the session." (skills page, `hooks` field). Hooks-page quote: project skill hooks are registered "when you or Claude invoke the skill, including in a `-p` run in a folder you haven't trusted." This gives a variant of B: a stub skill that registers a hook only once invoked (relevance: LOW, not evaluated further).

### 3.2 How user, project and local hooks combine  (relevance: HIGH; relation: extends; answers (e))

- Hooks page, "Hook locations": "Hook entries merge across settings levels rather than replacing each other: user, project, and local settings add their own hooks without removing managed ones, and the `disableAllHooks` setting can't disable managed hooks from outside managed settings."
- Hooks page, "Hook handler fields": "When an event fires, its matching hooks run in parallel." and "If you define the same handler in more than one settings file, it runs once."
- Settings page, "Lists merge instead of overriding": "When you set the same list key, such as `permissions.allow`, in more than one file, Claude Code combines the lists instead of picking one, so each file can add entries without removing another file's."
- Settings page, "Settings precedence": single-valued keys follow "managed settings, command line, project local, shared project, user" with the highest level winning.
- Answer to (e): hooks from user, project, local and managed scopes are all added together; none replaces another; identical handlers run once; matching hooks run in parallel (so a user-level hook and a project hook for the same event do not wait for each other). Relation: supports the codebase finding (per gaps-and-questions.md section 6, quoting 03) that a user-level hook entry is additive with the image-baked entries.

### 3.3 Managed-settings drop-in directory  (relevance: HIGH; relation: extends; answers G-03)

- Managed settings page, "Where each mechanism stores the policy": "File-based: `managed-settings.json`, an optional `managed-settings.d/` directory, and `managed-mcp.json` in the system directory: ... `/etc/claude-code/` on Linux and WSL".
- Same page, "Split a file-based policy across teams": "Claude Code merges `managed-settings.json` first, then every `*.json` file in the directory in alphabetical order." Merge rules: single values - "the later file's value replaces the earlier one"; lists - "the two lists combine, with duplicates removed"; nested blocks - "merge key by key". "Claude Code ignores hidden files and files that don't end in `.json`."
- Managed hooks: the hooks page lists "Managed policy settings" as a hook location; the managed page, under `managedSourcesBehavior: "merge"`, lists `hooks` among "Lists ... Combines the entries from every source" (table row: `permissions.allow`, `hooks`, `sandbox.network.allowedDomains`, ...). I did not find a sentence reading "a drop-in file may contain a `hooks` key" in the text returned; the evidence is the combination of (i) drop-ins are merged into one managed document with the same key rules as `managed-settings.json`, (ii) `hooks` is a settings key and a list-merged one, (iii) managed policy settings are a documented hook location. So: documented by inference, stated as "accepts and list-merges `hooks`" (HIGH likelihood), not by a single explicit sentence.
- Managed vs user hooks: managed hooks are additive to user hooks, not replacing them (3.2 quote). Exceptions that would REMOVE user hooks and user skills: the managed key `allowManagedHooksOnly` ("When `true`, restricts which hooks run") and `strictPluginOnlyCustomization` ("Block skills, agents, hooks, and MCP servers from user and project sources; `true` locks all four, an array names which"). If a managed file in `/etc/claude-code/` sets either key, options B and D (user-level skill or hook) stop working; the content of any `/etc/claude-code/` file in the Coder image is NOT established by this pass: UNVERIFIED (the codebase research files 02/03 cover the managed-settings.d use; the check belongs to them).
- Source ranking: "1. Remote settings ... 2. MDM or OS-level policies ... 3. Managed settings files, `managed-settings.d/*.json` and `managed-settings.json` merged together"; default `first-wins` uses "the highest-ranked source that delivers at least one policy key and ignores the rest". Remote settings are fetched only when the session "authenticates to Anthropic's API directly with an eligible credential, signs in to a gateway ..."; "when `ANTHROPIC_BASE_URL` points somewhere other than Anthropic's API, it starts at the next source". Whether a Coder workspace sets `ANTHROPIC_BASE_URL` to a gateway is UNVERIFIED here (the project instructions mention LiteLLM, which suggests it, but that is not read from a config file in this pass).
- Delivery timing: delivery table, file-based row: "Read at startup and reloaded when a file changes".
- Relation: extends G-03: option D2 (a drop-in under `/etc/claude-code/managed-settings.d/`) is a documented file location whose hooks list-merge with the user's; the managed layer cannot be disabled by the user's `disableAllHooks`, which also means a managed first-use hook would run for every user in every project and could not be turned off by them.

## Area 4: Workspace trust, mid-session reload, timing

### 4.1 Hooks are held back until the folder is trusted (interactive sessions)  (relevance: HIGH; relation: extends; affects (d), G-04, G-08)

Source: https://code.claude.com/docs/en/hooks , section "Security considerations / Workspace trust". Reliability: official docs.

- "Claude Code checks workspace trust before it runs any hook from a settings file."
- "Interactive session: Claude Code holds back hooks from every settings file, including your own `~/.claude/settings.json`, until you accept the workspace trust dialog for the folder, or for a parent directory whose trust extends to it".
- "`-p` or SDK session: Claude Code never shows the dialog and treats the folder as trusted, so hooks committed in a repository's `.claude/settings.json` run in a folder you've never trusted".
- Consequence for D: in an interactive session in a folder never opened with Claude Code (no trust yet), the user-level SessionStart hook does not run until the trust dialog is accepted. Whether the held-back SessionStart hook then runs late in that same session, or only from the next session, is NOT stated in the text read: UNVERIFIED. The same trust model applies to project-level hooks, so no hook-based option escapes it.
- Skills are not gated the same way: permissions page, "What runs before you trust a folder", row 1 says a project skill's hooks and `allowed-tools` are "Used" even when only a parent folder is trusted and in `-p` runs, and "Workspace trust never gates a skill's `allowed-tools` in any session". (The same row says hooks in settings files are "Used" for the "trusted only a parent folder" column; this agrees with "a parent directory whose trust extends to it".) Relation: a user-level skill (B) is not subject to the hook-trust hold-back, but runs only when invoked.

### 4.2 Hook configuration changes in a running session  (relevance: MEDIUM; relation: extends; answers G-04 first item)

- Hooks page, "Disable or remove hooks": "Direct edits to hooks in settings files are normally picked up automatically by the file watcher."
- Settings page, "When edits take effect": "Claude Code watches your settings files and reloads them when they change, so it applies most edits to the running session without a restart, including edits to `permissions`, `hooks`, and credential helpers such as `apiKeyHelper`." and "Claude Code also loads a settings file you create mid-session if its folder existed when the session started. For the project's `.claude/` folder, it loads the file even when you create the folder in the same session."
- Answer to G-04 (running session picks up a changed `hooks` block): yes, per the docs, for settings files in existing folders (and for a project `.claude/settings.json` even if `.claude/` is new). This contradicts nothing in the codebase files; it closes UV-42 from official text (not tested live).
- Distinct from skills: the skills watcher does NOT cover a `.claude/skills/` folder created mid-session (1.3), while the settings watcher does cover a `.claude/` folder created mid-session.

### 4.3 What SessionStart output the user sees  (relevance: LOW; relation: extends; G-04)

## Area 5: Permissions for running a shell command from a skill or hook

Source: https://code.claude.com/docs/en/permissions and the skills page (section "Inject dynamic context"). Reliability: official docs.

### 5.1 Default Bash behaviour  (relevance: HIGH; relation: extends; answers (c), permission half; G-04)

- Permissions page, "Permission system" table: Bash commands - Approval required "Yes, except a built-in set of read-only commands"; "Yes, and don't ask again" = "Permanently per repository and command". File modification - "Yes", "Until session end".
- So an install command Claude runs through the Bash tool prompts the user by default (Manual mode); allow rules in settings or `allowed-tools` remove the prompt for exactly the matched pattern.
- The effect of `skipDangerousModePermissionPrompt: true` (G-04): not on the permissions text read: UNVERIFIED (it relates to bypass mode; the codebase file 03 holds the Coder setting).

### 5.2 Skill `allowed-tools` and `!`command` injection  (relevance: HIGH; relation: extends; answers (c))

- Skills page, "Inject dynamic context": "Injected commands never prompt for permission while the skill renders. Claude Code checks each one against your permission rules first. A command a deny rule matches aborts the invocation with `Shell command permission check failed for pattern "..."`." and "Outside auto mode, when a command's permission check returns anything other than allow, Claude Code aborts the invocation with the same error. This includes a rule that would normally ask you. To keep an unmatched command from aborting here, pre-approve it with `allowed-tools`."
- Same section: "Deny and ask rules still override `allowed-tools`." and "The grant clears when you send your next message."
- Disable switch: "To disable this behavior for skills and custom commands from user, project, plugin, or additional-directory sources, set `"disableSkillShellExecution": true` in settings. Each command is replaced with `[shell command execution disabled by policy]` instead of being run. Bundled and managed skills are not affected."
- Answer to (c): a user-level skill (or command) can run a shell command in two ways. (1) `` !`bmad install ...` `` at render time: needs the command to be allowed by a permission rule or by the skill's `allowed-tools: Bash(<pattern>)`, otherwise the invocation aborts (outside auto mode); deny/ask rules still win; `disableSkillShellExecution` would turn it off. (2) Claude calls Bash after reading the skill: a normal permission prompt unless an allow rule or `allowed-tools` pre-approves the pattern (grant for that turn only). Settings needed for a prompt-free first-use install: `allowed-tools: Bash(bmad install *)` in the stub's frontmatter (or an equivalent `permissions.allow` entry in user settings), and `disableSkillShellExecution` not set. The exact `Bash(...)` pattern syntax was not re-read; the page example uses `Bash(${CLAUDE_SKILL_DIR}/scripts/render.sh *)`.
- Relation: extends G-08 / option B: a stub whose instructions say "run `bmad install ...`" will prompt the user unless pre-approved; that prompt is itself a user-visible consent step, which may be wanted given the owner question in gaps-and-questions.md section 5.
- Hook vs tool permissions: PreToolUse hooks run for tool calls and "can deny the tool call, force a prompt, or skip the prompt", but "Deny and ask rules are still evaluated regardless of what the hook returns". The pages read do not state that a SessionStart command hook is subject to Bash permission rules; hooks are described as running "with your full user permissions" ("Disclaimer"), executed by Claude Code itself and not through the Bash tool. I treat "a SessionStart/UserPromptSubmit command hook runs without a Bash permission prompt" as the best reading, marked UNVERIFIED in the sense that no sentence says it in those words.

### 5.3 Statement on skills/hooks modifying the project directory  (relevance: MEDIUM; relation: extends; answers (f) consolidated)

- Hooks: "Command hooks execute shell commands with your full user permissions. They can modify, delete, or access any files your user account can access." (Security considerations / Disclaimer). Skills: "The skill's edits to other files stay, so use git to revert them." (skills page, "Run skills in a subagent").
- Plugin and skill content the user did not write is treated with caution by the docs (trust dialog, `strictPluginOnlyCustomization`), but no sentence prohibits a user-level skill or hook from creating `_bmad/` or `.claude/skills/` in the current project. Nothing was found on "first-use initialisation" as an endorsed pattern except the `reloadSkills` text (2.4).

## Key External Findings

Answers to (a) to (f) (each with its source; quotes are in the numbered subsections):

- (a) ANSWERED, split answer. A project `.claude/skills/` that already existed when the session started is watched and new skills are picked up in the same session without a restart; a top-level skills directory that did NOT exist at session start is not watched and needs `/reload-skills` (or a restart). Source: https://code.claude.com/docs/en/skills , "Edit a skill during a session": "If you create a top-level skills directory that didn't exist when the session started, run `/reload-skills` to pick up the skills you put there." A SessionStart hook can avoid the manual step by returning `reloadSkills: true` (https://code.claude.com/docs/en/hooks , "Reload skills that a hook installs": "To make skills that a SessionStart hook installs available in the same session, return `reloadSkills`."). Relevance HIGH. Relation: extends G-01. Residual UNVERIFIED: whether a first install from a user-prompt-time mechanism (B, or D on UserPromptSubmit) can trigger the re-scan without the user typing `/reload-skills`; no hook output field for re-scan was found for UserPromptSubmit.
- (b) ANSWERED. User skills: `~/.claude/skills/<skill-name>/SKILL.md` ("All your projects on this machine"); project skills: `.claude/skills/<skill-name>/SKILL.md`; user and project commands: `commands/*.md` under `~/.claude/` and `.claude/` ("Single-file prompts; same mechanism as skills", https://code.claude.com/docs/en/claude-directory , File reference table, scope "Project and global"). Collisions: "Enterprise over personal, and personal over project." (https://code.claude.com/docs/en/skills , "Resolve skills that share a name"); a skill beats a same-named command file. A user-level stub must not reuse a `bmad-*` name or it will shadow the project's real BMAD skill. Relevance HIGH. Relation: extends G-02 / UV-07.
- (c) ANSWERED with one residual. A skill can bundle and run a script (`${CLAUDE_SKILL_DIR}`, `allowed-tools: Bash(...)`) or inject a command with `` !`cmd` ``. Injected commands "never prompt for permission while the skill renders" and abort outside auto mode unless an allow rule or `allowed-tools` matches (https://code.claude.com/docs/en/skills , "Inject dynamic context"); `disableSkillShellExecution` can switch the feature off. A Bash call made by Claude prompts by default except read-only commands (https://code.claude.com/docs/en/permissions , "Permission system"). Relevance HIGH. Relation: extends G-04 / G-08. Residual UNVERIFIED: the exact `Bash(...)` pattern grammar for `bmad install` and whether the Coder image sets `disableSkillShellExecution` or bypass mode.
- (d) ANSWERED. SessionStart receives `session_id`, `transcript_path`, `cwd`, `permission_mode`, `hook_event_name`, `source` (and optionally `model`); UserPromptSubmit additionally receives `prompt`; `CLAUDE_PROJECT_DIR` is exported to the hook process. Both can add context (plain stdout or `hookSpecificOutput.additionalContext`); only UserPromptSubmit (and PreToolUse) can block; SessionStart has "No blocking or decision control". Timeouts: 600 s default for command hooks, lowered to 30 s on UserPromptSubmit. User-level hooks in `~/.claude/settings.json` apply to "All your projects", but in interactive sessions "Claude Code holds back hooks from every settings file, including your own `~/.claude/settings.json`, until you accept the workspace trust dialog" (https://code.claude.com/docs/en/hooks , "Security considerations / Workspace trust"). Relevance HIGH. Relation: extends G-04 / G-08; the trust hold-back is new and affects D. Residual UNVERIFIED: whether the held-back SessionStart hook runs later in the same session after trust is accepted; whether `cwd` differs from `CLAUDE_PROJECT_DIR` in a Coder workspace.
- (e) ANSWERED. "Hook entries merge across settings levels rather than replacing each other" (user, project, local, managed); the same handler defined twice runs once; matching hooks run in parallel (https://code.claude.com/docs/en/hooks , "Hook locations" and "Hook handler fields"). `/etc/claude-code/managed-settings.d/*.json` is a documented location merged "in alphabetical order" after `managed-settings.json`, lists combined with duplicates removed (https://code.claude.com/docs/en/managed-settings , "Split a file-based policy across teams"); `hooks` is list-merged and is a documented managed hook location (by inference from the combination, 3.3). Relevance HIGH. Relation: extends G-03 / UV-25 (D2 is feasible per the docs). Residual UNVERIFIED: no single sentence says a drop-in file may hold `hooks`; managed keys `allowManagedHooksOnly` and `strictPluginOnlyCustomization` would disable user hooks/skills if the image sets them (unchecked here).
- (f) ANSWERED (negative). No official statement forbids a hook or skill from modifying the project directory. Positive statements: "Command hooks execute shell commands with your full user permissions. They can modify, delete, or access any files your user account can access." (hooks page, Disclaimer); "The skill's edits to other files stay, so use git to revert them." (skills page); the `reloadSkills` text describes hooks "writing into `~/.claude/skills/` or `.claude/skills/`". No official statement endorses or restricts a first-use project bootstrap as such. Relevance MEDIUM. Relation: extends (nothing contradicts the codebase finding that the BMAD install writes only inside the project).

Other important discoveries:

- Hooks and settings are live: edits to `hooks` in settings files are picked up in a running session, and even a `.claude/settings.json` created in a new `.claude/` folder mid-session loads (https://code.claude.com/docs/en/settings , "When edits take effect"). Skills are different (see (a)). Closes UV-42 from official text.
- Skill descriptions are always in context: "Every skill in the skill listing adds to your context on every turn" (skills page); a user-level stub adds one listing entry to every project. Relevance LOW.
- Skills in a `.claude/skills/` below the start directory load only when a file there is read or edited, or after `/add-dir` (v2.1.257 or later); parents up to the repository root are scanned at start. Relevant to D-3.
- Docs version caveat: the docs mention version gates up to v2.1.314 and the changelog's newest visible entry is 2.1.319 (the docs' exact version is not stated); `claude --version` in this workspace prints 2.1.319; the image's version and `reloadSkills` introduction version (reported as 2.1.152 by a user-authored issue quoting the changelog) are UNVERIFIED from first-party text.

Not answered by official sources in this pass (UNVERIFIED): the held-back-hook timing after trust acceptance; whether SessionStart stdout is displayed to the user; the meaning of `skipDangerousModePermissionPrompt` (not read); whether the Orca `PermissionRequest` hook decides permissions (not a Claude Code docs question); the Bash permission pattern grammar for the install command; first-party text for the `reloadSkills` version.

## Recommendations from External Research

1. If option D is kept, shape it as a SessionStart hook (source `startup`) that, only when the project lacks `_bmad/config.toml` and is a project the owner covers, runs the image-baked `bmad install --directory "$CLAUDE_PROJECT_DIR" ...` and then prints `{"hookSpecificOutput":{"hookEventName":"SessionStart","reloadSkills":true}}`. This is the only documented mechanism that makes freshly written project skills visible for the first prompt of the same session without the user typing `/reload-skills`. Do not use UserPromptSubmit for the install: 30 s default timeout and no re-scan field found.
2. Plan for the workspace-trust hold-back: in an interactive session a user-level hook does not run in a never-trusted folder until the trust dialog is accepted. Put "first use in a brand-new, never-opened folder" in the open-risk list of the report, and decide with the owner whether a stub skill (B), which is not gated by hook trust, is the better fit for that case. The test for the plan should observe a hook in a fresh workspace (CI, not a one-off script).
3. If option B is kept, name the stub so it cannot equal any `bmad-*` project skill (personal beats project, so a same-named stub would shadow the real skill), set `allowed-tools: Bash(...)` for the exact install command only if the owner accepts a prompt-free install, and keep the stub free of BMAD content. After the stub runs the install in an open session, tell the user to run `/reload-skills` (the project `.claude/skills/` directory is new, so it is not watched).
4. A user-level artifact (B or D) is visible or active in every project on the machine ("All your projects"), so the stub or hook must test for the project type and for `_bmad/` and do nothing otherwise. This supports the owner question in gaps-and-questions.md section 5 (item 1) and should be quoted there as a fact about blast radius, not as an interpretation.
5. For D2 (managed-settings drop-in), the docs make a drop-in with `hooks` a documented, list-merged location, but a managed hook cannot be turned off by the user and applies to every project; check the image's `/etc/claude-code/` for `allowManagedHooksOnly` and `strictPluginOnlyCustomization` before choosing B or D, since either would disable user-level skills/hooks (codebase check, not external).
6. Closing items for the implementation phase (CI observation, not one-off scripts): which Claude Code version the image ships, whether `reloadSkills` works there, whether SessionStart hook output is shown to the user, and whether a trusted-after-start session runs the held-back hook.
7. Treat the codebase as the source of truth: nothing here overrides verified code behaviour. The external facts above change the ranking inputs for B and D (a SessionStart + `reloadSkills` hook is cleaner than a prompt-time stub for the already-open-session case; trust and blast radius are the new costs), not the finding that 6.9.0 has no user-scope install.
