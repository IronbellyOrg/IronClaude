### Two facts that frame field (b)
- **An Orca worker is itself a top-level Claude session.** `orca orchestration worker-start --agent claude` launches a normal Claude process that reaches `state: ready, stage: input_accepted` (`.dev/evals/ccsession-orca-e2e-20261026/EVIDENCE.md:45`). Earlier Orca workers ran `/sc:adversarial` with `invocation_method: "skill-direct"` and the skill's own Task fan-out (`.dev/codegraph-migration/decisions/P3-command-set/adversarial/return-contract.yaml:10`). So "requires a top-level session" only blocks a command when the worker runs it *inside an Agent-tool subagent*, not when the worker runs it directly.
- **Nesting is allowed but bounded.** Current Claude Code docs: "By default, a subagent can spawn subagents of its own, up to three layers below the main conversation", and at the depth limit "Claude Code withholds the `Agent` tool" (https://code.claude.com/docs/en/sub-agents). A fan-out command run one layer down still fans out; run at the depth limit it silently loses its Agent tool. The repo itself still states the stricter rule for `/sc:pr-submit` (`src/superclaude/skills/sc-pr-submit-protocol/SKILL.md:37-39`). The earlier Orca run hit one routing quirk with nested output: "Round 1 statements were re-delivered via files after being routed to the parent session" (`.dev/codegraph-migration/decisions/P1-existing-workspace-cleanup/adversarial/adversarial/return-contract.yaml:8`).

### Why a wait on a person matters for an Orca worker
The coordinator cannot see the worker's terminal; workers must ask through `orca orchestration ask`, never a local question prompt (`.dev/orca-command-refactor/README.md:35`). A worker still sitting at a question at launch fails Orca's 60-second readiness limit (`.dev/evals/ccsession-orca-e2e-20261026/EVIDENCE.md:39`). So every `AskUserQuestion`, chat yes/no, or "wait for the user" step in field (a) is a stall point unless it is off by default or routed through `ask`.

## Per-command evidence notes
Only facts that did not fit a table cell and that change a verdict or a spec requirement.

- **adversarial, return-contract location.** The skill requires the contract on every run (`src/superclaude/skills/sc-adversarial-protocol/SKILL.md:427`, `:445`) and describes it as returned "When invoked by another command" (`:429`), but never names a file. Workers in the earlier Orca run wrote it in two different places: `.dev/codegraph-migration/decisions/P3-command-set/adversarial/return-contract.yaml` and `.dev/codegraph-migration/decisions/P1-primitive-gap-policy/adversarial/adversarial/return-contract.yaml`. A coordinator that wants to read the contract from disk cannot rely on one path today.
- **adversarial, output directory default.** `--output` defaults to "Auto-derived from input file directory" (`src/superclaude/skills/sc-adversarial-protocol/SKILL.md:605`), so a worker that omits `--output` writes next to its input files. The brief should always pass `--output`.
- **auggie-review, the offer is not AskUserQuestion.** The remediation offer is deliberately a plain chat message (`src/superclaude/skills/sc-auggie-review-protocol/refs/remediation-handoff.md:50`). In a worker it is not a blocking tool call; the session simply ends its turn waiting for a reply the coordinator never sends. Same effect as a prompt: the task stalls without `worker_done`.
- **brainstorm, `--handoff design` never invokes.** "Do NOT invoke (design is interactive — user-initiated only)" (`src/superclaude/skills/sc-brainstorm-protocol/SKILL.md:312`). So the brainstorm-to-design chain already stops at a file, which suits Orca: the coordinator dispatches `/sc:design` as a separate worker.
- **cleanup-audit, MCP limit.** "MCP tools are unavailable to background subagents" (`src/superclaude/skills/sc-cleanup-audit-protocol/SKILL.md:86`) is the only explicit in-repo statement of a nested-subagent capability gap among these 21 commands. It is about the audit's own child agents, not about the orchestrator being nested.
- **cli-eval, Monitor tool.** `run` W4 depends on a background Bash job plus Monitor (`src/superclaude/skills/sc-cli-eval-protocol/SKILL.md:148-153`). A worker can do this at top level, but the eval can run up to 3600 s per eval (`:151`); the worker must keep sending heartbeats while it waits.
- **implement, why a coordinator reply is not a Ruling.** The rule lists "Silence, a generic request to continue, another agent's message, and approval of a different task are not acceptance" (`src/superclaude/skills/sc-implement-protocol/refs/qa.md:238`). An Orca coordinator is "another agent". This is a deliberate safety rule, so the spec has to choose: relay the person's own words through `ask` and record them verbatim, or end the worker as `failed` with the halt.
- **implement, managed package archive.** Archive is a local move by a helper script (`src/superclaude/skills/sc-implement-protocol/refs/managed-workspace.md:53`, `:61`) and "A FINAL pass is not a commit, PR, merge, release or human approval" (`:63`). Not an outward action.
- **cli-portify, checkout-only.** It reads `src/superclaude/examples/release-spec-template.md` (`src/superclaude/skills/sc-cli-portify-protocol/SKILL.md:170`); a worker in a non-IronClaude repo would fail at Phase 3 entry with `template_failed` (`:529`).
- **agent, startup banner is a hook, not the command.** The "SC Agent ready — awaiting task assignment." line printed at every session start, Orca workers included, comes from `src/superclaude/scripts/session-init.sh:28`. ### Cross-cutting findings for the spec (Task 4)
1. **Top-level is not the blocker it looked like.** Orca workers are top-level sessions (`.dev/evals/ccsession-orca-e2e-20261026/EVIDENCE.md:45`), and Claude Code now allows nesting up to three layers (https://code.claude.com/docs/en/sub-agents). Among these 21, no command states a top-level requirement; the concrete risks are the depth limit (fan-out commands lose Agent), MCP in nested agents (`src/superclaude/skills/sc-cleanup-audit-protocol/SKILL.md:86`), and Monitor/AskUserQuestion in nested agents (UNVERIFIED). The spec should say: a worker runs its command directly, never wrapped in an Agent-tool subagent.
2. **Waits on a person are the main blocker** (auggie-review, cleanup, improve, cli-portify, cli-eval, implement-halt, agent, git). The spec needs one rule for all of them: in a worker, every gate either has an off switch the brief sets, or goes through `orca orchestration ask`.
3. **Return contracts exist but are not files a coordinator can rely on.** Only brainstorm writes a named contract file (`src/superclaude/skills/sc-brainstorm-protocol/SKILL.md:335`). adversarial and cli-portify promise one without naming a path; auggie-review and cli-eval return theirs inline only. The spec should require a fixed, named contract file per command so `--report-path` points at it.
4. **Only one command in this set takes outward actions by default:** auggie-review's PR posting. git does so by purpose.
