THEME "ledger": change the loop's architecture from repeated whole-document reviews to a finding LEDGER with separate "find" and "verify" phases. Design: review 1 is the only full find pass and writes a ledger file (one row per finding: id, anchor quote, severity, status open / fixed / verified / reopened / deferred); the reviser answers ledger rows and records what it changed per row; each later round is a VERIFY pass that checks only the ledger rows (is the finding resolved by the change, and did the change break the sentence it touched), with at most one bounded "new defect on changed lines" check, and exactly one final whole-document sweep at the very end whose new findings are reported but not looped on. Work out: the ledger file format and where it lives (so a script can read it), who is allowed to change a row's status, how the loop terminates by counting rows (a computed rule, not a feeling), how this differs from 427's `--re-review` (which still re-reviews the document), and how the same ledger contract could be adopted by the other review commands outside spec-panel (`/sc:reflect`, rf-qa agents, the `/sc:implement` final review), because those are four of the five recorded incident types and 427 never reached them. Compare a stateful single reviewer session that keeps its own memory against a file ledger and recommend one.
