THEME "ponytail": a severity-and-necessity audit of the fixes using the installed ponytail review skill. The owner's idea, to be specified as the primary design: at the END of the SECOND fix round (after the reviser has applied the fixes of fix cycle 2, before the loop closes or escalates), run a `ponytail:ponytail-review` pass whose instructions say: validate the ACTUAL severity and the NECESSITY of each fix, that is, for every applied fix, was the finding it answers really blocking (a real defect: wrong behaviour, false claim, missing required deliverable, security or data-loss risk) or only minor, and is the added text needed at all or is there a smaller change or a deletion that fully solves it. The output is a per-fix table (finding id, claimed severity, validated severity, necessary yes/no, smaller alternative, verdict keep / shrink / revert) that the loop then APPLIES (revert or shrink the unnecessary fixes) and that decides the final verdict, in a single pass that is itself never re-reviewed (so the audit cannot become another non-converging loop). Work out: the exact brief handed to the ponytail reviewer (what it receives: baseline, current document, the findings and dispositions, the fix diff; what it must return), whether `ponytail:ponytail-review` can be invoked as a skill from the loop and what its default output looks like (read the skill), how the apply step is done safely (who reverts, how it is logged, how revert avoids reopening the finding), and how a revert changes the verdict (a finding whose fix is reverted because it was minor is recorded as minor and closed, not open). ALSO evaluate, in the same spec, two alternative placements and say which you recommend and why: (a) after every fix cycle, and (b) as a triage of the findings BEFORE the first fix. The owner's placement (end of second fix round) must be fully specified even if you recommend a different one. Predict the effect on review-3 blocking count and growth for each placement.
