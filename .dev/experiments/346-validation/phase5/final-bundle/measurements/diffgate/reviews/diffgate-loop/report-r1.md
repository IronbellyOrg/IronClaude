=== REQUIREMENTS ANALYSIS ===

**Karl Wiegers (requirements quality).** The decision in section 1 is well argued and its evidence gaps are stated honestly (`SPEC:41-45`). The defects are in the contract requirements that an implementer must turn into exact behaviour.
- WC-4 (`SPEC:62`) defines the report location as `<output-dir>/return-contract.yaml` "where `<output-dir>` is the directory the coordinator passed (`--output` / `--output-dir`)". That rule cannot be met for several commands the spec itself lists: `/sc:workflow` treats `--output` as retired and stops with `E-LEGACY` (`src/superclaude/skills/sc-workflow-protocol/SKILL.md:24`) and writes its contract into a package whose id is generated at run time, `TASK-WF-<subject>-<timestamp>` (`SKILL.md:44`; `refs/return-contract.md:3`); `/sc:tdd` and `/sc:init-lite` take a file-valued `--output` (`src/superclaude/commands/tdd.md:49`, `src/superclaude/commands/init-lite.md:32`), and section 3.1 confirms "`--output <file>`" for both (`SPEC:87,90`). The adversarial row puts the contract at `<output>/adversarial/return-contract.yaml` (`SPEC:83`), a different path from WC-4's. So "known before dispatch" is false for workflow, and undefined for tdd and init-lite. **R1.1, MAJOR, blocking.**
- WC-4 also says "Commands that already write a contract keep their fields and add the missing ones" (`SPEC:62`) while requiring a `status` field from a fixed four-value set. The existing contracts already have a `status` field with other values: workflow `status: success | partial | failed` (`refs/return-contract.md:7`), adversarial `status: "success"` nested under a top-level `return_contract:` key (`src/superclaude/skills/sc-adversarial-protocol/SKILL.md:432,436`), reflect `status: stopped-precondition` (`src/superclaude/skills/sc-reflect-protocol/SKILL.md:250`). Keeping the old field and adding `status` is impossible without renaming one; the 7.2 step-4 check `assert d['status'] in {'succeeded','partial','failed','blocked'}` (`SPEC:183`) then fails on a correct adversarial run (no top-level `status`) and on a correct workflow run (`success`). **R1.2, MAJOR, blocking.**
- The load row says "Report: none", "Resume: n/a" and use it only inside another worker's brief (`SPEC:112`), and the Decisions table says a report file for load "would be an unrequested addition" (`SPEC:265`). AC-1.1 asserts "every command in sections 3.1-3.2 has a `## Unattended mode` section naming `return-contract.yaml`" (`SPEC:195`), and load is a 3.2 row. The implementer must either give load a contract (against its row) or ship a failing AC-1.1. **R1.6, MAJOR, blocking.**
- Section 3.1 says "The only command changes are the small fixes in the last column" (`SPEC:79`), and brainstorm and init-lite have "None" there (`SPEC:84,87`); P1 and AC-1.1 add `--unattended` and the section to every 3.1 command (`SPEC:159,195`). The phase text wins, so behaviour is inferrable. **R1.8, MINOR.**

**Gojko Adzic (specification by example).** Run WC-4 with a concrete example: Given the brief `/sc:workflow "add X" --handoff none --unattended --output .dev/wk/a/`, When the worker runs it, Then workflow stops with `E-LEGACY` before any package exists, writes no YAML (`refs/return-contract.md:39`), and the worker sends `--outcome failed` with no report (WC-5, `SPEC:63`). The P1 fix "Write the contract for pre-creation STOPs too" (`SPEC:92`) cannot say where, because the only directory workflow writes into does not exist yet. The example shows R1.1 is not a wording issue. Given `/sc:adversarial ... --output out/` finishing successfully, Then `yaml.safe_load(out/adversarial/return-contract.yaml)['status']` raises `KeyError` (the key is `return_contract`), so a correct run fails 7.2 step 4 (R1.2).

**Alistair Cockburn (actors and goals).** Three actors are named clearly: the coordinator, the worker session, the command (owner column of `SPEC:57-70`). Two requirements put a duty on the wrong actor:
- WC-6 makes the command choose "a fresh output directory so a re-run starts clean" (`SPEC:64`), but WC-4 makes the coordinator pass the directory before dispatch (`SPEC:62`) and section 2.3 has the brief carry it (`SPEC:73`). A retry worker started with `--retry-of` gets the same brief, so either it reuses the first attempt's directory (what WC-6 forbids) or the command picks a new one and `worker_done --report-path` no longer matches the path the coordinator recorded. WC-3's "re-invoke ... the command with the answer as a flag" (`SPEC:61`) inside one worker hits the same collision with the first run's `status: blocked` contract. **R1.3, MAJOR, blocking.**
- WC-7's primary actor is the worker session, and its goal is "runs the command directly in its own session" (`SPEC:65`). The brief arrives inside an Orca preamble that begins "You are working inside Orca" (the shape of this worker's own preamble). The repo's rule that forces the Skill call fires only "When a message starts with `/sc:<name>`" (`src/superclaude/core/CLAUDE.md:73`), so it does not fire for a worker. Nothing in WC-7 or in its checks requires the Skill tool call: AC-0.4 checks only "no Agent-tool wrapper, verified in the step-5 transcript" (`SPEC:194`), and step 5 checks only that `AskUserQuestion` is absent (`SPEC:184`). A worker that reads the command file and performs the protocol from memory passes every check. **R1.4, MAJOR, blocking.**

=== ARCHITECTURE ANALYSIS ===

**Martin Fowler (interfaces).** The boundary is the right one: commands expose a flag-and-file interface (`--unattended`, an output location, `return-contract.yaml`) and know nothing of Orca (`SPEC:16`, `SPEC:51`). That is a clean port. The port is under-specified in exactly the two places an interface needs to be exact, location (R1.1) and schema (R1.2): one generic report shape over commands that already own a `return-contract.yaml` with their own `status` vocabulary needs a separate field name or a separate file, and the spec chooses neither.

**Michael Nygard (failure modes).**
- Outcome mapping WC-5 is sound and the Orca facts support it: a worker's own `failed` report does not count toward the circuit breaker (`CAPS:80`), so mapping `blocked` to `failed` does not burn retries.
- WC-10 says "A command step that blocks a single tool call for longer than 5 minutes ... must be split" (`SPEC:68`). Read literally it covers a foreground Agent-tool fan-out call (adversarial debates, tdd research), which a command cannot split, and the ready-today commands get no change for it (`SPEC:83,90`). The harm is limited: whether Orca uses heartbeat age at all is UNVERIFIED (`CAPS:130`), and absence of a signal never authorizes stop or release (`CAPS:111,125`). **R1.10, MINOR.**
- WC-12's "stops without sending `worker_done`" on `consumer_fenced` (`SPEC:70`) and WC-5's "exactly once" (`SPEC:63`) read as a conflict; WC-12 is the more specific rule and Orca's guide says the same (`CAPS:67`). **R1.13, MINOR.**

**James Whittaker (adversarial).**
- I can break this specification by **Sentinel Collision Attack**. The invariant at **D1 (a) and SA-1** ("a person never types it", `SPEC:228`; prompts unchanged without `--unattended`, `SPEC:146`) fails when **a person's own quoted argument contains the text `--unattended`**. Concrete attack: before, a person runs `/sc:troubleshoot "the worker ignores --unattended and still prompts"`; the command's `## Unattended mode` section says the mode is on "when the caller passes `--unattended`" (`SPEC:51`) and defines no parse rule, so a model reading `$ARGUMENTS` switches mode; after, the person's `--fix` offer and STOPs resolve as `blocked` and a contract file appears in their tree, breaking SA-1 and SA-3. **R1.7, MAJOR, blocking (FR-8 GAP in table row G3-S).**
- I can break this specification by **Sequence Attack**. The invariant at **WC-4/WC-6** fails when **a retry worker is dispatched with the first attempt's brief**. Concrete attack: attempt 1 writes `out/return-contract.yaml` with `status: blocked`; the coordinator retries with `--retry-of` and the same `--output out/`; attempt 2 either overwrites attempt 1's evidence (WC-6 violated) or writes to `out-2/` (report path differs from the one recorded at dispatch). This is R1.3.
- I can break this specification by **Zero/Empty Attack**. The invariant at **WC-4 "written on every outcome ... including stops before any other output exists"** (`SPEC:62`) fails when **the brief omits the output flag under `--unattended`**: there is no directory to write into and the spec names no fallback or refusal. This is part of R1.1 (row G4-Z).

**Sam Newman (evolution and versioning).** The spec adds a shared contract with no version field and makes the installed copy (`~/.claude/WORKER-CONTRACT.md`, `SPEC:52`) the only reference each command section points to. A worker in a checkout whose `~/.claude/` was installed from an older version reads an older contract than the command it runs. Inferrable risk, no concrete wrong outcome named; folded into note R1.9 together with the baseline drift.

**Gregor Hohpe (integration).** The message exchange is request/reply over a durable mailbox (`CAPS:58-62`) and the report is a pointer, not content (`CAPS:79`). The spec handles both correctly (WC-3 resume by message ID; coordinator opens the file, `SPEC:62`). Two checks are fragile: 7.2 step 2 asks for `worker-show` "at least once per 5 minutes" (`SPEC:181`) while step 3 blocks in `check --wait` for up to 900 s (`SPEC:182`), so one coordinator session cannot do both as written (**R1.11, MINOR**); and step 5 relies on `worker-read --source transcript` containing tool-call names (`SPEC:184`), which `CAPS:131` does not establish (**R1.12, MINOR, UNVERIFIED**; origin/master commit `f3c1ef062` later changed step 5 to read the session file).

**Architecture verdict input.** AC-C1 scans `src/superclaude/core` (`SPEC:172`), the folder P0 writes the contract file into (`SPEC:158`). SA-2 permits Orca to appear "as an example of a caller's question channel inside the contract file" (`SPEC:147`), and the contract must also tell the worker session how to report and check (WC-5, WC-12, `SPEC:63,70`). The natural text, for example `orca orchestration ask --from ...`, matches the AC-C1 pattern `orca(-ide)?[[:space:]]+(orchestration|...)`, so the spec's own permitted content fails its own every-phase check. Corroboration: origin/master's contract file contains such a line (`origin/master:src/superclaude/core/WORKER-CONTRACT.md:101`). **R1.5, MAJOR, blocking.**
