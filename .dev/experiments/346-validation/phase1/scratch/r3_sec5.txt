### 4.1 Requirements analysis
=== REQUIREMENTS ANALYSIS ===

**Karl Wiegers (requirements quality).** The round-2 contradictions are gone: WC-6 (b) and the reading guide now state one rule (`SPEC:69`, `SPEC:98`), and the report directory has one precedence (`SPEC:56`). Three requirement-quality defects remain. First, the coordinator obligations the revision rewrote in section 2.3 (dependents created only after inputs settle, `SPEC:84`; the fan-in cap and staged merge, `SPEC:86`) carry no ID, so 7.4's "Every requirement has at least one check" (`SPEC:298`) is true only of WC and SA rows; nothing verifies the two rules that fixed round-2's MAJOR N1 and CRITICAL N5, and nothing checks that P0's `WORKER-CONTRACT.md` contains any rule at all (AC-0.1 checks only that the name is listed and the file installs, `SPEC:259`, `SPEC:290`) (M1). Second, "exactly one report directory" (`SPEC:56`) depends on whether a command's output flag is "directory-valued", but the rows that add an output flag never say which kind they add (analyze "add `--output`", `SPEC:121`; spec-panel "add `--output`", `SPEC:142`; build, business-panel, design, explain, index, test "add a report path"/"add an output path", `SPEC:123-130,133,145`); `/sc:analyze` has no `--output` today (`cmd/analyze.md:22`) (M3). Third, two Resume cells cannot be classified under the new WC-6 rule: cleanup-audit's "`progress.json` checkpoint" (`SPEC:107`) and save's "it writes resume state" (`SPEC:141`) say neither "no new flag" nor "flag"; the skill says only that `progress.json` "enables resume-from-checkpoint on session interruption" (`sk/sc-cleanup-audit-protocol/SKILL.md:76`), and `DISP2:58` concedes the fact is unstated (M8). "How would a coordinator validate that a crashed cleanup-audit may take `--retry-of`? The spec gives it nothing to read."

**Gojko Adzic (specification by example).** AC-1.7 is the only example of a same-brief retry, and it does not exercise the property WC-6 (b) needs. The first attempt is stopped "before it settles" (`SPEC:271`), and a stopped run has usually written no contract, because WC-4 writes the contract at an outcome (`SPEC:67`); then "holds no field value from the first attempt" is true of an empty set. Its pass condition is also weaker than the rule: WC-6 (b) says "no field of the first attempt survives" (`SPEC:69`), AC-1.7 only that no surviving value "contradicts the retry's own result". A concrete Given/When/Then is missing: *given* a first-attempt contract carrying a sentinel field, *when* the retry runs, *then* the sentinel is absent (M6). The worked example (`SPEC:88-93`) still holds against Orca's verbs.

**Alistair Cockburn (actors and goals).** The ask policy's actor is the worker re-invoking the command "with the answer as the command's argument or flag ... and the same report directory" (`SPEC:66`). For an approval gate the actor has no such argument: cli-portify's three approval gates resolve as blocked "with the artifact to review named in the contract" (`SPEC:127`), and task's TFEP "present to user" (`SPEC:143`) has no answer flag either. For review-translation the blocked run has already written its context summary before it blocks (`SPEC:139`), and its Resume cell is "add a resume input, or fresh run", which WC-6 treats as unsafe for a same-directory re-run; yet the ask path re-runs it in place (M2). The person who gives a Ruling under D2 (b) is again an actor the implement row excludes unconditionally ("a Ruling halt is never asked, whatever the brief's gate policy", `SPEC:131`), while WC-3 limits that to "while open decision D2 is (a)" (`SPEC:66`) and D2 (b) lifts it (`SPEC:344`) (M9).

### 4.3 Adversarial analysis (Whittaker)
=== ADVERSARIAL ANALYSIS ===

**A1. Zero/Empty attack (MAJOR, M6).** I can break this specification by **Zero/Empty Attack**. The invariant at **AC-1.7 (`SPEC:271`), verifying WC-6 (b) "no field of the first attempt survives" (`SPEC:69`)** fails when **the first attempt is stopped before it writes any contract**. Concrete attack: (1) dispatch `/sc:init-lite --unattended --output <dir>/context-audit.md --report-dir <dir>`; (2) `worker-stop` 10 s after `state: ready`, before the command has written `<dir>/return-contract.yaml`; (3) cancel, then `--retry-of`. State before the retry: no first-attempt contract. State after: the retry's contract only. "Holds no field value from the first attempt" is trivially true, so AC-1.7 passes for an implementation that merges new fields into an existing contract instead of rewriting it, the exact defect WC-6 (b) exists to exclude.

**A2. Divergence attack (MAJOR, M3).** I can break this specification by **Divergence Attack**. The invariant at **section 2.1 report directory, "exactly one" (`SPEC:56`)** fails when **a brief for a command whose output flag is added in P1 passes both `--output` and `--report-dir`**. Concrete attack: brief `/sc:analyze src/ --unattended --output .dev/a/report.md --report-dir .dev/a/`. If P1 adds analyze's `--output` as a file flag (as tdd's and init-lite's are, `SPEC:109,112`), the brief is valid and the contract lands in `.dev/a/`. If P1 adds it as a directory flag (as brainstorm's is), the same brief is refused before any work with the WC-4 error and `worker_done --outcome failed`. The spec does not say which (`SPEC:121`), so the coordinator cannot write a brief known to be valid.

**A3. Sequence attack (MAJOR, M2).** I can break this specification by **Sequence Attack**. The invariant at **WC-3 ask path (`SPEC:66`)** fails when **the blocked gate fires after the command has written output**. Concrete attack: `/sc:review-translation <target> --unattended --report-dir .dev/rt/` with `On a blocked gate: ask the coordinator` and no pre-confirmed context. Run 1 writes its context summary and blocks (`SPEC:139`); the worker asks; the coordinator answers; the worker re-invokes the command "with the answer ... and the same report directory". Run 2 writes into the same `reports/localization/` files (`SPEC:139`). State after: the contract is replaced whole, but run 1's other files are overwritten or left beside run 2's, which WC-6 (b) forbids for any command whose Resume cell is not a no-flag resume or overwrite; review-translation's is "add a resume input, or fresh run". For cli-portify (`SPEC:127`) the answer to an approval gate has no argument or flag at all.

**A4. Accumulation attack (MAJOR, M5).** I can break this specification by **Accumulation Attack**. The invariant at **fan-in staged merge (`SPEC:86`)** fails when **the coordinator plans more than 100 inputs**. Concrete attack: 150 `/sc:troubleshoot` workers. Groups hold at most 10, so there are at least 15 group results, but "one merge Task over the group results, which must also number 2 to 10". No rule allows a third level or caps N at 100. State after planning: no valid plan.

**A5. Sentinel collision attack (MAJOR, M7).** I can break this specification by **Sentinel Collision Attack**. The invariant at **7.2 step 6 (`SPEC:249-253`)** fails when **the checker's own step 4 writes into the worktree**. Concrete attack: a worker that writes only `<dir>/return-contract.yaml`. Step 0 snapshot; worker runs; step 4 `uv run python -c ...` creates `.venv/` (no `.venv` existed). State after: step 6's `find -newer` and the status diff print every `.venv/` file; none is under `<dir>`, a documented command artifact, or a named background tool, so a correct worker fails AC-1.2.

**A6. Sequence attack (MAJOR, M8).** I can break this specification by **Sequence Attack**. The invariant at **WC-6 retry routing (`SPEC:69,98`)** fails when **a cleanup-audit worker crashes mid-pass**. Concrete attack: the coordinator reads the Resume cell "`progress.json` checkpoint" (`SPEC:107`). If that resume needs no flag, WC-6 (b) allows `--retry-of` with the same brief; if it does, WC-6 (a) requires a new Task. Neither the row nor the skill (`SKILL.md:76`) says which, so two coordinators following the spec take different, mutually exclusive actions on the same crash.

### 4.5 Pipeline dimensional analysis (Fowler + Whittaker)
The revised fan-in at `SPEC:86` is the only multi-stage count-changing flow.

```text
Single-stage plan (N <= 10, capped at planning, SPEC:86)
[Coordinator: N input Tasks, N <= 10]
        | all N settle
        v
[S succeeded] [P partial] [B blocked] [F failed]        S + P + B + F = N
        |   usable U <= P | re-run replaces or drop | retry replaces or drop
        v
[Admitted A <= N <= 10]   (a re-run replaces its input, never adds one)
        +-- A < 2        : no merge; report to person                OK
        +-- 2 <= A <= 10 : merge Task, dropped inputs listed          OK
[Consumer: /sc:adversarial --compare, 2-10 files (cmd/adversarial.md:15)]   OK

Staged plan (N > 10)
[N inputs] --> [G groups of 2-10] --> per group: A_g admitted
        A_g = 0 -> group dropped;  A_g = 1 -> passed on;  A_g >= 2 -> group merge
        --> [G' <= G group results] --> final merge (fan-in rule: G' < 2 -> report)
        G <= 10 required ("must also number 2 to 10")  =>  N <= 100
        N > 100: G >= 11, no rule                               <-- MISMATCH (planning)
```

Consistency check: with N = 12, a single-stage plan is not allowed and the staged plan gives G = 2 (for example 6 + 6), so A never exceeds what its consumer accepts. The runtime counts are conserved. The remaining mismatch is at planning time: N = 150 needs G ≥ 15 group results for a consumer that accepts 10. FR-19 classifies dimensional mismatches as CRITICAL; the panel classifies this one MAJOR (via FR-8) because it is a planning guard with no runtime count divergence, and records the disagreement in 4.6.

### 4.6 Expert consensus and disagreements
**Consensus.** The round-2 fixes are in the spec text and are correct in substance; the core decision (Orca coordinates, commands stay Orca-free, `SPEC:18`, `CAPS:97-98`) still holds. The new defects sit in the edges of the new machinery: the checks that should prove it (M1, M6, M7, M11, M12), the per-command rows it now depends on (M3, M4, M8), the ask path (M2), and consistency of text the revision did not touch (M9, M10, M13, M14).

**Disagreements.**
- *M5 severity.* Whittaker would apply FR-19 (CRITICAL) because a consumer limit is exceeded. Fowler and Hohpe hold MAJOR: runtime counts are conserved, the mismatch exists only for plans above 100 inputs, and FR-8 already makes the GAP MAJOR. Kept MAJOR.
- *M4 severity.* Fowler would rate it MINOR, because implementers will obviously amend the invariant. Wiegers holds MAJOR: init-lite calls the invariant "non-negotiable" (`SKILL.md:59`) and the row says "None", so following the spec exactly means violating a stated safety rule. Kept MAJOR.
- *M8 severity.* Hohpe would rate it MINOR, because a cautious coordinator can always choose a new Task. Whittaker holds MAJOR under FR-8: the guard cannot be evaluated from the spec, and `--retry-of` is the cheaper path a coordinator will reach for. Kept MAJOR.
- *M11, M12.* Kept MINOR: the intended order and step exceptions are inferable.
