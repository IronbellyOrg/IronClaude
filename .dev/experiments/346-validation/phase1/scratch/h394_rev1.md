### Contradictions and defects in the stated rules

**B-1 (BLOCKING). Backtick substitution inside a push reaches `main` at `full --submit`.**
Change 9 N5 splits at backtick, so the backtick never appears in a word. Change 11 item 4 blocks only a push argument containing `$`. Result: ``git push origin a:b `echo c:main` `` is segment 1 `git push origin a:b` (allowed at FS) plus segment 2 `echo c:main` (NONE). Real git pushed to `main` (test 8). The earlier Round 2 text said "no `$` or backtick"; Change 11 dropped the backtick. T-NRM-3 lists the backtick as a separator but no test covers it in a push.
Required fix, Change 9 add after N2: "Before N5 runs, set flag **BT** when the text contains a backtick." Change 11 item 4 add: "...or BT is set in a command that contains a PUSH". Add tests `T-PSH-11 test_backtick_in_push_blocked` (``git push origin a:b `echo c:main` `` is LL-PUSHNAME at FS) and update T-NRM-3.

**B-2 (BLOCKING). Backslash-newline splits a push into two segments.**
Change 9 N2 deletes `\` first, leaving the newline, and N5 then splits at the newline. A shell treats `\<newline>` as a join. `git push origin a:b \<newline> c:main` becomes `git push origin a:b` (allowed) and `c:main` (NONE). Real git pushed to `main` (test 7). Agents wrap long commands with continuations all the time, so this is also the likeliest accidental route.
Required fix, Change 9 replace N2 with: "**N2.** Replace each backslash followed by a newline with one space (the shell joins the lines). Then delete every `'`, `\"` and `\\` character..." Add test `T-NRM-5 test_backslash_newline_joins` (the push above is LL-PROTECTED at every level; `git push origin a:b \<nl> c:d` at FS is allowed).

**B-3 (BLOCKING). Dashed git built-ins are not git words.**
`/usr/lib/git-core/git-push`, `git-commit`, `git-merge`, `git-pull` exist on this host as symlinks to `git` (test 9). `$(git --exec-path)/git-push origin main` is a one-line route, not a variable chain. Change 9 N7 and Change 10 look for basename exactly `git`.
Required fix, Change 10 add: "A word whose basename is `git-` followed by a name `<n>` is the git word followed by the subcommand `<n>` (so `/usr/lib/git-core/git-push` is `git push`)." Add `T-GIT-12 test_dashed_builtins` (`git-push origin main` and `/usr/lib/git-core/git-push origin main`: LL-PROTECTED; `git-commit` at F: LL-COMMIT).

**B-4 (BLOCKING). gh api write detection misses common forms and a main-branch write route.**
Change 12 H2 skips "the values of `-X`, `--method`, `-f`, ..." and decides write by "a `-X` or `--method` value other than GET". It does not say what happens for `--method=POST`, `-XPOST`, `--raw-field=a=b`, `--field=a=b` (gh uses pflag, which accepts all of them). For `gh api --method=POST repos/o/r/merges` the path is found, no method value is seen, no `-f` word is seen: the call reads as a read, class NONE, and H5 does not apply because the segment has a gh word. That is a merge at every level. Also, the MERGE word list (`merge`, `git/refs`, `updateref`, `createref`, `deleteref`, `createcommitonbranch`) has no word for the REST contents API (`PUT repos/o/r/contents/<path>` with `branch=main` commits straight to `main`), which is a push to `main` at `FS`. A GraphQL mutation read from a file (`-F query=@m.graphql`) shows no `mutation` word.
Required fix, Change 12 H2: "A **method flag** is `-X`, `--method`, a word starting `--method=`, or a word that starts with `-X` and has more text. A **field flag** is `-f`, `-F`, `--field`, `--raw-field`, `--input`, a word starting `--field=`, `--raw-field=` or `--input=`, or a word starting `-f` or `-F` with more text." Add `contents/` to the MERGE words for writes. Add to R10: "`gh api` input read from a file (`@file`, `--input`) is not inspected." Tests: `T-GH-10` for `--method=POST repos/o/r/merges`, `-XPOST`, `--raw-field=` and a `PUT repos/o/r/contents/x -f branch=main`, all LL-MERGE at every level.

**B-5 (BLOCKING). N3 and N4 need a regex tool that Change 22 does not allow, and the N6 `tr` set loses the segment boundaries.**
Change 9 says N5 and N6 "run as `tr` calls". N3 (`/./` to `/`) and N4 (redirection removal with a next-word rule) cannot be done with `tr`. Change 22 item 3 lists the only allowed subprocesses ("at most one `jq` ... `tr` only for Bash and Monitor text ... `mkdir`, `mv`, `touch`, `rm`"), Change 3 says "no awk, no Python", and Change 26's `path_without` builds a PATH from "bash and the coreutils the script uses". The executor rule is "if a detail is missing here, the rule is not in v1", which would drop N4 and make `git push origin a:b 2>&1` a PUSHNAME block at FS (T-NRM-2 fails). Separately, N6 as written replaces every character outside `A-Za-z0-9._/=:@+~$-` with a space; applied by one `tr` over the whole text this also replaces the newlines N5 just created (test 6: boundaries lost).
Required fix: Change 9 add: "N3's `/./` step and N4 run in one `sed -E` call (or in the same `jq` call with `gsub`). The `tr` set of N6 includes the newline." Change 22 item 3: add `sed` (one call) to the list. Change 26: `path_without` also keeps `sed`; T-FC-3 removes `tr` or `sed` in turn.

**B-6 (BLOCKING). Background subagents are a turn-starting route that TURN does not cover.**
Change 16's reason for TURN is that a Monitor line or background task notice "starts a turn whose text the agent chose", and V6 says UserPromptSubmit fires on turns the harness starts itself. A completion notice from an `Agent` or `Task` call with `run_in_background: true` is the same mechanism and the subagent's final text is chosen by the agent. P5 already reads `run_in_background` for every tool, but class TURN is defined only for `Bash`. Change 8 item 8 states "the agent cannot produce a prompt event; turn-starting tools are blocked before approval" and T-TRN-4 claims it lists "every turn-starting or input-injecting route". Both are untrue as written, and OB-H1 item 5 does not record this payload either.
Required fix, Change 16 item 1: add "an `Agent` or `Task` call whose `tool_input.run_in_background` is `true`". OB-H1 item 5: add "and of a background-subagent completion". T-TRN-1 and T-TRN-4 add the case. Row 11 of the Change 20 table adds it.

**B-7 (BLOCKING). AC-5 "fails closed ... when required state is missing" is not met for a missing session file, and no owner decision or AC-map caveat says so.**
Change 21's failure table says "session file deleted: the session reads as ordinary". An unreadable or invalid file does fail toward `worktree` (good), and a missing pending record at bind degrades (good), but the state the AC names ("required state is missing") for an already-bound session is exactly the case that releases it. The plan records it only as R3. AC-6 gets an explicit limit (O-7) and a "limit" note in the AC map; AC-5 gets neither.
Required fix: add owner decision **O-16**: "AC-5 and a missing session file. Default: accepted. A bound session whose file is gone reads as ordinary; this is also the release route (R3)." Alternative: "none available with file state alone". Change 28 AC-5 row: add "limit: O-16, R3". Section 13 sentence: "AC-5's fail-closed clause covers an unreadable, empty, invalid or unknown session file and a missing launch record; it does not cover deletion of the session file."

**B-8 (BLOCKING). False claim about messages in Change 10, and a bigger effect than stated.**
Change 10 "Departs from (2)" says applying UNKNOWN only to the first git word in a segment avoids "blocking commit messages and PR bodies that mention git". G4 repeats it for `git commit -m "fix git handling"`. That holds for a single-line message only. A heredoc or multi-line body is split into one segment per line (N5), and the first git word in each line is classified on its own: a body line `use git for hooks` has S = `for`, so UNKNOWN, blocked at every level including `FS` (row 31 pins the single-line form but the claim in Change 10 says the opposite). A simulation of `git commit -m "$(cat <<'EOF' ... fix: use git for hooks ... EOF)"` gave a segment `fix: use git for hooks`. The same applies to `gh pr create --body` text, which `/sc:pr-submit` writes at `FS`.
Required fix: reword Change 10 "Departs from (2)" and G4 to: "UNKNOWN applies to the first git word of each segment. A one-line message is one segment; a multi-line message or heredoc body is scanned line by line, so a body line that starts a sentence with `git <word>` is UNKNOWN and blocked at every level. LL-TEXT names the way around (`-F <file>`, `--body-file <file>`)." Add this case to R8 and as a pinned over-match row in Change 20, and count it in OB-H3's "how often LL-TEXT fires".
