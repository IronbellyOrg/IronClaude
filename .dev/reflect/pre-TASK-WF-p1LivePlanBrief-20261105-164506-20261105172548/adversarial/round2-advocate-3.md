## 3. New evidence not yet presented

- **E1. The "whole folder" strictness in P:58 came from the fix pass, and the old wording would pass today.** `post-fix-rechecks.md` row 2 (MEDIUM) reads "Install line compares only changed command files; spec says every file", and the fix is "Task 1 compares every file under `src/superclaude/commands/`". The spec has no such rule: `grep` for `cmp` in the spec finds only AC-0.2 (line 310, HOW-WE-WORK.md). The only "every file" near the install text is spec line 282: "without it the installer skips every file that already exists", which is about `--force`, not a comparison rule. Lines 163 and 167 are report-table rows. The brief's S:87 does say "every file under `src/superclaude/commands/`", so the fix pass followed S:87 and cited the spec for it. Measured: the branch changed 17 command files since the merge base, and none is `README.md` or `__init__.py` (`git diff --name-only ... | grep -E 'README.md|__init__.py'` finds nothing). So the pre-fix, changed-files-only line would have passed today; the post-fix line returns rc=2 for exactly `README.md` and `__init__.py` (`cmp` re-run: "No such file or directory" for both installed copies). That makes C-001 a defect the fix pass introduced.
- **E2. Why the Regression label is defensible and what the label is measured against.** Taxonomy `Regression` = contradicts "an explicit constraint in the spec" (line 74) and "rationale does not authorise contradiction" (line 94). The explicit constraints are S:17 and P:21: "If the installed files differ from the branch" / "any installed file differs". `README.md` and `__init__.py` are not installed files (`install_commands.py:11` `_EXCLUDE_FILES = {"README.md"}`; `list_available_commands` globs `*.md` and applies the exclusion at lines 142-143; `__init__.py` is not `*.md`). P:58 therefore contradicts P:21 inside the plan, and S:87 is a latent defect in the brief that the plan copied and sharpened ("the whole folder, changed or not", "PASS only when every `cmp` exits 0"). Both statements hold: inherited from S:87, and a regression against S:17, P:21 and the pre-fix plan. Severity HIGH is not disputed.
- **E3. C-003 has a mechanical mitigation already in the plan.** Task 23 saves `git status --short` before and after each run (`ac13-status-before.txt`, `ac13-status-after-1.txt`, `ac13-status-after-2.txt`, listed in the P:544 acceptance). `return-contract.yaml` is not gitignored (`git check-ignore -v .dev/p1-live/x/return-contract.yaml` returns rc=1), so a contract file created by either run would show as `??` in the after-status, and an overwritten tracked one as ` M`. The subtraction the exemption sentence needs can therefore be read from files the plan already saves. The defect is only that the pass clause (P:541, "the find output is empty") does not say so. LOW, one clause.
- **E4. Why the clean-tree check exists, and why scoping beats deleting.** The `cmp` in P:58 compares the installed files with the feature worktree's working copy, not with the branch commit. Disposable worktrees are made from `refs/heads/ironbelly/...`, the commit. If `src/` had uncommitted edits when the owner installed, the `cmp` would pass while the disposable worktrees held different files. That is the purpose of "a dirty tree makes the worktrees differ from the branch" and it is a real hazard, so the check should stay for `src/`, `plugins/`, `tests/` and `.claude/`. A change under `.dev/tasks/` cannot cause that hazard. Task 25 already tolerates package edits ("apart from this package's own files", P:586); P:58 and P:61 ("each one passes") do not. A failing P:58 clause is also not one of the recorded-result categories (only the install line may be FAIL in P:61), so, if it fires, Task 1 itself would be non-compliant rather than the run recording `not run`. I have not verified how `/sc:implement` reacts to a failed Task 1 acceptance; it is the consequence that makes C-002 worth a fix even though the trigger is conditional.
- **E5. U-003 is a lc18 problem, not an lc08 problem.** P:227 (lc08) says `pgrep -af -- '--watch'` "shows no watcher process started by the worker", a human-judged qualifier that survives a wrapper line. P:451 (lc18) says the second output "has no new process", and the wrapper PID differs per call, so the literal rule fails with nothing wrong. S:72 has the same wording. A second possible source (the worker's own `claude` process if its argv carries the brief text) is UNVERIFIED; I could not see an Orca-launched worker's argv here, so I do not claim it.

Negative checks (no finding).** Step 4's assertion `d['worker_contract_version'] == '1'` is correct against the contract: `WORKER-CONTRACT.md:32` documents the value as the string `"1"`, `sc-workflow-protocol/refs/return-contract.md:48` and `sc-brainstorm-protocol/SKILL.md:384` write it quoted, and the same one-liner is in spec line 289. `pyyaml>=6.0` is a project dependency (`pyproject.toml:38`), so `import yaml` under `uv run python -c` works.
