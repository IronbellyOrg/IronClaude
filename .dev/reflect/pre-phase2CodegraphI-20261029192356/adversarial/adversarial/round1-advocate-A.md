## Steelman of Variant B

The strongest version of Variant B's argument:

Other bullets in the same list state their own outcome too: plan:46 "exits 0", plan:47 "prints `coder-handoff-prompt.md`". plan:21 speaks of "every acceptance block" and "every line", and the fenced blocks (plan:57-64, 160-168, 181-189, 198-207, 240-251, 275-285) are the blocks. That is the plan departing from its source without reason, and B correctly adds the consequence: under `set -u` the line aborts with an unbound variable.

A `$ART` defined once in Constraints is not in scope inside those separate shells and would be unbound under `-u`. B's "spell out the full path" fix (P2R2-4) works; A's (R1-04) needs extra wiring.
5. **Auditing the T1 artifacts is real coverage work.** P2R2-5 found two false containment attributions in the coverage matrix (INF-037 U4 -> Task 7; INF-056 U23 -> Task 3, as the calibrator corrected), which A never checked.

Every point above is genuinely right as far as it goes, and I concede points 2, 3 and 4 below.

## Key strengths claimed (numbered, each with evidence)

1. **plan:48 is a defective check, whatever the outcome rule (X-001).** The orchestrator pre-check shows the command exits 1 on clean input and exits 0 when it prints a violating path: its exit status is the inverse of its pass condition. I re-ran the clean-input shape under `bash -euo pipefail`: exit 1, block aborts. plan:21 says "every line must exit 0", and nothing in the plan exempts bullets from that rule. So an executor or QA pass that runs all acceptance commands under the plan:21 harness gets a false failure on every clean commit. B's reading needs an unstated exemption; A's reading takes plan:21 literally. Either way, a criterion whose exit code says "fail" when it should pass is a correctness defect that needs a fix, not "fix: None" (P2R2-7).
2. **U11 is in the wrong task (U-001, R1-05).** U11 is "`claude --version` fails -> failure before discovery or download" (source.md:296). source.md:101 puts that check in the phase function, "before discovery and acquisition", which Task 5 creates in `install_mcp.py` (plan:104). Yet plan:92 and plan:96 put U11 in Task 4, whose `pytest` gate at plan:96 must pass "with U1-U11 ... present". Task 4 cannot pass U11 without code from Task 5. The calibrator confirmed this, inherited from source.md:466. B did not find it.
3. **`&&` and `! cmd` lines do not gate inside a block (U-003, R1-07).** The orchestrator confirmed that `bash -euo pipefail` keeps running past `false && true` and `! true` mid-block. The affected lines are plan:162 (`sh -n ... && cmp ...`), plan:165 (`grep ... && ! grep ...`), plan:202-203 (`rg -q ... && rg -q ...`) and plan:244 (`grep ... && ! grep ...`). An INTERNALERROR in the hook test run (plan:165), or a missing `SUPERCLAUDE_CODEGRAPH_AUTOINIT=0` doc line (plan:202), passes the block silently. The spec knows this mechanism: source.md:625 says "if-form: set -e ignores a failing `! cmd`", but applies it only to T6. B did not find it.
4. **Task 14 cannot meet its own artifact criterion (X-004, R1-04).** plan:253 requires `./artifacts/t14-final-run.txt` and `./artifacts/t14-new-failures.txt`, but the block at plan:242-250 writes only `/tmp/p2-final-run.txt` and `/tmp/p2-new-failures.txt` and has no copy line. 5. **`./artifacts/` paths go to the wrong folder when run (X-003, R1-04).** Task 16 runs "from the worktree root" (plan:272), and every acceptance block runs from the repo root (both reviewers state this, A-004). From there, `./artifacts/t3-run2.json` (plan:85) is the project-root `artifacts/`, which the user rule says is never staged, while plan:24 requires the package's `artifacts/` to be staged. The result is either a false "file not found" at plan:85 or evidence written where it can never be committed. That is "important", not "minor".
6. **`grep -i connected` passes on a disconnected server (U-005, R1-09).** plan:282 accepts any line containing "connected", which also matches "Disconnected" and "Not connected". The spec's own layer 2 step 5 adds the negative check `grep -iE 'disconnected|not connected|failed'` (source.md:375); T12 (source.md:714) and plan:282 do not. Calibrator: confirmed, inherited.
7. **Smaller confirmed finds B lacks.** R1-08: plan:216 makes `uv run --no-project python -c 'import yaml ...'` primary, but `pyyaml` is a project dependency (orchestrator pre-check), so the fallback form should be primary (source.md:649-651). ## Concessions

1. **R1-07 cites plan:84 wrongly.** plan:84 is a standalone bullet that must "exit 0". Run on its own, `A && B` returns A's failure status, so it gates. The calibrator is right, and the citation should be dropped. The finding stands for plan:162, 165, 202-203 and 244.
2. **R1-06 is overstated.** Task 6's acceptance (plan:123-125) never checks the Ready line; Task 7 owns `codegraph_ready()` (plan:131). This is an ordering ambiguity, not a failing gate.
3. **R1-11 is overstated.** plan:19 includes unrepeated details by reference, plan:223 points Task 13 at §4.2, and source.md:416 carries the fallback.
4. **R1-01's own fix is incomplete.** `test -z "$(...)"` hides a failing `git diff`: I re-ran `bash -euo pipefail -c 'test -z "$(false)"'` and it passes. If `HEAD~1` does not resolve, A's fix passes without checking anything. A sound fix writes the diff to a file as its own gating line, then tests the filtered result.
5. **R1-01's class is wrong.** The guard is plan-added and authorized by source.md:755 and plan:23, so it is an authorized expansion whose command form is defective. It is not drift. The fix is still required.
6. **R1-02 and R1-07 should not be "drift".** Both are copied verbatim from the spec (source.md:710 and :601, 604, 636, 675). A labels other inherited copies "necessary" (R1-05, R1-09), so A is internally inconsistent here. See A-002.
7. **The `$ART` fix is fragile.** A Constraints-level variable is not in scope in separately invoked `bash -euo pipefail` blocks (source.md:445) and would be unbound under `-u`. B's literal path is more robust (C-004).
8. **R1-04 bundles three defects.** B's split (P2R2-3, P2R2-4) is easier to merge, verify and track (S-002, C-002).
9. **R1-03's "necessary" label is the weaker call.** The spec has `E` (source.md:534) and the plan dropped it, which is a divergence the plan made. "Drift, minor" (B) fits better (X-002).
10. **Neither card flagged the user-scope check's exception.** source.md:210 says a user-scope `jq` failure "caused by an entry the retire step reported as kept ... means the user runs the printed command". plan:286 restates that exception only for local scope, so plan:277 can also fail on an intended outcome. Neither A nor B caught this; it should be added to the merge as a new finding.

## Shared assumption responses (A-001, A-002: ACCEPT/REJECT/QUALIFY + reason; A-003 comment)

**A-001 — QUALIFY.** plan:21 says "Every acceptance block runs under `bash -euo pipefail`: every line must exit 0". It does not define "block", and the plan states some bullets by output rather than exit status (plan:45, plan:47 "prints", plan:48 "prints nothing", plan:86). Conditions for the merge:
- (a) A bullet that names its own outcome is judged by that outcome. Under that reading plan:48 meets its "prints nothing" criterion on a clean commit.
- (b) Any harness that runs acceptance commands mechanically under plan:21 (an `sc:implement` QA pass, for example) judges by exit status. Under that reading plan:48 fails falsely on every clean commit, because its exit code is inverted.
- (c) So the merged finding should stay a required fix. Its class is "authorized expansion, defective command form" and its severity is important. The fix makes the pass condition and exit 0 coincide: write `git diff --name-only HEAD~1 HEAD` to a file as its own gating line, then test the filtered output with the `|| true` brace groups. Wrapping the whole pipeline in `test -z "$(...)"` (A's R1-01 fix) is not enough, because it hides a failing `git diff` (re-run: `test -z "$(false)"` passes under `-e`).
- (d) The plan should add one sentence to plan:21 saying whether bullets inherit the exit-0 rule. That closes the ambiguity for every bullet, including plan:107 and plan:86.

**A-002 — REJECT.** Drift means the plan diverged from its source without justification. When the plan copies a spec line verbatim and the defect is in the spec (R1-02 from source.md:710; R1-07 from source.md:601, 604, 636, 675; R1-05 from source.md:466; R1-09 from source.md:714), the plan follows its source. The defect is the spec's, and the fix is a necessary deviation from the spec text, recorded with `origin: spec`. Variant A applied this correctly to R1-05 and R1-09 but not to R1-02 and R1-07, so its labels need correcting. Variant B's uniform "drift" is consistent but wrong in the same direction. Two exceptions are genuine plan-made divergences and stay outside this rule: plan:48 (plan-added, see A-001) and plan:107 (the plan dropped the spec's `E` definition, so drift).

**A-003 comment (CONTRADICTED by source.md:706).** I agree the shared assumption is contradicted, and both cards, A included, missed it. source.md:706 says T12 has "Files: none in the repository; the outputs go only into the issue-#323 comment". plan:272 writes `./artifacts/t16-live-verify.txt`, and plan:287 requires it to exist. There is also an internal conflict. plan:272 says "Commit point: none in the repository", but plan:24 (and the user rule) says `.dev/tasks/` and its `artifacts/` are always staged. On the post-merge workspace, the t16 file would be an untracked, unstaged package file with no commit to carry it. Classification: drift, minor-to-important. The fix writes the output to `/tmp/p2-t16-live-verify.txt`, pastes it into the G6 comment, and removes the artifact-file clause from plan:287. This also settles C-001 in A's favour: the local-scope report belongs in the G6 comment (plan:286, source.md:211), not in a t16 repository file (P2R2-1's fix).
