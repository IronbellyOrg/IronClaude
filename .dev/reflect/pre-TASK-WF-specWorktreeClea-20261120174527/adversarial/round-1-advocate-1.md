## Weaknesses identified in variant 2

1. **F2 is graded BLOCKING against the spec's own instructions.** The spec tells the implementer to "run the check on a merged and an open pull request" (`source.md:299`) and to reuse the landed check in the build (`source.md:32`, `:159`, `:375`). The helper's header documents "The only write is git fetch of the base branch and refs/pull/<N>/head, which touches objects and FETCH_HEAD only" (`branch-landed.sh:32-33`). Running a spec-mandated helper whose only write is an object fetch into `.git` is not a safety break under the rule (no data lost or exposed, no boundary crossed); it is a Medium note about the recorder's blind spot.
2. **F2 quotes the dry-run invariant without its definition.** `source.md:256` reads "Dry run is the default and changes nothing (the recorded commands contain no removal)". The parenthesis defines "changes nothing" for the test; an object fetch is not a removal. The plan's own constraint bans removal, moving, clearing, terminal close, automation and push (`PLAN:19`), not a fetch. The temp file and `rm -f` at `branch-landed.sh:99` and `:40` are the helper's own `mktemp` in the temp folder, not a file in any worktree.
3. **F3 ignores the normative verb definition.** The spec's verb table defines `archive` as "Runs only the evidence step of section 7 on one worktree: copy, push, check against GitHub" (`source.md:83`). Section 7 step 1 says the step needs the merged pull request and the steps that follow are about `.dev` files (`source.md:186-192`). The patch-and-bundle phrase sits in a "What is not saved" aside (`source.md:214`) with no step, format, folder or test case (none in `source.md:246-271`). The plan's reading that this is not a build requirement is defensible, and it is disclosed (`PLAN:25`, `PLAN:170`), so the grade should be Medium (follow-up candidate: ask the owner), not BLOCKING.
4. **F1 is narrower than the defect.** It covers Tasks 3, 4 and 7 only. It misses Task 2 (`PLAN:49`), Task 5 (`PLAN:85`), Task 11 (`PLAN:161`) and Task 12 (`PLAN:174`), and it does not see the missing collector tests.
5. **F4 is a headline only.** No evidence survived the cut, so it cannot be graded from the card itself; the strength of the point comes from the spec, not from the card.
6. **Self-reported confidence 0.95 is not matched by the grading.** Two of four visible BLOCKING grades do not hold under the grading rule (items 1 to 3 above).

## Shared assumptions (A-001, A-002)

**A-001 (tasks are checked one at a time, so a forward reference is a defect): QUALIFY.** The per-task model is the stated one: every task carries its own "Acceptance criteria" and "Depends on" lines (for example `PLAN:35`, `:43`, `:47`), and `/sc:implement` (the default executor for a workflow plan) runs per-task spec-compliance QA. So a check that cannot be met when its task ends is a real defect (`PLAN:62`, `:73`, `:108`, `:161`, `:174`). But a check that explicitly defers its assertion to a named later task (`PLAN:49`, `:63`, `:76`, `:85`) is a declared deferral and should not count as blocking under the same assumption. C-001 stays BLOCKING on the hard cases alone.

**A-002 (BLOCKING is applied the same way in both cards): QUALIFY.** Variant 1's three grades each name a rule ground and meet it (F2 is covered word for word by the "wrong number in an acceptance check" clause). Variant 2's F1 meets the rule; F4 likely meets "Missing" on the spec's evidence (`source.md:276`); F2 and F3 do not meet it (see Weaknesses 1 to 3) and should be Medium. The FAIL verdict is still safe, because C-001, C-005 and C-006 each block on their own.
