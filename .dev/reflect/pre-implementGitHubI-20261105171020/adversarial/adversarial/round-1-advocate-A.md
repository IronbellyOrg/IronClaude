## Shared assumptions

- **A-002: ACCEPT.** Removing `--dangerously-skip-permissions` from argv is enough for ccsession's own behaviour. A case-insensitive grep of the whole `ccsession-tag` skill for `dangerously-skip|bypassPermissions|defaultMode|skipDangerous|permissions` hits only `ccsession:109` (comment), `ccsession:124` (the assignment the plan replaces), `README.md:341` (prose), `README.md:739`, and `ccsession.env.example:6` (chmod advice). No tier `--settings` payload or other launcher path adds a bypass. A user's own Claude settings are outside ccsession and outside the spec's "no permission-bypass flag" wording.
- **A-004: ACCEPT.** `CCSESSION_PERMISSIONS` stays exported into Claude's environment and a nested `ccsession` inherits it. `ccsession-orca:183` and `:242` unset only `CCSESSION_NAME` and `CCSESSION_ASK_TIMEOUT`, with a comment that these must not leak into a nested Claude; `ccsession` has no unset of the new variable either. A nested launch staying in non-bypass mode is the safe direction, and a bad value cannot be inherited because `ccsession` exits 2 before any `exec` (`ccsession:124`). Untested but harmless. A one-line test is optional, not required.
- **A-007: QUALIFY.** The plan isolates exactly the two files that assert launch flags (Task 1: `test_ccsession_tag.py`; Task 3: `test_ccsession_tiers.py`), which covers a valid `default` exported in a Coder workspace shell. Because the check is global (C-003), a typo'd value would make the unisolated `test_install_ccsession.py:224-238` (`--help`, `**os.environ`, `check=True`) fail with exit 2; a valid `default` would not break that test. So the gap is real only for a bad exported value. Either launch-scope the check (which also resolves C-003) or add `CCSESSION_PERMISSIONS` clearing to that test's env. This is another reason to resolve C-003 by scoping rather than by documentation.
- **A-008: QUALIFY.** True that line 124 runs before the env file (`ccsession:847-849`), so the env file cannot set `CCSESSION_PERMISSIONS`. But the env file is sourced before the six `exec` lines (`:1799-1868`), and `$CC_CLAUDE_FLAGS` is an ordinary shell variable, so an env-file assignment to `CC_CLAUDE_FLAGS` overrides both the default and the opt-in. That is pre-existing behaviour and `ccsession.env.example` does not document it (grep finds no `CC_CLAUDE_FLAGS` there). The consequence for the plan is wording: Task 7 says the file "is read after the launch flags are chosen", which is imprecise because the file can still change the flags through `CC_CLAUDE_FLAGS`. Reword it to say the variable is read before this file is sourced, and keep the claim limited to `CCSESSION_PERMISSIONS`.
