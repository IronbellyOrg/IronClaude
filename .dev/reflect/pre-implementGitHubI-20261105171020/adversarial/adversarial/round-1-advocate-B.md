## Shared assumptions

**A-002 — removing `--dangerously-skip-permissions` from argv suffices; no other ccsession-controlled source re-enables the bypass. ACCEPT.** My grep over `src/superclaude/skills/ccsession-tag` for `bypassPermissions` / `defaultMode` / `dangerously-skip` returns only `ccsession:109` (the header comment) and `ccsession:124` (the assignment being replaced), plus a README mention. The tier `--settings` payload is built solely from `modelSettings.<model>.autoCompactWindow` (`models.py:707-712`, attached to launch args at `ccsession:1175-1179`), so it carries no permission mode. A user's own Claude settings are outside ccsession's control and outside the spec's "adds no permission-bypass flag" wording (`source.md:1`) — the assumption holds within that boundary.

**A-004 — `CCSESSION_PERMISSIONS` staying exported into Claude's environment is harmless. QUALIFY.** Nothing in the plan unsets it: Task 4 edits only the flag-default block (PLAN:73-84), and the codebase precedent of unsetting inherited session variables (`ccsession-orca:242` unsets `CCSESSION_NAME CCSESSION_ASK_TIMEOUT`) is not extended. For nested `ccsession` launches inheritance is probably the intent (the inner launch stays non-bypass), but the plan never states it and no test pins it; with a *bad* value the question cannot arise (the launch exits 2 first). Accept only if the corrected plan adds one Constraints sentence stating the variable is deliberately inherited, or deletes it before the six `exec` lines if not.

**A-007 — clearing the variable in the two test files' fixtures isolates the suite. REJECT.** The check is global (the `case` replaces the line-124 assignment, which executes before the dispatch at `ccsession:1671-1703`), so per-file autouse fixtures cannot protect tests that invoke ccsession with an inherited environment: `tests/unit/test_install_ccsession.py:227-238` runs `ccsession --help` with `env={**os.environ, ...}` and `check=True` — a developer shell exporting a bad value makes it exit 2 and the test raises CalledProcessError; the same file's lines 276-277 and 302-303 pass `**os.environ` with `check=True` as well, and ccsession is invoked from other unisolated files (per the diff analysis: `test_cli_install.py`, `test_cli_doctor.py`, `tests/cli/test_install_hooks.py`). The corrected plan should clear `CCSESSION_PERMISSIONS` (and ideally `CC_CLAUDE_FLAGS`) in a shared conftest or in every file that inherits the environment. Neither card raised this beyond Task 3's `CC_CLAUDE_FLAGS`.

**A-008 — line 124 fixes the final flag string; the env file cannot change the outcome. QUALIFY.** True for `CCSESSION_PERMISSIONS` itself: the case has run and chosen `_cc_default_flags` (or exited 2) before `ccsession:847-849` sources `~/.claude/ccsession.env`, so the file cannot flip the permission mode. But the env file *can* still change the outcome through `CC_CLAUDE_FLAGS`, which the sourced file may assign: a non-empty value there overrides both the old and new defaults (pre-existing behaviour, consistent with PLAN:20), and an env-file `CC_CLAUDE_FLAGS=""` produces empty flags — contradicting the plan's "an empty value still takes the default" phrasing when the emptiness arrives via the file rather than the shell. Tasks 5-7 document only the `CCSESSION_PERMISSIONS` limitation (PLAN:97, 111, 121). Accept the assumption for the variable it names; the corrected plan should either state the `CC_CLAUDE_FLAGS`-via-env-file caveat or fold it into the same U-005 test.
