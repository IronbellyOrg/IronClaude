## 4. The risk V1 raised and left unverified: record lines with `link="no payload"`

Claim: with `QUESTION_LINK_PASSED = True`, a payload-less row gets `link="no payload"` and Task 6 appends ` | dispatchId=unknown | link=no payload` to every record question line. Verified true by the plan text and export.py:101 (`f"{q.qid} | {q.text}"` is the line Task 6 extends), and by real traffic: release-gates.md:60 says 2 of the 41 questions carry no payload, and `make_question_rows` builds `"payload": None` (conftest.py:266), so every synthetic row takes this path.

Does any existing test in tests/observe assert on exact record question lines in a way that would change? **No.** The search covered every `record_text` use, every `reason unknown` assertion, every `QuestionLine(`/`Question(` construction and every test that reaches the link-on path:

- Only the command-level tests can reach a link-on collector, because `Collector(...)` defaults to `link=False` everywhere else (test_export.py:264, :303; test_golden_contract.py:405-410; test_render.py:427; test_question_cap.py:45; test_snapshot_schema.py:430; test_collector.py:487, :663; test_view.py:913). With link off, `q.link == ""`, no suffix, no change.
- The command-level tests are test_commands.py:652-674 and :677-690, and only after the C-001 fix wires `run_once`. Their question-line assertions are `"COORDINATOR QUESTIONS" in lines` and `f"one Run only: {QRUN}" in lines` (:670, whole-line matches of the title and run line, which get no suffix), `sum("reason unknown" in l for l in lines) == 4` (:671, a substring count; the suffix goes after the text, so the count stays 4) and the exact counts line (:673, not a question line). The width check at :689 is on the screen, which does not use the record suffix.
- test_export.py:278 counts lines with `" | "` and `"reason unknown"` (still 3, and it runs with link off). test_golden_contract.py:432 and test_render.py:453-669 count `reason unknown` on screens built from `q.text`/`screen_text`; for a row with no `ask`, Task 4 defines `screen_text` as the subject form, byte-identical to `text`. test_view.py:943 asserts `q.text.endswith("reason unknown")` on `QuestionLine.text`, which Task 4 keeps as the subject form.
- No test asserts `endswith` on a record line or compares a whole question record line.

One existing test does change, and the plan already covers it: test_parse.py:589 asserts the parsed `Question` has no attribute `dispatch_id`; Task 2 adds that field and its AC rewrites that test (plan line 54). No other existing test constructs a `Question` or `QuestionLine` positionally (test_questions.py:25 uses keywords; view.py:683 and parse.py:524 are the only source constructions), so the new defaulted fields break nothing.

Conclusion: the risk is real as behaviour (every link-on record line gains the suffix, including payload-less rows) but it is the stated intent of Task 6 ("the record ... contains the dispatch id and the link state of every question"), and it breaks no existing test. Residual MEDIUM-level advice for the merge, not a new finding: add one assertion that a payload-less row yields `dispatchId=unknown | link=no payload` in the record, so the suffix on those rows is pinned rather than incidental.
