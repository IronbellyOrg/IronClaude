## 1. Recommended option, and agreement with the spec

**Recommended: option (a), amended.** `/sc:pr-submit` does not run as an Orca worker and gets no `--unattended` mode and no Phase 4 changes. Each PR's run happens in one ordinary top-level Claude session that stands in that PR's own child worktree, and it starts only when the person's own instruction names that PR. The carrier is the coordinator's own session once a check shows it can stand in that worktree for the whole loop; until then it is a session opened in the child worktree, either by the person or launched for the person by the coordinator (the debate's third option, (c), usable only after a smoke test). Several PRs at once means several such sessions, one per PR, and only when the person names them. Option (b), a worker per PR, is deferred, not rejected.

## 3. The "attended, in-session" check (is option b viable?)

The git-ownership debate left one question open: does a chat-mode Orca worker count as the "attended, in-session" run that pr-submit requires (`decisions/git-ownership/debate/adversarial/round2-advocate-c.md:75`)? Checked against the current skill and command (the installed `~/.claude/` copies are byte-identical to `src/`, `diff -q`, 2026-11-02):

- **What "attended" means in pr-submit's own text.** "The monitor is an **attended, in-session** loop: closing the session loses it. Durability comes from the write-ahead JSONL run-log + `--resume`, never from detachment. This skill cannot survive its own session" (`src/superclaude/skills/sc-pr-submit-protocol/SKILL.md:43-45`). The forbidden cases are "a background shell, detached loop, or subagent" (`SKILL.md:82-84`) and "Run headless / detached, or imply a background daemon" (`SKILL.md:303`; `src/superclaude/commands/pr-submit.md:85`). It must run "in the main orchestrating session", never inside an Agent-tool subagent (`SKILL.md:47-49`).
- **Nothing requires a person to watch at monitor 2 or 3.** "There is no interactive confirmation before a push (Wave 6 has no confirm step): the `push_decision` record + the `--monitor 3` arming ... is the recorded authorization" (`src/superclaude/skills/sc-pr-submit-protocol/refs/state-machine.md:170-172`); `CLAUDE.md:50` says the same ("pushes the fixes without asking"). At monitor 2 the run applies and validates fixes and then halts before any push, with no question (`SKILL.md:273`). HALTs end the run and leave recovery text to read afterwards (`SKILL.md:316-318`). This is a reading of the skill text; no unwatched run was observed. The one person-facing step is at monitor 1, which ends on a "fix these? y/n" proposal (`SKILL.md:272`); the spec already refuses monitor 1 under `--unattended` (`.dev/orca-command-refactor/specs/orca-worker-contract-spec.md:56`).
- **A terminal Orca worker meets that text.** It is a top-level Claude session in its own terminal (`.dev/orca-command-refactor/inventory/orca-capabilities.md:161`; `orca-ide orchestration worker-start --help` line 38), which is what the debate concluded unanimously (X-001, 95%, `decisions/D3/debate/adversarial/debate-transcript.md:598`).
- **A chat-surface worker is UNVERIFIED.** Orca starts a worker as a chat or a terminal according to the person's own setting, and "Not every worker has a terminal" (`worker-start --help` lines 42 and 44); a launch reports `outcome.kind` `structured` (a chat) or `terminal` (`orca-ide skills get orca-cli` line 47). No source read here shows whether a chat-surface Claude session has the Skill and Task tools and can hold foreground Bash waits for the length of a poll. The same question applies to the recommended route's launched tabs, because `agent launch` follows the same setting (`orca-cli` line 63), so it does not separate (b) from the recommended route; the recommended route answers it with a smoke test on the person's actual setting (section 5, AC-4.4).

**Verdict:** the "attended" rule does not rule (b) out; a terminal worker satisfies it, and a chat worker is UNVERIFIED. (b) stays deferred for its other costs, not for this one: under D4's recommendation, option (c′), no brief can authorize a worker to push (`decisions/D4/RECOMMENDATION.md:77`), so a pr-submit worker could run only below monitor 3, which conflicts with the repo's monitor-3 rule (`CLAUDE.md:50`; `HWW:223`: "disclose the policy conflict and withhold execution"); it needs the Phase 4 build and AC-4.3 (`SPEC:185`, `SPEC:276`); and its HALTs become blocked contracts one hop from the person (`SPEC:67`, `SPEC:137`).

## 4. What this means in practice

**What a person sees and does.**
- When the background helpers finish a change, the main assistant does not open the pull request on its own. It tells you the change is ready, which branch and folder it is in, and the exact command to open and watch the pull request.
- If you say "open the PR for this one", the work is prepared first: the changes are saved, brought up to date with the main branch and sent to GitHub, with your approval. Then the pull request is opened and watched in one window that belongs to that pull request.
- That window shows the review loop as it runs: it waits for the automated reviewers, fixes what they confirm (only real problems, not style notes), sends the fix, answers the reviewer and tries again, at most twice. If it gets stuck or reaches the limit, it stops and tells you in that window what to do next. You decide.
- If you have several pull requests and ask for them all at once, you get one window per pull request. The main assistant opens them for you and then stops watching; you check each window. It does not report back when they finish.
- Until a short test proves the main assistant can open those windows correctly on your setup (chat or terminal style), you open the window yourself in that pull request's folder and type the command it gave you.
- Later, if a check shows the main assistant's own conversation can work inside that pull request's folder for the whole review, it may run the review loop itself in your conversation instead of a separate window. That check has not been done.

**What changes from today.** Today you, or the main assistant, simply run the pull-request command where you are. After this decision every pull request gets its own folder, and the command runs from a window in that folder. Nothing in the pull-request command itself changes.

**What could go wrong.**
- Two windows watching the same pull request could each send changes and confuse the review. The rule is one window per pull request; the main assistant checks for an existing one before opening another, but it cannot yet reliably see whether you opened one by hand (UNVERIFIED).
- Closing a window stops the watching. It can be restarted from the record it keeps, but only if that pull request's folder has not been deleted, so folders are kept until the pull request is merged or closed.
- If the branch was not sent to GitHub first, the pull request cannot be opened; if it was sent and then brought up to date afterwards, the command stops with instructions that need a manual fix (section 6, D4 row). The preparation steps, in their fixed order, exist to prevent both.
- Nobody tracks the parallel windows for you. If you forget one, it may sit stopped until you look.
- In one rare case (a reviewer refuses a very large change), the command can make one extra fix beyond the two-round limit; this is reported to you as an exception.

**Cost to change later.** Low. Nothing in the pull-request command is built or changed now, so switching later to option (b), helpers that watch pull requests and report back, costs the same then as now: the Phase 4 build, one acceptance test on a scratch pull request, and a change to the separate decision that today forbids helpers from pushing (D4). Dropping the window-opening route later is one sentence. The real cost sits elsewhere: the worktree-per-pull-request rule (CR-01) and the git-ownership wording must be settled together with this one (section 6).
