## 1. Recommended option and confidence
**Recommended: option E, the hybrid, as merged in `ADV/merged-output.md`.** In one line: the coordinator owns every push, PR, review reply, issue or status comment, merge and worktree removal; a worker may make local commits only in its own child worktree and only when its brief quotes the user's instruction granting them; nobody else writes git state.

The rule set, in short:
1. **Outward actions** (push, PR, review replies, issue and status comments, remote branch deletion) belong to the coordinator in its main chat, only when the user's instruction names the action, always against `IronbellyOrg/IronClaude`, PRs only through `/sc:pr-submit --monitor 3` (`CLAUDE.md:41-53`). The coordinator runs pr-submit only from the PR-head checkout with no other writer there for the whole loop, because pr-submit binds to the checkout it runs in and has no path flag (`pr-submit/SKILL.md:268,316`; `src/superclaude/commands/pr-submit.md:8`).
2. **One exception, opt-in only:** under D3 (b), one pr-submit worker per PR in that PR's own child worktree, when the user asks for parallel PR monitoring and only after a test shows an Orca worker counts as attended (`pr-submit/SKILL.md:303`; UNVERIFIED today).
3. **Worktrees** are created by Orca at Orca's default paths, never under `.dev/worktrees/`: one feature worktree where the coordinator runs, plus a child worktree (`worker-start --worktree new-child --base-branch <feature branch>`) only when a trigger applies: the worker may commit, runs `/sc:implement` beside any other writer, runs pr-submit, is a parallel experiment, or writes the user index (CR-01 T1-T4 plus one trigger, `CR01:16-20`).
4. **Coordinator commits and merges in a shared worktree** happen only when no worker runs there, with explicit paths, `git commit --only -- <paths>`, a `git status --porcelain` cross-check, and stop-and-report on any hook failure (`pr-submit/SKILL.md:274` uses the same `--only` guard).
5. **Worker local commits** are off by default (`EVAL:74`): allowed only with a quoted, scoped grant, as the sole writer of its child worktree, for `/sc:implement` only between tasks (`implement/refs/retry.md:41`) and dormant until #326's per-task commit step (K3, `EVAL:63`) exists.
6. **Everything else:** under `--unattended` a worker never runs `git add` (including `.dev/tasks`), never commits, never moves HEAD and never touches a remote, except `/sc:implement`'s own private-index snapshots, refs and revert (`implement/SKILL.md:111,113`; `implement/refs/retry.md:220`).

**Confidence: 75% (moderate).** For: all five advocates converged on E (24 of 25 diff points, 96%, `ADV/debate-transcript.md:1319-1322`), and E won the base selection on the level-1 tiebreaker (`ADV/base-selection.md`, Combined Scoring). Against: the debate ended `BLOCKED_BY_INVARIANTS` with five HIGH gaps (`ADV/debate-transcript.md:1277-1282`). The merge closes all five on paper, but two of those fixes need the user's decision (narrowing D4; deferring `.dev/tasks` staging in worker sessions), and the central hazard (implement's revert deleting other writers' files) is derived from protocol text, not observed in a run (`implement/refs/managed-workspace.md:85`).

**Single biggest risk:** every rule above is prose that each session's model must obey. Nothing mechanical stops a worker from running `git add`, `git commit` or `git push`: the guard is optional and off by default, and the audit of git and GitHub write commands in the installed skills (INV-032) has not been run, so the "workers write no git state" rule is not yet shown to hold.

## 2. Strongest losing argument
**Option A: the coordinator runs every git and GitHub action itself.** It is the strongest loser and it actually scored highest before the tiebreaker: combined 0.904 against E's 0.898 (`ADV/base-selection.md`, Combined Scoring), with equal qualitative scores (25/30). Its case, at its strongest:
- **One writer per index.** Git refuses a second writer outright (`index.lock`, `ADV/variant-1-original.md:11`), so with one git actor lock collisions cannot happen.
- **Direct authorization.** The person talks to the coordinator, so the session that hears "commit" is the one that commits; no brief can lose or widen the instruction (`ADV/variant-1-original.md:17`).
- **Cheapest.** No command changes; spec wording only (`ADV/variant-1-original.md:37`).
- **E's worker lane is mostly dormant.** `/sc:implement` per-task commits need #326 K3, which does not exist, so E's distinctive feature cannot run for implement today (`EVAL:63`; E conceded this, `ADV/round2-advocate-e.md:13`).

Why it lost: (1) A's founding claim, "workers never run a mutating git command", is false: `/sc:implement` writes refs, builds a private index and restores or deletes files on revert (`implement/SKILL.md:111,113`; `implement/refs/retry.md:220`). (2) A worker commit lane already exists today: `/sc:task` executes `commit` and `push` as EXEMPT steps, and the spec only says "refused unless authorized" (`SPEC:144`); A gives that lane no guard, E does. (3) #326 asks for per-task commits and per-experiment branches (`EVAL:51-52`); A can never serve them. (4) E won 15 of 25 diff points alone against A's 4 (`ADV/debate-transcript.md:1317`).

What A keeps: with no commit grant in any brief, E behaves exactly as A (`ADV/invariant-probe.md:27`, INV-019). A is E's default.

## 3. What this means in practice
- **You talk to one session, and that session does everything that leaves your machine.** Pushing code, opening a pull request, replying to reviewers and posting comments all happen in the coordinator's chat, the one you type into, and only when you have asked for that specific thing. Pull requests always go to your own copy of the project (`IronbellyOrg/IronClaude`), never to the public SuperClaude project.
- **Helpers do the work but do not save it to history by default.** The helper sessions Orca starts (workers) write files and reports. They do not commit, push or post. The coordinator reads what they did and commits it for you when you ask.
- **Each feature gets its own folder, and risky work gets a side folder.** Orca creates one working folder (a worktree) per feature, in its usual place. A helper gets its own side folder only when it would otherwise get in others' way: when you let it commit, when it runs the plan executor next to other people's edits (that executor can undo files it did not write when a task fails), when it runs the pull-request reviewer loop, or when it is one of several competing attempts. Helpers that only write a report share the feature folder.
- **If you want commits as the work goes, say so.** For example: "run the plan in its own folder and commit after each task". Then that one helper may make local commits in its own side folder, for that run only. It still never pushes. You can withdraw the permission; the helper sees that before its next commit. Per-task commits inside the plan executor (`/sc:implement`) wait until that command gains a commit step (issue #326).
- **Side folders are merged back and cleaned up by the coordinator.** When a helper's result is accepted, the coordinator merges its branch into the feature branch, then deletes the side folder and branch. It never deletes anything that still holds unsaved work, an open pull request, or a report it has not read, unless you say so.
- **Watching several pull requests at once is optional.** By default the coordinator handles one pull request at a time in its own chat. If you ask to monitor several in parallel, each gets its own helper and side folder; this stays switched off until a test shows such a helper meets the reviewer loop's "a person is present" rule.
- **What can still go wrong.** These are rules the AI sessions follow, not locks. Until the planned scan of every command for git and GitHub write steps has run, and the optional blocking guard is tested, a helper that ignores a rule is caught only by the coordinator's review afterwards. Local commits are reversible; pushes are not, which is why only the coordinator pushes.
