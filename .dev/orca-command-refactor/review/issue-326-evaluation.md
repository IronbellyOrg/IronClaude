F4 also cites rule 10, which exists only on master.
2. **Revise the spec once, applying FDR-D1 to FDR-D7 (the current review is FAIL, `FDR:109`) together with F0-F5.** F2 and FDR-D3 touch the same 7.2 worktree setup, so they are cheapest fixed together. Then run the spec's normal fresh-context review.
3. **Get the user's answer to D4 (with F4's and F5's added clauses) and to the F0/F1 local-commit authorization before #326 designs its relay.** Those answers decide whether a worker may run any git or GitHub action, which is the core of #326's Phase 2-P.
4. **#326 Phase 1-P (structural refactor of `/sc:git`) can run in parallel with spec P0-P1**, because no spec phase edits `cmd/git.md` (it is coordinator-only, `SPEC:156`). Re-plan it first per S1-S9: `/sc:workflow ... --depth standard --handoff none`, then `/sc:implement`, each as a top-level session or Orca worker, not as nested subagents.
5. **#326 Phase 2-P/3-P (git and GitHub behaviour inside other commands) waits until spec P2 has landed for the commands it touches, and until P4 for implement, post-release and pr-submit.** Both efforts edit the same command and skill files; the spec's P1-P3 edits must be additive and are checked for zero deleted lines per file (SA-4, AC-C5, `SPEC:172`, `SPEC:229-232`), so concurrent #326 edits to those files would fail that check or be mixed into it.
6. **#326's per-task-commit feature (K3) lands after spec P4**, because both change `sc-implement-protocol` and the retry-ladder constraint in F1 must already be in the spec.
7. **Sub-modules (K1) and post-merge branch deletion (K4) have no ordering constraint** against the spec; schedule them by #326's own priority.
