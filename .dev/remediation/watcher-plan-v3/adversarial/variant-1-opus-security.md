## Q-3 Does a field change or a label move updatedAt (BLOCKING, decision)
- **Change.** Read per-field times as well as the item time. Today `PROJECT_ITEMS_QUERY` asks the Status value for `name` only (github.py:95-97). Task 3 changes it to alias `status: fieldValueByName(name: "Status")` and `pipeline: fieldValueByName(name: "Pipeline")`, each `... on ProjectV2ItemFieldSingleSelectValue { name createdAt updatedAt }`, plus the item's `updatedAt`. The Task 4 rule voids an approval when the latest of these times is at or after `approved_at`, and also when any of them is unreadable. Public query examples request `createdAt` and `updatedAt` on that type (GitHub community discussion 102740), but this is not verified here. Task 3's read-only introspection therefore also lists the `ProjectV2ItemFieldSingleSelectValue` fields. Task 3 adds an owner-run observation on a test issue, recorded in `./artifacts/t3-updatedat-observation.md`: change the Pipeline, note the item time and the field time; then apply the approval label and note whether the item time moved. If the label moves the item time, drop the item time and keep only the field times. If no field time moves when a field changes, return R31 to the owner (level-specific label).
- **Files.** `github.py`, the `ProjectItem` dataclass at predicates.py:113-118, `_project_item`; the shape fixture `tests/issue_watch/fixtures/_assumed_shape/graphql_project_items.json`; plan:55, plan:58 and plan:65.
- **Risks.** When Pipeline is cleared there is no value object to read a time from, so the field reads as None. That moves the level down, which is the safe direction. Timestamps have one-second resolution, so a change in the same second as the approval voids it; that fails closed.
- **Tests.** Fixtures where the item time is early but the field time is late give a refusal, and the reverse also refuses. With all times early the issue passes. A missing field time refuses.
- **Rejected.** The item `updatedAt` alone: whether a field change moves it, and whether a label leaves it alone, are both unverified, and either error flips the rule (fail-open or void-all).

## Residual risks
- The guard is text-only (guard:774-775). /sc:pr-submit's own GitHub writes already go through scripts the guard never reads (`reply-resolve-thread.sh:131`). So, by inference, an agent at any level could write a script that posts a comment or applies a label. Only credential separation closes this: launched agents and workers would hold a token with no issues or projects write. That is a Coder row.
- The ungoverned claim session reads untrusted issue text under the approver login. Q-1 part B limits what a prompt injection there can approve; it does not limit comments.
- Q-1 part B forces the owner either to approve from a second login or to use a dedicated launch login (an owner decision).
- R31 stays unverified until the owner runs the Q-3 observation. Until Q-2's observations pass, only Pipeline None launches, even though Task 17 enables repos automatically.
