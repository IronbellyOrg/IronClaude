## Follow-up candidates (Medium and minor, none blocking)

**F2 (Medium, MAJOR label): the launcher spec exports the three variables for everyone in tier mode.**
- Task 9 says the exports run whenever tier mode is on. The launcher already limits who may use which tier: `user_access` in models.py, and `test_named_tier_checks_definition_and_owner`. The default rule for ordinary users is `*=tier2:tier2,tier3,tier4`.
- A launcher built as written would route `model: opus` and `model: sonnet` agents to tier1a and tier1b for owners who may not use them.
- The document never states this condition, so it is Medium. The spec should export each variable only for a tier that is defined and that the owner may use, and the Task 6 and Task 3 wording should say so.

**F3 (Medium, MAJOR label): the tier-id allow-list has no way to absorb other legitimate hits.**
- The Python constants test gets a residual allow-list. The `claude-gw-tier` text test does not; its allow-list is fixed at the three workers, sc-issue-protocol and ccsession-tag.
- The repo I reviewed has `src/superclaude/cli/review/data/review-tiers.default.json` and `review-panel.live7.json`, both containing `claude-gw-tier`. They fall under the scanned `cli` directory and match no allow-list entry.
- If those files exist at the plan's base, the test fails on the unchanged tree. That breaks the "remaining tests pass" criterion in Task 1 and the criterion in Task 2.
- I could not confirm they exist at the base, so this stays Medium. Add a residual allow-list for the tier-text test too.

**F4 (minor): "outside one nothing is set" is not true for a non-tier launch in a Coder workspace.**
- Task 6 says nothing is set outside a tier workspace, while the same task says the defaults file exports real ids today.
- Task 9 itself says a non-tier launch "leaves the inherited environment untouched". In that case the inherited exports still decide what the aliases mean.
- Reword to "the launcher sets nothing; inherited values apply".

**F5 (minor): Task 6 and Task 1 can be read to want different text.**
- Task 1's test needs the literal strings `ANTHROPIC_DEFAULT_OPUS_MODEL=claude-gw-tier1a` and the other two. Task 6 describes a mapping table ("opus to claude-gw-tier1a via ANTHROPIC_DEFAULT_OPUS_MODEL") and asks for the exports "spelled exactly as in the mapping table".
- A table with separate columns would fail the test. Say that the page must also contain the three `NAME=id` lines.

**F6 (minor): the scratch copy of the tier test breaks its own path setup.**
- The module sets `REPO_ROOT = Path(__file__).resolve().parents[2]` and derives `SKILL_DIR` from it. A copy under ./artifacts/t9-scratch/ resolves the wrong root.
- The red run would then fail on a missing launcher, not on an AssertionError, which Task 9 forbids.
- Task 9 should tell the implementer to set `REPO_ROOT` explicitly in the scratch module.

**F7 (minor): Task 5's notes pin values from a file that changes.**
- The note quotes defaults.sh values as fact. The file is versioned (now 20261112-1), and the Tier 3 value has already changed once (CHANGELOG.md in /etc/aidev02/aienv.d/).
- The notes should record the file version or observation date, or the effect description may be false when read later.

**F8 (minor): a positional reading of the worker pins is wrong.**
- Task 1 lists the three files without order and the values as tier3, tier2, tier1a, while the constraints list the files as t1, t2, t3.
- Pairing them by position gives t1 to tier3, which is wrong. Name the pairs (t1 to tier1a, t2 to tier2, t3 to tier3).

**F1 (minor): the first constraint contradicts the tasks if read literally.**
- "Edit under src/ only" conflicts with tasks that create or edit files under tests/, docs/, plugins/ and .dev/. The next sentence shows the real intent, which is not to edit `.claude/` copies.
- Reword to "do not edit .claude/".
