## Medium findings (follow-up candidates, not blocking)

- An implementer who follows the spec builds three exports that run whenever tier mode is on. That is wrong for an owner who may not use tier1a or tier1b.
- `models.py` has `user_access` and `in_my_tiers`, and the shipped defaults let ordinary members use only tiers 2, 2b, 3 and 4. For them, `opus` and `sonnet` would point at tiers they cannot use, and most agents use those two aliases.
- The current launcher (lines 896-898) already gates each export on the owner's usable tiers.
- Not blocking because the source decision states the exports unconditionally. The document also never states an owner-access requirement, so this is a requirement gap. It is a missing requirement, not a stated text that does harm.

**F2 (Task 9): copying the test module into `./artifacts/t9-scratch/` breaks its paths.**
- The module sets `REPO_ROOT = Path(__file__).resolve().parents[2]` and then does `sys.path.insert` and `import models`. Copied verbatim into `.dev/tasks/.../artifacts/t9-scratch/`, `parents[2]` is the package folder, not the repo.
- The result is a `ModuleNotFoundError` at collection, which the AC explicitly rules out ("not a KeyError and not an import error").
- The text never says to repoint `REPO_ROOT`. Medium because a competent implementer would see the error and fix it.

**F3 (Task 1): the `claude-gw-tier` scan skips most of the Python package.**
- The source asks to scan "Python" for picker ids. The test scans only `agents`, `commands`, `skills`, `cli`, `hooks` and `core`.

- No hit exists today. The guard has a hole the source asked to close.
