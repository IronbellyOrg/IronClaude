## Findings

### F1 (MAJOR, blocking, unpassable-check): Task 10's third acceptance criterion cannot pass against the file the plan itself produces

Grading check: "An implementer who follows the stated text as written builds the design doc with all of Task 10's stated edits and the claim-mode lookup `gh api user -q .login` still in it, and that file is wrong because the acceptance criterion 'Every `gh api` path in the file spells `repos/<R>/...` except the one documented `orgs/<owner of R>/issue-fields` read' cannot pass: `user` is a `gh api` path (the skill's own call rule in `SKILL.md` line 73 lists `user` as an allowed path) that spells neither `repos/<R>/...` nor the allowed `orgs/` read."

This holds with no further assumption. Verified: `docs/designs/sc-issue-command.md` line 157 contains `gh api user -q .login` (the claim-mode login lookup, pre-existing). Task 10's edit list (the grep-for-"label" places, section 11, flags table, B7, acceptance line 6) touches nothing that removes or rewrites that line, and no other task edits the design doc. The sibling rules the plan writes into `SKILL.md` (line 73) and `refs/create.md` (line 9) both explicitly allow `user`; the Task 10 criterion simply dropped that allowance. An implementer or QA checking the criterion mechanically (grep `gh api` in the file) gets a failure that the plan's own edits cannot fix without changing claim-mode behavior the plan never authorized.

Fix: add "or `user`" (matching the SKILL.md rule) to that acceptance criterion, or scope it to the paths Task 10 actually rewrites.

### F2 (MAJOR, blocking=false, Medium under follow-up candidates): "writes exactly two things" contradicts the mode label the same document applies

The Constraints say the skill "writes exactly two things to a created issue besides the issue itself: the issue type ... and the Complexity field value", while the Goal and Tasks 1, 2, 4 and 6 all apply the mode label through `--label` on `gh issue create`, a third write to the created issue. Grading check fails to be blocking: the sentence only does harm if the implementer picks the literal reading and drops `--label`, which would contradict four explicit tasks; the document as a whole admits one coherent reading (the sentence counts the two new classification writes). Needs the charitable reading, so Medium.

### F3 (MAJOR, blocking=false, Medium under follow-up candidates): no reason value for a failed label lookup

Wave 1 defines `lookup failed: <reason>` as a recorded, non-fatal outcome for every lookup, and the type and field output lines both carry a `lookup failed` reason. The label output line has exactly one reason, `label missing in repo`. When `gh label list` itself fails, the plan never states what the label line says; the only specified behavior reports "missing in repo", which is false (the state is unknown, not absent). A requirement the document never states, so Medium, not blocking.

### F4 (MINOR, note): base commit reference does not resolve

The constraints cite "the issue analysis on commit `1aa2e5c3`"; that object does not exist in this repository (`git cat-file -t 1aa2e5c3` fails; history is one squashed commit). The plan's own "re-read the live file before each edit" rule makes the line numbers advisory, so this is a note.

### F5 (MINOR, note): case mismatch inside the flags row

Task 4 keeps the depth rule text ("quick = simple, standard = medium, deep = complex", lowercase) next to the new capitalized values `<Simple | Medium | Complex>`. `refs/labels.md` matches option names case-insensitively, so no wrong outcome; cosmetic only.
