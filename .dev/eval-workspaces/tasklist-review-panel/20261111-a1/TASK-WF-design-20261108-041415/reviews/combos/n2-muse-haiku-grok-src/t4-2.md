## Findings

### F1, blocking. The write limit contradicts the create sequence.

Grading check: An implementer who follows the stated text as written builds a create path whose only writes to the new issue are `gh issue create --type` and one Complexity POST, and that path is wrong because the goal and Task 2 also require the mode label and the pushback comment.

The constraint says the skill writes exactly two things to a created issue besides the issue itself: the issue type, through `gh issue create --type`, and the Complexity field, through one POST. Task 2 tells the same implementer to follow specification 2.1: apply the mode label, pass `--type` when the type is listed, create the issue, read the type back, POST the field, then post the pushback comment. Specification 2.1 keeps a STOP code for that comment (`E-POST-FAILED`). The goal says create mode applies the mode label (`bug` or `enhancement`).

Those texts cannot all be true. The live create path puts the label on `gh issue create --label` and posts the comment with `gh issue comment` when a standard or deep check disagrees. Both are writes to the issue beyond the two the constraint names. Obeying the constraint drops the label the goal requires, or drops the comment whose failure is still specified as STOP. Obeying Task 2 breaks the constraint.

### F2, Medium. The `--mode` cell names only Feature or Bug.

Task 6 sets the `--mode` meaning to "the Feature or Bug issue type". Task 1 and source Q7 say a feature whose area is `tests` gets Test, not Feature. The constraint lists three defaults the owner may reverse: the `orgs/` read, keeping `--type`, and keeping the mode labels. Source section 3.4 says the same three (Q4, Q5, Q6). Q7, feature plus area `tests` gives Test, is the rule, not a default. Task 12 tells the owner check to list four reversible defaults, including "area `tests` giving Test". The skill tasks and the label rule still require Test. The note would tell the owner they may drop it.

### F4, Medium. Field read-back does not say what `value` is.

Specification 2.1 and Task 1 say to read `issue-field-values` and treat the field as not set when "the value" is absent. They never say that, for a single-select field, `value` is an option id. The live `refs/labels.md` section "Field read-back shape", and `test_field_readback_uses_the_field_id_and_option_name_not_numeric_value`, require comparing `single_select_option.name` and forbid comparing the numeric `value` to Simple, Medium, or Complex. An implementer who compares `value` to the option name reports `not applied after create` on a successful write. The plan marks the POST unverified and does not carry this check. Task 1's "must contain" list does not include it. Keeping the live paragraph is allowed, but the plan never requires it.
