## Findings by area

### Requirements and testability (Wiegers, Crispin)

**F1: Medium (MAJOR, not blocking).** Task 8's acceptance line says reverting any one of Tasks 1 to 5 turns a new test red. No listed new test asserts on text that Task 3 adds to `SKILL.md`.
- Test 2 only says an `orgs/` path "appears only in" three files, which is a subset check.
- Test 3 is satisfied by `create.md` and `labels.md` alone.
- The only test that goes red on a Task 3 revert is the Task 7 updated test, which is not a new test.
- Reading the criterion strictly, an implementer who writes exactly the six listed tests builds a suite where it cannot pass.
- I rate this Medium, not blocking, because it needs a guess that the implementer extends test 2 or 3 to require `SKILL.md`.

**F2: Medium (MAJOR, not blocking).** No step says when `not set: field Complexity <value>: option not found` is printed.
- Task 1 requires "every reason listed in specification 2.4", which includes `option not found`.
- Task 2 tells the implementer to follow the 2.1 sequence. That sequence only covers "field missing in the scout" (`field not found in org`).
- When the field exists but has no option matching Simple, Medium or Complex, the implementer may print the wrong reason or nothing.
- This is a requirement the document never states, so it is Medium.

**F3: Medium (MAJOR, not blocking).** The read-back of the field value does not say how to decide that the value is present.
- Task 1 says only "read-back with `gh api repos/<R>/issues/<N>/issue-field-values`".
- The plan sends the option name in the POST. The GET response may identify a single-select value by a numeric option id and the option name in a nested key. I did not confirm this against GitHub's docs.
- The live repo's own later test pins that shape: it says "Do not compare the numeric `value` directly" and compares `single_select_option.name`. This is repo evidence only.
- If an implementer compares the option name to `value`, every successful write prints a false `not applied after create` line.
- Task 12's manual check would catch it, but the plan never names it as unverified.

### Architecture and interfaces (Fowler, Nygard)

**F4: Medium (MAJOR, not blocking).** The plan does not say who writes the `Issue type` row of `flags.md`.
- Task 2 says `flags.md` "gets a derived `Issue type` row by the Q7 rule".
- The T1 and T2 workers write `flags.md` in the "a flag missing" cases, and the constraints say their files stay unchanged.
- Their job text lists only "mode, type, complexity, reasons".
- Source 2.1 says "orchestrator or T1/T2 worker". The live `create.md` (which I did not diff against baseline) has the orchestrator derive the row after the worker returns, but the candidate never assigns that step.
- Left open, a worker may leave the row blank or wrong.

**F5: Medium (MAJOR, not blocking).** A `--type` flag that `gh issue create` itself rejects is treated as a fatal create failure.
- Task 2 says the type step is non-fatal "after the issue exists". It also says any `gh issue create` failure is STOP `E-CREATE-FAILED`.
- If `--type` is rejected before the issue exists (for example, an older `gh` without the flag), the run stops. No retry without `--type` is specified.
- The plan sets no minimum `gh` version.
- The documented intent, "a failed type never stops the run", then fails for that case. This is an unstated requirement, so it is Medium.

### Consistency notes (Whittaker, Cockburn)

**F6: Minor.** The Constraints say the skill writes "exactly two things" to a created issue besides the issue itself. Task 2 and Task 3 also have the skill apply the mode label and post the pushback comment. No task is built wrongly because of this. The sentence should say it writes exactly two classification fields.

**F7: Minor.** The Constraints say to edit only under `src/superclaude/`, `tests/`, `docs/` and the plugin refs folder. Task 12 requires `./artifacts/owner-manual-check.md` and `./artifacts/t12-checks.log` in the package. The intended reading is that the constraint covers repo files. The sentence should say so.

**F8: Minor.**
- Task 3 says to add "`gh issue create ... --type <name>`" to the write list. The constraints require `--repo <R>` on every `gh issue` line, and the fork-safety scan fails a line without it. Source 2.3 spells it `gh issue create --repo <R> ... --type <name>`.
- Task 10's acceptance line says every `gh api` path in the design doc is `repos/<R>/...` or the one `orgs/` read. The claim Wave 1 text in that doc contains `gh api user -q .login`, and `--claim` text must not change. Read literally, that criterion cannot pass. The intended reading excludes `user`.
