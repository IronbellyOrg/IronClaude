## Blocking finding

**F1. The write limit and the create sequence cannot both be true.**

Grading check: An implementer who follows the stated text as written builds a create flow whose only writes to the new issue, besides the issue itself, are `gh issue create --type` and one Complexity POST, and that is wrong because Task 2 requires a pushback comment after the issue exists.

The constraint says the skill writes exactly two things to the created issue besides the issue itself: the type, through `gh issue create --type`, and the Complexity value, through one POST. Task 2's Wave 5 sequence also posts the pushback comment (`gh issue comment`) and says `E-POST-FAILED` keeps its current meaning, which is that comment failing and stopping the run. A comment is a third write to the issue. The two instructions cannot both be followed. Dropping the comment drops the disagreement notice and leaves `E-POST-FAILED` with nothing to attach to in create mode. Keeping the comment makes the "exactly two" rule false.

## Follow-up candidates

**F2 (Medium).** Task 6 tells the implementer to write a `--mode` cell that says the issue type is Feature or Bug. Task 1 says a feature whose area is `tests` is Test, and Task 6's own `--type` cell says the same. The two cells can be read as a pair (mode picks Feature or Bug, area `tests` overrides to Test), so this is not blocking. Read alone, the `--mode` cell is false.

**F3 (Medium).** Task 2's instructions name the exception `orgs/<owner of R>/issue-fields`. Task 2's acceptance criterion requires the file to state `orgs/<owner>/issue-fields`. Those strings are not the same. The criterion can pass if the file contains both, which Task 8 allows. A file that follows only the task body fails the criterion.

It becomes true only if the implementer adds an assertion the list does not name. Task 7's updated test would catch a Task 3 revert, but that test is not a new test.

The "if the phrase appears, otherwise leave the file alone" clause prevents a wrong edit.
