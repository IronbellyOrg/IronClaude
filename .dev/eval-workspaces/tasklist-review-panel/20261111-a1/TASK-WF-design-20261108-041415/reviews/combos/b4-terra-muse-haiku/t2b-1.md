### F2 (Medium). "Exactly two things written besides the issue itself" conflicts with the mode label and the pushback comment

The Constraints say the skill "writes exactly two things to a created issue besides the issue itself: the issue type ... and the Complexity field value", while the Goal and Tasks 2, 3 and 6 require applying the mode label and posting the pushback comment. An implementer could read the constraint as a cap and drop one of those, or read it as classification-only and keep both. Narrow it to "exactly two classifications besides the mode label" or name the label and comment as exceptions.

### F3 (Medium). Maintainer label lines versus the `--repo <R>` rule

The Constraints require every `gh label` line in the skill, refs or agents to carry `--repo <R>`, and Task 1 says to keep only the `bug` and `enhancement` lines in the maintainer block. Those lines in the live file carry `--repo <owner/repo>` with the instruction "Replace `<owner/repo>` with the target repo", because a maintainer may target a repo other than the origin. Keeping them verbatim breaks the stated `--repo <R>` rule; rewriting them to `<R>` changes who the maintainer instruction addresses. Say which one wins.

### F4 (Medium). The Complexity read-back comparison is never specified, so a naive implementation reports every successful write as not set

Task 1 specifies the POST and "read-back with `gh api repos/<R>/issues/<N>/issue-field-values`" but never says what in that response proves the value landed. For a single-select field the read-back's `value` is an option id, not the option name, so an implementer who compares it with `Simple`, `Medium` or `Complex` produces a `not set: field Complexity <value>: not applied after create` line on every successful run, and `complexity_field: null` in the return contract. The live `labels.md` already carries the needed rule, compare `single_select_option.name` on the row whose `issue_field_id` matches, and treat a failed or unparseable read-back as not applied. Task 1 should require that text, and Task 8 should test it.

### F5 (Medium). `./artifacts/` in Task 12 has no stated base directory

Task 12 says to write `./artifacts/owner-manual-check.md` "in this package" and to save `./artifacts/t12-checks.log`, while the Constraints limit edits to `src/superclaude/`, `tests/`, `docs/` and one plugin refs folder. Run from the repo root, `./artifacts/` is the project-root artifacts folder, which the project rules treat as a different folder from a task package's `artifacts/`. Name the package directory the path is relative to so the manual check lands where a later reader looks for it.

### F6 (Minor). The new `orgs/` scanner test does not say how bare prose or required presence is handled

Task 8 requires a regex scan asserting every `orgs/` path equals the allowed one and "appears only in `create.md`, `SKILL.md` and `issue-worker-t3.md`". Specify that bare `orgs/` prose is not a path and that the holder set is exactly those three files.
