**F2. Medium. Missing requirement, not blocking.** Task 1 tells the implementer to read the field back with `gh api repos/<R>/issues/<N>/issue-field-values` and to treat the value as absent when it was not applied. GitHub's list payload puts an option id in `value` (example: `"value": 1`) and the option name in `single_select_option.name`. The plan never says that. Checking the `value` property against `Simple`, `Medium`, or `Complex` reports a successful write as `not set`. Treating any present `value` as success accepts the wrong option. Searching the body for the option name happens to work. The live `labels.md` already has the correct comparison, and `test_field_readback_uses_the_field_id_and_option_name_not_numeric_value` requires those sentences. Task 1's required text does not include them, and Task 7 says to change only assertions of the old label wording, so a rewrite that follows Task 1's list and drops that paragraph fails the existing test until Task 12 forces a fix. The plan can still be satisfied by keeping the paragraph. It does not state the rule.

**F3. Medium. Missing requirement, not blocking.** Source 2.4 and 2.5 require `not set: field Complexity <value>: option not found` when the field exists but no option matches. The Wave 5 sequence Task 2 copies from source 2.1 has only two field branches: option matches, so POST; field missing or lookup failed, so `not set`. It has no branch for "field present, option not equal". An implementer who transcribes that sequence and only pastes the 2.4 line into the format block never emits the line, so the final output and `classification_missing` stay silent. The live `labels.md` step does remember the case, but only as the bare token `option not found`, not the full `not set:` line. Task 1's acceptance check only requires the format strings to appear, so that check passes while the run stays silent.
