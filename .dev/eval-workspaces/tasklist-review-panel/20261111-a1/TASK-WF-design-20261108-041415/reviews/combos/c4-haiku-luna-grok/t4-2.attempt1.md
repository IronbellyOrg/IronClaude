## Findings

**F1, Medium (not blocking).** An implementer who follows the stated text as written builds a read-back that treats "the value" as the same string posted in `"value":"<option name>"`, and that check is wrong because GitHub's GET returns `value` as the numeric option id and the name under `single_select_option.name`. It stays Medium because the other reading (section 2.1's "if the value is absent" means the row is missing) does not make that mistake, and the plan never picks a JSON path. On this tree, `test_field_readback_uses_the_field_id_and_option_name_not_numeric_value` already requires the id-versus-name sentences in `labels.md`. Task 1's rewrite list does not include them. Task 12 tells the implementer to fix a red test in `src/superclaude/`, so the acceptance check can still pass. A tree that has only the tests Task 8 lists would not catch it.

**F2, minor.** Task 2's body writes `orgs/<owner of R>/issue-fields`. The same task's acceptance check asks for `orgs/<owner>/issue-fields`. Tasks 3, 5, and 10 use the long form. Task 8 allows both. The plan defines `<owner>` as the part of `<R>` before the slash, so both strings are one GET. An implementer can put both sentences in `create.md` and satisfy every check. No wrong call is forced.

**F3, Medium (not blocking).** An implementer who follows "exactly two things" as a closed list builds a create path that sets the issue type and the Complexity field and does not apply `bug` or `enhancement`. That is wrong because the goal and Wave 5 require the mode label. It stays Medium because the other reading fits the same words: the label is part of creating the issue (`--label` on `gh issue create`), and the two extra writes are `--type` and the one POST. The tasks that name the label are specific enough that the worse reading is a guess.

**F4, Medium (not blocking).** An implementer who follows Task 5 records a 404 from `orgs/<owner>/issue-fields` on a user-owned repo as `lookup failed`. Section 2.5, which Task 2 says to apply, maps that case to `field not found in org`. The issue is still created and a not-set line is still printed. Only the reason text changes. Task 4 already allows both `not found` and `lookup failed` as scout results, so this is a reason-code clash, not a stop-the-run bug.

**F5, minor.** The `--mode` cell Task 6 prescribes says the issue type is Feature or Bug. A feature whose area is `tests` is Test (Task 1, Q7). The same task's `--type` cell states that Test case, so writing both rows does not drop Test.

No acceptance check is impossible to meet, no stated pair forces data loss, and no stated pair crosses a safety boundary. The GitHub POST shape in the plan (option name, `POST` not `PUT`, integer `field_id`) matches the current issue-field-values docs. The manual check in Task 12 is still the right place to confirm a real issue, which the plan already marks unverified.
