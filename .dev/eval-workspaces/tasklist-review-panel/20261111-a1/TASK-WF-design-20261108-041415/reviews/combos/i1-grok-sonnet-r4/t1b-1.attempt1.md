- Test 2 says orgs paths appear "only in" three files, which can be read as "a subset of", so removing the `SKILL.md` mention stays green. Test 3 checks `-X POST` and `issue-field-values` across the folder as a whole, so `create.md` and `labels.md` keep it green.

- It becomes blocking only if the implementer takes the weaker reading, so it is Medium.

**F2 (Medium): Task 3 gives a `gh issue` string with no `--repo`.**
- An implementer who copies Task 3's `gh issue create ... --type <name>` into the `SKILL.md` write list builds a code span with no `--repo`.
- The scan `test_every_gh_issue_pr_label_mention_carries_repo` flags any code span containing `gh issue` without `--repo`, and Task 8 requires that scan to stay green.
- Specification 2.3 and the constraints show the `--repo <R>` form, so a careful implementer will add it. That makes it Medium.

**F3 (Medium): the read-back of the Complexity value is under-specified.**
- Task 1 and the Task 2 Wave 5 steps say "read back" and "if the value is absent". The return contract's `complexity_field` is "the option name read back".
- The GET response carries `value` (string, number or integer) and a separate `single_select_option` object, and the plan says nothing about which to compare.
- An implementer who compares `value` with `Medium` could print `not set: field Complexity Medium: not applied after create` on a write that worked. `complexity_field` would then come out `null`.
- I could not confirm from the docs that `value` is an option id. That part is UNVERIFIED.
- The live `refs/labels.md` already has a "Field read-back shape" section that the plan never asked for, which suggests the executor hit this.
- Task 12 lists three UNVERIFIED points and omits this one.

**F6 (Medium): the Task 10 acceptance line cannot pass if checked literally.**
- It says every `gh api` path in `docs/designs/sc-issue-command.md` spells `repos/<R>/...` except the one `orgs/` read.
- The design doc has the claim-mode line `gh api user -q .login` (line 157 in the live file). `user` is allowed by the skill's own rule, but it is not `repos/<R>/...`.
- The only way to satisfy the literal text is to edit claim text, which the constraints forbid.
- A reasonable reader exempts `user`, so it is Medium.

**F4 (minor): the constraint says "exactly two things".**
- The constraint says the skill writes exactly two things to a created issue besides the issue itself (the type and the Complexity value).
- The Goal and Task 2 also apply the mode label and post the pushback comment.
- Read literally the two disagree. The intent is clearly "no other classification write", so this is a note.

**F5 (minor): `./artifacts/` may resolve to the wrong folder.**
- Task 12 says to write `./artifacts/owner-manual-check.md` "in this package".
- Run from the repo root, `./artifacts/` is the project-root `artifacts/` folder, which the project rules say is never staged. The package's own `artifacts/` is the one that must be staged.
- It also sits outside the constraint that lists the only edit locations. "In this package" mostly settles it, so this is a note.

**F7 (minor): the Task 6 "agree" check has no shared wording.**
- Task 3 gives the skill Will Not "never creates an issue type or an issue field and never writes a field other than Complexity".
- Task 6 gives the command only "creates no issue types or issue fields".
- Task 3 adds nothing to the skill's Will list, yet Task 6 rewrites the command's create Will line.
- "Agree" has no exact text to test. The existing Will test only checks tokens, so nothing fails, but the two files can drift.
