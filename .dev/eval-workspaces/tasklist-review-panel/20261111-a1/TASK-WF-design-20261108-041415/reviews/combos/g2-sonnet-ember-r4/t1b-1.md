No finding passes the grading check for blocking. Each one below needs a guess about which of two allowed readings an implementer picks, or it is a requirement the plan never states. All are Medium or minor.

**F1 (MAJOR label, Medium by grading): the Task 8 check cannot be met by the tests Task 8 lists, for Task 3.**
- Check applied: an implementer who follows Task 8 as written builds seven tests. Reverting Task 3 (`SKILL.md`) then turns none of them red, yet the criterion says reverting any one of Tasks 1 to 5 must turn a new test red.
- Why only Medium: the "orgs paths appear only in `create.md`, `SKILL.md` and `issue-worker-t3.md`" test is written as an upper bound. If read as an exact set it would catch the revert.
- The implementer can also just add a `SKILL.md` assertion. The live repo did exactly that (`test_skill_md_states_the_create_rules_of_the_issue_type_and_field`).

**F2 (MAJOR label, Medium): Task 3's wording for the write list omits `--repo`.**
- Check applied: Task 3 says to add `gh issue create ... --type <name>` to the orchestrator's write list. Copied literally, that backtick span has no `--repo <R>`.
- The shared scan `gh_lines_missing_repo` (`tests/skills/test_issue_worker_agents.py:31`) flags any backtick span containing `gh issue` without `--repo`. The existing fork-safety test would then fail, against the constraint and the Task 8 criterion.
- `source.md` section 2.3 writes it with `--repo <R>`, so a careful implementer adds it. That is a guess, hence Medium.

**F3 (MAJOR label, Medium): Task 6 does not carry everything Task 3 puts in the skill's Will Not list.**
- Check applied: Task 3 adds "never writes a field other than Complexity" to the skill. Task 6 only adds "creates no issue types or issue fields" to the command. Its criterion says the two lists agree.
- Followed literally, the command lacks one item the skill has. The live repo added that item to both and tests it.
- Medium because "agree" is loose and the plan never states the missing item for the command.

**F4 (MAJOR label, Medium): the field read-back comparison is never specified.**
- Task 1 says to read back with `gh api repos/<R>/issues/<N>/issue-field-values`, and the source says to report "not applied" if the value is absent. Neither says how to match the value.
- The POST sends the option name. The live `labels.md` has a "Field read-back shape" section saying a single-select read-back returns an option id, and that the row must be matched by `issue_field_id` and `single_select_option.name`. I did not verify that against GitHub.
- An implementer who compares the returned `value` with `"Medium"` would print a false `not set: field Complexity Medium: not applied after create` after a good write. They would also leave `complexity_field` null.
- Medium because it is a missing requirement and depends on the unverified API shape. The owner's manual check in Task 12 would catch it.

**F5 (MINOR): the constraint "exactly two things" is too loose.** It says the skill writes exactly two things to a created issue besides the issue itself (type and Complexity). The goal and Task 2 also have it apply the mode label and post the pushback comment. No acceptance criterion depends on it.

**F6 (MINOR): the Task 10 criterion is over-literal.** "Every `gh api` path in the file spells `repos/<R>/...` except the one `orgs/` read" ignores `gh api user -q .login` at `docs/designs/sc-issue-command.md:157`, which is claim text and stays. The constraint "No file may contain a brace placeholder" also conflicts with the prohibition sentence at line 334 of the same doc, which names `{owner}/{repo}`. Both are harmless if read as scoped to the skill folder and agents.

**F7 (MINOR): the goal and the third return-contract block differ.** The goal says the third block lists every classification not set. The plan and `source.md` 2.2 put only the `not set` lines in `classification_missing`. A missing mode label stays in `labels_missing` in the first block.
