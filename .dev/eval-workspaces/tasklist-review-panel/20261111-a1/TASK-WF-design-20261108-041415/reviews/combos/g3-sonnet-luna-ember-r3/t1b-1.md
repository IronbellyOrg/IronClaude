**Follow-up candidates (Medium and minor; none fail the review)**

- **F2 (Medium): field read-back check is under-specified.**
  - The plan says to remember `not applied` "if the value is absent" from the read-back.
  - GitHub's docs say POST takes the option name, and that each response item has `single_select_option` (id, name, color). They do not say whether a single-select `value` in the response is the id or the name.
  - An implementer who compares `value` to `Medium` may report `not applied after create` on every run, even when the write worked. That would print a false `not set` line and set `complexity_field` to null.
  - The plan should say to match on `issue_field_id` plus `single_select_option.name`.
  - The live `labels.md` already added a "Field read-back shape" section for this. The plan never asks for it.
- **F3 (Medium): `--type` has no guard for a `gh` that lacks the flag.**
  - The plan checks the type name against `issue-types` but not that `gh issue create` accepts `--type`.
  - Task 12 calls the flag UNVERIFIED. On an older `gh` the create command fails with an unknown-flag error, which is STOP `E-CREATE-FAILED`. The issue is then never filed, which breaks the rule that a failed type never stops the run.
  - The plan should say to omit `--type` and record a `not set` line when `gh issue create --help` lacks the flag.
- **F4 (minor): two constraint wordings clash with other tasks.**
  - "Edit only under `src/superclaude/`, `tests/`, `docs/`, `plugins/...`" is broken by Task 12 writing `./artifacts/` files in the package.
  - "writes exactly two things to a created issue besides the issue itself" is broken by the pushback comment, which the plan keeps.
  - Readers will resolve both sensibly.
- **F5 (minor): Task 10's last criterion is stricter than the file allows.**
  - It says every `gh api` path in `docs/designs/sc-issue-command.md` spells `repos/<R>/...` except the `orgs/` read.
  - The same file legitimately contains `gh api user -q .login` (line 157 in the live file), and the project rule itself allows `user`.
- **F6 (minor): the plan does not say who fills the `Issue type` row in `flags.md`.**
  - The T1 and T2 workers are unchanged but write `flags.md` from the template, which now has that row.
  - Wave 5 re-derives the type by rule anyway, so the row is informational. It could still disagree with what gets filed.
