## Findings

### F1 (MAJOR, blocking): Task 10's `gh api` acceptance criterion cannot pass on the existing design doc

An implementer who follows Task 10 as written builds a design doc where every `gh api` path other than the `orgs/` read spells `repos/<R>/...`. That is wrong because `docs/designs/sc-issue-command.md` already contains `gh api user -q .login` in the claim flow (live line 157). Constraint 4 says claim text stays unchanged, and Task 2 says the allowed paths are `user` or `repos/<R>/...`. The criterion fails on that line as written, unless claim-flow text is rewritten against Constraint 4. Fix by adding `user` to the criterion.

### F2 (MAJOR, not blocking, Medium): Task 8's revert criterion cannot hold for Task 3

Reverting Task 3 (SKILL.md) leaves all seven listed new tests green. None of them asserts SKILL.md text:
- Test 2 only forbids stray `orgs/` paths.
- Test 3 is read folder-wide, and `labels.md` and `create.md` still carry the POST text.

An implementer who writes the listed tests fails the criterion "reverting any one of Tasks 1 to 5 turns a new test red". It needs a guess that the implementer adds a per-file SKILL.md assertion the plan never lists. Per-file reading of test 3 is allowed, so this is Medium.

### F3 (MAJOR, not blocking, Medium): how to match the Complexity read-back is never stated

The plan says to read back with `gh api repos/<R>/issues/<N>/issue-field-values` and to report `complexity_field` as "option name read back". It does not say how to match the result. GitHub's GET response has `issue_field_id`, a primitive `value`, and a separate `single_select_option.name`. An implementer who compares `value` to "Medium" prints a false `not applied after create`. This is a requirement the document never states, so it is Medium.
