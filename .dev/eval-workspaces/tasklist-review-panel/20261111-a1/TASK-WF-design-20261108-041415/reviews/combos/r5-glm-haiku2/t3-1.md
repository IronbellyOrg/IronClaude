## Findings

**F1 (MAJOR, graded Medium, not blocking), missing requirement: the Complexity read-back has no stated success criterion.**
Grading check: "An implementer who follows the stated text as written builds a field read-back that compares the raw returned `value` with the option name it POSTed, and that is wrong because the issue-field-values read-back returns an option id (not the option name) for a single-select field, so every successful write would be reported as `not set: field Complexity <value>: not applied after create`." The sentence needs the implementer to improvise the comparison (the plan is silent), so under the rubric this grades Medium, not blocking: it is an unspecified edge case, and no stated acceptance criterion fails. The executed repo closed this gap with the "Field read-back shape" section of `labels.md` plus a pinning test; the plan should have contained that requirement.

**F2 (MINOR, note): "exactly two things" conflicts with the kept pushback comment.**
The Constraints say the skill writes exactly two things to a created issue besides the issue itself, while Task 2's Wave 5 sequence keeps the pushback comment and its `E-POST-FAILED` STOP code, which is a third write to the issue. The task text is explicit, so an implementer keeps the comment; the constraint just needs "exactly two classifications" wording. No wrong outcome on any reading that survives the acceptance criteria.

**F3 (MINOR, note): the new `complexity-field.json` artifact is undocumented in the output inventories.**
Wave 5 writes `.dev/issues/<N>/complexity-field.json`, but no task adds it to the command file's Outputs table row for create mode or to the skill's files-table note (the pattern used for `clickup.json`). Readers of the command file cannot discover the artifact. Cosmetic; the write itself is unambiguous in `create.md` and `labels.md`.

Line-anchor drift (for example HOW-WE-WORK `/sc:issue` row named at line 329, live at line 330; the return-contract test named at 492-520, live at 545-579) is covered by the plan's own constraint that line numbers "must be re-read in the live file before each edit", so it is recorded here as a note, not a finding.
