## Follow-up candidates

**F1 (Medium).** The field write is specified. The read-back check is not, and the live response does not echo the string that was posted. Task 1 tells the implementer to POST `{"issue_field_values":[{"field_id":<id>,"value":"<option name>"}]}` and then read `repos/<R>/issues/<N>/issue-field-values`, and to report `not set: field Complexity <value>: <reason>` when the set did not stick. GitHub's list response puts a numeric option id in `value` and the name under `single_select_option.name` (GitHub Enterprise Server 3.21 issue-field-values example: `"value": 1`, `"single_select_option": {"name": "High"}`). The write API wants the option name in `value`, so the POST body itself matches the docs. An implementer who treats read-back `value` as that same name reports every successful Complexity write as not set. The plan never says to compare `single_select_option.name`. That wrong check is the worse of two readings, not a step the text forces, so this does not fail the review. The sentence that would have to hold with no guess does not: the plan does not say "compare `value` to the option name."

**F2 (Medium).** The constraint says the skill writes exactly two things besides the issue: the type, via `gh issue create --type`, and the Complexity value, via one POST. The goal, Task 1, Task 2, and Task 6 also require the mode label on that same create call. If create-time flags count as "besides the issue" (the constraint counts `--type` that way), the label is a third write and "exactly two" is false. If the label is part of the issue itself, "exactly two" can stand. Dropping the label is the worse reading. The rest of the plan requires the label, so this stays a warning.
