## Follow-up candidates

### F1, Medium (label MAJOR, not blocking). Resume cannot both release a landed push and reject a moved head

An implementer who follows the stated text as written builds a resume function whose only inputs are mode, ordinal, guard, read, pending, dangling branch, and published, then re-enters the release decision with "push completed" set. That release decision returns "release, no edits" when the edit count is 0, before it compares the head, and it returns "hold" when the head differs from the target commit. The resume inputs include neither the target commit nor this cycle's edit count. Passing an edit count of 0 marks the pull request ready without the head check, including when the head moved. Passing a positive count and no target commit holds every landed push, so the scenario check "landed releases" cannot pass. The plan never states the missing inputs. This needs the worse of those two readings, so it is Medium, not blocking.

### F2, Medium (label MAJOR, not blocking). A ready request that did not apply is both "back to the previous phase" and "always held"

An implementer who follows the stated text as written builds a fold that, for any direction, restores the phase from before the request, and also a test where a ready request followed by "not applied" must end in phase held. Those agree only when the phase before the request was already held. The same paragraph does not say that. After a failed release, the phase before the request is "release pending", and restoring it is not "held". Forcing "held" skips the later retry-release step, so a failed release that never landed stays stuck. The sentence is passable if the test includes an earlier held phase. That is the worse-reading case, so it is Medium.

### F3, Medium (label MAJOR, not blocking). The Wave 0 check can reject the bullet it requires

An implementer who follows the stated text as written builds a Wave 0 bullet that says the off notice is printed at monitor level 3 and that no draft call is made, and a test that fails when that bullet names a level-3 or draft condition, and that must also pass on the real file. Read strictly, the required bullet names both, so the test cannot pass. Read as the task's own test wording ("no `L3 only`" and no draft gate), the same bullet passes. Medium, because the failure depends on the worse reading.

### F4, minor. The "43" search still prints a line

`models.py` has a comment that the conflict-cycle events are the 42nd and 43rd. Task 2 does not change it. After the enum grows to 45, that comment is still true and is not a claim that the enum has 43 members, so the acceptance check can pass. An implementer who treats any search hit as failure will edit a correct comment.
