**F1 (Medium, not blocking).** An implementer who follows the stated text builds a fold where `settled(draft, failed)` leaves phase `RELEASE_PENDING` and `owned_draft` false, then an engage decision that returns `HOLD` rather than `ENGAGE` or a halt. The same run does halt (`terminal_halted`). A later `--resume` at monitor 3 does not: pending is empty, so resume row 9 is `NOOP`, and the next engage is `HOLD(ownership_unproven)`. `HOLD` elsewhere in this design means do not mutate and keep going. Nothing here says this `HOLD` stops Wave 4. The unsafe outcome (edits on a still-mergeable pull request) needs that extra reading, so it is not blocking. The sentence that would make it blocking does not hold on its own.

**F2 (Medium, not blocking).** Task 9 requires the Wave 0 bullet to say the off line is printed at L3, and the task body says the test rejects "`L3 only`" or a draft gate. The acceptance criterion says the same test fails when the bullet "names an L3 or `draft` condition" and still passes on the real file. Read the criterion broadly and the required "at L3" sentence fails its own test. Read it as the task body's "`L3 only`" gate and the test passes. That is the worse of two readings the text allows.

**F3 (Medium, not blocking).** `resume_decision` is specified without `target_sha` or this cycle's `applied_edits`, but row 4 must re-enter `release_decision` with only `push_completed=True`. Release with cause `pushed` needs the head to equal `target_sha`. The only value that returns `RELEASE` with no head is `applied_edits=0`, which also marks the pull request ready when the head does not match. The plan never says to pass 0, and it does not forbid adding the missing arguments. The bad release needs the worse choice.
