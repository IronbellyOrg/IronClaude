## Findings

**F1 (MAJOR, blocking, unpassable-check). `resume_decision` has no way to release on a landed or published push.**
- An implementer who follows the stated text as written builds `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)` whose row 4 calls `release_decision` with `push_completed=True`.
- That signature carries no `target_sha`, no per-cycle `applied_edits` and no `cycle_id`.
- `release_decision` releases with cause `pushed` only when `read.head_sha == target_sha` (row 8), and releases with `no_edits` only when `applied_edits == 0` (row 7).
- With neither input available, row 4 can only return `HOLD(head_mismatch or push_not_completed)`.
- It is wrong because the Task 4 criterion that `landed` and `published=True` each "re-enter `release_decision` with `push_completed=True`" and the Task 11 criteria that `landed` releases and a normal `push_completed` crash releases before the re-trigger cannot pass.
- The built `resume_decision` in the repo had to add `applied_edits`, `target_sha` and `cycle_id` keyword arguments. Its docstring says that without `target_sha` the guard holds.
- Task 8's Resume section also never says where the held cycle's `target_sha` comes from on `--resume`.

**F2 (MAJOR, not blocking, follow-up). Task 9 says the Wave 0 bullet has no L3 condition, then requires an L3 condition in it.**
- The bullet must carry "no L3 or `draft` condition" and also state that "at L3 with `--merge-guard off`" the line is printed.
- The acceptance criterion says the test fails when the bullet "names an L3 or `draft` condition". Read literally, the real bullet fails that test.
- The body of Task 9 words the test narrower (`L3 only` or `draft` gate wording), so an implementer can choose the passing reading.
- Not blocking, because it needs a guess about which reading to pick.
- Fix: say that the off-line sentence is excluded from the scan, or that the ref-loading sentence is the one that must be ungated.

**F3 (MINOR, note). The force-push line test covers more files than Constraints names.**
- Constraints mention the force-push wording rule only for new `SKILL.md` lines.
- `test_skill_forbids_force_push` scans every `.md` and `.sh` file under the skill directory, so the new `refs/merge-guard.md` and `scripts/set-draft-state.sh` are covered too.
- Task 1 and the Task 8 static tests would likely catch it, but the Constraints text understates the scope.

**F4 (MINOR, note). The exit code of the `not_open` case is unspecified.**
- Task 7 requires `--to ready` on a merged PR to print `ok:false` with `error:"not_open"`.
- The exit-code criterion lists only 0, 1, 2 and 127 and does not say which one `not_open` uses.
