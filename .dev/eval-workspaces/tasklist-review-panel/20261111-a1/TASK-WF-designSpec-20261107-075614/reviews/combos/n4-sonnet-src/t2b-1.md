## Follow-up candidates

Medium findings (warnings; they never fail this review):

1. Task 11 omits a dependency on Task 2. The scenario driver appends guard events to a real `RunLog`, and `RunLog.append` rejects event types outside the closed enum, so the driver cannot append `draft_guard_requested` or `draft_guard_settled` until Task 2 has added them. Task 5 has the same gap for its run-log rebuild tests. `./source.md` section 10 requires dependencies to be declared completely, one line per dependency, for every task whose output another task consumes. In task-number order this never bites; an executor that parallelises or reorders by the declared graph can start Task 11 or Task 5 too early and fail on the unknown event type. Adding `Depends on: Task 2` to both tasks closes it.
2. The Wave 0 bullet wording in Task 9 is ambiguous. The task says the bullet "carries no L3 or `draft` condition" and, in the same sentence, that it states the unprotected line is printed "at L3 with `--merge-guard off`", while the acceptance criterion says the test fails when the bullet "names an L3 or `draft` condition". An implementer who writes the test as a substring ban on L3 makes the required bullet fail its own test; an implementer who scopes the check to the resume clause, as the task's own test description suggests, passes. The plan should state plainly that the resume clause is unconditional and only the off-notice clause is L3-gated, and that the test checks the resume clause.
3. The Resume protocol in Task 8 does not say where the re-entered release decision gets its inputs. `resume_decision` row 4 re-enters `release_decision` with `push_completed=True`, and that function also needs this cycle's `applied_edits` count and the `target_sha` the head is compared against. The ref text as specified names `published` and the branch strings but never says the target SHA comes from the held cycle's push record. An implementer who defaults `applied_edits` to the resume run's own zero count releases through the `no_edits` row without the head comparison, marking a PR ready even when its head has moved since the held cycle's push. Stating the two input sources in the Resume section removes the guess.

Minor findings (notes):

4. The classification step in Tasks 8 and 12 is narrower than the candidate's own constraint. The constraint requires a `WRITE_VERB_CLASSIFICATION` entry for every new line containing `gh pr`, `gh api` or a git write verb, but Tasks 8 and 12 only instruct entries for lines matching `gh pr` or `gh api`. Task 8 also allows fenced command lines starting with `git`. A ref or command line carrying a git write verb would be missed by the task instruction and caught only by the task's own run of `tests/skills/test_worker_contract.py`. Extending both last-step instructions to the git write verbs makes the instruction match the constraint.
5. The `guard_status` acceptance list in Task 3 says the test covers every phase and cause, but the enumerated cases never name phase `HELD` mapping to `held` or phase `RELEASED` mapping to `released` directly. The word "including" leaves room for the test author to add them, so this is a completeness nit in the enumeration, not a gap in the specified behaviour.
