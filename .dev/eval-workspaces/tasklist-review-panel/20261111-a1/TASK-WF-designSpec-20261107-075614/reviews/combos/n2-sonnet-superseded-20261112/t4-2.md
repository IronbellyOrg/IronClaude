## === REQUIREMENTS ANALYSIS ===

**F1. Resume cannot both release a landed push and refuse a moved head.** Critical. Blocking. (Nygard, Whittaker)

An implementer who follows the stated text as written builds a `resume_decision` whose only inputs are mode, ordinal, the folded guard, the live read, the pending list, the branch string, and a published flag, and whose landed path only re-enters `release_decision` with `push_completed=True`. That call cannot see the pushed commit. The release table returns ready only when the live head equals that commit, and returns hold when it does not. With no commit to compare, the landed path either holds, so Task 11's "landed releases" check fails, or it marks the PR ready without that comparison, including when the live head is a different commit. The second result breaks the plan's own rule that the PR becomes ready only after the fix push is confirmed on the PR head.

The pure module already in this checkout has the same hole called out in its resume notes, and it takes the missing commit and this cycle's edit count as extra arguments. The plan never adds those arguments, and Task 11 forbids the scenario test from inventing the branch result, so the test cannot smuggle the commit in through a hand-written branch string either.

**F2. A failed draft settle is not drafted again and is not halted on resume.** Major label, Medium. (Nygard)

An implementer who follows the fold builds `RELEASE_PENDING` with ownership left false after a failed draft call. On resume the pending list is empty, and the "live PR is draft" hold does not match, so the stated otherwise-row is no-op. The next engage hits the unowned release-pending row and holds. The same-run script failure is specified to halt before edits. The resumed run is not. The worse reading, which the action names support, continues the fix on a PR that is still mergeable. That reading is not forced, because the plan never says what the engage procedure does with hold.

**F3. User override never reaches the status the exit report needs.** Major label, Medium. (Wiegers)

The plan says to implement every effect-table row and to report `user_override` from `guard_status` when the disabled cause is `user_override`. The user-override row sets the phase to disabled and clears ownership. It does not set the cause. A fold that follows that row does not match the status rule, so the exit field falls through. An implementer can infer the cause from the settle event. The plan never says to.

**F4. Mode off plus an existing hold is unspecified in the status field.** Major label, Medium. (Adzic)

Status is specified for mode off only when there is no guard record. Resume at mode off with a held record is specified to report held and print the clear command. A reader who treats "mode off" as an immediate status of `off` reports the PR as unguarded while resume still says it is held. The plan's tests do not decide which reading is required.
