## Findings

### F1. Resume cannot both release a confirmed push and check the head. CRITICAL, blocking. Contradiction.

An implementer who follows the stated text as written builds a resume decision that must release after a confirmed push and must also hold unless the live head equals `target_sha`, but the decision is not given `target_sha` or this cycle's edit count, so it either marks the pull request ready without that proof or the crash test that requires release cannot pass.

Task 4 fixes the resume parameters at `mode`, `ordinal`, `guard`, `read`, `pending`, `dangling_branch` and `published`, and says row 4 re-enters release with `push_completed` true. The same task says a fixing cycle releases only when the live head equals `target_sha`, and holds when it does not. A zero edit count releases for a different reason, and Task 11 treats the zero-edit case as separate from the crash cases. The folded guard record does not store `target_sha` or the edit count. The read result has the live head only. The real crash resolver keeps `target_sha` on the push record and does not return it as the branch string. Task 11 then requires the landed branch and a normally completed push to release, and forbids the test from passing a handwritten branch string. No build can honor the release rows and those crash outcomes at the same time.
