**F3. Medium (repo pin versus the origin fallback).** An implementer who follows the stated text as written builds `set-draft-state.sh` so that it passes the origin-URL tests, which require a `gh repo view --json nameWithOwner` line, and a static check that every `gh` line carries `--repo` or a `repos/` path. That fallback line, as written on `retrigger-review.sh`, has neither. Adding `--repo "$REPO"` makes both checks pass, but that line runs only when the repo is still empty, so the fallback cannot resolve the fork. Weakening the check to the existing repo-scope helper also passes and keeps the fallback. The plan does not say which.

**F4. Medium (a later fix cycle keeps the earlier cycle id).** An implementer who follows the stated text as written builds engage row 7 as "already held, do nothing" and treats a push as published only when its cycle id equals the id stored on the guard. A new cycle can run while that stored id is still the earlier cycle (the plan's own zero-edit release case). The normal release call does not compare the two ids, so it can still mark the pull request ready. A crash after the new cycle's push does not: publication is false, the dangling window is empty, and resume does nothing, so the pull request stays a draft after a confirmed push. The plan never says to point the guard at the new cycle id.
