## Follow-up candidates

**F1 (Medium).** An implementer who follows the stated text as written builds a fold where a failed draft settle sets phase `release_pending` and leaves ownership false, and an engage decision that follows all 11 rows then returns hold for unproven ownership. That is a bad recovery, not a broken acceptance check: the first failure is specified to stop before any edit, and the plan never says a hold continues into a push. On resume of that same log, if the draft call did not land, nothing is pending to reconcile, so the next engage holds and the run never drafts the PR. The only stated way out is turning the guard off.

**F2 (Medium).** An implementer who follows the stated text as written mints a new cycle id for each fix cycle, leaves an already-held guard as a no-op (row 7 of the 11), and treats a push as published only when `push_completed` carries the guard's cycle id. That is wrong for a later cycle that starts while the PR is still held (the plan says a failed validation stays held): the new push's id never matches, so a crash after a normal `push_completed` does not release. The acceptance test can still pass because it uses one cycle. The plan never says to rebind the held guard onto the new cycle id. This is a missing rule, not two statements that cannot both be true.

**F3 (Medium).** An implementer who follows the stated text as written adds a Wave 0 bullet that says the off notice is printed at monitor level 3, and a test that fails when that bullet names a level-3 condition. That pair fails the test only if "names a level-3 condition" means any mention of level 3. The same task also says the test rejects "level 3 only" or a draft gate, which allows the off sentence. The worse reading is a guess, so this does not fail the review.
