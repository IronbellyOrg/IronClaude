## Follow-up candidates

**F1. Wave 0 bullet is described both as carrying no L3 or draft condition and as containing an L3 condition.**
Task 9 requires a Wave 0 bullet "that applies at every ordinal and in both modes and carries no L3 or `draft` condition", and in the same sentence requires it to state "that at L3 with `--merge-guard off` the line "Remediation is unprotected: --merge-guard off." is printed once". The acceptance criteria then require a test that fails when the bullet "names an L3 or `draft` condition", while the task text for the same test narrows that to "contains no `L3 only` or `draft` gate wording". An implementer who writes the test as a plain substring check for `L3` builds a test that fails on the very bullet the task requires. The narrower "gate wording" reading resolves it, so this is Medium, not blocking. Fix direction: make the acceptance wording match the task wording (forbid gate phrasing such as "L3 only", not any mention of L3).

**F2. `resume_decision` row 4 cannot reach a release with the signature the plan gives it.**
Task 4 defines `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)` and requires row 4 to re-enter `release_decision` with `push_completed=True`. `release_decision` as defined in the same task also needs `cycle_id`, `applied_edits` and `target_sha`, none of which is a `resume_decision` parameter, and the fold record defined in Task 3 has no `target_sha` field. An implementer who implements exactly the stated signature builds a resume row 4 that can only hold, never release, unless they invent the extra inputs. The checkout's implementation resolves this by adding optional `applied_edits`, `target_sha` and `cycle_id` parameters, which the plan never mentions. Medium: the plan should state where `target_sha` comes from on resume (for example the held cycle's push event) and whether the extra parameters exist. Grading note: this needs the guess that the implementer does not add those parameters, so it is not blocking.

**F3. The Wave 8 bullet text in Task 10 drops the Medium-or-higher trigger that Task 8 makes a condition of engaging.**
Task 8's Engage step engages "only when at least one verified finding of Medium severity or higher is routed to a fix", for review-fix and CI-fix cycles. Task 10's Wave 8 bullet is described only as stating "that a CI-fix cycle engages with kind `ci` and releases after `push_completed` before the CI re-poll", and its acceptance test asserts only that CI-fix sentence. An implementer who writes the Wave 8 bullet exactly as Task 10 describes builds a protocol step that engages the guard for any CI-fix cycle, including one with no verified Medium-or-higher finding, leaving the PR draft-held for a cycle the guard was not meant to cover. The Engage ref loaded by that bullet does carry the trigger, so a careful implementer restates it; that guess is why this is Medium. Fix direction: Task 10 should require the Wave 8 bullet to repeat the Medium-or-higher routed-finding condition, and its test should assert it, as the Wave 3 test already does.

**F4. The candidate is not self-contained: its normative tables live only in the missing `./source.md`.**
The front matter names `source: ./source.md`, and Tasks 3, 4, 7, 8 and 11 define their core behavior as "following ./source.md sections 4.1, 4.2 and 4.6", "the exact calls, the one-line JSON shapes and the exit codes 0, 1, 2, 127 of section 4.4", and "the twelve test names of ./source.md section 7 and the acceptance trace of section 5". That file is absent from the candidate package, so a reader of the candidate alone cannot derive the 11 engage rows, the 9 release rows, or the script's JSON shapes beyond what the acceptance criteria happen to restate. In the intended package layout the source sits beside the plan, which is why this is Medium rather than blocking, but the review could not verify those tables against their source. Fix direction: bundle the source with the candidate, or inline the three decision tables and the script contract in the plan.
