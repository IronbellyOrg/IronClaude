## Findings

### F1. The draft-state script cannot pass both checks Task 7 requires

An implementer who follows the stated text as written builds `set-draft-state.sh` with the same origin-remote resolution as `retrigger-review.sh`, and a static test that fails that script.

Task 7 says to model the script on `retrigger-review.sh`, with the same resolution from the origin remote, to put it on `_RESOLUTION_SCRIPTS`, and that it must pass those origin-URL tests. Those tests require a line that runs `gh repo view --json nameWithOwner` with no `--repo`: the repo is not known yet, which is why that call exists. The same task's acceptance criterion says the new test asserts every `gh` line carries `--repo` or a `repos/` path. The fallback line has neither, so that assertion fails. Adding `--repo` to the fallback so the assertion passes makes the call use the repo it is supposed to discover. When the origin remote cannot be read, the script no longer learns the repo, and a later `gh pr` call can follow `gh`'s default onto the upstream parent. The two checks in Task 7 cannot be true of one script.

### F2. A crash after a confirmed push cannot both release and prove the PR head

An implementer who follows the stated text as written builds `resume_decision` with only `mode`, `ordinal`, `guard`, `read`, `pending`, `dangling_branch`, and `published`. Row 4 then calls `release_decision` with `push_completed=True`. That function returns a release for a pushed cycle only when the live head equals `target_sha`, and it returns a release with no head check only when this cycle's edit count is 0. Neither value is an input of `resume_decision`, and neither is a folded guard field. A completed fix push is not a zero-edit cycle: the plan says a zero-edit cycle blocks the push, and the acceptance trace has `fix_applied` before `push_completed`. Row 8 therefore does not match, and row 7 must not. The function holds. Task 11 requires this crash to release before the re-trigger. That criterion cannot pass. The only ways to force a release invent a head proof the plan does not have, and then mark the PR ready when the head was not shown to be this cycle's fix.

The push for the new cycle uses the newly minted id. Publication is then looked up on the old id, and a confirmed push of the new cycle does not release.
- **Resume treats a landed retry as ambiguous after a failed attempt.** Reconcile confirms only when the observed timeline count is exactly the run's toggle count plus one. A call that failed on the client but landed is counted in `failed_mutations`, not in the toggles, so the count is higher than that exact match. The plan then says anything else is ambiguous and holds. The unsettled request never settles, and a later cycle stays held.
- **A user override does not set the cause the status mapping reads.** The fold row for `skipped` / `user_override` sets the phase to disabled and clears ownership. It does not set `disabled_cause`. The status mapping returns `user_override` only when that cause is set. A literal fold leaves the reported status off that row, so the run does not report `user_override` as section 5 requires.
- **An unreadable timeline is reported as a failed read.** Task 7 says a failing `gh` call prints `ok: false`. A failed timeline call is a failing `gh` call, and it also sets `transitions` null and `complete` false. Engage matches "read not ok" before "timeline unreadable", so the unreadable path never runs for a read this script can produce. The PR still stays draft or the run still halts. The stated reason is wrong.
