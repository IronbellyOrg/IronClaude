## Blocking findings

### An unrelated zero-edit cycle can release unpublished fixes (F1)

**Severity:** MAJOR, blocking  
**Category:** safety  
**Perspectives:** reliability, requirements, adversarial sequence analysis  
**Location:** Task 4 acceptance criteria, against the Goal and Task 8 exit behavior

Task 4 explicitly requires release when the new cycle applies zero edits **while the guard still holds an earlier fixing cycle**. It does not require that earlier cycle’s fixes to have been published.

An implementer who follows the stated text as written builds a release decision that marks the PR ready when a new zero-edit cycle encounters a guard holding an earlier unpublished fixing cycle, and that behavior is wrong because the earlier fixes remain unpublished while the plan requires unpublished work to leave the PR draft.

Concrete sequence:

1. A fixing cycle engages the guard and applies edits.
2. Validation or publication fails. The PR stays draft, with those edits unpublished.
3. A later cycle applies no additional edits.
4. Task 4 requires `RELEASE` with cause `no_edits` because the later cycle’s edit count is zero.
5. The PR becomes ready even though the work protected by the held guard remains unpublished.

This is an explicit required result, not a guess about how an implementer handles an unspecified case. The source design’s release table repeats the same defect; referring to that table does not resolve the contradiction.

**Recommended correction:** narrow zero-edit release to proof that the work protected by the held guard requires no publication. A different cycle’s zero edit count must not discharge an earlier cycle’s unpublished work.

### The required Wave 0 bullet fails its own acceptance test (F2)

**Severity:** MAJOR, blocking  
**Category:** unpassable-check  
**Perspectives:** requirements and testing  
**Location:** Task 9 instructions and acceptance criteria

Task 9 requires one flat Wave 0 bullet to contain the condition:

> “at L3 with `--merge-guard off`”

Its acceptance criteria simultaneously require the Wave 0 test to fail:

> “when it names an L3 or `draft` condition”

An implementer who follows the stated text as written builds a Wave 0 bullet containing the required L3 condition for the off notice, and that bullet is wrong because the specified acceptance test must reject a bullet that names an L3 condition.

The intended distinction is understandable: loading the resume reference must be unconditional across ordinals, while printing the off notice is conditional. But the stated test rejects the condition anywhere in the bullet rather than checking whether it gates reference loading.

The existing skill text illustrates this distinction: its resume hook applies at every ordinal and contains a separate L3-only off-notice sentence.

**Recommended correction:** narrow the test to reject an L3 or draft-mode condition on **loading the resume reference**, while allowing the explicitly required L3 condition on printing the off notice.
