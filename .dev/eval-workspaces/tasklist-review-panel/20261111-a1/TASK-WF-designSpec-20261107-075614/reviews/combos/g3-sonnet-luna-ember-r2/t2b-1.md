## Grading check (blocking finding F1)

An implementer who follows the stated text as written builds a test that compares the full live S5a and Wave 6 pre-push sentences byte-for-byte against constants that contain only their start text, and that test is wrong because a start-text constant can never equal the full sentence, so the Task 10 acceptance criterion cannot pass as written (or passes only as a prefix check that is not byte-identical).

## Findings

### Blocking

**F1 (MAJOR, blocking, unpassable-check): Task 1 records only the start text, Task 10 demands byte-identical proof from it.** Task 1 (O4) requires recording "the literal start text of the S5a sentence and of the Wave 6 pre-push sentence", while Task 10 requires those sentences be "asserted byte-identical by comparing the live text with string constants (the literal start text recorded in `./artifacts/pre-build-gate.md`...)". A start-text constant proves only a prefix. The source (section 10) requires constants "taken from the existing pins", i.e. the full pinned text, not a start excerpt. As written, no test can both use only the recorded start text and prove byte identity of the whole sentence.

### Follow-up candidates (Medium and minor, not blocking)

- **F2 (MAJOR, Medium, other): Resume row 4 "re-enter" is underspecified.** Task 4 defines `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)` with no `applied_edits`, `target_sha`, or head inputs, yet its acceptance test says row 4 cases "each re-enter `release_decision` with `push_completed=True`". `release_decision` needs those inputs for rows 7-8 (`no_edits` vs `pushed`). An implementer must guess whether `resume_decision` returns `RELEASE` directly or the caller re-enters; the two readings give different `cause` values. Needs the intended caller and the `applied_edits` value pinned.
- **F3 (MAJOR, Medium, contradiction): Wave 0 bullet wording test is ambiguous.** Task 9 requires the bullet to state the L3 `--merge-guard off` line, while its test must fail when the bullet "names an L3 or `draft` condition" and "contains no `L3 only` or `draft` gate wording". A naive substring test for `L3` fails the required sentence; a gating-aware test passes. The plan should state the exact predicate (e.g. absence of a gating phrase, not absence of the token `L3`).
- **F4 (MINOR, note, missing-requirement): Classification tasks narrow the constraint.** The Constraints section correctly requires an entry for any line containing `gh pr`, `gh api`, or a git write verb, but Tasks 7, 8, and 12 each add entries only for lines matching `gh pr` or `gh api`. A `git push` line in the new ref (allowed by Task 8's fenced-command list) would be an unclassified hit. The tasks should repeat the full verb set or explicitly forbid git write verbs in the new text.

## Reviser brief

Revise only blocking finding F1: record the full pinned S5a and Wave 6 pre-push sentence text in Task 1 (or change Task 10 to a prefix assertion that matches the start text actually recorded). Do not edit F2-F4 in this cycle.
