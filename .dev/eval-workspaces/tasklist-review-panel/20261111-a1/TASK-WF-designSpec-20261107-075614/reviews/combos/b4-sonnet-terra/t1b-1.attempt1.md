## Findings

**F1: Task 4 `resume_decision` row 4 cannot do what it says with the stated signature (MAJOR, Medium, not blocking).**
- The stated signature is `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)`.
- Row 4 says "re-enter `release_decision` with `push_completed=True`". `release_decision` also needs `applied_edits`, `target_sha` and `cycle_id`, and row 8 compares `read.head_sha` with `target_sha`.
- `GuardAction` has no member meaning "re-enter release", so the action, reason and cause a row 4 test must assert are not defined.
- The Task 11 crash scenarios ("`landed` releases", "normal `push_completed` releases") need a real RELEASE.
- The Task 8 Resume section is not told where the held cycle's `target_sha` comes from.
- Grading check: an implementer who follows the text builds a `resume_decision` that either returns an invented marker action or calls `release_decision` with a made-up `target_sha`, and that is wrong because the head proof cannot succeed. This needs a guess about which reading the implementer picks, so it is Medium.
- The as-built code added optional `applied_edits`, `target_sha` and `cycle_id` parameters to cover this gap.
- Suggested fix: name the extra inputs in Task 4, or state that row 4 returns RELEASE and the SKILL then runs `release_decision`.

**F2: Task 9 Wave 0 bullet: required text and the test's pass condition conflict on wording (MAJOR, Medium, not blocking).**
- The bullet must carry no L3 or `draft` condition.
- The same bullet must say that "at L3 with `--merge-guard off`" the unprotected line is printed once and "no draft call is made".
- The acceptance criterion says the test fails when the bullet "names an L3 or `draft` condition".
- Grading check: an implementer who writes the test as "no `L3` and no `draft` anywhere in the bullet" builds a test that fails on the required text. This needs a guess that the intended condition is "gates the loading", so it is Medium.
- The as-built bullet does contain "At L3 with `--merge-guard off`", and its own text uses "draft" in `draft_guard_requested`, so the real test must be narrower than the criterion.
- Suggested fix: write the test as a gate-wording check, for example no "L3 only" and no "`--merge-guard draft` only" in the Wave 0 bullet.

**F3: Task 13 asserts something `git status` cannot show (MINOR, note).**
- The criterion says `git status --short` lists changes "under ... gitignored `.claude/` mirrors". Ignored files never appear there, so that part is vacuous.
- It is harmless: the real check is that no `.claude/` path except `settings.json` is staged.
- The untracked `.dev/eval-workspaces/` already present at base falls under `.dev/`, so it does not fail the check.

**F4: Task 3 `guard_status` reports `released` for a run that never engaged (MINOR, note).**
- At ordinal 3 with no guard record, `guard_status` returns `released`. A run that never engaged the guard therefore prints `merge_guard: released`.
- The plan and `source.md` both state this deliberately, and the test is pinned.
- It may mislead a reader into thinking a draft round trip happened. `off` would not fit either; only a documented gloss helps.
