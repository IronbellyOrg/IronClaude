**F1, Medium (labelled MAJOR). Task 4: the `resume_decision` signature cannot do what row 4 says.**
- Grading sentence: an implementer who follows the stated text builds `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)`, and its row 4 must "re-enter `release_decision`".
- Why that is wrong: `release_decision` also needs `target_sha` and `applied_edits`, which this signature does not carry. Without them the head check can never succeed, so the function holds or releases without proof.
- Why it stays Medium: it needs a guess between adding parameters (better) and a placeholder (worse). The plan never says which `GuardAction` row 4 returns, so its test cannot assert a result.
- Evidence: the built version in the repo added `applied_edits`, `target_sha` and `cycle_id` to `resume_decision`.
- Task 11 ("`landed` releases", "normal `push_completed` releases") depends on this.

**F2, Medium (labelled MAJOR). Tasks 3 and 4: a later cycle while the guard is still held leaves `published` pointing at the wrong cycle.**
- Grading sentence: an implementer follows engage row 7 (`HELD` gives `NOOP(already_held)`) and `held_cycle_published` (matches `guard.cycle_id`), and builds a guard whose `cycle_id` stays at the first cycle.
- Why that is wrong: if a first release is held (unreadable timeline, head mismatch) and a second cycle pushes, a crash after the second push's `push_completed` makes `published` false for the guard's cycle. No resume row matches and the PR stays draft after a confirmed push.
- Why it stays Medium: the plan states no requirement for this path, so it is an undefined state, not a stated text that does harm.
- Evidence: the built version added a `REBIND` action (`cycle_rebound`) to cover this.
