## Blocking

### F1. A later cycle is marked ready because an earlier cycle already pushed

An implementer who follows the stated text as written builds an `engage_decision` that, on every held guard, returns `NOOP` (`already_held`) and never changes `cycle_id`, plus a resume path that treats any `push_completed` for that stored id as publication and re-enters release. That is wrong because the pull request is marked ready while a later cycle's fixes are still only local.

Section 4.1 row 7, which Task 4 adopts as "all 11 rows, first match wins", is: phase `HELD` means `NOOP(already_held)`. Nothing in that row, or in the fold rows Task 3 adopts, writes the new cycle id when engage is a no-op. Task 3 then defines publication as a `push_completed` whose `cycle_id` equals the guard's stored id, recovered or not. Task 4 says a held guard with `published=True` and no dangling push re-enters `release_decision` with `push_completed=True`.

Concrete run, using only those rules:

1. Cycle `fix-1` is drafted and its push is logged. The release read is unreadable, so release row 5 holds. The phase stays `HELD` and `cycle_id` stays `fix-1`.
2. Cycle `fix-2` (or a CI cycle, Task 10) reaches engage. Row 7 returns `NOOP`. No new guard event is written, so the stored id stays `fix-1`. The `fix-2` edits are not pushed.
3. The run crashes. `detect_crash_window` returns nothing (the `fix-1` push already completed). `held_cycle_published` is true because that push carries `fix-1`.
4. Resume row 4 re-enters release and marks the pull request ready.

The goal in the candidate forbids that: ready only when that cycle's push is confirmed on the pull request head. `recovery.resolve_crash_window` cannot save this. On a landed push it appends `push_completed` and returns `"landed"`, which is the same publication bit.
