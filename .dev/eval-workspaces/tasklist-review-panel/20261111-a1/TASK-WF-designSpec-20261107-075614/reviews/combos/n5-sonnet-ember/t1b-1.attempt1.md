## Follow-up candidates (Medium, do not fail the review)

- **F1 (Task 4, row 4 of `resume_decision`):** the signature and the "re-enter `release_decision`" wording cannot both hold. In the built repo the function carries extra optional arguments (`applied_edits`, `target_sha`, `cycle_id`). With the default `target_sha=None` it returns HOLD for a `landed` crash instead of releasing. The text should say which of these it is:
  - the function returns RELEASE directly, or
  - the SKILL calls `release_decision` itself and the function only signals it.

  Task 11's "`landed` releases" test depends on the choice.
- **F2 (Task 9, Wave 0 test):** the acceptance criterion says the test fails when the bullet "names an L3 or `draft` condition". The task body says "no `L3 only` or `draft` gate wording". The bullet must also mention L3 (the `off` line) and the `draft_guard_*` event names. Say "gating condition" in the criterion.
- **F3 (Task 4):** the zero-edit test has a new cycle release a guard that an earlier cycle holds, and `release_decision` never compares `cycle_id` with the guard's own. If the earlier cycle's push never landed, the PR becomes ready with fixes still unpublished. Either require that cycle's push proof, or state that the earlier push is known to be confirmed.
- **F4 (Task 4):** `notes` carries `auto_merge_armed`, but no task says what the SKILL does with it. `source.md` G4 says converting to draft may disarm auto-merge, and the guard never re-arms it. A user's armed auto-merge could silently vanish. Add one requirement: report it, or restore it on release.

## Notes (minor)

- **F5:** `guard_status` with no record at ordinal 3 returns `released`. A halt with `draft_guard_unavailable` caused by a failed first read leaves no record. No task tests the override that reports `unavailable`.

- **F7:** the Task 11 scenario tests run a test-owned driver that applies the decisions. Checks such as "no `pr ready` at ordinal 2" test the driver, not the `SKILL.md` text. Tasks 9 and 10 only check wording.
