## Findings

All are graded Medium or minor. For each, the grading sentence needs a guess between two readings the text allows, or points at a requirement the plan never states. None meets the blocking test.

**F1 (Medium): row 4 of `resume_decision` needs inputs its signature does not carry.**
- Task 4 fixes `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)`.
- It also says row 4 re-enters `release_decision(... applied_edits, target_sha, cycle_id ...)`.
- An implementer who follows the signature as written builds a resume function that cannot test the head or the zero-edit proof. Its release path then never fires for `landed` or `published`, and Task 11's "landed releases" and "published releases before the re-trigger" can pass only if the driver does the release itself.
- The plan never says what row 4 returns. The crash record holds `target_sha`, and nothing passes it in.
- The existing implementation hit this and added three keyword arguments. Its docstring says a missing `target_sha` makes the guard hold.
- Medium because the implementer must guess between extending the signature and inventing placeholder values.

**F2 (Medium): the "every `gh` line" scan in Task 7 clashes with the repo-resolution test it must also pass.**
- Task 7 requires a static scan that every `gh` line carries `--repo` or a `repos/` path.
- It also requires the script to pass the `_RESOLUTION_SCRIPTS` tests. Those tests require a line with `gh repo view --json nameWithOwner` after the origin lookup, and that line has no `--repo`.
- A literal scan fails on the line the other test demands. The existing repo-scope check exempts it through `_REPO_RESOLVE`, and the plan does not say to reuse that exemption.

**F3 (Medium): the Wave 0 bullet is told both to carry no L3 condition and to say "at L3".**
- Task 9 says the bullet "carries no L3 or `draft` condition", and the test "fails when it names an L3 or `draft` condition".
- The same sentence requires the bullet to state that "at L3 with `--merge-guard off`" the unprotected line is printed, and that no draft call is made.
- A literal test fails the required text. The Task 9 body narrows the test to "L3 only" or `draft` gate wording, so an implementer has to pick that narrower reading.

**F4 (Medium): when a CI-fix cycle engages is not defined.**
- Task 8 puts "review-fix cycles and CI-fix cycles" under "Engage at the end of Wave 3, only when at least one verified finding of Medium or higher is routed to a fix".
- Task 10's Wave 8 bullet says a CI-fix cycle "engages with kind `ci`" with no finding condition.
- A failing CI check is not a verified Medium finding, and a CI-fix cycle has no end of Wave 3.
- Task 8 also asks for "the single place" where the cycle id is minted, while fix ids and CI ids come from two waves.
- An implementer must guess between engaging every CI-fix cycle and never engaging one.

**F5 (minor): Task 13 never stages anything.**
- Its acceptance criterion requires `.dev/tasks` to be staged with `git add .dev/tasks`.
- The task body has no staging step.
- "Gitignored `.claude/` mirrors" also cannot appear in `git status --short`.

**F6 (minor): the classification step names only `gh pr` and `gh api`.**
- Tasks 7, 8 and 12 add classification entries only for lines that match `gh pr` or `gh api`.
- `WRITE_VERB_RE` also matches `git add`, `commit`, `push`, `merge` and `stash`. A ref or command line that says "git push" would need an entry too.
- The Constraints section covers git write verbs, so the acceptance test would catch a miss. The task steps do not mention them.
