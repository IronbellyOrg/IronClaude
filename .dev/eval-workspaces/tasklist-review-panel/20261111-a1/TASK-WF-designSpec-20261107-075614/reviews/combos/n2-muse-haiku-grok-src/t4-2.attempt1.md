## Blocking findings

### F1. A later cycle's unpushed fix is marked ready

An implementer who follows the stated text as written builds an engage step that, while the guard is already held, does nothing for every new cycle id, and a resume step that treats the old cycle's completed push as proof of publication and marks the pull request ready. That is wrong because the newer cycle's fixes are still only on the machine.

Task 4 says to implement all 11 engage rows, first match wins. Row 7 of the source table that sentence points at is "phase held, do nothing", with no check that the cycle id changed. Task 3 says publication is true when any completed push carries the guard's current cycle id. Task 8, from source section 3, says an unreadable timeline after engage does not release and keeps pushing. Task 10 then starts a CI-fix cycle with a new id. Resume row 4 sees the old push, calls release with publication true, and marks the pull request ready. The plan's own goal says ready is allowed only when that cycle's push is on the pull request head.

### F2. A crashed CI-fix cycle posts a review re-trigger

An implementer who follows the stated text as written builds a resume step that, after a CI-fix push is confirmed, releases the draft and then runs the review re-trigger. That is wrong because a CI-fix cycle must re-poll CI and must not request another review.

Task 11 says a crash after a normal completed push releases before the re-trigger, and Task 8 says the resume section is taken from source section 5, whose crash traces then run the S5a re-trigger. Task 10 says a CI-fix cycle releases after the push and before the CI re-poll. The existing Wave 8 text says an L3 CI push must not call the re-trigger script, and `crash_resume_plan` sends a landed `ci` push to the CI wait, never into a review state. One resume procedure cannot do both.
