## Blocking findings

### F1. Resume row 4 cannot perform the release head check: `resume_decision` is given no `target_sha` or per-cycle edit count to pass to `release_decision`

Task 4 defines `release_decision(*, mode, ordinal, cycle_id, guard, read, applied_edits, target_sha, push_completed)` with release row 8 requiring `push_completed` and `read.head_sha == target_sha`, and defines `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)` with row 4 re-entering `release_decision` with `push_completed=True`. Neither `resume_decision`'s inputs, nor the folded guard record of Task 3 (fields `phase, phase_before_request, cycle_id, original_is_draft, baseline, run_toggles, unsettled, failed_mutations, owned_draft, disabled_cause`), carry the pushed cycle's target SHA or its applied-edit count. So no implementation of the stated signatures can both release the normal-`push_completed` resume case that Task 11 requires (a crash after a normal `push_completed`, `published` true, releases before the re-trigger) and hold when the PR head has moved after that push: the two cases differ only in a SHA the function never receives. Passing `read.head_sha` as its own target makes row 8 always true and releases a moved head; passing `None` makes row 8 never true and the published case never releases.

Grading check: An implementer who follows the stated text as written builds `resume_decision` with only the seven stated inputs re-entering `release_decision` for row 4, and that is wrong because `release_decision` can only confirm the fix push is on the PR head by comparing `read.head_sha` to a `target_sha` that no stated input, event fold field, or Task 8 Resume step supplies, so the row either releases without the head confirmation the goal requires or never releases a normally published cycle.

Fix direction (for the reviser, not applied here): give resume a way to know the held cycle's pushed SHA, for example an optional `target_sha` (and `applied_edits`) parameter on `resume_decision` sourced by the SKILL from the held cycle's `push_completed` event, and state in Task 8 which event field the SKILL reads it from; add a Task 4/Task 11 case where `published` is true and the live head differs from that SHA, expecting `HOLD`.

- F2 (Medium). Task 9's Wave 0 bullet is described both as carrying "no L3 or `draft` condition" and as stating the L3 `--merge-guard off` print, and its acceptance says the test fails when the bullet "names an L3 or `draft` condition" while the test description in the same task only forbids "`L3 only` or `draft` gate wording". Grading: this needs the worse of two readings to do harm, so it is Medium, not blocking.
- F3 (Medium). The engage table (all 11 rows via Task 4) makes a `HELD` guard a `NOOP(already_held)` for any cycle, and `held_cycle_published(events, guard)` judges publication against the guard record's single `cycle_id`. The plan never states what happens when a later cycle (for example a CI-fix cycle) begins while an earlier cycle is still `HELD`: no new request is appended, so the guard keeps the earlier cycle id and a resume can judge the later cycle's release against the earlier cycle's `push_completed`. The plan should either state that a new cycle cannot start while `HELD` (and which step enforces that) or state how the guard record follows the new cycle.
- F4 (minor). The constraint requires a `WRITE_VERB_CLASSIFICATION` entry for every new line containing `gh pr`, `gh api` or a git write verb, but Tasks 7, 8 and 12 each only require entries for lines matching `gh pr` or `gh api`. A new git write line in the script, the ref or the command file would be an unclassified hit and fail `test_every_write_verb_hit_is_classified` at the end of a task whose own acceptance includes that test file. Align the per-task wording with the constraint.
- F5 (minor). Task 11's forbidden-call assertion for an originally draft PR only forbids "`pr ready` without `--undo`" in the fake `gh` log. Because the script checks state before calling, a wrongly routed `--to draft` attempt on an already-draft PR also produces no `pr ready` call, so this assertion alone cannot detect it; the scenario should also assert the `skipped/already_draft` settle (or that the script was never invoked with `--to`) for that case.

Reviser brief: repair only F1 in the candidate; F2 to F5 are follow-up candidates and must not be edited in a fix cycle for this review.
