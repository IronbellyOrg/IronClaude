## Blocking finding

**F1, safety.** An implementer who follows the stated text as written builds a fold where a failed draft request ends in phase `RELEASE_PENDING` with `owned_draft` still false, and the next engage decision then returns `HOLD` and never drafts the pull request, which is wrong because later waves still apply the fix on a mergeable pull request.

The fold acceptance rule says a failed draft settle sets `RELEASE_PENDING` and does not change `owned_draft`. A new guard record does not set `owned_draft` (only a confirmed draft settle sets it true). Engage row 6, which Task 4 says to implement with the other ten rows, first-match, is: phase `RELEASE_PENDING` and not `owned_draft` returns `HOLD(ownership_unproven)`. That row sits before the "already draft" row and before any retry. So a draft call that failed, including one that actually landed, is never retried and never confirmed. The plan's own halt rule covers only the attempt that just failed. On `--resume` the request is already settled, so it is not reconciled, and Wave 4 still applies edits. The goal says the pull request is turned into a draft as soon as a verified Medium-or-higher finding is routed to a fix. This path never does that again.

## Follow-up candidates

**F2, Medium (major label, not blocking).** The script task says the static test rejects every `gh` line that lacks `--repo` or a `repos/` path, and the same bullet says the script must pass the origin-resolution tests. Those tests require a `gh repo view --json nameWithOwner` fallback, which is the one `gh` call that must not carry `--repo` because the repo is not known yet. A literal reading fails a correct script. The other reading copies the existing scoped-command check and allows that fallback. The worse reading is a guess, so this does not fail the review.

**F3, Medium (major label, not blocking).** The Wave 0 bullet must say the unprotected line is printed at L3 with the guard off, and must not be gated on L3. The acceptance line also says the test fails when the bullet "names an L3 or `draft` condition". Read as "must not be gated" (the same task's "L3 only" and "draft gate" wording), the required bullet passes. Read as "must not mention L3", the required bullet fails its own test. That depends on the worse reading.

**F4, Medium (major label, not blocking).** `resume_decision` is specified without `applied_edits`, `target_sha` or `cycle_id`, but row 4 re-enters `release_decision`, which requires all three. The crash tests say a landed push releases. Passing `applied_edits=0` releases via `no_edits` and skips the head check. Passing the real edit count and target SHA releases only when the head matches. The plan never says which arguments the re-entry uses.
