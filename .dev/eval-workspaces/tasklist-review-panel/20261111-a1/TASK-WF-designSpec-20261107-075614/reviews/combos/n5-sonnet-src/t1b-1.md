## Findings

### F1 (Medium): `resume_decision` row 4 cannot call `release_decision` with the stated inputs

An implementer who follows the stated text builds `resume_decision` with exactly eight keyword inputs. Row 4 must "re-enter `release_decision`", which also needs `applied_edits` and `target_sha`. Those two inputs are not in the signature, because `release_decision` row 7 and row 8 read them. The implementer must either add inputs or have row 4 return a release without the head check. The second choice breaks the rule that release needs a confirmed push on the PR head. It is Medium because the text allows the sound reading of adding inputs. The existing code did add `applied_edits`, `target_sha` and `cycle_id` to this function. The acceptance criteria also say "the row 4 result" without defining the returned action.

### F2 (Medium): No rule for deriving this cycle's applied-edit count

Task 4 requires `applied_edits` to be this cycle's count, not the run-wide field. Task 8 repeats "this cycle's applied-edit count". Neither task says where the SKILL gets that number. If it passes the run-wide field, a zero-edit cycle after a fixing cycle holds the PR draft instead of releasing it. This is a missing requirement, so it is Medium. Task 11 tests the pure function with a hand-set count, so no test would catch a wrong source in the protocol text.

### F3 (Medium): The Wave 0 bullet "carries no L3 condition" yet must say "at L3"

Task 9 says the bullet "carries no L3 or `draft` condition". The same task requires it to say that "at L3 with `--merge-guard off`" the line is printed. The acceptance criterion fails the test when the bullet "names an L3 or `draft` condition". Read literally, the real bullet fails its own test. The natural reading is that loading the ref is not gated, while the `off` notice names L3. The implementer must narrow the test to guess that reading, so it is Medium.

### F4 (minor): "Exact event order" is stricter than the source

Task 11 asks for the "exact event order" of seven events. The source says they "must appear in this order", and its sequence also writes `push_initiated` between `fix_applied` and `push_completed`. A strict consecutive match fails if the driver writes `push_initiated`. Compare a filtered sequence instead.

### F5 (minor): `--read` with a failed timeline call leaves `ok` and the exit code open

Task 7 says a failing timeline call prints `transitions: null` and `complete: false`. It also says a failing `gh` exits 1 with `ok:false`. If `ok` is false, the engage and release rows for an unreadable read win over the timeline rows. The outcome is the same (halt or hold), but the reason text differs.
