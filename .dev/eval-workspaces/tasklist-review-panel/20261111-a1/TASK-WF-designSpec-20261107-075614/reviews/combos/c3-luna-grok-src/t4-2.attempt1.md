# Critique: merge-guard implementation plan

The plan matches its design on the event count, the pure module boundary, the draft script's exit codes, the flag default, and the pins that forbid editing the re-trigger sentence or the pre-push sentence. One stated path breaks the guard's safety rule. The rest are follow-ups.

## Blocking

### F1. A failed draft attempt, once resumed, lets fixes land on a still-mergeable pull request

An implementer who follows the stated text as written builds a fold where a failed draft settle sets the phase to release-pending and leaves ownership false, and an engage decision that returns hold rather than halt for that state. A resumed run then keeps editing. That is wrong because the pull request was never turned into a draft, so the fixes are mergeable. This breaks the guard's safety boundary.

The failure row is explicit: a failed draft settle moves to release-pending, counts a failed mutation, and does not change ownership. On a first engage, ownership is still false, because only a confirmed draft settle sets it. The engage table the plan says to implement in full (design section 4.1, row 6) then returns hold for "ownership unproven", not halt. The first run does halt, because the failure story says to stop before any edit. Resume is a different path. The failure is already settled, so nothing is pending. Resume row 9 is a no-op. The Wave 0 bullet then continues into the normal waves. The next engage hits the same hold and does not stop the run. Edits and a later push proceed while the pull request is still ready.

Nygard: the failure is recorded, and the recovery path treats it as "do not touch the draft flag" instead of "do not edit". Whittaker (sequence): fail the draft call, settle it, resume, and the hold no longer means halt.

## Follow-up candidates

Medium (do not fail this review):

- F2. The status map returns "user override" only when the disabled cause is user override. The effect row for that settle sets the phase and clears ownership, and it never sets the cause. The already-draft row shows the table names the cause when it means to set it. A literal fold does not produce the status the report requires. An implementer can still pass the status test with a hand-built record.
- F3. Resume is specified with no edit count, no target commit, and no cycle id, but row 4 must call the release decision, which needs all three. Release returns "no edits" whenever the edit count is 0, and that row is checked before the head matches. Passing 0 marks the pull request ready without proving the head. Passing no target leaves a landed push on hold, so the pull request stays draft. The plan never says which value to pass.
- F4. While the guard is already held, engage row 7 is a no-op and does not move the stored cycle id. A later cycle still mints its own id and the push uses that id. Publication is true only when a completed push carries the guard's stored id. A crash after the later push can leave the pull request draft. This needs a second cycle to start while the first is still held (the design says an unreadable timeline keeps pushing). That extra step is why this stays a warning.

Minor:

- F5. Task 10 says the re-trigger sentence and the pre-push sentence are byte-identical to the "literal start text" Task 1 records. The existing pins are fragments, not the whole sentence (the re-trigger pin starts at "AFTER resolve", mid-sentence). Asserting the whole sentence equals that fragment fails. Asserting the fragment is still present passes. Use the second reading.
