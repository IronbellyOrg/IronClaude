## Architecture and failure behaviour

The guard record is one folded value, not a new monitor state, and the module is forbidden from importing recovery. That split matches the code: recovery already imports the run log, so the import the plan forbids would cycle.

Two failure edges are not closed by the stated text:

- Resume is told to call the release decision with only "the push completed", but that function is not given this cycle's edit count or the commit it should see on the pull request. Release treats zero edits as "mark ready" before it compares the commit. An implementer who passes zero edits, so that "the push landed, so release" passes without a commit to compare, marks the pull request ready when the fix is not confirmed on the pull request head (finding F1). The safe reading is to add those two values to the resume call. That reading is a guess, so this does not fail the review.
- A failed attempt to make the pull request a draft stores "release pending" and does not record that this run owns the draft. The next engage then returns "hold, ownership unproven", and the plan never says that this hold stops edits. The same-run failure does halt. A later resume does not (finding F4).
