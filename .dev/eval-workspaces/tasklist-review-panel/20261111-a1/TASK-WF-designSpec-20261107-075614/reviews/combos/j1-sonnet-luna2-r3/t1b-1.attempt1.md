## Findings

I graded each finding with "An implementer who follows the stated text as written builds X, and X is wrong because Y." None of the sentences holds without a further assumption, so none is blocking.

**F1 (Medium): `resume_decision` cannot carry the data it must hand to `release_decision`.**
- An implementer who follows Task 4 builds `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)`.
- Its row 4 must "re-enter `release_decision`". That function needs `cycle_id`, `applied_edits` and `target_sha` (release rows 7 and 8), and none is in the signature or in the folded `guard`.
- With no `target_sha`, row 8 can never match, so the "`landed` releases" and "normal `push_completed` releases" criteria (Tasks 4 and 11) cannot pass as written.
- A default of `applied_edits=0` would release on the `no_edits` row without a head proof.
- The plan never says which values resume passes, or which action row 4 returns. The criterion "gets the row 4 result" has no defined result.
- This is Medium because the implementer must add parameters and pick defaults the text does not give.

**F2 (Medium): the Wave 0 bullet rule and its test criterion disagree on "L3".**
- Task 9 says the bullet "carries no L3 or `draft` condition", yet it must state that "at L3 with `--merge-guard off`" the line is printed.
- The body's test wording is "no `L3 only` or `draft` gate wording". The criterion says the test fails when the bullet "names an L3 or `draft` condition".
- Read literally, the required sentence fails the criterion.
- The implementer picks between a narrow reading (gate wording only) and a broad one (no L3 mention at all). This is Medium.

**F3 (Medium): the "exact event order" assertion does not say whether it is a subsequence.**
- A real cycle also writes `push_decision` and `push_initiated`, per section 5 of `source.md`, between `fix_applied` and `push_completed`.
- Whole-log equality against the seven listed events fails against a driver that follows the push triad. Dropping the triad events contradicts the same section 5 text.
- Filtering to the seven events is the sound reading, but the text does not say so.

**F4 (minor): "every `gh` line" is too broad in Task 7.**
- Read literally, it also catches `command -v gh` and the `gh repo view --json nameWithOwner` fallback.
- That fallback line is required by the `_RESOLUTION_SCRIPTS` tests, which Task 7's next criterion also requires. Neither line carries `--repo`.
- The existing `_repo_scoped` helper already exempts the resolution idiom, so naming that helper would remove the clash.

**F5 (minor): exit codes for `not_open` are unstated.**
- Task 7 gives exit 1 "on a failing `gh`", and its `verify_failed` output follows `source.md`.
- `not_open` is not a `gh` failure, and its exit code is not stated or tested.

**F6 (minor): the final `git status --short` check lists ignored files.**
- Task 13's check says `git status --short` lists "gitignored `.claude/` mirrors". It never lists ignored paths.
- That clause is vacuous and can mislead.
