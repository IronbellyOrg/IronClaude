That scan fails on the origin-resolution fallback line `gh repo view --json nameWithOwner` and on the `command -v gh` line.
- Task 7 also requires the script to pass the `_RESOLUTION_SCRIPTS` tests and be modelled on `retrigger-review.sh`. Those tests require the `gh repo view` fallback line.

- Medium, not blocking: the implementer has to pick one of two readings and the better one is clear.

**F2 (Medium, non-blocking): the Wave 0 bullet wording in Task 9 is ambiguous.** The bullet must carry "no L3 or `draft` condition". The same task requires the bullet to say that "at L3 with `--merge-guard off`" the unprotected line prints.
- The acceptance criterion says the test fails when the bullet "names an L3 or `draft` condition".
- The test description in the task body says only that it rejects "L3 only" or `draft` gate wording.
- Read the strict way, the mandated `off` sentence fails its own test. The implementer has to choose the narrower test (a gate on loading the ref), which is the intended one.

**F3 (minor): the pinned-sentence check in Task 10 is weaker than its name.** The byte-identical assertion for the S5a and Wave 6 pre-push sentences compares against "the literal start text" that Task 1 records. A start-text constant would not catch an edit made later inside a sentence, which is exactly what the "after, never inside" rule is meant to prevent. Task 1 should record the full sentence.

**F4 (minor): the classification step names too few verbs.** The classification instructions in Tasks 8, 9, 10 and 12 name only `gh pr` and `gh api` lines. `WRITE_VERB_RE` also matches `git add`, `commit`, `push`, `merge`, `stash`, `update-ref` and `worktree add|remove`. A new ref or command line that mentions `git push` or `git commit` in prose would be unclassified until the test fails. The top-level Constraints already cover git verbs, so this is a consistency gap only.
