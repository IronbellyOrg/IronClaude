## Findings

No finding passes the grading check for blocking. For each one below, the sentence "an implementer who follows the stated text builds X, and X is wrong because Y" needs a guess about which reading the implementer picks, or rests on a requirement the document never states.

**F1 (MAJOR, Medium). A held guard is not tied to a later cycle.**
- Task 3 says `held_cycle_published` matches the guard's `cycle_id`.
- Task 4 says `engage_decision` has 11 rows. In the source tables the row for a held guard returns `NOOP(already_held)`.
- Nothing updates the guard's `cycle_id` when a later cycle reuses the draft. The source marks this case as unreleased in the "unreadable timeline" row.
- Scenario: cycle `fix-1` pushes, then release holds on an unreadable timeline. Cycle `fix-2` finds the guard already held and engages as a no-op. A crash then happens before the `fix-2` push, and on resume `held_cycle_published` finds the `fix-1` push and returns true.
- Resume row 4 then re-enters release, and the PR may be marked ready with `fix-2`'s fixes unpublished. Whether it releases depends on which `target_sha` the SKILL passes on resume, and the plan never says. That is why this is Medium.
- Task 11's crash tests cover only a single cycle, so they would not catch this. The repo's merge-guard ref has a `REBIND` action that closes exactly this gap, which suggests the design missed it.

**F2 (MAJOR, Medium). Task 3's `guard_status` and fold criteria leave two wrong implementations passing.**
- The source fold row for `settled(any, skipped, user_override)` sets the phase to `DISABLED` but never says `disabled_cause = user_override`, yet `guard_status` keys on that cause. No Task 3 criterion covers that fold row.
- The `guard_status` criteria test mode `off` only with no record. A reading where `mode == OFF` alone maps to `off` would also pass those criteria. It would hide a held PR on `--resume --merge-guard off`, which the plan's own Resume text says must be reported as held.

**F3 (MAJOR, Medium). The Task 9 Wave 0 bullet wording is ambiguous.**
- The body requires the bullet to "carry no L3 or `draft` condition".
- The body also requires it to say that "at L3 with `--merge-guard off`" the line is printed, and to say "no draft call is made".
- The criterion says the test fails when the bullet "names an L3 or `draft` condition". A literal test written from the criterion fails on the required sentence.
- A narrower reading, where only gating wording such as "L3 only" counts, passes. The implementer can reword, so the criterion is passable and the finding is Medium.

**F4 (MINOR). The CI-fix engage trigger is undefined.**
- Task 8 and Task 10 route CI-fix cycles through an engage whose only stated trigger is "a verified finding of Medium or higher routed to a fix".
- A failing CI check is not a review finding. The text does not say what triggers engage for a CI-fix cycle.

**F5 (MINOR). The place where the cycle id is minted is stated two ways.**
- Task 1 and Task 8 defer the minting place to the open item O1.
- Task 10 fixes it in the Wave 3 bullet ("mints the cycle id").
- If O1 finds the id is assigned elsewhere today, Task 10's bullet would add a second source.

**F6 (MINOR). The acceptance trace in Task 11 says "exact event order".**
- The real flow also appends `push_initiated` between `fix_applied` and `push_completed`.
- The source says the events must appear "in this order", which means a subsequence. The word "exact" can fail a correct driver.

**F7 (MINOR). The exit code for `error:"not_open"` is unspecified.**
- Task 7 lists exit 1 only for a failing `gh` or a failed verification.
- `not_open` is neither, so a test cannot assert its exit code.

**F8 (MINOR). Byte-identical checks compare only a start text.**
- Task 10 compares the live sentences against "the literal start text" recorded in Task 1.
- That proves only the beginning of each pinned sentence, not that the whole sentence is unchanged.
