## Follow-up candidates

**F1 (Medium).** Resume is specified with no target commit and no edit count, but a landed fix may be marked ready only when the live head equals that commit. An implementer who follows the stated text as written builds a resume function that re-enters the release decision with only "push completed" set, and that is wrong on one of the two readings the text allows: either a landed fix never becomes ready (the release rule holds when the head does not match a target the function never receives), or it becomes ready without checking the head (by pretending the cycle edited nothing). The scenario tests only pass if a later parameter is added. That is a gap, not a sentence that fails on every reading.

**F2 (Medium).** A failed attempt to make the pull request a draft is specified to leave the guard waiting to release, with ownership unchanged, which on a first attempt means not owned. The resume table then does nothing when the pull request is still ready. The plan never says that resume halts again or tries the draft again, so a resumed run can keep editing a pull request that is still mergeable. That behavior is absent from the plan, not required by a sentence that is already wrong.
