## Findings

### F1. Resume cannot prove the push it is required to release

Grading check: An implementer who follows the stated text as written builds a `resume_decision` that takes only mode, ordinal, guard, read, pending, dangling branch, and published, and whose landed and published-push rows return the result of `release_decision` called with the push marked completed. That result is wrong because a ready release for a real push is allowed only when this cycle's edit count is not zero and the live head equals the target commit, and neither value is an argument of `resume_decision` or a field of the guard record.

Task 4 fixes the signature and says row 4 re-enters `release_decision` with the push marked completed. Task 4 also says `release_decision` holds when the head differs from `target_sha`, and returns a zero-edit release only when `applied_edits` is 0. Task 11 requires the landed branch and a normal completed push with no dangling window to release. `GuardRead` (section 4.1) has the live head and not the target commit. The fold fields listed in Task 3 do not include the target commit or the edit count. `resolve_crash_window` returns `"landed"` and does not pass a target commit into the guard.

Every return that satisfies the landed and published release checks is therefore one of two unproved releases: a zero-edit release (row 7 runs before the head check), or a release that treats the live head as its own target. Both mark the pull request ready without the publication proof the release rule requires. There is no way to satisfy the signature, the row 4 call, and the crash-test release together.

### F2. An engage halt with no guard record is reported as released

Grading check: An implementer who follows the stated text as written builds `guard_status` so that ordinal 3 with no guard record reports `released`, including when engage halts because the timeline cannot be read, before any guard event is written. That report is wrong because section 4.1, which Task 3 says to implement, says a halt whose reason is `draft_guard_unavailable` reports `unavailable`.

Task 8 orders the steps as read, decide, then append the request before the mutation. Rows 3 and 8 of `engage_decision` halt at decide time, so no request is written and the fold stays empty. Task 3's acceptance test requires that empty case to be `released`. Task 8 also says the output field is the `guard_status` mapping, so the exit report cannot substitute `unavailable` without failing that test. The same halt is both required (Task 8) and mapped to the value section 4.1 reserves for "this run never held the pull request."

### F3. A later fix cycle while the guard is already held never takes that cycle's id

Medium. Task 4 row 7 is `NOOP(already_held)` for every held guard, with no cycle check. Task 11 says a validation failure leaves the phase held. A later cycle, including the CI-fix engage Task 10 requires, then does not store its own id. `held_cycle_published` looks up the earlier id, so a crash after the later cycle's completed push does not take the published release. This needs a second cycle to start while the phase is still held, which the happy path avoids by releasing in Wave 6 first. The plan never states that case.
