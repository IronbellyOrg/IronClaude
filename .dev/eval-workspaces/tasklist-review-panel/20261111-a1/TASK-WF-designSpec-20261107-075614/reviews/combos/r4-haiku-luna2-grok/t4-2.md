## Follow-up candidates

**F1. Medium. The draft script's repo fallback.** An implementer who follows the stated text as written builds a script where every `gh` line, including the origin fallback, carries `--repo`, and also adds that script to `_RESOLUTION_SCRIPTS`. That pair is not yet a broken acceptance check: the resolution test stubs `gh` and ignores arguments, so both checks can pass. It is the worse reading of the two rules. The existing scope check treats bare `gh repo view` as the one allowed unscoped call, because that call is how the repo is discovered. Pinning `--repo "$REPO"` on it runs the discovery call with an empty repo. Grade is Medium because harm (fail closed, or gh's default repo) depends on which reading the implementer picks.

**F2. Medium. Ready request that did not apply.** An implementer who follows the stated text as written builds a fold that both restores the previous phase for every direction and, for a ready request followed by not_applied, returns HELD. Those agree when the previous phase was already HELD. They disagree if the ready request is the first guard record: restore yields no record, and the ready sentence demands HELD. HELD with ownership left false can later mark the pull request ready. Grade is Medium because the sentence does not say the ready request is the first record; the draft sentence next to it does.

**F3. Medium. Wave 0 bullet versus its own test.** An implementer who follows the stated text as written builds a Wave 0 bullet that says the off line is printed at L3 with `--merge-guard off`, and a test that fails when that bullet names an L3 or draft condition. The same task also says the test fails on "L3 only" or draft-gate wording and must contain the off line. The off line itself has neither "L3" nor "draft". Grade is Medium because a test aimed at gate wording passes, and a test aimed at any "L3" mention does not.

**F4. Medium. Resume re-entry has no edit count or target SHA.** An implementer who follows the stated text as written builds `resume_decision` with no applied-edit count, target SHA, or cycle id, then re-enters `release_decision` with only `push_completed=True`. `release_decision` returns `RELEASE` / `no_edits` when the count is 0, before it compares the head. The plan never says which count or SHA the re-entry uses. Passing 0 marks the pull request ready without a head match. Passing nothing and requiring a head match makes "landed releases" fail. Grade is Medium because the document never states the arguments, rather than stating a wrong value.

**F5. Minor. Idempotency parenthetical.** The plan says leave `tests/pr_submit/test_idempotency.py` (7 sets) unchanged. That file has six tests, and its own comment calls one of them the 6th set. Leaving it unchanged is still right. The count is only a label.

No blocking finding. An acceptance check can still be written for every case the plan fully states. The four Medium items are the worse of two readings, or a value the plan never sets.
