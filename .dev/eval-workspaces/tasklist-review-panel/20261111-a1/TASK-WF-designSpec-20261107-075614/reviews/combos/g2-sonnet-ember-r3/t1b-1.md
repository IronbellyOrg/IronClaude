## Follow-up candidates (Medium and minor, none blocking)

**F1 (Medium).** Task 12 names the section "Merge guard" (with a space). Its acceptance criterion says `grep -n "merge-guard"` must show the section heading. An implementer builds a heading "Merge guard", and the grep does not show it, because the heading has no hyphen. The text also allows "Merge guard (`--merge-guard`)", which passes. The real file uses that form. Fix: name the heading text in the task.

**F2 (Medium).** Task 7 lists exit codes 0, 1, 2 and 127. The `not_open` result (`ok:false`, not a `gh` failure and not a failed verification) has no stated exit code, and no criterion asserts one. An implementer builds exit 0 for it, which is wrong if a caller reads only the exit status and treats it as success. The wrong outcome depends on how the caller is written, which the plan does not fix.

**F3 (Medium).** Task 9 says the Wave 0 bullet "carries no L3 or `draft` condition". The same task requires it to say "at L3 with `--merge-guard off`" and "no draft call is made". Read literally, the criterion's test fails on the bullet's own required text. The real test strips the `off` line before scanning. Fix: say which part of the bullet the scan excludes.

**F4 (Medium).** Task 10 requires the S5a and Wave 6 pre-push sentences to be "byte-identical" against string constants. Task 1 records only the "literal start text" of them. A constant that holds only the start proves the start, so an added sentence inside the pinned sentence would pass. Fix: record and compare the full pinned sentences.

**F5 (Medium).** `source.md` says a halt with reason `draft_guard_unavailable` reports `unavailable`. Task 3 and Task 8 only carry "the first-match mapping", and no criterion tests the halt case. When the timeline is unreadable at engage there is no guard record, so `guard_status` at ordinal 3 returns `released`. An implementer who follows the candidate text alone reports `merge_guard: released` for a run that halted because the guard was unavailable. The real ref handles it. Add a criterion.

**F6 (minor).** The constraints say ordinals 0 to 2 "change only by one report line". Tasks 4, 8 and 9 also add held-guard reporting on resume below ordinal 3, and a `merge_guard` output row that prints `off` there. No behaviour is mutating, but the scope sentence is inaccurate.

**F7 (Medium, hedged).** `held_cycle_published` matches a `push_completed` against the guard record's own `cycle_id`. The Wave 3 bullet mints a new id every cycle, even when engage returns `NOOP(already_held)`. If a second routed cycle starts while the first guard is still held and unpublished, and the run crashes after that second push but before release, `published` stays false. The PR stays draft and is reported `held`. This is the safe direction, but it is stuck until a human clears it. Whether the run can reach a second cycle after a failed validation is not stated.

**F8 (minor).** The force-push line test scans every `.md` and `.sh` file under the skill directory, including the new `refs/merge-guard.md` and `set-draft-state.sh`. The candidate limits that warning to new `SKILL.md` lines. Task 8's existing-test run would catch a hit, so this is only a missed warning.

**F9 (minor, UNVERIFIED).** Release requires the live head to equal `target_sha` right after the push, with one retry only for a failed mutation. If the API lags behind the push, the result is `HOLD(head_mismatch)` with no re-read. G1 to G6 do not cover this timing. Consider adding it to the disposable-PR checks.
