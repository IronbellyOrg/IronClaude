## Blocking finding

### F1. Resume row 4 cannot re-enter the release decision with the inputs the plan gives it

Grading check: An implementer who follows the stated text as written builds `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)`, whose row 4 must re-enter `release_decision(*, mode, ordinal, cycle_id, guard, read, applied_edits, target_sha, push_completed)`, and that call is wrong because `resume_decision` receives neither this cycle's `applied_edits` nor its `target_sha`, so the release proof the goal requires (head equals `target_sha`, or a zero-edit proof for this cycle) cannot be checked from the stated inputs.

This is not a wording nit. The folded guard record defined in Task 3 carries no `target_sha` and no per-cycle edit count, and `resume_decision` is given no event list from which either could be recovered. An implementer therefore has only bad options, and each one passes some stated test while breaking another stated requirement:

- Call `release_decision` with invented values. Passing `target_sha` taken from the live read makes the head check tautological, so a PR whose head moved to a different commit is marked ready, contradicting the release rule in Task 4 and the moved-head halt required by the scenario task. Passing no target makes row 4 hold forever, so the crash-after-a-normal-`push_completed` case in Task 11 never releases before the re-trigger.
- Skip the re-entry and return `RELEASE` directly from row 4. That readies the PR on `published` alone, with no head or zero-edit proof at all.
- Add the missing parameters. That is the right fix, but it is not what the plan states, and Task 8's Resume section, which is written from the same signature, never tells the protocol to pass a target or an edit count to resume either, so the protocol and the pure core disagree about who owns the proof.

Concrete wrong outcome: after a crash following a completed push, a resumed run either leaves a correctly pushed PR draft forever (reported `held`, user must clear it by hand) or marks a PR ready whose head was never proven to be the held cycle's push. Both outcomes violate the candidate's own goal that release happens only when that cycle's fix push is confirmed on the PR head.

Fix direction for the reviser: give `resume_decision` the two missing inputs (or a stated derivation of them from data it already receives, for example the held cycle's push record), and make Task 8's Resume steps pass them, naming where the protocol obtains the held cycle's `target_sha` after a crash.

## Follow-up candidates

These are Medium and minor findings. They do not fail this review, do not trigger a revision, and are not part of the Reviser brief.

### F2 (Medium). A later cycle that engages while the guard is still held has no stated way to take over the guard

Task 4's own acceptance text proves the situation occurs: a release decision is called "for a new cycle while the guard record already holds an earlier fixing cycle". Yet the engage table the plan adopts returns `NOOP(already_held)` for a held guard regardless of which cycle is asking, and no task states a rebind, a cycle-id update, or any other step that moves the folded `cycle_id` to the new cycle. The consequence an implementer can produce is that publication and head checks keep being judged against the earlier cycle: `held_cycle_published` answers for the old cycle's push, so a resumed run can treat the new cycle as published when only the old push landed, or hold a new cycle whose push did land because the guard still names the old one. I grade this Medium rather than blocking because reaching it needs the worse reading that a second cycle starts before the first is released, and the ordinary release path's head check limits the damage; the plan never states the takeover rule either way.

### F3 (Medium). The Wave 0 bullet test is written two incompatible ways

Task 9's body asks for a test that the bullet "contains no `L3 only` or `draft` gate wording", while Task 9's acceptance criteria ask for a test that fails "when it names an L3 or `draft` condition". The same bullet is required to state that "at L3 with `--merge-guard off`" the unprotected line is printed, so it necessarily names L3. An implementer who writes the acceptance-criteria version literally (for example asserting `L3` is absent from the bullet) produces a test the required bullet can never pass; an implementer who writes the body version produces a test that does not enforce the acceptance wording. The intended check is evidently about gating wording on the resume clause, not about the letters L3, but the plan does not say that in the acceptance criteria, so the outcome depends on which of the two stated texts the test author follows.

### F4 (Medium). `guard_status` for a held guard under `--merge-guard off` is left to a coin flip

Task 3 adopts the first-match mapping of source section 4.1, whose first clause gives `off` when the mode is `off`, and Task 4 simultaneously requires that mode `off` at ordinal 3 with phase `HELD` returns `REPORT_HELD`, a behaviour that only makes sense if a held record outranks the mode in the exit report. Task 3's acceptance cases test mode `off` only with no guard record, so both implementations pass the plan's tests while disagreeing on the one case that matters for the exit report: a run that finds a held guard with the guard switched off either reports `held` with the clear command or reports `off`, telling the user nothing is guarded while the PR is in fact an unmergeable draft. The draft itself still blocks a merge, so this is a reporting defect, not a safety breach, and it is Medium.

### F5 (Minor). The per-task classification steps are narrower than the plan's own constraint

The plan's constraints require a `WRITE_VERB_CLASSIFICATION` entry for every new line containing `gh pr`, `gh api` **or a git write verb**, but the closing steps of Tasks 7, 8 and 12 only instruct entries for lines matching `gh pr` or `gh api`. A ref or script line carrying a git write verb would therefore be left unclassified by an implementer who follows the task step instead of the constraint, and the stale-entry and unclassified-hit tests run in those same tasks would then fail for a reason the task text never names. The constraint text is correct and discoverable, so this is a note, but the task steps should repeat it in full.
