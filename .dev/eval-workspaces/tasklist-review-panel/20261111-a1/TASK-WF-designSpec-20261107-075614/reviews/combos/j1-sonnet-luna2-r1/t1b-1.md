## Findings, each with the grading sentence

**F1 (MAJOR, graded Medium): the `resume_decision` signature cannot supply what its row 4 needs.**
An implementer who follows the stated text builds `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)` and makes row 4 "re-enter `release_decision`". That is wrong because `release_decision` row 8 needs `target_sha` and row 7 needs this cycle's `applied_edits`, and the signature carries neither. The Task 4 criterion also never says what row 4 returns. The implementer must invent extra parameters or hard-code values; passing `read.head_sha` as the target would make the head proof vacuous. The existing build had to add `applied_edits`, `target_sha` and `cycle_id` keyword arguments to this function. Medium because the implementer can pick the sound reading.

**F2 (MAJOR, graded Medium): after one failed engage the guard can never engage again.**
An implementer who follows the stated fold rows and engage rows builds this. `settled(draft, failed)` gives `RELEASE_PENDING` with `owned_draft` false, and engage row 6 then returns `HOLD(ownership_unproven)` for every later engage. I ran the built code: after one failed engage, a ready and unguarded PR gives `HOLD ownership_unproven` for cycle `fix-2`. It is wrong because the plan only says "halt `draft_guard_unavailable`" for the failing run. On `--resume`, or in any later cycle, the plan states no handling for an engage `HOLD`. The built ref says "keep going and report `unavailable`", which lets edits and the push proceed with the PR mergeable. Medium because what the SKILL does on an engage `HOLD` is never stated.

**F3 (MAJOR, graded Medium): the Task 9 Wave 0 bullet is told to carry no L3 condition and an L3 condition.**
An implementer who follows Task 9 literally gets two requirements: the bullet "carries no L3 or `draft` condition", and it says "at L3 with `--merge-guard off`" the unprotected line is printed. Taking the first literally prints the line at every ordinal. That is wrong because `source.md` 4.3 says the flag is inert below `--monitor 3`. The wording test "contains no `L3 only` or `draft`" is also unclear about whether it greps the bare words. Medium because the natural reading (the ref-loading hook is ungated, only the print is L3) is available.

**F4 (MAJOR, graded Medium): "single mint place" conflicts with the Wave 8 CI-fix cycle, and the CI trigger is missing.**
An implementer who follows Tasks 1, 8 and 10 gets these texts:
- Task 1 and Task 8 want one place that mints the cycle id.
- The Wave 3 bullet mints it "at the end of Wave 3".
- The Wave 8 bullet engages a CI-fix cycle "with kind `ci`" and gives no severity trigger.

A CI failure has no verified-finding severity, so the "Medium or higher routed finding" trigger either never fires for CI or is dropped. It is also unclear where a `ci-<n>` id is minted if the CI-fix cycle does not pass through the end of Wave 3. Medium because the implementer must choose between the readings.

**F5 (MAJOR, graded Medium): a lagging PR head after a good push has no stated handling.**
An implementer who follows Task 8 builds Release as one read that requires "head equals `target_sha`". GitHub can show the old head for a few seconds after a push. That single read then gives `HOLD(head_mismatch)` and the PR stays a draft. The S5a re-trigger runs next, and gate G5 (do the reviewers act on draft PRs?) is unverified. A round could therefore be spent on a draft PR. The text has "one retry" only for a failed mutation, and never says whether the re-trigger waits on a `HOLD`. Missing requirement, so Medium.

**F6 (MAJOR, graded Medium): resume below ordinal 3 reports and does not reconcile, contrary to `source.md` section 3.**
An implementer who follows Task 4 builds "ordinal 2, `ENGAGE_PENDING`, non-empty `pending` gives `REPORT_HELD` (row 2 wins over row 3)". `source.md` section 3 says that on `--resume` at any ordinal "unsettled requests are reconciled before any edit". Below ordinal 3 the request therefore stays unsettled. The report says `unavailable` while the PR may really be a draft, and it only settles at a later L3 resume. Medium because the candidate is consistent with `source.md` row 2, and the conflict is inside `source.md` itself.

**F7 (MINOR): Task 7 says the static scan asserts "every `gh` line" carries `--repo` or a `repos/` path.**
The same script must keep `gh repo view --json nameWithOwner` as the origin fallback, because the `_RESOLUTION_SCRIPTS` tests require that line. Read literally, the scan would fail on it. The existing `_repo_scoped` helper exempts that line. The fix is to reuse `_repo_scoped`.

**F8 (MINOR): Task 7 gives no exit code for the `not_open` case.**
Task 7's exit-code list names 0, 1, 2 and 127. A `--to ready` on a merged PR prints `ok:false` with `error:"not_open"`, and that is neither "failing `gh`" nor "failed verification", so the code is left to the implementer.
