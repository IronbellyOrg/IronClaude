## Verdict
Not ready as written. The dependency order, the sync-dev cadence and the CORE_PURE rules hold up, but two acceptance criteria can't pass as literally written (F1 and F7). Two decision contracts are under-specified (F2 and F3). There is also one release-safety gap the card missed: a held guard keeps the earlier cycle's id (F8). Of the card's F1 to F7, all seven are confirmed. F7 is widened and raised to MAJOR.

## Findings (prose)
- **F1 confirmed (MAJOR, blocking).** Plan:108 says every `gh` call carries `--repo "$REPO"` or a `repos/` path. Plan:113 has the test assert that statically, and also requires the script to pass the `_RESOLUTION_SCRIPTS` tests. Those tests need a `[ -n "$REPO" ] || REPO="$(gh repo view --json nameWithOwner ...` line (tests/pr_submit/test_static_grep.py:545-550, model at scripts/retrigger-review.sh:50), and that line has neither. The wording comes from the spec itself (source.md:377). The repo's own predicate `_repo_scoped` accepts the resolution idiom (test_static_grep.py:126-129). The plan names the stricter rule, so the criteria contradict each other.
- **F2 confirmed (MAJOR).** Resume row 4 says "re-enter `release_decision` with `push_completed=True`" (source.md:166). But `resume_decision`'s parameters (source.md:109, plan:70) have no `cycle_id`, `applied_edits` or `target_sha`, all of which `release_decision` needs (source.md:107). So the criterion at plan:77 can't be built as specified. Repo evidence: the later implementation had to add all three, with `max(1, applied_edits)` and a HOLD when `target_sha` is missing (src/superclaude/pr_submit/merge_guard.py:528-572).
- **F3 confirmed (MAJOR).** source.md:112 says a halt with reason `draft_guard_unavailable` reports `unavailable`. But `guard_status(guard, mode, ordinal)` has no halt input. Engage rows 3 and 8 halt before any request is written, so the guard record is `None`, and plan:61 pins "no record at ordinal 3 gives `released`". No task assigns the override (Task 8 at plan:124, Task 11 at plan:166). The real `guard_status` has no halt branch either (merge_guard.py:339-362); the override was only added later as a protocol test.
- **F4 confirmed (MINOR).** The `user_override` fold row (source.md:206) never sets `disabled_cause`. The fold criterion (plan:60) tests only `already_draft`, while `guard_status` keys on the cause (source.md:112).
- **F5 confirmed (MINOR).** The baseline is recorded before `make install` and `make sync-dev` (plan:33). Task 13 then accepts any failure already in that baseline (plan:199). docs/memory/reflect/deviation-patterns-post-release-v5.0.0.md:7 records about 43 mirror failures in fresh worktrees. Task 13 does re-run `make verify-sync` and the two sync-hook test files separately, which narrows but does not close the gap.
- **F6 confirmed (MINOR).** `GuardRead` uses `is_draft`, `head_sha` and `auto_merge_armed` (source.md:88-91), but the script prints `isDraft`, `headRefOid` and `autoMergeRequest` (source.md:230). No task owns the conversion. The shipped ref only lists the JSON keys (refs/merge-guard.md:35-36).
- **F7 confirmed and widened (MAJOR, not MINOR).** The Wave 0 bullet must say "at L3 with `--merge-guard off` ... no draft call is made" (plan:137, source.md:241). The test must fail when the bullet "names an L3 or `draft` condition" (plan:140). Both the word `L3` and the word `draft` are required in the bullet, so the literal criterion can't pass. The spec contradicts itself at source.md:241. Repo evidence: the shipped test had to strip "the three parts that may name an ordinal, L3 or the draft events" before scanning (tests/pr_submit/test_merge_guard_protocol.py:407-411).
- **F8 new (MAJOR, safety).** The fold table never says which event sets the fold's `cycle_id` (source.md:190-206). Engage row 7 `HELD` → `NOOP(already_held)` (source.md:139) leaves a held guard on the earlier cycle. `held_cycle_published` checks `guard.cycle_id` (source.md:108). A failure sequence follows:
  1. Cycle 1 pushes, but its release is held because the timeline is unreadable.
  2. Cycle 2 makes edits and the run crashes before the push.
  3. On resume, `published` is true from cycle 1's push, so row 4 re-enters release (source.md:166).
  4. Without a cycle-2 `target_sha` (F2), the PR can be released while cycle 2's fixes are still local.
  The plan's criteria (plan:62, plan:77) test only single-cycle cases. The implementation had to invent a `REBIND`/`cycle_rebound` action (refs/merge-guard.md:74).
- **F9 new (MINOR).** Task 10 claims the S5a and Wave 6 pre-push sentences are asserted "byte-identical", but against "the literal start text" only (plan:33, plan:154). A start-text match can't catch an edit later in the sentence. The shipped constant is only `"- **Wave 6 (L3 only):**"` (test_merge_guard_protocol.py:556).
- **F10 new (MINOR).** The classification steps in Tasks 7, 8 and 12 (plan:108, :124, :182) list only `gh pr`/`gh api` lines with a single verb key. But `WRITE_VERB_RE` also matches `git add`, `commit`, `push`, `merge` and `stash` (tests/skills/test_worker_contract.py:2019-2021), and a line with two verbs is keyed as `"a+b"` (test_worker_contract.py:2067-2072). The constraint at plan:22 names git write verbs, but the per-task steps don't. A Pre-push or Release sentence in the ref that names `git push` needs an entry, and the instruction gives the wrong key shape. The stale-entry test would catch this, but only after a failed run.
