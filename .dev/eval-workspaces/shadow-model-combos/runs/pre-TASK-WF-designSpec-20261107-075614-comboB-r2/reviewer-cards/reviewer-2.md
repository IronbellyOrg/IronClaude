## Findings (prose)

- **F1 — MAJOR, blocking: an unavailable guard can be reported as released.** The spec requires `unavailable` after a `draft_guard_unavailable` halt, including a failed initial read that creates no guard record. Task 3 explicitly tests that no record at ordinal 3 reports `released`; Task 8 delegates reporting to that mapping without specifying a halt-reason override. Add an end-to-end reporting criterion for both read failure and unreadable timeline before the first request. This confirms T1 F3. Evidence: source.md:112, plan:61, plan:124.

- **F2 — MAJOR, blocking: the resume-release criterion lacks the inputs needed to prove publication.** Task 4 requires `resume_decision` to re-enter `release_decision`, but its signature omits `target_sha`, `applied_edits`, and `cycle_id`. In particular, `published=True` proves that a push-completed event exists, not that the current head equals the intended target. The criterion cannot establish the required release proof through the declared interface. Specify whether the caller performs the release check or provide the necessary inputs, then test a moved head during resume. Evidence: source.md:107-109, source.md:156-166, plan:70-77.

- **F3 — MAJOR, blocking: Task 7 requires incompatible repository-scoping checks.** Joining `_RESOLUTION_SCRIPTS` requires the origin-first resolution sequence, including its `gh repo view --json nameWithOwner` fallback, as shown in the supplied grounding. That resolution call has neither `--repo` nor a `repos/` path, so the separate "every `gh` line" scan rejects it. The existing repository-scope predicate expressly permits this resolution idiom. Make the new scan distinguish repository resolution from PR/API operations. This conflict is also inherited by the spec's test-hygiene wording. Evidence: source.md:221, source.md:377, plan:108-114.

- **F4 — MINOR, non-blocking: the fold-to-status test misses the user-override cause.** The status mapping requires `disabled_cause == "user_override"`, but the corresponding fold row specifies only `DISABLED` and `owned_draft=False`. Task 3's detailed cause assertion covers `already_draft`, while its status test can use an independently constructed guard. Those tests can pass even when a folded override cannot produce the required status. Add a settle → fold → status assertion. This confirms the narrow test gap in T1 F4; the cause omission starts in the spec's fold table. Evidence: source.md:112, source.md:206, plan:60-61.

- **F5 — MAJOR, non-blocking: emitted guard-event payloads lack a discriminating acceptance check.** The spec defines the exact request-key format, attempt numbering, first-request-only fields, and skip payload. Task 3 tests matching keys supplied to the matcher, Task 8 directs event appends without spelling out that producer contract, and Task 11 checks event order. None explicitly checks that the event producer generates those fields and distinct retry keys correctly. A matcher test with hand-built valid keys would not catch a producer that reuses attempt keys. Evidence: source.md:184-185, plan:62, plan:124, plan:168-172.

- **F6 — MINOR, non-blocking: the matrix omits requirement-bearing spans.** The 66 inferred rows contain no explicit units for the full event payload contract, preservation of corrupt-line rejection, the one-retry release-failure contract, or complete dependency declarations. Some have plan coverage—Task 11 incorporates the twelve scenario contracts—but they are absent from the inventory used to claim coverage. Add those units before treating the union percentage as evidence of exhaustive coverage. Evidence: source.md:184-185, source.md:208, source.md:315, source.md:363.

T1 cross-check: I did **not** adopt F5 as a demonstrated defect: its stale-environment premise is unverified here, and Task 13 independently requires successful sync and installation checks. I also did **not** adopt F6 as a missing named adapter: the protocol's read/decide steps and scenario driver can perform the JSON-to-`GuardRead` conversion; different field names alone do not prove an uncovered requirement. Evidence: plan:124, plan:166, plan:199.
