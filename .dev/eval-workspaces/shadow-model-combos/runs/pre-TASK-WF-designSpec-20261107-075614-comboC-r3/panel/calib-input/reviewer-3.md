# Reviewer 3 card (refactorer): UC-1 pre-execution reflection, Tier 2

## Summary

The task structure mostly holds up against the base commit. I found no import cycle, the event-count and key-set pins are named correctly, and the script and test-import approach follows existing code. I found six problems. One is MAJOR. The function that decides what to do on resume is told to re-enter the release decision, but it is not given the commit, edit count or cycle it needs to do that. The other five are MINOR:
- the Wave 0 resume bullet is placed only relative to Wave 1, which is too loose;
- the plan does not say that the whole Wave 6 line is already pinned;
- three test files are edited by tasks with no declared order between them;
- four tasks rely on Task 1's output without declaring it as a dependency;
- the per-task classification wording covers fewer verbs than the Constraints rule.

## Findings

**F1 (MAJOR, missing-requirement): the resume decision cannot supply what the release decision needs.** In Task 4, `resume_decision(*, mode, ordinal, guard, read, pending, dangling_branch, published)` must "re-enter `release_decision` with `push_completed=True`" for row 4 (plan:70, plan:77). `release_decision` also needs `cycle_id`, `applied_edits` and `target_sha` (spec:107, spec:166). None of these is a `resume_decision` input, and no task says where they come from. An implementer could take `target_sha` from the live `read.head_sha`, which would make release row 8's head check always pass. Or they could pass `applied_edits=0`, which hits row 7 and releases with cause `no_edits` instead of `pushed`. The plan should say:
- `cycle_id` comes from `guard.cycle_id`;
- `target_sha` comes from the dangling `push_initiated` record when the branch is `landed`, or from the cycle's `push_completed` event when `published` is true (the head-binding bullet at base `SKILL.md:275` already takes it from the record);
- `applied_edits` is this cycle's count, which is at least 1 once a push exists.

It should also add a test that fails when `target_sha` is taken from the live read. This agrees with T1 recommendation 1.

**F2 (MINOR, other): the Wave 0 resume bullet is placed only "before Wave 1".** Task 9 says the new Wave 0 bullet only has to come before the Wave 1 bullet, and its test checks only that (plan:137, plan:140). At the base commit, Wave 0 has three bullets in order: all ordinals (`SKILL.md:274`), head binding (`:275`) and conflict check (`:276`). On `--resume`, the head-binding bullet is where `resolve_crash_window` produces the branch. The guard's Resume section needs that branch as `dangling_branch`. A bullet placed right after `SKILL.md:274` would describe guard resume running before the branch exists. Task 9 should require the bullet after the "Wave 0 head binding" bullet, and the test should check that order too.

**F3 (MINOR, other): the whole Wave 6 line is already pinned, not just two sentences.** Task 10 protects only "the S5a re-trigger sentence and the Wave 6 pre-push sentence" and allows "new sentences after, never inside, the pinned sentences" (plan:150, plan:154). At the base commit, the entire Wave 6 bullet is one physical line (`SKILL.md:282`). That line is a `WRITE_VERB_CLASSIFICATION` key, keyed on its exact stripped text (`tests/skills/test_worker_contract.py:1199-1206`, verbs `git add+git commit+gh pr+git push+gh api`). The same is true of the three Wave 0 lines (`:1167-1190`). Appending a sentence to the end of that bullet makes the entry stale and fails `test_classification_table_has_no_stale_entries`. Task 10 should say the Wave 3, 6 and 8 additions are separate bullet lines, and that the existing Wave bullet lines stay byte-identical as whole lines. That whole-line pin is also a stronger byte-identity proof than comparing only the sentences' start text.

**F4 (MINOR, other): the same files are edited by tasks with no declared order.**
- `tests/pr_submit/test_static_grep.py` is edited by Task 5 (`CORE_PURE_FILES`, plan:85) and Task 7 (`_RESOLUTION_SCRIPTS`, plan:108). Task 7 depends only on Task 1 (plan:106), and Task 5 only on Tasks 3 and 4 (plan:82-83).
- `tests/pr_submit/test_merge_guard_protocol.py` is extended by Tasks 9, 10 and 12. Task 12 (plan:179-180) has no order against Tasks 9 and 10 (plan:134-135, plan:148). These tasks may also add `WRITE_VERB_CLASSIFICATION` entries to `tests/skills/test_worker_contract.py`.

A parallel or reordered executor could produce conflicting edits. Add `Depends on: Task 5` to Task 7 and `Depends on: Task 10` to Task 12.

**F5 (MINOR, missing-requirement): Task 1 dependencies are only implied.** The spec says a task depends on every earlier task whose output it uses, and that "the protocol tasks need the pre-build record" (spec:363). These tasks all use `./artifacts/pre-build-gate.md` but reach Task 1 only through other tasks:
- Task 9 uses the recorded pins (plan:137) and declares only Tasks 6 and 8;
- Task 10 uses the O4 start text (plan:154) and declares only Task 9;
- Task 12 uses the pins (plan:182) and declares only Tasks 6 and 8;
- Task 13 compares against the base-commit record (plan:195, plan:199) and declares Tasks 2, 10, 11 and 12.

Add `Depends on: Task 1` to Tasks 9, 10, 12 and 13.

**F6 (MINOR, contradiction): per-task classification wording is narrower than the rule.** Constraints line 22 requires a classification entry for every new line with `gh pr`, `gh api` *or a git write verb*. Tasks 7, 8 and 12 say only "every line that matches `gh pr` or `gh api`" (plan:108, plan:124, plan:182). `WRITE_VERB_RE` also matches `git push`, `git add` and the other git write verbs (base `test_worker_contract.py:1098-1101`). Task 8's Pre-push and Release prose is a likely place for one. The `git remote get-url` line the script copies is not a write verb, so the gap matters mainly for the ref and the command file. These tasks should say "every line that `WRITE_VERB_RE` matches". This agrees with T1 recommendation 4.

**Rows checked and found sound at the base commit:**
- No import cycle. The package `__init__` imports `classifier`, `conflicts`, `detection`, `fsm`, `models`, `reviewers` and `severity_router`, but not `run_log` (`__init__.py:22-96`). `recovery` imports `run_log` (`recovery.py:37`), which is why `merge_guard` must not import `recovery`.
- `_NEW_KEY_DEFAULTS` and the exact key-set asserts (`test_run_log.py:312-317`, `:403-404`) match what Task 5 describes.
- `test_allowed_tools_cover_every_program` scans only `NEW_REFS`, and scripts are not granted one by one in `allowed-tools` (`test_conflict_sync_protocol.py:35`, `:587-611`; `SKILL.md:4`). So Task 8's own "the `scripts/` path exists" check is the right proof.
- `_RESOLUTION_SCRIPTS` requires the origin `sed` line and origin before `gh repo view` (`test_static_grep.py:479-549`). The model script `retrigger-review.sh` satisfies both.
- One test module importing from another has a precedent (`test_conflict_sync_protocol.py:21`).
- The cycle ids `fix-<n>` and `ci-<n>` do not collide with the reserved prefixes (`conflicts.py:1242-1244`).
