## Findings

- **F1: `cycle_id` is never rebound (confirmed T1-F1).**
  - The fold field list names `cycle_id` (spec 190). No effect-table row (spec 194 to 206) sets or changes it after the first request.
  - Engage row 7 returns `NOOP(already_held)` for a later cycle (spec 139). `held_cycle_published` and resume row 4 key on `guard.cycle_id` (spec 108, 166).
  - A second cycle that reuses a held draft is therefore judged against the earlier cycle's push. Task 3 (plan 52 to 60) has no criterion for this.
- **F2: Task 8 narrows the spec's source sections (confirmed T1-F2).**
  - Spec 240 says the protocol ref carries "sections 3 and 4.1 to 4.4". Plan 124 builds it from sections 3, 4.1, 4.5, 4.6 and 5.
  - Sections 4.2 (event fields, key format, baseline), 4.3 and 4.4 (the `--read` JSON) are dropped. Task 8's acceptance criteria never ask the ref to state the event fields, yet it tells the SKILL to append `draft_guard_requested`.
- **F3: the `unavailable` halt vs. `guard_status` (confirmed T1-F3).**
  - The spec says a halt with `draft_guard_unavailable` reports `unavailable` (spec 112).
  - The read-failed and timeline-unreadable halts (engage rows 3 and 8, spec 135 and 140) happen before any request event. With no record, first-match returns `released`.
  - The Task 3 test (plan 61) pins "no record at ordinal 3 (released)". The Task 4 engage tests do not cover this.
- **F4: a failed first engage leaves a dead-end state.**
  - `settled(draft, failed)` sets `RELEASE_PENDING` and leaves `owned_draft` unchanged (spec 199). On a first request `owned_draft` is false.
  - Engage row 6 then returns `HOLD(ownership_unproven)` without looking at `read.is_draft` (spec 138). Resume row 8 at least checks "live draft" (spec 170); engage row 6 does not.
  - If the draft call failed without landing, the PR is ready and unguarded. Later cycles hit row 6 and never re-engage, while `guard_status` reports `unavailable`.
  - Task 3 covers the fold row (plan 60). Task 4 covers each engage row in isolation (plan 70). No criterion covers "first engage failed, then a later cycle or resume".
- **F5: resume row 4 outranks rows 5 and 6 when `published` is true.**
  - Row 4 fires on `landed or published` (spec 166). Rows 5 and 6 test `dangling_branch` only afterwards (spec 167, 168).
  - If an earlier push completed normally (`published` true, and stale per F1) and a later push left `dangling_branch == "ambiguous"`, row 4 re-enters release with `push_completed=True`. That bypasses `HOLD(ambiguous_remote_tip)`.
  - Release row 8 still checks `head_sha == target_sha`, which limits the damage.
  - Task 4 tests `published=True` only with `dangling_branch is None` (plan 77).
- **F6: `guard_status` wording is ambiguous for mode `OFF` with a held record.**
  - Spec 112 reads "`mode == OFF` or `ordinal < 3` with no guard record gives `off`". It can mean OFF always wins, or only OFF-with-no-record.
  - Resume row 2 (spec 164) shows a held draft under mode `OFF` must be reported held with the clear command. Under the first reading the output field would say `off` while the PR is still draft.
  - Plan 61 tests only mode OFF with no record.
- **F7: resume row 6 has no phase condition.**
  - Row 5 requires phase `HELD`. Row 6 (`ambiguous` gives `HOLD`) does not (spec 167, 168).
  - A `RELEASED` or `DISABLED` guard with an ambiguous dangling branch still returns a HOLD for a guard that holds nothing. Row 2 exempts those phases, but nothing exempts them from row 6.
  - Plan 77 tests `ambiguous` only for the `HELD` case.
