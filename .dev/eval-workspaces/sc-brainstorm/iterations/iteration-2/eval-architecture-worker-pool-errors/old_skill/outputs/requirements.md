# Requirements: Redesign Error Handling Across the Worker Pool

> Generated by `/sc:brainstorm "redesign error handling across the worker pool" --strategy enterprise --depth deep`
> Protocol: v1 (monolithic, in-context personas)

## Intro

The worker pool's error handling is inconsistent and has caused production incidents. We need a unified approach. This is an enterprise-depth brainstorm covering taxonomy, DLQ design, replay tooling, observability, and migration.

---

## Phase 0 — Codebase Context

There are around 12 worker fleets sharing a base library at `internal/workers/base/`. The base has a basic retry helper at `base/retry.py` used by some fleets. Two fleets have homegrown DLQs (`ingest-workers/dlq.py` and `webhook-delivery-workers/failed_queue.py`) with different schemas. The rest have ad-hoc try/except sprawl in their handlers.

Q1 had three incidents traced to error-handling bugs — email-dispatch burned SMTP credits with infinite retries, image-processing thrashed pods on a corrupt input, and webhook-delivery silently dropped customer webhooks.

## Phase 1 — Socratic Exploration

**Q1. Is this one service or a class of services?**
A: Twelve fleets sharing a base library. Each has overridden error semantics.

**Q2. What's driving this now?**
A: Three Q1 incidents and a $40k retry-cost spike that the CFO noticed.

**Q3. What does "done" look like?**
A: Canonical error library, standardized DLQ, per-fleet SLOs, all 12 fleets migrated, quarterly chaos tests.

**Q4. Any non-negotiable constraints?**
A: No message loss for billing-critical fleets. Backward-compat with in-flight messages. <2-week migration chunks per fleet. <5% latency overhead.

**Q5. Rollback plan?**
A: Per-fleet feature flag in the base library. Old code marked deprecated for 2 weeks before deletion.

**Q6. What's the worst-plausible failure of the new design itself?**
A: A misclassified retryable error retried forever (same failure mode, new mechanism). Or the unified DLQ becoming a SPOF.

**Q7. Future state in 12 months?**
A: All fleets sharing taxonomy, DLQ has self-service replay UI, retry-induced spend ≤1/4 of today's, new fleet onboarding ≤1 day.

## Phase 2 — Multi-Persona Analysis

### Architect

Build a unified error subsystem with typed error classes (Retryable, NonRetryable, Poison), a DLQ contract, and a replay tool. Refactor `base/retry.py` in place. Each fleet migrates by replacing try/except sprawl with subsystem calls. Per-fleet DLQ with a shared replay tool — the industry consensus from Shopify and Slack engineering blogs. Migration takes ~2-3 quarters across 2-3 platform engineers.

### DevOps

Migrate by pain order, not architectural cleanliness. The three Q1-incident fleets go first: email-dispatch, image-processing, webhook-delivery. Then billing-critical (billing-batch, ingest). Then the 7 small fleets as a final pass with code-mod assistance. Build the on-call runbook for DLQ operations explicitly; "replay them" is not a runbook. Set DLQ retention policies per fleet. Rate-limit replay tools by default.

### QA

The chaos harness must ship with the MVP, not after fleets are migrated. The Q1 incidents are exactly the failure modes that integration tests miss and chaos tests catch. Eight test classes: transient retry, deterministic fail-fast, poison quarantine, downstream rate-limit storm, DLQ unavailability, attempt-bounded retry, replay-rate-limit enforcement, replay-audit completeness. Each fleet's migration must demonstrate all eight against its own handler.

### Security

The DLQ is a data-exposure surface. Per-fleet IAM (`dlq:read:<fleet>`, `dlq:replay:<fleet>`), no engineer-wide default. PII redaction at DLQ-write time (producer schemas tag PII fields). Audit log for every read/write/replay with operator justification. Retention caps (30 days default). Replay sandbox mode for billing-critical fleets. MFA on the future web UI.

### Performance

The 5% latency budget is hard, not soft. Hot-path overhead must be ≤100µs p99 enforced by per-PR benchmark. Async DLQ writes (don't block worker liveness). Batched audit-log writes. Bounded-cardinality metrics (no per-message labels). Run email-dispatch in shadow mode first because it's the highest-volume fleet — latency regressions show up there first.

## Phase 3 — Validation

Feasible across all domains. The main risk is migration timing — 12 fleets across 2-3 quarters with platform engineering throughput is tight but doable. The chaos harness shipping at MVP (vs later) is the most contested point — QA insists, architect agrees, DevOps wants to defer. QA's position is correct: the Q1 incidents are the failure modes the harness catches.

## Phase 4 — Specification

### Functional Requirements

- Build `internal/workers/errors/` subsystem with typed error taxonomy.
- Per-fleet DLQ on a shared envelope schema (Kafka and Postgres impls).
- Shared CLI replay tool with rate-limit and sandbox mode.
- Audit log on every DLQ write/read/replay.
- PII redaction at DLQ-write time.
- Chaos harness with 8+ test classes shipping at MVP.
- Per-fleet feature flag for rollback.
- Per-fleet observability dashboard.
- Migration order: incident fleets first, then billing-critical, then bulk.

### Non-Functional Requirements

- Hot-path overhead ≤100µs p99.
- Retry-induced cost reduced ≥4× by end of Q3.
- Zero billing-critical message loss.
- Aggregate throughput floor ≥13M msg/hour (current ~15M).
- DLQ retention 30 days default.

### Acceptance Criteria

- All chaos tests green per fleet before migration done.
- Per-fleet error-rate SLO defined with alerting.
- Per-fleet runbook published.
- 2-week canary soak with zero billing-critical loss.
- Per-PR latency benchmark green.
- End-of-Q3 cost reduction ≥4× from Q1 baseline.

### Risks

- Misclassified retryable error causing infinite-retry-equivalent.
- DLQ unavailability cascade (Cloudflare-2023 pattern).
- Latency regression causing fleets to disable subsystem.
- PII leak via failed-message audit.
- Replay-throttle bypass becoming default.
