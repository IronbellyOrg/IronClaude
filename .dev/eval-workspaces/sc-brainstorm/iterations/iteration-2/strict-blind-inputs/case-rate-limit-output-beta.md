## Phase 1 — Socratic Exploration

Eight questions driving requirements discovery, with plausible user-style answers (non-interactive eval):

**Q1. Which API endpoints need rate limiting — all public endpoints, or a specific subset (auth, write-heavy, expensive operations)?**
A: All public endpoints to start, with stricter limits on auth (login, password-reset) and write operations.

**Q2. What is the rate-limiting unit — per IP, per API key, per authenticated user, or a combination?**
A: Combination: per API key for authenticated traffic, per IP for unauthenticated traffic. API key limits should be configurable per-customer-tier.

**Q3. What algorithm — fixed window, sliding window, token bucket, leaky bucket?**
A: Token bucket preferred — smooths bursts while enforcing average rate. Sliding-window log as fallback for endpoints needing strict fairness.

**Q4. Where does the limiter live — application middleware, reverse proxy (nginx/Envoy), API gateway, or a dedicated service (Redis-backed)?**
A: Application middleware for fine-grained control + Redis for shared state across instances. Reverse-proxy limiting as a coarse outer ring.

**Q5. What happens when a client exceeds the limit — 429 + `Retry-After`, queue and delay, or hard-drop?**
A: Standard `429 Too Many Requests` with `Retry-After` header. Also expose `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset` on every response.

**Q6. How configurable do limits need to be — static config, per-tier (free/pro/enterprise), per-endpoint, or fully dynamic via admin?**
A: Per-tier defaults overridable per-endpoint, with an admin override path. No live-tuning UI for v1 — config file + restart is acceptable.

**Q7. Are there bypass requirements — internal services, health checks, admin operations, allowlist IPs?**
A: Yes — health/liveness checks, internal service-to-service traffic (mTLS), and an admin allowlist must bypass.

**Q8. What observability is required — metrics on throttled requests, per-key consumption, alerting on systemic throttling?**
A: Prometheus counters for throttled count by route + key tier, plus a log entry per throttle with key-id (hashed). Alert when >5% of any endpoint's traffic is being throttled for >5 minutes.

## Phase 2 — Multi-Persona Analysis

Five personas coordinated in-context (no subagent spawning — v1 pattern). Each gives ~300 words.

### Architect

A rate-limiting layer for a public API is fundamentally a **cross-cutting concern** and belongs in middleware, not in handlers. The first architectural decision is where in the request path the limiter sits: too early (edge proxy) gives coarse IP-level protection but loses key/tier awareness; too late (per-handler decorator) repeats work and is hard to audit. The right shape is a single ASGI/WSGI middleware that runs *after* auth (so it knows the principal) but *before* business handlers, with a tiered fallback so that even unauthenticated paths get IP-bucket protection.

State storage is the second decision. Single-instance deployments can use an in-process counter, but anything serious needs shared state — Redis is the industry default because INCR + EXPIRE is atomic and cheap (~0.5ms p99 in-region). The architectural risk is **Redis becoming a SPOF**: if Redis is unreachable, the limiter must fail-open (allow traffic, log the degradation) rather than fail-closed (refuse all traffic). This is a deliberate availability-over-correctness trade.

Algorithm choice should be **token bucket** for smoothness with burst tolerance. Reject fixed-window for its boundary-spike problem (a client can send 2× the limit by straddling a window boundary). Sliding-window-counter is a fine alternative if Redis Lua scripts feel too heavy.

Cross-cutting integration points to surface in the design phase: (1) request ID propagation so throttled requests are traceable, (2) the `X-RateLimit-*` header contract is part of the public API and needs versioning discipline, (3) the limiter MUST emit the same metrics surface as the rest of the API (Prometheus, OpenTelemetry trace spans).

Recommend `/sc:design` next focus on: middleware composition order, Redis topology (primary/replica vs cluster), fail-open semantics, and the public header contract.

### Analyzer

Root-cause framing: *why is rate limiting being added now?* The brief doesn't say. Three plausible drivers, each leading to different requirements:

1. **Abuse defense** — bots, scrapers, credential-stuffing. Drives per-IP + per-key limits, low burst tolerance on auth endpoints, CAPTCHA-on-threshold escalation. Security-led.
2. **Capacity protection** — preventing one tenant from starving others. Drives per-key tier limits, fairness-focused algorithm (sliding window), graceful degradation. SRE-led.
3. **Commercial enforcement** — tier monetization (free=100 req/min, pro=10K req/min). Drives configurable limits, accurate billing-grade counters, customer-visible quota dashboards. Product-led.

These are not mutually exclusive but the priorities differ. **Open question**: which driver dominates? Without that, downstream design will optimize for the wrong axis.

Risk inventory: (a) **state-sync hazards** — if Redis is sharded, a key can map to multiple shards if hashing rotates; pin to consistent-hash slot. (b) **distributed clock skew** — sliding-window math fails silently if instance clocks drift; pin time-source to Redis server time, not local. (c) **header information leakage** — `X-RateLimit-*` headers tell attackers exactly when they can resume; for some abuse-defense cases, suppress these. (d) **starvation** — a single legitimate spike (a customer running a one-off batch) can trigger limits; need a burst-credit mechanism.

Recommend producing a **threat model** alongside the requirements doc — what attacks does this defend against, what attacks does it NOT defend against (e.g., distributed botnets where per-IP is useless).

### Frontend / API Consumer

From the perspective of a client integrating against this API, rate limiting is only as good as the **contract clarity**. The single biggest pain point of poorly-rate-limited APIs is opaque 429s — the client doesn't know how long to wait, doesn't know if the limit is per-IP or per-key, and can't tell if they're approaching the limit before they hit it.

Mandatory client-facing contract elements:

- `X-RateLimit-Limit` — the ceiling for this window.
- `X-RateLimit-Remaining` — calls left in this window.
- `X-RateLimit-Reset` — unix-epoch when the bucket refills (preferred over delta-seconds; less ambiguous across timezones).
- `Retry-After` — RFC-7231 compliant, in seconds, on every 429.
- A documented quota endpoint (`GET /v1/usage` or similar) so clients can pre-flight check before a batch.

SDK considerations: official SDKs should auto-retry on 429 with exponential backoff respecting `Retry-After`, with a configurable max-retry. Without this, every customer reimplements (poorly) the same retry loop.

Documentation requirements: a dedicated "Rate Limits" page with per-tier ceilings, per-endpoint overrides, the algorithm in plain English ("you can burst up to 100, then sustained 10/sec"), and example 429 responses with the exact header shape.

UX edge case: webhooks and long-polling endpoints — rate-limiting these by request count is wrong; consider concurrent-connection limits instead, or exempt and rely on connection caps.

### Backend

Implementation surface: a middleware that runs per request, computes a bucket key (composite of tier + key-id + endpoint-class), increments a Redis counter via Lua script (atomic check-and-increment), and either passes through or returns 429.

Concrete data shapes needed:

- Bucket key format: `rl:{tier}:{key_id}:{window_id}` — explicit, debuggable, easy to scan.
- Lua script: GET → compare → INCR → EXPIRE in one round-trip. Single network call, <1ms.
- Config schema (per-tier): `{tier: free, default_rpm: 60, burst: 10, overrides: {/auth/login: {rpm: 10, burst: 2}}}`.

Performance budget: limiter must add <2ms p99 to request latency. This is achievable with Redis Lua + connection pooling but blown by naive multi-call Python (3-4 round-trips).

Failure modes the implementation MUST handle:

- Redis timeout → fail-open, increment `rate_limiter_degraded_total` counter, log WARN.
- Redis returns error → same as timeout.
- Clock skew → never use `time.time()` for bucket math; use `redis.TIME` server-side.
- Hot keys (one tenant hammering a single endpoint) → consider sharded counters for top-N tenants.

Test surface: unit tests for the algorithm, integration tests against a real Redis (or fakeredis), load test verifying the <2ms p99 budget, chaos test verifying fail-open behavior.

Stack-specific note: if implementing on the *current* IronClaude codebase, there is no web framework — backend cannot start until that foundation is chosen. Re-confirm scope.

### Security

Threat model the rate limiter defends:

- **Credential stuffing / brute force**: per-IP + per-account limits on `/auth/login`. Hard limit (e.g., 5/min/account, 20/min/IP) with exponential lockout after threshold.
- **API key abuse / leaked keys**: per-key limit catches a leaked key suddenly hitting 100× normal rate; pair with anomaly detection.
- **L7 DoS / scraping**: per-IP limits on unauthenticated endpoints. Pair with CAPTCHA or proof-of-work challenge at threshold.
- **Enumeration attacks**: rate limits on `/users/{id}` or `/resources/{id}` style endpoints — even valid clients shouldn't iterate.

Threats the rate limiter does **NOT** defend (must be called out):

- Distributed botnets — per-IP is useless when each request comes from a different IP. Need behavioral fingerprinting layer above.
- Authenticated abuse from a legitimate-looking key — needs anomaly detection, not rate limiting.
- Application-logic abuse (e.g., one expensive query = many cheap ones) — needs per-operation cost weighting, not per-call counting.

Security-specific requirements:

- API key in the bucket key MUST be hashed in logs (don't log raw keys).
- `X-RateLimit-Remaining` may leak information; consider omitting for unauthenticated endpoints.
- Lockout escalation paths (auth endpoints) need an out-of-band unlock mechanism (support contact, email-link reset) — don't lock users out permanently.
- Alerting on systemic 429 spikes is a security signal, not just an SRE signal — wire it to security ops too.

Compliance hooks: if SOC2/PCI scope, document the rate-limit policy as a control and capture evidence (log retention, alert receipts).

## Phase 4 — Specification

### Functional Requirements

1. **FR-1**: All public API endpoints SHALL enforce a rate limit appropriate to the requester's authentication tier.
2. **FR-2**: The system SHALL support distinct limits per tier (e.g., free, pro, enterprise) with per-endpoint overrides.
3. **FR-3**: Unauthenticated requests SHALL be limited by client IP; authenticated requests SHALL be limited by API key.
4. **FR-4**: When a client exceeds its limit, the system SHALL return HTTP 429 with `Retry-After` and the standard `X-RateLimit-*` headers.
5. **FR-5**: Every response SHALL include `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` headers.
6. **FR-6**: Internal service-to-service traffic, health checks, and an admin allowlist SHALL bypass the limiter.
7. **FR-7**: Configuration SHALL be reloadable without redeploy (e.g., on SIGHUP or hot-reload from config store).
8. **FR-8**: A `GET /v1/usage` (or equivalent) endpoint SHALL allow authenticated clients to query their current consumption.

### Non-Functional Requirements

1. **NFR-1 (Performance)**: Limiter overhead SHALL be <2ms p99 added latency.
2. **NFR-2 (Availability)**: If the state store (Redis) is unreachable, the limiter SHALL fail-open and emit a degradation metric.
3. **NFR-3 (Accuracy)**: Limit accounting SHALL be accurate within ±5% under sustained load (acknowledges minor race-window slop).
4. **NFR-4 (Observability)**: Metrics SHALL include throttled-request counters by endpoint and tier, exported in Prometheus format.
5. **NFR-5 (Security)**: API keys SHALL NOT appear in logs in plaintext; use a stable hash.
6. **NFR-6 (Scalability)**: The design SHALL support horizontal scaling of the API service with shared limit state.
7. **NFR-7 (Operability)**: Runbook entries SHALL exist for: Redis outage, sustained 429 alerts, customer "I'm being throttled" tickets.

### Acceptance Criteria

- **AC-1**: A free-tier client exceeding 100 req/min on `/v1/data` receives HTTP 429 with `Retry-After: 60` and `X-RateLimit-Remaining: 0`.
- **AC-2**: A pro-tier client exceeding 10K req/min on the same endpoint also receives 429 with appropriate headers.
- **AC-3**: When Redis is killed mid-test, requests continue to succeed (fail-open) and the `rate_limiter_degraded_total` counter increments.
- **AC-4**: Health check (`/healthz`) returns 200 even when caller is over their normal quota.
- **AC-5**: An authenticated client can call `GET /v1/usage` and receive their current bucket state.
- **AC-6**: Load test of 1000 RPS shows p99 added latency <2ms vs. baseline.
- **AC-7**: Brute-force attack (100 login attempts from 1 IP in 1 minute) is throttled by request 21 and logged.
