## Intro

This brainstorm explores whether to adopt GraphQL for the public API. Goal: a clarified requirements specification. Downstream `/sc:design` takes it from here.

---

## Phase 0 — Light Research Context

Web search ran in v1 mode (single-shot, lighter touch than the v2 research-light enrichment):

- Apollo Federation v2 is the most enterprise-deployed GraphQL gateway.
- GraphQL Yoga + Mesh is the OSS alternative for wrapping REST.
- Shopify and GitHub run public GraphQL with persisted-queries-only for partners.
- JSON:API and OpenAPI 3.1 offer REST-evolution patterns (sparse fields, compound documents).
- HTTP/2 multiplexing addresses many "too many round-trips" complaints without API surface change.
- Walmart Labs is the cautionary tale for public GraphQL without strong schema governance.

## Phase 1 — Socratic Exploration

Six questions probing the topic (architecture-quick is 6-question depth):

**Q1. What's driving this — pain, partner request, or strategy?**
A: All three. 2 enterprise partners asked for GraphQL specifically (mobile round-trip pain). Internal pain on over-fetching (1 mobile screen pulls from 6 endpoints). Strategic: v3 API planning starts Q3, this is foundational input.

**Q2. Scope — parallel API, replacement, or gateway?**
A: Most likely a gateway in front. NOT replacing REST.

**Q3. Who consumes?**
A: First-party (40%), integration partners (35%), public developers via SDKs (25%).

**Q4. Non-negotiables?**
A: OAuth2 + API-key auth must continue; latency budgets (200ms P95 first-party, 500ms P95 partners); REST versioning current; observability per-resolver.

**Q5. In-house GraphQL experience?**
A: Limited. 2 engineers with prior background; 1 small internal admin endpoint. Operational ramp is significant.

**Q6. Deadline?**
A: Soft. v3 planning starts Q3 2026; need recommendation by then.

## Phase 2 — Multi-Persona Analysis

Two personas, ~300 words each.

### Architect

The right shape is a GraphQL gateway in front of existing REST services. Apollo Federation v2 (managed via GraphOS) handles schema governance, query planner, query cost analysis, and contracts. Persisted-queries-only for partners (Shopify / GitHub pattern); ad-hoc queries are first-party only. REST stays for the public-developer long-tail unchanged. Strategic angle dominates: v3 planning needs a built foundation so the question "should we have GraphQL?" is answered by data rather than inertia. ~18 engineer-weeks for engineering + 2 quarters operational ramp. Managed gateway lock-in is the deliberate trade for operational velocity.

### Backend

The over-fetching pain is real but NOT uniquely GraphQL-shaped. Phase A: HTTP/2 + Cache-Control + payload audit (~2-4 engineer-weeks). Phase B: REST evolution to sparse-fields / compound documents on the top 12 endpoints (~6-10 engineer-weeks); pilot with the 2 partners who asked. Phase C: focused GraphQL endpoint ONLY if Phase A+B leaves real, measured pain that REST evolution provably can't address. The in-house expertise gap is dominant operational risk; even Apollo GraphOS doesn't eliminate it. v3 planning needs a *credible recommendation backed by measurement*, not a built gateway.

## Phase 4 — Specification

### Functional Requirements

1. **FR-1**: Phase A — HTTP/2 + Cache-Control + payload audit on top 12 endpoints.
2. **FR-2**: Phase B — REST sparse-fields on top 12 endpoints; partner pilot.
3. **FR-3**: Phase C — focused GraphQL endpoint, IF Phase A+B reveals GraphQL-shaped residual pain.
4. **FR-4**: Persisted-queries-only for partners under Phase C.
5. **FR-5**: First-party-clients-first rollout under Phase C.
6. **FR-6**: Existing OAuth2 + API-key flows continue across all phases.
7. **FR-7**: Existing REST API backward compatible at every phase.

### Non-Functional Requirements

1. **NFR-1**: Auth flows unchanged.
2. **NFR-2**: No breaking changes to existing REST.
3. **NFR-3**: Phase A latency improvement ≥25% on merchant-dashboard reference OR assumption disproved.
4. **NFR-4**: Latency budgets preserved (200ms P95 first-party, 500ms P95 partners).

### Acceptance Criteria

- **AC-1**: Phase A measurement baseline captured before any tuning lever.
- **AC-2**: Phase A measurement report shows quantitative latency / round-trip delta attributable per-cause.
- **AC-3**: Phase B sparse-field support on top 12 endpoints; SDKs updated.
- **AC-4**: Partner pilot answers documented (yes/no on "sufficient?" question).
- **AC-5**: Phase C trigger decision documented at end of Phase B.
- **AC-6**: v3 planning input document delivered before Q3 kickoff.

### Open Questions for User

3. Schema governance ownership unspecified (Phase C only concern).
4. Versioning model under GraphQL (Phase C only).
