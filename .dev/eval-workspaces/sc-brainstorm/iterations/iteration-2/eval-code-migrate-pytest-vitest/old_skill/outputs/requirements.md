# Requirements: Migrate Test Suite from pytest to vitest

> Generated by `/sc:brainstorm "migrate our test suite from pytest to vitest" --depth normal`
> Protocol: v1 (monolithic, in-context personas)

## Intro

This brainstorm covers the migration of the test suite from pytest to vitest. We'll consider scope, tooling, risks, and a phased approach.

---

## Phase 0 — Codebase Context

Looked at the repo. Frontend tests live under `frontend/tests/`. There's a script `scripts/run-frontend-tests.sh` invoked from pytest somehow. Backend tests use plain pytest and won't change. No prior vitest config exists.

The integration story is that pytest currently "drives" the frontend tests by shelling out — so the migration is more about replacing the invocation layer than rewriting test bodies. Probably.

---

## Phase 1 — Socratic Exploration

**Q1. Why are we doing this?**
A: pytest-driving-JS is slow and weird. Vitest is the native runner for a Vite stack.

**Q2. Is the entire test suite moving?**
A: No — only the frontend slice. Backend stays on pytest.

**Q3. How do we keep CI green?**
A: Probably migrate in batches and don't merge a PR until both runners agree.

**Q4. What about coverage?**
A: Need to keep the combined coverage report working. Vitest can output LCOV, which is what we already merge with.

**Q5. What about Storybook fixtures?**
A: Storybook imports from `frontend/tests/fixtures/`. As long as we don't move that path, should be fine.

**Q6. Deadline?**
A: End of next sprint ideally.

## Phase 2 — Multi-Persona Analysis

### Architect

This is a runner-replacement, not a test rewrite — the tests are JS/TS files being driven by pytest as a wrapper. So the architectural risk is low. Set up vitest, point it at the existing test directory, swap the CI invocation. The interesting design choice is whether to extend `vite.config.ts` or create a standalone `vitest.config.ts`. Extending is cleaner because the React plugin and aliases are already configured. The coverage provider choice (istanbul vs v8) matters for compat with the existing nyc-style output — istanbul is the safer pick.

### Refactorer

Don't big-bang this. Move tests in directory batches, with both runners running per PR until the batch is verified. Keep the centralized `frontend/tests/` directory — don't co-locate at the same time as migrating, that's two refactors. Delete the bridge only after everything's moved.

### QA

The big risk is silent test-skip — vitest's default file glob might not match the existing test filenames, in which case it runs zero tests and reports green. Verify the test count after migration matches the pre-migration baseline. Also worried about assertion-semantic diffs between jest-style and vitest-style at edge cases.

### DevOps

CI minutes will improve a lot. Pre-migration the frontend job takes ~9 min; vitest natively should be ~90s. Worth capturing the baseline before cutover so the improvement is provable.

### Frontend

JS engineers will love this — Vitest UI, watch mode, in-IDE debugging all come back. The pytest bridge has been a constant pain.

---

## Phase 3 — Validation

Feasible. Migration is straightforward because the test bodies don't have pytest fixtures (they're JS files being shelled out, not real pytest tests). Coverage merge keeps working as long as we pick istanbul. Storybook keeps working as long as we don't move the fixtures.

---

## Phase 4 — Specification

### Functional Requirements

- Set up vitest by extending `vite.config.ts`.
- Install `@vitest/coverage-istanbul` for coverage output compatible with the merge pipeline.
- Migrate frontend tests in directory batches.
- Each batch PR runs both runners until verified.
- Delete the pytest-shell bridge after all batches are moved and verified.
- Keep `frontend/tests/fixtures/` in place for Storybook.

### Non-Functional Requirements

- CI green at every commit.
- Frontend CI job under 2 minutes wall-clock.
- Coverage report still merges into the existing LCOV.

### Acceptance Criteria

- `pnpm test` runs vitest and exits 0.
- Coverage report merges cleanly.
- Storybook still builds.
- pytest-shell bridge is removed from CI workflow and Makefile.
- Frontend CI wall-clock < 2 min.

### Open Questions

- Co-locate tests next to source files, or keep centralized tree?
- Coverage provider: istanbul (compat) or v8 (speed)?
- How long should the parallel-run period be before deleting the bridge?
