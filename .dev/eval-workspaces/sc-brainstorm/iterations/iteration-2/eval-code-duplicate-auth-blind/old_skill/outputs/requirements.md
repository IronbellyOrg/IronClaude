# Requirements: Consolidate Three Duplicate Auth Modules

> Generated by `/sc:brainstorm "consolidate three duplicate auth modules" --depth deep`
> Protocol: v1 (monolithic, in-context personas, no blind mode)

## Intro

This brainstorm explores consolidating three independently-evolved auth modules (`legacy_login.py`, `api_login.py`, `mobile_login.py`) into a shared core to eliminate security drift. Goal: a clarified requirements specification. Downstream `/sc:design` and `/sc:workflow` take it from there.

## Phase 0 — Codebase Context

**Code-relevance detection**: Topic mentions specific modules and consolidation verb. Phase 0 triggered. Glob/Grep fallback (Auggie unavailable).

### Three modules

- `services/web/src/auth/legacy_login.py` — session-cookie + CSRF + custom CAPTCHA (~1200 LOC).
- `services/api/src/auth/api_login.py` — api-key + OAuth2 client_credentials (~800 LOC).
- `services/mobile_bff/src/auth/mobile_login.py` — OAuth2 PKCE + biometric step-up (~950 LOC).

### Shared primitives that exist

- `services/shared/security_utils/` — Argon2id, JWT (HS256), lockout (Redis-backed). Well-tested. Keep.

### Persistence

User table and Sessions table shared across all three. No schema migration required.

### Behavior deltas detected

- Lockout thresholds differ: 5/15min (web), 10/5min (api), 7/10min (mobile).
- Password policy enforcement differs by service.
- CSRF is web-only.
- Audit destinations differ (CloudWatch, Splunk, S3).

## Phase 1 — Socratic Exploration

Eight questions on the consolidation:

**Q1. What's the end state?**
A: One `services/shared/auth_core/` library consumed by all three services with thin service-specific entry points for protocol-specific concerns.

**Q2. What drift incidents motivated this?**
A: (1) Oct 2024 JWT-library CVE patched in api within 48h, in web after 11 days. (2) Feb 2025 password-policy length update landed in web and api but not mobile for 4 months.

**Q3. Are wire formats negotiable?**
A: No. Session and token formats must remain wire-compatible.

**Q4. What's the latency budget?**
A: P99 ≤ 80ms across all three post-consolidation.

**Q5. What's the audit-preservation requirement?**
A: 90-day overlap during which both unified and legacy destinations write; after 90 days, unified becomes canonical.

**Q6. What's the rollout shape?**
A: Per-service shadow → 5% → 50% → 100%, with kill switches at every phase.

**Q7. What's the test surface?**
A: Unit, contract, integration, E2E, security pentest.

**Q8. What's the forcing function?**
A: Compliance audit cycle at end of Q3 has flagged "inconsistent auth controls" — must be mid-migration with documented plan by then.

## Phase 2 — Multi-Persona Analysis

Five personas coordinated in-context, ~300 words each.

### Architect

The right shape is a shared core with per-service adapters. Plugin-style flows allow OAuth2 PKCE, api-key, password-flow, and biometric step-up to be first-class extension points. Override registry pattern allows per-service deviations only with documented security sign-off. Unified audit via Kafka with legacy-destination consumers during the 90-day overlap. Migration phased per-service starting with api (fewest behaviors). ~18 engineer-weeks.

### Refactorer

Plugin framework is over-engineered for the measured drift (which is primitive-level: JWT CVE, password-policy length). Smaller scope: shared `policy.py` (~300 LOC) and shared `audit_emitter.py` (~300 LOC). Per-service flow code stays in service repos where ownership is honest. ~10 engineer-weeks. Half the cost; addresses the measured harm.

### Security

Migration of auth IS an auth change. Two code paths in parallel during shadow/canary creates a new class of risk: divergent lockout state (exploitable), divergent audit (compliance gap), sensitive data in shadow-mode logs. Required: lockout store unified from Phase 0, audit dual-write with idempotency UUIDs, pre-migration + per-cutover pentest, sensitive-data redaction in shadow runner. ~3 engineer-weeks added on top of either architecture.

### QA

Test surface is the load-bearing investment. ≥120 unit cases, ≥150 contract cases, ≥90 integration cases, shadow-mode runner with ~50K-request corpus per service, ≥30 E2E scenarios, ≥4 pentest engagements. ~8 engineer-weeks for test development. Coverage on new core ≥95%. Shadow-mode delta detection runs before any canary phase.

### DevOps

Rollout mechanics determine ship vs. slip. Required: per-service feature flags with sub-flag granularity, promotion checklist as code, dashboards-before-code, per-phase runbook entries, on-call briefings per phase, production-shadow alignment, hard timer on 90-day overlap with reconciliation gate, quarterly override-registry review. Lesson from billing_core consolidation post-mortem: dashboards built after the fact missed the early-signal window on a regression that became Sev-2. ~5 engineer-weeks parallel to app work, requires SRE involvement.

## Phase 4 — Specification

### Functional Requirements

1. **FR-1**: Single source of truth for password policy, lockout policy, JWT validation, audit event schema in shared `auth_core/`.
2. **FR-2**: Override registry — per-service deviations require named entry with security-review sign-off.
3. **FR-3**: Unified audit emitter via Kafka with legacy-destination consumers during 90-day overlap.
4. **FR-4**: Lockout store unified from Phase 0 (no per-service divergence during shadow mode).
5. **FR-5**: Audit dual-write with idempotency UUIDs.
6. **FR-6**: Shadow-mode runner with delta detection (outcome, lockout side-effects, audit content, latency).
7. **FR-7**: Per-service feature flags with sub-flag granularity.
8. **FR-8**: Promotion checklist as code artifact, gated execution.
9. **FR-9**: Dashboards built before Phase 0 builds begin.
10. **FR-10**: Pre-migration + per-cutover pentest (≥4 engagements).
11. **FR-11**: Migration ordering: api → web → mobile.

### Non-Functional Requirements

1. **NFR-1**: Login latency P99 ≤ 80ms post-migration.
2. **NFR-2**: New core test coverage ≥95% line + branch.
3. **NFR-3**: Audit reconciliation: zero gap between legacy and unified at 90-day gate.
4. **NFR-4**: Drift prevention is structural — CVE patchable in one PR, deployed across all three services in one release.
5. **NFR-5**: Shadow-mode delta zero on 50K corpus before exiting shadow.

### Acceptance Criteria

- **AC-1**: All unit cases (≥120) green; ≥95% coverage on new core.
- **AC-2**: All contract cases (≥150) green.
- **AC-3**: All integration cases (≥90) green.
- **AC-4**: Shadow-mode runner shows zero deltas on 50K corpus per service.
- **AC-5**: All E2E scenarios (≥30 per service) green.
- **AC-6**: Pentest findings ≤ LOW before each promotion.
- **AC-7**: Login latency P99 ≤ 80ms post-migration.
- **AC-8**: Audit reconciliation gap = 0 at 90-day gate.
- **AC-9**: Three legacy modules deleted by end of migration.
