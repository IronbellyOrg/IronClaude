## Question 1: attestations: read

**Verdict: NO. `attestations: read` on `IronbellyOrg/IronClaude` is not needed for `gh attestation verify <file> -R colbymchenry/codegraph`.**

Evidence:

1. **Which endpoint gh calls.** gh CLI source at `cli/cli` commit `9490d204a2ba95434153dedce99898ce9f281426` (trunk on 2026-10-31; latest release `v2.103.3`, the same version as the local `gh`):
   - `pkg/cmd/attestation/api/client.go:117`: with `--repo`/`-R` set, the request URL is `safeurl.JoinPath("repos", owner, name, "attestations", params.Digest)`, i.e. `GET /repos/{owner}/{repo}/attestations/{subject_digest}` (with `per_page`, and `predicate_type` when given). `:123` is the `--owner` alternative (`/orgs/{org}/attestations/{digest}`), not used by the spec.
   - `client.go:234-240`: when the API returns a `bundle_url` instead of an inline bundle, gh fetches it with `c.externalHttpClient.Get(...)`; `client.go:61` documents that client as "makes HTTP calls to all non-GitHub API endpoints" (blob storage, no GitHub token permission involved).
   - `verify.go:210`: the only other GitHub API call, `GetTrustDomain` (`GET /meta`, `client.go:291-292`), runs only when `ghauth.IsTenancy(opts.Hostname)` (GHE.com tenancy hosts), not for `github.com`.
   - `verify.go:245`: `cmdutil.DisableAuthCheckFlag(verifyCmd.Flags().Lookup("bundle"))`, so without `--bundle` gh's own auth check applies and **a token must be present** (`GH_TOKEN`). The spec already sets `GH_TOKEN` on the `fetch` step (spec §2.3, line 137). Presence of a token is the requirement, not a permission on it.
   - Source URL: https://github.com/cli/cli/blob/9490d204a2ba95434153dedce99898ce9f281426/pkg/cmd/attestation/api/client.go and `.../pkg/cmd/attestation/verify/verify.go`.
2. **What that endpoint requires.** GitHub REST docs, "List attestations" (https://docs.github.com/en/rest/repos/attestations?apiVersion=2022-11-28):
   - "The authenticated user making the request must have read access to the repository. In addition, when using a fine-grained access token the `attestations:read` permission is required."
   - "Fine-grained access tokens for 'List attestations'": works with "GitHub App installation access tokens" (among others); "The fine-grained token must have the following permission set: 'Attestations' repository permissions (read)". Then: **"This endpoint can be used without authentication or the aforementioned permissions if only public resources are requested."**
   - `colbymchenry/codegraph` is public (the release assets and API are readable anonymously; see item 4), so the permission sentence does not apply to this request.
3. **What a `GITHUB_TOKEN` permission covers.** https://docs.github.com/en/actions/concepts/security/github_token: "The `GITHUB_TOKEN` secret is a GitHub App installation access token ... The token's permissions are limited to the repository that contains your workflow." The workflow syntax reference (https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax) lists `attestations: read|write|none` and describes it as "Work with artifact attestations. For example, `attestations: write` permits an action to generate an artifact attestation for a build." So `attestations: read` in IronClaude's workflow would grant read of **IronClaude's** attestations only; it cannot grant or change access to `colbymchenry/codegraph`'s attestations. That access comes from the public-resource rule in item 2.
4. **Live check of the exact endpoint, no token.** `curl -H 'Accept: application/vnd.github+json' 'https://api.github.com/repos/colbymchenry/codegraph/attestations/sha256:ef0af416092128fb1ccc723786000b7edf4a6971fe604acd08bf966e4f37b828?per_page=1'` (the v1.6.2 `linux-x64` tarball hash, `install_codegraph.py:29`) returned **HTTP 200** with an attestation (`repository_id` 1137078255, a `bundle_url` on `tmaproduction.blob.core.windows.net`). An anonymous caller has no permissions at all, so no permission is needed to read these public attestations.
5. **The `gh attestation verify` manual** (https://cli.github.com/manual/gh_attestation_verify) says the command fetches attestations "via the GitHub API" scoped by `--owner` or `--repo` and states no permission or scope requirement.
6. **Official precedent is about generation, not verification.** GitHub's attestation guides (https://docs.github.com/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds; https://docs.github.com/actions/security-guides/using-artifact-attestations-and-reusable-workflows-to-achieve-slsa-v1-build-level-3) require `attestations: write` plus `id-token: write` to **generate**; neither documents an `attestations: read` requirement for verifying another repository's public attestations.

Limits: the conclusion rests on GitHub's documented public-resource rule plus an anonymous live call; it was not observed inside an Actions job with exactly `contents/pull-requests/issues/actions: write` and everything else `none`. That is UNVERIFIED until T7's dry run, but the documented failure the spec anticipates (a 403 fixed by `attestations: read`) is contradicted by items 2-4.
