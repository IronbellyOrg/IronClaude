## Consequences for the design (spec §3)

- The hook must not run `status`, `index` or `sync` on a checkout: each can destroy a concurrent run (rows 6, 7), and none can tell whether a run is active (row 4).
- The hook only needs to start `init --yes` when `<top>/.codegraph/codegraph.db` does not exist (row 12: a `.codegraph/` without a database is never built by the daemon). Concurrent inits are harmless (rows 2, 3). An interrupted init is healed by the daemon on the next MCP connection (row 9), and every session connects because the server is registered with `alwaysLoad`. No completion marker, PID file or lock is needed.
- Agents must not run `status` or `index` by hand while an `init` or `index` may be running. The process to look for is `node … lib/dist/bin/codegraph.js init|index` (the `bin/codegraph` launcher `exec`s node; RR reproduced that `pgrep -f 'codegraph (init|index)'` never matches and `pgrep -f 'codegraph\.js (init|index)'` does).
- Superseded by this table: the earlier rule "rebuild with `codegraph index` when a database exists without a marker" (spec D3) and the PID-file/status design (spec D15).
