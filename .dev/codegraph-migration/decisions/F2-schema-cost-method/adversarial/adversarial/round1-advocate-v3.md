# Round 1 Advocate: Variant 3 (option C, byte proxy gate plus session measurement as recorded evidence)

Persona: architect (structure, dependencies, long-term impact on Phase 2 and Phase 3). Depth: quick. Round 1 only. All paths are under `.dev/codegraph-migration/` unless stated.

## Position Summary

V3 has the right structure: the stdio byte harness must run in every case, because it is the only method that works for an unattended executor with no login (`decisions/F2-schema-cost-method/context.md:10-11`) and the only one that proves explore is hidden and blocked (`specs/phase-2-codegraph-install-spec.md:97`). A session token measurement should be layered on top as evidence. V3's disagreement rule is wrong as written, though. It only works in one direction, and on the measured +7,004 to 7,488 B delta the cross-check can never fire (X-001). The merged method should keep V3's two-leg shape and replace its single cut-off with a three-band rule, so the session measurement decides only inside the band where the bytes-per-token constant is what actually decides the outcome.

## Steelman of V1

V1 is the simplest method that meets every Phase 2 hard rule. It runs offline in a throwaway directory with a sandbox HOME, needs no login, and is deterministic (`variant-1-original.md:3,6`). That matches the executor described in `context.md:10-11` exactly. The same Node client answers the X-25 question that Phase 2 says is still UNVERIFIED (`specs/phase-2-codegraph-install-spec.md:97`: "with the key set, `tools/list` has no `codegraph_explore` ... and a `tools/call` of `codegraph_explore` returns an error"). It also counts the server instructions bytes explicitly (U-001), which matters because the instructions text says "There is a single tool, `codegraph_explore`" and may change when explore is hidden (`diff-analysis.md:24`). V1 is honest about its own error direction: the 3 B/token constant "may fail a list that would pass a real measurement" (`variant-1-original.md:13`). That error is fail-safe, because a false fail ships the `status`-only branch, which still keeps explore blocked (`specs/phase-2-codegraph-install-spec.md:96`). V1 is also fully scriptable as `jq`/`node` assertions, which fits the T2 step style (`specs/phase-2-codegraph-install-spec.md:485-495`).

## Steelman of V2

V2 measures the quantity the threshold is actually written in. P3-D1 accepts "the 2K-token pass threshold" (`specs/phase-3-codegraph-adoption-spec.md:349`), and the merged P3 rule talks about "the always-loaded schema delta" per session (`decisions/P3-access-model/adversarial/P3-access-model-merged.md:155-156`). Only a real Claude Code session counts that, including any per-tool wrapping Claude Code adds and its real tokenizer, which `diff-analysis.md:23` says are the two unknowns that decide which side of 2,000 the delta lands on. Its isolation through `--strict-mcp-config --mcp-config <cfg>` with only codegraph registered is the strongest unique idea in the set (U-003, rated High): every other server cancels out of the delta, and no `claude mcp add` runs against the real HOME, so it does not break the literal Phase 2 rule (`context.md:10`). V2 is also the only variant that could observe the deferral question P3 asks to record ("Record whether the seven tools are deferred behind tool search", `P3-access-model-merged.md:155`).

## Strengths Claimed

1. **The gate never blocks the unattended executor.** The check "runs once, in task T2 before the expected entry is written, by an unattended executor" and the "sandbox HOME has no Claude login" (`context.md:10-11`). V3's A leg always runs (`variant-3-original.md:6`). Architecturally this matters because T2 is the phase function, registry entry and dispatch task (`specs/phase-2-codegraph-install-spec.md:482-484`); a stop there stalls every later Phase 2 task and the Phase 3 G3 gate (`specs/phase-3-codegraph-adoption-spec.md:19,24`).
2. **One harness is mandatory in every variant anyway.** Phase 2 names T2 step 0 as part of the X-25 proof (`specs/phase-2-codegraph-install-spec.md:97`), and V2 itself admits it "does not by itself prove explore is blocked (needs the stdio client anyway)" (`variant-2-original.md:13`). So the stdio harness is a fixed dependency. The real question is only what decides on top of it, and V3 is the only variant that makes that layering explicit (U-004, rated High).
3. **It produces the evidence the downstream decisions need.** P3 says the 2K threshold "is proposed, not measured, and the user confirms it" (`P3-access-model-merged.md:156`). V3 records both numbers, or an explicit "session measurement: not run" line (`variant-3-original.md:3`), in the evidence file that T2 step 1 already reads (`Selected MCP_TOOLS:` line, `specs/phase-2-codegraph-install-spec.md:487`). That gives the user and Phase 3 a dated record to confirm or revisit the threshold, instead of only a pass/fail bit.
4. **The failure direction is safe.** V3 lets the real measurement remove tools but never add context beyond what was measured (`variant-3-original.md:3,13`). That matches P3-D1's intent that the failure branch "keeps explore blocked" (`P3-access-model-merged.md:157`) and Phase 2's single-constant design ("The installer builds the env from `MCP_TOOLS`; nothing else hard-codes the value", `specs/phase-2-codegraph-install-spec.md:97`).
5. **It previews a Phase 3 gate early.** Phase 3 G5 later checks, in a real session, that `mcp__codegraph__codegraph_callers` and `_status` are listed and `_explore` is not (`specs/phase-3-codegraph-adoption-spec.md:21`). When V3's B leg runs, the same fact is observed in Phase 2, before the value is locked into the spec, U12, layer 2 and the Coder handoff (`specs/phase-2-codegraph-install-spec.md:96`).

## Weaknesses Identified in Others

1. **V1: a heuristic constant decides a near-line outcome.** On the real v1.6.2 data, the delta is +7,004 to 7,488 B (`diff-analysis.md:15-16`), so V1's 6,000 B gate fails by 1,000 to 1,500 B (`diff-analysis.md:22`), while the token estimate ranges from 1,751 to 2,496 depending on the rate (`diff-analysis.md:23`). V1 would therefore move Phase 3 to its CLI and artifact transport (`P3-access-model-merged.md:157`) on the strength of an UNVERIFIED constant alone. That is a whole access-model change in Phase 3 decided by one guess.
2. **V1: no record of deferral.** P3 asks the check to "Record whether the seven tools are deferred behind tool search" (`P3-access-model-merged.md:155`). A byte count cannot observe that, and V1 never says so (A-002).
3. **V2: it stops the unattended executor.** "an unattended executor without auth stops (human item)" (`variant-2-original.md:10`), against `context.md:10-11`. Phase 3 already carries a similar human item (H5, `specs/phase-3-codegraph-adoption-spec.md:341`), and adding another one at a Phase 2 gate turns a measurement into a blocking dependency.
4. **V2: its "real quantity" has no validity guard (X-002).** V2 admits that whether `--strict-mcp-config` with `alwaysLoad` lists the tools is UNVERIFIED (`variant-2-original.md:12`). If the seven tools were deferred in that configuration, B would measure a near-zero delta and pass falsely (`diff-analysis.md:51`), and nothing in V2 would catch it.
5. **V2: noise without a rule, and real-HOME side effects.** It acknowledges "small run-to-run noise" with no repeat or tolerance rule (C-008), and "sessions rewrite other parts of `~/.claude.json`" (`variant-2-original.md:11`) without a guard like the `.mcpServers` hash check that T2 step 1 already uses (`specs/phase-2-codegraph-install-spec.md:489,493`).
6. **V2: it does not prove X-25.** See `variant-2-original.md:13`. A V2-only method still has to build V1's client, so it is not simpler overall.

## Concessions

1. **X-001 is a real flaw in V3.** My pros claim "the heuristic is cross-checked" (`variant-3-original.md:7`), but the rule lets B override only a pass (`variant-3-original.md:3`). On the measured data A fails (`diff-analysis.md:22`), so the cross-check can never fire, and V3 gives the same `status` result as V1. In the one case that matters for this release, V3 adds cost without adding information to the decision. The one-directional rule is only safe-biased. It does not cross-check anything.
2. **V3 inherits V2's open gaps when B runs:** no noise rule (C-008), no validity guard (C-009, X-002), and the UNVERIFIED JSON `usage` field names (`variant-3-original.md:12`).
3. **The method is defined by reference** (S-001). V3's method paragraph points at A and B instead of stating the commands, so an executor must assemble it from two documents. A merged spec must be self-contained.
4. **More spec text and two scripts** (`variant-3-original.md:11`). That cost is only justified if the second leg can change the outcome, which needs the band rule below.
5. **"When a logged-in `claude` is available" is not a mechanical condition.** V3 does not say how the executor detects it, so in practice the B leg may never run.

## Shared Assumption Responses

- **A-001 (the delta is far from 2K, so the method choice does not change the outcome): REJECT.** The orchestrator measured +7,004 to 7,488 B, which is 1,751 to 2,496 tokens depending on the bytes-per-token rate (`diff-analysis.md:15-16,23`). Each method can give a different verdict on this exact data, so any merged rule needs an undecided band instead of a single cut-off.
- **A-002 (server-level `alwaysLoad: true` loads all seven listed tools in full): QUALIFY.** For the byte gate it is the right working assumption, because counting every tool as fully loaded gives an upper bound on context cost, which is the conservative direction. As a fact it is unproven: only `codegraph_explore` carries the per-tool `_meta.anthropic/alwaysLoad` flag (`research/codegraph-evaluation.md:85`), and P3 calls the deferral behaviour UNVERIFIED and asks for it to be recorded (`P3-access-model-merged.md:155`). The session leg must record listed or deferred status, and a deferred result must invalidate B as a gate rather than count as a pass.
- **A-003 (the outcome is binary: seven tools or `status`): QUALIFY.** F2 should keep the binary outcome, because P3-D1 fixed the branch (`specs/phase-3-codegraph-adoption-spec.md:349`) and Phase 3 primitives name `_node` for outline mode (N-002), so a six-tool list without `node` would change Phase 3, not just Phase 2. However, `codegraph_node` alone is 2,864 of the 9,223 B (`diff-analysis.md:19`), and without it the list would pass even V1's gate. The evidence file should record per-tool bytes so that a later P3 decision can weigh a smaller list on data, and F2 should not invent that list itself.

## Proposed Merge Improvements

All constants below are proposals and are recorded in the evidence file as such. The threshold itself stays "proposed, not measured" until the user confirms it (`P3-access-model-merged.md:156`).

1. **Leg A (always runs, sandbox HOME, offline after download).** Use a throwaway `mktemp -d` directory, the verified and extracted pinned v1.6.2 tarball, and a tiny `git init` repo. Run the stdio client twice: run 1 with `CODEGRAPH_MCP_TOOLS` unset, run 2 with exactly `node,search,callers,callees,impact,files,status` (a real run, not derived from the 8-tool run, so instruction changes are captured, `diff-analysis.md:24`). Define `D = (bytes of JSON.stringify(run2 tools/list .result.tools) + bytes of run2 initialize .result.instructions) - (same for run1)`, using full tool objects (the larger, conservative figure, `diff-analysis.md:15`).
2. **X-25 assertions are a hard stop, not a gate input.** Run 2 must list `codegraph_callers` and `codegraph_status`, must not list `codegraph_explore`, and a `tools/call codegraph_explore` must return an error (`specs/phase-2-codegraph-install-spec.md:97`). If any assertion fails, the executor stops with a mid-level decision (§7), because even the `status` branch depends on the explicit list hiding explore.
3. **Three bands on D.**
   - `D <= 5,000 B` (2,000 tokens even at a dense 2.5 B/token): PASS by A. Value: the seven tools.
   - `D >= 8,000 B` (above 2,000 tokens even at a generous 4 B/token): FAIL by A. Value: `status`.
   - `5,000 B < D < 8,000 B`: UNDECIDED. Leg B decides if it runs and is valid. The current measured data (+7,004 to 7,488 B) falls here.
4. **Leg B (runs only in the undecided band, never blocks).** Preconditions, checked mechanically: `claude --version` succeeds within 10 s and a one-shot auth probe (`claude -p "reply ok"` with a 60 s timeout) exits 0. If either fails, B is "not run (reason)". Configuration: `--strict-mcp-config --mcp-config <cfg>` registering only the extracted codegraph with `alwaysLoad: true` (U-003). Run each configuration (env unset; 7-tool env) three times, with a 120 s timeout per run. Token figure per run: input + cache creation + cache read from the JSON result (U-002; field names UNVERIFIED). Before and after all B runs, hash `jq -S '.mcpServers' ~/.claude.json` as T2 step 1 does (`specs/phase-2-codegraph-install-spec.md:489,493`); any change is a stop.
5. **Leg B validity guard (closes X-002 and C-009).** B is valid only if all of these hold: (a) the session init event of each 7-tool run lists `mcp__codegraph__codegraph_callers` and `mcp__codegraph__codegraph_status` and not `mcp__codegraph__codegraph_explore` (whether `--output-format stream-json --verbose` exposes this list is UNVERIFIED; if it cannot be parsed, B is invalid); (b) the median token delta is at least `D / 6` (a floor below which the tools are almost certainly deferred or missing); (c) the max minus min spread within each configuration is at most 200 tokens (closes C-008). If (a) or (b) fails, record `Deferred: yes or unknown` and treat B as invalid; that result is also a Phase 3 finding for G5 (`specs/phase-3-codegraph-adoption-spec.md:21`).
6. **Decision in the undecided band.** If B is valid: PASS when the median token delta is at most 2,000, else FAIL. If B is not run or invalid: the value is `status` (the existing fail branch, `specs/phase-2-codegraph-install-spec.md:96`; no new mechanism, explore stays blocked), the executor continues without stopping, and it logs a non-blocking human item with the exact B commands. A person who later runs B and gets a valid pass flips the single `MCP_TOOLS` constant (`specs/phase-2-codegraph-install-spec.md:97`) and reverts the literal replacements.
7. **Fixed evidence file shape** in `evidence/P2-mcp-tools-schema.md`, one fact per line, so later steps and Phase 3 can grep it: `Bytes delta D:`, `Band: pass|undecided|fail`, `Per-tool bytes:` (all eight tools), `Instructions bytes run1/run2:`, `Explore hidden: yes`, `Explore call blocked: yes`, `Session measurement: <median tokens, three runs each> | not run (<reason>) | invalid (<reason>)`, `Deferred: no|yes|unknown`, `Decided by: A|B|default`, `Threshold status: proposed, not user-confirmed`, and last the existing `Selected MCP_TOOLS: <value>` line that T2 step 1 parses (`specs/phase-2-codegraph-install-spec.md:487`).
8. **INV-015 note.** P3 asked for the measurement "in a session that also has codebase-memory registered" (`P3-access-model-merged.md:155`). The delta is additive, so B's single-server configuration is enough for the number, but tool-search deferral may depend on total tool load. The merged spec should either add codebase-memory to B's `<cfg>` or record in the evidence file that INV-015 was waived and why.
9. **Scope guard for A-003.** F2 keeps the binary outcome. If the result is FAIL or default `status`, the evidence file states the D that the six-tool list without `node` would have (`D - bytes(node)`) as data only, and points to P3-D1 as the owner of any smaller-list decision.
