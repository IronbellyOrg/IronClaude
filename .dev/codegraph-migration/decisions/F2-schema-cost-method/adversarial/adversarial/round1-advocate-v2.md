# Round 1 advocate: Variant 2 (option B, real session token measurement)

Persona: performance (efficiency, measurement fidelity, resource usage). Depth: quick, Round 1.

## Position Summary

The orchestrator's own byte data puts the 7-tool delta at 1,751-2,496 tokens, straddling the 2K line (`diff-analysis.md:23`), so the only thing that can decide this gate correctly is the real token count that Claude Code sends, which is what Variant 2 measures. A byte proxy is a good cheap pre-screen and the only way to prove explore is blocked, but it must not be the decider inside the uncertain band. The merged method should run V1's harness always and make V2's session measurement decisive (in both directions) whenever the byte delta falls in that band, with guards that make a deferred-tools false pass impossible.

## Steelman of V1

V1 is the strongest option on everything except fidelity. It is deterministic, offline after the download, free, needs no login and runs in the sandbox HOME that the Phase 2 rules already require (`variant-1-original.md:6-8`; `context.md:10`). It is the only variant that by itself proves review finding X-25, that an explicit list hides and blocks `codegraph_explore` (`variant-1-original.md:3`, "asserts `codegraph_explore` absent from run 2's list and that a `tools/call codegraph_explore` in run 2 returns an error"), which the spec says is still UNVERIFIED and must be proven in T2 step 0 (`phase-2-codegraph-install-spec.md:97`). It explicitly counts the server instructions bytes (`variant-1-original.md:3`), which the P3 merge asked to be inspected (`P3-access-model-merged.md:155`). Its 3 B/token rate is deliberately conservative, so any list it passes is very likely to pass the real measurement too: a pass from V1 is trustworthy. For an unattended executor that must never stop, it is the only fully scriptable option.

## Steelman of V3

V3 recognises that each method covers the other's blind spot: A always runs and proves X-25, B measures the real quantity when it can (`variant-3-original.md:3-8`). It never blocks the executor and it forces an honest evidence line, "session measurement: not run", rather than silently implying a real measurement happened (`variant-3-original.md:3`; diff U-004 rated High, `diff-analysis.md:60`). It also states a disagreement rule up front, which V1 and V2 lack, and that rule leans safe: a real measurement can only make the outcome more conservative (`variant-3-original.md:3`). As a structure (two methods, explicit precedence, mandatory evidence line) it is the closest to the right merge.

## Strengths Claimed

1. **V2 measures the quantity the threshold is defined in.** The threshold is "at most 2K tokens per session over the default listing" (`phase-2-codegraph-install-spec.md:94`; `P3-access-model-merged.md:156`). Bytes are not tokens; the conversion is the dominant error term here. On the measured +7,004-7,488 B the token figure is 2,335-2,496 at 3 B/token and 1,751-1,872 at 4 B/token (`diff-analysis.md:23`): the method choice, not the server, decides the outcome. Only a tokenizer-backed count removes that error.
2. **V2 captures what Claude Code actually injects, not what the server emits.** Claude Code prefixes names with `mcp__codegraph__`, may wrap or trim schemas, and injects server instructions; V1 itself concedes "Claude Code may wrap or trim schemas, so the real context cost can differ from the bytes" (`variant-1-original.md:11`). The diff notes that the instructions say "There is a single tool, `codegraph_explore`" and may or may not change when explore is hidden (`diff-analysis.md:24`); V2 counts whatever the client really sends, including any change in instructions, with no assumption (C-007).
3. **V2 is the only method that can observe deferral, which the P3 merge asked for.** P3 §9.1 says: "Record whether the seven tools are deferred behind tool search ... Both are UNVERIFIED (INV-010)" (`P3-access-model-merged.md:155`). Deferral is a Claude Code behaviour (`research/codegraph-evaluation.md:77`, plain form "loses `alwaysLoad`, so Claude Code defers the tool behind tool search"); a stdio client talking to the server directly cannot see it at all. Only an observation inside a Claude Code session can answer A-002.
4. **V2 isolates the delta cleanly (U-003, High).** `--strict-mcp-config --mcp-config <cfg>` with only codegraph registered (`variant-2-original.md:3`) makes every other server and user setting cancel out of the delta, and both flags exist in the installed CLI (`context.md:9`; observed again in `claude --help` this round: "--mcp-config <configs...> Load MCP servers from JSON files or ..." and "--strict-mcp-config").
5. **V2 respects the hard registration rule.** The rule forbids `claude mcp add/remove` against the real HOME (`context.md:10`; `phase-2-codegraph-install-spec.md:99`). V2 never registers anything: `--mcp-config` loads the server for one session only. The spec already accepts that real-HOME sessions rewrite non-MCP parts of `~/.claude.json` and guards only `.mcpServers` with a hash (`phase-2-codegraph-install-spec.md:332`, "only MCP servers: live sessions rewrite the rest of the file"; `:489`, `:493`), so V2 can reuse the exact same guard.
6. **V2's resource cost is small and bounded.** Two one-turn `-p "reply ok"` runs on the same base prompt; the second run mostly hits the prompt cache. That is a few tens of thousands of input tokens once, in one task, for a value that then ships in every user session (`context.md:11`). Getting the gate wrong in the pass direction costs every session up to roughly 500 extra tokens; getting it wrong in the fail direction drops Phase 3 to the `status`-only branch with CLI and artifact fallbacks (`phase-2-codegraph-install-spec.md:96`; `P3-access-model-merged.md:157`). A one-time measurement cost is the efficient trade.
7. **The token accounting formula is explicit (U-002).** "input + cache creation + cache read" (`variant-2-original.md:3`) counts the whole context regardless of cache state, so a warm cache on run 2 cannot hide tokens.

## Weaknesses Identified in Others

1. **V1's gate fails this exact data on the heuristic, not on a measurement.** With the 6,000 B gate the measured +7,004-7,488 B fails by 1,000-1,500 B (`diff-analysis.md:22`), yet at 4 B/token the same bytes are 1,751-1,872 tokens, a pass. V1 itself warns it "may fail a list that would pass a real measurement, dropping Phase 3 to the `status`-only branch" (`variant-1-original.md:12`). That is exactly the case on the table.
2. **V1 cannot see Claude Code's wrapping, prefixes or deferral.** Its own Cons (`variant-1-original.md:11`) plus P3's explicit ask to record deferral (`P3-access-model-merged.md:155`) mean V1 alone leaves INV-010 open.
3. **V3's cross-check never fires in the case that matters (X-001).** V3's rule is one-directional: "If B runs and its delta exceeds 2000 tokens while A passed, B wins" (`variant-3-original.md:3`). With the real data A fails, so B can never rescue it; the Pros claim "the heuristic is cross-checked" (`variant-3-original.md:7`) is false on this input (`diff-analysis.md:50`). V3 spends the cost of running B and then ignores B's answer.
4. **V3 bakes V1's conversion error into the decider.** Because A is the gate, V3's outcome on this data is `status` regardless of the real token count (`diff-analysis.md:22`, "A (and C, whose gate is A) would set `MCP_TOOLS = "status"`").
5. **Neither V1 nor V3 defines a noise or validity rule (C-008, C-009).** V3 inherits B's noise "with no rule" (`diff-analysis.md:43`), and no variant guards against B measuring a deferred listing (`diff-analysis.md:51`). V3 is exposed to V2's false-pass risk whenever B runs, although its one-directional rule happens to stop that particular false pass from changing the outcome.

## Concessions

1. **Auth.** V2 needs a logged-in `claude` and network to Anthropic; the sandbox HOME has no login (`context.md:10`; `variant-2-original.md:10`). The executor that runs T2 is itself a Claude Code session, so a login in the real HOME is likely, but that is UNVERIFIED (it could be an API key in the environment only, and `--bare` reads only `ANTHROPIC_API_KEY` or `apiKeyHelper`, per `claude --help`). V2 alone stops the unattended executor when auth is missing (C-006). That is a real defect of V2 as a standalone method.
2. **Real HOME.** V2 runs against the real HOME. `--strict-mcp-config` keeps `mcpServers` untouched, but sessions rewrite other parts of `~/.claude.json` (`variant-2-original.md:11`). The `.mcpServers` hash guard (`phase-2-codegraph-install-spec.md:332`, `:493`) contains this, but it does not make the run side-effect free.
3. **UNVERIFIED fields and flags.** The JSON `usage` field names and whether `--strict-mcp-config` with server-level `alwaysLoad` lists the tools are UNVERIFIED (`variant-2-original.md:12`). The spec's own step 1 probe exists because nobody has yet confirmed `alwaysLoad` survives `add-json` (`phase-2-codegraph-install-spec.md:99`).
4. **No explore-blocked proof.** V2 does not prove X-25 (`variant-2-original.md:13`; C-004). The stdio harness from V1 is needed regardless, so V2 can never be the whole method.
5. **False pass if tools are deferred (X-002).** If the seven tools were deferred behind tool search in the measured config, V2 would see a near-zero delta and pass, and V2 as written has no guard (`diff-analysis.md:51`). This is the most serious flaw in V2; the merge below fixes it with two independent guards.
6. **Noise.** V2 admits "small run-to-run noise" with no rule (`variant-2-original.md:12`; C-008). Hooks, date strings and git status in the system prompt can differ between runs.
7. **Isolation versus realism.** P3 asked for the measurement "in a session that also has codebase-memory registered (INV-015)" (`P3-access-model-merged.md:155`). `--strict-mcp-config` with only codegraph is cleaner for the delta but does not reproduce that condition, which may matter if deferral depends on the total tool load.

## Shared Assumption Responses

- **A-001 (delta not near the threshold): REJECT.** The orchestrator's measurement puts the delta at 1,751-2,496 tokens depending only on bytes per token (`diff-analysis.md:23`); the method choice flips the outcome, so the merged method needs an explicit undecided band in which the real measurement decides.
- **A-002 (server-level `alwaysLoad` loads every listed tool in full): QUALIFY.** It is the intended behaviour but UNVERIFIED (only `codegraph_explore` carries the per-tool `_meta.anthropic/alwaysLoad` flag, `research/codegraph-evaluation.md:85`; INV-010, `P3-access-model-merged.md:155`). It must be observed, not assumed, and only a Claude Code session can observe it, so the merged method must assert it inside B and treat an unobservable result as "B invalid", never as a pass.
- **A-003 (outcome is binary: 7 tools or `status`): QUALIFY.** The failure branch is fixed by P3-D1 (`P3-access-model-merged.md:157`; `phase-2-codegraph-install-spec.md:96`), so trying smaller lists is out of F2 scope. The method should still record per-tool bytes (node is 2,864 of 9,223 B, `diff-analysis.md:19`) and per-arm tokens so a later decision can reopen the branch without re-measuring.

## Proposed Merge Improvements

1. **Always run V1's stdio harness first** (sandbox HOME, pinned v1.6.2, tiny `git init` repo). Record: `tools/list .result.tools` bytes per arm, model-facing bytes per arm (prefixed name, description, inputSchema), per-tool bytes, `initialize .result.instructions` bytes and text per arm. Assert in arm 2: `codegraph_explore` absent, `codegraph_callers` present, `tools/call codegraph_explore` returns an error. Any X-25 assertion failure fails step 0 outright (no B can override it).
2. **Use a three-zone byte rule on the model-facing delta (D bytes):**
   - D <= 6,000 B: pass (3 B/token is conservative), B optional and recorded only.
   - D > 10,000 B: fail, `MCP_TOOLS = "status"` (even at 5 B/token that exceeds 2,000 tokens).
   - 6,000 B < D <= 10,000 B (the measured +7,004 B lands here): B decides, in both directions.
3. **B inside the band, exact shape:** two configs in a private `mktemp -d`, identical except `CODEGRAPH_MCP_TOOLS`; each registers only codegraph with `alwaysLoad: true` (plus codebase-memory in both if Phase 2 keeps it registered, to meet INV-015 without disturbing the delta). Run from an empty non-git throwaway cwd with `claude -p "reply ok" --output-format json --strict-mcp-config --mcp-config <cfg> --no-session-persistence --model <pinned model>`, order A, B, A, B. Hash `.mcpServers` of the real `~/.claude.json` before and after, as the spec does (`phase-2-codegraph-install-spec.md:489`, `:493`); a mismatch fails step 0.
4. **B validity guards (fail closed; any failure makes B "invalid", never "pass"):**
   - The session's tool inventory (for example the `system`/`init` event of `--output-format stream-json`, field names UNVERIFIED and to be confirmed by the first run) lists all seven `mcp__codegraph__codegraph_*` names in arm 2 and only `codegraph_explore` in arm 1, with no tool-search placeholder standing in for them.
   - Token delta T >= D / 5 (a real listing cannot tokenise below 5 B/token; a deferred listing would show T close to 0).
   - Each arm's two runs agree within 50 tokens; one re-run of the pair is allowed, then B is invalid.
   - The `usage` fields `input_tokens`, `cache_creation_input_tokens` and `cache_read_input_tokens` are all present and numeric (names UNVERIFIED; if absent, B is invalid).
5. **Decision inside the band:** valid B with T <= 2,000 tokens: pass (7 tools). Valid B with T > 2,000: fail (`status`). B not run or invalid: take the `status` branch, write "session measurement: not run" or "session measurement: invalid (<guard>)" and a one-line note that re-running step 0 with a login may upgrade the value. Never pass inside the band without a valid B.
6. **Evidence file** (`P2-mcp-tools-schema.md`) records: byte figures and per-tool bytes, zone, B's per-run usage numbers, which guards passed, the instructions text diff between arms, the deferral observation (for P3 INV-010), and the `Selected MCP_TOOLS:` line that T2 step 1 already reads (`phase-2-codegraph-install-spec.md:487`).
7. **Note for the user:** the 2K threshold is "proposed, not measured, and the user confirms it" (`P3-access-model-merged.md:156`). Since the measured delta sits at the line, the evidence file should state the real token figure plainly so the user can confirm or move the threshold with the number in front of them.
