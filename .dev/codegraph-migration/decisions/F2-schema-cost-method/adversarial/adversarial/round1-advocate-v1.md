# Round 1 advocate: Variant 1 (option A, byte proxy over stdio)

Persona: analyzer (evidence quality, logical consistency). Depth: quick, Round 1.

## Position Summary

The stdio byte harness should be the mandatory, always-run core of the merged method: it is the only one of the three that is deterministic, runs under the Phase 2 sandbox rules, and also proves X-25 (explore hidden and blocked). But the orchestrator's measurement (+7,004 to +7,488 B, `diff-analysis.md:15-16`) lands inside the conversion-rate uncertainty, so V1's single 6,000 B cut-off alone is not good enough; the merge needs a three-band rule where only the middle band calls on a session measurement or a human item.

## Steelman of V2

V2's strongest case: the 2K threshold is stated in session tokens (`P3-access-model-merged.md:156`), and only a real Claude Code session measures session tokens. Bytes are a proxy at two removes: the tokenizer rate is unknown, and Claude Code may add per-tool wrapping such as the `mcp__codegraph__` prefix or drop fields such as `annotations` (`diff-analysis.md:16,23`). With the measured delta sitting between 1,751 and 2,496 tokens depending only on the assumed rate (`diff-analysis.md:23`), any byte rule is effectively a guess at exactly the point where the guess decides the outcome. V2 also brings the best isolation idea: `--strict-mcp-config --mcp-config <cfg>` with only codegraph registered, so every other server cancels out (U-003, rated High at `diff-analysis.md:59`). And it runs the exact Claude Code version (2.1.312, `context.md:9`) that will load the server, so wrapping, deferral and prefixing are all included for free.

## Steelman of V3

V3's strongest case: it is the only variant that never blocks the unattended executor (`context.md:11`) and still uses the real measurement when it exists (`variant-3-original.md:3,6-7`). It makes the evidence file honest by forcing a "session measurement: not run" line (U-004, High, `diff-analysis.md:60`), so a reader can tell whether the decision rests on the heuristic or the real number. It also states a disagreement rule, which neither single-method variant needs but any merge does.

## Strengths Claimed

1. **Runs under the Phase 2 rules with no human.** V1 needs no login and no real HOME: "Deterministic, offline after download, no auth, no cost; runs in any sandbox HOME" (`variant-1-original.md:6`). The context fixes both constraints: never touch the real HOME with `claude mcp`, and the sandbox HOME has no Claude login (`context.md:10`); the check runs once by an unattended executor (`context.md:11`). V1 is the only single method that satisfies all three.
2. **It is the X-25 proof the spec already requires.** The spec says the hide-and-block behaviour is UNVERIFIED and that T2 step 0 is the proof: "with the key set, `tools/list` has no `codegraph_explore` and has `codegraph_callers`, and a `tools/call` of `codegraph_explore` returns an error" (`phase-2-codegraph-install-spec.md:97`). V1 does exactly this in the same client (`variant-1-original.md:3,7`). V2 concedes it "Does not by itself prove explore is blocked (needs the stdio client anyway)" (`variant-2-original.md:13`). So the V1 harness must exist in any outcome; the only question is whether something is added to it.
3. **It measures run 2 directly, which the existing data does not.** The orchestrator's seven-tool figure is derived from the 8-tool run and "assumes the other schemas do not change when explore is absent" (`diff-analysis.md:24`). V1 starts the server with the exact 7-tool key, so it removes that assumption.
4. **It counts the server instructions explicitly.** V1 adds `initialize .result.instructions` bytes (`variant-1-original.md:3`; U-001). This matters: the instructions say "There is a single tool, `codegraph_explore`" and "may or may not change when explore is hidden" (`diff-analysis.md:24`), and they are 6,786 B (`diff-analysis.md:17`), roughly as large as the whole tool delta. If the instructions change with the key, a tools-only comparison would miss it; V1 does not.
5. **It is honest about its own error direction.** V1 states the rate "may fail a list that would pass a real measurement" (`variant-1-original.md:12`). The diff confirms V1's self-description was accurate (X-001, `diff-analysis.md:50`). The error is one-sided toward the safe branch (`status`, explore stays blocked, `phase-2-codegraph-install-spec.md:96`), never toward an over-budget registration.
6. **Fully scriptable acceptance.** The result is a byte count and two assertions, checkable with `jq` and `node` (`variant-1-original.md:8`), which fits the spec's style of shell-asserted steps (for example the sandbox probe at `phase-2-codegraph-install-spec.md:486-494`).
7. **It cannot be fooled by deferral.** Because it reads the server's own `tools/list`, a client-side decision to defer tools behind tool search cannot shrink the number. That makes it an upper bound on the always-loaded cost, which is the right direction for a cap.

## Weaknesses Identified in Others

1. **V2 has an unguarded false-pass path (X-002).** V2 claims it "Measures the real quantity" (`variant-2-original.md:6`) but also lists as UNVERIFIED "whether `--strict-mcp-config` with `alwaysLoad` lists the tools" (`variant-2-original.md:12`). If the seven tools are deferred behind tool search in that config, the measured delta is near zero and V2 passes, then the real registration may behave differently. Nothing in V2 detects this (`diff-analysis.md:51`). A measurement whose validity is unverified cannot be "the real quantity" without a validity check.
2. **V2 blocks the unattended executor.** "An unattended executor without auth stops (human item)" (`variant-2-original.md:10`). The context says the check runs once, unattended, in T2 before the expected entry is written (`context.md:11`), so V2 as sole method makes T2 step 0 depend on a human every time auth is absent.
3. **V2 touches the real HOME.** It "Uses the real HOME" and "sessions rewrite other parts of `~/.claude.json`" (`variant-2-original.md:11`). The spec guards real registrations with a before/after hash even for a sandboxed probe (`phase-2-codegraph-install-spec.md:489,493`); V2 states no equivalent guard.
4. **V2's isolation may not match the P3 measurement condition.** P3 asks for the delta "in a session that also has codebase-memory registered (INV-015)" and to "Record whether the seven tools are deferred behind tool search" (`P3-access-model-merged.md:155`). V2's `--strict-mcp-config` with only codegraph (`variant-2-original.md:3`) removes the other servers. The token delta cancels either way, but if tool-search deferral depends on how many MCP tools are loaded in total (UNVERIFIED), V2's isolated session may defer differently from the real one, so it does not answer P3's deferral question for the real configuration.
5. **V2 has no noise rule.** It admits "small run-to-run noise" (`variant-2-original.md:12`) yet uses a hard cut at 2,000 tokens (`variant-2-original.md:3`). Near the line, which is where the measured data puts us (`diff-analysis.md:23`), noise alone can flip the result.
6. **V3's cross-check cannot fire on the actual data (X-001).** V3 claims "the heuristic is cross-checked" (`variant-3-original.md:7`), but its rule only lets B override a pass (`variant-3-original.md:3`). On the measured +7,004 to +7,488 B, A fails (`diff-analysis.md:22`), so B can never change the result. In the one case where the heuristic's known error matters (a false fail, `variant-1-original.md:12`), V3's extra machinery adds cost and no correction. This is an internal contradiction, not a style point.
7. **V3 inherits all of V2's validity gaps when B runs.** "B's UNVERIFIED flags/fields still apply when it runs" (`variant-3-original.md:12`), and V3 lets B overrule A, so an invalid B (for example one that measured with tools deferred) could still be trusted in the pass-to-fail direction without any check.

## Concessions

1. **V1's gate fails on the measured data, and that failure is probably partly an artefact of the rate.** At 3 B/token, +7,004 to +7,488 B is 2,335 to 2,496 tokens, so V1 sets `MCP_TOOLS = "status"` (`diff-analysis.md:22-23`). At 4 B/token the same bytes are 1,751 to 1,872 tokens and would pass. V1 alone would drop Phase 3 to the CLI-and-artifacts branch (`phase-2-codegraph-install-spec.md:96`) on the strength of a heuristic constant I cannot verify. That is a real cost, not a safe default with no downside.
2. **"Conservative" was the wrong word for the 3 B/token rate if it is not grounded.** V1 calls it conservative (`variant-1-original.md:3`) and its own con calls it a heuristic (`variant-1-original.md:12`). No file in the evidence set gives a measured bytes-per-token figure for this server's JSON. A single fixed rate at a single cut-off claims a precision the evidence does not have.
3. **Bytes are blind to Claude Code's wrapping and filtering.** The diff shows two plausible byte bases that differ by about 500 B (full objects 7,488 B vs model-facing fields 7,004 B, `diff-analysis.md:15-16`). V1 uses full `JSON.stringify` objects (`variant-1-original.md:3`), which includes `annotations` that may never reach the model. V1 cannot tell which base is right; only a session can.
4. **V1 cannot answer P3's deferral question.** P3 asks to record whether the seven tools are deferred (`P3-access-model-merged.md:155`). Strength 7 (blind to deferral) is also a weakness: V1 reports an upper bound but cannot say what Claude Code actually loads.
5. **V2's U-003 isolation idea is better than anything V1 offers for a session measurement,** and V3's "not run" evidence line (U-004) should be adopted.

## Shared Assumption Responses

- **A-001 (delta far enough from 2K that the method does not change the outcome): REJECT.** The orchestrator's numbers put the delta at 1,751 to 2,496 tokens depending only on the bytes-per-token rate (`diff-analysis.md:23`), so the method choice decides between 7 tools and `status`; every variant's single cut-off is unsafe here and the merge needs an explicit undecided band.
- **A-002 (server-level `alwaysLoad: true` loads all seven listed tools in full): QUALIFY.** For a cost cap, assuming full loading is the correct worst case and V1's bytes already embody it; but only `codegraph_explore` carries the per-tool `_meta.anthropic/alwaysLoad` flag (`codegraph-evaluation.md:85`) and P3 calls the server-level behaviour UNVERIFIED (`P3-access-model-merged.md:155`), so the merged method must record observed deferral separately rather than assume it, and must not let a "deferred" observation lower the cost reading used for the gate.
- **A-003 (binary outcome, 7 tools or `status`): QUALIFY.** Choosing a smaller list is outside F2's scope because P3-D1 fixed the failure branch (`P3-access-model-merged.md:157`, `diff-analysis.md:77`), but the harness already sees each tool's size (`codegraph_node` alone is 2,864 B, `diff-analysis.md:19,71`), so the evidence file should record per-tool bytes to let the user make a later decision without a rerun.

## Proposed Merge Improvements

1. **Always run the V1 stdio harness first, in a `mktemp -d` dir with a sandbox HOME.** Run 1: env unset. Run 2: `CODEGRAPH_MCP_TOOLS=node,search,callers,callees,impact,files,status` (measured directly, not derived from an 8-tool run, closing the caveat at `diff-analysis.md:24`). Record per run: (a) full-object bytes of `JSON.stringify(result.tools)`, (b) model-facing bytes (`"mcp__codegraph__"+name`, `description`, `inputSchema` only), (c) `initialize.result.instructions` bytes. Gate quantity `D` = delta of (a) plus delta of (c), the upper bound; (b) is recorded beside it.
2. **X-25 assertions in the same harness (blocking):** run 2's tool-name set equals exactly the seven `codegraph_*` names, contains no `codegraph_explore`, and `tools/call codegraph_explore` in run 2 returns a JSON-RPC error or `isError: true`. If any of these fails, T2 step 0 fails regardless of bytes, because the spec's premise (`phase-2-codegraph-install-spec.md:97`) is false.
3. **Three-band rule on `D`:**
   - `D <= 6,000 B`: pass (under 2,000 tokens even at 3 B/token).
   - `D > 8,000 B`: fail, `MCP_TOOLS = "status"` (over 2,000 tokens even at 4 B/token).
   - `6,000 B < D <= 8,000 B`: undecided. The measured data (+7,004 to +7,488 B, `diff-analysis.md:15-16`) lands here, so this band is the expected case, not an edge case.
4. **Session measurement only in the undecided band, or as an optional confirmation elsewhere,** using V2's `--strict-mcp-config --mcp-config <cfg>` isolation (U-003), with these guards:
   - Real-HOME guard: hash `jq -S '.mcpServers' ~/.claude.json` before and after and require equality, as the spec's probe does (`phase-2-codegraph-install-spec.md:489,493`).
   - Noise rule: run each configuration twice; session delta `T` = (larger of the two 7-tool readings) minus (smaller of the two default readings).
   - Validity floor: the reading counts only if `T >= D / 5` (no more than 5 B per token). A smaller `T` means the tools were probably deferred or not listed (X-002), so the reading is recorded as "invalid: probable deferral" and not used. This also gives P3 its deferral observation (`P3-access-model-merged.md:155`).
5. **Decision rule with a valid session reading:** pass if `T <= 2,000`, else fail. Outside the undecided band, a valid `T > 2,000` still turns a byte pass into a fail; a `T <= 2,000` never turns a `D > 8,000 B` fail into a pass (that combination implies over 4 B/token and is treated as suspect).
6. **Undecided band with no valid session reading:** never stop the run (`context.md:11`). Set `MCP_TOOLS = "status"` (the safe branch, `phase-2-codegraph-install-spec.md:96`), and log a mid-level decision (§7) stating `D`, the band, and that a logged-in session measurement or the user's confirmation of the threshold (`P3-access-model-merged.md:156`) can lift it to the seven-tool list.
7. **Evidence file `.dev/codegraph-migration/evidence/P2-mcp-tools-schema.md`** must contain: the `Selected MCP_TOOLS: <value>` line the later step reads (`phase-2-codegraph-install-spec.md:487`); both byte bases per run; instructions bytes per run; per-tool bytes; the band; the X-25 assertion results; and either the session readings with `T`, the floor result and the HOME-hash result, or the literal line `session measurement: not run` (U-004).
