# Context: how existing workspaces lose codebase-memory-mcp and Serena (Phase 1, issue #323)

Decision: what IronClaude code (if any) actively removes previously installed codebase-memory-mcp and Serena registrations and companion files on EXISTING workspaces when `./update.sh` or `superclaude install` runs after Phase 1, and what it must never touch.

Goal text (task brief): after Phase 1, `./update.sh` on an existing workspace and `superclaude install` on a fresh one leave no codebase-memory or Serena binary registration, MCP entry, permission, companion skill/agent/hook, CLAUDE.md mention or docs reference that IronClaude owns. Leftovers owned by the Coder image or by the upstream binary's own uninstaller are handed off, not removed by IronClaude. Safety: exact user scope only; never touch unrelated or same-named project/local entries; decide whether indexes and memories are kept or deleted.

## Verified facts (worktree at 55d40308)

- `update.sh` runs exactly `pipx install --force ./`, `superclaude install --force`, `make sync-dev`, `superclaude doctor` (`update.sh:7-10`); the list and order are pinned by `tests/cli/test_update_script.py:13-18`.
- `superclaude install` is the only command both dev workspaces (`update.sh:8`) and Coder workspaces (Coder `catalogue/ironclaude/install.sh:120`, `timeout 60 superclaude install ... </dev/null`, `--force` added when the pinned SHA changes, `:91-95`) run. `superclaude update` is documented never to touch MCP/native state (`docs/user-guide/mcp-installation.md:24`).
- Today `superclaude install` has a required codebase-memory phase (`src/superclaude/cli/main.py:254-262`) that Phase 1 deletes. Serena is never installed by `superclaude install`; only by `superclaude mcp --servers serena` (`install_mcp.py:55-61`) or, on Coder, by Coder's `mcp-bundle-core/install.sh` (uv tool install serena-agent==1.7.0, registers `serena` at user scope only if absent, on every workspace start).
- Exact-entry helpers exist: `read_user_mcp_entry(name)` (`install_mcp.py:714-754`) parses `~/.claude.json` (or `$CLAUDE_CONFIG_DIR/.claude.json`) directly, rejects duplicate keys, reads ONLY top-level `mcpServers` (user scope), returns "unknown" on any error; `_run_registration_command` (`:766-772`) runs the Claude CLI with a 60 s timeout and never echoes output; `_cleanup_user_native_registration` (`:916-948`) removes the exact user entry via `claude mcp remove <name> --scope user` and re-reads to verify absence. It is hard-coded to the codebase-memory name today.
- Live workspace (this one): user-scope `codebase-memory-mcp` = `{type: stdio, command: /usr/local/bin/codebase-memory-mcp, args: []}` (shape IronClaude writes, `install_mcp.py:866`); user-scope `serena` = `uvx --from serena-agent==1.7.0 serena start-mcp-server --context claude-code --project-from-cwd --enable-web-dashboard false --enable-gui-log-window false` (identical to the registry pin `install_mcp.py:59` and to Coder's bundle argv). No local-scope or project `.mcp.json` entries with either name. Binary `/usr/local/bin/codebase-memory-mcp` is root-owned (Coder image). `serena-agent` 1.7.0 is a uv tool (installed by Coder's bundle, not by IronClaude). `~/.cache/codebase-memory-mcp` 4.2 MB (no project indexes); `~/.serena` 62 MB (logs, language servers, config, empty global memories); 12 project `.serena/` folders.
- Workspace kinds for codebase-memory: A = Coder-baked binary, IronClaude only registered it (this workspace); B = IronClaude itself ran the upstream installer (receipt `~/.local/bin/.superclaude-codebase-memory.json` present, upstream companions in client configs); existence of any B workspace is UNVERIFIED; C = fresh, nothing to remove. Existing removal code (`superclaude mcp --uninstall --servers codebase-memory-mcp`) refuses kind A (binary is external) before it reaches registration cleanup (`install_mcp.py:957-959`).
- Installers are copy-only: no installer deletes a command/agent/skill that is no longer shipped (`install_core.py:62-73`, `install_commands.py:50-63`, `install_skill.py:47-48`). Hook registrations are refreshed in place only under `--force` (`install_hooks.py:393-431`); `update.sh` and Coder's SHA-change path both use `--force`.
- Phase 1 (per the Serena memory decision) keeps `/sc:save`, `/sc:load` and every other command/agent/skill name; no installed primitive file disappears from `src/`. `~/.claude/mcp/` is not installed (MCP_Serena.md and configs are package data only).
- Existing IronClaude policy: indexes kept; "IronClaude does not erase companion/cache files" (`install_codebase_memory.py:74-78`); upstream `codebase-memory-mcp uninstall` keeps indexes unless `--delete-indexes`.
- Coder runs `superclaude install` with a 60 s total bound and offline in CI (`--network=none`). Phase 1 and Phase 2 are planned to land on IronClaude master as one merge unit (W5 research 5.3).
- Coder's bundle re-registers `serena` on every workspace start until Coder removes Serena from the bundle (Phase 2 Coder handoff).

## Options

- option-a.md: registration-only retire step inside `superclaude install`.
- option-b.md: retire step that also removes IronClaude-provable binaries and global tools.
- option-c.md: no automatic step; explicit consented command plus handoffs.
