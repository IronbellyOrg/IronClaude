# Decision M-c context: what a failed proof produces

System: as in M-major-versions/context.md. Before opening a PR the monitor proves the candidate in an isolated HOME. Failure classes: (1) integrity: a hash in SHA256SUMS does not match a tarball, or `gh attestation verify` fails; (2) behaviour: install, index, tools/list or the print-config drift check fails; (3) infrastructure: GitHub API or download unavailable.
Facts: the Coder monitor (IronbellyOrg/Coder .github/workflows/ironclaude-upstream-monitor.yml, read 2026-10-30) pushes the bump branch first, then opens a ready PR on PASS and a DRAFT PR with a `needs-build-proof` label on FAIL (comment: draft is "the only hard non-mergeable state available"; label is best-effort), and exits neutral with a step summary when the upstream API is unreachable. IronClaude has no such label today (labels: bug, documentation, duplicate, enhancement, good first issue, help wanted, invalid, question, wontfix). Nobody watches IronClaude Actions run summaries; issue and PR notifications reach the owner. IronClaude's repo setting allows Actions to create PRs (`can_approve_pull_request_reviews: true`).
Question: on a failed proof (classes 1 and 2), does the monitor open a draft PR, an issue, or both?
