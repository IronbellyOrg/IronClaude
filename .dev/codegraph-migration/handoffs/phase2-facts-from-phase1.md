## 2. The retire step as built (source section 3)

Module `src/superclaude/cli/install_retired_mcp.py`; tests `tests/cli/test_install_retired_mcp.py` (72 tests). Verified against the code, not only the spec:

- **Entry points.** `run_retire_step()` (no arguments today; prints one line per action and returns a name -> outcome dict), `classify_retired_entries()` (pure read; returns `Finding(name, verdict, reason)` tuples in the order receipt, marker, `codebase-memory-mcp`, `serena`), `list_lines()` (for `install --list`), `update_notice()` (for `update`), `doctor_warning()` (for `doctor`). The table `RETIRED_MCP_SERVERS` maps each name to a classifier returning `(verdict, reason)`; it carries the sunset comment.
- **Placement.** `main.py` `install()` calls `run_retire_step()` after `install_user_setup`, inside its own `try/except Exception` that only prints a warning; no outcome changes the install exit code.
- **Removal helper.** `install_mcp._remove_exact_user_entry(name, matcher, *, deadline=None, per_call_timeout=10.0)` re-reads and re-matches the user entry right before `claude mcp remove <name> --scope user` and reads it again afterwards; it returns one of removed, absent, changed, replaced, unverified, unknown, timeout, failed, skipped. It runs `claude` through `install_mcp._exec_claude`, a direct argv exec in its own session that kills the process group on timeout, with output discarded. Bounds: 10 s per call, 15 s for the whole step (`PER_CALL_TIMEOUT`, `STEP_CAP`). Phase 2 can reuse the helper for the readiness-gated removals.
- **Matchers.** `codebase-memory-mcp`: absolute command with basename `codebase-memory-mcp`, `type` stdio or absent, `args` absent or `[]`, `env` and `headers` absent or `{}`; kept when the command is the current home's `~/.local/bin/codebase-memory-mcp` and that file exists, or when it sits under a different home's `.local/bin`. `serena`: Tier R rows (a)-(c) removed (`env`/`headers` absent or `{}`); everything else with `start-mcp-server` in its argv is Tier K (kept, `TIER_K_LINE` printed); non-empty `env`/`headers` is "customised registration" (kept); no `start-mcp-server` is "not a Serena launcher registration" (kept).
- **Files.** The receipt `~/.local/bin/.superclaude-codebase-memory.json` and marker `...pending` are deleted only when the binary is gone and each file is a private owned regular file in non-symlinked, non-writable-by-others directories; otherwise they are listed.
- **Never touched.** Local-scope and project `.mcp.json` entries, every binary, uv tools, `~/.local/bin/install.sh`, upstream companions, `~/.cache/codebase-memory-mcp`, `~/.serena`, project `.serena/`.
- **Messages.** Restart-sessions line, codebase-memory companions note, removed Serena argv plus the `serena-local` re-register command (`SERENA_REREGISTER`), the absolute upstream `uninstall` command (printed whenever `~/.local/bin/codebase-memory-mcp` exists and a retired item was found), `uv tool uninstall serena-agent`, and the data delete commands labelled "only if you no longer need them".
- **Read-only surfaces.** `superclaude install --list` prints one line per retired name; `superclaude update` prints only "legacy registration present: run `superclaude install`"; `superclaude doctor` adds a warn-only check "Retired MCP registrations".
- **Known small gaps** (recorded as notes in the task package, not blockers): when only the upstream binary exists and nothing else is found, `run_retire_step` returns early and does not print the absolute `uninstall` hint (`artifacts/retries/T4/notes.md`).

## 4. Phase 2 override: Serena removal

The Phase 2 spec (`.dev/codegraph-migration/specs/phase-2-codegraph-install-spec.md`) amends Phase 1's retire step. Quoted from its section 2.12:

> ### 2.12 Retiring Serena once codegraph is ready (amends Phase 1's retire step)
> 
> Requirement (user, via the coordinator, `orchestration/README.md` "Coordinator concerns"): after `./update.sh` on an existing workspace, Serena and codebase-memory must be completely absent. Phase 1 alone keeps the current-pin `serena-agent==1.7.0` entry (its Tier K), which is the entry this workspace has. Decided by `/sc:adversarial` at standard depth (`decisions/P2-serena-entry-removal/adversarial/P2-serena-entry-removal-merged.md`; options A keep Tier K and leave it to Coder, B remove once codegraph is ready, C remove only off Coder; scores B 0.898, C 0.853, A 0.835; convergence 18/18):
> 
> - `codegraph_ready()` (in `install_mcp.py`): one read-only predicate on current state, shared by `install`, `install --list` and `doctor`. True when the user entry `codegraph` either equals the expected entry (§2.4) or is an owned entry whose command's `--version` prints `1.6.2`, or is a user-managed entry whose command resolves to an executable (any version: the user chose it). `install()` passes `codegraph_success and codegraph_ready()` to the retire step, so a failed phase in this run never counts as ready.
> - When ready, the retire step also removes: (a) every user-scope entry other than `serena-local`, matched by shape rather than by key name, whose args contain `start-mcp-server` (this covers `serena` and a renamed Serena launcher), whose `type` is stdio or absent, and whose `env` and `headers` are each **absent or `{}`** (Coder's bundle and `claude mcp add` write `"env":{}`, and the live entry on this workspace has it: third review finding 1); and (b) the kind-B `~/.local/bin/codebase-memory-mcp` registration (its binary and upstream companions stay; the upstream `uninstall -y` command is printed). Each removal prints the removed argv. A launcher entry (any name) with a non-empty `env` or `headers` is kept and reported. The re-register hint uses the name `serena-local`, which the rule never removes. Phase 1's Tier R `serena` rows get the same "absent or `{}`" wording (Phase 1 amendment list, T0b).
> - When not ready: Phase 1's behaviour is unchanged (Tier K kept, hint printed); Tier R rows and the `/usr/local/bin/codebase-memory-mcp` entry are still removed unconditionally (Phase 1 §3.2).
> - Local-scope (`projects.*.mcpServers`) and `.mcp.json` entries are reported with the exact command, never removed (Phase 1 §3.3).
> - Kept by policy and stated in docs and CHANGELOG: `~/.serena`, project `.serena/`, `~/.cache/codebase-memory-mcp`, the uv cache, and (off Coder) a user-installed `serena-agent` uv tool, for which the removal command is printed.

What Phase 2 must change in Phase 1's code to implement `codegraph_ready()` gating:

- Add `codegraph_ready()` to `src/superclaude/cli/install_mcp.py` (read-only predicate on the user entry `codegraph`).
- Give `run_retire_step()` a parameter for the readiness result (today it takes none) and have `install()` pass `codegraph_success and codegraph_ready()`; extend `_classify_serena` so that, when ready, a launcher entry (any key other than `serena-local`) whose args contain `start-mcp-server` and whose `env`/`headers` are absent or `{}` is a "remove" verdict, and add the kind-B `~/.local/bin/codebase-memory-mcp` registration; keep the Tier R rows and the `/usr/local/bin/codebase-memory-mcp` entry unconditional.
- Update `list_lines()`, `update_notice()` and `doctor_warning()` so they call the same `codegraph_ready()`.
- `TIER_K_LINE` and the `CHANGELOG.md` entry already say the current-pin Serena registration is kept only until codegraph is ready, and name `serena-local` as the re-register name.
