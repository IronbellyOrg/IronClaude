## How a watcher-launched session appears to the sweep

Facts first, each with its source.

1. **What the watcher starts.** `orca agent launch --agent claude --worktree path:<config.worktree> --surface terminal --prompt "/sc:issue --claim <N>" --json`, run as a plain process with `cwd` set to that one worktree (`launch.py:95-116`, `:358-370`; design `issue-watcher.md:15, 68, 619-626`). The prompt is fixed to `^/sc:issue --claim [1-9][0-9]{0,8}$` (`launch.py:33`). There is no `--pipeline` or `--submit`.
2. **It is not an Orca orchestration Worker.** `agent launch` "starts the agent the way a new agent tab does" (`orca-ide agent launch --help`); worker Dispatches come from the separate `orchestration worker-start` / `dispatch` verbs (`orca-ide orchestration --help`). So the session has no Run and no Dispatch row. UNVERIFIED: that Orca writes no Run record at all for `agent launch`; the live test should confirm it (finding W-04).
3. **The watcher keeps almost nothing about the session.** From Orca's reply it keeps only `operation_id` (design `issue-watcher.md:688`, `launch.py:42-45`, `record` entry field `operation_id`). No session id, pane key, terminal handle or tab id is stored. `status --json` and the audit lines carry none either (`cycle.py:1326-1335`, design 10.1).
4. **What the sweep scans.** Orca rows come only from `worker-list --run <R>` for the bound or given Runs (`orchestrator-mode.md:241-245`); a run with no `--run` and no binding exits 2. Transcripts are scanned for the project key of the sweep root plus every path in `orca worktree ps --json` (`probes.py:1203-1214, 1263, 1347-1348`). A live call on this host listed 29 worktrees and 43 `claude` agent rows, so a registered watcher worktree is very likely scanned. `agent launch` needs an existing Orca workspace (help text), so the watcher worktree is registered.
5. **So the session is a transcript-only row** (`orca: None`, `row_id` `transcript:<session_id>`, `classify.py:903-926`). Its `person_started` comes from `_person_origin` (`classify.py:748-767`):
   - Today (`session_join` unknown, `orchestrator-mode.md:65, 992`): None, note `tab map join not observable`, class `could not determine`.
   - Later, if a tab-map entry exists (only when the Claude command is `ccsession-orca`, `orchestrator-mode.md:32`, README `:234-235`): None, note `Orca pane session, not in scoped Runs` (`classify.py:61, 762-765`), class `could not determine`.
   - Later, if path A is observable and there is no tab-map entry: **True** with note `origin not proved: no tab-map entry; ...`, which reaches rule 8 `person_active` and prints as "person session (active)" (`classify.py:302-315`). That label is wrong in kind: nobody typed the command.
6. **Never as worker, never owned.** `/sc:issue` is on the never-as-worker list (`WORKER-CONTRACT.md:23`), so the session is a top-level session, but it is not a coordinator: no Run is bound to it, so WC-16 (`WORKER-CONTRACT.md:286`) does not apply and nothing sweeps it on a timer. WC-13 forbids workers from running `agent launch` (`:62`); the watcher is a plain process (design `:68`), so that is consistent.
7. **The claim can start a second agent.** Without `--pipeline` the claim uses the default level `worktree` (`issue.md:43`, `claim.md:93`; PR #425 merged and in HEAD): it creates or reuses the Orca worktree `issue-<N>` and launches another Claude agent there under the launch-level guard. That second agent is also not Run-bound. See W-01.

Summary: to the sweep, a watcher session is an unowned, Run-less transcript whose origin is either "could not determine" or, in a later state, mislabelled as person-started. The report would never say "started by the watcher for issue N".

## Verdict

Partly aligned; not ready to run FU-1 live as written.
- Two contradictions: the watcher's fixed prompt triggers the claim's default `worktree` pipeline (W-01, W-02), against the watcher's own "claim only" decision and the claim's ship gate; and #409/Coder#477 picture a coordinator that the watcher design does not use (W-06).
- A watcher session is Run-less, unowned and unrecorded: the watcher keeps only an Orca operation id, so neither the sweep nor an observer can join it to a transcript (W-03, W-04, W-05).
- #450's live test and 24 h shadow run (a dry run with no Orca call) do not capture the facts Orchestrator mode needs; the edits above add them.
- Aligned and safe as they stand: plain-process launch, WC-13, never-as-worker, claim-marker detection, read-only `status`.
- UNVERIFIED and left for FU-1: whether `agent launch` creates any Run, which Orca Claude command the host uses, and whether the session stalls at the name prompt.
