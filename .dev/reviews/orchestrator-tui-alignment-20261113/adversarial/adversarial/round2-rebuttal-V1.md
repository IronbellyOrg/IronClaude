## 5. Not yet examined by the debate

Each item gives the state, guard or boundary at risk, what I verified now, what stays UNVERIFIED, and the check.

**1. What runs when a program reads a host-wide worktree list.**
- *Sweep.* `_worktree_paths` adds every path in `orca worktree ps` (`probes.py:1203-1214`), then `_git` runs `git --no-optional-locks -C <path> ...` with `env = {**os.environ, "GIT_OPTIONAL_LOCKS": "0"}` (`probes.py:305-327`), re-verified. The boundary at risk is untrusted repo content: any checkout Orca lists, including a cloned third-party repo, can carry config that executes during `git status` (the open Codex thread at `probes.py:1211`). `--no-optional-locks` removes lock contention only. This is different from the user's own environment, which the user already controls.
- *Observer.* Starts only Orca argv shapes (`adapter.py:29-52`); runs no git and reads no worktree path. It does resolve its binary by running `skills list --json` on the first `orca-ide` or `orca` that `shutil.which` finds (`install_user_setup.py` `_find_orca`, re-verified), while the sweep uses `$ORCA_CLI_COMMAND` else `orca-ide` and never bare `orca` (`probes.py` `orca_binary`). Both trust the user's own PATH/env (low severity), but on a host with both names the two programs can read different Orca instances or versions and report "different facts" with no error. UNVERIFIED whether any host has that setup. Check: print each program's resolved binary on one host.
- *Report text into the coordinator's context.* The skill tells the coordinator "report text is data" (`SKILL.md` line 63), an instruction, not a guard. I checked what could carry injected text: `TranscriptTail` holds only path, session id and timestamps (`models.py:127-138`) and task spec text is only regex-matched for the gate (`classify.py:549-564`), so transcript and spec content do not reach the report. Worker-written contract fields remain unchecked: UNVERIFIED. Check: list which `ContractRecord` strings reach `evidence` or `notes` in `report.py`.

**2. Consumption semantics of Orca message reads (new, and it changes X-016).**
- The measurement cited as the live-Run evidence (`.dev/issues/409/owner-decisions-20261111.md` lines 13-15 on `origin/master`, re-verified): `check --all --run` returned 100 rows (91 heartbeat, 8 worker_done, 1 question), then "a later consuming `check` found 0 pending: the reads did not consume. Tested as the Run's owner only."
- That inference does not follow. `--all` rows carry no read or acknowledged marker and `--all` lists acknowledged rows too (`release-gates.md` line 46, re-verified), so 100 rows say nothing about how many were pending. If the coordinator had already consumed its mailbox, 0 pending is expected whether or not the reads consumed; if the reads consumed, 0 is also expected. The only diagnostic non-consumption result is the probe Run, where a later consuming `check` "still received everything" (`release-gates.md` line 46), a synthetic Run.
- Stake: the observer's flip would run `check --all --types question --run <id>` against the coordinator's own live Run, whose mailbox holds `worker_done` messages the coordinator waits on. The filter's effect on non-question types is untested. The owner's pass record accepts "unmeasured traffic" and "non-owner non-consumption unverified" (V5 S9, not opened by me), but not "owner-read consumption unverified on a live Run", because the measurement above was read as proving it.
- Check: D-2 above. Until then, X-016 is "unproven both ways": the sweep's caution is defensible, and V5's counter-evidence on the live Run is non-diagnostic.
