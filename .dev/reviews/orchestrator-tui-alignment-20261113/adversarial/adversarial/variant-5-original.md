### 3. Data sources and the exact Orca verbs read

Only `adapter.py` starts a process (no shell, own session, process group killed on timeout). Three argv shapes only (`adapter.py:29-32`, `:153-188`):

1. `orchestration worker-list --json --limit 100` plus optional `--run <runId>` and `--cursor <c>` (R1).
2. `skills list --json` (binary discovery, once, inside `_find_orca`: tries `orca-ide` then `orca`, accepts a candidate only if it lists the `orca-cli` topic; `install_user_setup.py:36,247-270` on master).
3. `orchestration check --all --types question --run <runId> --json` (R2, only past the guard; `commands.py:173-187`). Plain `check`, `--peek`, `--ack`, `--wait`, `--retry-request`, `dispatch`, `inbox`, `run-use`, `run-create`, `send`, `ask`, `reply`, `reset` are on a prefix-matched forbidden list (`adapter.py:34-50`).

Caps: one read per 15 s per observer process, at most 5 calls per read (4 `worker-list` pages plus 1 message call when questions are on), 8 MiB per call, 10 s per call (`PER_CALL_TIMEOUT` marked UNVERIFIED until the first live read measures it), stderr kept to 2 KiB, backoff doubling to 60 s, STALE after 45 s without a good read (`adapter.py:57-63`, `collector.py:28-34`, `view.py:32-34`). Caps are per process; several observers multiply the load and there is no lock (`commands.py:84-85`, adapter-contract "A-008").

Row fields read from `worker-list` (`parse.py:58-90`): `dispatchId, taskId, runId, workerState, dispatchStatus, terminalState, resource.{id, ownershipState, releaseState, worktreeId, ownerDispatchId, originDispatchId, recoveryAttemptCount}, projection.{outcome, role, provider.id, host.{id,kind}, workspace.{id,kind}, stage.{worker,dispatch,activity,detail}, nextAction.kind, liveness.{verdict,source,observedAt}, evidence.{durable,liveStatus,lastObservedAt}}`. Any other key is counted and dropped. Message rows (`parse.py:419-461`): `id, run_id, from_handle, subject, priority, thread_id, created_at`; `body`, `payload`, `to_handle` are not kept.

### 4. What the observer does with the data (no classification)

### 8. What "live read off" means, and the rule for switching it on

Two different live reads: the `worker-list` read is live and on by default. The coordinator-questions read is off: `QUESTION_GATE_PASSED = False` (`commands.py:63-67`), so `--questions` prints `question read not enabled: QUESTION-OBSERVATION has not passed`, exits 1, and makes no Orca call, not even binary discovery (`commands.py:173-187,375-378`). With `--fixture` it exits 2. Rule (comment at `commands.py:63-66`, `release-gates.md` "Agents cite the owner's statement"): the constant may be flipped only against a record in which the owner states that QUESTION-OBSERVATION passed, cited by path. Facts the gate rests on (release-gates.md:38-50, sibling): `check --all --run` returns only the mailbox of the Run the caller is bound to; any other caller is fenced (`consumer_fenced`), a caller with no terminal identity gets `no_active_terminal`; Q-1 (an unbound terminal reading another terminal's Run) FAILED on 2026-11-11 (`q1-result.md`); reads did not consume, tested as the Run's owner on probe Runs and on the coordinator's own Run; at most 100 rows per read, applied after the type filter; no read marker, so a handled question still lists; real message rate unmeasured (the Task 17 sample is a 5-row synthetic Run, owner ruling "Yea I accept"). So the questions panel works only in the terminal that holds the Run, never via `run-use`.

### Could `observe` read the sweep, could the sweep reuse `observe`, merge or retire?

- **`observe` reading the sweep report or JSON.** Possible only after the sweep stores its JSON (today it prints to stdout and stores Markdown only). It cannot replace the observer's own collector: one sweep covers one Run, 50 shows and 90 s, against a fleet read of hundreds of rows. It could add an optional "coordinator view" panel that fills the facts the observer marks `unavailable (no source)` (frozen plans, safe to close) for one Run, labelled with the report's age. That is an enrichment, not a source.
- **The sweep reusing `observe`'s adapter, parse and sanitize.** Technically possible for paging and parsing. It cuts against the sweep's design: `models.py` is standard-library only, `probes.py` is the only module that starts a process, the allow-list is exact-token and owner-signed, and PR #539 is in review. The only real gain is paging. Not recommended now.
- **Merge or retire.** Neither should be retired: they answer different questions (what Orca says about every worker, live, for a human; what a coordinator needs to know about its Run from Orca plus disk, as a dated record). Recommendation: keep separate, with one written contract (decision D1).
