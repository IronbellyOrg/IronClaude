## 5. Not yet examined: the integration contract between the sweep and the observer

Everything in this section is a proposal for the owner; nothing is posted or written outside this file. "Verified now" marks facts I re-read for this round.

### 5.1 What the contract is, and what it is not

A short, tracked, written note that names the two programs, the two JSON schemas, the one join key, the words both print, the Orca verbs each may call and the files each writes. It is documentation plus a pinned vocabulary. It adds no runtime link between the programs in its first version: the observer does not read the sweep, the sweep does not read the observer, and neither gains a new file or key. That is deliberate, because the sweep's one-report-file rule is pinned (NFR-001: design line 128; `tests/sweep/test_readonly.py:300`; `tests/sweep/test_cli_contract.py:1474`; verified now) and its JSON goes to stdout only after the report is published (`commands.py:270-277`).

### 5.2 Owner and location

- **File.** `docs/designs/observe-sweep-contract.md` (tracked and shipped with the repository; not under `.dev/`, which is task and issue scratch space). New file, so it does not touch PR #539.
- **Owner: the Orchestrator mode design (#339).** Reason: the sweep's JSON is the stricter contract (golden-tested key set; `ROW_KEYS` pins), it is the one other consumers ask to change (V1 F-01, V3 Edit 5, V4 F2), and the observer's snapshot is, by its own schema, "PROPOSED, not an Orca contract" and additive-only. The observer's spec (`.dev/issues/409/bmad/spec-orca-observer/release-gates.md` and `adapter-contract.md`) and `docs/designs/orchestrator-mode.md` section 1 link to the note; neither restates its tables.
- **Amendment rule.** A change to a shared word, the join key, either schema's version, or an Orca verb either program may call must edit the note in the same PR. Review of both programs asks "did this touch the note".
- **Registry rows, not governance.** The note lists four more contracts so nobody calls them "the JSON v1" again: the watcher's `status --json` and `dispatch.json` (R2-V2, R2-V4) and any future v2 record. It governs only the first two rows below.

### 5.4 What each program publishes for the other: nothing new, and the rules for what already exists

- **Nothing is published for the other program in version 1 of the note.** Reason: any sweep-side addition (sidecar JSON, new keys) collides with NFR-001 and the golden pins in a PR that is still contested; any observer-side addition is unneeded because the sweep has no reader.
- **What exists today and how a future reader must treat it.**
  - *Observer snapshot* (`snapshot.json`): last writer wins (`SNAPSHOT_NAME` fixed, `export.py:26`; two live observers overwrite each other); written by atomic replace, mode 0600; required top-level keys `schemaVersion, producer{name,version}, cycle, generatedAt, source{namespace,status,observedAt}, page, scope, counts, rows`; no writer pid and no liveness flag, so the file keeps its last `source.status` after the process exits (all verified now). ### 5.5 Versioning rule for the two JSON schemas

- **Names.** Always "observe snapshot v1" and "sweep report JSON v1". A bare "JSON v1" is wrong in any issue, doc or test name.
- **Observe snapshot v1.** `schemaVersion` const 1, camelCase, `"UNKNOWN"` strings, rows keyed `dispatchId`, `additionalProperties: false`. Adding an optional key: same version, with a schema and test change in the observer's PR. Renaming, removing or changing the meaning of a key: v2. Consumers must ignore unknown keys and must not validate with a frozen copy of the producer's schema, because the producer's own schema rejects extras and would reject a newer file.
- **Sweep report JSON v1.** `schema_version`, snake_case, `null`, rows keyed `row_id`; key set pinned by a golden test. Adding an optional key: stays v1 with a deliberate golden-test change in the owner's PR (not inside #539); renaming or removing: v2.
