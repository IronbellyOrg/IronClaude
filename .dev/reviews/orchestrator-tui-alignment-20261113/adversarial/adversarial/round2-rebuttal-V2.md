### 5.1 What the launched session may do (permission boundary)

- **What the design claims.** The launch argv has 12 elements and no permission flag, pinned by a test (T10, `issue-watcher.md:667`; `launch.py:95-116`). Runbook 14.2 (`issue-watcher-setup.md:625-630`) concludes "the session runs in its default, interactive mode, which keeps a human between the session and any write", and names the risk: the claim reads the issue title, body and comments, text "anyone with comment access can write" (R13, R18). NG-4 adds no session constraint beyond the deployment gate (`issue-watcher.md:70`).
- **Why that conclusion is not established (new).** The argv decides nothing about the mode; the Orca Claude command does. The command that makes a session identifiable and governed is the ccsession wrapper (`claim.md:125`: "Orca's Claude command must be the ccsession-orca wrapper"; V2 W-09). `ccsession-orca` ends in `exec "$CCSESSION" ... --claude-args` (`ccsession-orca:186,189`), and `ccsession` defaults to `--dangerously-skip-permissions --allowedTools=Grep` unless `CCSESSION_PERMISSIONS=default` is set (`ccsession:135-141`, re-read). So the two things the debate wants for the watcher session, an identity the sweep can join (W-03, W-09) and a human gate before writes (14.2), pull in opposite directions unless the host sets `CCSESSION_PERMISSIONS=default`. If it is unset, a session that reads untrusted issue text runs with no permission prompts (`--dangerously-skip-permissions`).
- **What bounds it either way.** The prompt is only `/sc:issue --claim <int>` (D3, `launch.py:84-92`); the approval gate (T2-T4: allow-listed human approver, body and non-own comments older than the approval, `issue-watcher.md:659-661`) bounds who can put text in front of the session, but text arriving after the re-read still reaches it (R13).
- **UNVERIFIED.** The mode the first session actually runs in on a Coder workspace and the host's `CCSESSION_PERMISSIONS`. FU-6 asks the first half; the second half is not in the runbook.
- **Check.** D-C above. **Action:** make FU-1 record `CCSESSION_PERMISSIONS` and the session's real mode, and decide explicitly (owner) whether the watcher host sets `default`; put the decision beside Q1.

### 5.2 Who owns the launched session

### 5.4 Restart and double-launch

- **At-most-once is per issue, per intact single store.** `pending` is saved durably before the spawn (`issue-watcher.md:524-534`). A crash after the spawn leaves `pending`, which the next cycle's sweep marks `abandoned(pending_orphan)` and never relaunches (T-8, C3/C4): a session may be running while the record says abandoned. If the claim comment was posted, the marker later promotes the entry to `claimed` (T-10).
- **A lost reply is `unknown`, not a retry.** Timeout at 120 s, non-zero exit, non-JSON or no id all give `unknown` (`launch.py:326-349`); the entry leaves only through a marker or `reset N --forfeit-guarantee` (T-13, `issue-watcher.md:471-472,491`). Orca's help is explicit: "re-issue the same command from the same directory on the same host with --retry-launch <operationId>. Never retry as a fresh launch" (re-read). `status --json` prints that retry argv only for entries that have an `operation_id` (`cycle.py:1308`).
- **New failure mode from the assumed shape.** `OPERATION_ID_PATHS` (`launch.py:39-45`) is a guess pinned by four `_assumed_shape` fixtures. If the real success reply carries the id elsewhere, every correct launch classifies `unknown` / `no_operation_id`, has no id for a retry command, counts toward the day cap and stays `unknown` until a marker appears. That is a real outcome of running FU-1 on an unverified shape, not a theoretical one, and `reset --forfeit-guarantee` would then permit a second launch of an issue whose first session is alive.
- **Documented residual risks:** R11 restored backup, R12 two stores on one login ("one enabled workspace per login"), R14 a hand claim during a launch (`issue-watcher-setup.md:641-644`). None has a mechanical guard.
- **The claim itself is mostly safe against a second agent (R1 concern narrowed, verified).** `cmd_launch` returns `already_launched` when the issue worktree's `worktree.json` record or its mirror holds a `launch` entry (`orca_worktree.py:1689-1707`; `claim.md:120`), and re-claiming is idempotent (`claim.md:43`, comments edited via markers `:87-92`). Residual: if `issue-<N>` or the untracked `.dev/issues/` data is removed, a re-claim can start a new agent. A claim whose Wave 8 is refused (`W-ENFORCEMENT-ABSENT`, `claim.md:124-126`) still posts its comments and still leaves the marker, so the watcher records `claimed` while no second agent exists (V2 W-15; aligned but opaque).
- **Action:** FU-1 must show the real operation-id path before the cron entry is enabled (already the gate); the runbook should say that `reset --forfeit-guarantee` on an `unknown` entry requires first checking Orca for a live session in the configured worktree.
